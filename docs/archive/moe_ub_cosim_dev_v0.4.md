2026-10-06 用户明确收窄本版范围：不新增多 TP 能力或相应验收。选路增量针对原生 STORE/LOAD 的逐包选路；既有 WRITE/RTP 保留为兼容基线。下文按此要求执行。

## 1. 基线与继续适用的要求

主仓基线为 `749c8c55fce4e5199888b63b3ae56cf55d7d92ef`，
ns-3-UB 基线为 `a9539ddff9c8713975a50901f922c250cfcf8585`。
实现应从锁定依赖出发，必要的依赖修改按[开发维护说明](../development.md)逐层保存。
现行[系统架构](../architecture.md)、[后端参考](../../backend/README.md)和[模型依据](../model_validation.md)继续适用，以下仅规定增量。

所有操作继续共享唯一的 ns-3 时间及持续存在的网络。
计算依赖由本次真实完成事件推进，记录过程不得改变包、路径、优先级或执行顺序。
同芯片不同 die 的交付继续采用本地事件；die 指芯片内的计算裸片，不新增芯片内网络。

通用实现放入现有 Python、C++ 后端及必要的依赖模块，不在研究脚本中修改调度器、队列或回调。
不得根据实验名称、某个操作身份或预期结果设置隐藏分支。
真实输入来源、模型近似、功能验证与硬件精度分别说明，不由本版功能验收替代硬件校准。

## 2. 当前缺口与实现起点

| 能力 | 基线事实 | 本版要求 |
|---|---|---|
| 原生逐包选路 | 主仓尚未接入原生 STORE/LOAD；既有 WRITE/RTP 固定关闭多 TP 和 packet spray | 配置原生路径的逐包喷洒并核对源端、交换出口及平面范围；不新增多 TP |
| 原生内存操作 | 上游已有 STORE/LOAD，主仓仅提交 WRITE/RTP | 接入操作、依赖、完成、字节来源和资源退出 |
| 端侧成本与出口变化 | 已有计算/打包耗时，结构化网络配置不能在重放中调整 | 支持通用参数与物理出口服务区间，明确可重放边界 |
| 等待统计 | 已有 FIFO 事件，出口缓存观测还包含处理中数据 | 定义准确的统计对象，输出时间均值和峰值 |
| 保存与采样 | 现有离线采样依赖逐包事件，零窗口按无发包判定 | 分开聚合与详细记录，显式声明可执行的采样操作 |

具体代码依据如下，链接固定于本版起点，后续实现不能只修改文档消除缺口。

- [配置固定值与操作配置校验][base-config]限制当前 WRITE/RTP 及选路设置。
- [WRITE 适配器][base-write]固定提交 `URMA_WRITE`，并依赖目标写入和 URMA 事务对象 Jetty 的清理回调。
- [上游操作分支][ub-app]将 URMA 的 RTP/CTP 选择与原生 `MEM_STORE`、`MEM_LOAD` 分开。
- [端口观测][base-observation]解析 RTP WRITE，保存发送事件、FIFO 审计和业务字节来源。
- [现有重放][base-replay]与[离线采样][base-slice]分别负责重新执行依赖图和重新聚合历史事件。

## 3. 参数与有效配置

新增设置必须进入版本化结构化输入，经过合法性检查，随运行保存解析后的有效值和来源。
具体字段拼写由实现统一确定，同一含义不得在用户配置、计划与后端中使用不一致的单位或默认值。
若改变旧格式的含义，应升级对应输入格式版本；文档版本号不自动成为输入版本号。

| 参数对象 | 必须说明并检查的内容 |
|---|---|
| 事务操作 | 发起方、数据拥有者、消费者、STORE/LOAD 或既有 WRITE、业务字节数、供数依赖 |
| 路由方式 | 源出口候选、交换出口候选、是否最短路径、原生逐包喷洒、随机种子和运行号；多 TP 不在本版范围 |
| 原生请求 | 请求/响应粒度、有效线程数、允许的未完成请求数、合法长度及短尾处理 |
| 端侧准备 | 所属阶段、计费单位、作用对象、非负耗时、与已有成本的覆盖或相加关系 |
| 出口服务 | 物理节点与出口、区间起止整数纳秒、整数 bit/s 发送速率、区间外基准值 |
| 记录策略 | 观测对象、窗口、统计项、是否保留详细事件、真值输出范围及资源预算 |

配置检查必须在业务激活前完成，拒绝未知字段、无效端口、非法组合和不支持的操作。
请求粒度若会按原生模型对齐，应校验并输出最终有效值，不能只记录用户填写的值。
有效配置应从实际对象回读；设置被忽略、落到另一层或被默认值覆盖时不能报告成功。
不同事务操作、不同路由方式不必形成全部组合，支持矩阵应列清已验收组合并拒绝其余组合。

## 4. 原生逐包选路

原生 STORE/LOAD 通过 `UbLdstApi` 生成请求与响应，直接调用选路和物理出口，不经过 URMA/RTP 的 TP 通道绑定。
本版开放其 `UsePacketSpray` 包级选路设置，依据为[原生请求路径][ub-ldst]和[逐包选路][ub-routing]。
`EnableMultiPath` 属于另一条 URMA/RTP 路径；本版不新增或验收多 TP，现有参考路径保持原配置。

必须区分源端物理出口选择与交换机等价出口选择。
每种支持方式应声明候选路径集合及实际分散粒度，保留拓扑、平面和物理端口的对应。
源出口与交换出口分别使用实际可达候选；开启喷洒不自动意味着跨所有平面。
需要跨平面时，应通过原生可用路径实现，并以小场景请求与响应的包路径记录证明实际行为。

优先复用上游包级路由及乱序处理，不能用预先均分端口字节或固定发包时刻替代。
发包与选路使用声明的随机状态，不读取内部操作来源；观测开关不得消耗新的协议随机数。
路径发生时延差时，接收端仍按有效交付汇总完成，不能以某个最后发出包先到而提前释放依赖。

验收应包含原生固定选路与逐包喷洒的可区分对照，以及受控路径时延差。
核对实际源出口与交换出口、乱序后字节守恒、回调次数和后继计算时刻。
不同路径的包占比只用于核对实现行为，不预设有限样本必定完全均匀。

## 5. 原生 STORE 与 LOAD

本版应保留既有 URMA WRITE/RTP，并接入 ns-3-UB 原生 STORE、LOAD。
URMA 的传输模式改为 CTP 不算完成原生 LD/ST 接入。
通信模板负责逻辑贡献、数据布局与依赖，底层操作负责请求、响应和完成，两者分别记录。

| 操作 | 发起与供数 | 数据就绪 | 发起资源完成 |
|---|---|---|---|
| STORE | 数据拥有者发起，业务数据送往消费者 | 目标收到该操作全部有效数据后，才可释放消费者依赖 | 原生确认满足后，释放对应请求资源 |
| LOAD | 消费者发起读取，数据拥有者提供响应数据 | 消费者收到全部所需响应数据后，才可继续使用结果 | 按原生请求完成条件释放，不能用发出读取请求代替 |

操作描述必须显式区分数据方向和请求方向，不能沿用 WRITE 的源/目的含义机械交换编号。
LOAD 的供数就绪与读取发起关系必须由模板中的明确依赖实现。
若模板通过跨 rank 通知确认供数就绪，该通知应执行真实通信，不由宿主调用制造零耗时通知。
不能在生产计算尚未完成时返回可供消费的数据，也不能读取历史完成时刻调度请求。

应复用[原生请求路径][ub-ldst]和执行器的内存任务回调，补充联合路径所需的被动完成通知。
一次逻辑数据交付只产生规定的请求和响应；计算依赖、数据就绪、事务完成及资源释放分别处理。
回调重复、分段乱序、数据先到而消费者等待后登记时，不能重复计数或回溯执行时间。
分段累计应核对不可变的总字节数，全部有效字节到齐才确认数据就绪。

STORE 请求中的有效数据与 LOAD 响应中的有效数据分别归属到业务操作。
读取请求、响应头、确认及对齐开销分别核算，不能把整个 LOAD 响应报文都计为有效数据。
短尾、零业务但有模板状态消息、跨多请求拆分必须有明确处理；不接受的长度在提交前拒绝。
新增协议解析和来源通知应复用端口计数与存储，不依赖新建 Packet 继承另一个包的 UID。

线程和未完成请求限额应按配置真正生效，不能保留[原生入口][ub-app]固定两个线程作为隐含约束。
任务、分段、原生线上编号的映射应有容量与复用规则，检验编号边界及在途请求互不混淆。
清理应覆盖线程队列、未完成计数、任务映射和观测来源，不能直接套用 WRITE 的 Jetty 清理。
网络退出判定须包含这些状态；只有所需依赖、回调与物理网络均已退出，才报告运行完成。

至少交付一个小型 MoE 模板输入，使 STORE 和 LOAD 分别进入完整调度、执行、观测流程。
模板必须说明哪些行为来自 CANN 布局，哪些是本平台定义的原生操作映射。
不把原生包级路径通过写成完整 NPU 指令、地址系统或集合通信库的硬件等价实现。

## 6. 端侧准备成本与出口服务变化

端侧准备成本用于表示通信数据准备及提交前处理，应优先复用和扩展现有计算、打包阶段的参数。
参数明确作用于哪类阶段、哪个 rank 及每次调用的计费单位，最终转换为非负整数纳秒。
已由计算或打包耗时配置包含的成本不能再次叠加；额外成本必须单独说明并且只发生一次。
成本变化应改变对应节点的实际完成及后继提交时刻，不得修改输出时间戳来模拟影响。

出口服务变化按物理节点和有向出口指定，与业务操作身份无关。
本版应支持半开时间区间 `[start_ns, end_ns)` 内的正发送速率覆盖，到期恢复配置的基准速率。
同一出口区间不得重叠；结束早于开始、越出声明执行范围或速率非正时，应在启动前拒绝。
一条双向链路的两个方向分别指定，不能隐式同时修改对端。

已成功开始发送的包按开始时确定的速率完成，边界后新开始的包使用当时有效速率。
边界时刻与发包事件同刻时，行为必须由上述区间定义确定，不取决于事件恰好先插入队列。
包数、报文内容和队列积压保持真实演化，不按速率比例改写完成时刻或历史窗口。
应保存基准值、区间和实际生效检查，不用全局固定延迟冒充特定出口的服务变化。

变化可能延后整个运行的完成时间。执行预算和观测范围必须分别声明。
达到执行预算但任务未结束时记录未完成及原因，不能把截断结果标为正常完成。
执行完成但超出观测范围时，应标明观察不完整；完整运行对照必须扩大范围后重新采集。
软件不得在不告知配置变化的情况下自动延长预算或把未观察区间补成零。

## 7. 操作事件与等待字节统计

保留定位实际依赖所需的操作级事件，包括准备阶段、请求提交、数据就绪及资源完成。
事件由真实节点和回调产生，明确作用对象与时间含义，不用首包、末包代替整个操作起止。
公开新增字段应经过格式升级并说明采集假设；内部全局身份和真实依赖仍放在 `truth/` 或执行资料中。
不要求算法读取完整逐包时间线，也不把仿真可见信息写成硬件已经能够采集。

新增网络统计限定为必要的等待字节时间均值和峰值，按明确的出口与窗口输出。
实现前应在记录格式中确定具体对象：已经准备好等待出口调度的 VOQ，与已进入出口的 FIFO 分别命名。
VOQ 指按目标出口组织的等待队列；在链路上发送的包不属于等待字节。
字节量采用所选队列实际保存的包字节口径，说明包含的头部和控制消息，不与业务有效字节混用。
若统计包含进入 VOQ 前的处理中数据，字段必须直接表明这一范围，不能仍称纯 VOQ 长度。

[上游出口缓存 getter][ub-queue]包含 VOQ 和 ingress processing，两者不可仅按函数名解释。
现有 trace 对部分控制包更新不完整；新统计应覆盖其声明范围内的全部状态变化。
对于宣称的统计对象，开始状态、入队、转移、出队和窗口结束都必须参与正确结算。

时间均值按字节量的时间积分除以窗口实际长度计算，结果单位为字节；峰值为该窗口内的最大字节量。
实现可在状态变化时累计上一状态持续的面积，只保存当前状态、上次时刻、面积和峰值。
跨窗口的持续积压必须分配到各窗口，尾窗采用实际长度，时间转换沿用设备本地时钟定义。
没有发送但等待量非零的窗口仍应保存，不能继续把无发包窗口统一解释为全部统计为零。

小场景应覆盖非空初始观测、跨窗积压、发送间歇、边界变化、尾窗，以及均值和峰值的独立手算。
统计启停不得改变协议执行；额外状态只用于累计，不调用有副作用的调度函数查询结果。

## 8. 聚合保存、详细记录与再次采样

记录策略必须区分持续保存的窗口统计与选择性保存的详细执行资料。
聚合方式应直接从当前事件更新计数、积分与峰值，不先生成全量逐包 JSON 再丢弃。
详细方式用于受控的小场景或指定端口、区间，应有明确事件、空间和宿主资源预算。
已有详细首轮数据包仍应可读，新策略不能悄悄降低旧输入的采样能力。

评价所需的操作到端口窗口对应可按声明的应用消息类别，在执行时聚合到 `truth/`。
业务数据与应用元数据分别保存；模板应明确区分附随元数据、计数发布、完成标志等实际消息类别。
纯应用状态消息即使业务字节为零，也应在选择保留该类别时具有来自实际传输的操作、端口与窗口对应。
不能从同窗元数据总量倒推操作来源，也不能把协议确认自动作为应用状态消息；类别登记不得改变执行。
只保留这种分类窗口真值时，不能宣称仍保存完整逐包来源；清单应声明保留类别、范围和预算。
协议必要的在途身份与评价用记录分别管理，关闭详细保存不等于删除协议运行所需状态。
公开观测不包含操作来源、真实时钟变换或用于精确匹配的内部标识。

| 保存的信息 | 后续允许的操作 |
|---|---|
| 原始发送事件及相应来源 | 在记录范围内按已有能力重新分窗；来源关闭时不能补出真值 |
| 基础窗口的计数、面积和峰值 | 边界对齐地合并窗口，计数与面积求和、峰值取最大 |
| 只有窗口聚合，没有状态变化记录 | 不允许任意移动边界、改变漂移、细分窗口或恢复逐包顺序 |
| 未记录的端口、区间或统计项 | 必须重新执行相应仿真，不能通过默认零值生成 |

需要任意边界的等待统计时，只有发送事件仍不够，还须保留所统计对象的状态变化与初始状态。
`slice inspect` 应显示保存类型和可用范围；`sample` 在生成输出前检查能否满足请求。
不支持的采样应明确报错，不能插值伪装精确结果；不同保存方式的输出标明各自的有效范围。
记录选择应支持限定端口和时间范围，避免要求全网所有端口始终按最细周期导出。

新增统计应单独核算常驻状态、输出量和执行开销。以同一小型输入和随机配置，比较开启与关闭新增统计时的执行结果、宿主耗时、峰值 RSS 及产物字节；RSS 表示进程驻留内存。估算较大范围时，按对象数、每窗字节量和窗口数计算密集输出量，不能只用计数器个数宣称低开销。对实际硬件尚未确认的采集接口，只说明所需状态与读出条件，不把仿真测量当作硬件开销。

## 9. 公开流程与重放边界

新能力须通过已有 `moe-ub run`、`slice`、`sample`、`replay`、`validate` 流程交付。
命令和配置需要调整时同步帮助与用户指南；本规范不预先声明尚未实现的新命令。
独立小例应能从新输出目录运行，不依赖目标数据下载、历史日志或临时脚本。

重放仍从新网络的完整首轮图开始，由当前网络事件推进，不能照历史包时刻发包。
结构化网络配置应支持经过校验的出口服务区间调整，保存原配置摘要及实际覆盖值。
允许修改的其他网络设置应逐项列明，不能通过关闭旧校验接受任意后端属性。

| 修改 | 要求 |
|---|---|
| 出口速率及其区间 | 不改变图语义时可在重放中覆盖，重新执行协议并采集输出 |
| 路径或喷洒配置 | 仅在端点、任务和依赖不变且该组合已验证时允许覆盖 |
| STORE/LOAD、通信模板、贡献或消息拆分 | 重新生成图，不能在旧图里仅替换操作枚举 |
| 已编入图的准备成本、计算成本 | 重新生成相应图，不能保留旧节点耗时而只改运行标签 |
| 观测窗口、记录范围 | 重新执行或满足第 8 节的已有记录条件，另核对完成覆盖范围 |

输出清单应区分完整执行与完整观测，并能拒绝拿范围不完整的产物充当完整运行结果。
原始执行、重放和导出分别记录是否成功，不把文件摘要检查视为协议等价证明。

## 10. 验收与文档交付

各能力先通过独立小用例，再组合到小型 MoE 场景，最后完成代表性的完整首轮验证。
测试输入放入 `fixtures/`，检查程序放入 `tests/`；研究配置与分析不成为平台功能测试的依赖。
实现中发现错误时，应形成最小复现并修复通用路径，不依赖完整场景反复定位。

| 验收项 | 最低证据 |
|---|---|
| 路由和喷洒 | 实际分散范围、时延差与乱序、独立字节核对、回调唯一性 |
| STORE/LOAD | 请求与业务方向、供数依赖、完整有效交付、短尾和并发、状态回收 |
| 标识与资源 | 小输入检查编号边界、连续提交、在途隔离，正常结束时无悬挂资源 |
| 准备成本 | 只计一次，未改动的成本不变，实际提交和后继执行随参数变化 |
| 出口服务区间 | 开始、恢复及同刻边界，两个方向互不误改，在途包遵循既定规则 |
| 统计与保存 | 独立积分/峰值、无发包但非零等待、零业务状态消息的分类来源、记录启停不影响执行、预算拒绝 |
| 用户流程 | 新运行、保存、允许的采样、后端重放、公开结果校验及不支持操作拒绝 |
| 兼容性 | 既有 WRITE/RTP 小例及已保存详细数据的读取与必要回归 |

最终完整首轮应覆盖本版选定的原生操作与逐包喷洒组合，明确使用的参数和近似。
该步骤用于确认实际规模上的执行、记录及资源约束，不要求每种参数组合都做完整规模验收。
完整 64 轮服务不作为本版完成门槛；所有重型执行仍需明确预算，失败不自动提额重跑。
平台验收不依赖某项研究取得正面结论。

完成时更新架构、后端参考、模型依据、记录格式和用户指南中各自负责的当前行为。
必要测试证据留在对应 fixture，运行原始资料留在登记的输出目录，当前任务只链接结果。
本文保留要求和依据，不累加命令清单、实验结果或实现日记。
