写作时先给对象和用途，再给必要概念与操作。专业名、schema 字段和命令保留准确拼写，首次出现时解释；例如直接写“输入格式与约束”“保存首轮任务图”“发送资源释放”，不要用没有定义的“合同”“切片闭环”“账本回收”代替。长篇过程记录保留在 Git 历史或运行日志中，当前文档保存结论、原因和证据入口。

文档整理不改变技术定义。原方案与现行说明的对应关系见设计档案；发现实现偏离已批准要求时，先说明影响，再按明确任务修复或提出方案修订。独立研究材料 `traffic_mapping_v0.1.md` 不在仓库中；需要调整其研究定义时应取得原件，不能凭摘要补写。

## 目录与产物

| 路径 | 内容 |
|---|---|
| `python/moe_ub_cosim/` | 命令入口、服务调度、计划生成与数据导出 |
| `backend/` | C++ 联合后端、计划读取与 UB 适配 |
| `examples/` | 普通用户可复制修改的小型运行输入 |
| `tests/`、`fixtures/` | 自动检查，以及版本化测试输入、预期和证据摘要 |
| `experiments/` | 独立研究的设计、配置组合、分析和评价代码 |
| `scripts/` | 依赖检查、维护和专用资源测量程序 |
| `third_party/` | 固定版本的外部依赖 |
| `data/`、`runs/`、`build/` | 本地来源数据、实验结果和编译产物，不提交 Git |

不预建与任务无关的空模块或占位测试。虚拟环境、下载缓存、凭证和本机私有配置不提交。重要实验结果另行备份；忽略规则不表示可以删除。子模块保留各自的许可证和忽略规则，不重新格式化整个上游，不用宽泛排除规则隐藏源码改动。

## 平台、测试与实验

平台模块负责通用输入、执行行为和记录语义；`tests/` 与 `fixtures/` 验证这些行为是否正确；`experiments/` 使用已验证的能力回答具体研究问题。平台验收不以研究方法获得正收益为条件，实验也不承担仿真器功能实现。

实验只调用公开 CLI 或稳定的读取接口，平台不反向依赖实验。已有功能 fixture、测试辅助函数及阶段资源测量程序保持原用途；正式实验使用自己的版本化配置。需要通用场景生成或执行能力时，在平台模块中交付，再由实验调用。绘图与统计依赖按需放入实验环境，不自动成为平台基础依赖。

实验可在自己的目录维护分析和指标计算的小型检查，不把研究收益设为平台回归断言。发现平台缺陷时，提炼最小输入并补相应功能检查；平台修复与实验修改分别提交，重新生成受影响结果。比较采用明确的平台及依赖提交，不混用行为不同的版本。

大型输入和结果存于 `data/`、`runs/`；实验配置、生成或获取方法及必要摘要保存在实验目录。输入包须说明来源、版本和校验方法，不能只引用某台旧机器的路径。沿用平台运行清单记录有效配置、版本、预算与产物摘要，实验仅补条件与运行的对应关系及分析结果。结果说明在取得实际结果后编写，执行日志不追加到设计文档。

## 性能现象核查

实验执行者同时负责检查现象的机制依据。一次运行正常结束、统计一致或平台测试通过，只能支持相应执行事实，不能自动证明现象来自真实系统，也不能代替研究价值判断。先用工作量、必要依赖和简单服务量估算解释现象，再指出仍需要验证的额外等待；不要把模型定义能够直接推出的结果当成新发现。

某项配置成为疑似瓶颈时，主动追踪代码默认值、输入覆盖、生效对象、参数作用范围及占用/释放事件，区分测试便利设置、参考假设和源码或硬件依据。仿真对象与硬件实体的关系应明确，不能按名称或默认数字直接对应。已经接受且无新反证的输入和成本基线不反复重查；核查集中在会改变当前结论的机制。

对照前列出少量竞争解释，写明各自预期的事实、什么结果会削弱解释，以及为何所选对照能够区分它们。先核对参数是否同时改变请求数量、字节拆分、消息顺序、资源总量、释放条件或选路；一个字段变化不等于一个作用因素变化。对照应由实际执行推进，未能保持的条件单独解释，不以重复运行确认同一个预期关系代替机制判别。

明显等待应沿实际前驱和资源占用者追踪到允许继续的事件。缺少事实时，先查已有原始记录、实际队列和回调，再增加有界且不扰动执行的记录或最小测试。发送前等待可能受此前传输及确认反馈影响；仅看当前包的路径不能排除网络作用。累计等待、相关性、某条被选中的前驱链与可消除的业务损失分别说明，保留并列依赖和未解释部分，不重复计时。

已授权范围内的源码核对、局部重分析、小型测试和必要补采应连续自主完成。若结果否定原解释，应按证据调整后续检查，而不是继续调参保住现象；也不能在仍有可执行的小核查时只写未知并把问题全部留给使用者。确因权限、资料、预算或实质性范围扩张受阻时，记录已查内容、已排除解释和最小缺项，不通过猜测补齐或自动扩大任务。

候选去留以机制可信、影响有意义及已有信息是否足够为依据，不按阶段编号自动进入算法开发。需要新增测量时说明它消除哪项具体歧义，认真使用已有工作量、时序和拓扑作为基线。负面结果、模型缺陷和没有信息增量均应正常收尾；不能削弱基线或制造热点来维持研究必要性。具体检查和结论写入所属实验文档，进度仍只维护在当前任务页。

## 固定依赖与子模块

主仓库只直接包含 `third_party/LLMServingSim` 和 `third_party/ns-3-ub` 两个子模块。ASTRA-sim 由 LLMServingSim 固定，Chakra 由 ASTRA-sim 固定。每个子模块是独立 Git 仓库，其地址和精确提交由直接父仓库的 `.gitmodules` 与 gitlink 记录。

| 依赖 | 直接父仓库 | 维护方式 |
|---|---|---|
| LLMServingSim | 主仓库 | `baoy21/LLMServingSim` 的 `cosim` 分支保存项目修改 |
| ns-3-UB | 主仓库 | `baoy21/ns-3-ub` 的 `cosim` 分支保存项目修改 |
| ASTRA-sim | LLMServingSim | `baoy21/astra-sim` 的 `cosim` 分支保存项目修改 |
| Chakra、fmt、spdlog | ASTRA-sim | 原上游固定提交 |
| analytical 内存与网络后端、csg-htsim、原生 ns-3 后端 | ASTRA-sim | 原上游固定提交 |
| googletest、yaml-cpp | analytical 网络后端 | 原上游固定提交 |
| ns-3-ub-tools | ns-3-UB | GitCode 配套仓库固定提交 |

[锁文件](../deps.lock.json)显式登记 11 项依赖；检查脚本还递归检查 googletest、yaml-cpp，共 13 项。`baseline_commit` 是最初审阅的上游基线，`checkout_commit` 是当前使用的提交。项目补丁可以更新后者，上游升级需要独立决定。

初始化使用 `git submodule update --init --recursive`，不使用 `--remote`。新检出的子模块通常处于固定提交的 detached HEAD，也不会继承开发机的工作分支和 `upstream` 配置。拉取失败时保留具体路径、提交和错误，不能换到另一个版本来绕过。

修改依赖前确认任务允许、工作区状态清楚，并从锁定提交建立任务分支。维护仓库通常用 `origin` 指向项目可写仓库、`upstream` 指向原来源；只读依赖不需要为了命名统一修改远端。来源改变时一起更新父仓库 `.gitmodules` 和锁文件的 `clone_url`，`upstream_url` 继续记录原始来源。

保存与发布均由内向外进行。例如修改 ASTRA-sim，先提交其源码与测试，再提交 LLMServingSim 的 ASTRA gitlink，最后提交主仓库的 LLMServingSim gitlink、锁文件及相关改动。父仓库只能引用已经保存且可从记录远端取回的子提交；主仓库提交不会自动保存子模块内部修改。Chakra 等更深依赖同样逐层处理。

联合程序只能链接 ns-3-UB 的一套 ns-3。ASTRA 的其他后端源码作为原生基线保留，不能与联合程序混用，也不能因为目录里有其他后端就删除它们。

## 选择与记录检查

在完整、已初始化的检出中，`bash scripts/check_deps.sh` 检查锁文件、各仓库 HEAD、gitlink、来源和工作区状态。它不联网、不初始化、不切换版本、不编译，也不删除文件。返回 0 只说明本次检查范围内一致；1 表示发现版本或状态问题；2 表示缺工具或输入错误使检查无法开始。它不能证明远端可访问、构建成功或模型准确。

按实际改动选择最小相关检查，随后运行受影响回归：

| 改动 | 应检查的内容 |
|---|---|
| 仅文档 | 差异与链接、命令对应的帮助或已有用例、技术说明迁移是否完整 |
| Python 输入、图生成或导出 | 对应单元检查、非法输入、字节或记录的独立核算 |
| 调度、后端与网络交互 | 小型实际联合执行、完成事件、因果反馈、资源退出及受影响回归 |
| 公共命令或安装流程 | 不继承旧构建和运行产物的小型完整用户流程 |
| 目标规模相关行为 | 先小场景，再在所需能力就绪后完成任务要求的最终规模检查 |

最小公开操作流程可参考 [check_user_workflow.py](../tests/integration/check_user_workflow.py)；首轮重放与基线的独立比较入口是 [check_slice_target.py](../tests/integration/check_slice_target.py)，其目标规模检查只在任务需要时运行。`moe-ub validate` 本身不能代替这个比较。

不要为文档修改重新构建或执行完整目标场景。代码实现中途也以小场景为主，完整 64 步服务不是 v0.3 当前收尾标准；已确认的最终范围见[首轮验收记录](../fixtures/m10_research_slice/README.md)。

运行记录包含实际命令、工作目录、输入及相关版本、退出状态、日志位置和必要资源峰值。完整命令与日志放在运行目录；Git 中保存用于复核的摘要与稳定检查程序。测试成功、输入真实性和硬件校准分别记录，不以新的结果直接覆盖旧预期，也不把失败检查点删去后只保留成功结论。

仿真明确限制宿主时间、进程内存与累计磁盘占用。失败时保留原因和已有产物，不自动提高预算或重跑。只清理本任务明确登记、能够再生的临时数据，保留来源、必要结果和清理说明。系统安装、sudo、全局配置及大型下载按已有授权执行。

## 任务与交接

用户确认目标后，代码助手负责维护 `tasks/current.md`。任务页写目标、范围、状态、检查方式和结果入口；执行中的中间进度可替换更新，不逐段追加整份日记。`pending`、`in_progress`、`blocked`、`completed` 分别表示未开始、执行中、受阻、验收完成，页首与结果必须一致。

同一阶段包含平台和实验任务时，在该页分别记录状态与依赖，明确当前执行哪一项；阶段进度只在这一处维护。规范保存要求，实验说明保存研究方法，二者不重复维护进度表。交接材料完成不表示代码或实验已经完成；未实现的接口不得在用户指南中写为可用。

用户已持续授权任务完成且验证通过后创建本地提交。只提交本任务改动，不覆盖已有工作；发布采用当前任务或会话中的明确授权，没有授权时不推送。已经允许连续完成的内部步骤不再次等待确认，完成后停止于已确认目标，不自动启动后续候选事项。

提交标题沿用仓库的 `类型(可选范围): 动作与对象` 格式，例如 `feat(observation): ...`、`fix(backend): ...`、`docs: ...`、`experiment: ...`。平台功能与实验分别提交，标题应描述本次实际改动。历史提交摘要可能被配置和证据引用；修正旧标题会改变提交标识，不能为了统一格式自行改写历史。

切换任务前保存已完成工作；旧任务原文由 Git 历史保留，必要时在里程碑中加一行结果和证据链接。不要将一次性授权、旧机器环境或当前任务状态复制到长期维护规则中。并行工作明确文件责任，涉及子模块和构建时使用互不干扰的目录。

## 用户操作的维护要求

普通用户和 agent 使用相同的公开命令。可复用操作进入版本控制，通过配置修改实验条件；`runs/` 中的临时脚本不能成为必需步骤。新增接口同步维护帮助、输入格式、单位、默认值和覆盖顺序、路径解析、输出、预算及错误说明。

命令和文档未验证一致前不能标记交付完成。最小示例应独立于真实数据账户和历史产物；目标数据另行准备并说明来源。公开命令现有用法见用户指南，原始交付方案保存在设计档案中。许可证选择、改变仓库可见性和托管 CI 等工作仍按具体授权处理。
