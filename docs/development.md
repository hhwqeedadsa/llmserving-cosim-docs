# 开发管理说明

本文件补充 v0.2 的目录、Git 和文档维护约定，不改变技术范围与验收条件。开发环境为原生 Linux。当前任务进度见 `tasks/current.md`，已确认的环境、构建和仿真结果见 `environment.md`。

## 1. 每份文档各负责什么

| 文件 | 内容 | 更新条件 |
|---|---|---|
| `docs/moe_ub_cosim_dev_v0.2.md` | 系统行为、接口、模型边界、M0 至 M5 与测试要求 | 用户批准技术方案修订后更新 |
| `docs/development.md` | 目录、Git、子模块、文档和检查流程 | 用户批准开发管理规则调整后更新 |
| `AGENTS.md` | 每次任务必须执行的简短约束及阅读入口 | 开发规则变化时同步更新 |
| `docs/tasks/current.md` | 当前一个小步骤的目标、状态、范围、权限、验收和结果 | 开始新任务前确定范围，结束时同步更新状态和实际结果 |
| `docs/environment.md` | 实际确认的系统、工具、构建命令及环境问题 | 获得本地检查或运行证据后更新 |
| `README.md` | 已可用入口、当前状态与文档链接 | 相应入口实际可用或状态变化后更新 |
| `docs/bootstrap.md` | 本次远端仓库准备的记录 | 仅更正本次准备记录，不用它持续承载项目进度 |

从主仓库根目录启动代码助手，先读取当前任务，再读规范相关章节。技术规范决定某项功能应怎样执行，当前任务只决定本轮实现到哪里。发生冲突时先记录具体位置，不让代码助手自行变更研究定义或降低验收条件。

规范附录引用的 `traffic_mapping_v0.1.md` 是单独的研究定义材料，本次最小仓库没有复制该文件或会议材料。M0 不依赖它执行；后续涉及关联语义的独立调整时，应先取得原文件，不凭规范摘要补写原文。

这里只展开主要依赖，其他上游递归子模块按各自父仓库记录保留。`check_deps.py` 是 Shell 入口的标准库实现，不是仿真前端。

M1 再创建最小 `backend/` 和相应测试；M2 再增加 `python/moe_ub_cosim/`、通信生成和四 rank 功能输入。后续目录沿用 v0.2 第 11.2 节，不预先建立全部空类、配置或占位测试。

主仓库保存自研代码、规范、小型人工构造输入和可检查的预期结果。`build/`、`runs/`、`data/`、虚拟环境和下载缓存不提交 Git。重要实验的原始结果应另行备份，忽略规则不代表可以删除。凭证和本机私有配置不得提交。

根目录的忽略和换行规则只管理本仓库。子模块生成文件按其已有规则处理；确需增加本机排除项时记录具体目录，不用宽泛排除隐藏源码改动，也不重新格式化整个上游。

## 3. 两个直接子模块与递归版本

主仓库只直接记录 `third_party/LLMServingSim` 和 `third_party/ns-3-ub`。ASTRA 由 LLMServingSim 的 gitlink 固定，Chakra 由 ASTRA 的 gitlink 固定。不在主仓库另外复制一份 ASTRA 或 Chakra。

`deps.lock.json` 显式记录四个核心组件和准备时从父仓库读到的辅助 gitlink。更深层依赖继续由固定父提交中的 gitlink 决定。`repo-local-check` 已完成 13 个依赖仓库的递归初始化与静态检查，包括 GitCode 上的 UB 配套工具；这只确认本次源码获取和检出状态，不证明构建或仿真可用。锁文件中的准备期检查描述保留，后续实际运行结果写入 `environment.md`。

初始化命令为：

```bash
git submodule update --init --recursive
```

该命令在本地使用，取回父仓库记录的版本，不使用 `--remote`。失败时保存具体路径、提交和错误，不换到其他分支。不要假定所有远端都支持只取某个提交的浅克隆。

原生基线可能保留 ASTRA 的其他网络后端源代码。联合程序只链接 ns-3-UB 一套 ns-3；不能以“目录内存在两套源代码”为由删除上游基线，也不能将两套 ns-3 一起链接。

## 4. 上游修改怎样保存

M0 保持上游源码不变，先分别检查环境、命令和依赖。若必须修补上游错误，先记录原因并申请一个明确的修复任务，不将修复与功能开发或依赖升级混在一起。

开始修改某个依赖时，为它选择经用户授权的维护仓库和任务分支。已有 `baoy21/ns-3-ub` 可以在获准后使用项目分支，不要求再建一份同名 fork。没有写入权限的仓库则需获准的 fork 或维护副本。不要因为连接显示可写就修改依赖默认分支。

维护阶段约定 `upstream` 指原来源，`origin` 指项目可写维护仓库，`cosim` 保存已检查的项目修改，短期 `task/...` 分支保存本轮工作。M0 直接从上游克隆时，`origin` 仍可以是原上游；此时只读，不为了命名统一提前改变远端。

子模块通常检出为 detached HEAD，修改前先从锁定提交建立分支。远端来源改变时，父仓库 `.gitmodules` 与锁文件中的 `clone_url` 一起更新；只改本机 remote 不会让其他克隆知道新来源。`upstream_url` 继续记录原始来源。

一次 ASTRA 修改的保存顺序为：先在 ASTRA 提交源码与测试，再在 LLMServingSim 提交 ASTRA gitlink，最后在主仓库提交 LLMServingSim gitlink、锁文件和本项目相关测试。修改 UB 时，先提交 UB，再更新主仓库。

发布时同样由内向外推送。父仓库引用的子提交必须能从记录的维护远端取回。工作区中的未提交源码不能作为已保存的可复现版本，主仓库的一次普通提交也不会自动保存子仓库内部修改。

锁文件中的 `baseline_commit` 表示最初审阅的上游基线，`checkout_commit` 表示本项目目前采用的提交。获准的项目补丁更新后者并记录补丁提交；升级上游基线另行决定。不要把修补当前版本与跟随上游最新版混为一件事。

## 5. 当前任务与提交节奏

初期一个代码助手会话负责写入，另一会话若参与则先只审阅。主仓库 `main` 保存已经检查的步骤；开发时按需创建一个 `task/...` 分支，不提前建立全部阶段分支。嵌套子模块修改仍按上一节逐层保存。

代码助手每次只完成 `current.md` 的一个小步骤。任务记录说明允许的读写、是否允许初始化依赖、是否允许运行，以及本地提交与推送的权限。没有授权的动作不由“完成任务”这一目标自动推导出来。

2026-09-27 用户给出的持续授权为：每个任务完成且验证通过后，代码助手自行整理记录并本地提交，不推送；下一项任务仍由用户确认。提交前检查完整差异与工作区，只提交本任务相关文件，子模块改动仍按由内向外的顺序保存。当前任务或用户后续指令有更严格限制时按其执行。系统软件安装、全局配置变更等权限不因这项提交授权而扩大。

任务结束后记录实际修改、命令、退出状态、日志位置和剩余问题，将状态与结果同步，再保存本地提交。`pending` 表示尚未开始，`in_progress` 表示执行中，`blocked` 表示存在需解决的阻塞，`completed` 表示本步骤验收已通过；不能让页首状态与结果段互相矛盾。

用户负责确认下一项任务目标及额外限制，代码助手负责维护任务文件和交接。切换时先提交已完成且验证通过的旧任务记录，再替换 `current.md` 的目标与范围，并提交新的任务说明。旧记录保留在 Git 历史中；必要时单独归档简短阶段报告，不建立第二套重复进度表。只要求准备或切换任务时，将新任务置为 `pending` 并写明等待执行确认；用户明确要求开始或执行后，按已确定范围工作，不重复询问已有授权。

有明确并行需求后再使用独立完整克隆，并分别管理子模块与构建目录；初期不依赖多个会话共享同一嵌套子模块工作目录。

## 6. 依赖检查脚本的范围

入口为 `bash scripts/check_deps.sh`，调用同目录标准库 Python 脚本。需要 Bash、Git 和 Python 3，具体版本在本地环境记录中确认。该脚本已在 `repo-local-check` 中经审阅并执行，退出 0；命令与日志位置见 `environment.md`。

脚本读取锁文件、各仓库当前 HEAD、索引中的 gitlink、`.gitmodules` 和工作区状态。先检查显式登记的依赖，再递归检查实际存在的其他 gitlink。它会报告未初始化、版本不符、子模块指针已暂存但尚未提交、来源记录不一致，以及依赖源码的未提交修改。

脚本不联网、不执行初始化、不切换分支、不更新锁文件、不编译、不删除文件。主仓库普通文件的修改作为警告输出，便于记录任务进度；依赖内部修改或 gitlink 不一致使检查失败。忽略目录中的产物不属于源码清洁度检查。

返回 0 表示本次检查范围内的版本与工作区一致；返回 1 表示发现依赖或状态问题；返回 2 表示参数、锁文件格式、缺少工具等使检查无法开始。脚本无法证明远端提交仍可访问、环境能编译或模型真实，也不检查联合程序的链接结果。

若脚本本身有问题，先保存错误和最小原因，再按获准任务修改脚本。不要直接修改依赖版本让检查变绿，也不要把“工具执行失败”写成“依赖通过”。

## 7. 环境与验证记录

当前目标是原生 Linux，不预设具体发行版、编译器版本或 GPU。先记录本机事实，再对照锁定源码建立环境。缺少系统依赖时报告需要的包与用途；安装、sudo 和全局配置变更先获授权。

M0.1 将 UB 原生样例和 LLMServingSim 原生样例分别完成，不要求起步就统一所有构建环境。M0.3 再决定联合核心库、链接边界和相关选项。只保存实际运行过的命令，不先写假设可用的整套构建脚本。

运行记录至少包含工作目录、输入、命令、相关提交、退出状态和输出路径。先运行最小相关检查，再运行受影响回归。仿真结果与参考值不同需要解释原因，不能直接把新结果覆盖成预期。

文档描述具体对象、动作和结果，分别说明已有代码、拟议修改、实际测试与未验证项。环境记录不包含凭证、主机敏感信息或未经授权的内部数据。对技术规范的必要变更单独提出，不在进度记录中悄悄改变接口。
