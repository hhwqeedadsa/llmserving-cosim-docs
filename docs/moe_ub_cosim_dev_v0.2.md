# MoE 推理服务与 UB 网络联合仿真开发指南

版本 v0.2  
修订日期 2026-09-27  
用途：指导开发者或代码助手逐步实现、联调和验收。

本框架根据推理请求生成计算和通信任务，在 UB 网络中执行这些任务，再记录各端点的通信操作与交换机端口流量。网络中的实际完成事件决定后续任务何时可以开始，也影响前端下一轮处理哪些请求。框架服务于 `traffic_mapping_v0.1.md` 定义的操作实例与端口时窗关联研究。[P1]

采用的路线保持为 **LLMServingSim 服务前端、其绑定的 ASTRA-sim/Chakra 执行层，以及 ns-3-UB 网络后端**。本版不引入 ServeGen、SimAI、AICB 或 SimCCL，不实现端网关联算法，也不纳入项目中的主动测量协议研究。

本次修订以 v0.1 和已确认的修改方案为依据。主要变化是单独规定通信库行为怎样建模，说明各类输入能决定什么，把最小观测与来源核验提前，并将开发计划拆成逐项通过测试的小步骤。依赖版本与首个通信模板保持不变。

**实现状态**：本文是一份开发约定。已有代码能力沿用此前对指定版本的审阅记录，本次没有升级依赖，也没有完成联合编译、运行或目标设备校准。文中拟新增的模块、消息、配置和测试均不表示已经实现。每项能力是否可用，以第 13 章相应阶段的实际测试结果为准。

## 0. 当前决定与开发起点

服务前端负责请求队列、批次和逻辑 KV Cache 容量。ASTRA-sim 负责计算与收发任务的依赖和资源占用。ns-3-UB 负责传输协议、分包、链路、交换机和流控。Chakra 用于保存执行图，即计算与收发任务以及它们之间的等待关系。

| 项目 | 本版决定 |
|---|---|
| 运行结构 | 一个 Python 服务前端和一个 C++ 联合后端；一次实验中的全部网络端点和交换机放在同一后端内 |
| 仿真时间 | 由 `ns3::Simulator` 推进；前端使用后端报告的绝对时间 |
| 前后端交换的数据 | 图文件保存本轮任务，JSONL 管道消息通知提交和完成；不逐包唤醒 Python |
| 通信表示 | 一次逻辑操作展开为有方向、有数据量、有依赖的发送和接收任务 |
| 首个通信模型 | `direct_rank_dedup_v1`，作为明确标注的参考模板 |
| 首个 UB 模式 | `URMA_WRITE` 与 RTP；其他模式在实现前拒绝配置 |
| 初始部署 | 一个 MoE 模型，静态专家放置，注意力 DP 与专家 EP，TP=1、PP=1 |
| 计算执行 | 根据固定耗时或计算 profile 模拟资源占用，不执行模型数值前向 |
| 研究输出 | 端侧操作记录、网侧聚合计数、独立真值、运行配置及验证结果 |
| `traffic.csv` | 保留为原生 UB 基线和调试导出，不作为长期框架的动态任务入口 |

**第一项开发工作是复现上游样例，第二项是执行一个计算任务和一对 UB 收发。** 这两项通过后，再生成一个 MoE 层，随后验证连续多轮执行、动态组批和共享网络。P/D 交接与真实模型数据在后续阶段加入。

正文描述各阶段最终需要遵守的接口，不要求在起步阶段实现全部字段和功能。开发者每次只实现当前阶段所需的部分，未完成的功能在配置检查时明确报错。第 13 章规定了每一步的输入、完成条件和下一步。

## 1. 目标、范围与术语

### 1.1 研究任务与框架职责

研究方法最终读取已有端侧操作记录和交换机端口计数，判断某次通信操作的数据是否经过某个端口的某个采样窗口。一次操作可以对应多个端口和窗口，同一窗口也可以包含多个操作。框架负责产生这些观测及独立核验真值，不预先规定操作一定具有可识别的流量特征。[P1]

为支持这一任务，框架需要根据请求与部署生成通信需求，让各次传输实际使用仿真中的链路和队列，并根据传输完成事件继续执行。不同设备的观测时间可带有偏移和漂移，但执行内部始终使用同一个仿真时间。

运行正确性与模型真实性分别验收。前者检查数据量、依赖、时间、资源和记录是否一致；后者检查通信方式、计算耗时和负载数据是否有目标系统依据。功能样例可以验证前者，不能单独证明后者。

### 1.2 本版规划的支持范围

第 13 章全部相关阶段完成后，框架应支持一个 MoE 模型、固定专家放置、文件请求流、连续组批、多层和多解码步骤。多个注意力实例可以组成一个专家通信组，也可以配置使用不同 NPU 的独立通信组，共享交换机与链路。P/D 分离和经过 UB 的 KV 交接在 M4 加入。

早期采用给定 KV 已就绪的解码场景。模型、请求和计算耗时均可使用小型功能样例，不必先部署真实大模型。这个场景仅模拟解码执行，不报告完整预填充或完整服务的首 Token 延迟。

暂不实现模型数值前向、动态专家迁移、动态精度选择、复杂推测解码、注意力与专家的独立设备部署、同一物理 NPU 上多个独立模型的抢占、跨机分布式仿真、P4 部署或自动根因诊断。TP、PP、复杂微批次交叠和共享 HBM 带宽争用也不在首版实现范围内。

一个 rank 对应一个模拟 NPU。每个 rank 同时只激活一张图，并且只有一份计算任务占用计算资源。图内通信可以与计算重叠，前提是执行依赖允许。独立通信组不共用 NPU，因此它们的同时执行不会隐含增加一张 NPU 的计算能力。

### 1.3 基础概念

**请求**表示一次推理服务输入。前端将可处理请求组成一个批次，记录每个请求当前的预填充范围或解码步骤。**实例**管理自己的请求队列和批次，不必拥有一份完整模型副本。

注意力采用数据并行时，不同实例处理不同请求；专家采用专家并行时，各专家分布在通信组的不同 rank 上。同一 NPU 可以承担本地请求的注意力计算，也可以处理其他 NPU 发来的专家输入。设备清单和通信组成员必须显式给出，不通过并行因子相乘推断。

**Dispatch**将 Token 的中间表示送到相应专家所在设备。**Combine**将专家结果送回原 Token 所在设备并完成模板规定的合并。二者是不同的逻辑操作，各自可以产生多条传输。

**Trace**在本文主要指专家选择记录。**计算 profile**指指定设备与输入形状下的计算耗时依据。**通信模板**规定逻辑操作怎样复制、分块、发送和等待。三者不能互相替代。

### 1.4 标识与对应对象

| 标识 | 含义 |
|---|---|
| `service_id` | 一个逻辑模型服务，可包含 P、D 角色和多个调度实例 |
| `instance_id` | 一个具有独立请求队列和批次状态的前端实例 |
| `rank_id` | 一名模拟执行参与者的编号，本版与 NPU 端点一一对应；不表示实际启动一个操作系统进程 |
| `group_id` | 显式给出成员的通信组 |
| `batch_id` | 某实例一次调度产生的批次，各请求的解码步骤可以不同 |
| `wave_id` | 同一 EP 组共同执行的一轮前向，连接各成员本轮批次；这是本项目的组织标识 |
| `operation_id` | 一次逻辑通信调用，由参与 rank 的本地调用组成 |
| `transfer_id` | 一次有方向的数据传输；分块后每个分块分别分配标识 |
| `ub_task_id` | UB 应用层任务号，与操作和传输编号分开 |
| `graph_id` | 一次提交的图集合编号，与 rank 和局部节点号共同定位任务 |
| `t_ns` | 全局绝对仿真时间，单位纳秒，用于执行与内部核验 |
| `local_time_ns` | 某设备导出的本地时钟值，不默认与其他设备对齐 |

专家到 rank 的放置、rank 到 UB 端点的连接属于已知配置。操作到传输的对应由生成器建立。操作到端口时窗的真实关系要从本次网络执行中记录，不能直接从前两种对应关系推定。

### 2.3 联合构建方式

主开发环境为原生 Linux。锁定 UB 场景文档给出的 Python 3.12 和 UB-only 构建方式是初始参考，M0 要在实际开发机验证。[S13]

联合后端作为 ns-3-UB 构建系统中的新可执行程序，链接 ASTRA 核心和固定 Chakra 的读取组件。进程内只链接 ns-3-UB 一套 ns-3，避免重复的同名类型和全局状态。

ASTRA 的 Workload、System 和计算资源管理保留；原 analytical/ns3 网络入口不编入联合程序。上游没有可直接使用的核心库构建目标时，新增明确列出源文件的目标，不将整个仓库一起编入。

C++ 标准、库版本和编译选项在 M0 以锁定源码及构建结果确定。M0 结束时需要保留可重复构建的环境记录、原生基线输出，以及联合程序实际使用的库清单。

## 3. 一轮请求怎样经过前端和后端

### 3.1 从当前批次到下一次调度

前端收到后端报告的当前时间和完成通知后，更新各请求进度，并把已经到达的请求放入队列。调度器为可以执行的实例选择批次。共享 EP 的成员需要同时给出本轮批次或零 Token 参与状态，前端据此建立本轮任务。

前端读取模型结构和专家选择，将专家编号映射到 rank。通信模板把 Dispatch、Combine 转成具体收发任务，同时加入计算任务与等待关系。这些任务先保存在 `ExecutionPlan` 中校验，再导出为每个 rank 的 Chakra 图文件。

后端装载图后，ASTRA 检查任务的前驱是否完成、资源是否可用。计算任务在仿真时间中占用相应资源；发送任务交给 UB 适配器。ns-3-UB 实际执行传输，并报告目标数据就绪和源端事务完成。ASTRA 据此继续后继任务。

本轮必要任务全部完成后，后端通知前端。前端再依据新的时间和请求队列组织下一轮。若另一独立组仍在传输，它的队列、在途数据和流控状态继续存在，新一轮通信将与它共同使用网络资源。

### 3.2 模块接收什么、交出什么

| 模块 | 输入 | 处理与输出 |
|---|---|---|
| LLMServingSim 服务前端 | 当前时间、完成通知、请求和逻辑内存状态 | 更新请求进度，为可执行实例选择本轮批次 |
| 路由读取与放置模块 | 请求的 Token/层索引、专家选择记录、放置表 | 给出源 rank、目标专家及目标 rank，并累计本地专家计算负载 |
| 通信生成模块 | 路由结果和通信模板 | 生成收发任务、字节量、分块、局部计算与依赖 |
| Chakra 导出模块 | 校验后的 `ExecutionPlan` | 写出固定 schema 的图文件及独立语义侧表 |
| ASTRA 执行层 | 各 rank 的执行图、完成回调 | 按依赖与资源限制启动计算和收发任务 |
| UB 适配器 | 收发请求和内部传输描述 | 提交 UB 任务，将网络事件通知到正确的执行节点 |
| ns-3-UB | UB 任务、拓扑、路由和协议配置 | 执行传输、排队和流控，产生本次完成事件及网络观测 |

`ExecutionPlan` 和 Chakra 文件只描述任务，不自行计算网络耗时。通信矩阵只表达端点间数据需求，不能代替操作身份、依赖和完成条件。

### 3.3 程序结构

```text
Python 前端进程
  请求文件、模型、部署、路由、计算耗时
  LLMServingSim 请求队列与调度
  路由读取、专家放置、通信任务生成
  ExecutionPlan 校验与 Chakra 图导出
                │
        JSONL 控制消息与图文件
                │
C++ 联合后端进程
  前后端交互驱动
  ASTRA 任务执行与资源管理
  UB 适配器与传输执行器
  UB 协议栈、端点、链路和交换机
  ns3::Simulator 事件队列
                │
  完成通知、端侧记录、端口计数、独立真值
```

路由读取器 `RouteProvider`、放置解析器 `PlacementResolver`、通信生成器 `CommunicationLowerer`、交互驱动 `CoSimDriver` 和 `UbNetworkAdapter` 是本项目拟新增模块。它们的名称用于对应代码职责，不表示上游已经有相同接口。

### 3.4 状态由谁维护

| 状态 | 唯一责任方 |
|---|---|
| 请求、批次、P/D 角色和逻辑 KV 容量 | Python 服务前端 |
| 专家选择、放置、操作级数据量和模板选择 | 前端路由与通信生成模块 |
| 执行依赖、计算占用、发送槽 | ASTRA 执行层 |
| 收发匹配、UB 任务关联、完成回调生命周期 | UB 适配器与传输执行器 |
| 分包、连接、重传、路径、端口队列和流控 | ns-3-UB |
| 全局执行时间 | `ns3::Simulator` |
| 观测口径、本地时钟变换 | 观测模块 |
| 操作与实际传输来源 | 独立真值模块 |

### 3.5 避免重复执行和重复计时

联合模式由 ASTRA 管理任务依赖，`UbTrafficGen` 不再管理同一批任务的阶段依赖。计算时间只进入计算节点，不能又写入 UB 任务延迟。

网络操作由通信生成模块展开一次，ASTRA 执行已有 SEND/RECV，不再将同一操作展开为 ALLTOALL。原集合通信模型仅保留在原生基线。

计算 profile 已包括的内存访问不再由另一内存模型重复计时。经过 UB 的 KV 交接使用实际传输时间，其前端解析通信耗时关闭。资源和计时的其他规则在相应章节定义，不在各模块各建一份副本。

## 4. 输入数据与中间表示

### 4.1 数据来源及其适用范围

| 输入 | 决定的内容 | 不能单独决定的内容 |
|---|---|---|
| 请求文件 | 到达时间、输入输出长度和服务归属 | 实际组批结果、专家选择和包发送时间 |
| 模型与部署配置 | 层结构、向量维度、专家数、Top-K、设备分工和放置 | 真实计算耗时和某轮拥塞情况 |
| 专家选择轨迹 | 指定请求、Token 和层选择了哪些专家 | 目标设备、通信库分块、UB 完成时间 |
| 计算耗时数据 | 指定设备和输入形状下的计算持续时间 | 本次网络等待以及所有硬件资源竞争 |
| 通信模板及依据 | 数据复制、聚合、分块、发送顺序和完成条件 | 未纳入模板的真实通信内核细节 |
| 网络场景配置 | 端点连接、交换拓扑、链路和协议参数 | 本次各操作实际经过端口的时间分布 |

输入来源分别记录。使用真实专家选择轨迹时，仍可能使用参考计算数据和参考通信模板；运行报告要分别说明，不能将整次实验统称为真实部署复现。

### 4.2 通用字段与单位

全局时间和持续时间使用非负整数纳秒，本地时钟值及偏移使用有符号整数纳秒，字节量使用无符号 64 位整数。接口需要缩窄类型时先检查上界。正耗时统一向上取整，原本为零的语义连接节点保持零。

规范化输入和输出都带 `schema_version`，未知主版本拒绝。文档版本 v0.2 不要求将原来的 `cosim/1`、`request/1` 或配置 schema 改成 2；只有接口出现不兼容变化时才升级对应 schema。

操作身份由请求上下文、组和调用次序生成。传输身份由操作及传输次序生成，不使用通信耗时、实际发送时间或特殊数据量编码操作身份。

### 4.3 请求、路由和放置

`RequestRecord` 的字段如下。

| 字段 | 要求 | 含义 |
|---|---|---|
| `request_id` | 必填 | 运行内唯一请求编号 |
| `service_id` | 必填 | 所属逻辑模型服务 |
| `arrival_ns` | 必填 | 请求进入服务的绝对仿真时间 |
| `input_tokens` | 必填 | 输入长度，正整数 |
| `output_tokens` | 必填 | 指定生成长度，正整数；本框架不预测结束 Token |
| `route_ref` | 使用轨迹时必填 | 专家选择记录的位置或索引 |

```json
{"schema_version":"request/1","request_id":"A","service_id":"moe0","arrival_ns":1500,"input_tokens":128,"output_tokens":16,"route_ref":"routes/A.jsonl"}
```

路由记录 `RouteChoice` 至少保存 `request_id, phase, token_index, layer_id, expert_ids`。`phase` 为 `prefill` 或 `decode`。解码索引从 0 开始，由数据适配器转换源文件的口径，不默认源数据第零项就是解码。前端还需保留源文件索引，以便核对。[P1]

`expert_ids` 按所选模型规则校验。本版不丢弃被选专家，不增加专家副本，不在网络重试时重新抽样。缺失记录默认报错；显式合成输入按合成数据记录。

放置表 `Placement` 提供 `(service_id, role, group_id, layer_id, expert_id) → rank_id`，并单独提供 `rank_id → ub_node_id`。专家可按层放置在不同 rank，但一次运行期间放置固定。

### 4.4 修改配置后哪些数据可以继续用

网络带宽、拓扑或路径变化通常不改变已经给定的专家选择，但会改变实际传输时序。专家放置或源请求到 rank 的分配变化时，重新生成端点间需求和计算负载，不沿用旧通信矩阵。

批次组成变化时，按各请求当前 Token 步骤重新组合路由，计算输入形状也相应更新。即使批次大小相同，成员不同、步骤不同或层号不同，也不能直接复用同一组路由结果。

更换模型结构、Top-K、路由规则，或启用会改变专家选择的精度与容量策略时，先检查旧轨迹是否仍适用。无法证明适用的轨迹不作为新配置的真实路由。更换计算设备或计算 dtype 时，同样检查计算 profile 的有效范围。

这些检查属于生成前的输入校验。前端发现不匹配后报错，并指出具体文件和字段，不在后台自动替换数据源。

### 4.5 执行中间表示 `ExecutionPlan`

前端先把本轮工作写成以下对象，校验后再导出 Chakra。`ExecutionPlan` 只保存与检查任务，不是另一套执行调度器。

| 对象 | 核心字段 |
|---|---|
| 图集合 | `graph_id, wave_id, instance_batches, rank_ids, ready_ns` |
| 逻辑操作 | `operation_id, kind, service_id, role, wave_id, layer_id, group_id, participants` |
| 计算节点 | `node_id, rank_id, duration_ns, resource_id, deps` |
| 发送节点 | `node_id, rank_id, transfer_id, deps` |
| 接收节点 | `node_id, rank_id, transfer_id, deps` |
| 传输描述 | `transfer_id, operation_id, src_rank, dst_rank, payload_bytes, chunk_index, transport_profile_id` |
| 来源侧表 | 请求、Token、专家与操作、传输之间的关系，仅供生成和核验 |

`deps` 仅引用同一 rank 的节点，跨 rank 等待由配对的 SEND/RECV 表达。数据量为零时不建立 UB 任务，本地计算和必要的完成关系仍然保留。

每个有向分块使用独立 `transfer_id`，运行内不复用。`payload_bytes` 包含模板规定的激活或结果数据，以及随数据传输的应用元数据。UB 报头、应答和重传由后端生成，不在这个字段重复增加。

`transport_profile_id` 指向统一的 UB 传输配置。它与通信模板版本不同，也不能按操作分配不同值来制造可识别流量。首个模板只使用一种默认传输配置。

### 4.6 Chakra 图文件与侧表

使用锁定的 `casys-kaist/chakra` schema 与读取器，为各 rank 生成 `<prefix>.<rank>.et`。[S7] 节点采用 COMP、COMM_SEND、COMM_RECV，以及经过该读取器测试的零时间依赖节点。可以直接通过 Python 编码 protobuf，不要求保留上游逐层文本中间格式。

SEND/RECV 传递 `comm_size, comm_src, comm_dst, comm_tag`，`comm_size` 表示字节量。锁定路径以 `UINT8` 发起传输。[S7] `comm_tag` 使用运行内唯一的正 31 位整数，并通过侧表对应到 `transfer_id`；达到上界时明确报错。

`comm_tag` 是模拟器内部匹配键，不作为新增字段写入业务报头。语义侧表使用 `(graph_id, rank_id, node_id)` 定位任务。不同图可以复用局部节点号，但不能复用仍可能收到回调的图或传输身份。

M1 可以直接生成一张小图验证接口；M2 再由 `ExecutionPlan` 自动导出相同结构。两种入口都使用同一 ASTRA 执行层和同一 UB 适配器。

## 5. 前端怎样生成本轮任务

### 5.1 选择请求并记录执行进度

前端在后端通知的时间接纳已经到达的请求。LLMServingSim 调度器为当前可执行实例选择批次，保留每个请求自己的预填充 Token 范围或解码步骤，不用一个批次步骤代替所有请求的进度。

共享 EP 的实例提交本轮批次后，前端按 `wave_id` 汇集成员。没有待处理 Token 的成员提交零业务负载状态，仍可承担接收其他成员数据的专家计算。全部成员均无工作且无待处理通信时，不生成空转的业务 wave。

汇集批次是前端生成任务的步骤，不自动增加网络屏障或同步包。目标通信实现确实有同步、填充或控制消息时，在第 6 章的模板中明确表示。上游占位逻辑不能自行变成虚构请求或业务字节。

### 5.2 建立模型计算任务

前端复用模型结构，按本轮输入查找注意力、路由相关处理、专家计算、合并及其他必要计算的耗时。MoE 层位置、隐藏维度、专家数和 Top-K 按模型配置保留，普通层不改成 MoE 层。

研究用非均匀路由逐层生成，关闭将首个 block 的路由和通信复制到所有层的路径。计算 profile 查找可以缓存，但缓存键必须包含实际影响耗时的输入形状。[S10][S11]

纯计算节点只包含计算模型负责的耗时。通信等待由后端完成事件产生，不能先把参考轨迹中的网络等待计入计算，再等待一次 UB 传输。

### 5.3 读取专家选择并找到目标设备

`TraceRouteProvider` 按请求、阶段、Token、层索引读取专家选择。`SyntheticRouteProvider` 用于功能测试或明确声明的统计实验，记录分布和种子。

合成路由按 `(seed, request_id, phase, token_index, layer_id)` 确定。网络事件顺序变化不会改变同一 Token 的专家选择，便于检查网络变化本身的影响。

放置模块把每个专家映射到 rank，同时累计各专家收到的输入。本地专家不产生交换网络传输，但仍增加本地专家计算和结果合并的负载。

### 5.4 生成通信并导出图

通信生成模块接收上述 Token、专家和 rank 关系，按第 6 章模板生成 Dispatch 和 Combine。它输出每条传输的源、目的、数据量、分块和依赖，而不直接指定传输结束时刻。

前端检查收发配对、字节量、节点依赖、组成员和资源引用，然后导出图及侧表。后端执行这些图，决定实际发送、排队和完成时刻。导出成功只证明格式可用，执行正确性仍由 M1、M2 检查。

### 5.5 P/D 交接在 M4 单独加入

P、D 使用不同的 rank 组和专家放置。P 完成预填充后，前端创建 `KV_TRANSFER` 操作。KV 数据提供器根据模型缓存格式、dtype、Token 范围和 P/D 分片映射，给出需要传输的各分片；不将 MHA 的缓存公式无条件用于 MLA 等格式。

D 在传输前预留目标 KV 容量，P 保持源缓存直到交接成功。D 所需分片全部就绪后，请求才进入可解码队列。本版要求两侧缓存布局兼容；需要重排或转换时先拒绝，后续通过明确计算与传输任务支持。

本版沿用 `kv_handoff_policy="between_iterations"`。P 完成本轮计算后保留源 KV，并预留交接所需源 rank；这些 rank 所属的 EP 组在预留解除前不启动依赖它们的新一轮。D 在当前 wave 完成的边界优先处理已接纳的交接。当相关源 rank 和目标 D 组都可提交时，后端原子装载 KV 收发图，完成后双方恢复调度。待交接请求按入队顺序处理。

单个请求的 KV 超过所选 D 组可提供的总容量时直接报错；只是当前空闲容量不足时，请求等待，D 继续处理已有工作以释放空间，不提前占用它的执行图。P 的源 KV 在等待期间继续占用容量。没有可推进事件却仍在等待时，按第 7.6 节报告死锁。

这一规则允许 KV 与其他独立组的 EP 通信竞争，但不与占用的 P/D rank 自己的计算重叠。它是保守的交接模型，不用于评价同组异步 KV 与计算重叠的收益。后续改变这一限制需单独增加受资源管理的执行上下文。

仅有解码路由时，继续使用给定 KV 已就绪的解码模式；功能测试也可使用标明来源的合成预填充。完整真实路由场景需要匹配的预填充数据，不能从解码记录捏造。

## 6. 通信库行为建模与传输任务生成

### 6.1 这一层负责哪些行为

推理程序提出一次 Dispatch 或 Combine，通信实现决定它怎样完成。例如，一个 Token 选择同一远端 rank 上的两个专家时，可以复用一份输入，也可以分别复制；结果可以先在远端合并，也可以分别返回。这些选择会改变数据量、端侧处理和同步位置。

本框架用通信模板描述选定的执行规则，不直接运行 NCCL、HCCL 或目标 UB 通信内核。模板生成具体任务，ASTRA 执行任务，UB 负责网络过程。包级仿真再细，也不会自动补出模板遗漏的通信行为。

每份研究配置要说明采用的模板、依据和未覆盖行为。首个模板用于检查生成器、依赖和接口；只有核对了具体运行时及配置，才能将相应模型用于讨论该实现的通信表现。

### 6.2 一个模板需要明确的内容

| 内容 | 必须回答的问题 |
|---|---|
| 通信参与者 | 哪些 rank 参加，零 Token 成员是否仍接收或发送数据 |
| 数据表示 | 激活、结果和应用元数据各有多少字节，传输 dtype 是否相同 |
| 复制与合并 | 同一目的 rank 上多个专家是否复用输入，结果在哪里聚合 |
| 传输对端 | 直接发给目标，还是由另一 NPU 中转 |
| 分块与发送顺序 | 数据怎样分块，各分块及对端按什么顺序进入可执行状态 |
| 并发与缓冲区约束 | 同时允许多少发送，哪些完成事件释放发送或缓冲区资源 |
| 同步与结束 | 本地操作等待哪些发送、接收和处理事件，是否存在真实全局同步 |
| 端侧处理 | 打包、解包、局部合并等由哪些计算节点计时，是否已包含在 profile 中 |

这份说明是模板的完整行为约定。初期只实现下面的参考规则，不同时实现所有可选算法、通道组织或流水方式。

### 6.3 参考模板 `direct_rank_dedup_v1`

模板名称和含义沿用 v0.1。一个 Token 命中同一远端 rank 的多个专家时，Dispatch 向该 rank 发送一份输入向量，并在内部保留该 Token 的目标专家集合。目的 rank 对各专家执行计算，再将同一源 Token 的本地结果加权合并，Combine 返回一份结果向量。

本地专家输入和结果不经过网络，计算与局部合并仍计入本地计算模型。Dispatch 和 Combine 分别指定传输 dtype、应用元数据字节数和分块大小。功能样例可令应用元数据为零，这只是参考假设，不代表实际通信实现没有元数据。

每个 rank 的专家计算等待本次本地 Dispatch 所需输入就绪，并等待模板要求的本地发送完成。本地 Combine 满足所需发送、接收和处理条件后，才能进入依赖它的后续计算。统计一个操作的全组最晚完成时刻，不会额外插入所有 rank 等待的屏障。

设 `n_ij` 为源 rank i 上至少选择了一个位于 j 的专家的不同 Token 数。对于 `i != j`，Dispatch 主体字节数为：

```text
n_ij × hidden_dim × dispatch_element_bytes
```

Combine 根据结果合并规则独立计算。只有一份输入对应一份聚合结果、传输精度相同且应用元数据不造成差异时，两阶段矩阵才互为转置。

真实实现采用逐专家复制、中间转发、其他同步位置或分块计算时，新建模板版本，不修改本名称的既定含义。`communication_profile_basis` 取 `reference_model` 或 `runtime_adapted`；后者还需记录目标实现版本与配置，且不自动表示已通过运行验证。

### 6.4 通信分块与 UB 分包

`chunk_bytes` 是通信模板一次任务所处理的数据上限。超过该值的有向数据段按顺序拆分，末块保留真实剩余长度。每块分配独立 `transfer_id` 和 SEND/RECV；UB 再按自身协议将任务分成网络包。

通信分块可能决定等待和缓冲区复用，UB 包大小决定底层传输单位，两者分别配置。改变 MTU 不应重新定义逻辑操作，改变 `chunk_bytes` 也不能隐含修改 UB 报头和应答规则。

首个模板不模拟分块到达后立即启动部分专家计算。专家计算等待本地 Dispatch 的全部必要条件；以后支持分块消费时，必须生成相应的分块计算及依赖。

### 6.5 发送顺序、并发与端侧处理

参考模板将本地可发送任务按操作内的目的 rank、分块索引固定排序。在不违背执行依赖的前提下，ASTRA 按这个顺序申请发送槽。排序仅使参考模型可重复，不声称对应某个真实库的通道调度。

`send_slots_per_rank` 规定同时在途的 SEND 数量，RECV 等待不占发送槽。M1 先使用一个槽；M2 在单层结果正确后再增加槽数并检查。原集合通信基线保留原资源规则。[S8]

发送槽在第 8.3 节定义的 `send_done` 释放。UB 自己的连接、队列和 outstanding 限制继续生效，模板发送槽不覆盖这些协议限制。若真实实现另有通信通道或缓冲区复用规则，需作为该模板的独立状态说明，不能认为一个发送槽参数已覆盖全部行为。

打包、解包和局部合并通过计算节点表示。profile 已包含某项处理时，模板不再重复增加同一耗时。首个模板不模拟通信内核与其他任务争用共享 HBM 带宽，相关结论受第 9 章范围限制。

### 6.6 通信中转与网络选路

通信中转指源 NPU 先把数据发送到另一 NPU，再由后者继续发送；模板必须显式生成两段传输和中间依赖。网络选路指一段端到端传输经过哪些交换机与端口，由 UB 网络决定。

首个模板使用直接端到端传输，不增加中转 NPU。它仍允许 UB 按网络配置选择路径。单纯修改交换机路由，不能自动产生通信库层的中转或聚合。

### 6.7 模板输出与验证依据

模板向 `ExecutionPlan` 输出操作、传输、计算任务和本地依赖。每个任务必须能追溯到输入 Token、专家或明确的协议控制规则。输出中不写本次通信的预测完成时间。

目标实现适配时，保留版本、调用配置、参与组、通信算法与相关参数，以及源码、日志或测量依据。逐项说明哪些行为已经核对，哪些采用近似，哪些尚未覆盖。没有依据的控制消息和流水阶段不自行补成真实行为。

模板的验证方法见第 13.9 节。参考模板与目标实现适配采用相同输出接口，分别保存依据和验证状态。

## 7. 根据完成事件继续执行与调度

### 7.1 两种反馈分别发生在哪里

第一种反馈发生在本轮任务内部。某份专家输入未到达时，ASTRA 保持依赖它的计算处于等待状态；必要输入和其他条件满足后才启动计算。计算结束后再允许对应结果回传。

第二种反馈发生在推理服务层。本轮完成时，后端把完成时间交给前端；前端更新请求进度，再根据此时的请求队列组批。M1、M2 先验证第一种反馈，M3 再加入第二种。

所有通信使用同一套网络对象。组 B 开始发送时，组 A 尚未完成的传输、端口队列、流控和连接状态继续保留。新图可以替换已经结束的执行任务，但不能因此重建或清空整个网络。

### 7.2 唯一的执行时间

`ns3::Simulator` 推进联合执行。ASTRA 计算节点通过 `sim_schedule()` 登记完成事件，网络任务也在同一事件队列中执行。[S14][S15]

`now_ns` 表示绝对时间，`duration_ns` 表示持续时间。前端收到消息后执行 `current_ns = now_ns`，不累加独立批次耗时。锁定版本的 Chakra runtime 与 profile 单位转换沿用既定接口，在输入处转换一次，并用 1,000 ns 计算样例检查。[S7][S11]

联合程序不同时运行 analytical 的时间队列。等待 Python 生成图时，仿真时间暂停；图生成和管道通信的现实耗时不自动计入推理时延。要模拟 CPU 调度开销时，另外建立有依据的耗时节点。

### 7.3 何时与服务前端交换消息

M3 使用 `cosim/1` JSONL 协议，每行一条 JSON 消息。初始时刻、已登记的新请求到达、本轮执行完成或 KV 交接完成时，后端请求前端作一次服务决策。普通包到达和单条传输完成只在 C++ 内继续执行，不逐条唤醒 Python。

后端发出 `DECIDE` 后等待一条对应的 `COMMIT`。期间不继续执行新的 ns-3 事件。前端一次返回当前时刻应提交的图、下一次外部唤醒时刻及服务是否结束。

这套消息协议只用于联合运行入口，上游原运行模式继续使用自己的接口。M1、M2 可以使用固定功能图驱动程序，M3 再接入 LLMServingSim 调度对象，无需提前实现完整服务循环。

### 7.4 消息格式

每条消息包含 `schema_version="cosim/1"`、`run_id` 和单调递增的 `decision_id`。stdout 只写协议消息，日志写 stderr 或文件。EOF、非法 JSON、编号不匹配或子进程失败都应立即报告，不无限等待。

以下是消息格式示例，数字不表示实际运行结果。

后端向前端报告本轮已完成：

```json
{
  "schema_version": "cosim/1",
  "type": "DECIDE",
  "run_id": "run01",
  "decision_id": 8,
  "now_ns": 80000,
  "completed": [
    {"kind": "WAVE_DONE", "wave_id": "D.w0", "graph_id": "g12", "finished_ns": 80000}
  ],
  "available_rank_ids": [0, 1, 2, 3]
}
```

前端提交下一轮，并登记下一次请求到达时刻：

```json
{
  "schema_version": "cosim/1",
  "type": "COMMIT",
  "run_id": "run01",
  "decision_id": 8,
  "now_ns": 80000,
  "submissions": [
    {
      "graph_id": "g13",
      "wave_id": "D.w1",
      "rank_ids": [0, 1, 2, 3],
      "workload_prefix": "graphs/g13/llm",
      "semantic_manifest": "graphs/g13/semantics.json"
    }
  ],
  "next_wakeup_ns": 91000,
  "input_exhausted": false,
  "service_finished": false
}
```

`next_wakeup_ns` 是前端已知的下一次外部变化时间，或 `null`。非空时必须晚于当前时间。图在当前 `now_ns` 启动，本版不在一条消息中提交未来时刻才激活的图。

`input_exhausted` 只表示没有未来新请求。`service_finished` 表示前端的请求、队列和待交接状态均已处理完。后端还需检查自己的任务与网络是否结束，才能退出。

### 7.5 同时刻事件与图装载

ns-3 在同一时刻按确定的事件顺序处理回调。交互驱动将已收集的完成通知按事件类型、实例或组编号、图编号排序后交给前端。相同时刻稍后产生的新通知可以触发下一次同时间决策，但不回溯修改已经启动的任务。

收到一组图后，后端先校验所有 rank 图、侧表、传输配对和资源映射，并确认目标 rank 没有在途图。随后装载全部图、登记传输描述，最后按 rank 顺序在同一时间激活。任何图校验失败时，整组提交失败，不先运行其中一部分。

原 `add_workload()` 的装载与直接启动行为需要分离。[S7] 登记传输描述不等于接收节点已经完成或发送可以越过前驱；实际收发仍由 ASTRA 按图派发。

初始化先创建全部执行与网络对象，再发出 `now_ns=0` 的首次决策。锁定 ASTRA 构造函数要求已有图时，使用验证过的零业务初始化图。它不推进时间，不产生网络包，也不进入业务操作记录。

### 7.6 新请求到达和实例忙闲

后端为 `next_wakeup_ns` 登记事件。即使组 A 正在传输，也要在组 B 的请求到达时刻通知前端；不能等 A 完成才让空闲的 B 获得请求。

同一 EP 组的成员按一轮共同执行，因此某成员暂时没有本地 Token 不表示它可以独立启动另一轮。独立 EP 组之间则不增加全局同步。

设备全空闲但未来还有请求时，直接推进到下一次到达。所有实例都忙时，新请求进入队列，不替换在途图。没有业务事件、没有未来唤醒，但仍有未满足依赖时，输出等待对象并报告死锁，不靠固定增加时间继续运行。

### 7.7 分层完成和正常结束

单条传输的完成由第 8.3 节定义。某个 rank 的本地操作完成由通信模板规定，日志分别记录各 rank 的时刻。一个 wave 完成则要求参与 rank 的必要图全部完成；不能因单个 rank 提前结束就通知整轮完成。

一张图完成时，所有节点及该图的接收等待、执行回调均应结束。仅仅没有新任务可下发，或发送槽全部空闲，不足以判断完成。

整个运行正常结束还要求前端服务完成、全部图完成、无在途 UB 事务与数据、必要统计已刷新。周期观测定时器不构成继续运行理由，退出时取消；协议重试定时器按其对象生命周期清理。

## 8. UB 网络适配器

### 8.1 ASTRA 接口怎样对应到 UB

接口签名以锁定 ASTRA 的 `AstraNetworkAPI` 为准。[S14] 下表规定适配器需要实现的行为，具体 UB 执行入口在第 8.2 节说明。

| ASTRA 调用 | 联合后端的动作 |
|---|---|
| `sim_send` | 复制必要参数，登记回调，查找传输描述，异步提交一份 UB 写任务后返回 |
| `sim_recv` | 登记等待该传输的数据就绪；不再发送第二份网络流量 |
| `sim_schedule` | 把相对耗时转换为 ns-3 事件，到期调用原回调 |
| `sim_get_time` | 将 `Simulator::Now()` 转为锁定接口所需的当前时间 |
| `sim_notify_finished` | 报告本 rank 当前图迭代结束，不直接终止服务 |

所查原生 SEND/RECV 使用 `UINT8`，该路径的 `count` 是字节量。[S7] 其他数据类型在支持前拒绝，避免将元素数误当成字节数。

`sim_request*` 可能来自调用栈，适配器复制所需字段，不异步保留原指针。每份回调状态保存图、节点和传输身份，直到相关事件处理完毕。

### 8.2 分离 UB 传输执行与 CSV 调度

此前源码审阅显示，`UbApp::OnTaskCompleted()` 使用 `UbTrafficGen` 查询清理信息和推进阶段。[S12] 联合模式不能直接跳过任务登记，也不能在 ASTRA 已经管理依赖后再走同一套 CSV 依赖。

本项目提取 `UbTransferExecutor`，负责保存任务上下文、提交 UB 请求、清理连接和 Jetty 相关资源，并通知完成接收者。原 CSV 模式仍由 `UbTrafficGen` 接收完成通知；联合模式由 `UbNetworkAdapter` 接收，不访问 CSV 阶段表。

这一改动优先通过小范围封装实现，保留原 UB 协议逻辑和资源释放路径。不仅仅覆盖一个 Jetty 回调，也不创建假 CSV 阶段来回避改造。

拓扑、路由和 UB 传输连接配置复用原 `UbUtils` 初始化能力。[S13] 这里的 UB 传输连接与模型张量并行 TP 是不同对象。联合入口运行时按需登记业务任务，不从 `traffic.csv` 一次性装载全部未来负载。

### 8.3 数据就绪、事务完成与发送完成

| 事件 | 本版含义 | 作用 |
|---|---|---|
| `data_ready` | 目标协议栈已收齐有效数据并满足该模式的上层可消费条件 | 完成 RECV，允许依赖接收的计算继续 |
| `transaction_done` | 源端 UB 应用或事务确认该任务完成 | 清理物理事务，并作为本版发送完成依据 |
| `send_done` | 当前配置定义的发送调用完成事件 | 完成 SEND，释放发送槽 |

本版固定 `sender_completion="transaction_done"`，所以 `send_done` 使用源端事务确认时刻。它是沿用既有完成路径的保守模型，不等于最后一个包离开发送端，也不自动等于真实主机 API 返回。[S12][S15]

接收端 `data_ready` 单独产生。开发时沿锁定 UB 接收路径核对去重、重组和相关事务处理，在数据确实可用的位置挂接被动回调，并确认如何对应 `transfer_id`。某个包到达、链路应答或源端事务完成，都不能未经核对直接替代这一事件。

M1 可以先打通源端完成，再补接收就绪，但阶段通过需要两者均有可靠来源。测试替身可以检验不同事件时刻的处理逻辑，实际 UB 接收事件则必须由源码和集成测试确认，不从预期时间反推。

将来需要本地注入完成或真实异步调用语义时，增加独立事件源和配置；本版不悄悄更改 `send_done` 含义。

### 8.4 匹配与生命周期

收发使用 `(src_rank, dst_rank, comm_tag)` 匹配。适配器检查它与唯一 `transfer_id`、固定字节量一致。SEND 和 RECV 可以任一方先登记。

数据先到、RECV 后登记时，适配器保存已到达状态，在登记时通过当前时间事件完成接收回调，不回到过去执行。迟到 RECV 状态不能随源端事务结束一起被删除。

`data_ready`、`transaction_done` 和两侧回调均只处理一次。传输上下文在物理事务结束、所需回调完成、来源记录已保存之后释放。回调通过 `Simulator::ScheduleNow` 或验证过的等价机制进入队列，避免注册函数尚未返回就重入并销毁图。

后端故障、图失败和正常清理分别保留状态。收到过期回调时报告对应图和传输，不将它绑定到下一轮复用的局部节点号。

### 8.5 任务大小、优先级与协议范围

内部 `transfer_id` 使用稳定字符串或足够大的唯一编号，再分配 UB 可表示的任务号。总通信量可以是 64 位，但每个任务必须满足 UB 入口上界。[S12] 先按通信模板拆分大数据段，再检查每块；单块仍超界时拒绝配置，不静默截断或偷偷改变分块方式。

所有参考模板任务使用相同默认优先级和传输配置。只有实验明确研究业务类别时才允许修改，不能按操作身份选择独特优先级、路径或固定延迟来制造指纹。

首版仅实现 URMA_WRITE/RTP。ASTRA 的 RECV 是等待事件，不翻译成 URMA_READ。通用内存节点也不直接翻译成 UB Load。未来增加 READ 或原生 Load/Store 时，要单独说明请求方向、返回数据方向、完成位置和计算消费条件。

## 9. 计算、内存和数据真实性

### 9.1 计算耗时的两种来源

| 来源 | 用途 | 允许的表述 |
|---|---|---|
| 固定耗时或明确函数 | 验证时间、依赖和资源占用 | 功能样例或给定假设下的实验 |
| 指定设备的 profile 或性能模型 | 给出模型与输入形状相关耗时 | 说明设备、模型、dtype 和有效范围内的依据 |

LLMServingSim 允许外部测量或厂商模型按要求提供 profile CSV，这提供了非 GPU 设备的接入形式，不提供目标 NPU 的现成数据。[S16]

联合模式使用显式 COMP runtime，默认关闭 ASTRA roofline 替代路径，不按历史通信耗时直接完成网络任务。网络耗时由 UB 执行产生。

### 9.2 有效范围和校准状态

查表输入包括实际影响耗时的参数，例如计算类型、dtype、输入形状、上下文规模和专家负载。超出 profile 范围默认报错；探索实验显式允许外推时，记录次数、方法和偏离范围。

缺少目标 NPU 数据时，可使用参数化计算模型开展参考实验，并记录 `calibration_status="unvalidated_reference"`。不能仅用 GPU 耗时乘算力比例后称为 NPU 校准。

路由来源、计算依据和通信模板的验证状态分别记录。真实路由、参考计算、参考通信模板可以组成一项合法的模型实验，但结论范围应与这三项条件对应。

### 9.3 内存容量与生命周期

模型权重、KV、计算工作区和通信缓冲区的容量应当自洽。用于功能验证的小型模型和真实模型配置分别命名，不把真实大模型的 rank 数任意缩小到四张卡后仍声明可部署。

本版内存管理首先保证容量和 KV 生命周期，不模拟共享 HBM 带宽争用。计算 profile 已包含的本地访存耗时不重复增加。通信缓冲区有固定或可计算占用时，按模板配置计入容量。

因此，本版不能直接验证内存消费变慢如何通过硬件缓冲区传播反压。该问题需要另行建立经过校准的端侧消费与缓冲区模型，不在当前推进计划中同时实现。

## 10. 观测、真值与输出

### 10.1 从最小收发开始保留来源

M1 就为每条任务保留操作、传输和 UB 任务的对应，并在至少一个实际交换端口累计计数。M2 检查多条 MoE 传输，M3 检查连续多轮与不同通信组，M5 再完成多设备本地时钟和正式研究输入。

早期记录可只覆盖测试使用的端口和字段，但字段含义与正式输出保持一致。无需先写全量逐包文本或完整分析系统，直接在事件位置累计即可。

### 10.2 端侧操作记录

每个 rank 分别记录逻辑调用的开始与完成。默认开始时刻为该调用前驱满足、进入通信执行阶段的时刻，完成时刻为模板规定的本地发送、接收及处理条件全部满足的时刻。这是模拟的设备执行语义，不自动对应主机 API 提交和返回。

操作记录在 ASTRA 对应执行位置产生，不能从第一包或最后一包的网络真值倒推出端侧时间。目标 profiler 记录不同事件时，需要单独说明适配关系，无法获取的字段不进入算法输入。

端侧输出使用本地记录编号及允许的调用上下文。内部全局 `operation_id` 和跨 rank 绑定放在真值注册表中；只有目标记录确实能提供的信息，才可以通过实验字段白名单开放。不要仅保留整组最早开始、最晚结束的一对时间。

### 10.3 端口计数口径

一个计数位置由 `switch_id, port_id, direction` 指定。配置明确计数发生在发送开始、接收完成或其他已核对的位置。一次实验固定一种口径，观测与核验使用同一挂接点。

默认计入模拟器在该位置实际处理的整包字节 `counted_packet_bytes`。它不包括模拟器未表示的编码、FEC 等物理开销。数据、重传和控制包按实际经过该位置的次数计数。

内部另记业务有效负载 `business_payload_bytes`。本版用于关联真值的主体为激活、专家结果和 KV 的有效数据；应用元数据和 UB 协议开销另行核对，不能当成主体数据重复累计。`payload_bytes` 仍按第 4.5 节包含随数据发送的应用元数据，二者名称不互换。

后端要能将任务的有效数据范围对应到实际包内字节范围。若已有协议会拆分或合并任务，按实际范围记录来源；无法确认来源时，相关真值测试不通过。没有业务有效负载的控制包可增加观测计数，但不虚构其业务归属。

重传的业务数据每次经过端口都进入相应时窗，与唯一交付的数据量分开。全网所有端口累计量也不与应用字节量直接相等，因为同一份数据可能经过多个计数位置。

### 10.4 本地时钟与采样窗口

执行始终使用全局 `t_ns`。输出时按设备转换本地时间，例如：

```text
local_time = floor((1 + drift) × t_ns + offset_ns)
```

时钟模型必须单调。偏移和漂移只影响观测，不改变计算、传输和调度。M1 至 M4 可使用零偏移调试配置，M5 再开启不同设备的偏移与漂移。

采样窗口采用本地半开区间 `[start_local_ns, end_local_ns)`，由该设备的采样起点确定。无包窗口输出零，缺失记录不当作零流量。只在显式观测区间内生成窗口，同一设备各端口共享其设备时钟。

全局时间和时钟变换参数仅保留在内部输出，研究算法输入不包含这些对齐答案。

### 10.5 归属真值与一致性检查

按研究定义，`b(operation, port, local_window)` 表示某操作在指定端口时窗中实际被计入的业务数据。`b > 0` 时，操作与该时窗存在真实关联。[P1]

内部侧表、已有任务标识或不增加线速字节的仿真元数据可以追踪来源，但这些标识不参与业务路径、QoS、流控或时延计算，也不新增业务协议中的操作标签。

验证分开检查两种守恒。第一，发送与接收的唯一有效数据量符合生成需求。第二，每个端口时窗内各类实际包字节之和等于观测总计数。第二项含数据包、背景包、元数据所在包的字节及控制包开销，不能只加 `business_payload_bytes` 后与整包计数比较。

打开或关闭内部来源记录不应改变模拟传输、资源状态和完成时刻。观测模块不主动发包，统计更新不引入业务执行事件。

### 10.6 输出目录和访问边界

```text
runs/<run_id>/
  manifest.json
  inputs/
  graphs/
  observed/
    endpoint_ops.jsonl
    port_windows.csv
    public_config.json
  truth/
    operation_registry.jsonl
    transfer_registry.jsonl
    attribution_windows.csv
    clock_models.json
  metrics/
    service_metrics.json
    validation.json
  logs/
```

`observed/` 是关联方法唯一允许读取的目录。`public_config.json` 只保存实验允许的静态配置；不会默认暴露逐 Token 专家选择、逐消息矩阵或全局图节点。`graphs/` 和 `truth/` 用于开发与核验，不因与观测文件相邻就允许算法读取。

`manifest.json` 记录依赖与项目 commit、配置及输入 hash、随机种子、时间和字节单位、路由来源、通信模板、发送完成语义、分块与并发、计数位置、时钟模型、计算数据范围及验证状态，并说明运行是否正常结束。

`mode` 区分 `fixture` 和 `research`，表示运行用途，不代替校准状态。参考模型也可用于声明假设的研究实验；它不能被标成已复现真实硬件。

## 11. 配置、目录与代码改动位置

### 11.1 分阶段使用同一配置入口

## 12. 同一组样例逐步验证前后端

### 12.1 四 rank 单层输入

本节是确定性功能样例，不代表真实模型部署或实测数据。rank 0、1、2、3 分别对应四个 UB 端点，本层专家放置如下。

| Rank | 专家 | 本轮本地请求 |
|---|---|---|
| 0 | 0、1 | A |
| 1 | 2、3 | B |
| 2 | 4、5 | C |
| 3 | 6、7 | D |

各请求提供一个 Token，Top-K 为 2，隐藏维度为 4096。Dispatch 和 Combine 均使用每元素 2 字节，应用元数据为零，所以一份向量为 8192 字节。首个用例的通信分块上限不小于 8192 字节。

| 请求 | 源 rank | 专家选择 | 远端目的 rank |
|---|---|---|---|
| A | 0 | 2、4 | 1、2 |
| B | 1 | 0、5 | 0、2 |
| C | 2 | 4、6 | 3，专家 4 在本地 |
| D | 3 | 1、3 | 0、1 |

本例取第 10 个解码步骤，规范化 `token_index=9`，`layer_id=7`。实际批次不要求各请求具有相同步骤。

### 12.2 先检查字节和本地计算

生成 `D.w0.L7.dispatch` 和 `D.w0.L7.combine` 两个操作。Dispatch 主体矩阵的行表示发送 rank，列表示接收 rank。

```text
           dst0   dst1   dst2   dst3
src0          0   8192   8192      0
src1       8192      0   8192      0
src2          0      0      0   8192
src3       8192   8192      0      0
```

Dispatch 有七条远端传输，共 57,344 字节。当前精度与合并规则下，Combine 为其转置，也有七条传输。合计十四条传输、114,688 字节，不含 UB 开销；每条传输对应一对 SEND/RECV。

四个 rank 的专家计算输入份数依次为 2、2、3、1。rank 2 的三份包括 A 对专家 4 的输入、B 对专家 5 的输入，以及 C 的本地专家 4 输入。本地传输被过滤后，第三份计算不能丢失。

### 12.3 再检查等待关系

rank 2 的任务关系如下。图中的等待是本参考模板的约定。

```text
rank 2 本地注意力和路由完成
    ├─ Dispatch SEND 2→3
    ├─ 本地 Token C 的专家输入就绪
    ├─ Dispatch RECV 0→2
    └─ Dispatch RECV 1→2

必要接收、本地输入及本地 Dispatch 发送完成
    ↓
rank 2 专家计算与本地结果处理
    ├─ Combine SEND 2→0
    ├─ Combine SEND 2→1
    ├─ 本地 Token C 的专家 4 结果
    └─ 等待 Combine RECV 3→2
    ↓
本地 Combine 条件全部满足
    ↓
下一层计算
```

先用测试替身给定完成事件，隔离检查执行层。设本地输入在 5,000 ns 就绪，发送 2→3 在 18,000 ns 事务完成，输入 0→2 在 20,000 ns 就绪，输入 1→2 在 26,000 ns 就绪，专家计算耗时 12,000 ns。

则专家计算在 26,000 ns 开始，38,000 ns 结束，Combine 发送不能早于 38,000 ns。将最后一份输入推迟 4,000 ns 后，计算开始变为 30,000 ns、结束变为 42,000 ns。这只规定依赖响应，不声称整个 wave 也恰好在该时刻完成。

随后换成真实 UB 后端执行同一图，让网络产生完成时刻。集成测试检查依赖与事件是否一致，不要求 UB 恰好产生测试替身中的时间。

### 12.4 只改变专家选择，检查去重

保持其他 Token 不变，将 A 的专家选择改为 4、5，两者都在 rank 2。按照参考模板，0→2 只发送一份 8192 字节输入，rank 2 执行两份专家计算，再合并为一份结果返回 2→0。

此时 Dispatch 的 0→1 消失，远端传输变为六条，49,152 字节。Combine 同样六条，两阶段总计 98,304 字节。四个 rank 的专家计算输入份数变为 2、1、4、1，总数仍为八份。

这个变体验证网络输入去重与专家计算计数是两个动作。它不引入第二种通信算法，也不使用唯一数据大小帮助关联算法辨认操作。

### 12.5 只改变分块，检查任务展开

恢复第 12.1 节专家选择，将 `chunk_bytes` 改为 3072。每条 8192 字节传输拆成 3072、3072、2048 字节三块。

每个阶段生成二十一块，两阶段共四十二个 UB 任务，总业务字节仍为 114,688。分块拥有不同 `transfer_id`，但仍归属原来的两个逻辑操作。本地专家计算不因分块增加到三倍。

先保持一个发送槽验证顺序与配对，再改变槽数检查可并发任务。不同分块或槽数可以改变实际完成时间，因此不要求流量曲线完全相同；要求总量、来源和模板依赖正确。

### 12.6 连续两轮，检查图和标识

同一组 A 至 D 再执行下一解码步，使用显式给定的同规模合成路由。新图可复用本地 `node_id`，但分配新的 `graph_id`、操作和传输编号以及 `comm_tag`。

第一轮完成后再提交第二轮，确认迟到事件不会更新新图。两轮使用同一网络对象。早期由固定功能驱动提交，M3 再用真实的服务前端决定第二轮批次。

### 12.7 再加入第二组，检查共享网络

在不同 NPU 上建立另一独立 EP 组，构造两组通信实际经过同一条饱和链路或同一出口的拓扑与路径。先分别运行，随后在同一次仿真中让两组传输重叠。

第二组开始时，第一组尚未完成的包和队列必须继续存在。检查共享位置的排队、实际完成时间，以及依赖计算的变化。再调整发起时刻或路径移除该重叠，作为对应检查。不要求任意并发都会变慢，也不预设平均分配带宽。

端口计数提供聚合结果，内部来源表记录两组分别贡献哪些窗口。测试不把前文手算时间写入后端，以免用固定时间回放代替资源竞争。

## 13. 逐步开发与验收

### 13.1 推进规则

**每次只增加一项新的执行能力，保留上一项可运行用例，并通过对应检查后再继续。** 小模型、固定耗时和合成路由用于排查接口问题，真实模型与复杂负载不作为早期验收的替代品。

阶段编号 M0 至 M5 沿用 v0.1。每个阶段再拆成顺序小步骤；这些步骤表示开发依赖，不表示需要并行开展多条工作线。

| 阶段 | 新增的主要能力 | 此阶段完成后得到的结果 |
|---|---|---|
| M0 | 可重复的上游基线与构建 | 能确认当前环境和后续改动的参照 |
| M1 | 一个计算任务与一对 UB 收发 | 有实际完成事件和最小来源记录的两端点用例 |
| M2 | 一个 MoE 层及连续固定图 | 字节、依赖、分块和图生命周期正确的四 rank 用例 |
| M3 | 动态请求、组批与多组共享网络 | 后端完成时间确实影响后续请求执行的服务原型 |
| M4 | P/D 交接与模型数据 | KV 容量及交接过程自洽，能够逐项接入真实数据 |
| M5 | 正式观测与模型验证 | 可复现、信息隔离且适用范围明确的研究运行结果 |

最小端侧记录、端口计数和来源核验从 M1 起逐步保留。M5 完成正式化与真实性验证，不是在最后才开始建设观测。

### 13.2 M0 先复现原生基线

**M0.1** 锁定第 2.1 节依赖，在目标开发机运行原生 UB 两端点经交换机通信样例，以及一个小型 LLMServingSim 样例。记录输入、版本、命令、返回状态和输出。

**M0.2** 运行与当前范围相关的上游 MoE、P/D 和成员忙闲不均回归，保留结果和未通过原因。只使用锁定版本存在的样例；缺失或失败时报告具体情况，不宣称全套上游回归已通过。

**M0.3** 确定 ASTRA 核心库、Chakra 读取组件与 UB 的联合构建方式，检查程序只链接一套 ns-3。先确认构建边界，不同时实现服务调度或 CCL 模型。

进入 M1 的条件是原生起步样例可重复、构建依赖明确。后续相关功能依赖的上游失败需在进入对应阶段前处理。原生数值作为回归参照；替换网络模型后，不要求时延仍与原解析后端完全相等。

### 13.3 M1 只执行计算和一对收发

**M1.1** 在联合执行时间上运行一个 1,000 ns 的 COMP，检查完成时刻与单位转换。此时不接请求调度，不读取专家路由。

**M1.2** 提交一份写任务和配对的接收等待，先使用一个发送槽。按第 8.2 节分离传输执行和原 CSV 调度，核实源端完成及资源释放，再保留原 CSV 样例回归。

**M1.3** 核对目标端数据就绪位置，分别处理发送与接收完成。测试先登记发送、先登记接收两种顺序，并让接收等待在数据到达后才登记一次。

**M1.4** 在一个实际经过的交换端口累计计数，保存该任务的操作、传输来源和有效数据范围。开关来源记录后，传输结果应不变。此时仅输出测试所需日志，不建设全量分析界面。

进入 M2 前，时间单位、两侧回调、唯一业务传输、资源清理及最小计数均应正确。源端能报完成但接收端事件尚未确认时，M1 仍未完成。

### 13.4 M2 先一层，再分块，再连续两轮

**M2.1** 使用第 12.1 节固定四 rank 输入，生成一层 Dispatch、专家计算和 Combine。保持固定耗时、一个发送槽、单块传输，检查十四条传输和本地计算。

**M2.2** 按第 12.3 节先使用测试替身检查延迟传播，再使用实际 UB 完成事件执行。核实专家计算只等待模板要求的本地条件，没有额外全局屏障。

**M2.3** 先运行同一目的 rank 多专家的去重变体，再运行分块变体，最后改变发送槽。每次只改变一个条件，检查字节、来源、依赖和在途数量。

**M2.4** 在同一进程和同一网络中连续执行两张固定图，复用局部节点号但不复用运行内身份。验证所有 rank 的图先装载后激活，旧事件不会更新新图。

进入 M3 前，单层和连续两轮用例可重复。此阶段没有动态请求到达、P/D 或复杂模型，前端只是将给定输入转换成图。

### 13.5 M3 再让请求动态进入

**M3.1** 将已验证的图生成和执行接口接入 LLMServingSim。先用一个 EP 组、一组预先到达的短请求、给定已就绪 KV，连续运行多个解码步骤。检查各请求步骤和结束状态，不改变单层通信模板。

**M3.2** 加入运行期间到达的新请求。先验证忙碌组只更新队列、不替换在途图；随后加入一个使用不同 NPU 的空闲组，检查它在自己的请求到达时刻被唤醒。

**M3.3** 在两组身份与时间正确后，按第 12.7 节设置共享瓶颈。对比独立与重叠执行，检查排队和完成变化，并检查变化是否传到依赖计算和下一次调度。

**M3.4** 覆盖部分 EP 成员没有本地 Token、某组先完成、输入已结束但仍有在途任务等情况。加入 EOF、后端异常退出和死锁检查，保证错误会明确终止并输出位置。

**M3 是继续扩大框架前的主要关口。** 动态到达、连续图、独立组共享网络和任务生命周期未通过前，不以增加模型层数、请求数量或 P/D 功能推进进度。

### 13.6 M4 单独加入 P/D 和真实数据

**M4.1** 先用小型模型和一个请求加入预填充及一次 KV 交接。P、D 组在交接时都处于可提交状态，使用 `between_iterations` 策略。检查目标容量先预留、源缓存后释放、所有 KV 到达后才能解码。

**M4.2** 单次交接正确后再增加待交接请求，检查排队和资源预留。随后与一个独立 EP 组同时运行，验证 KV 通过同一个 UB 网络竞争；不扩展为占用的 P/D rank 内异步计算重叠。

**M4.3** 网络与交接过程稳定后，逐项替换功能数据。先校验一个实际模型的层结构、专家配置和内存预算，再接入一段连续路由，最后替换相应计算耗时数据。每替换一项，都保留其余配置并检查差异来源。

没有真实预填充路由时，P/D 功能用例继续明确使用合成输入；真实路由实验可保持解码范围。没有目标计算 profile 时保留参考计算状态，不因此扩大到新的硬件模拟任务。

### 13.7 M5 整理研究输出并核对模型

**M5.1** 将前面已经存在的记录按第 10 章固定字段、目录和访问边界整理。加入设备本地时钟偏移与漂移，检查观测窗口、零计数及信息隔离。

**M5.2** 运行至少一段多层、多解码步骤的连续数据，检查观测与来源守恒、相同输入重复执行及完整结束。输入包含真实路由时，记录具体片段和转换过程；没有真实数据时只报告功能数据管线完成。

**M5.3** 对一个明确的目标通信实现核对第 6.2 节行为。具备执行记录时，再比较相应时序；缺少记录或设备数据时，逐项保留未验证状态，使用参考模型结论。测试正确与目标系统已校准分别报告，不合并为一个通过标记。

阶段结束时能够产生可用于关联研究的观测和独立真值，同时明确哪些参数有真实依据、哪些属于假设。框架交付不承诺关联方法一定能够唯一恢复所有操作。

### 13.9 模型真实性的检查记录

功能测试之外，每个研究用模型保留一份检查记录，依次说明输入数据来源、通信模板版本、目标实现配置、计算依据和有效范围。逐项记录已核对行为、支持证据、近似及未覆盖内容。

先检查端点间业务字节、复制与聚合、阶段顺序及完成条件，再检查指定采样窗口下的流量时序。验证阈值需要根据实际记录精度和本次研究的采样尺度，在拟合参数前明确。本指南不在缺少资料时预设统一的误差百分比。时间、流量和数据量各自比较，不能用一个平均时延掩盖阶段或端点分布差异。

参考模型通过功能测试后可以开展有明确假设的关联研究。对真实部署的结论则需要对应验证，不能用上游某模型服务指标的准确性替代 UB 端口时窗的验证。

## 14. 开发协作与交付

### 14.1 按当前步骤分配任务

开发者每次先确认当前阶段已通过的用例，只修改下一小步所需的模块。M1 主要涉及联合构建、UB 执行和回调；M2 加入任务生成；M3 再修改服务控制；M4 才加入 P/D 与数据适配。不要在 M1 同时建设所有前端模块。

多人协作时，前端负责批次、路由、计算查询和图输出；后端负责任务执行、UB 接口和完成事件；观测与测试负责计数、来源和用例。边界沿用 `ExecutionPlan`、`cosim/1` 和第 8.3 节事件定义，不分别修改同一字段的含义。

### 14.2 每次提交说明什么

提交记录说明所属阶段及小步骤、修改的行为、运行的输入、预期结果和实际结果。涉及模型假设或接口变动时，同步更新配置与对应测试。

上游补丁只处理当前功能或正确性需要的部分。无关性能优化、代码整理和依赖升级单独提交。失败用例先定位并修复，不通过改成均匀流量、固定通信时间或更简单输入静默绕过。

代码助手执行任务时，也以一个小步骤为单位。完成后给出实际修改和测试结果；尚未完成的模块保留未实现状态，不生成看似完整但没有行为保证的空框架。

### 14.3 分阶段可用结果与最终交付

M1 的交付是最小联合收发用例，M2 是参考 MoE 图与连续执行，M3 是动态服务原型。每一项都可保留为独立回归入口，但不能用其中一项代替整套系统完成。

本版全部规划完成后，交付固定依赖、可重建环境、统一命令、必要 schema、T01 至 T16、连续运行用例、观测与真值导出，以及至少一份来源和模型范围明确的研究运行记录。受访问限制的数据不打包公开。

README 说明已经实现的入口、并行范围、UB 模式、发送和接收完成定义、通信模板依据、计算数据状态及算法可读取的字段。运行正确性与模型真实性分别列出，未核实项目不写成已支持。

这套框架的完成标准是：指定请求产生可解释的计算与通信任务，任务在同一 UB 网络中正确执行，完成时间影响后续调度，观测与独立来源可以一致核验。它不负责保证关联算法成功，也不默认复现某款真实超节点的全部行为。
