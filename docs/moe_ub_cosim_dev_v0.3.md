本版目标是让已有联合执行链处理可配置的模型与部署、同一 rank 的多请求批次、多层与多组共同运行，并逐步接入有来源的路由、计算和目标通信行为。参数化、连续组批和组合运行用于补齐原方案所述的一般能力，不能因 v0.2 的限定用例已通过就视为完成。小型固定样例继续作为回归依据，其数值不能成为最终能力的白名单。

## 3. 必须保留的联合执行语义

1. 联合程序只使用 ns-3-UB 的一套 ns-3、一份仿真时间和持续存在的网络状态。组之间、轮之间和层之间保留真实队列、信用与在途包，不能靠独立运行结果相加模拟争用。
2. 每份逻辑数据交付只展开一次，其数据可消费条件与调用完成、资源释放条件分别定义。现有 URMA_WRITE/RTP 路径继续保持一份 SEND 一份业务写事务、RECV 仅等待；目标端 `RemoteWriteCommitted` 产生 `data_ready`，源端事务完成产生 `send_done` 并释放发送槽。该事件绑定只适用于已经验证的 WRITE 路径。新增 READ 或原生 Load/Store 时，按模式声明协议发起方、请求与数据方向、两侧完成事件和资源归属，不因登记两侧依赖重复发起事务，也不把 RECV 自动解释成 READ。跨芯片通信耗时仍来自本次网络事件；同芯片本地路径按第 4.1 节处理。
3. 每个 rank 对应的独立计算端点同时只有一张活动执行图和一个计算槽；首个 CM384 场景以 die 为该计算端点，不以双 die 的整芯片为单位。每组在既有装载协议下原子装载本轮各 rank 图。层间依赖属于本 rank 的执行图，不增加 v0.2 未规定的全组逐层屏障。
4. 请求到达时间、网络事件和调度反馈均使用仿真纳秒时间。活动图执行期间到达的请求先排队，不修改已经提交的图；Python 生成图所耗的真实时间不计入仿真。
5. 操作、图、传输和请求身份在声明的作用域内唯一，跨轮局部节点编号复用不能造成错误匹配。保持晚到 RECV、重复完成防护、最后一组结束及资源回收行为。
6. `observed/` 与内部真值分开。来源信息不改变业务包、选路、优先级、时间或调度决定；算法输入仍仅使用规定的观测。整包字节、业务字节、唯一交付字节和来源归属分别核验，控制包及重传不能混入唯一业务交付量。
7. 观测继续使用端侧实际操作起止、真实端口事件、本地时钟和半开采样窗口；零计数与未观测分开。功能正确性、数据真实性及硬件校准状态分别记录，缺少依据时保留 `unvalidated_reference` 等适当状态。

## 4. 行为要求

### 4.1 模型、放置与端点参数

EP 组成员、专家数、Top-K、每层静态专家放置和 `rank_to_ub_node` 必须使用显式配置。校验依据字段之间的关系，例如组非空、成员唯一、映射存在、专家编号合法、每个 Token 的专家选择数等于 Top-K，以及 `1 <= Top-K <= 专家数`。不能只将 EP4 改成另一组固定允许值，也不能只删除 Python 的限制而让后端继续使用旧常量。

本版每个 rank 对应一个独立计算端点，UB 端点映射必须一一对应到实际存在的计算端点，不能映射到交换节点，也不能让独立服务组复用同一个计算端点。rank 编号是逻辑身份，UB 节点编号是网络端点；传输描述、实际发送与接收、端侧记录、端口记录和真值关联必须使用正确的对应关系。不得继续把 rank 编号直接当作 UB 节点索引。

目标场景另外显式记录 rank 对应的计算 die、物理芯片、服务器及 fabric 接入关系；芯片身份必须在运行内唯一，不能只比较服务器内局部编号。CM384 场景保留 128 个逻辑 rank 和对应的独立计算资源，不因每芯片含两个 die 而合并成 64 个 rank。网络端点编号与芯片归属是不同信息，同芯片不要求合并 UB 节点；本版也不因此增加多个 rank 共享同一计算端点的能力。权重、KV 和工作区预算按声明的资源归属核算，不能将整芯片容量重复赋给每个 die。

跨芯片网络范围下，数据贡献分为同 rank、同芯片不同 rank、跨芯片三类。前两类不创建 ns-3 fabric 事务、链路包或交换端口流量；仍保留所有专家输入、Combine 贡献及生产者到消费者的完成依赖。同芯片不同 rank 的等待不能因没有网络回调而悬挂，也不能在源数据就绪前完成。必要端侧耗时并入明确的本地参考/profile，不建模 die 间互联带宽、协议或包。该分类在后续部署适配任务单独实现和验收；未声明芯片归属的旧输入不按相邻 rank 编号推断本地性，保留原交付范围。首个单层参数化任务仍保留现有 rank 到端点的单射映射与本地性定义。

允许专家在组内非均匀分布；逐层放置可以不同，但一次运行期间固定。与调度容量核验衔接时，专家权重占用必须按各层实际落在该 rank 的专家计算，再加该 rank 所需的共享权重，不能沿用均分专家权重估算非均匀放置的容量。组间模型和配置能否不同，由具体任务声明；不因此要求本版建立任意异构模型服务系统。

模型配置应明确所执行层段、层类型、隐藏维度、专家结构、注意力与 KV 所需维度、数据精度，以及 TP=1、PP=1 的范围。所选目标模型包含稠密层时，不能把所有层都替换成 MoE 层。省略 embedding、输出头或其他环节的实验必须声明省略范围，其耗时不能标为完整模型端到端 ITL 或 TTFT。

资源上限可以保留，但必须区分算法或协议限制、可配置资源预算与小型样例限制，给出检查位置及拒绝原因。不能静默截断请求、层、端口或采样窗口。兼容原输入时保留其含义；发生不兼容变更时明确 schema 版本与迁移或拒绝方式。

### 4.2 同一 rank 多请求连续批处理

连续批处理发生在迭代边界。每个 rank 有自己的请求集合和调度预算；同一 EP 组通过一次通信计算完成这些 rank 的本轮工作。各 rank 的批次大小可以不同，某 rank 本地没有解码 Token 时仍可能承接其他 rank 发来的专家计算。

解码阶段，一个已选请求每轮推进一个 Token。本轮各请求不必处于相同的解码位置；每个请求分别保留已计算长度、剩余输出、路由索引和完成时间。一个 rank 的逻辑操作可以包含多个请求的 Token，仍使用一张执行图，而不是为每个请求同时建立一张活动图。

应复用锁定版本 LLMServingSim Scheduler 已有的请求状态、批次选择、预算和逐请求完成能力，扩展联合前端的适配。不能只增大 `max_num_seqs`，同时仍使用 `batch.requests[0]`、单 Token 计划校验或 `generated == 1` 完成条件。批次完成要按实际 `scheduled_tokens` 逐请求记账：本轮被调度的每个解码请求恰好推进一个 Token，生成量与实际被调度请求数一致；只有达到终止条件的请求才结束，且请求完成只记录一次。

| 迭代 | rank 上执行的请求 | 迭代结束后的变化 |
|---|---|---|
| 第 1 轮 | A 的第 1 个剩余 Token、B 的第 1 个剩余 Token | B 仅需 1 个剩余 Token，因此完成并释放占用；C 在本轮执行期间到达并等待。 |
| 第 2 轮 | A 的第 2 个剩余 Token、C 的第 1 个剩余 Token | A、C 都尚未完成。 |
| 第 3 轮 | A 的第 3 个剩余 Token、C 的第 2 个剩余 Token | A、C 分别完成并释放占用。 |

该例假定 A、B、C 分别还需 3、1、2 个 Token，序列预算和 Token 预算均至少为 2，且 KV 容量足够。C 在第 2 轮加入，不等待 A 完成整个请求。批次成员只在边界变化，不能在同一轮的不同层之间临时插入 C。

第一版可先完成 KV 已就绪的纯解码连续组批，沿用已知输入及输出长度的场景；混合 prefill/decode、抢占、重算、交换及中途 KV 迁移不由本条自动引入。P/D 场景中的请求只有在其实际 KV 交付及接纳条件满足后才能进入 D 批次，不能以到达 D 队列替代数据就绪。

### 4.3 KV 容量与接纳

调度必须同时核验序列预算、本轮 Token 预算和内存容量。对于 KV 已就绪且输出长度已知的首版实现，采用保守容量策略：接纳前为该请求预留至最后一次计算输入所需的 KV 块，直到请求结束才释放。按锁定版本 Request 的口径，`request.output` 为最终总序列长度，目标 KV 长度为 `request.output - 1`；块数为该长度除以每块 Token 数后向上取整。预留容量不等于已经计算这些 Token，也不产生填充网络流量。

所有活跃请求及 P/D 等待交付占用必须使用一致的每 rank 块池账本，明确预留、已占用、交付完成和释放的关系，不能在联合前端与 Scheduler 中重复分配。ready-KV 的 `add_decode()` 路径若直接加入 running 队列，调用前也必须完成容量与接纳检查，不能借此绕过预算。仅检查当前已有序列长度不足以保证后续增长的容量；不能将 `reserve_full_isl` 的当前长度检查当作最终长度预留，也不能靠提前增加已计算 Token 数模拟预留。

单请求最终 KV 需求超过该 rank 扣除权重、工作区和通信缓冲区后的总 KV 容量时，给出明确输入错误。若请求本身能够容纳、只是当前空闲块不足，则请求排队，已有请求继续推进，释放后重新接纳。Token 预算针对本轮工作量；纯解码首版每个被选请求每轮需要一个 Token 额度，不能拿请求的总输出长度与单轮预算比较。无法容纳任何一个解码 Token 的配置应拒绝。不得静默降成永久单请求执行，也不得触发联合执行链尚未建模的抢占或重算。将来改成动态扩容策略时，必须另行给出避免循环等待的规则和测试。

真实路由仅覆盖一个观察片段时，单独声明片段内的 KV 预留上界和停止条件，容量保证只覆盖该片段；不能为方便调度而把真实请求的输出长度改成观察长度。达到窗口终点记录为观察结束，未完请求不记作 EOS 或正常请求完成。已经驻留的等待请求也计入 KV 占用；不得只计当前活动批次。

### 4.4 路由、通信归并与计算形状

批次变化后，按本轮每个请求的实际阶段、Token 索引和层读取路由，再依据该层放置生成通信。不能把一个请求的路由复制给整个 batch，不能要求不同请求的解码步数相同，也不能跨请求重复消费同一条路由记录。

`direct_rank_dedup_v1` 的去重单位保持为同一个 Token 发往同一个目标 rank。不同请求或不同位置的 Token 即使目标专家相同也不能相互去重。本地专家输入按第 4.1 节分类，不产生网络传输但必须计入专家负载。业务字节、分块与来源映射均由实际 Token 集合重算。其他通信模板的贡献复制、归并和 Combine 归约规则独立定义，不能将本参考模板的 rank 去重规则默认为 CANN 行为。

计算模型要接收实际批次形状、请求上下文长度、精度和每个专家的输入量。专家输入总量相同但分布不同的两个批次必须能作为不同输入被描述，是否耗时不同由所选计算实现与测量依据决定；不能用固定线性倍乘预先排除这种差异。首批功能验收可使用明确标记的参考耗时，真实 profile 在 M9 接入。

profile 必须注明模型或算子、设备、软件、dtype、形状、测量方法及适用范围。范围外输入默认拒绝；仅在配置显式允许时使用已说明且带状态标记的推算方法，记录次数及偏离范围，不得静默沿用单 Token 耗时。A100 实测可以作为 A100 计算依据，不能按峰值算力比例宣称完成目标 NPU 校准。

自行采集的真实路由必须固定模型权重、推理实现、精度和输入，按请求、阶段、Token、层保存并验证连续片段。公开轨迹先检查模型、精度和粒度是否匹配，取得文件后固定数据版本、校验值、选择清单及采集索引；发布者未披露的采集环境记为未知，不补写成已知。真实模型路由与目标硬件、目标精度同条件路由分别标注；随机权重、强制路由或合成轨迹不能标为真实模型路由。文件末尾不自动视为 EOS；筛选、截断及构造的片段退出条件必须声明。真实数据替换不改变上述输入消费与执行语义。

### 4.5 多层、多请求与多组组合

一轮指同一 EP 组为本次选定批次执行配置的完整层段。各 rank 的层依赖按实际计算、接收就绪及组合完成推进；本轮完成后才向本组 Scheduler 回报批次完成并选择下一批。不同组的轮次无需对齐，一组完成不等待其他独立组。

应让多请求批次、多层执行和多个 EP 组经过同一套可组合的计划与反馈路径，不能留下三个各自可运行、组合时互斥的演示入口。组合验收至少覆盖两组、多个层、不同 rank 批次大小及不同请求结束时刻，并在同一共享瓶颈上验证实际干扰。逐层静态放置变化也应经过组合路径核验。

已有 P/D 交接继续回归。是否在本版进一步组合多层 P/D、多个 P 组及多个 D 组，按所选研究场景单独安排；不把它默认为第一个连续组批任务的前置条件。

### 4.6 目标通信行为与规模

首个场景选择 CANN EP/MC² 的 Dispatch/Combine 行为基线，具体算子或内核版本、源码路径、算法和调用配置仍需固定并记录证据。HCCL 通用接口不自动等同于实际 MoE 算子路径。DeepEP 的既有源码核对可用于方法与参考模板对照；XCCL 可以作为后续独立场景，不是首个 CANN 场景的前置条件。

复现深度以影响网络流量、启动时刻和计算等待的行为为限：通信对象与贡献复制、数据和控制消息字节、阶段与同步作用域、分块顺序与并发、缓冲区复用、数据可见及资源释放条件，以及端侧准备和处理耗时。必要的量化、重排、同步等待等影响用依赖和局部 profile 表达，不要求逐条执行 AIV/MTE 指令、寄存器分配或完整本地轮询。AIV 内同步不能直接替换成额外的全 rank 屏障；MTE 方向也不能未经验证直接等同于 URMA READ/WRITE。

需要不同规则时新增独立模板及版本，保留参考模板的既有含义。若目标存在应用元数据、填充或不同精度，分别定义业务向量、元数据和线路字节，来源范围只覆盖其对应业务数据。不能把目标通信库名称加到配置后继续执行原参考传输，却宣称已复现目标行为。

SimCCL 可作为通信流与依赖生成层的设计参考，或在明确收益后局部复用；本版不将其或完整 SimAI 作为必需依赖。复用时将输出转换为现有执行计划，保留本次输入的逐 Token MoE 路由、来源状态及所选模板的非均匀字节分布，继续由同一 ns-3-UB 实例及实际完成事件推进。均匀 AlltoAll 不能替代逐 Token 路由，外部执行器的发送确认也不能直接替代接收数据就绪。

完整场景的规模验收安排在所需功能完成后的最后阶段，届时明确目标层数、EP 组及 rank 数、并发请求、输出长度、端口数、采样窗口和随机种子范围，再测量运行时间、峰值内存与输出体积。根据实际瓶颈调整按包记录、来源账本或流式输出，不能只提高请求数上限而忽略观测成本。不得预先宣称当前实现已在目标规模验证或必然耗尽内存。

拥塞、流控、拥塞控制开关和丢包重传分开描述。若选定实验需要开启当前尚未验收的控制模式或注入丢包，应先验证其事件生命周期、结束回收和真实重传观测；该要求不否定已有 UB 队列、信用及共享链路执行能力。

### 4.7 后端参数与事务模式

场景输入同时描述负载、部署、通信行为和 ns-3-UB 的有效配置。以下是参数合同范围，具体字段名与数值在场景输入适配任务中确定，不要求把所有后端内部常量都改成运行时开关。

| 参数组 | 应声明并保存的内容 |
|---|---|
| 访问与事务 | 访问模型、操作、协议发起端、请求和数据方向、传输角色及完成事件；数据、控制元数据可按实际行为使用不同 profile。 |
| 拓扑与选路 | rank/die/chip/server 与端点、链路和端口映射；带宽、传播及交换处理时间；平面、候选路径、通道建立方式、多路径和 packet spray 的实际配置。 |
| 分块与端点资源 | 集合消息分块、TA 分段、TP 数据载荷上限分别记录；发送槽、Jetty/通道在途额度，以及所选 LD/ST 路径适用的线程与 outstanding 额度。 |
| 交换与流控 | VL、调度方式、队列和共享缓冲、信用或其他已选流控参数。拥塞控制、故障及重传独立声明，关闭时保留不适用状态。 |
| 观测与复现 | 实际观测端口、事件位置、采样窗口、本地时钟、字节口径、来源记录、随机种子及固定依赖版本。 |

访问或编程模型与 RTP/CTP 传输模式是不同层的参数，不能混成任意可组合的枚举。在当前锁定的 [UbApp 实现](../third_party/ns-3-ub/src/unified-bus/model/ub-app.cc) 中，URMA READ/WRITE 使用 RTP 或 CTP 路径；`MEM_LOAD`/`MEM_STORE` 经独立的 `UbLdstApi` 路径，不应组合成“LDST + CTP”。底层存在入口不等于联合前端、事件反馈和观测已经支持。当前已验收的联合基线仍只有 URMA_WRITE/RTP；其他模式在选定实验确实需要时分别安排任务，未支持的有效配置明确拒绝，不静默降级为 WRITE。

新增模式须同时验证事务执行、数据就绪和调用完成、上下文与资源回收，以及相应数据包、控制包和重传的字节观测与来源关联。READ/LOAD 的协议请求由数据消费方发起，不能按请求方向错误标记业务数据方向；生产者准备、目标可读及消费依赖必须成立。包到达、反向 ACK 与完整数据可供计算使用分别核对，不能共用未经验证的 `RemoteWriteCommitted` 替身。

每次运行保存最终生效参数和配置优先级，包括场景选择、节点或链路覆盖、源码默认值与构建常量。集合分块大小不是 TP 包载荷上限，TP 数据载荷也不是整包线路字节。参数变化应能追溯到执行位置；不能只修改 YAML 中的值或只记录被覆盖的默认值。仅检查当前激活 profile 必需字段，未启用模式的参数不作为运行阻塞。

### 4.8 参数来源与实验就绪

场景选择、公开资料检索、版本固定、参考参数选择及可推导数值现在即可完成，不必等待 v0.3 功能实现。实现阶段负责证明这些输入真正影响计划、事务、完成反馈和观测。硬件测量用于校准，三者分别记录；已有场景 YAML 中的缺项不能一律推迟到版本完成后再处理。

参考网络实验的前提是激活配置完整、输入来源和假设明确、所需功能及因果反馈通过验证；没有测量依据的端侧或网络参数可以使用显式参考值及适当的敏感性对照。完整硬件校准不作为此类实验的统一前置条件。只有取得对应测量和误差证据后，才能声称复现真实硬件的绝对时延或容量极限。源数据访问尚未取得、真实文件尚未核验、所选模式未实现与硬件未校准，不能混成同一种缺项。

## 6. 验收要求

验收输入应足够小，能够独立计算预期结果；测试代码不得直接调用被测生成逻辑来生成同一份“预期”。有限样例用于证明行为，不用于反向定义允许的配置集合。

实现中途以小场景验证功能和受影响回归，在保留所验收行为的前提下使用少量 rank、层、请求和较短观察窗口。参数化、连续组批、多层多组组合、真实数据适配和通信模板均遵循这一安排，必要对照通过后不反复扩大中间验证规模。完整 CM384/R1 场景在所需能力就绪后作为最后的组合与规模验收，不作为每个小任务的通过条件。小场景仍需覆盖任务要求的真实 UB 联合执行，不能用计划导出或固定通信耗时代替。

| 验收项 | 必须证明的行为 |
|---|---|
| 参数化 | 原 EP4 样例保留十四次写、114688 业务字节及原等待语义；增加不同组大小、专家数、Top-K、非均匀放置和非恒等端点映射的对照；非法引用与映射在提交图前明确报错。 |
| 连续组批 | A/B/C 的实际批次成员符合第 4.2 节；每请求按自己的解码位置推进，提前完成的请求不再出现在后续批次，新请求在可用边界进入。 |
| 容量 | 预算变化改变实际接纳；暂时不足时等待且已运行请求继续完成，释放后接纳；单请求不可能满足容量时明确拒绝；无重复分配、释放或未建模重算。 |
| 路由与通信 | 不同请求和不同层的路由完整且各消费一次；参考模板按同 Token 同目标 rank 去重，CANN 等模板按各自规则核算；专家贡献、业务量、分块、元数据及来源范围可独立核算。 |
| 网络范围 | 同 rank、同芯片不同 rank、跨芯片三类对照均保留正确贡献和依赖；前两类 fabric 业务量为零，跨芯片使用实际 UB 事务；rank 身份、计算与容量不因芯片分组而合并或重复。 |
| 后端与通信模式 | 最终参数对应实际执行；只对已声明可用的模式验收，未支持模式明确拒绝；新模式分别核验发起与数据方向、就绪与资源释放、观测字节和正常回收。 |
| 组合与时间 | 至少两组与多个层共同执行，批次大小和结束时刻不同；共享瓶颈对比显示实际排队与完成变化，变化反馈到本组后续调度；独立组之间不增加逐层或逐轮屏障。 |
| 计算依据 | 实际批次、上下文与逐专家输入进入计算模型；总量相同、专家分布不同的对照可表达并按所选方法求值；有效范围外行为明确。 |
| 观测与真实性 | 端侧、端口和来源记录对应实际执行；整包与业务字节按各自口径守恒；开关来源记录不改变执行；真实、合成和参考输入状态可区分。 |
| 规模与结束 | 在声明目标规模和实验配置下记录时间、内存与产物；事件、图、发送与计算槽、KV 占用和上下文正常回收，无静默截断；观察窗口结束不伪造请求完成，按声明规则排空或清理的事件不计入该窗口。 |

阶段完成时运行必要的受影响回归，保留实际命令、目录、输入、版本、退出状态与日志路径。Python 计划测试不能替代参数或行为变化后的 C++ 构建及真实 UB 联合执行。已有功能基线包括写完成语义、连续图生命周期、动态到达、共享瓶颈、P/D 和观测；根据改动覆盖受影响部分，不机械重复无关的大规模实验。

最终验收需要一份在声明配置下组合所选能力的运行记录，并分别报告功能范围、路由来源、计算依据、通信匹配和校准状态。CANN 行为模型至少独立核算小型样例的贡献、字节、阶段依赖和有限并发，检查链路排队变化能够反馈到接收、计算及后续批次，并在研究实际使用的采样窗口下检查关键分块、并发和局部耗时的敏感性。尚未取得真实轨迹、硬件测量或目标行为证据时，不以合成样例通过将相应项目标为完成；已满足第 4.8 节条件的参考实验可以开展，未启用的 XCCL、事务模式或完整内核复刻不作为验收门槛。
