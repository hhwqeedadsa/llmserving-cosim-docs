# 代码、外部依赖与研究迭代的组织方案

本规范面向同时维护仿真平台和网络研究的仓库：公共代码回答“如何正确执行”，实验回答“某个网络机制是否影响业务”。目标是让新人能从一个结论找到配置、来源、平台版本及运行证据，也能切换网络后端而不复制整套前端。

下面区分现有目录、拟迁移结构和验收步骤。**本轮交付规范与必要入口，没有批量移动现有模块，也没有建立空目录或声称 RDMA 后端已实现。** 具体执行语义仍以[架构](architecture.md)、[后端](../backend/README.md)及[开发维护](development.md)为准。

## 1. 当前结构的优点与风险

| 现有结构 | 好处 | 需要改进的具体问题 |
|---|---|---|
| `python/moe_ub_cosim/` | 命令、调度、路由、图、记录均在一个可安装包中 | 领域模块平铺，容量/来源/实验采集/调度间的边界不易识别；新增后端容易继续把逻辑加进 `user_workflow.py` |
| `backend/` | 有真实 ASTRA/UB 适配、完成事件和记录，不只是离线 trace 拼接 | `cosim_service.cc` 等文件承担较多职责，服务控制、图装载和 UB 配置耦合；新增 RDMA 若直接加条件会扩大风险 |
| `third_party/` | 固定版本 gitlink，ASTRA 由 LLMServingSim 父依赖管理 | 不应在根目录再复制第二套 ASTRA；不同 ns-3 的头文件、动态库和输出不可混用 |
| `experiments/` | 研究有独立方法、配置和结论，已有观测/真值隔离要求 | 索引曾把 Scale-Up 筛选称为“唯一当前入口”，与新增 Scale-Out 不符；临时探针应进入有明确目的的实验，不散落根目录 |
| `tests/`、`fixtures/` | 小输入和历史验收摘要可核查 | fixture用于验证平台，不能偷换成正式实验的来源或成为实验的隐式驱动 |
| `data/`、`runs/`、`build/` | 大数据、产物和构建不污染源码 | 忽略目录不能随意清理；实验摘要要能找回输入hash和运行清单，否则换机只剩一张图 |

重点不是把文件夹变多，而是把**服务控制、工作量定义、传输实现和实验评价**的依赖分开。现有真实路由、动态反馈和明确身份应保留，不能为统一接口退化成固定结束时间或均匀流量。

## 2. 根目录的长期职责

| 路径 | 应放内容 | 不应放内容 |
|---|---|---|
| `python/moe_ub_cosim/` | 稳定的配置、来源校验、调度、图生成、公开执行/读取接口 | 某篇论文的条件组合、特定实验收益判断 |
| `backend/` | C++控制、ASTRA适配、网络适配和被动记录 | 数据下载、绘图、调参搜索；同一目标链接两套ns-3 |
| `third_party/` | 正式构建依赖，精确版本、许可证与父级gitlink | zip源码副本、随手clone的对比平台、大模型权重 |
| `examples/<use_case>/` | 无外部账号也能运行的小配置、说明 | 历史机器绝对路径作为必需输入、完整研究数据 |
| `tests/unit/`、`tests/integration/` | 输入与执行不变量、真实小流程、错误路径 | 要求某算法必须获得正收益的断言 |
| `fixtures/<behavior>/` | 小型测试输入、预期、验收来源摘要 | 把几GB原始路由压缩后提交来“保证复现” |
| `experiments/<question>/` | 一个稳定研究问题的方法、配置、探针、分析和必要结果 | 整份平台源码快照、每轮一套后端复制 |
| `docs/` | 使用、现行架构、维护、研究报告和决策理由 | 大量命令stdout、同一进度的多份副本 |
| `scripts/` | 依赖和仓库维护、受控获取等维护工具 | 第二套面向用户的仿真入口 |
| `data/` | 固定来源、原始/派生数据、研究clone | 凭证、待提交平台源码的唯一副本 |
| `runs/` | 一次执行的有效输入、manifest、日志与产物 | 最新公共脚本的唯一副本 |
| `build/` | 按工具链与后端隔离的编译目录 | 模型数据、跨ns-3版本共享的输出目录 |

`README`回答“能做什么”，用户指南回答“怎么操作”，研究报告回答“发现什么/证据多强”。进度只维护 `docs/tasks/current.md`；迭代记录不成为第二份每日进度表。

## 3. 公共代码的目标边界

以下是**随实际修改逐步形成的目标**，不是当前可导入的包路径：

```text
python/moe_ub_cosim/
  cli.py                  # 保留统一命令，按子命令延迟导入
  config/                 # schema、配置解析、单位与路径
  workload/               # 请求、真实路由、token与训练microbatch定义
  models/                 # 计算、容量、通信模板；来源与适用范围
  graph/                  # 计划/Chakra生成与身份、资源校验
  runtime/                # 推理调度、控制协议、执行与结果校验
  topology/               # placement、NIC/rail、路由及容量审计
  records/                # observed/truth格式、稳定读取和有界导出

backend/
  common/                 # 无特定ns-3类型的计划、身份、单位、控制与记录定义
  astra/                  # 图装载、资源与完成事件适配
  networks/ub/            # 现有UB实现
  networks/rdma/          # 新非UB实现；实际开发时才创建
  drivers/                # 分别构建的UB/RDMA服务入口
```

不要一次迁移所有模块。每个迁移记录原路径、新责任和导入关系；先补能检查真实语义的现有小例，再移动，确认公开CLI、序列化结果和小例记录等价。历史复现使用固定Git版本，不要求永久保留所有内部import的兼容包装。

建议的实际映射：

| 当前模块 | 目标责任 | 迁移触发条件 |
|---|---|---|
| `route_evidence/route_selection/route_records.py` | workload来源与逐token读取 | 首次增加训练来源格式时，复用校验而非再造解析器 |
| `plan/cann/native/full_model.py` | models通信模板与graph构建 | 改非UB通信模板时，先分开“字节/依赖定义”和“后端传输” |
| `configured_scheduler/full_model_service.py` | runtime推理调度 | 新后端接入时保持请求、KV与轮次语义；训练另有工作量入口 |
| `fabric/locality/scaleout.py` | topology与放置 | 增加NIC/rail配置时明确哪些字段只对UB生效 |
| `bounded_export/research_slice/record_storage.py` | records及有限执行归档 | 增加RDMA记录时保留schema版本及能力范围 |
| `ub_network_adapter/ub_write_transfer.cc` | networks/ub | 新RDMA目标出现时隔离，UB回归仍通过 |
| `cosim_service.cc` | drivers + common/astra职责 | 首先提取不依赖UB配置的控制/图推进，避免新建一份完整拷贝 |
| `port_observation.cc` | 后端事件适配 + 公共记录 | 区分UB物理出口与RDMA NIC/交换机队列语义，不能只改列名 |

依赖应大体为：配置/来源→工作量与模型→图→执行；记录schema不依赖实验。训练工作量可以复用图和网络，但不应塞进推理请求调度器假装训练。实验通过公开CLI/稳定读取器进入平台，平台不导入 `experiments/` 或 `tests/`。

## 4. 新RDMA后端的构建和能力边界

本仓正式依赖仍为父仓库锁定的 `third_party/LLMServingSim`、`third_party/ns-3-ub`；ASTRA及其原生ns-3由父依赖继续固定。本轮阿里clone在 `data/research/`，仅供独立探针，不因存在于磁盘上就成为正式平台依赖。

正式接入需要同时交付：

1. 独立构建目标及固定依赖。UB目标只链接ns-3-UB；RDMA目标只链接选定派生库，使用不同输出和运行库搜索路径。先保证一个后端完成小例，再考虑如何选择。
2. 稳定的工作量/事件接口。传输至少有唯一身份、src/dst、字节、依赖、数据就绪和事务回收；协议内部QP/ACK不泄漏成业务必须理解的设置。
3. 明确的后端能力声明。拟加入backend名称/commit、传输协议、精度、NIC与拓扑范围、完成语义、支持的观测、可重放范围；这些是待设计字段，不能假定现有manifest已有。请求的能力不支持时启动前拒绝，不能静默改用UB或理想带宽。
4. 同一执行内共享时钟和拥塞状态。多个EP组共用网络，后继计算由本次网络完成推进；不能把独立运行的scale-up/scale-out时延相加。
5. 版本与构建来源。先在依赖内保存源码与测试，再逐层保存gitlink和锁文件；不升级无关依赖。`deps.lock.json`用于正式依赖，实验来源记录用于对比clone，二者不能互相替代。

若最终需要同一业务同时经过本机与跨机网络，应在选定后端内以共享事件队列表示本机链路和RDMA，而非混链两套ns-3。真实NVLink/PCIe开销暂未校准时明确其近似，不把 `NVSwitchNode` 名字当硬件真实性证明。

## 5. 一轮迭代放哪里

**研究按问题建目录，迭代按Git提交和记录编号保存。** 例如“真实路由导致的跨机热点”是一个实验问题，里面的batch/EP/带宽变化是配置条件；“第7轮”“第8轮”不是新的平台根目录。

有内容时使用下面结构；不是要求现在创建全部子目录：

```text
experiments/<research_question>/
  README.md                 # 问题、入口、来源与结论导航
  plan.md                   # 假设、对照、验收范围
  configs/                  # 各条件有效参数或可复现参数矩阵
  probes/                   # 有界、独立的源码/协议探针
  analysis/                 # 读取明确输入的统计与画图
  tests/                    # 分析程序自身的非泄漏/统计检查
  results/                  # 小型指标表、证据索引、可分享图
  conclusions.md            # 结论、反例、适用范围和未验证项

docs/iterations/<iteration_id>.md  # 本轮结束时才保存精简决策/提交/证据链接
runs/<research_question>/<run_id>/ # 大产物，沿用平台运行manifest
data/<dataset>/<revision>/        # 原始来源，不修改原件
build/<backend>-<toolchain>/      # 每套ns-3单独构建
```

已有 `scaleout_backend_review/` 和本轮 `scaleout_scaling/` 是有实际内容的小型探针实验，保持可用，不为了套树形图迁移或复制。后续首次建立系统的热点研究时再按需增加 analysis/configs。

一轮记录建议只写：研究问题和限定条件；对应平台与实验提交；实际改变的因素；运行manifest及摘要入口；发现/反证；下一轮最小待验证项。工作中的状态仍只写current，结束后再冻结迭代说明，避免两份动态台账。

配置名表明研究因素，例如 `ep64_b1_uplink400g.json`；run_id区分重复次数、提交和时间。随机种子、真实来源修订、请求子集、专家放置、通信模板、精度和观测窗口必须进入有效输入。只有文件名或一条“设置为1024”无法复现。

## 6. 数据、产物与可复现性

| 对象 | 保存方式与边界 |
|---|---|
| 原始路由 | 固定数据集修订、路径、hash及使用限制；克隆仓库不自动获得访问权限 |
| 派生通信图 | 绑定原始路由、请求/训练microbatch、放置及通信模板，不预置网络完成时刻 |
| 执行输出 | 有效输入、平台/依赖提交和工作区状态、预算、真实命令、退出状态、事件与摘要 |
| 采集数据 | observed只包含声明开放的观测；truth用于评价，算法不得依赖其理想关联 |
| 分析结果 | 明确读哪些字段、过滤/窗口、单位、统计方法及原始run；保存画图程序和必要小表 |
| 失败运行 | 保留退出原因、限额与已有产物，不能只保留最后成功图 |
| Git内容 | 源码、配置、测试、小摘要；不含受限数据、令牌、大构建或全部逐包日志 |

沿用现有运行清单记录有效配置和版本；研究侧只补“条件→run→指标”的索引。容量估算、synthetic功能检查、真实来源统计、硬件校准和真实性结论分别标记。不同GPU/精度或训练与推理不能只改标签共用同一份时序结论。

千卡日志需预先限定端口/层/时间窗口；大规模结果备份位置和保留策略应随运行记录保存，Git忽略不是备份。清理仅限明确属于当前任务且能再生的产物，不能为了扩容删未知旧实验。

## 7. 渐进实施顺序与验收

| 阶段 | 动作 | 验收与风险控制 |
|---|---|---|
| 当前整理 | 新报告、索引、公共核算示例、实际内存探针 | 无源码搬迁、无gitlink变更；帮助/链接/小流程有效 |
| 首次RDMA接入 | 提取必要的公共控制和事件定义，独立网络目标 | 边界消息完成一次、零流量、图推进、网络排空；UB既有小例不受影响 |
| 拓扑扩展 | NIC/rail/链路/放置schema及容量检查 | 同机/跨机/跨leaf路径、端口容量、带宽生效对象可独立核对 |
| 来源扩展 | 训练路由/依赖输入，明确accepted/drop及前反向 | 真实训练来源与推理来源严格区分，单microbatch字节独立核算 |
| 规模工程 | 动态端口计数、惰性QP、元数据与日志预算 | 先保持小例事件/统计一致，再实测16/64/256/1024资源；不把省内存变成改语义 |
| 领域迁移 | 按上表逐域移入子包/子目录 | 独立迁移提交，公开CLI和序列化等价；与网络行为修改分开 |

平台修复和实验条件分别提交；研究若发现缺陷，先修平台最小用例，再重跑受影响条件。验收不要求某策略“必须更快”，也不以大规模任务能结束代替接口正确性。

最终应做到：研究者复制一个示例，填写模型/真实路由、batch、并行组、物理放置与网络条件，通过同一套公开接口得到有来源和预算的结果；开发者能更换通信实现而不重写调度、数据导入与分析。非UB后端和训练能力完成前，文档保持相应限制。
