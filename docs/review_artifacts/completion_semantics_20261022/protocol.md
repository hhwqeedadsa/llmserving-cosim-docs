# Dispatch窗口完成语义敏感性（执行前固定）

从干净`a6229b8`开始，上一轮为实质进展。本轮核查既有Dispatch数据微基准的全ACK窗口条件对时间和排序的影响，不开发新排程算法、不宣称哪个条件就是现代DeepEP或生产推理。

固定原研究四请求、层4/32的Decode入口5/6、三放置、两上层速率和三ECMP种子，共18个已完成ACK条件；保留其原始结果，不重跑。仅新增18个accepted依赖条件：将每个非首窗口对上一窗口各工作的`after.event`从`acked`改为`accepted`。全部工作ID、连接、字节、输入顺序、GPU/NIC/wire port、depth1、路由seed、协议/拓扑和观测预算不变。窗口根工作仍0ns；后续就绪严格由本次真实连续接收回调推进，不能把旧实验的时间写入新任务。

此微基准的工作是相互独立的有界字节写入，不复用同一源缓冲的真实张量数值；它没有计算、Combine、跨层控制或现代信号/flush。`accepted`只表示本连接字节前缀连续接收，不是GPU可见/完整应用安全完成。两类应用依赖都与真实源队列信用分开：depth1的旧工作仍须收到完整ACK才能释放槽；新工作即使已就绪，也不能提前发布到在用槽。相同QP保留序号及拥塞状态，全部窗口共享一个Simulator。

先在已有ACK记录上给出各关键窗口数据/ACK传播、序列化、交换排队和源尾包偏移的分解。ACK传播是协议反馈时间，不自动等于可以消除的业务损失。新对照的竞争解释：

1. 全ACK窗口条件明显增加串行等待：新条件可提前满足应用依赖；如果整体不变，应检查同连接ACK信用是否已阻止提前发布，不直接称网络无影响。
2. 共享物理出口的流量总量足以确定性能：输入和路径计数相同而完成改变时，它只能解释必要服务量；不能把“没有新字节”说成没有新的时序竞争。
3. 放置排序主要由窗口条件造成：逐种子/速率报告两种LPT及连续方案的排序是否改变，保留不变和仅几ns的差异。不能把故意放宽微基准依赖当作可部署的新算法。

主要结果为整体连续接收完成、最终ACK、排空；每窗最早/最晚就绪、发布、连续接收及ACK。accepted条件中不同窗口的ACK区间可能重叠，不能再将每窗ACK时长相加，也不能把逐窗最忙端口服务量之和自动当整体下界。仅全运行单一出口累计模型字节/速率的最大值作为无条件服务量下界，并明确传播及源信用未包括。

独立核验两组工作输入除依赖事件外逐字段一致；实际每源连接序号/packet payload/物理路径与总端口发送量保持；所有数据及ACK逐包路径/哈希、端口队列积分、连续接收和ACK因果核对。分别检查真实accepted回调使依赖就绪、同连接旧ACK前不发布和全部真实ACK后资源退出。遇到新ECN/PFC/CNP或分析器不支持事件时保留，不删记录或把新流量归零。

研究只用公开CLI/格式，不导入tests/fixture/平台内部生成器，不改变平台/固定依赖，无新构建安装下载。每命令60秒/RSS1GiB/地址2GiB，仿真5ms、单终态16MiB/100000捕获事件、运行器64MiB；准备/分析各32MiB、累计128MiB/300秒、卷预留8GiB。目录`/dev/shm/moe-completion-semantics-20261022/`。失败保留，不抬限或自动重试。旧记录仅只读且按hash检查，本机检查点保留输入/结果与必要来源；不将四请求推广为独立生产样本。
