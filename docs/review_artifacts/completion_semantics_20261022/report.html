实际做了什么

沿用四个R1真实路由请求，取(层4,入口5/6)、(层32,入口5/6)四个窗口。 EP4逻辑rank映射到四台服务器、两个Pod的GPU 0/2/4/6；物理拓扑含8个GPU、4个ToR、4个汇聚、2个核心交换机， 四个GPU实际承载任务。接入100Gb/s，上层100或25Gb/s，每链路传播1μs，ECMP种子11/29/47。 每份Dispatch数据14,464B，12条持久连接，每连接队列深度1。

比较连续放置、按全部Prefill统计分配、按尾部10个Prefill token统计分配三种既有方案。 后两者使用LPT（优先分配较重专家的负载均衡规则）。本轮没有改变放置，只将后续窗口的应用依赖从前窗全部 acked改为全部accepted。原18组网络结果只读保留，新增18组真实网络执行，全部窗口共享同一网络与仿真时钟。

三个时刻必须分开

时刻本模型的含义对后续传输的作用
accepted：连续接收目标传输层已连续收到工作对应的字节新条件用它满足下一窗口的应用依赖
ready：应用就绪声明的前驱事件都已发生不保证本连接还有可用发送槽
acked：发送方确认发送方收到覆盖相应字节的实际ACK两组都用它释放原队列槽；深度仍为1

每个工作实际发布时间都满足：published = max(应用就绪时间, 同连接上一工作ACK时间)。 新条件中共有270个工作已就绪却等槽，最长6,230ns。 例如seed11/上层25G/连续放置中，工作29在21,551ns就绪，仍等工作13的ACK到27,781ns才发布，等待6,230ns。

适用边界：这里是独立字节写入，不复用真实张量源缓冲。accepted不代表GPU可见、计算可启动或源buffer安全复用； 未执行计算、Combine、完整现代DeepEP/GIN或真实GPU。协议ACK也不是现代通信库的完整完成语义。

验证到了哪里

配对核对22,140条数据/ACK包的形状与物理路径、720个物理端口计数，全部一致（仅排除时间戳与包UID）。 新条件独立检查116,280次物理发送、94,140次ECMP选择、738个工作回调、576个交换出口队列积分、72个窗口。 两次只读包分析逐字节一致；修订后的比较器按内容hash识别旧结果，再分析所得JSON也逐字节一致。 另建真实根目录、以目录符号链接指向未改变的原输入，迁移根目录后的比较结果也逐字节一致；未复制大文件或重跑网络。 原ACK条件用修改后的检查器重新核验通过，没有重跑旧网络。全部无ECN、PFC或丢包，所以不能据此证明拥塞控制长尾。

18个新增网络条件及6次拓扑CLI共耗宿主20.54秒，进程树采样峰值RSS 416.14MiB。这是仿真器宿主资源，不是GPU显存或推理耗时。 无安装、下载、依赖变化或平台构建。准备阶段补拷贝未变化truth供独立核验，记录已保存，发生在网络执行前。

对论文方向的实际影响与下一步

这轮排除了“此前放置排序仅由全ACK窗口造成”的解释，但也说明只有流量和路径计数不足以精确确定完成时间。 尚未证明新的网络机制或算法；之前的简单链路基线很强，下一步应先针对它解释不了的真实在线依赖研究，避免用更多参数组合替代贡献。

  1. 先完成现代通信库完成事件、可见性、源缓冲寿命与队列信用的逐项对应及最小验收；本轮accepted配置不能替代这一工作。
  2. 补独立请求与可匹配的GPU/RDMA实测，对真实并发、共享链路和热点变化进行校准；当前四请求不足以证明泛化。
  3. 固定强链路基线与现有拓扑感知方法，只有出现不能由简单机制解释且有实际影响的问题，才进入新策略和留出评价。
  4. 千卡证据仍仅有此前1层×2轮、256个EP4副本的人工短任务；完整48层真实推理和EP1024均未验收。
