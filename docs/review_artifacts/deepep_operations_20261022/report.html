真实路由操作计划与网络后端边界

本轮把上一轮的语义差异落实为公开离线工具，并用四份真实请求验证。现在可以逐项检查数据、通知、逻辑连接上下文和设备侧完成依赖；尚不能执行对应的DeepEP包级网络或预测时延。对高水平论文的直接价值是排除错误建模和不成立的优化假设，研究贡献本身仍未建立。

平台提交为0cc140f，与后续研究代码、结果分开。新接口见操作计划示例，实际结果见summary、来源和带资源记录的命令。

1. 本轮完成什么

新增scaleout deepep-plan：根据显式选择生成每个token×expert的数据操作，保留零贡献count/flag，给每个操作分别记录提交、目标接受、GPU可见和发送工作完成的接口事件。逻辑QP key跨Dispatch/Combine与后续调用保持一致，但没有创建物理QP。buffer epoch标记调用次序，不自动宣告源缓冲可以复用。

新增deepep-check：核对保存表示，再计算没有时间的依赖闭包。--withhold暂扣一个接口事件，用于辨认哪些后续设备完成依赖它；不是丢包、重传或延迟测量。默认async_finish=False表示计算流等待通信流，不意味着CPU API调用阻塞。

平台通过九项单元反例、八条新目录公开命令与十项拓扑回归。单元反例包含两专家同目的地仍各发数据、空rank仍发通知、QP逻辑上下文跨调用、通知前的数据、目标消费与后续buffer清理依赖，以及精度、预算和篡改拒绝。这些是功能与因果范围检查，不是GPU/NIC校准。

2. 真实输入与实际结果

使用已取得的1472、1808、2675、6447四份R1-AWQ/MMLU原件，固定数据修订27febb7b2d24169560a9f6f83d38eb53f94916cf。每个文件只分配给一个逻辑rank；选择Decode入口1、2各自的源层3、4，得到16条原始token/层选择记录，按原始顺序组成四次MoE调用。

它是截取的MoE调用程序，没有其余模型层、attention、到达过程或实测计算时间；不意味着两层后模型就生成下一token，也不声称四卡能部署完整R1。BF16、四rank、连续等量专家放置、关闭跨rank P2P和单NIC是声明条件，数据集不提供这些部署事实。

六条正式命令均成功。最大子进程峰值RSS为94,572KiB，单命令最长约0.63秒，研究目录约17.1MiB，均在预先声明的60秒/单例、300秒/整轮、1GiB RSS、2GiB地址空间和64MiB新产物预算内。Linux wait4提供逐子进程资源统计，另采样进程树RSS。初次预检发现本机没有/usr/bin/time，在创建结果目录前停止；改用标准库wait4，没有安装工具、扩大限额或执行新网络。

3. 哪些“直接优化”不能成立

共有32个设备侧通信kernel完成节点，即四调用×两个阶段×四rank。正常依赖闭包全部可达；以下是暂扣接口事件的逻辑反例：

暂扣对象可达完成节点阻塞完成节点解释与边界
无320基础部分顺序无环，全部可达
首次Dispatch中rank 0给专家64的零count可见事件329专家属于rank 1，rank 1不能完成Dispatch，也不能发后续Combine通知，整组本次Combine及后续调用被阻塞
首次Combine中rank 0需要的专家64 flag可见事件725其余三个rank可先进入下一次Dispatch，但该Dispatch的接收最终仍需rank 0参与
首次一条数据put的sender_done事件320本应用图不直接等待发送反馈；未建模NIC队列/CQ/源buffer，不能据此说真机ACK延迟无影响

因此，空专家不是“没有通信、无需等待”；去掉整组完成屏障也不等于消除真实集合通信依赖。另一方面，不能用每条SEND都等最终ACK的模型替代GPU数据/通知完成，再把删除该等待得到的差值当成可部署收益。

这些反例只判断某条依赖是否必要，不给出等待多久、是否位于实际关键路径或能省多少时间。它们是实现验收条件，不是新调度算法或论文创新。

4. 网络后端还缺什么

新增的源码定位证据固定文件hash、Git blob和必要行号：ibgda_device.cuh为nonfetch调用构造MLX5_OPCODE_ATOMIC_MASKED_FA，使用4B操作数、返回缓冲地址和CQ更新标记。不能由函数名推断没有原子响应或完成资源，也不能把操作数宽度当线上包长。实际原子请求/响应、确认合并和NIC执行代价仍需协议依据与测量。

当前适配路径Fabric::Send/Inject只接收消息字节，原生RdmaHw::GetNxtPacket按剩余字节/MTU构造Seq/UDP/IP包；该路径没有接收本计划的原子verb、远端地址和值。完成路径又以固定QP总字节结束并删除QP。因此，仅把计划中的通知转成4B普通流，或复用端口号，都不足以实现目标库模式。

后端工作需要实现及验证的内容不能替代它的做法
持续QP与可追加工作分离连接、工作条目和字节/包序号；空闲保留状态；只把已就绪工作加入发送；工作完成与连接关闭分开预先注入未来层字节、每消息重建QP后搬运一个RTO值
写与原子操作数据写和4B原子加分别定义目标作用、响应和完成；同QP顺序、重复请求和重传语义明确全部变成只有长度的普通消息
GPU消费与buffer对接accepted、visible、发送工作完成、消费者结束；分别处理目标buffer清理与源buffer保留看到最后包就释放所有资源，或把CUDA event等同全部ACK
物理连接与网络把逻辑peer/expert key映射到实际NIC、连接与选路；按选定RoCE或IB设备校准因示例用了H800/CX7 IB就宣称当前RoCE式模型已校准

下一步应先固定运行时与协议目标，再按这些反例设计最小后端接口。没有模型依据时不擅自改锁定依赖；当前现有在线RDMA路径保持原行为。

5. 论文目标需要的版本和证据

本轮针对的是已有核对基础的v1.2.1，不是对最新库的泛化。2026-10-21取得的固定DeepEP README blob显示V2/V2.5已采用NCCL Gin、统一EPBuffer，并明确移除V1/NVSHMEM。该快照只证明公开文档所述API变化，没有证明新内核的通知和QP实现。源码身份和短摘录见上面的定位证据。

所以不能把“补齐旧版DeepEP模型”直接作为A类贡献，也不能拿旧版最弱模式作为唯一强基线。正式研究须固定一个与可用设备匹配的现代实现，重新核验其协议和完成语义；若选择旧版作校准对象，应明确适用部署，并以当前实现检验方法是否仍有增量。

当前最有价值的待验证问题仍是：真实非均匀MoE路由、多EP组共享Scale-Out链路时，哪些控制/数据/资源依赖导致显著业务损失；已有库、简单批量通知或同信息调度基线是否已足够解决。先用匹配测量和强基线证明问题，再决定机制；不要因为通知多就预设它是瓶颈。

真实两机RDMA、留出请求和千卡长工作量完成证据仍缺失。近期可交付的是有边界的操作语义、可复现反例和受校准的网络模型；网络/系统/仿真论文都还需要重要性、近邻差异、现代强基线与泛化证据，最佳论文仍是质量追求，不是目前结论。
