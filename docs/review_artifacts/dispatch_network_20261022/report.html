Prefill放置的数据传输、实际路径与交换机排队

本轮把前阶段的真实专家选择接入了原生RDMA ns-3，完成三种专家放置、两种上层速率的6组数据传输实验，以及1次固定重复。结论是：只让专家的计算输入更均衡，不保证网络传输更快；总发送量也不能单独解释完成时间。 这里的结果限于固定四请求、四轮Dispatch数据微基准，还不是完整现代DeepEP、端到端推理或千卡结论。

当前论文目标仍在进行中。这组结果增加了可以逐包核对的网络机制证据，但“总量相同而路径负载不同”“较慢上行导致排队”本身是已知网络规律，不能直接包装成新算法或A类论文贡献。

研究对象和固定条件

前阶段对照来自Patterns behind Chaos作者的公开Prefill计数放置实现，已经独立验证。这里固定使用三种已生成的放置：连续分配、按全部Prefill频次做容量约束LPT、按最后最多10个Prefill token频次做同类放置。LPT表示依次把高频专家放到当前计数最少且仍有容量的rank。规划不读取未来Decode。本轮不重新调整放置，不按新网络结果挑选窗口。

两种速率使用同一拓扑和相同ECN字节阈值32KiB/128KiB，旨在检查上层速率敏感性，不是相同建设成本下的架构比较或硬件参数推荐。实验设计、输入SHA及竞争解释在运行前固定于实验协议和配置。

这些完成路径上的ACK产生间隔和交换机等待均为0。其他包的ACK可能排队，不能据此声称整个网络没有ACK排队。就绪到尾包发出的时间包含NIC发送仲裁、同源连接竞争等，不能标作GPU开销。

逐包还核对了：源序号连续、源有效负载等于操作字节、包不跨工作边界、发出与到达的物理端口相连、端点不作为中转、每跳传播加序列化与时差误差不超过1ns。全部路径均为终端不转发条件下的最短路径；另根据锁定源码的地址、wire_port、seed和32位哈希独立验证了32,040次交换机出口选择。

每个交换机出口按enqueue/dequeue重新积分队列占用；再按每个包的“包长×驻留时间”独立求和，两者与导出的队列积分一致。队列积分单位为字节×纳秒，不能直接当作可消除的业务时延；最忙出口的字节/速率也只是服务量下界，未必对应完成轮的最后一条路径。

没有ECN标记，不代表没有排队

所有六组无丢包、ECN标记或PFC暂停。上层25G队列峰值33,616B虽然超过32KiB，仍未产生ECN，不是数据相互矛盾：hook记录总队列并包含刚入队的包，而锁定switch-node先从MMU移除出队包，再按该优先级队列剩余量判断ECN。独立重建的数据队列在出队后的最高剩余量只有32,580B，低于32,768B。源码身份和hash保存在核验材料中。

因此本轮支持的是正常无故障网络中，放置与实际汇聚路径引起的数据传输差异。它没有触发拥塞反馈控制，不能用于证明DCQCN参数优劣、ECN优化或丢包恢复策略有效。

复现与记录

准备只读取原件、固定放置和配置，分析只读取observed与公开输出，独立检查才读取truth和原始选择。入口、预算、产物及失败处理见实验README。本轮使用9条公开CLI：两次拓扑导出、六次条件执行和一次固定重复；原生动态库身份已核hash，未混入UB。

独立检查共覆盖4份原件/16条选择、244个工作回调、7,320个数据包及ACK的lineage、39,360次物理发送、142,800条捕获事件、192个交换出口队列和24轮完成。每份数据均拆为15个源包且没有重传；UID在本次核验范围内对应一条无循环传输路径，不把它当成任何网络中都唯一的包身份。

固定all100g/contiguous重复的result.json逐字节一致；分析四项产物独立重复也逐字节一致。首次检查器因局部变量load遮蔽读取函数而在读取输入前失败，已更名并保存原失败日志；真实仿真没有重跑。之后针对已观察到的ECMP汇聚和ECN口径增加了有依据的只读检查，未扩展实验矩阵。

每命令60秒、RSS1GiB/地址空间2GiB、仿真5ms、单次产物64MiB，新增累计128MiB，卷预留8GiB。六条件与重复的整运行器宿主墙钟约11.04秒，采样进程组峰值RSS约416.58MiB；这不是网络仿真时间、硬件吞吐或千卡可扩展性数据。逐项资源记录、精确命令、输入与hash及原始包队列结果都保存在本地检查点，Git仅保留必要摘要和复现代码。
