# MoE推理全栈联合仿真：三页材料配套讲稿

日期：2026年10月20日（北京时间）

建议讲述时间：约7—9分钟。第一页为原模板封面与简短自我介绍，后两页保留原有正文结构，说明现有联合仿真与拟增细节。下文可直接讲述；PPT备注也保存了逐页正文。

## 第一页：封面与汇报人介绍

大家好，我是李润宇。目前主要研究MoE推理中的通信与网络问题。这项工作同时关注两种互连：Scale-Up是设备或服务器内的互连，重点看UB端口、发送资源和队列；Scale-Out是跨服务器网络，重点看NIC、交换机、RDMA及多机共享出口。今天介绍我们怎样把请求与专家选择、计算和通信依赖、包级网络及完成反馈连接起来，以及下一步要增加哪些细节。

## 第二页：全栈仿真——让网络等待回到推理服务

我们的目标，是解释MoE推理中的机内和跨服务器通信为什么会拖慢生成，并比较在相同资源下，怎样的部署和通信方式更合适。研究重点是网络：token被送到哪些专家，这些专家放在哪些设备上，通信经过哪些机内端口、NIC或交换机出口，最后怎样影响本轮以及下一轮Decode。

这里说的“全栈”，是把请求调度、计算与通信任务、网络传输和服务反馈连接起来。它并不意味着已经模拟了GPU每个时钟周期，也不意味着已经覆盖训练、Prefill和所有推理模型。

这条链路分成五步。第一步，由LLMServingSim根据请求、batch和KV状态选出本轮任务，并读取相应请求在当前层、当前Decode位置的专家选择。第二步，结合专家放置，把这些选择变成明确的计算、发送和接收任务，算清设备之间的通信字节。第三步，用Chakra保存依赖，由ASTRA在前驱完成后执行任务。第四步，根据研究对象选择独立的网络后端：Scale-Up使用ns-3-UB表达设备端口、STORE/LOAD和内部队列；Scale-Out使用原生RDMA ns-3表达机内简化织构、跨机NIC、交换机队列和拥塞反馈。两条后端分别运行，不能把两次仿真耗时相加。第五步，后端将实际完成反馈上去：数据就绪后，后续计算才能继续；整轮完成后，前端才能推进请求和下一轮组批。

因此，我们输入的是带依赖的任务，开始时间由前驱和网络实际完成决定。一次Scale-Out运行中的多个推理副本共享一套持续的RDMA网络；一次Scale-Up运行使用自己的UB网络。两种结果分别解释各自的等待，网络慢了，会改变后面的计算和服务进度。

Scale-Up方面，128个计算端点、1024条真实来源请求的完整首轮已在UB后端执行并核验。在一个等资源对照里，目标出口队列积分增加57.60%，完整首轮只延长0.1532%；这提示我们必须把局部排队与关键路径区分开。Scale-Out方面，四份真实R1路由完成了4卡、两台服务器、两个Pod、两层两步的接入；128卡单EP与256、512卡多EP4副本也有完成证据。这些任务与网络模型不同，不能用完成时间互算扩卡收益。Scale-Out千卡两次在600秒预算处超时，尚未完成验收；目标硬件计算成本也仍需校准。

## 第三页：拟增加细节——机内与跨机网络机制

接下来，我们围绕同一个问题同步深化Scale-Up与Scale-Out：真实专家偏好和物理部署，在什么条件下会形成机内端口或跨机网络的关键等待，怎样在相同总资源下减少这些等待。

第一类细节是路由与通信组织。Scale-Up继续分析真实路由下的STORE/LOAD、发送资源与响应拆分；Scale-Out保留专家热点持续性和专家共选关系，研究目的节点去重，以及“机内汇聚、跨机交换、机内分发”的分层通信。打包、转发、合并和缓冲代价都要计入。热门专家不必然造成跨机拥塞：如果它在请求本卡，跨机流量可能更少。

第二类细节是物理连接与分层容量。Scale-Up要核查机内交换端口、有限缓冲、信用和发送槽；Scale-Out已有Clos、Agg、rail和平面的参数化输入，还要补清GPU与NIC亲和、共享NIC、跨rail中继和实际分流机制。比较方案时固定总带宽和端口预算，防止将增配硬件的收益算作算法收益。现有小例中，双平面并没有自动更快，说明需要看实际消息和路径。

第三类细节是协议等待与跨层归因。Scale-Up已有端侧就绪、发送槽、队列和信用记录；Scale-Out已有接收就绪、ACK完成、队列与ECN/PFC摘要。下一步对选定端口补有界时序，把两条路径中的关键前驱追溯到具体资源占用：慢在端侧发送、交换机排队、协议反馈，还是专家计算。各段等待只按实际关键路径解释，不能简单相加。

第四类细节是校准与规模效率。先在匹配的设备、软件、形状下补计算与通信测量，区分UB与RDMA的协议和硬件条件；必要时在局部引入GPU—NIC资源模型或硬件仿真。Scale-Out还需拆分构图、执行、逐包事件和写出成本，再重新验收千卡。Scale-Up已有完整首轮，可从真实关键等待和受控机制对照继续深化。

验证顺序是：先在两条后端各自的小场景里，固定请求、专家选择和资源，追踪真实关键等待；再分别做机内发送/信用机制与跨机放置/分层通信的等资源对照。证据支持哪条路线，就优先校准和深化哪条路线；不能把两个独立仿真的时间拼在一起。最后形成有明确适用边界的网络方法、可复核论文和可重复使用的实验基准。
