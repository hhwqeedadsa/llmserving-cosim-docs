从字节探针到真实MoE调用，还缺哪几层

上一轮“冷启动最快、连续两轮最慢”的结果仍是正确的参考模型事实，但目前不能解释成真实MoE默认配置的排序。本轮固定源码补查发现三项关键边界：真实库复用Context而不逐调用重建；当前每GPU对一条连接的探针没有表达现代库的多上下文映射；路由数据没有提供真实调用时刻，无法判断计算和其他通信给拥塞恢复留出多少时间。

本轮取得并核对6份固定小源码，没有运行下载代码。联合核对19份DeepEP/NCCL文件及29处摘录，独立枚举1080份token写的通道分配、18组连接映射。没有执行新的网络、GPU、构建或安装；下面的工作分布是源码条件核算，不是硬件配置读回或性能实验。

1. 连接生命周期：复用成立，但范围必须说清

固定DeepEP f6aa38f的EPBuffer构造时创建comm::Context，Context创建NCCL设备通信器，向GIN申请exclusive contexts。dispatch/combine使用同一context的dev_comm/window；销毁Context时才ncclDevCommDestroy。README示例按group和buffer容量复用EPBuffer，因此同一个复用buffer内多次调用可以共享长期存在的传输资源。应用也可以重建buffer、使用不同通信组或多个buffer，不能把示例复用方式说成所有服务的强制行为。

NCCL 12df1a1的GDAKI按每本地context、每peer创建并导出QP。全局context index先按连接数分解：connection=index%connections，local_context=index//connections。一次NCCL连接绑定其通信设备；多个context可以落在同一设备，多个连接也不能凭数量直接换算NIC带宽。self-peer和companion等资源另有条件，本文只统计跨rank数据用到的peer/context组合。

这支持后续模型保留连接身份，而不是逐消息新建。源码仍不能证明某款网卡具体如何维护/恢复拥塞状态，当前参考DCQCN不能借此变成现代NIC校准结果。

实际使用的上下文数量可以少于申请/调用数量。例如16SM/128KiB这个数学条件调用9个context，却只有1、2两个索引有数据。源码先按token_start=warp*SM+sm分工，再以1+(sm*warps+warp)%(QPs-1)分配上下文；小batch没有用满所有warp，不能只看“9个context”推断均匀条带化。

再假设4条NCCL连接，该条件的180写只分到connection1/2，分别117/63份，connection0/3为0。这个结果只说明映射可能产生不均，不证明生产multi-rail闲置、热点或时延收益。没有确定物理NIC绑定、ECMP端口、路径、GPU发布时间和真实共享内存时，不能把它称为实测链路利用率。

源码还存在一个需要单独核实的SM估计分支：direct的逻辑scaleout=1且无NVLink时，选瓶颈的条件不进入RDMA分支，而选择零NVLink流量，保持设备SM数再按偶数钳制。该结论以带宽辅助函数正常返回、运行到此分支为条件；本轮未取得这些环境辅助值或设备SM实值，也没有执行该函数，不能断言实际部署必然取某个数。它提醒我们应读回有效参数，不能把“自动”当已校准的最优配置。

4. 一个真实调用需要等什么

默认dispatch/combine的num_sms/num_qps均为0，表示自动决定；async_with_compute_stream默认False。C++ prologue让通信流等待previous_event，或等待当前计算流上记录的CUDA事件。epilogue默认让计算流等待通信流；显式异步时返回事件，消费方在自己的流上wait。这里排入的是GPU流依赖，不能写成主机逐调用全局同步，更不能当作所有rank ACK的时间。

fresh Dispatch入口屏障确保buffer可用；出口按实际数据写、所有相关QP的flush和远端signal等待推进。应用还需处理接收布局/可选epilogue，才能安全消费结果。真实前向用法通常是：输入就绪→Dispatch→专家计算→Combine→归约结果就绪→后续层/请求数据就绪。异步或多buffer可以重叠这些步骤，不能机械加上若干独立耗时。

GDAKI flush读取当时各peer已预留SQ的ticket前缀并等待CQ；屏障再发布/等待信号。它们没有把“排空所有CNP”或“所有QP恢复到线速”作为完成条件。不能由屏障完成推出拥塞状态已经清空，也不能把当前字节入口的全组ACK直接对应为库函数完成。

5. 路由数据能提供内容，不能提供真实时间

1472/1808/2675/6447四文件各129个条目，所有条目键都是数字层号，没有显式调用时间字段。专家选择可重建某轮数据份数和目的rank；条目次序不能给出CUDA就绪时刻、专家计算耗时、Combine结束、请求到达或NIC反馈时间。现有A100计算记录也不能自动充当这一Hopper+代码分支的校准。

因此上一轮的第二轮表示“同一Dispatch数据探针在全组ACK后立即再次就绪”，不是“已模拟下一真实MoE层”。真实间隔可能允许恢复，也可能有Combine和其他组流量继续竞争；源码本身不能决定哪一种占主导。本轮没有扫描固定空闲时间或挑选让反转继续成立的参数。

6. 后续仿真结构应该怎样改，服务什么问题

层次必须表达的内容验收依据当前状态
应用任务每rank/token数据就绪，Dispatch消费、专家计算完成、Combine发布和结果消费相同实际事件推进同一时钟，无固定通信完成时刻、无重复提交有离线现代事件/窗口核心，尚未接完整provider网络
连接与拓扑SM/channel→context→NCCL连接→物理NIC/peer QP，固定生命周期和线端口来源映射与有效配置；实际路径/端口字节守恒字节入口可声明持久流，尚无完整现代映射执行
资源与完成SQ/CQ、flush前缀、源buffer寿命、目标可见、self-peer和signal实际provider语义和最小事务校准，分别记录各完成事件多项功能核心存在，不能等价现代完整库
拥塞与共享同一网络内跨call/跨组连续队列、独立反馈、空闲恢复包与控制事件、实际QP状态，匹配NIC微测量参考机制可执行，未校准
强基线同一路由、布局、字节、就绪依赖，按源码配置多context；报告伴随路径/资源变化有效硬件参数、独立请求和必要对照当前单QP探针不足以作为默认生产基线
规模与论文持续服务、代表性拓扑和独立输入，再检查网络优化是否超越已有方法不只靠经典CC现象、单个小窗口或静态计数千卡完整执行、匹配硬件和主贡献仍未成立

改变context数往往同时改变分工、门铃/队列资源和ECMP哈希，multi-rail还会改变NIC绑定；不能把整组变化叫纯拥塞状态对照。下一次网络实验须先写明这些伴随变化，按实际数据/必要控制的物理出口服务量建立强基线，再解释剩余差异。未解决现代self-peer物理路径、signal成本和GPU可见性前，不称端到端现代DeepEP复现。

核验与维护

19份源码逐Git树/blob/长度/SHA256核对，29摘录保留原行号和公开固定提交链接；新6份每URL只请求一次。producer按token反解通道，checker按每SM/warp的token循环重新枚举，核对1080份写与18连接投影，包含来源四原件和API默认的AST读取；只解析，从未导入或执行下载源码。报告中的路由schema也重新检查原件hash。

两项维护错误保留在原始监控中：第一次prepare对相对source路径调用relative_to绝对ROOT失败，已统一resolve；首次checker以splitlines重建摘录时丢失末尾空行，已按显式换行分隔保留原文。只修研究工具，未重新请求源码、修改分析输入/定义或执行网络。当前报告与摘要来自修正后的独立核验。

新收集源码缓存≤1MiB。大件与归档位于/dev/shm/moe-invocation-semantics-20261023，仅易失内存盘，没有持久备份。来源缓存、四原件、源码快照、检查失败及成功记录均纳入有界归档；本地提交，不push。论文目标继续进行中：本轮收紧适用范围并明确实现与验证顺序，没有建立新算法、硬件收益或A类论文主贡献。
