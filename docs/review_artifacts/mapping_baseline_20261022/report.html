专家分组与节点映射：强基线与可改进空间

本轮得到一个会改变后续研究重点的结论：在这四请求、EP4的direct Dispatch条件中，两种Prefill计数LPT分组的较高通信量，不能靠更聪明地给四个专家组换节点来消除。 主要限制来自一个token需要覆盖多少个专家组，而不是四个组的节点编号。

这不是新的放置算法或论文创新。本轮完成的是强基线和可改进空间核查：避免把一个已有简单方法能够解决的问题当作研究突破，也避免继续在已经缺少空间的映射动作上投入。完整网络时延、硬件校准、规模与独立请求泛化仍未完成，A类论文目标保持进行中。

本轮怎样比较

上一轮包级实验已经证明，专家放置会改变物理路径、汇聚和排队。本轮进一步分开两个决策：哪些专家归为一组，以及这四个组分别放在哪个节点。

固定三种基础分组：连续编号、全Prefill原始频次LPT、尾部最多10个Prefill token频次LPT。每层每组64专家，LPT按高频优先分给计数最少的未满组，与已核对的作者artifact计数实现一致。这些只是容量约束下的抽象分组，没有证明完整DeepSeek-R1可以在四张实际GPU上部署。

基础来源是Patterns behind Chaos的公开实现zhongkaiyu/moe_exp_placement@b059b85，详细源码身份和适配见前阶段Prefill强基线报告。这里使用公开计数版本，不复现论文的H100/roofline性能，也不将已有Prefill放置与共激活洞察当作本项目创新。

每个基础分组比较三种节点映射，共9条件：保留原编号；枚举24个排列，用Prefill选择预测远端副本最少的映射；枚举24个排列，用Prefill选择预测最忙物理出口服务量最小的映射。每层选一次，随后评价全部128个Decode位置，不按未来窗口重新选最优。

源请求仍固定在rank0—3；只排列专家组。组内专家和计算贡献保持不变，最大计算输入严格不变；来源局部性、跨Pod与路径需求可以改变。这里允许在Decode前重新部署专家组，但没有建模权重迁移、buffer调整或冷启动成本，不能把重新部署当成免费优化。

预测对每个源的Prefill长度分别归一化。原四请求长度为105/28/10/6，不能直接让长prompt代表更多Decode请求。归一化后相当于每源一个token的经验目的覆盖概率；用最小公倍数转换成精确整数权重，不做浮点近似。尾部组使用相应的10/10/10/6个token。

这比前阶段只提供全局专家次数使用了更多信息：来源、token内共选和已知拓扑。因此不能把效果归给“排列动作”或某一项新增观测。本轮把它们作为更强的简单基线，而非新增信息价值的归因实验。

网络指标是什么

固定上一轮的upper25G Clos：8端点、4ToR/4Agg/2Core，rank到GPU为0/2/4/6；接入100G、上层25G，seed11，wire_port=21000+4src+dst，单rail/plane。准备程序调用公开topology入口，再依据固定静态ECMP规则计算数据和反向ACK路径，没有从Decode结果学习选路。

每份14,464B数据按1000B拆为15包，合计15,004B模型数据和720B反向ACK。按每个实际有向出口汇总字节/速率；100G出口每B为1单位，25G为4单位，一单位对应0.08ns理想序列化服务量。评价记录每窗口的最大出口服务量。

该指标是理想服务需求，不包含到达次序、排队和关键路径，不能称完成时延或推理加速比。静态数据与ACK路径分别与上一轮实际包记录核对，共24条连接方向路径一致；这是对路径依据的复用，本轮没有执行新的ns-3或GPU实验。

这不是“规划器基本没换位置”：六种非identity方案中，每种都有53—56层改变了排列。远端副本和物理服务量的目标也经常给出不同排列；两者仅有11—13层选择相同。尽管如此，两种LPT分组的总副本改善最多约0.32%，p50/p95出口需求没有改善。

平均变化还会掩盖窗口退化。例如全量LPT的最小出口服务量映射，在1,775个窗口降低最大出口需求，1,384个窗口增加，4,265个相等；尾部同类映射在1,734个窗口降低、1,836个增加、3,854个相等。不能只展示改善窗口，也不能从Prefill目标更小推出未来Decode的所有窗口更好。

六种非identity方案的最大计算输入，与各自原编号逐窗口完全相同；这是组标签双射的性质，不是GEMM性能测量。九条件的远端贡献、副本、出口需求、计算输入及逐层映射均有完整记录。

怎样判断是分组问题，还是规划器不够好

9条件完成后，追加了只读解释核查，没有增加部署方法或重跑结果。这部分是结果后的机制分析，不称预注册验证。

若一个token所选专家分布在K个专家组，任意节点排列至多让其中一个组留在源节点。因此，该token至少需要K−1份远端副本。这个下界不依赖预测准确率或ECMP，甚至允许每个token独立获得最理想的本地旁路；它只适用于本轮固定分组、单源rank、每远端组一份direct副本的定义，不是网络时延或带宽的通用下界。

对论文方向的实际影响

本轮收缩了一个候选方向：不把“只给固定专家组换节点”作为独立创新主线。它仍应该保留为便宜、明确、可复现的强基线，不能删除负面结果。

接下来更有依据的问题是：在专家计算负载、容量与迁移约束下，现有分组是否不必要地扩大了token的目的覆盖，改变分组是否能改善真实物理瓶颈，并在完整通信语义中形成净收益。应先比对已有共选、网络感知和超图放置工作，不能把已知集合覆盖关系、K−1下界或24排列搜索当作新理论。

下一步要求需要取得的证据
比较更强的已有分组基线对照已有方法的实际输入、目标、约束和开销，说明仍未解决的问题；已有方法足够时直接采用，不制造新颖性
同时评价计算与网络实际完成时间和最慢设备/出口，而非只追求一个输入计数；不能为了少通信无限制造计算热点
纳入系统约束专家容量、可用观测、部署/迁移成本、动态slot、buffer寿命和provider反馈；self-peer成本须有依据
取得未参与设计的请求固定采样规则、新请求的Prefill决策和Decode评价，不能反复使用开发四请求后称独立泛化
检查网络与规模泛化预先固定不同ECMP、rail/plane、连接和带宽分布；千卡入口能力与业务代表性分别验收
匹配实机校准对应库版本、GPU与活动RDMA硬件；A100不能冒充Hopper+现代分支校准

这些证据齐备且强基线后仍存在有意义的机制缺口，才值得投入新方法。本轮不证明已经达到A类，更不能据此承诺最佳论文。

数据、失败和复现边界

本轮尝试读取固定Hugging Face revision的目录元数据，以文件名和大小规则选4个新请求。请求在连接阶段超时，收到0B，没有选出或下载任何新原件。因此全部结果仍来自原四请求，不存在本轮独立留出组，也没有生产、训练或跨模型代表性主张。

初版采集器给urllib设置20秒socket timeout，但多地址连接可使整个请求延长，实际请求记录40.070秒、外层监控40.206秒。它没有满足单请求20秒的原定墙钟约束；外层60秒限制仍有效。已保存失败时的完整脚本和日志，并把后续采集改为带整请求deadline的子进程；本轮没有重试，也没有将修正后代码写成已成功下载。新实现完成静态/帮助检查，真实远程行为仍未复验。

研究只调用公开topology导出，复用旧包记录作独立路径核查，没有新GPU、网络仿真、构建、依赖变化或安装。规划从只含observed/inputs.json的新目录独立重跑，plans.json逐字节一致。独立检查覆盖4份原件、4,176个候选得分、174个层/分组、66,816窗口、1,069,056个矩阵位置；追加下界核查回读89,088个token覆盖并以174次动态规划核对oracle。

准备、规划、评价、检查和解释核查每命令均受60秒/RSS1GiB/地址2GiB限制，单阶段32MiB，新产物64MiB/累计128MiB、卷预留8GiB。评价约3.13秒，独立检查约4.98秒；这些只是宿主脚本时间，不是推理或通信性能。完整命令、状态、资源、hash与原始数据存于本地检查点，Git保留必要摘要、设计和复现入口。见实验协议与复现说明。
