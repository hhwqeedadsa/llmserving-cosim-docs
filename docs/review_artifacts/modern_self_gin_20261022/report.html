摘要 · 独立核查 · 检查点

现代GIN自发请求与网络基线更正

本轮发现并修正一个会影响网络研究基线的错误：发给自己不等于绕过通信库。固定DeepEP direct中的屏障通知和专家计数块仍进入GIN；固定GDAKI为它们创建self-peer QP。此前操作计划把这些请求归为普通本地操作。它们需要provider资源，但物理回环路径、服务成本及是否涉及外部线速尚未验证，不能直接添加交换机流量。

平台修复为c08cbb98acdb9a8b3bbc97fa959e0ca28ea817e8。本轮用相同四份真实原件、相同16条选择和相同声明参数重新生成计划；旧结果保留，未重写为新结果。实验通过公开CLI完成，不调用测试或fixture生成负载。结果与独立比较见摘要、核查、来源及归档。

3. 对千卡研究的具体约束

集群GPU数与EP组大小必须分开。对本分支一次Dispatch+Combine，若EP组有R个rank，四次屏障分别产生R²个signal，专家计数产生R²个bulk put，rank计数有R(R−1)个GIN请求；合计6R²−R个GIN控制请求，其中5R个为self-peer。它们与token数据请求分开核算。

4. 什么没有被证明，下一步怎样做

本次self零专家块可见或self屏障源完成被暂扣时，均阻塞后续32个应用完成节点。这是必要依赖的反例核查，不能解释为真实硬件一定有严重长尾。静态分类修复不是论文机制创新，18%的计数比例也不是性能收益。

当前后端的src=dst限制使它不能直接承载该现代分支。下一步必须单独定义self-peer GIN在NIC、WQE/CQ及内存中的行为，并与跨rank流在同一provider资源上推进；不能默默跳过、强加交换机路径或用零成本本地事件代替。然后接入窗口及现代事件核心，明确哪种GPU/NIC/provider可测、校准哪些成本。没有这些证据前，不使用MRT1给现代DeepEP排性能名次。

有A类论文竞争力的研究仍需证明正常真实负载中的关键网络等待存在、解释能排除模型伪影、方法优于现代强基线，并有留出数据、规模与匹配硬件校准。本轮让基线更准确，尚未满足这些论文要求。
