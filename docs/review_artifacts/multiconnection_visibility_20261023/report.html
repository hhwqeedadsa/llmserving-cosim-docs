多context的通信，不能只按一次通知判定完成

本轮把现代联合仿真的一项实施条件查得更具体：要知道一条完成通知究竟覆盖哪些context、QP和设备上的数据。 固定NCCL已提供逐context通知/等待的屏障分支；固定DeepEP自定义屏障采用先flush、再用context0通知的不同路径。不能将这两个协议合并成“全部数据到了就结束”，也不能仅凭源码差异断言DeepEP有错。

本轮只有源码和无时间有限模型，没有网络/GPU仿真、性能收益或硬件反例。它推进强基线与建模依据，尚非论文主贡献。

证据：HTML、源码身份、摘录、独立核验、执行前方法。

1. 人话解释这个问题

一张GPU可能同时通过多个通信context提交数据。context是软件提交上下文，每个context对某个peer有自己的队列对QP；多个context可能共享网卡，多个连接也可能绑定同一设备，不能将它们视为同一种对象。

需要分开四件事：源GPU不再使用发送缓冲、目标网卡收到数据、目标GPU能够读取数据、应用开始计算。源端收到ACK或flush返回，不能依据通用接口说明直接补齐其余事实。

例如数据A和B分别来自两个context。目标收到context0的完成通知时，是否一定能读取A和B，要由协议和provider保证。若通知只覆盖A对应的域，即使B已经到达网卡，也不能在模型里凭空宣布B已对GPU可见。这里的“域”是需要核实的可见性范围，不能预设为一张NIC，也不是新增的真实硬件实体。

关键新证据是NCCL实际逐context执行的分支，并非仅从API名字推测。该分支与DeepEP的不同，不足以证明后者违背GDAKI保证；DeepEP有预先flush，不能忽略它，再套用“通知超越仍在途数据”的注释来指控缺陷。GDAKI能力项也不能被我们擅自解释为已经测得跨NIC的全局刷新。

首个gin_barrier.h源码请求超时，没有重试；随后取得另外两份预先列出的implementation文件，均按固定tree核验。缺失声明头不妨碍检查已取得函数体的循环和分支，但本轮没有编译验证其公共调用方式。首次collector遇失败即停止，其日志和源码快照保留；后续只补取未请求过的文件，共3次请求、2次成功。

3. 有限模型究竟验证了什么

两个数据操作均已发起；分别保留目标接收、源本地完成、目标可见，再连接flush、signal、wait和consume。四组模型只有10或11个事件。为了给错误推导更强的前提，所有组额外假设目标接收先于源本地完成；这不是对通用GIN或全部真实硬件的断言。

生产分析用子集动态规划计数；独立checker递归枚举全部1,018个完整顺序、5,076个前缀，回查每条边与反例。四个分析产物重复逐字节一致。

单域反例为：receive0 → local0 → receive1 → local1 → flush → visible0 → signal0 → wait → consume，此时visible1尚未发生。它仅证明：若没有覆盖域1的保证，不能从这些前提推导所有数据已可读。 不代表真实GDAKI允许此轨迹。安全组的关系是显式前提，核验只是检查这些前提是否充分，不能当成发现新的硬件保证。

各顺序没有概率权重，88/360或26/210不是故障率、发生率或生产风险估计；也没有任何ns时延。

4. 为什么这会影响我们已有的真实路由

复用上一轮公开静态需求表，不重跑事件或网络：四份已见请求entry0/层4，共48个token，在声明8个调用contexts、2条连接的配置下，117份跨rank Combine put分别落在连接0/1的59/58份；操作数为849,600/835,200B。8个调用context都有远端数据操作。

这些设备号只是声明值，并非已读回的NIC配置。但它足以说明：当前条件输入不是“所有数据都在context0”的退化场景。未来在线后端必须解释其他context的数据如何在屏障后变得可读。两连接数据量接近，不等于网卡利用率接近，更不能据此推断完成时间。

控制基线也有区别。例如4个rank、请求17个context、2连接时，分配取整为18个context。一轮包含self的自定义单context屏障有16次signal API调用（12远端、4 self）；NCCL all-allocated-context分支为288次（216远端、72 self）。这是两个不同协议分支的API计数示例，不是实际WQE/包数、18倍时延或新优化收益。当前调用只用8个context，不能据此悄悄把generic遍历的allocated数量改成8。

5. 接下来怎么实现，怎样验证

  1. 固定应用协议：DeepEP自定义路径与NCCL all-context路径分别命名，保存allocated/active context，不把切换屏障算成网络策略收益。
  2. 按context → connection → device → peer QP保存有效绑定；另行声明有来源的目标可见性域及signal覆盖范围。域未知时完整性能执行不通过，不补全局零成本fence。
  3. 原生网络实际接收只更新接收事实；源ACK/CQ类回调只更新其已有依据的源完成；目标可见必须由所选provider规则驱动，继而解锁本地消费。现有MRT1 applied和字节accepted均不能冒充GPU visible。
  4. 将上述单域反例作为provider映射的拒绝用例；逐context通知和有证据的全域能力分别验证，不强制所有provider付同一种控制量。
  5. 匹配Hopper+/活跃RDMA环境后，分别测单context、同NIC多context、跨NIC连接：检查屏障后完整数据、源复用、self资源、实际原子与响应；保留原始错误/时序。硬件无错误也不能仅凭少量运行证明所有内存序。

本轮没有修改平台，当前现代事件计划仍明确要求外部provider兑现跨context可见性，并未宣称已在线执行。此前提出的self-peer物理服务、源buffer、CQ/WQE、匹配校准与独立请求缺项仍存在。

对论文的价值是防止在强基线里少算控制操作或制造过早计算，确保以后观察到的网络瓶颈来自真实执行关系。仿真论文仍需端到端校准、误差、开销与千卡泛化；网络论文仍需实际瓶颈、可消除损失及强方法对照。源码循环和有限反例都不足以单独支撑A类主贡献。
