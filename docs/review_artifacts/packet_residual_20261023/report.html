逐包核查：通信尾部的差额是否还能优化

本轮的实质结果是：在已经确定的六个数据传输条件中，全部完成时间都可由实际包到达、物理端口的串行发送顺序，以及数据接收触发ACK解释。99,720次物理发送均未出现超出这些已记录约束的额外时间间隙。因此，不能把“完成时间减去最忙端口服务量”的约12—13微秒直接叫作协议浪费，更不能据此宣称有同等大小的可优化空间。

平台改动与研究分别验收、分别本地提交，没有push。平台依据见报文头观测验收，研究执行前方法见残差核查方法。本轮是一个候选问题的机制核查，尚未建立A类论文的主贡献。

我们实际做了什么

沿用四份已见的DeepSeek-R1-AWQ/MMLU请求路由，固定entry0/第4层，每个来源最多16个token，实际16/16/10/6。EP4，256专家、top8、隐藏维度7168，声明BF16传输布局。每条件117次远端写，共1,692,288B、1,755个数据包和1,755个ACK；96个持久QP对象、深度32，工作全部在0ns就绪并发布。

拓扑保持四台服务器各一GPU、两个pod、一rail两隔离平面，每GPU一个声明双端口NIC，各端口100G。上层链路分别100G/25G；identity、按rank轮转、经典本地LPT三策略。它们都未改变本轮的逻辑token目的地和总字节。每次仿真使用自己的完整共享网络，并没有把不同运行的时间相加。

旧包记录只有UID和序号，同端点的多个QP可能出现相同ACK序号，无法普遍准确关联。新增packet_capture.wire_headers=true后，按保存事件提供实际IPv4及原生UDP/qbb端口。独立小例验证5组这种歧义；默认新旧结果逐字节一致。六条件补采进一步验证：去掉新表和开关后，所有原有结果字段完全相等。这是观测不扰动核验，不是新增六份独立性能样本。

对每次发送，检查三个事实：该端口前一个包何时发完、本包何时从上一跳到达，以及源数据或ACK何时具备发送条件。把这些已记录前驱允许的最晚时刻与实际发送时刻比较，六条件的所有差值均为0。源端数据根只在本轮已验证全部0ns发布时适用；ACK的根来自实际反向IP/端口和累计序号对应的数据接收。

这个结果不证明协议内部成本为0：未观测的约束可能被同时存在的端口占用遮住。结论只是在这六次执行中，现有包到达与端口先后关系已经足够解释全部发送时刻，未获得额外可消除等待的证据。

独立检查器不调用构图程序，直接重建端口与路径，核对10,530个数据包、10,530个ACK、99,720次物理发送，以及702项工作的精确QP接收/ACK完成。每跳按锁定ns-3的逐帧纳秒取整和传播延迟核算；5份固定原生源码与提交内容核对。修改ACK端口、传播边权或额外间隙的三种错误记录均被检查器拒绝。完整摘要见独立核验。

为什么不能把差额直接等同于传播时间

最忙端口的服务量是一个聚合下界，不是某一条具体包链。最终ACK的前驱可能先沿一条包路径走，再通过端口占用关系跳到另一个包；选择不同的并列前驱，会得到不同的加性解释。程序保留全部最大前驱和最终ACK并列项，不只保存一条好看的链。

对后续研究的实际影响

本地LPT的4.85%/6.01%改善仍保留为强基线，其完成时间减少量恰好等于最忙端口串行服务量减少。本轮进一步没有找到额外间隙来支持“隐藏的协议等待优化”这一解释。暂停在这个全部数据同时就绪的小例上继续搜索策略和参数，避免把经典平衡负载重新包装成创新。

下一项值得检验的问题是：当数据按真实计算与通信依赖陆续就绪、多个EP组同时共享上层网络时，简单服务量和经典平衡基线是否仍足够。要支持新机制，至少需要保留相同网络资源和真实完成回调，证明强基线之外确有额外等待，再用不同请求作留出验证。千卡数量和EP组大小应分别配置，不能把一千张卡全部强制放进一个EP组。

在进入该研究前，仍需完成现代通信调用的在线接入，区分数据到达、GPU可见、源缓冲可复用和队列释放，并补匹配硬件校准。现在的MRT1/持久字节载体仅为功能实现，四份路由不是生产或训练总体样本；本轮也没有GPU执行、self/control完整成本、重排成本、完整推理或千卡性能新证据。
