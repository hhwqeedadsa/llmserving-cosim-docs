为什么换成这批工作量

前几轮的小Decode窗口没有ECN/PFC，无法检验真实较大数据量下的反馈和源额度。 本轮取用户四份R1-AWQ/MMLU文件entry0的全部Prefill token，长度105/28/10/6，共149个；每个完整请求声明放在一个源rank。 连续等容量放置256专家、Top8，按目的rank去重，层4形成344份数据，每份14,464B，共4,975,616B有效负载。 没有复制原请求或把未来Decode步骤并作并发请求。

四个源映射到GPU0/2/4/6，跨四服务器、两个Pod；8GPU小Clos、100G接入/25G上层、seed11、12条持久连接。 所有独立写在0ns应用就绪，实际发送由ACK信用与DCQCN推进。两个条件仅改源工作队列深度1/8； 深度8是敏感性参数，未校准为真实NIC/CQ容量。同步可用与源部署也是声明条件，原数据没有到达时间。

先区分源长度不均与热门专家

149个token中，最长请求占105个，约70.47%；四源远端数据份数为236/67/25/16， 源峰/均为2.744；目的rank远端入量为38/95/89/122，峰/均为1.419。 同层单专家选择次数峰/均为4.725，各目的rank专家计算贡献为335/342/212/303。

这些指标的对象不同：单专家计算、源端发出、目的rank去重后的网络入量不能混成一个“热点程度”。 当前源映射中请求长度明显不均，不能把所有网络压力归因于热门专家；也没有执行重分配或证明改源映射可以免费消除差距。

Fabric没有覆盖这些属性。固定ReceiveUdp在每个包的ACK中依据ECN设置反馈标志，持久连接收到该ACK后调用DCQCN更新。 本次按真实数据接收、累计ACK序号和ACK接收时刻重建反馈，再按固定源码推进速率状态，未重新执行网络。

24条“条件×连接”的重建中，23条没有同纳秒外部事件/定时器顺序歧义，发送间隔都满足重建的速率约束。 其中135个实际发送间隔与100Mb/s下的包间隔在1ns内相符。 例如深度8/连接1，从56,409ns到139,289ns间隔82,880ns， 对应1036B模型帧在100Mb/s下的82,880ns。另一连接存在1次同纳秒采样歧义，明确排除其精确间隔认证。

最小重建速率可能发生在连接已无新包之后，因此JSON另外记录“实际发包时的最小重建速率”。 重建不是直接采样NIC内部状态，不证明已解释每一ns的整段业务时间；它支持“反馈降速与慢恢复是需要校准的机制解释”， 不能将1500μs默认值称为真实设备参数，更不能据此设计号称适用于生产的新算法。

核验范围与保留的失败

回查4份原件及4个已准备条件；实际核对9,094个源数据包、36,373个GPU端点事件， 核对源序号连续、数据长度、实际连续接收/ACK、slot复用及未发布项。完整条件40个物理端口的数据和ACK计数精确一致； 失败前缀40端口采用已送达/已注入路径界限，不能冒充全程逐跳捕获。捕获只选择4个活动GPU，交换机队列积分来自原生汇总观测，未独立逐事件重建。

第一次只读检查错误地假定尚未发布的工作已有字节区间，断言失败。源码确认这些区间在实际发布时才赋值， 检查器据此分开验证未发布状态；原失败、原脚本和修正记录均保留，没有修改平台或网络。 最终审计重复两份JSON逐字节一致，重复的只是只读核验。

接下来应改什么、论文还缺什么

  1. 把DCQCN的生效参数、覆盖来源和必要状态显式记录，避免小场景无反馈时隐藏默认值。先验收观测不改变包和时间，再开展独立研究。
  2. 补匹配硬件/库分支的反馈、恢复和源额度测量；以未参与拟合的大小与并发验证。当前没有校准依据，不通过挑更快的定时器制造收益。
  3. 在完整现代数据/计数/屏障/可见性语义下检查多EP组共享网络；本轮只有数据写入，没有计算、Combine或完整DeepEP/GIN。
  4. 补独立请求和更大部署。当前四请求、一个已执行层和声明同时就绪不能证明生产热点或泛化。

根卷打包前空间检查失败，未创建大文件；完整检查点改放内存盘，原打包失败及源码也保留。 内存盘检查点是易失的，尚未持久备份。小型报告进入本地Git，原始记录也仍留在内存盘。

本轮得到的是新的网络压力反例与参数证据，已改变后续检查方向；已知拥塞反馈现象本身不构成新的A类论文贡献。论文目标继续进行中。
