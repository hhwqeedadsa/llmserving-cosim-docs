创新点筛选与 MoE 安全恢复候选

2026-10-23。本轮先做创新筛选和独立条件检查，没有增加恢复平台接口，也没有执行 GPU、实机 RDMA 或新的包级性能实验。总体论文目标仍进行中。

1. 先明确拟研究的创新点

优先检验的候选是：在网络或部分执行端故障后，保留健康端已经完成且仍然有效的 token／专家结果，在旧传输可能尚未退出的情况下，安全地补做必要部分，继续完成在途 MoE 推理请求。

这里的“保留”必须有证据：输入、模型权重、逻辑专家身份和本轮结果身份一致；数据确实已经生成并保存在健康端；后续旧写无法覆盖它；重做不能重复累计贡献。既不能把收到通知当成全部数据安全，也不能丢专家、改 Top-K 或减少必要工作来换速度。

它比“加重传”“做故障隔离”“支持多 rail”具体，但目前只是优先验证的研究假设，尚不是已经成立的创新。本轮得到的是限定模型下的反例和强基线边界，没有证明方法优于近邻或值得部署。

若成立，论文应有三个相互支撑的结果：

1. 一种描述“哪些结果有效、哪些旧写仍可能发生、哪些任务必须补做”的恢复状态表示，而不是只记录 QP 或 rank 是否存活。

2. 在固定缓冲、信号和连接约束下，生成安全恢复计划的方法：隔离冲突目标，保留有效结果，只补做缺项，并说明何时必须退回整组重试。

3. 在真实通信库和服务系统中，证明它比经过调优的重新连接、整请求重试和现有局部恢复更好；包括记录、额外窗口、复制、同步及稳态成本。

第三项是价值门槛。一个操作是否完成的日志、代际标签、区间冲突判断或额外缓冲，本身都不是新的论文贡献。

3. 哪些方向保留，哪些不能再当创新

角度具体问题已有工作／当前证据本轮决定
网络多 EP 组共享网络时，按服务依赖发布数据是否优于按大小／负载分流？已测 LPT 的 4.85%—6.01%收益由最忙端口服务量变化解释；已有 coflow／依赖调度条件保留；必须有真实就绪、强基线仍无法解释的等待，先不做新策略
系统与恢复能否安全保留健康端结果，继续完成故障时的在途请求？EEP 已有成员收缩、专家覆盖恢复和重新加入；其第3.1节将故障时在途请求交给客户端重试优先判别“在途结果保留与补做”，不能再以成员收缩或不重建实例为创新
缺陷发现新旧连接、目标窗口和通知的交错，是否违反实际库承诺？本轮 CPU 模型找到条件反例；固定 DeepEP 某些超时路径是 trap建立可执行检查条件；没有合法真实调用的复现，就不称库漏洞
安全同一注册授权范围内，恶意 peer 是否能越过按专家划分的隔离？ReDMArk 已研究 RDMA 注入、权限和 DoS；普通授权边界问题已有大量先例合作式／敌对模型分开；不把通用 RDMA 权限问题包装成 MoE 新攻击
仿真方法哪些抽象会改变恢复安全性或方案排序？已有联合仿真、混合／多保真思想；目前缺排序误差与成本收益证据作为支撑与备选，不继续无目标堆后端功能

4. 近邻查新改变了什么

一手来源已明确覆盖对本项目的约束
固定 NCCL comms.rstNCCL_SHRINK_ABORT 终止原 communicator 在途操作；新旧 communicator 不共享资源。默认 shrink 对未完成操作另有限制“排除失败 rank、建立新 communicator”不是创新。文档不自动证明任意外部 GPU 窗口可安全复用
EEP v1，§3.1—3.2可变成员、专家覆盖与图可见路由；故障在途请求报告失败并由客户端重试；不内部重试这些请求必须比较健康结果保留的价值，不能仅比较静态 DeepEP 或全实例重启。其范围排除 Byzantine／静默损坏，不据此声称它有漏洞
Varuna v1，§3.2—3.4操作执行识别、完成日志、原子结果恢复与 DCQP 切换“记录完成后选择性重传”已有。还须认真处理它明确讨论的操作成功但后继日志写失败的角落情况，不能把近邻接口假定成无条件原子提交日志
ByteExpress v2，§5—7跨层缓冲所有权、流控、连接监测、RPC 重试、替代副本／路径和 TCP fallback“跨层恢复”和“故障目的端隔离”已有；文中也明确没有建立全部状态变更操作的 exactly-once 保证
MoC-System v3MoE 训练的部分专家检查点、分片与异步持久化训练检查点是独立近邻；不能把专家级恢复／部分检查点统称为首次。本候选不依靠允许精度变化的部分保存
OptiNIC v1面向 ML 的部分／丢失数据处理、恢复上移与编码机制其允许的损失／编码与质量条件必须核对。当前候选保持必要专家贡献，不通过省略结果取得收益
ReDMArkRDMA 安全机制、注入、未授权访问和 DoS 攻击与缓解不能宣称首次发现 RDMA 不安全；需有 MoE 特有资产、攻击者权限、受支持路径和实际影响证据
PyTorch Elastic 2.14worker 故障时整组停止／重启；检查点进度由应用处理可作为恢复粒度参照，不能代替 EEP 等更强 MoE 基线，也不能将训练整组重启直接当推理唯一基线
Linux RCU 说明延迟回收，等待旧访问退出再复用对象“旧写未退出就不能复用”是经典问题。新意若存在，必须来自 MoE 特定的可部署恢复表示与实际价值

5. 本轮已经完成的实践

新增独立的 CPU 有限事件枚举工具，代码位于研究目录。不读取未来网络顺序来帮助策略决策，不调用 GPU 或仿真器内部真值。

模型给予同一 QP 内数据先于通知的强顺序。恢复连接与旧连接可以交错；目标写入表示抽象内存实际更新，不等同实测 GPU 可见。对每种合法顺序，在通知允许的各个位置安排消费，再检查消费内容以及消费后是否仍会被旧写修改。

机制／对照本轮有限模型结果限定解释
超时后清零并复用有反例旧通知可能错误放行消费
只给通知加轮次标签有反例新通知正确，也不能阻止旧 payload 覆盖新数据
双缓冲，只恢复一次且使用不同地址未发现反例所检查旧写不指向新地址；不是任意恢复次数的证明
双缓冲，随后回绕旧地址有反例旧写仍可能到达时，缓冲数量不替代退出证据
等全部旧队列明确退出再复用未发现反例强安全基线；真实退出代价和永久故障下进展未测
仅等待同范围冲突旧工作未发现反例在这个单冲突例中与全局等待等价，不能算独立性能样本
不冲突地址和独立通知域继续未发现反例合作式有限旧写模型成立时适用；没有 MoE 吞吐收益测量
同 QP 顺序且通知有代际未发现反例保留这一控制，不能把跨 QP 乱序风险推广为同 QP 必然出错
仅撤销 key，已校验 DMA 可继续有反例条件思想实验；不宣称实际 dereg／abort 具有这种弱语义
撤权并明确保证旧 DMA 退出未发现反例其保证作为前提，尚未绑定实际 provider API

10组模型共检查415个网络顺序、630个可消费交错；这是模型枚举数量，不是随机故障样本或生产发生率。部分组使用等价事件结构，不作为独立证据重复计数。机器结果和完整反例见summary.json。

一个手工复核的反例是：超时 → 复用地址 → 新数据写入 → 旧数据迟到覆盖 → 新轮通知到达 → 消费。即使旧通知全部被拒绝，消费内容仍错误。另一个交错在正确消费后才发生旧写，说明结果需要保护到最后一次使用，不能只检查通知瞬间。

另完成一个权限范围检查：合作式故障只考虑已发布旧工作时，不重叠地址和独立通知域可以继续；恶意持 key 方可以在整个授权窗口内提交新写，此时已发布 WQE 的小范围不足以证明隔离。两种情况不能共用“专家之间互不影响”的结论。该检查使用声明区间示例，不是对现代 provider 注册权限的实测。

固定 DeepEP 源码核对同时确认：部分超时路径直接 trap；某些计数消费后清零，signal 使用滚动计数，put 用注册窗口及偏移。它们要求恢复设计认真处理状态生命周期，但没有证明当前 DeepEP 存在上述原位恢复漏洞。本仿真器 MRT1 也未提供连接替换／窗口原位恢复接口，本轮没有对它执行攻击或故障恢复。

6. 下一步只做能判别创新价值的实验

1. 先测有没有值得保留的在途工作。 在选定真实库中区分链路故障与 rank 故障，记录哪些结果已落在健康端、哪些 KV 和请求状态仍有效。若工作大多丢失，或恢复专家权重的数秒开销完全淹没节省的微秒工作，就停止这个候选。

2. 确定旧写退出证据。 对实际 abort/shrink／QP 销毁、窗口撤权和 GPU 可见性分别取得保证。若正确使用现有接口已经以足够低成本解决，则采用现有接口，不另造撤权机制。

3. 比较同信息、同资源的强基线。 至少包括 EEP 式在途失败／客户端重试、NCCL abort/shrink 加应用重试、明确旧队列退出后重试、有限新窗口及可适配的操作级恢复。必须分别报告没有旧结果保留时、仅保留结果时、加隔离机制时的成本。

4. 只在差距成立后实现候选方法。 以健康端不可变结果和已确认的旧写范围构造最小必要补做集合；记录／复制／额外显存／同步成本全部计入。对旧通知、迟到数据、重复原子和缓冲回绕给出反例驱动验收，失败回退为明确请求失败。

5. 最后扩规模与论文主张。 先小型真实功能复现与匹配测量，再多 EP／多 rail／不同层级带宽；扩到百卡、千卡分别报告执行和资源。只能在独立请求和真实失败条件上证明价值后谈服务尾延迟，不能从本轮枚举推导 p99 改善。

安全支线还需要单独证明攻击者确实持有哪些权限、是否跨信任边界、是否存在受支持的真实攻击路径。如果只是应用错误地相信恶意参与方，不能当作新安全漏洞。

7. 本轮结论与目标状态

本轮明确淘汰了“支持重试／缩成员就是创新”“加 epoch 就能安全恢复”“有 CPU 反例就发现了真实漏洞”等说法。优先候选收窄为不丢弃健康端有效结果的 MoE 在途请求恢复，并把旧写退出、结果身份与有限资源作为必须同时满足的条件。

创新性仍待定，第一项价值实验优先于继续补通用功能。若最终只有经典内存回收、通用完成日志或 EEP 式成员恢复的组合，则不作为主论文贡献。当前平台、反例工具和文献审计是研究基础，整体 A 类论文目标保持进行中。
