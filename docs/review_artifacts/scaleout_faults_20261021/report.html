最终ACK丢失时，接收数据和后续计算可以完成，但发送事务尚未结束。故障组首轮64个节点完成63个，下一轮没有提交；另一组仍完成两轮。

固定哪些条件

32个起点就绪请求、每rank batch 4、H1024/F4096/E16/Top-K2、1层2步、三层Clos与100G链路。专家路由、放置和声明计算成本固定。只在指定接收设备丢一次包，共同提交的任务图逐字节相同。故障组尚未提交的未来图不能计入“相同已执行流量”。GPU标签不构成硬件校准。

实际对照

如何解释

中间包丢失后，后续乱序包触发NACK，发送端重传，接收与ACK完成都推迟。最终ACK丢失时，接收在11.649 μs就绪，但源端直到5 ms窗口结束也没有完成回调。故障组的64个节点只有一个SEND未结束，另一组的16个请求仍完成两步。不能把全局运行失败误判成所有组或交换机都卡住。

平台探针还验证：较早的ACK丢失可由后续累计ACK覆盖；尾包、NACK丢失和重复丢包可以产生停滞。它们不是“每次丢包都增加一个固定时延”的模型。
