以可靠仿真为主线的 Scale-Out 结构改进

本轮把此前“最终确认丢失后可能一直停住”的缺口落实为可选协议扩展，并验证网络恢复能正确推动资源回收和前端下一轮。目标是建设能够解释 MoE 通信长尾、支持网络方案对照的联合仿真器。新增机制是否可信、输入是否有来源、硬件是否校准分别判断，不以某项策略获得正收益代替平台验收。

1. 最终服务什么问题，受哪些约束

平台服务于 MoE 推理中的 Scale-Out 通信研究：模型、batch、专家选择和部署形成怎样的 All-to-All-v；Clos/Agg、rail/plane、各层带宽、注入量、排队、拥塞反馈和故障如何影响后续计算与整个请求推进。网络是主线，计算图和系统资源用于说明网络事件何时真正影响业务。

实际链路为 LLMServingSim 组批 → Chakra 计算/通信依赖图 → ASTRA 执行 → 同一原生 ns-3 网络 → 收发完成反馈 → 后续图和下一轮组批。网络输入包含消息源、目的、字节、plane及依赖；后续通信何时就绪由执行决定，不把独立流量运行拼接成一次联合仿真。

本轮限定8个逻辑GPU、两组交错EP4推理副本、每rank batch4、H1024/E16/Top2、1层2步ready-KV Decode、100G三层Clos。通信是按rank聚合的直接成对All-to-All-v，不代表完整NCCL/DeepEP算法；两个副本没有训练DP梯度同步。计算、GPU标签与超时参数为声明值，无数值模型执行、新硬件测量或千卡运行。参数化拓扑能描述千卡，不等于已证明千卡分组仿真资源可承受。

非UB后端只链接固定ASTRA所带原生RDMA ns-3，不与ns-3-UB混链；所有组、层和步骤共用一个Simulator。单次仿真5ms、宿主60秒、RSS1GiB、地址2GiB、产物512MiB；研究累计256MiB，运行卷预留8GiB。失败保留原因，不自动提高预算。

3. 实践结果：同一个任务，网络故障如何影响系统

在固定FIFO每源3消息/8192 B软件额度下，对GPU 0→4的Dispatch消息1丢弃一次最终ACK，业务量6144 B。五组实验共同实际提交的图逐字节相同，已发消息首包路径相同。成功与失败运行分别保留，不用失败停止时刻冒充完成时间。

条件整体完成/停止时间目标完整ACK目标发送payload结论
原生无故障122068 ns17500 ns6144 B正常基线
恢复开启、无故障122068 ns17500 ns6144 B除新增恢复报告外，结果逐字段相同
原生、最终ACK丢失一次5ms，失败停止未发生6144 B源端等待确认，后续通信受额度阻塞
开启恢复、同一ACK丢失一次131105 ns69660 ns6288 B一次超时重传，真实前端继续下一轮
持续丢失、最多两次超时重传297486 ns，失败停止未发生6432 B有限时间内明确失败，不报告成功

关键时间链为：11476 ns接收端已收齐 → 17486 ns源端累计确认到6000 B → 57486 ns超时 → 实际重发尾部144 B → 接收端重新发累计ACK → 69660 ns完整确认、QP清理及额度归还 → 消息13/14获准 → 首轮82774 ns结束，真实前端提交下一轮 → 整体131105 ns完成。

原生失败时，交换机末态队列为0，目标却仍占用6144 B软件额度，消息13/14继续等待。因此，“数据到了”和“网络队列空了”均不足以说明发送已完成，也不能把这段等待全算成交换机排队。这是网络确认、系统资源和业务依赖共同造成的停滞。

恢复后的整体耗时比无故障多9037 ns，即7.40%；目标ACK晚了52160 ns。两者不同，说明并发副本和网络重叠会改变业务影响，不能把单条消息的等待直接当成端到端损失。该结果验证故障恢复，不宣称吞吐优于无故障基线。

持续丢失时，两次超时重传发生在57486、137486 ns；第三次到期297486 ns明确失败。接收数据已齐但源仍只确认6000 B，发送QP、额度和未完成图保留到诊断/销毁。另一个副本此前已完成的工作如实记录，整个运行仍失败。

完整数值、图进展、源额度所有者、实际回调和前端历史见实验结果、HTML数值版与详细数据。实验只调用公开CLI，平台与实验分别实现、提交和验收。

4. 平台验收与公开使用

19个网络probe和5个实际联合服务用例通过预期断言，覆盖尾包、ACK/NACK、连续丢失、短超时、同刻ACK/超时、双plane、机内crossbar排除、失败保留、资源回收与网络排空。原故障11probe/3服务、准入11probe/9服务、结构11probe/3服务及超额拒绝回归通过。60项Python和3个纯C++检查通过；13项依赖检查通过，默认结果与修改前实际二进制一致。

公开流程从新拓扑执行3个probe及完整2层4步服务。首次服务的83388条包事件使结果达到17933537 B，超过原16MiB读取预算：网络虽执行完，完整用户流程仍失败。没有扩大预算；将示例包明细限制1000条后，新目录完整通过，完成4波、628条消息、1512图节点，1000615 ns。原失败与截断标记均保留，协议计数及恢复事件继续记录。

普通使用者从恢复示例复制配置和命令，修改完整RDMA JSON中的recovery即可；默认不启用，显式native保留原协议。rdma-diagnose读取完成或失败结果，诊断命令成功不代表原仿真通过。详细记录不全时只核验终态和计数，不冒充完整时序重放。功能证据见恢复验收。

5. 机制依据与不能外推的部分

ACK进展计时和指数退避原则参考RFC6298第5节；这是一份TCP文献，并非RoCE实现规范。Linux v6.12 RXE接收器对重复SEND/WRITE重新确认，RXE完成器有限重试后报告错误。这些提供设计动机，本项目没有复刻其PSN状态机或网卡实现，采用明确声明的字节序号Go-Back-N扩展。

40μs初始RTO不是硬件测量值，没有RTT自适应、选择性重传、QP复用、完整通信库分块、故障重路由或作业重启。当前重试耗尽终止整个共享运行，不模拟单QP错误传播后其他业务继续。短超时的实际服务已产生大量重复确认，说明恢复会增加网络负担；参数需结合传播、排队和反馈时延校准，不能直接推广到千卡。

6. 下一步沿哪些维度完善

以下为有优先级的改进建议，尚未作为本轮已实现能力。此前注入字节额度、队列积分和源阶段诊断见结构报告；恢复工作承接了其中的可靠性缺口。

优先级与维度下一项具体方法验收方式服务的研究问题
P1：传输精度用已有声明模式作对照，增加可选择的RTT采样/自适应RTO；先取得小规模网络或网卡测量作为校准依据无故障误重传、真实故障完成率、恢复时间、额外线上字节分别比较；防止重传样本污染RTT估计如何区分拥塞长尾与丢包恢复长尾
P1：系统错误语义明确图节点失败和请求终止协议，再实现单QP失败传播；有限释放失败资源，保留失败证据不把错误当成功；其他独立副本可继续，依赖失败节点不能执行故障影响范围是单通信、单副本还是整项服务
P1：通信执行真实性明确直接成对All-to-All-v、分块流水线与QP复用的边界，逐项加入可配置算法同等业务量和相同路由来源下核对拆分、依赖、实际QP数和协议字节EP消息大小、热点和注入节奏如何塑造网络压力
P2：网络规模先剖析固定交换机MMU和每流状态，分离不变拓扑与活动队列表示，再按16→128→更大规模验收每一级同时满足资源预算、字节/回调/队列守恒；通过后再跑千卡千卡Clos/Agg、多rail、分层带宽方案能否真实执行比较
P2：负载代表性接入已核验来源路由，保留逐请求/层/步骤热点，不只用随机均匀选择；训练需独立前后向与DP同步定义选择频率、热点持续性、rank聚合字节及网络输入均可追溯专家不均衡怎样转成跨机热点，而非人为造热点
P2：观测与交付根据输出字节预算选择summary/有界明细，进一步考虑流式结果；始终保留完整性与来源记录配置不扰动执行，超额明确失败，公开小流程可独立重现大规模实验怎样可诊断、可复现、可交换

这些改进最终都回到同一个判据：输入明确、机制有依据、事件能追溯、资源可承受、完成和失败都可信，之后才用该仿真器评价网络优化方案。
