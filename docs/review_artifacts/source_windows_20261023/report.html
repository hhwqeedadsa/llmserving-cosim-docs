让实际收到的内容，成为下一次通信的输入

本轮解决一个具体缺口：此前可以由收到数据触发下一次通信，但put内容仍来自配置中的固定hex。现在可以在真正发布put时读取本次接收窗口，将实际收到的字节继续发送，并阻止已提交读期间的提前覆写。

这是研究平台的功能进展。完整现代MoE执行、时延校准和论文主贡献尚未成立。

与网络研究的关系

最终目标是解释正常MoE推理中，实际就绪、队列、连接、路径和共享链路怎样共同形成通信等待，再用强基线、真实输入和匹配测量验证优化是否有效。只输入独立流量总量，无法证明后续通信在什么时候真的具备输入，也容易把错误的缓冲区复用当作性能收益。

本轮把“实际数据流”接到持久网络，后继包不再由预设常量冒充接收结果。它为检查早发、数据代际和缓冲区覆盖提供了基础，但还不能直接给出现代DeepEP的性能结论。

具体实现了什么

GPU0发送 → GPU4实际接收并声明处理 → GPU1实际接收并声明处理 → 回传GPU0

公开输入使用moe-rdma-transactions/3。put可指定源key、address、bytes；source固定属于发送GPU。提交时取得源范围读使用记录，真正发布时读取当前窗口，实际MRT1事务完成后释放。即使因深度1排队，也继续保护。重叠读允许；普通写、原子写和本地清零不能覆盖活跃范围。

全部事务、处理阶段和确认共用一个ns-3时钟及持久连接，不把各阶段独立运行耗时相加。v1/v2保留原有结果格式。

重要边界：保护从哪里开始

源读保护从put提交开始。本地处理目前只声明耗时，没有数值输入输出，也没有处理输入的读保护。在处理期间、后继put提交之前覆盖接收区，后继会发送新数据。这个反例已实际运行并保留，不能把本轮实现说成完整MoE缓冲区生命周期正确。

MRT1是功能报文，ACK保护不是GPU source-safe或真实CQ。当前发布处一次快照，不模拟逐包DMA；目标应用也不等同GPU可见。部分全局applied依赖仅用于功能编排，不能当作真实源端可观察信息。

下一步的判别门槛

  1. 定义本地处理的实际输入/输出范围、读取时刻和复用权限，用跨阶段覆盖反例核验；先补齐正确性，再比较性能。
  2. 将现代事件与provider分层完成连接，保留self-peer资源和signal覆盖范围；没有依据的物理路径、可见性和代价明确列为不支持。
  3. 取得匹配GPU/NIC/provider的测量和独立请求留出，再评价多组共享Scale-Out网络的长尾、路径及拓扑策略。目前没有新的千卡成功或算法收益证据。

本轮不追加新算法和规模扫描，不以平台功能数量代替论文创新。
