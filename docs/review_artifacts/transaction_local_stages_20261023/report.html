Scale-Out：收到数据后处理，再继续通信

本轮补上实际接收窗口、本地排队处理与后续网络事务之间的因果链。全部共用一个原生 ns-3 网络和时钟，处理中连接与网络状态继续保留。没有向远端查询“应该收到什么”来放行本地任务。

这是仿真平台功能验收。本地处理耗时由用户声明，尚无GPU测量；未执行现代DeepEP/GIN，也没有证明性能收益或论文主贡献。

新增能力

moe-rdma-transactions/2区分远端事务和本地阶段。接收计数和数据同时满足时，本地节点入队并消费计数；每GPU一个串行槽，实际完成后才能发后继事务。不同GPU可重叠，旧排队工作优先，零时长经过调度事件。

实际核验结果

检查结果
人工两轮10事务、6本地节点、14源包、560B载体负载；逐包解码和窗口重放通过
排队GPU4在18,096ns消费入队，106,042ns开始，146,042ns完成；后继无提前发送
错误计数/数据仅3个事务完成，7个后继等待；不清零、不偷发
5ms截止保留已消费但仍排队状态，长处理和未发生的后继均未补造完成
兼容性三组v1新旧二进制逐字节相同；纯远端v2仅多四个说明字段
回归三组旧流程24条CLI、10项输入检查、13项固定依赖检查通过

新流程24条公开CLI和9条原生命令，其中对9类非法输入分别检查两种入口拒绝。源负载独立解码、端点RX/ACK、同GPU FIFO、跨GPU重叠和仅本地尾部均有记录。ACK口径限定于已验证的非重叠人工例，未声称一般多流端口解码。

仍需解决的系统与网络问题

入队清零不保证数据在排队期间不被覆盖。还要把现代调用、provider完成和buffer复用协议接入实际网络，明确自发通信的物理路径，并取得匹配硬件校准。当前小例不代表千卡生产MoE负载，不能将固定MRT1报文当真实RoCE原子成本。
