已经支持的判断

恢复方式确实会改变共享网络的排队

已有正常/故障对照，具备真实包、源反馈和逐跳队列记录，可以把某条流的接收变化解释清楚。这里“真实包”指仿真实际产生的包。

尚需验证的判断

这种排队是否值得提出一种新方法？

要先证明它进入完整任务的关键路径，并且现有恢复限速、公平调度等方法仍有不足。多个独立请求共享网络的影响也尚未建立。

04 / 创新候选与下周计划

让恢复安排服务于任务完成

候选方向：结合当前可观测的 MoE 阶段进度，安排恢复流与正常流的发送节奏。下面是计划，不是已实现的新算法，也未承诺性能数字。

第一步 · 证明空间

完整调用还被网络拖慢多少？

将成熟恢复与拥塞控制接入现代完整调用；沿依赖检查故障前后完成时间，区分排队、源限速、等待反馈及计算假设。

交付：整次调用的正常/故障对照，以及每类等待的依据。剩余影响很小，就结束这个候选。

第二步 · 比过已有方法

阶段信息是否真的有帮助？

比较默认恢复、固定恢复限速、普通公平调度和阶段感知调度。方法只能使用当时已知的信息，不能提前知道故障或未来关键路径。

交付：相对强基线的完成时间、吞吐与恢复代价。通用方法已足够，就不包装新机制。

第三步 · 检验适用边界

换热点、batch 和网络还有效吗？

在能力和预算明确后比较不同请求规模、热点、分层带宽和故障位置，补独立负载；再逐步扩大规模，记录宿主开销。

交付：在哪些条件下有效、何时无收益或变差。完整千卡应用与硬件校准仍需单独验证。

预期收益的主指标：（基线任务完成时间 − 方法任务完成时间）÷ 基线任务完成时间。故障额外等待的减少比例另外报告。只减少某条流的等待或模拟器同步次数，不算同一种收益。

有意义吗？

如果网络恢复确实卡住任务终点，减少等待有助于提升服务效率、降低同资源下的尾延迟；当前尚未证明生产收益或成本节省。

能做出来吗？

小规模功能调用与包级分析已经具备。接下来先完成强基线集成和最小调度对照；真实 GPU/RDMA 性能仍需要匹配环境校准。

为什么由我们做？

现有链路能同时看到专家选择、通信依赖、实际包和队列，具备验证跨层问题的条件。平台能力是研究基础，不自动构成论文创新。

最终形成什么？

先交付可复核的收益空间与机制解释；若新方法优于已有方法，再形成论文和可复用基准。研究候选不成立时保留负面结论。

查看可直接用于周报的文字

点评：关注研究收益和剩余优化空间，明确预期成果，回答“有没有意义、能不能做出来、为什么由我们来做”。

点评落实：本项研究面向 MoE 推理中的跨机通信拥塞与故障恢复，目标是在相同网络资源下减少任务等待。本周已具备真实专家路由、包级网络和完整功能调用的分析能力，并发现恢复期间未丢包通信受到排队拖累的现象。下一步以成熟恢复与拥塞控制为基线，先测清整次任务的收益空间，再验证结合任务进度的调度方法，形成有明确适用边界的机制结论和实验基准。

本周工作：

  1. 跑通基于真实专家选择的四卡单层 MoE 完整通信调用，保留阶段依赖与屏障，能够追踪任务等待。
  2. 完成正常与故障下的恢复机制对照，发现成熟选择性重传已显著减少通信窗口的故障增量，明确后续必须采用强基线。
  3. 定位未丢包通信受到共享队列拖累的现象，并复核数据与任务依赖，明确仍需验证其对整次任务的影响。

下周计划：

  1. 将成熟恢复机制接入完整调用，测清故障与排队造成的任务级等待及优化空间。
  2. 比较恢复限速、公平调度与结合任务进度的调度，评估完成时间、吞吐及恢复代价。
  3. 结合不同 batch、专家热点和网络带宽验证适用边界，条件具备后逐步扩大规模。
