# 上一周期工作复盘：网络恢复、RDMA与重度丢包

**结论先说：** 上周期把有限 MoE 推理任务接入逐包 RDMA 网络，比较了故障恢复与仿真决策方法，并跑了 57% 和 86% 的单消息丢包案例。它们验证了研究链路能执行真实网络事件并反哺请求完成，也暴露了具体模型下的停滞和回退开销。**目前没有一项新恢复算法或两项论文创新已经成立。** 选择重传、超时恢复、路由阶段分析和增量重仿真都有较强先例；已有负面结果应当计入结论。

## 2. RDMA/RoCE遇到丢包时怎么办

RDMA是一类远程内存访问和通信方式；RoCE是把RDMA承载在以太网上。它们不是“RDMA协议”和“RoCE协议”二选一。常见RoCE部署使用RC（可靠连接）队列对。Verbs配置中有ACK超时、请求重试次数和RNR重试次数等字段；实际NIC/固件会决定具体重试和错误上报行为。`ibv_modify_qp`文档列出了RC状态转换中的 `IBV_QP_RETRY_CNT`、`IBV_QP_RNR_RETRY` 和 `IBV_QP_TIMEOUT`：[libibverbs手册](https://man7.org/linux/man-pages/man3/ibv_modify_qp.3.html)。

需要分清三种机制：

1. **拥塞预防/缓解。** RoCE网络常用PFC配合ECN/DCQCN控制拥塞，尽量避免队列溢出丢包。PFC是链路暂停，ECN/DCQCN是拥塞反馈与调速；它们都不等于端到端重传，也不是每个RoCE部署都采用完全相同配置。
2. **可靠传输。** RC通过序号、ACK/NAK和超时/重试维持可靠操作。传统有序接收路径可以在缺口处回退重发；选择性恢复则需要接收端保存乱序数据与丢包状态，只补缺失段。RNIC型号和软件版本不同，不能概括成“所有RoCE都只用Go-Back-N”。
3. **上层恢复。** 重试耗尽后，通信库或推理服务可以报错、隔离某条流、重新创建通信资源、重路由请求或重启任务。它们需要各自处理已发数据的可见性、缓冲释放和重复执行，不能由链路重传替代。

**本仓库的实现范围：**这次推理服务 `rdma-run` 使用的固定 ns-3 RDMA 分支按序接收，后继越过缺口时产生 NACK，发送端从未确认位置恢复发送；默认这条服务配置没有增加有界超时恢复。此次可选 `recovery.mode=go_back_n` 添加40µs初始RTO、160µs上限和3次重试，耗尽时停止整次共享仿真。本轮没有启用Karn RTT估计。固定分支源码可见 `ReceiverCheckSeq`、`ReceiveAck` 与 `RecoverQueue`：[rdma-hw.cc](/home/lry/moe-ub-cosim/third_party/LLMServingSim/astra-sim/extern/network_backend/ns-3/src/point-to-point/model/rdma-hw.cc)。

**选择性重传已经在项目中存在，但不在这次推理服务执行路径中。** `PersistentStreams`/事务探针已有 `selective_repeat/1` 和流耗尽隔离的功能参考；`rdma-run` 当前恢复配置仍是Go-Back-N。两条路径不能写成同一个已校准的生产RoCE后端。入口代码见[persistent_streams.cc](/home/lry/moe-ub-cosim/backend/rdma/persistent_streams.cc)和[配置校验](/home/lry/moe-ub-cosim/python/moe_ub_cosim/scaleout_streams.py)。Linux RXE也是软件实现，可用于理解一种RC请求重放状态机，不能替代硬件RNIC行为：[固定Linux源码版本](https://github.com/torvalds/linux/tree/adc218676eef25575469234709c2d87185ca223a/drivers/infiniband/sw/rxe)。

## 3. 重度丢包推理仿真结果

已在8个逻辑GPU、两组交错EP4、H1024/E16/Top2、声明计算的一层两步Decode任务上实际运行7个服务条件，均捕获完整逐包事件。目标是一条0→4、6144B的Dispatch，共7个数据包。网络为100Gb/s三层Clos，单rail；无故障服务54.362µs。原始数据在易失目录 `/dev/shm/moe-heavy-loss-20261028/`，摘要在[重度丢包网页](../../experiments/heavy_loss_inference/results/20261028/report.html)。本轮离线分析重新生成的结果与提交摘要逐字节一致；另用独立程序从两批原始抓包重算了发送次数、丢包命中、ACK、服务完成和另一组进度，核验摘要见[verification.json](../../experiments/heavy_loss_inference/results/20261028/verification.json)，原始抓包及复现材料已封装为[离线证据包](../review_artifacts/heavy_loss_inference_20261028/evidence.tar.gz)。

| 条件 | 目标消息与服务结果 | 说明 |
|---|---|---|
| 无故障 | 服务54.362µs，目标确认17.673µs | 参考基线 |
| 原生模式：两轮各丢目标序号0/2000/4000/6000 | 这两轮各丢4/7包；目标数据确认停滞，服务到5ms仿真上限未完成 | 源端发了两遍全消息后没有新的恢复推进。观察到1个NACK。默认NACK间隔500µs；这份配置没有RTO兜底。它是此固定分支/配置的结果，不是生产RoCE结论。 |
| 有界恢复：两轮各丢4/7包 | 目标于57.154µs确认，服务于91.297µs完成；相对基线增加36.935µs | 每个故障轮都从缺口重发整条6,144B消息，源发送3遍、重复载荷12,288B。 |
| 有界恢复：两轮各丢6/7包 | 目标于57.154µs确认，服务于91.297µs完成 | 同样首包缺失，所以同样整体重发。累计发送也为3遍/18,432B；不能推断其他丢包位置的比例无关性。 |
| 有界恢复：持续丢同4个序号 | 444.203µs报 `recovery_retry_exhausted`，没有目标成功确认 | 发送5遍、重复载荷24,576B；组0未完成，组1在共享仿真停止前已完成两轮。组1第二轮比基线早332ns，不能称它完全未受影响；故障仍停止了整次仿真。 |
| 有界恢复：丢4/7个非最终累计ACK | 服务54.362µs，目标确认17.673µs，和基线一致 | 后续更大的累计ACK覆盖了缺口；仅支持此有限确认序列。 |

比例必须带分母。57%和86%是**前两轮发送中**各丢4/7和6/7包。把最后成功的一轮也算上，目标消息全程丢包比例分别是8/21=38.1%和12/21=57.1%；持续故障是20/35=57.1%。这都是针对单条目标消息的确定性序号丢包，**不是全网随机50%或86%丢包率**。但57.1%的持续单消息故障和57.1%的完整有限运行丢包率，确实满足“50%以上的极端案例”要求。
