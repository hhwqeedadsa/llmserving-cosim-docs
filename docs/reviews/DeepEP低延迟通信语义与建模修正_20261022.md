# DeepEP低延迟通信语义与Scale-Out建模修正

本轮确认：当前仿真适合研究声明的成对All-to-All-v抽象，但不能直接解释为DeepEP低延迟实现。最重要的差异是连接复用、应用通知和完成条件。此前源额度、恢复和故障实验的执行事实保留；向真实通信库推广的主张需要重新建立。

本报告属于论文路线的G1通信语义核查。完成静态核查与四请求核算，不表示硬件校准、修改后的真实库模型或论文贡献已经完成。[机器可读证据](../review_artifacts/deepep_semantics_20261022/audit.json)记录固定源码、SHA-256、Git blob、行号、必要摘录和输入身份；[检查结果](../review_artifacts/deepep_semantics_20261022/verification.json)明确核查范围。

## 1. 核查对象与边界

目标是DeepEP v1.2.1，固定提交为`9af0e0d0e74f3577af1979c9b9e1ac2cad0104ee`。核验七份C++/CUDA/Python源码，以及此前缓存的Buffer Python和README，共九份文件。每份与同一固定完整Git树中的blob和字节数一致。未安装或执行DeepEP，也未改变十三项锁定依赖。

只讨论低延迟Dispatch/Combine，主要服务Decode。正常吞吐模式的NVLink/RDMA转发、Prefill和训练必须另建语义，不能套用本报告的通知数量。README中的跨机示例为H800/CX7；本机已有A100小形状测量不能替代该模式跨机校准。

真实数据使用已取得的四份R1-AWQ/MMLU路由：1472、1808、2675、6447。每份有128个Decode入口、58个MoE层、256专家、Top-8，总计29,696条请求/层记录。数据只有专家选择，采集运行时版本、激活精度和请求到达仍未知。

核算显式假设四个逻辑rank、每rank一请求、连续等量专家放置、关闭跨rank P2P、相同Decode入口组成一个观察窗口。这里的同步和部署由实验声明，不是数据集提供的现场部署；没有把四卡层段当作能容纳完整R1权重的生产部署。

## 2. 代码究竟有哪些差异

| 对象 | 固定DeepEP低延迟路径 | 当前非UB Scale-Out | 对研究的影响 |
|---|---|---|---|
| QP，即RDMA队列对 | Buffer初始化配置RC池；内核用peer与本地expert索引已有QP，推进WQE发送队列的resv_head。E01、E02 | 每逻辑消息`AddQueuePair`；最终ACK后清理。`fabric.cc:297–379` | 短连接初态和连接间共享历史不能直接对应生产库 |
| 数据粒度 | 每token×expert一次put；同一rank多个expert各保留一份。E03 | 贡献数相同，但按src/dst rank聚合为一条大消息。`scaleout_service.py:130–179` | 向量总量接近不代表小消息、包边界、QP调度和排队等价 |
| count与完成flag | 每source/expert发布count；Combine每expert/原source发布flag；零token也通知。E04、E05 | 只为有数据的rank pair建SEND/RECV；没有这些应用通知 | 稀疏数据不等于稀疏通信参与者；模型可能少表达必要等待 |
| 字节 | BF16 Dispatch为`2H+16`；FP8为`H+4H/128+16`；BF16 Combine为`2H`。E06 | 两方向共用`count×H×activation_bytes` | 一个精度字段不能完整描述Dispatch/Combine不同打包格式 |
| 数据就绪 | 接收kernel先等count/flag，再搬运、打包或归并。E04、E05 | 原生连续接收完整字节即放行RECV。`fabric.cc:380–389` | NIC收到数据、GPU可见、接收kernel完成需分别建模 |
| 生命周期 | Dispatch和Combine各翻转双buffer；async返回CUDA事件；hook后续执行接收。E08、E09 | SEND等完整ACK；整个EP图全部回调结束才允许下一步。`astra_adapter.cc:25–59`、`service.cc:39–54` | 当前步间完成是明确的模型边界，尚未证明等于真实服务边界 |
| 软件额度 | QP深度默认环境值1024，源码要求足够大以跳过WQ slot检查；双buffer另有限制 | 3槽、16KiB等为外加软件控制 | QP数、WQE数、消息数和GPU buffer不能按同一个“槽”解释 |

E01—E10的精确源码位置见机器证据。静态源码支持同一库生命周期内按相同key访问既有QP状态；没有证明具体网卡的RTT估计、拥塞状态、重连行为和时延。`internode::init`内部及NVSHMEM/驱动完整生命周期未在这九份文件中展开核验，不能补写为已验证。

锁定ns-3的`rdma-hw.cc:230–267`还显示，每次AddQueuePair都会设置size、初始速率和对应拥塞控制状态；`548–563`在完成后取消相应定时器并删除QP。本项目没有在此模拟真实建QP握手时延。“每消息新建”首先意味着状态初始化与生命周期差异，不能据此凭空增加连接建立耗时，或断言全部时延差异由建连开销造成。

另外，单个put会按注册内存key边界拆成多个WQE（E07）；不能把一次put、一条WQE、一个网络包和一次ACK当成同一个计数。源代码中定义quiet函数也不说明每次调用都执行quiet，本报告未作此推断。

## 3. 四份真实路由的定量核查

核算覆盖128×58＝7,424个四请求/层窗口。若组内rank数为G、专家数为E，每轮Dispatch的非自身count操作为`(G−1)E`；Combine flag同数。这里G=4、E=256，每窗口每个阶段768次，共1,536次。它与有多少专家收到token不同。

| 指标 | 全部7,424窗口 | 对应既有“两层×两步”公开任务图 |
|---|---:|---:|
| 非自身token×expert贡献，单方向 | 176,567 | 91 |
| 当前两个方向的rank聚合消息 | 138,818 | 76 |
| 目标库两个方向的数据put调用 | 353,134 | 182 |
| Dispatch count原子操作 | 5,701,632 | 3,072 |
| Combine flag原子操作 | 5,701,632 | 3,072 |
| 零token的count操作 | 5,525,065 | 2,981 |
| 零token的Combine flag操作 | 5,525,065 | 2,981 |
| 完全无数据的有向rank pair，单阶段合计 | 19,679 | 10 |
| BF16 Dispatch额外token元数据字节 | 2,825,072 | 1,456 |

在这个小batch声明部署中，96.90%的非自身count对应零token；22.09%的有向rank pair没有向量数据。后者仍参与目标库的通知过程。已有公开输出的两个wave、76条消息均与原始路由的rank聚合向量核算逐条一致，说明差异来自抽象范围，而不是原始路由丢失或字节计算错误。

这些数字是逻辑调用数量。尤其5,701,632次原子操作不等于同数网络包，也不能乘4字节得到线上流量。原子操作有协议、WQE、CQ和返回行为；P2P开启后还要重新分类同机路径。没有执行新网络包，也没有测得通知导致的排队或时延。

对于BF16数据向量，补Dispatch的16B元数据只增加双向向量字节的约0.0558%。因此不能预设“漏16B”是主要时延来源。更有判别价值的问题是：小数据、大量通知以及持续连接共同存在时，是否改变排队位置、关键等待或优化方案排序。它目前只是可证伪假设，未证明新颖或重要。

## 4. 现在如何修，什么情况下才能修改平台

不通过少建几个QP、删步间屏障或提前释放额度来制造改进。当前声明抽象继续保留为可复现基线；新增真实库模式必须另命名并记录固定版本。

| 步骤 | 具体交付与做法 | 可进入下一步的条件 |
|---|---|---|
| 1. 补操作语义 | 在独立模式中分别表达data put、count发布、flag发布、buffer epoch；保存src/dst、expert、payload、依赖与逻辑QP key | 两token去同rank不同expert仍有两份数据；零token仍有通知；本地与RDMA路径分类正确 |
| 2. 分离连接和工作 | 连接按peer/expert/NIC选择；操作另有id和单调序号区间。生命周期、路径和策略不再从每消息新端口隐式决定 | 重复两轮同key复用、不同expert分离、序号跨轮连续；拥塞和故障资源不提前归还 |
| 3. 后端能力修正 | 原生ns-3当前`AddQueuePair`建立固定总量，完成即删除并取消拥塞定时器。须明确追加工作、空闲与关闭接口，分离工作完成和连接关闭 | 在改固定依赖前独立设计、最小复用/空闲/重传反例验收；仅复用端口或搬运RTO历史均不算实现 |
| 4. 三种完成事件 | 分别记录远端通知可见/接收kernel完成、发送工作完成、buffer可复用；接收hook和事件依赖显式生成 | 最终ACK延迟、数据延迟、通知延迟、第三次buffer使用四类反例各保持因果正确 |
| 5. 校准后对照 | 获得受支持跨机设备后，比较同Buffer连续调用、冷调用、稀疏路由、零token专家和hook模式 | 分别核对数据/操作数、连接身份、阶段时延与误差；不能只拟合总时延 |

第二步不能假设peer/expert/NIC key已经等于网卡真实连接号；多NIC下库使用的RC池及设备索引规则需与配置共同核对。第三步不能预先把未来所有层的数据加到一个巨大QP中，否则等于提前注入尚未就绪的数据。

两机RDMA是否可用尚未获得答复，不据此假定硬件资源。可继续做操作计划、最小反例和静态模型核对；跨机精度声明必须等匹配测量。当前没有更改网络执行、第三方代码和完成事件。

## 5. 对论文路线的直接调整

首先收紧C12：当前“每消息新建QP”与固定DeepEP低延迟路径的连接语义不等价。这比原先“尚未证实等价”更明确，但不否定平台原本明确声明的成对All-to-All-v研究能力。

近期主线仍是正常、无故障、真实非均匀路由下的共享Scale-Out网络。优先比较当前聚合抽象与有依据的操作模型，判断模型差异是否改变网络瓶颈和方法排序；恢复作为补充。若通知和连接差异在匹配测量/强基线下没有实质影响，就记录无影响，不强行把语义复杂度写成论文贡献。

网络论文需要证明真实瓶颈和现有方法未解决的损失，再给出可部署机制；系统论文需要证明调度、通信与执行依赖的新增协同收益；仿真论文需要证明可推广的模型修正、误差改善与规模成本。三条路径都需要强近邻对照、留出数据和校准，不能由本轮源码审计直接选定。

千卡与multi-rail/Clos/分层聚合的后续规模研究继续保留。当前不能把千卡拓扑生成或512卡参考执行写成千卡完整推理验证，也不能由四请求复制扩展成生产热点证据。

## 6. 复现与检查

脚本只使用Python标准库，离线读取固定源码、原始数据与公开`rdma-run`输出，不导入平台私有图生成器、tests或fixture。来源获取方法为`experiments/paper_readiness/collect_deepep.py`；本轮只获取约0.24MiB响应，没有新增模型或大型数据下载。

```bash
python3 experiments/paper_readiness/audit_deepep.py \
  --source-dir data/research/deepep_semantics_20261022 \
  --manifest experiments/moe_trace_hotspots/results/four_requests_20261018/manifest.json \
  --graphs /dev/shm/moe-real-four-20261018/service \
  --output /dev/shm/my-deepep-audit
```

`--graphs`可省略，省略时只做原始路由与源码核算；不会声称核对了已有执行。输出目录必须不存在；失败保留，不覆盖。前两次审计定位器未区分重复出现的API说明而断言失败，已改为明确核对两个低延迟函数的位置，失败目录和原因保留；没有重跑网络或删减源码约束。

独立检查逐项枚举7,602,176个source/expert项，而不是复用核算函数；检查同rank不同expert、零贡献通知、原始输入/证据hash、25份行号与摘录、确定性重复和本地HTML链接。公开input/wave JSON移到新目录后重新核算，结果逐字节一致。HTML生成与链接检查不表示浏览器视觉验收。所有结果仅支持本报告范围，整体论文目标保持进行中。
