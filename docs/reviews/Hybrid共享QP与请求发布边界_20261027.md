# Hybrid 多通道如何共享发送队列，现有仿真还缺什么

2026-10-27；核查起点 `2be34d4`。本轮只读固定源码和当前适配器，不运行新网络、GPU或旧条件，不修改平台和依赖。新增13份路由的来源确认已在[接收报告](../../experiments/route_coverage/results/local_additions_20261027/report.md)登记，本轮不重复接收和统计。

结论：**Hybrid 的真实共享对象是 provider QP，发布对象是该 QP 已准备好的请求前缀，不能按通道分别发包。现有平台已经有显式前缀功能，但还没有完整的 Hybrid 资源绑定，也不能表达多个 GPU 生产者分开预约槽位、完成描述符和敲门铃的交错。** 这些是接入范围，尚不是新的仿真方法或网络收益。

此前的[连接身份核查](现代连接共享范围与网络优化对象_20261024.md)已经研究过 direct 路径的 QP 身份，本轮不重新计算那37条活跃QP；此前的[前缀发布实现](../tasks/submission_prefix_spec.md)也继续作为已有能力。新核查集中在 Hybrid 的调用链、发布 handler 的适用范围和原生适配器实际保留的边界。

## 1. 从通道到真正的 QP

固定 DeepEP `f6aa38fe06cd4a0489e7730365d4e0114970a2f3` 的 `hybrid_dispatch.cuh:58–79` 说明每个 warp 是一个通道，并调用 `get_qp_mode`。`comm/barrier.cuh:57–88` 按 SM 数、通道数、可用 context 数分配索引：

- 只有一个索引时，通知与数据使用索引0；跨SM共享时采用GPU范围的共享规则。
- 有多个索引且存在通知 warp 时，通知使用0，数据从1开始分配。
- 资源足够时按SM分配；不足时多个SM/通道按取模共享。不是每通道总有独立QP。

`comm/handle.cuh:27–34` 将这个索引传给 `ncclGin`。固定 NCCL `12df1a11afad322be5a204a2db890161cbf8131d` 的 `impl/gin__funcs.h:113–130` 再拆成：

```text
connectionId = contextIndex % ginConnectionCount
contextId    = contextIndex / ginConnectionCount
```

GDAKI 的 `gin_gdaki.h:60–64` 使用当前 handle 的 `gdaki_ctx[contextId].gdqp[peer]`。因此持久资源身份至少要保留 devComm、发送GPU、provider connection、connection内context及peer；物理设备另由该connection的实际绑定确定。源/目的GPU相同，不能直接证明同QP；通道不同，也不能直接证明不同QP。

现有 `modern_deepep_plan.py` 已有 `qp_mode` 和 `context_assignment`。Hybrid logical输入目前没有声明provider、context分配及物理设备，也没有完整网络执行；不能为补齐字段而擅自指定一个默认现代硬件配置。

## 2. 哪些请求会推动发布

固定 Hybrid Dispatch 的三类调用要分开：

| 对象 | 源码行为 | 建模时必须保留 |
|---|---|---|
| rank计数和expert计数 | 179–187行先聚合rank-count put，再普通expert-count put | 同peer/同通知context上的先后顺序；后者可推动前缀发布 |
| token数据 | 450–457行的远端put带 `AggregateRequests` | 准备数据请求；不能当作一个合并大消息 |
| 通道tail/finish | 337–348行调用 `red_add_rel`，不带聚合标志 | 远端走GIN signal；本地域在wrapper中走直接atomic，不能生成假的self RDMA包 |

`handle.cuh:102–121` 对 `red_add_rel` 先检查是否可通过对称地址访问：同rail的本地域可直接执行GPU atomic，远端才调用GIN。rank/expert计数的 `put` 则按wrapper注释可以让self请求经NIC API，不能只根据peer等于本卡统一删掉全部self操作。

`gin_gdaki.h:43–48` 将 `AggregateRequests` 翻译成 `SKIP_DB_RINGING`，并没有把多个payload合并成一个RDMA操作。是否跳过发布还取决于实际handler，见下一节。

一个手工因果见证说明跨通道共享为何必须保留：在相同QP上，A通道先准备数据a，B通道准备数据b，随后B提交非聚合finish。在DB类前缀规则下，B可以一起发布 `[a, b, finishB]`；a不必等A自己的finish才进入NIC。**但A的转发者仍需收到A自己的tail/finish才能按规则消费a。** 这是源码允许的事件关系示意，没有执行GPU或测量时刻，不代表已经观察到应用收益。

## 3. AggregateRequests 不是所有 handler 的统一规则

固定DOCA设备头的 `doca_gpunetio_dev_verbs_qp.cuh` 实际区分以下路径：

| handler | 固定源码事实 | 当前 `explicit_prefix/1` 的适用性 |
|---|---|---|
| GPU_SM_DB | 524–551行检查SKIP；未跳过时锁定、取producer前缀最大值并ring；同次推进可有两次物理门铃写 | 只覆盖逻辑准备/发布前缀，不覆盖锁、物理写和时间成本 |
| GPU_SM_NO_DBR | 502–513行检查SKIP；取最大producer前缀后ring | 同样只覆盖逻辑边界 |
| CPU_PROXY | 638–647行的submit函数调用ring_proxy，此处没有按SKIP直接返回 | 不能直接沿用“聚合操作不发布”的DB规则；实际proxy消费还需追踪 |
| CPU_PROXY_FREE_FLOW | 231–241行按每个WQE写ready标记；submit分支直接返回 | 不属于当前普通ready前缀/门铃模型；实际消费次序不能从这几行推定 |

主submit的AUTO分派在650–682行读取实际 `qp->nic_handler`。host在 `gin_host_gdaki.cc:792` 传入配置，但默认参数0为AUTO；缓存源码和本机条件没有给出运行时实际选中了哪个handler。因此本轮不能把DB路径写成“默认现代DeepEP在所有机器上的行为”。表格也不声称覆盖所有BlueFlame API。

一次逻辑发布和一次物理门铃写不是相同计数。聚合标志也不是选择性重传、报文合并或拥塞优化算法。

## 4. 当前平台表达到了哪里

| 边界 | 已有实现 | 缺项及影响 |
|---|---|---|
| 单QP预约/有限深度 | `GinWorkQueue::ReserveBatch/CanPrepare`，按最后预约槽是否可用判断 | 真实WQE拆分及provider CQ成本未校准；不能把一项MRT1事务当作任意真实操作的精确WQE数 |
| 准备与发布分开 | transactions/5的 `explicit_prefix/1` 和prepared回调 | 这是已经交付的功能，不能再次作为新贡献 |
| 跨操作的前缀发布 | `RemoteTransactions::PumpExplicit` 允许非聚合操作发布此前已准备的同连接请求 | 只有把实际共享QP映射成同一持久连接才能保留跨通道作用；不得跨连接发布 |
| 保留源数据和实际完成 | 在发布时按source模型捕获字节，ACK/原子回复按既有规则完成 | 功能字节模型，不代表GDAKI/GPU实际DMA读取及内存序时刻 |
| GPU生产者的独立预约与准备 | queue核心允许分项Prepare；当前网络适配器在Submit后立即Pump | 外部接口不能指定“已预约但描述符尚未准备”的生产者，不能研究该等待的真实开销 |
| 多生产者门铃交错 | 当前适配器按已提交操作顺序同步准备/发布 | 不表达先预约者晚敲门铃、后预约者先敲门铃等交错；未证明是当前声明范围内的平台漏洞 |
| Hybrid全调用 | 公开命令只生成逻辑路由和有限Dispatch回放 | 通知、屏障、完整Combine及provider绑定尚未组成一个完整Hybrid网络调用 |

代码依据：`backend/rdma/remote_transactions.cc:353–359, 387–410`，`backend/rdma/transaction_session.cc:215–228`；功能queue在 `backend/rdma/gin_work_queue.hh`。后者头部还有早期“Not linked into Fabric yet”的注释，不能靠这句注释判断当前是否接入；实际适配器已调用它。本轮不改变平台源码。

真实设备路径还有两个不能跳过的关系：

1. `onesided.cuh:67–103` 先预约、准备，再mark-ready和submit。普通共享模式的mark-ready在 `qp.cuh:156–195` 按预约次序推进；后预约生产者可能等待更早的生产者完成准备。完整资源DAG可以表达这条依赖，不能据此宣称普通任务图必然失效。
2. DB类submit对producer取最大值。假如更晚前缀已由另一生产者发布，较早生产者迟到的门铃可不再推进；当前queue核心的 `PublishThrough` 则拒绝前缀回退。现有同步适配器不会生成该交错，因此这是未来并发生产者接口需明确的语义，不能将手工调用核心的拒绝直接称为当前网络错误。

## 5. 下一项应当验证什么

**先补一条可信的Hybrid执行路径，再判断仿真创新是否成立。** 不继续增加QP数量统计，不重开已关闭的slot、静态缓存或健康四卡排序实验。

平台增量应先另写规范，明确选择DB/NO_DBR等一个受支持handler，保持未知的AUTO行为为未知，声明context/物理NIC/持续资源身份；按源码保留聚合、进度、self旁路和必要通知。若要研究准备竞争，必须让预约、描述符就绪及发布成为可分开的实际事件，不能用固定延迟冒充观测。

研究再与**正确分层流模型、保留共享QP/准备前缀/动态buffer的完整资源DAG**比较。对照固定路由、调用、带宽、总队列容量、源保护和完成条件；不能以每操作立即发包的弱模型作为唯一基线。只有错误决策造成的损失或完整仿真宿主成本有实质差距，才支持两个候选之一。GPU准备/门铃成本及provider消费未知时，不报收益率或同成本优化上界。

两个候选仍是“可靠网络决策所需的最小表示”和“保留交互影响的低成本细化”，**本轮均未成立**。共享QP、普通资源DAG和显式前缀本身都是需要使用的已有方法。若强基线继续消除差距，就应淘汰相应创新理由，不能把不断接入源码称作论文成果。
