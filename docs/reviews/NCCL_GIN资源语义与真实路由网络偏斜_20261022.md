# NCCL GIN资源语义与真实路由网络偏斜

现代通信库已经减少了热点专家造成的重复发送，但没有消除目的卡的负载不均。要研究这种不均是否形成可优化的网络等待，仿真器必须先准确表示连接绑定、工作队列、通知和完成事件。本轮完成固定源码核查与全部现有解码路由核算，没有执行新的网络仿真或测量硬件。

证据入口：[固定源码及逐段摘录](../review_artifacts/nccl_gin_20261022/sources.json)、[上下文映射核查](../review_artifacts/nccl_gin_20261022/mapping.json)、[全量路由摘要](../review_artifacts/nccl_gin_20261022/routes-summary.json)、[逐窗口数据](../review_artifacts/nccl_gin_20261022/routes-windows.csv)、[验证记录](../review_artifacts/nccl_gin_20261022/verification.json)、[本地检查点](../review_artifacts/nccl_gin_20261022/archive.json)。前阶段[现代DeepEP核查](../review_artifacts/deepep_modern_20261022/report.html)仍保留其范围。

## 1. 固定研究对象与约束

NCCL固定为v2.32.3-1、提交`12df1a11afad322be5a204a2db890161cbf8131d`；DeepEP固定为`f6aa38fe06cd4a0489e7730365d4e0114970a2f3`。18份NCCL源码/说明通过完整Git树、blob和SHA256校验，另复核3份固定DeepEP源码。只读获取累计响应1,121,498B、请求用时约11.44秒，没有安装、升级或执行通信库。

目标是推理解码时多个专家并行组共享Scale-Out网络的等待。当前只研究选定的GIN/GDAKI路径，不能推广到所有NCCL provider、网卡或硬件版本。现代DeepEP的Hopper+等运行条件仍须与实际设备匹配；没有A100上的现代库校准结果。训练、生产请求总体、完整千卡推理与故障下的真实性均未由本轮验证。

## 2. 上下文、连接、NIC和QP是四层对象

GIN是GPU发起网络操作的接口。应用传入的context index先选择GIN连接，再选择该连接内的上下文，最后在provider中找到面向peer的队列对（QP）。QP持有传输状态；工作队列条目（WQE）描述一次提交的工作。

| 源码层次 | 固定源码说明 | 仿真含义 |
|---|---|---|
| 应用上下文索引i | `connectionId=i%C`，`contextId=i/C`，C为连接数 | 一个索引不是一张NIC或一个独立消息 |
| 分配数量 | 请求数量向连接数的整数倍上取整 | 请求5个、连接2条时分配6个；分配量与实际活跃量不同 |
| GIN连接 | 建连使用`localGinDevs[commIdx % nLocalGinDevs]` | 需记录实际本地设备；多条连接可以落在同一NIC |
| GDAKI上下文 | 每连接的上下文数组，再按peer访问QP | 不能把DeepEP参数直接解释成整个集群的QP总量 |
| 数据通道 | DeepEP按SM、warp和通知角色选context index | 小batch可能只激活少数通道；分配更多上下文不保证用上更多NIC |

离线核查覆盖连接数1—4、请求上下文数1—32，共2,209次索引比较。另用明确声明的算术示例：2个SM、每SM 4个dispatch warp、调用使用5个上下文、2条连接。一个token只由SM0/warp0处理，选择上下文1/连接1；8个token才覆盖两条数据连接。控制上下文0走连接0。这是源码表达式示例，没有运行CUDA，也不是设备配置或吞吐预测。

因此，“增加QP数量”可能同时改变NIC分流、通道共享程度、总队列容量和竞争关系。后续对照应分别固定连接/NIC绑定、有效上下文、每队列深度与总槽数，解释不能固定的条件。否则不能把变化归因于单个资源因素。

## 3. 完成事件不能合并为一个消息完成

| 事件或机制 | 固定证据 | 后端必须保留的区别 |
|---|---|---|
| `flush` | API保证put源buffer可复用，不承诺远端完成 | 本地完成不直接唤醒远端GPU消费者 |
| strong signal | 同peer、同context此前put的可见性受其保证 | 不能无依据扩展成跨NIC、跨context的全局屏障 |
| legacy signal默认 | DeepEP沿用requirements初始化值，NCCL默认`ginStrongSignalsRequired=true`，再传入描述符 | 不能按较弱通知语义建模当前固定组合；这是源码链条，尚非编译运行验证 |
| GDAKI flush实现 | 读取相关QP已保留工作的位置，等待CQ并执行system fence | flush有明确覆盖范围；不能等待未来才就绪的工作 |
| 槽可用检查 | 先原子取得工作索引，再在将复用的槽上检查CQ | reservation ticket和真正可写槽分开；队列满时会阻塞提交 |
| signal实现 | 构造64位原子fetch-add WQE及返回操作数 | 不是“8B普通数据消息”；WQE数量不是包数量 |

CQ是完成队列。对端数据已接受、GPU已能消费、发送工作完成、CQ进度允许复用槽，这些事件有联系但不能直接等同。即使应用没有直接等待某条ACK，完成反馈也可能通过有限队列阻止后续提交；上一轮离线图中sender_done不直接阻塞kernel完成，不能据此排除网络反压。

GDAKI在没有显式设置时有provider队列深度默认值，但DeepEP会传自己的深度。不能直接拿默认128当成实机运行值，更不能据此证明此前软件3槽额度是真实硬件瓶颈。

GDAKI另有MLX5特定的put可见性处理，源码能力项`FlushesAllPutsOnAnySignal`及注释说明到达signal会flush先前收到的put。现代DeepEP会flush多个上下文，再用上下文0做屏障。跨连接、跨NIC组合的精确可见性与代价需要匹配硬件验证；静态资料的边界不能当作发现DeepEP错误。

## 4. 聚合提交不是把所有操作合成一条流

`AggregateRequests`在所读GDAKI中映射为跳过doorbell ringing。doorbell是通知NIC处理已准备工作的提交动作：工作仍分别占有队列位置，随后满足条件的提交可通知NIC处理准备好的前缀。该标志本身不会取消槽可用检查，也不自动将计数、数据和signal合成一个WQE或包。

仿真需分开取得索引、取得槽使用权、准备完成、通知NIC、发送和完成反馈。并发准备不能让尚未写完的条目被消费；纯聚合准备且没有后续通知时，也不能凭空发送。具体CQ模式还可能合并完成信息，不能强行要求每操作一个CQE。

provider对大put的1GiB分段是WQE级传输上限，网络MTU决定包级切分。这两个粒度不可混用。实际线上字节还包含协议头、响应与重传，本轮没有从调用数猜这些数量。

## 5. 全部真实路由的网络核算结果

输入仍是已核对的四份R1-AWQ/MMLU原件，数据集revision为`27febb7b2d24169560a9f6f83d38eb53f94916cf`。每请求128条Decode记录、58个MoE层，E256/Top8/H7168。声明EP4、每rank一个请求token、连续等分64个专家、跨rank全部RDMA；相同Decode序号组成一个假设同步窗口，没有观测到真实请求到达或发起时刻。这不是完整R1四卡部署证明。

覆盖7,424个窗口、29,696条token-layer选择；独立按目的专家区间枚举核对118,784个矩阵项。只核算fresh-routing direct Dispatch，不把Combine套用相同公式。

| 指标 | 逐专家贡献口径 | 现代direct目的rank去重 |
|---|---:|---:|
| 跨rank贡献/目的token份数 | 176,567 | 69,409 |
| 仅hidden的BF16操作数字节 | 2,531,264,512B | 995,047,424B |
| 每窗口目的rank入量最大值/均值，p50 | 1.500 | 1.333 |
| 同上，p95 | 2.074 | 1.500 |
| 同上，最大值 | 2.833 | 2.400 |

最大值/均值按每个窗口4个目的rank的跨rank接收份数计算，再对窗口取经验分位数。不同专家计算输入的rank偏斜p50=1.5、p95=1.875、最大2.75，与去重后的网络偏斜不同。69,409份是分发操作所需token副本数，不是API总调用数、线上包数或总流量。

去重后有330个窗口的目的rank入量相同，181个窗口恰好覆盖全部12个非自身方向，零跨rank流量窗口为0。其余窗口仍有不均，但不能由此声称交换机拥塞：需要实际发起节奏、拓扑、端点绑定和服务速率才能形成排队。四份请求中的相关记录也不能当作7,424个独立总体样本。

hidden字节不含token元数据、对齐、计数、屏障、响应和包头。逐专家口径与direct口径的差值是已存在通信机制的差别，不是我们提出算法获得的加速比。所有窗口累计后接近均匀，也不能排除短窗口不均；相反，短窗口偏斜不能直接推出长期拥塞。

## 6. 当前后端应改什么，为什么

当前`Fabric::Send`公开给适配层的是id/src/dst/bytes/plane及接收、ACK回调；它没有GIN连接、显式NIC、远端偏移、原子值或可追加WQE。逐字节消息新建QP再清理的模式，不能通过新增一个“复用”标签变成现代运行时。

已形成[现代操作与后端实施规范](../../experiments/paper_readiness/modern_backend_contract.md)，当前是待实现设计。后续工作按以下顺序推进：先固定物理端点与团队映射；生成现代去重、计数、屏障操作；表示持久连接和有限工作队列；实现所选provider事务及完成事件；再接同一ns-3时钟与包级反馈。未知原子协议、可见性或不支持的rail连接应明确拒绝，不能用普通小流替代后宣称真实。

研究对照需要同时满足现代算法和物理可部署性：direct要求的FULL互通与hybrid的RAIL/NVLink转发不可混用；端点NIC选择也不能被交换机ECMP替代。Clos、汇聚和HPN式拓扑的比较须注明各层端口、带宽、超售、rail及转发成本。在这些条件成立后，再检验多EP组的路由不均是否形成简单基线无法消除的关键等待。

## 7. 本轮支持与不支持的结论

支持：现代direct去重会明显降低这四份请求在声明放置下的Dispatch副本数和目的rank偏斜；固定GIN/GDAKI有真实的持久上下文、队列反压和完成边界；当前字节消息适配不足以表达它们。

不支持：现代库在本机运行成功、网络热点已导致显著业务损失、提出方法有加速、千卡完整推理已验证，或已形成A类论文贡献。匹配硬件校准、留出请求、共享网络的在线验证及更大规模证据仍需补齐。当前研究目标保持进行中。

复核方法见[实验README](../../experiments/paper_readiness/README.md)。本轮HTML检查本地链接，尚无浏览器视觉验收。源码摘录预检曾因peer循环定位在多个函数重复而失败，已改为定位唯一flush函数，未重取源码、提高预算或重跑网络。
