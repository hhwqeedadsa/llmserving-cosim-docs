# Prefill放置强基线：计算更均衡，通信未必更少

在同四份真实路由上，采用数据集作者公开代码中的两种 Prefill 频次贪心放置，Decode 每窗口最忙 rank 的计算输入 p95 都从 15 份降至 14 份，但跨 rank Dispatch token 副本分别增加 16.12% 和 14.56%。这不是测得推理变慢，而是确认了后续网络研究不能用计算均衡代替网络评价。

另一项构造性核查说明，即使保留全部单专家和专家对出现次数，也不总能决定按目的 rank 去重后的通信量，甚至不能保证两个放置方案的通信量排序。这个结论可由集合覆盖关系解释；高阶共选、超图与放置本身不是新颖性主张。本轮加强了基线与问题边界，没有完成现代 DeepEP 包级基线或证明A类论文贡献。

## 一、最接近的已有工作已经做了什么

数据集作者的[Patterns behind Chaos，固定v5](https://arxiv.org/html/2510.05497v5)已经分析单专家不均衡、专家对共激活和 Prefill—Decode 关联，并给出晶圆 GPU 仿真与实机专家放置案例。故“专家有热点”“共激活并非独立随机”“可以利用 Prefill 做放置”均不能作为本项目的新发现。

需要区分其共激活洞察与实际放置算法：正文 Insight 5 讨论拆开共激活专家以增加计算并行度，同时明确存在通信权衡；Case Study 2 的 Remap 依据 Prefill 专家负载排序分配，并不是以专家对矩阵为输入的算法。我们不能把下面的两两统计反例写成对其实际算法的否定。

| 对照对象 | 主要目标与范围 | 对本研究的约束 |
|---|---|---|
| 原文共激活分析 | 已有专家对偏斜、路由分组、放置/并行度权衡的观察 | 共激活现象和静态放置不能直接作为创新 |
| 原文实机案例 | Qwen3-235B、8张H100/NVLink、SGLang/DeepEP；报告专家三次线性计算时间，明确排除 Attention、All-to-All 和 top-k | 其计算时间加速不等于本项目的 scale-out 网络或端到端加速；原文没有以这个指标宣称后者 |
| 原文晶圆案例 | 多 chiplet、HBM/计算/D2D 资源；原文报告单GPU专家和双GPU P2P校准 | 不能将其视作已验证千卡 Clos/RDMA，亦不能以不同对象给对方功能打叉 |
| 当前公开放置代码 | `zhongkaiyu/moe_exp_placement@b059b85…`，容量受限、按 Prefill 频次降序的 LPT 贪心；另有最后10 token版本 | 是本轮采用的更强参考基线，不再只与随机放置比较 |

本次核对同一完整 Git 树中的四份源码、Git blob和 SHA256。HEAD 是本次读取时的固定版本，尚未核对其与论文 Zenodo 评价版本的对应关系。正文描述 roofline Cost，当前公开函数 `generate_greedy_placement` 直接加专家频次；本轮按后者适配，不把它叫作论文 roofline/H100 重现实验，也不据此断言论文实现错误。

作者当前实机artifact入口还指向 `core12345/real_GPU_exp_placement_trace`；本机四份 R1-AWQ/MMLU 来自此前另一个数据目录，不能混同为其 Figure 17 原始输入。本轮未下载新路由、模型或运行作者程序。来源与精确摘录见[sources.json](../review_artifacts/prefill_placement_20261022/sources.json)。

## 二、这轮如何避免看未来选放置

固定协议见[研究配置](../../experiments/paper_readiness/placement_baselines_protocol.md)。沿用四请求、256专家/Top8、层3—60、Decode entry1—128、EP4和每rank一请求；EP4是条件映射，不表示完整R1在四卡上可部署。Prefill是entry0，四份记录各含105、28、10、6个token。源rank按manifest文件次序分配，所有放置共享相同的原始选择。

准备程序将 Prefill 频次写入 observed，将未来 Decode 选择和来源写入 truth。放置程序只接收 observed 目录，没有 Decode 或真值输入；评价程序才读取未来选择。用新路径仅恢复 observed 文件再生成放置，结果逐字节相同。Prefill属于相同四请求的先行信息，后续Decode不是独立请求留出集。

固定三个条件：连续等量放置；全部 Prefill 频次 LPT；每请求最后最多10个 Prefill token 的频次 LPT。LPT（Longest Processing Time first，此处以次数作负载代理）先按频次降序，逐专家放到尚未满且累计负载最小的rank；专家ID和rank ID固定破平局，每rank恰好64专家。它是贪心算法，不保证全局最优。

两种LPT均按原始次数统计，和已核查的公开函数相符，不进行请求平权。全量统计中长Prefill自然权重更大；最后10个token版本也不是严格请求平权，因为最短记录只有6个。选择规则在看到Decode结果前固定，不从两个版本中选“赢家”。

本轮不比较需要额外专家槽的 Dup；若后续加入，应同时增加其显存、复制及调度成本，不能在固定64专家/rank条件下免费给副本。EPLB及其他强方法也尚未完成对照，因此这还不是全部强基线评测。

## 三、实际观察到的计算—通信权衡

以下统计各覆盖7,424个窗口。窗口由相同层/Decode位置组成，是声明的对齐，不是实测同步。计算输入是专家贡献次数，不是计算时间；入量是去重token份数，不是包数或NIC吞吐。

| 条件 | 跨rank Dispatch副本 | 相对连续放置 | 跨rank专家贡献 | 最忙rank计算输入 p50 / p95 / 最大值 | 最大目的入量 p50 / p95 |
|---|---:|---:|---:|---:|---:|
| 连续放置 | 69,409 | 基准 | 176,567 | 12 / 15 / 22 | 3 / 3 |
| 全部Prefill频次LPT | 80,596 | +16.12% | 178,170 | 11 / 14 / 18 | 3 / 3 |
| 最后最多10个Prefill token频次LPT | 79,515 | +14.56% | 177,544 | 11 / 14 / 20 | 3 / 3 |

每窗口总计算输入均为32份。LPT改变专家到rank的映射，因而同时改变计算聚合、本地旁路、目的rank覆盖及去重；这不是只改变计算均衡的单因素实验。固定每份Dispatch put布局时，可以按副本比例换算这部分字节变化；不包括计数、屏障、响应、重传或Combine，不能称作整次推理通信增加相同比例。

配对结果也没有保证每个窗口计算都改善：

| 条件 | 计算最大输入降低 / 相等 / 增加的窗口 | Dispatch副本减少 / 相等 / 增加的窗口 |
|---|---:|---:|
| 全部Prefill LPT | 4,161 / 1,266 / 1,997 | 602 / 1,181 / 5,641 |
| 最后最多10个token LPT | 4,080 / 1,307 / 2,037 | 675 / 1,251 / 5,498 |

这为后续网络实验提出了有判别力的问题：当计算输入减少、发送量增加时，在NIC受限、上行受限和多组共享网络下，哪一部分真正暴露在推理关键路径上？目前没有网络时长、真实GEMM profile或迁移开销，不能回答净收益正负，也不能把上述比例写成实机退化。

## 四、为什么全部专家对统计仍不一定够

构造一个EP4、256专家、每rank64专家的合法容量映射，令源rank0有4个token，其他rank没有源token，即batch=[4,0,0,0]。每token选8个专家，其中5个固定为{6,7,8,9,10}、都放在rank0；另外3个从以下集合选取：

| token | 路由族A的三个可变专家 | 路由族B的三个可变专家 |
|---|---|---|
| 0 | {0,2,4} | {0,2,5} |
| 1 | {0,3,5} | {0,3,4} |
| 2 | {1,2,5} | {1,2,4} |
| 3 | {1,3,4} | {1,3,5} |

两族每个可变专家均出现2次，每个固定专家出现4次；全部专家对的出现次数也完全相同。剩余245个未选专家可填满各rank余下槽位，不影响例子的选择或通信。

比较两个放置：P把{0,2,4}放在rank1；Q把{1,3,5}放在rank1；其余选中的专家均在rank0。两者每rank专家总数均为64。在两族和两个放置下，计算贡献向量一律为[26,6,0,0]，逐专家远端贡献一律为6，但去重后的Dispatch份数为：

| 输入 | P放置 | Q放置 | 通信量较少者 |
|---|---:|---:|---|
| 路由族A | 4 | 3 | Q |
| 路由族B | 3 | 4 | P |

因此，一个只接收这两个阶次统计、并在P/Q中选放置的方法，无法保证对两族均选到通信份数较少者：输入统计完全相同，正确选择却不同。这是对信息充分性的反例，不是对所有亲和性启发式的经验否定。它也没有宣称网络完成时间排序必然相反。

计数原因是按目的rank是否被某token的专家集合覆盖来去重，涉及集合交叠的高阶项。常规超图/集合覆盖方法已有这种区别；本项目不能仅将专家对换成超图就宣称新算法。需要证明的是：在代表性真实负载和真实实现中，哪些简化会改变重要网络决策，如何以低成本保留必要信息。

上述反例为人工代数输入，不是四请求中的观察，不满足某个具体模型全部路由限制的证明，也不作模型准确率声明。精确选择、完整等容量映射和核算见[pair_counterexample.json](../review_artifacts/prefill_placement_20261022/pair_counterexample.json)。第一次复核把奇偶族的预期P/Q数值写反而失败；手工逐token核对后更正标签方向，保留原失败日志，没有改变原件、算法、不变量或真实基线结果。

## 五、论文定位应如何收紧

现有工程、去重公式和热点观察都不足以建立新颖性。本轮补上了一个更可信的参考方法和一个明确的信息边界，候选问题是：面向现代去重通信，怎样在保留网络方案排序的同时降低联合仿真成本？这仍是待验证的研究问题，不是已完成的方法。

验证必须分两层。先在正常无故障条件下，检验原始路由、边际热度、两两统计或累计矩阵的替代，是否改变绝对链路服务量、实际排队及业务完成。然后在留出请求上检验新的简化方法是否保留方案排序、绝对误差和最差退化；不能只在同四请求上拟合，再称为泛化。

现代在线实现仍缺self-peer GIN物理路径及成本、provider/CQ服务和GPU可见性等关键依据。已有MRT1事务功能不等价现代RoCE/GIN，不能绕过这些缺项把“数据流小例”升级为现代完整基线。下一项网络执行应明确它检验哪项机制及未覆盖部分；若结论依赖未知成本，应给敏感性边界，匹配设备后再校准。

千卡部署、真实训练热点、不同模型和batch泛化仍未取得完成证据。当前可见硬件仍不满足固定现代分支的匹配校准，不重复将A100局部功能证据外推。论文目标保持进行中。
