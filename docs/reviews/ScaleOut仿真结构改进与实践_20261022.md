# Scale-Out仿真结构改进与实践

2026-10-22。本轮已实施三项结构改进并完成小规模对照：消息数与逻辑字节双约束、常量空间的交换机队列积分、源端协议进度与阶段诊断。平台本地提交`7630b98`，没有push。新增能力用于解释和比较网络行为；当前实验没有取得优于透传的服务性能收益。

## 1. 最终服务什么问题

目标是研究：MoE模型跨服务器执行时，专家选择形成的通信不均衡，怎样经过拓扑、链路带宽、交换机排队和端点协议，最终影响推理的完成时间与长尾；再验证网络结构或通信方法是否真正改善业务。

应能回答具体问题：同样的Token和专家选择，换Clos/Agg、rail数量、上下行带宽、专家放置或通信粒度，哪些端口更忙、哪里开始等待、哪些请求受影响、改善是否转移了瓶颈。输出应同时提供网络证据和业务结果，不能仅凭交换机队列下降就宣布优化成功。

本平台继续组合三类能力：LLMServingSim负责请求组批与KV记账；ASTRA负责计算/通信依赖图执行；锁定的原生RDMA ns-3负责Scale-Out包、队列、反馈和链路事件。我们完善它们之间的任务、完成与资源边界，不把三者已经具备的能力算成新的网络算法。Scale-Up的ns-3-UB入口保持独立，不混链、不拼接不同运行时间。

## 2. 当前约束与输入边界

| 对象 | 当前实际范围 | 不能据此宣称什么 |
|---|---|---|
| 服务任务 | 本轮为KV已就绪的Decode，8GPU、两组交错EP4、32请求、batch/rank4、1层2步；H1024、E16、Top-K2 | 不是完整生产模型运行，不含Prefill、P/D迁移或训练优化结论 |
| GPU与计算 | 使用A100标签和显式声明的计算耗时；不执行张量数值运算 | 不是A100实测校准；换GPU名字不会自动获得准确的计算、显存或NIC模型 |
| 专家选择 | 沿用固定合成路由；平台已有有限真实路由回放入口 | 不能把合成流量称为真实训练热点；此前4份MMLU路由也不能代表整个模型和负载分布 |
| 网络 | 本轮固定100G三层Clos；平台已有参数化Clos/Agg、multi-rail/plane和机内模型 | 已能生成千卡拓扑，不等于千卡包级联合执行已经验收 |
| 通信 | 按GPU对聚合Dispatch/Combine，原生网络再按MTU分包；每条逻辑消息新建QP | 不是DeepEP/NCCL真实分块、通道或持久QP实现；MTU分包不等于应用通信分块 |
| 完成 | 连续接收数据→RECV；完整ACK及原生发送映射移除→资源回收→SEND | 数据到达不等于ACK完成，发送映射移除不等于GPU缓冲、接收QP或KV全部释放 |
| 资源与复现 | 单次仿真5ms/宿主60秒/RSS1GiB/地址2GiB；小场景、固定依赖和输入 | 不通过失败后加预算或改输入来制造成功；本轮没有千卡或硬件性能测量 |

前端提交的是按本轮组批和专家选择生成的Chakra依赖图，含COMP、SEND、RECV及消息端点/字节/plane；不是事先固定完成时间的流量录像。网络实际完成事件返回后，前端才推进下一步。改变batch、模型或专家路由需要重新构图；网络拓扑、带宽、协议与观测另行配置并记录。

EP（专家并行）决定哪些GPU共同承接专家贡献及All-to-All；多组EP可代表复制的服务组，但本轮不模拟训练DP（数据并行）的梯度All-Reduce。因此，训练DP、推理副本与EP组不能只按组名互换。

## 3. 本轮具体改了什么

### 3.1 发送控制：同时约束消息数与逻辑字节

旧实现每源只数活跃消息：一条2KiB消息和一条8KiB消息各占一个额度，难以分辨大小差异。现在可选`admission.max_active_bytes_per_source`，与`max_active_per_source`同时生效。额度统计从准入到资源回收期间的整条逻辑payload和，同一源跨所有plane共享，同机crossbar排除。

控制器仍只读当前已提交的源端任务、目的GPU、字节和本源资源，不读取未来专家路由、远端队列或接收端真值。FIFO保留全局就绪顺序；目的端轮转保留每目的端FIFO，只在当前额度容纳得下的目的端队首之间选择。无合格任务时不轮询、不计虚假的重复决策成本。

这是一种明确的软件注入约束，**不是硬件NIC在途窗口或GPU通信缓冲模型**。省略或0保留旧字节行为；单消息超过非零额度明确拒绝，不偷偷拆分或放宽。例子见[bytes8192.json](../../examples/scaleout_rdma_admission/bytes8192.json)，范围与错误语义见[使用说明](../../examples/scaleout_rdma_admission/README.md)。

### 3.2 网络观测：汇总不依赖保存每个包

新增`queue_metrics=true`，每个交换机出口维护当前队列字节、最后变化时刻、峰值、累计字节×纳秒和事件次数。内存与实际端口数成正比，不随包数积累历史；它不减少网络本身的包级事件。

这里修正了统计口径：原生入队钩子在加字节后触发，出队钩子在减字节前触发。适配层先核对字节守恒，再统一成变化后的状态积分。否则直接积分旧无事件类型记录，可能把已出队的包错误保留到下个事件。

新汇总覆盖全程全部交换机BEgressQueue出口与优先级，排除正在序列化的包，不包括GPU发送QP队列。开启完整包记录、记录截断到3条，或使用summary模式关闭明细，均得到相同积分。正常和故障两类运行，还分别与逐包“大小×驻留时间”独立核对。

### 3.3 系统诊断：明确等待发生在哪个阶段

记录源QP累计确认序号`snd_una`、下一个发送序号`snd_nxt`，不再只看接收端是否齐备。离线诊断把就绪→准入、准入→首包、首包→数据齐备、数据齐备→完整ACK、完整ACK→资源释放分开。

完整消息各段之和等于其就绪到回收时间；未完成段保留null，另外给停止时已经等了多久。数据交付包含序列化、传播、队列和可能的恢复，不能把整个区间称为排队；不同消息的累计时间也不能直接当服务关键路径。

源端协议进度、接收端完成、全局队列和图依赖均为离线评价资料，不反向交给在线准入策略。详细生命周期截断时只报告终态，不假装已经重建完整占用历史。

## 4. 实践结果与新发现

固定输入的完整结果见[实验结果](../../experiments/scaleout_structure/results.md)和[HTML阅读版](../review_artifacts/scaleout_structure_20261022/report.html)。这里保留直接影响后续方案的结论。

| 条件 | 服务完成时间 | 队列积分 B·ns | 端口队列峰值 | 每源活跃逻辑字节峰值 |
|---|---:|---:|---:|---:|
| 不限制发送 | 54.362μs | 63352868 | 8912 B | 32768 B |
| 消息数上限3 | 63.545μs | 69269180 | 8912 B | 18432 B |
| 消息数3＋字节8192，FIFO | 122.068μs | 43422304 | 9624 B | 8192 B |
| 同额度，目的端轮转 | 113.045μs | 41323132 | 9624 B | 8192 B |

第一，按字节约束确实改变了活跃payload，但没有改善当前业务性能。轮转比同额度FIFO快7.39%，仍比透传慢107.95%。不能只选FIFO作为弱基线，把这个相对改善写成对整体服务的收益。

第二，轮转这次确实有了不同选择机会。13070ns时源1剩4096B，FIFO队首消息36需要8192B，轮转选择另一目的端的消息38、2048B。实际逐源身份顺序发生改变；同目的端内部顺序、共同任务图和已发消息首包路径保持不变。上一阶段“消息数上限1下FIFO与轮转完全同序”的结论仍成立，两者采用了不同的资源条件。

第三，队列积分、峰值和服务耗时不能互相替代。count3的积分甚至高于透传；字节FIFO积分较低，峰值却从8912B升到9624B。这说明改变注入会改变后续流量相位，限制更紧并不保证每个出口峰值下降；具体峰值的重叠消息归因尚待单独核查，不能仅凭相关数值认定原因。

第四，ACK故障仍未被“修复”。目标消息1为0→4的6144B Dispatch；接收数据齐备，源端只确认到6000B、发送序号6144B。最终ACK丢失后资源未回收，仿真5ms预算内业务未完成；停止时交换机队列为0。这是端点协议与软件额度的等待传播，不是队列仍在积压的证据。

第五，新增独立的网络压力校验，7个源各向一个目标发送128KiB，确认当前后端能够触发ECN/DCQCN。得到790次端点CE接收事件，7条完成流均见反馈，最后完整ACK为84281ns；PFC暂停通知为0。它是传输功能压力输入，不是实际MoE热点或训练样本。

这个校验还澄清了一个监测陷阱：独立CNP包数为0，但ACK/NACK头携带CNP标志，原生`ReceiveAck`据此调用DCQCN处理。不能仅凭没有独立CNP包就说没有拥塞反馈。源端完成时速率也已低于100G；这些是模型执行事实，不是对真实网卡参数的校准。

完整记录共32208条包事件，`result.json`为5381140B；summary为41831B，两者执行逐字段一致，队列积分均为28096606272B·ns、峰值245640B。省下的是详细输出，不能据此声称网络事件复杂度或千卡运行瓶颈已经解决。

## 5. 后续修改的顺序、方法与验收

| 优先级与维度 | 针对的问题 | 具体方法与位置 | 完成标准或停止条件 | 状态 |
|---|---|---|---|---|
| P0：完成与资源边界 | 数据到达、ACK和回收混用会提前推进 | 保持`rdma/fabric.cc`事件边界；逐消息重建所有者与阶段 | 失败不报成功，重复回调/提前释放被拒绝，默认执行兼容 | 本轮已实现并回归 |
| P0：注入与消息大小 | 消息数无法表达大小差异 | `communication_admission.hh`双约束、严格FIFO与可容纳目的端轮转 | 数/字节均守恒，跨plane共享，同机排除；超额拒绝 | 本轮已实现；当前无透传以上收益 |
| P0：可扩展观测 | 保存每包历史制约规模，旧钩子口径易误读 | `queue_integral.hh`常量状态；summary与受选包记录分离 | 全包/截断/无明细汇总一致，独立驻留积分核对 | 本轮已实现，不等于千卡验收 |
| P1：可靠恢复与失败语义 | 锁定库缺少通用ACK超时恢复，尾包/最终ACK丢失可能停住 | 从源端合法ACK进展驱动RTO（重传超时）、退避与重试上限；还须检查接收端重复数据的累计ACK行为；修改原生`rdma-hw`前明确协议依据及依赖维护路径 | 尾包/ACK/NACK丢失、重复包、迟到反馈、只回收一次；超出重试有明确失败，不能依赖接收真值补ACK | 尚未实现，不能把诊断当恢复 |
| P1：代表性负载 | 小Decode输入没有重拥塞，incast只是传输压力 | 用已校验来源的逐Token/逐层专家选择回放，保留时间相关、热点持续与专家放置；batch/EP/副本规模分别控制 | 明确推理/训练、输入范围和缺失；至少能解释负载到链路矩阵的映射，不为策略制造热点 | 现有回放能力可复用，代表性与新对照待验证 |
| P1：通信库粒度 | 当前GPU对聚合不能代表真实分块/通道 | 在`scaleout_service.py`构图前明确DeepEP/NCCL语义；先实现受依据约束的逻辑分块、依赖与缓冲，再映射native QP | payload守恒、chunk消费者正确、ACK与缓冲寿命不混用；与未分块及真实库对照 | 待通信库/测量依据，不靠拆分制造调度收益 |
| P1：千卡内存与执行成本 | 原生交换机有固定1025×1025×8的uint32数组，仅此项每交换机约32.1MiB | 先按实际端口稀疏或动态存储，检查`switch-node.h/.cc`及MMU引用；另分析逐目的路由构建、图节点数和事件量 | 小拓扑逐事件/输出等价，再32/64/128逐级测RSS/事件数/耗时；预算失败即停 | 未改依赖、未跑千卡，本轮只解决观测历史增长 |
| P2：拓扑与选路对照 | 不同rail和层间带宽的影响可能被端点瓶颈盖住 | 在`scaleout_topology.py`分别生成Clos/Agg及multi-rail；固定NIC总带宽、交换机端口预算和业务量，明确rail到GPU、ECMP种子及上行收敛比 | 数据/ACK双向可达，实际路径和每层利用率可核验；先做小拓扑，避免同时增加链路总资源 | 已有生成器，本轮未扩展选路策略 |
| P2：GPU/NIC与重叠 | GPU标签、每消息新QP和统一成本限制解释能力 | 计算profile、GPU内存与NIC/QP/DMA分别建模和校准；有真实库依据才做QP复用、跨轮或缓冲重叠 | 资源生灭明确，不重复算计算/通信，完成前不得提前复用 | 尚无新硬件校准，暂不自动扩展 |

恢复模型实施时必须显式区分锁定原生模式与新增模式，默认保留原语义。只看发送端当前未确认字节和进展来触发，不能依据“接收端已经收到全部”直接伪造成功。接收端重复包当前返回路径也要一起审查；只调用一次`RecoverQueue`未必能让最终ACK丢失恢复。若缺少真实协议依据，保留当前失败作为模型限制，先补来源与最小协议设计。

千卡目标采用“拓扑可生成→资源可负担→端到端执行可完成→包级证据可采→结果可校准”的分步验收。端口汇总可常开，详细包事件只选端口/时段；减少记录不改变整个网络共享同一仿真时钟及拥塞状态。不能把多个小网络独立运行后相加冒充千卡共享网络。
