# Scale-Out恢复稳健性与清理交付

本阶段交付了三项实际结果：继续清理已确认无用的环境和派生文件；完成持久事务“准备后统一发布”的本地实现、回归及提交；完成54个真实包级网络条件，确认上一轮20μs超时收益的适用范围。论文主贡献仍在筛选，当前结果没有硬件校准含义。

## 最终目标、服务对象和约束

联合仿真器服务于AIDC中的MoE推理网络设计：把请求、batch、专家路由及并行部署产生的通信，放进可以配置拓扑、端口、带宽、路径和协议的共享网络，观察网络如何影响实际任务完成。重点维度是热点造成的竞争、尾部通信、反馈等待、资源释放与恢复安全。目标是形成可复现的机制解释和优化证据，并沉淀可复用平台。

本轮的限定很明确：8GPU、两个交错EP4组、每rank batch4、H1024/FFN4096/E16/Top2、一层两步ready-KV Decode、100G三层Clos。每条件92条消息、389120B必要payload；源端FIFO总额为3条消息/8192B，完整ACK并清理QP后才释放额度。计算耗时为声明值，路由合成，A100只是描述标签。没有执行GPU、训练、现代DeepEP、生产故障率估计或千卡完整推理。

前端沿现有公开服务入口选批并生成Chakra任务图；ASTRA按依赖发起SEND/等待RECV，原生RDMA ns-3逐包传输。实际接收齐备和完整ACK分别推进消费者与发送资源，最终反馈前端继续下一步。每个条件的全部组和步骤共用同一网络状态。结果没有通过相加独立流耗时得到。

## 清理了什么，保留了什么

各阶段合计净减少约4.92GiB可见文件占用：扩展安装包缓存、已过期或未使用的编辑器版本、旧Triton/npm缓存、未使用的Frontier环境、旧构建目录，以及已从原始trace逐字节核对的normalized派生文件。旧Frontier环境保留包版本清单。313份旧网络日志和队列CSV先归档核验；8份原始GPU测量trace改为无损gzip，逐文件解压后SHA256与原件一致。另将1,046份旧包级日志归档，逐成员核验后移除散文件，净减少530,853,705B，日志内容可完整恢复。

源码、固定依赖、模型权重、真实路由数据、唯一测量内容、当前前端Python和实际服务/原生库保留。原始profile恢复方式是先对对应`.trace.json.gz`执行`gzip -dk`，再运行原目录`normalize_traces.py`；没有把原始测量当废物删除。详细操作与hash在本机`runs/disk_cleanup_20261023/`。

根目录所在Btrfs共享底层存储，期间df可用量多次从数GiB降到0又上升；可见目录大小与底层使用量也不相等。因此4.92GiB指文件净减少，不能写成分区可用空间净增加。后续大件继续放内存盘，源码与必要小报告入仓库。

## 平台改动已经完成

本地提交`aec2bb4`增加v5可选显式前缀发布模式：`aggregate_requests=true`只准备描述符，`false`发布同连接的已准备前缀。真实prepared回调可驱动前端追加工作；发布时读取受保护的实际源字节，请求ACK及原子返回完成后才回收资源。put和原子仍各自执行，没有合并成一个请求。未启用时默认结果保持。

同连接延迟发布前没有数据包；另一连接可以独立发送。深度不足、全部聚合尾或等待未发布前缀会保存真实未完成状态，不自动补发布。32条验收命令、17项输入单元、事务/在线会话/稀疏窗口回归以及13项固定依赖检查通过。新源码根、空cwd和包内8个原生库实际执行3条公开命令、2次网络，除库路径外完整结果相等。首次归档checker错误地把系统库也计入8个ns-3库，失败保留；修正后核验已有成功结果，没有重复网络。

使用和证据见[前缀发布小例](../../examples/scaleout_rdma_transactions/README.md#准备工作后统一发布)、[验收](../../fixtures/submission_prefix/README.md)与[恢复](../../fixtures/submission_prefix/recovery.json)。这是MRT1功能规则，不提供物理MMIO门铃次数或真实GIN时延；GPU可见性与完整现代事件接入仍未完成。模型中的聚合尾阻塞不能当作生产库漏洞。

## 网络实验的主要发现

先登记45条件：每跳传播500/2000/4000ns，固定20/40/80μs、Karn40及Karn40加每源历史，分别无故障、丢一次目标尾数据、丢一次最终ACK。看到冷启动问题后，另登记9个Karn80强基线条件，只把已有Karn初值由40改80μs；原45条件没有覆盖或重跑。详细输入与边界见[方法](../../experiments/recovery_delay/protocol.md)。

下表为无故障条件。重复payload相对每条件389120B必要数据计算；业务完成与网络排空是不同指标。

| 每跳传播 | 方法 | 首次实际反馈往返 | 重复payload | 超时次数 | 业务完成 / 网络排空 |
|---|---|---|---:|---:|---|
| 0.5μs | 固定20μs | 6.522μs | 0 | 0 | 70.492 / 70.492μs |
| 2μs | 固定20μs | 24.522μs | 237568B（61.05%） | 60 | 226.154 / 246.154μs |
| 4μs | 固定20μs | 48.522μs | 389120B（100%） | 92 | 434.068 / 454.068μs |
| 4μs | 固定40μs或Karn40 | 48.522μs | 237568B（61.05%） | 60 | 434.154 / 474.154μs |
| 4μs | Karn40加历史 | 48.522μs | 59392B（15.26%） | 16 | 434.068 / 434.068μs |
| 4μs | 固定80μs或Karn80 | 48.522μs | 0 | 0 | 434.068 / 434.068μs |

**发现一：短超时收益依赖反馈时延。** 每跳0.5μs时，20μs相对40μs在尾数据/最终ACK故障下，业务分别早19.963μs/20.340μs，收益约20.93%/21.80%，只多重传144B。每跳2μs时首次反馈晚于20μs，无故障也误重传。因此上一轮20μs的结果是条件性改进，不能直接改成全平台默认。

**发现二：只看推理完成时间会漏掉网络浪费。** 每跳4μs、固定20μs无故障时，必要数据额外发了一整份，业务完成仍与保守80μs相等，网络晚20μs排空。固定40μs也会产生大量误重传，排空晚40.086μs。源payload、线上多跳字节、反馈、业务完成和物理排空必须一起报告。

**发现三：Karn40的长路径问题来自过短启动和采样机会。** 目标第一次发包4.203μs，40μs计时器在44.203μs到期，正常首反馈52.725μs才到；重传使该样本歧义，本QP剩余期间没有新的原始包可采。不能期待短消息在第一次误判后自动学会正确RTT。历史把之后QP的重复量减少75%，但目标首次冷启动仍有误重传；68次历史命中并不自动等于业务收益，0.5/2μs六组共有执行字段完全相等。

**发现四：强基线能解决一部分问题。** Karn80在三个传播条件的无故障情况下均无重复量；短路径尾丢失时，收到首反馈后RTO降到20μs，业务完成与固定20μs相同。仅把Karn40初值设置得更合理，就消除了本轮长路径健康流误判。这部分不应包装成新恢复算法的需求。

**发现五：保守估计仍可能延长真实丢包等待。** 每跳2μs，Karn的首个24.522μs样本使初始RTTVAR为12.261μs，RTO为73.566μs；尾数据/最终ACK的业务比固定40μs分别晚19.606μs/14.212μs，Karn80也一样。每跳4μs，Karn80尾数据/ACK条件业务完成473.674/464.280μs，而固定80μs均为434.068μs。已有估计器、初值、消息长度和应用重叠共同决定结果，不能选一个有利场景宣布自适应全面更优。

这些差值都来自相同网络条件下的实际执行；无故障参考只是条件对照，不是所有优化的理论下界。54个条件中必要工作、216份任务图、同传播条件下的消息身份和首尝试路径均核对相等。独立重放1296个捕获源消息、累计ACK计时、Karn和有限历史，提前超时/夸大字节/虚构历史命中三类篡改均被拒绝。包捕获仅GPU0/4，不能声称全网每包都独立验证。

## 创新判断与接续工作

本轮收缩了两个候选：统一缩短RTO不是通用解法；把已有Karn或历史缓存组合起来也没有形成独立创新。保留经典强基线的价值，是避免把配置不足误判成新研究问题。当前更值得追踪的对象仍是MoE的通信尾部如何阻塞必要计算、发送资源和安全恢复，以及能否在真实负载上改善业务与网络双指标。

下一步平台重点是持久连接真正丢包后的重放与完成安全。目前stream/事务入口仍拒绝旧式fault/recovery配置：持续增长的字节区间不能直接套用固定消息长度计时器。实现时需要源端真实已发高水位、累计ACK、空闲后追加、重传排空和逐工作信用回收；接收重复字节不能重复执行原子或远端副作用。之后才能用真实MoE路由、并发与不同路径检验方法。GPU可见性、匹配硬件校准、现代完整应用和千卡执行仍需独立证据。

54份宿主监控均完成且无剩余进程，监控时间合计72.354秒，峰值采样RSS约439.2MiB。驱动累计95.149秒，补充轮记录已包含原45条件，不能重复相加。最终研究树约148.17MiB，小于256MiB；离线复算另3.512秒。中间准备和分析命令未全部持久记录耗时，因此这些数值不是完整阶段耗时实测。

898成员、30,761,368B的离线检查点压缩为2,991,399B，新源码根及空cwd复算三份产物逐字节相等；随后核验持久副本SHA256为`80a1f8eb5a084d4cedc08e78ff811ba1bdadf8c9d88f63814b9d3a5c6fe24d0d`。本地持久副本见[备份收据](../review_artifacts/recovery_delay_20261023/persistent_backup.json)，含离线分析所需输入和源码，不含部署环境，也不是独立远程备份。reproduction.json中的易失存储说明记录的是复制前状态。
