# MoE_expert_selection_trace：结构、热点分析与 Scale-Out 使用方法

本次核对了公开目录元数据、配套论文 v5、仓库历史来源清单和路由读取代码；随后已读取用户提供的4份R1/MMLU原件，并完成热点统计及小规模网络接入。实际文件与结果见[四请求核验报告](../../experiments/moe_trace_hotspots/results/four_requests_20261018/report.md)。结论是：这套数据适合研究推理请求的专家偏好、持续性和共选关系，再结合明确的专家放置与网络模型研究跨机通信；它本身不是网络包trace，也不是训练路由数据。

最初公开资料调研时，原始HF连接超时，镜像README接口返回401，当时尚未读取原件；该阶段的[研究证据](../../experiments/moe_trace_hotspots/sources.json)保留原状。随后用户自行下载并提供4份JSON，代理没有接受新条款或下载更多原始路由；通过固定版本的公开目录Git blob OID与大小核对了这4份原件，并在本机生成其SHA-256。

## 1. 数据来源与目录

- 数据集：[core12345/MoE_expert_selection_trace](https://huggingface.co/datasets/core12345/MoE_expert_selection_trace)。
- 本次公开元数据的修订：`27febb7b2d24169560a9f6f83d38eb53f94916cf`，与仓库历史来源清单一致。
- 配套论文：[Patterns behind Chaos: Forecasting Data Movement for Efficient Large-Scale MoE LLM Inference，arXiv:2510.05497v5](https://arxiv.org/html/2510.05497v5)。
- 元数据标记为 `gated=auto`：公开目录可读取，不表示当前环境已取得原始文件访问权。

公开目录确认存在四个模型目录：

| 目录 | 注意事项 |
|---|---|
| `cognitivecomputations/DeepSeek-R1-AWQ` | 仓库历史导入和校验过的来源是这一目录的MMLU子集 |
| `Qwen/Qwen3-235B-A22B-FP8` | 是235B模型，不是当前Scale-Out基准的Qwen3-30B-A3B |
| `meta-llama/Llama-4-Maverick-17B-128E-Instruct` | 论文报告其MoE层Top-1，不能照搬Top-8共选分析 |
| `moonshotai/Kimi-K2-Thinking` | 应使用该来源的真实模型结构，不能按R1结构解析 |

可见任务路径包括 `mmlu/<学科>`、`mmlu_ZH_CN/<学科>`、`Chinese-SimpleQA/<类别>`、`livecodebench/execution`、`HuggingFaceH4/aime_2024`，Llama目录还包含 `hellaswag/test`。不同模型的任务集合并不完全相同。

例如：

```text
cognitivecomputations/DeepSeek-R1-AWQ/
  mmlu/
    abstract_algebra/
      0.json
      ...
Qwen/Qwen3-235B-A22B-FP8/
  Chinese-SimpleQA/
    中华文化/
      0.json
```

基本组织方式是“模型—任务—学科/类别—单请求JSON”；任务路径深度并不固定，解析时应保留完整原始路径。公开列表还出现部分 `tar.gz`，不能将压缩包和解压后的JSON重复计数。

本次元数据接口恰好返回100000个siblings，其中可见99994个JSON；没有证明这是完整枚举。因此[元数据摘要](../../experiments/moe_trace_hotspots/metadata-summary.json)中的模型/任务计数均标为可见记录数，不作为全数据集总量或任务占比。历史已审计的R1/MMLU目录有13922份JSON，这只是一个子集的历史目录结果。

## 2. 单文件记录结构

以下具体结构由仓库历史R1校验记录支持，并已用本轮4份用户原件重新完整检查；其余三个模型的每种原始格式仍未逐一验证。

```text
一个JSON文件 = 一个请求的观察记录
  外层数组 = 按执行顺序排列的入口
    入口0 = Prefill
    入口1、2、3…… = 后续Decode步骤
      层号字符串 = 该层的专家选择
        MoE层：二维数组 [token行][Top-K专家编号]
        Dense层：null
```

R1来源声明为61层：0～2为Dense，3～60为58个MoE层；每层256个路由专家，每token选8个。专家身份是 `(模型, 层号, 专家ID)`；不同层的expert 7不是同一个专家。

下面仅是简化结构示意，不是真实观测样本，也省略了其他必需的层：

```json
[
  {"0": null, "3": [[7,12,35,49,80,101,160,211],
                      [7,19,35,62,83,110,171,230]]},
  {"0": null, "3": [[7,12,35,62,80,110,160,230]]}
]
```

首入口在每个MoE层有prompt长度那么多行；Decode每入口每层一行。`null`只表示没有路由专家选择，不表示该Dense层没有计算。Top-K记录也不覆盖始终激活的shared expert。

原始记录没有给出仿真所需的所有内容：

| 可以从路由记录取得或派生 | 需要另外提供或核实 |
|---|---|
| 层号、步骤顺序、每token选择的专家ID | 每条记录的真实纳秒时间、真实batch和请求到达过程 |
| 每层各专家的被选次数、共选和相邻token关系 | token源GPU、专家所在GPU及NIC/服务器/Pod归属 |
| 由首入口推导的prompt长度、可观察Decode入口数 | 实际激活精度、通信实现、分块和协议开销 |
| Prefill与Decode选择的差异 | router分数、accepted/drop/pad、权重迁移与计算耗时 |

文件末尾不等于模型产生EOS，文件长度不必等于完整输出长度。入口1的绝对输入token位置按既有读取器为 `prompt_tokens`，入口i为 `prompt_tokens+i-1`；不要把Prefill当作第一轮Decode。

来源目录的AWQ/FP8名称说明权重/模型版本，不能据此把激活通信也设成4 bit或FP8。采集权重和运行软件的精确修订、硬件与激活dtype等未知项，在现有manifest中明确保留为未知。

## 3. 热点应该怎样统计

### 3.1 先看一层内的访问偏斜

对固定模型、层、任务和阶段，设token数为N、每token选K个专家、专家数为E，专家e被选次数为c[e]。

- token选中概率：`c[e]/N`，所有专家相加为K。
- 全部选择中的份额：`c[e]/(N*K)`，所有专家相加为1。
- 相对均匀负载：`c[e]/(N*K/E)`；最大值即峰/均比。
- 补充Top-m专家合计份额、零访问专家数、变异系数。

例如“被10%的token选中”和“占全部专家选择的10%”不是同一个量。计算均值必须包含未被选中的专家。

Prefill和Decode分开计算，否则长prompt会压过Decode统计；同时保留逐请求结果与token加权汇总，避免把长输出请求的偏好当成所有请求的共同偏好。按任务、学科、语言和长度分层，不直接混合四个模型。

### 3.2 再看热点是否持续

在单请求内按连续8/16/32个Decode token划分窗口，观察Top-m集合、峰/均比及相邻窗口热点集合Jaccard。跨请求不能把文件名或目录顺序当真实到达时间，也不能把token窗口称为微秒窗口。

对照可采用：原始顺序、保持每层直方图的顺序打乱，以及相同E/K/token量的均匀随机。联合打乱请求内各层的入口顺序可保留同入口的跨层组合，破坏相邻token关系。随机种子、打乱范围和保留条件需要记录；不要把改变专家放置称为“打乱后消除了热点”。

### 3.3 检查热点能否预测

用Prefill或前若干Decode token预测之后的窗口，检查热点集合覆盖率、排名相关性以及跨任务泛化。预测器不能读取未来Decode；用完整Decode统计选择放置只能作为明确标记的oracle上界。

### 3.4 检查专家是否经常一起被选中

统计同层、同token内的专家对共选次数。热门专家对的高计数可能仅由单个专家本来就热门造成，不能直接当作额外相关性；进一步分析需控制边际频率的随机基线。Top-1模型没有同token专家对，不应硬套Top-8结论。

## 4. 从热点专家到Scale-Out网络

专家热门不必然意味着网络拥塞。它可能位于请求本卡；也可能被分散放到不同NIC。研究需要保留如下转换：

```text
真实token→expert选择
  → 声明token源GPU和expert→GPU放置
  → 每层、每轮的GPU对通信矩阵
  → 同机/跨机/跨Pod归属及rail/plane
  → 按依赖释放通信，在ns-3中执行
  → 端口排队、ECN/PFC、数据就绪
  → 本层及本轮Decode完成时间
```

设 `A[s,d]` 为源GPU s上的token选择GPU d所持专家的总贡献数。在当前Scale-Out“每专家贡献一份向量”模板中：

```text
Dispatch[s,d] = A[s,d] × hidden_size × activation_bytes
```

同卡项不发网络；同服务器不同卡走机内模型；跨机项走RDMA。相同GPU对的贡献合成一个逻辑消息，Combine按当前假设反向返回同样的向量字节。R1若声明BF16参考激活，单贡献为7168×2=14336 B；这不是采集dtype的证据。

如果通信库按目的GPU/服务器去重，多个被选专家共享一份token向量，字节应按去重后的目的地计数；不能继续套逐专家复制公式。两种模板必须分别核算机内转发、归并、metadata和probs等成本，不能用“聚合”一词把字节相加与真正去重混为一谈。

数据没有原始源GPU和真实到达时间时，可以显式声明放置和到达/组批模型进行回放。但结论是“真实专家选择＋声明部署/时序下的网络结果”，不能称为原集群实测网络复现。

### 如何改变batch

组合B个独立请求，在每轮取每个请求对应的一个Decode入口，再构建该轮的路由矩阵。不能把一个文件的B个连续Decode步骤合并冒充B个并发请求。需要说明B是每卡还是每EP组，并处理不同请求长度和观察结束；当前两轮固定基准也不能直接代表长时间服务。

### 接入当前仓库的具体位置

已有 `route_evidence.py`、`route_records.py` 提供来源校验、逐请求逐层选择，历史UB路线已经使用。非UB默认的 `scaleout_service.py::routes` 仍产生合成路由；本轮新增可选 `route_replay`，由 `scaleout_replay.py` 校验逐请求原件并替换选择，公开操作见[来源回放示例](../../examples/scaleout_route_replay/README.md)。不能修改一个seed就当作接入本数据集。

接入口为每个rank/slot明确分配不同原文件和起始Decode入口，保留原专家ID、层号、E/K，把文件摘要、入口和token行保存到wave证据。调度完成才推进来源索引；运行目录保存原件快照并由独立检查器核对。支持逐层静态等容量重排，不支持免费复制或无成本迁移。有限片段最多4个连续MoE层；完整GQA结构必须覆盖来源全层，当前不支持完整R1的Dense/MLA。

不应把R1的256个专家编号取模128后用于Qwen3-30B，也不能因为同为Top-8就混用模型。即使改用Qwen3-235B目录，也必须匹配其94层和真实模型维度，不能把它当48层30B的实测路由。

## 5. 作者已经做了什么，我们还能研究什么

论文v5第III节已经研究：相邻层/相邻token相关性、Prefill与Decode相似性、任务/语言相关的专家偏斜，以及专家共选。这些是论文观察，不是本次新跑出的数据结论。

第VI节进一步提出Prefill驱动的专家重排和复制，在8×H100/NVLink上使用SGLang、DeepEP。其第VI-B节明确评价指标为专家的三个线性层计算耗时，**排除Attention、All-to-All和Top-K耗时**。因此，直接提出“统计热点”“用Prefill预测热点”或“把热门专家分散”不足以作为新贡献；相关方案应作为基线。

我们的网络研究可以进一步回答：

1. 作者的计算负载均衡放置，到了跨Pod网络后，是否增加远端字节、汇聚流量或慢轮次？
2. 相同专家频率下，热点持续性、请求源位置和多副本同步程度是否改变NIC/ToR/Agg上的排队？
3. 在相同显存和NIC预算下，网络感知放置与分层Dispatch/Combine，能否改善端到端Decode尾部而非只改善专家计算？
4. 在单rail、多rail和双plane中，上述策略的排序是否改变？独立rail需要显式中继，不能把端点当交换机补通。

建议最小对照：固定真实请求、原始E/K与任务；比较连续专家放置、计算负载均衡放置、网络感知放置，并配合均匀随机与保频率的时序打乱。报告每层Dispatch/Combine、跨机字节、NIC负载、选定出口队列、ECN/PFC和Decode步长；原论文的计算耗时另列。不得通过多加上联、无成本复制/迁移或提前读取未来路由制造收益。

## 6. 本次交付和实际边界

新增[离线分析工具](../../experiments/moe_trace_hotspots/README.md)，支持：逐层分阶段频率、峰/均比、Top-m份额、共选计数、单请求窗口热点，以及Prefill/Decode热点集合重合。复用原始解析器，校验文件SHA-256与完整形状；对文件数、字节、共选计算和输出均有限额。

4项手工计数与错误输入检查通过，并完成一次公开CLI人工输入流程。它们验证统计定义和来源检查，不是原始数据实证。离线工具本身不预测网络时间、不生成真实源rank，也不自动下载数据。另新增的服务接入口需要显式声明源rank和部署，已用4卡人工样例验证来源回放、两轮反馈及等容量重排；随后用用户提供的4份真实R1路由完成两层、两轮原生网络接入核验，未进行真实数据上的优化对照。

历史1024请求子集是“所有入口合格且至少64个Decode入口”的筛选结果，存在长度和任务选择偏差，不能直接当总体热点分布。历史1024请求清单所需原件本机仍不齐全。本轮独立使用用户提供的4份原件，合计约7.81 MiB、512个Decode token；例如原始层24的专家72被179个Decode token选中（34.96%），只代表这份小样本。4卡、源层3—4、两轮网络接入通过，但没有真实数据优化收益或总体热点结论；扩大研究需保留分层抽样、拒绝原因和文件摘要。
