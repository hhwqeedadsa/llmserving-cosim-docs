## 1. 这个系统实际服务什么问题

它最合适的定位是：**研究 MoE Decode 中，Token/专家分布和批次怎样形成通信，实际网络排队怎样推迟消费者及下一轮服务**。主线是通信因果关系和网络诊断，不是生成文本，也不是通用 GPU 周期级模拟器。

它已经超出“从某个 Block 导出一张流量表”的阶段。Python 用 LLMServingSim 的调度、请求、批次和 KV 对象决定本轮工作；生成器将逐请求、逐层路由转成计划和 Chakra 依赖图；C++ 的 ASTRA 执行图；唯一 ns-3-UB 网络执行实际包与完成事件。通信回调释放后续计算，整轮完成后再回到 Python 组批。

```mermaid
flowchart LR
  I[请求 / 路由 / 模型 / 成本 / 放置] --> S[LLMServingSim 调度适配]
  S --> P[计划与 Chakra 图]
  P --> A[ASTRA 依赖执行]
  A --> U[UB 事务 / 唯一 ns-3 网络]
  U -->|真实完成回调| A
  A -->|WAVE_DONE| S
  U --> O[被动端口与队列记录]
  A --> O
  O --> V[observed 算法输入]
  O --> T[truth 评价真值]
```

Python 构图的宿主耗时不计入仿真时间。计算来自声明成本或匹配形状的 profile；没有执行 GPU 数值前向。rank 是逻辑成员，CM384 参考中对应一个 die，不应直接把 rank 数称作 GPU 数。

一次组决策通过 `DECIDE → COMMIT → WAVE_DONE` 完成；组内成员联合提交，空源端仍可能承担远端专家。没有额外全 rank 逐层屏障。不同组独立推进，共享持续存在的同一个网络，不能通过合并多次独立运行来替代。

WRITE/STORE 的目标数据就绪与源端事务完成分开，前者允许消费者继续，后者释放发送资源；LOAD 由消费者发起，先有真实 32 B 元数据供数通知。这个区别是分析长尾和反馈的基础。

前端注入后端的内容是每个 rank 的 **Chakra `.et` 依赖图与配套 JSON 执行计划**：图内包含 COMP/SEND/RECV、前驱、参考计算 ns 和通信标签；计划补足请求/Token/层/专家来源、传输字节、业务与元数据范围、发起方/供数方/消费者及物理映射。`generate.py` 负责导出，C++ 重新核对，`ub_network_adapter.cc` 将图节点提交给 UB。不是把预先写死开始/结束时刻的 packet trace 注入网络，也不走旧的 `UbTrafficGen` CSV 阶段回放。包的真实释放取决于这次图的前驱和资源，包路径和排队由这次网络决定。

## 3. 做得好的地方

1. **网络完成能回到服务。** 后续计算和下一轮选批依赖本次实际回调，没有将 analytical 耗时再加一遍，也没有给网络写死完成时刻。
2. **对通信语义处理细。** 业务向量、附随元数据、计数、标志及 LOAD 就绪通知分别核算；接收数据可用与源端回收分开，减少“全算成网络慢”的错误归因。
3. **同芯片、跨芯片与资源约束显式表达。** `deployment` 决定本地交付，A3 参考模板引入分核、局部缓冲和复用条件，比整 rank 统一发送槽更接近源码需要表达的问题。
4. **证据边界清楚。** 算法读 observed，理想对应关系留在 truth；被动来源不参与选路或改变包。有限观测能力与硬件可采集能力也分开说明。
5. **重现设计较完整。** 固定依赖、规范输入、生效属性快照、公开 CLI、有界存储、完整首轮保存与后端重放，适合继续协作。
6. **已有研究能够接受负面结果。** Scale-Up 筛选保留竞争解释、较强基线和 no-go 判断；没有把每项诊断记录都包装成新方法收益。见[既有结论](../../experiments/scaleup_issue_screening/conclusions.md)。

这些优点依据主仓源码及版本化证据的审阅。大型历史验收不等于本轮独立重跑，CANN 行为参考也不等于真实设备校准。

## 5. Scale-Out 的实质缺口及优先级

### P1：不能把“跨服务器 UB”写成“已支持 RoCE”

`backend/backend_config.cc` 固定 RTP 路径的 CBFC、HASH 最短路，禁用重传及 UB CC；原生 STORE/LOAD 另有请求/响应与喷洒。这些是 UB 模型，不能分别等同于 Ethernet PFC、ECN 标记或 DCQCN。修改链路速率只回答当前 UB 抽象中的容量/排队问题。

若论文评价 RoCE 网络，需在同一事件时钟和完成接口下实现/接入对应传输，定义 QP/NIC 共享、确认、重传、ECN/PFC 和拥塞控制，再对实机校准。不能把另一套独立 ns-3 库直接链接进当前程序。

### P1：服务器共有出口和机架层次表达不够方便

`fabric.py` 已有多服务器、多个平面及 L1/L2 路由，因此“完全没有 Scale-Out”不准确。但原生成器给每设备每平面直连接入，默认全网同一种速率/延迟；服务器 L1 直接上公共 L2，没有单独机架层。可手写 link overrides，仍缺少面向服务器/机架的配置与审计。

需要区分卡接入总带宽、服务器实际外发能力、同机架路径、跨机架上联和多个组是否共用这些资源。多个流必须进入同一个物理端口的队列，不能只给每条独立流增加固定“跨机延迟”。**本轮改进针对这一层。**

### P1：硬件类别与 profile 适用范围不能只改名字

主完整模型入口用声明成本，不因把名称改成 A100/H100 就自动获得对应计算耗时。已有 A100 表只覆盖 FP16 小形状 FFN/GQA，不覆盖 R1 MLA 或 Ascend CANN。不同 GPU/NIC 组合会改变发包节奏、并行和端侧资源，需有匹配设备/软件/形状的数据。

网络研究可先固定有依据的计算释放节奏，比较网络拓扑/队列；做绝对性能预测时必须再校准，不能用峰值 TFLOPS 换算替代。

### P2：跨节点 MoE 的通信库层次尚未建立

现有 A3 模板有明确源码分支与 TP1 范围，不代表跨节点 DeepEP/NCCL 的转发、聚合、分层 dispatch/combine 或 GPU—NIC 亲和关系。相同 Token/专家矩阵，跨节点库可能产生不同线上字节与消息次序。需另建源码依据和字节/依赖测试，而不是沿用 A3 规则后改网络名称。

### P2：接收服务与 NIC/内存资源尚不能做完整归因

现有队列/信用/回调证据很好，但没有接收方消费服务引起的有限缓冲反压，也没有完整 PCIe、DMA、HBM、NIC 引擎模型。若研究“目标算得慢导致上游堵”，必须先实现有限容量与释放条件，单独延后消费者 COMP 不会自动形成真实的网络反压。

### P2：可分发复现仍受私有依赖制约

主仓库能 clone 不代表依赖能访问。首次初始化本轮出现直接私有子模块无权限；锁文件的 `verification` 还保留最初 `not_run` 元数据，应理解为历史记录，实际验收应看具体 fixture/本次日志。后续产品应提供完整的依赖访问说明、工具链清单与轻量冒烟检查，而不是混用你旧机器的二进制。

## 7. 本轮具体修改与支持范围

新增 `moe-ub scaleout prepare`，代码为[scaleout.py](../../python/moe_ub_cosim/scaleout.py)，用户输入见[小例](../../examples/scaleout/README.md)。它生成 DEVICE—服务器汇聚交换节点—机架交换机—单骨干树形网络：

1. 单独配置设备接入、服务器共享上联、机架共享上联的速率/延迟。每个节点/端口真实连接，同服务器设备外发必经同一出口。
2. 显式 rank/物理设备映射，复制服务/成本并只改层内的物理映射；同芯片仍走已有本地交付。
3. 输出有向出口表、活跃成员路径表、物理放置和容量切口；区分同芯片、同服务器、同机架、跨机架。
4. 为现有 `scenario-run/1` 写足 link overrides。不能只改 CSV 速率，因为现有 `resolve_topology` 使用 defaults 与覆盖项生成生效网络。
5. 预先限制节点/端口/路由/连接数量，拒绝重复映射和旧目录覆盖；用公开 `resolve/run` 延续实际执行，不新增独立时间轴或伪造完成时间。

这是分层拓扑和输入审计能力，**不是新 RDMA 协议实现**。首版单平面、单骨干，无 ECMP 备选路径。树结构用于清楚区分共享瓶颈；不是声称替代已有多平面 fabric，更不是任意规模数据中心生成器。

## 8. 分步目标、验证与最终研究目标

| 步骤 | 目标 | 完成标准 |
|---|---|---|
| 本轮结构审阅 | 找到真正可以复用的因果执行路径 | 本页源码关系、优势、旧工作对照与能力边界 |
| 本轮分层网络输入 | 能改放置/各层速率，并知道流经过哪一个共享出口 | 独立 BFS 核对路由与跳数；解析后速率不丢；重复生成一致；实际后端验收另列状态 |
| 随后小型联合实验 | 证明服务器/机架出口影响真实事务与消费者推进 | 单次共享网络、事务恰好发起一次、网络排空、有限请求正常结束、参数实际生效 |
| 对照与机制定位 | 区分字节增长、出口容量、并发、路由与目标服务 | 固定工作量比较服务器带宽/机架带宽；放置实验另列本地化改变；业务与包字节分开 |
| 硬件与协议校准 | 将模型内观察联系到实际设备问题 | 匹配设备、拓扑、库版本和消息形状；必要时补 NIC/协议并校准分位数和误差 |
| 论文与工具产出 | 回答一个有普适意义的网络长尾问题，并能让别人验证 | 可证伪机制、优化方法、强基线、反例和实机/仿真对照；可获取依赖、输入与轻量基准 |

近期产出应是可审查工具、网络问题清单与机制小实验；仅做三层拓扑或 batch 调参不足以构成创新论文。若后续取得真实跨服务器长尾及可信校准，可以先形成系统/网络 workshop 的测量或工具论文，再按贡献深度考虑 IMC、CoNEXT、ICDCS 等测量/系统方向；若有新的拥塞/通信机制与充分评估，再评估 SIGCOMM、NSDI、INFOCOM 等方向。这里是贡献与成熟度的对应关系，不是录用承诺或已核实的截止日期。

最终目标是：在给定模型、请求、部署和网络约束下，解释**哪一类共享出口/排队/协议依赖导致了多少服务长尾，什么改变能改善，以及何时无效**。工具应服务这个可验证的问题，而不是以“支持更多参数”本身作为学术结论。

优先核查三项可证伪假设：服务器出口受限时，同机多个源的真实发包应汇入同一个出口并产生等待；只提高服务器上联未必解决机架瓶颈；网络变慢应改变消费者开始时刻，而固定计算节点的持续时间不变。如果这些事实不出现，应检查业务是否实际跨越该出口、在途额度是否先限制发送、负载是否足够，而不是继续调低带宽制造收益。单次正常退出或结构超卖比不能单独证明拥塞。

硬件校准可以从同机/同架/跨架的单流开始，覆盖小消息与大消息，再测试并发发送和多对一汇聚，分别对照有效载荷、线上字节、完成分位数和端口/队列。选用 A100 或其他设备时，明确 GPU、NIC、链路、交换机和软件版本；跨服务器 NCCL/DeepEP 的实测不能直接给 UB STORE/LOAD 模型背书，须先核对操作语义和消息分解。
