# 千卡 MoE Scale-Out：网络规模、并行策略与热点研究

本报告服务于**跨服务器 MoE 通信与网络长尾**研究：输入真实路由和明确的 batch，把专家负载转换为 rank/NIC/交换端口的工作量，再检验通信机制、放置和拥塞控制如何影响迭代或推理完成时间。千卡是目标规模，不是现有验收结论。Scale-Out 路线采用非 UB 的 RDMA/ns-3 后端；当前在线 `moe-ub run` 仍只支持 UB。

本轮完成了参数化容量核算、真实交换机对象内存探针和研究设计，没有完成千卡逐包执行、非 UB 在线接入或真实训练热点统计。原始 JSON 等待用户提供；不继续下载大型数据。此前接口与协议缺陷的源码和探针见[后端研究](scaleout_ns3_backends_20261015.md)，本轮证据入口见[规模实验](../../experiments/scaleout_scaling/README.md)。

## 1. 能否做到千卡：必须区分三个问题

| 问题 | 当前能否回答 | 本轮证据或缺项 |
|---|---|---|
| 能否描述 1024 GPU、多个 EP 组和 Clos 链路容量 | 可以核算 | 新增 `scaleout capacity`，不生成网络执行结果 |
| 在锁定 RDMA 库中，交换机有哪些确定的内存负担 | 可以测量与推导 | 实际编译、分配 0/8 个对象，结合固定数组源码 |
| 千卡完整训练/服务能否在给定主机预算中完成、误差多大 | 尚未验证 | 尚需修复完成语义、接入后端，并测量 QP、包事件、路由、图和日志开销 |

不能用“有 1025 个端口槽位”“拓扑能生成”“估算脚本通过”证明千卡仿真成功。千卡规模不要求 1024 张宿主 GPU；网络仿真消耗的是宿主 CPU、内存和磁盘，仿真的 GPU 则通过容量与计算配置描述，两者要分别记录。

### 1.1 已证实的资源问题

ASTRA 锁定的 ns-3 派生库和阿里库的 `SwitchNode` 都定义：

```cpp
uint32_t m_bytes[1025][1025][8];
```

这是入口端口×出口端口×优先级的计数，不是模型权重。单数组 33,620,000 B，即约 32.06 MiB；构造函数清零会实际触碰页面。阿里 `NVSwitchNode` 也有同样数组。实际阿里构建中 `sizeof(SwitchNode)=33,665,384`、`sizeof(NVSwitchNode)=33,665,320`、`sizeof(SwitchMmu)=188,664` B；后者另行分配，不能把 sizeof 节点当全部内存。

初次有界运行，8 个普通交换机的自测 RSS 从 13,930,496 增至 284,463,104 B，差 270,532,608 B，约 258.0 MiB。统一脚本另有一次复现；具体机器波动保存在[摘要](../../experiments/scaleout_scaling/results.json)。探针没有链路或包，因此这只是固定对象开销。

示例采用 1024 GPU、128 台八卡服务器、32 个 leaf 和 32 个 spine，每 GPU 一张 400G NIC，每 leaf 接 32 张 NIC、32 根 400G 上行，每 spine 连接全部 32 个 leaf。若额外为每台服务器建一个 NVSwitch 节点：

| 对象 | 数量 | 仅上述固定数组 |
|---|---:|---:|
| Ethernet leaf+spine | 64 | 2,151,680,000 B，约 2.00 GiB |
| 建模 NVSwitch | 128 | 4,303,360,000 B，约 4.01 GiB |
| 合计 | 192 | 6,455,040,000 B，约 6.01 GiB |

这是**数组推算，未创建 192 个节点**，且不含 MMU、缓冲中的包、QP、路由、ASTRA 图、日志。当前库 `scratch/common.h` 还维护 `pairRtt/pairBw/pairDelay/nextHop/portNumber` 等映射，其中全主机对初始化会增加接近 N² 的准备时间和内存。先测量这些项，才知道千卡的真正限制。

改进方向是按实际端口数分配计数、必要时采用稀疏结构，按实际通信对惰性创建 QP，压缩可重建的路由/主机对元数据。示例按端口槽位（含槽位零）估算的计数数组约 5.51MiB，**这不是已实现后的 RSS**，不能宣称内存优化已取得此收益。修改需要保留入口/出口、优先级、PFC/MMU 和统计语义，检查未连接端口、最高端口号及对象销毁，不能只把常量改小。

### 1.2 分辨率与规模路线

1. **先校正语义。** 使用明确纳秒时间；一条消息只注入一次，接收方只等待；区分数据可读、发送资源释放和事务排空。上一轮阿里尾包判断导致发送回调重复/缺失的问题尚未修复，修复前不解释业务长尾。
2. **16/64 GPU 短窗口逐包。** 从单流、incast、All-to-All-v、多 EP 组竞争开始，覆盖零流量、边界长度和梯度竞争；校验发送/接收次数、字节及因果顺序，再测包事件、RSS和运行时间。
3. **256 GPU 共享 Clos。** 窗口内保留真实微批、专家放置和时间相关；统计队列、PFC/ECN/CNP、重传、QP 数、采集成本。多个 EP 组必须在同一 fabric 上并行，不能各跑一遍相加。
4. **1024 GPU 有界逐包。** 固定相同观测窗口、预算和来源，在 1024 GPU 上重测；超过预算正常记录失败，不默认提高限额。优先几个代表层/微批，不预先承诺完整训练 epoch。
5. **长时间研究另设经校准的流级模式。** 用逐包模式标定拥塞/完成时间的适用范围，在相同片段报告误差与失效条件；不能把理想带宽除法当作同精度替代，也不能混合两次独立执行的耗时。

MPI/MTP 是后续性能选项，不是千卡正确性的前提或保证。跨分区队列、反馈和时间同步必须保留；不能把相互争用的组拆成互不影响的仿真。扩大 MTU、缩短 trace、取消热点或只取均值都会改变研究对象，应作为新的对照条件。

## 2. Batch、All-to-All、EP 与 DP 怎样配置

EP（Expert Parallelism，专家并行）让一个模型副本的专家分布在多个 rank；DP（Data Parallelism，数据并行）让副本处理不同数据。两者可以同时使用。必须说明 DP 指 dense/attention 的数据并行 rank 数，还是一个完整专家集合的副本数。

在本轮核算限定的 TP=PP=1、每 GPU 一个 attention rank、无专家张量并行条件下：

- GPU 总数 `N`；每 EP 组 `P` 个 rank，完整专家集合有 `N/P` 组副本；每 rank 持有 `E/P` 个专家。
- dense/attention DP rank 数为 `N`，expert DP 副本数为 `N/P`。这里不能再写 `N=dense_DP×EP`。
- SimAI 锁定 `MockNcclGroup.cc` 也显式检查 `TP×DP×PP=ngpus`、`EP×DP_EP=DP`；变量名相同不保证不同平台含义一致。
- E=256 时，直接均分专家不能设 EP=1024。千卡可以是 EP64×16 个完整专家副本组；要扩大到超过 E 的 EP，必须另行引入专家张量切分或复制分工，并修改通信/计算语义。

### 2.1 Batch 的明确口径

| 阶段 | `b=sequences_per_rank`、`S=sequence_length` 的含义 | 每 EP 组每层输入 token |
|---|---|---:|
| Decode | 本步每序列产生 1 个 query token，S=1；已有 KV context 不乘进本步 MoE 字节 | P×b |
| Prefill | 等长序列的本次 query 长度 S；实际系统须按每请求长度求和 | P×b×S |
| 训练 | 每 rank 每 microbatch b 条长 S 序列；另有梯度累积 A | P×b×S |

本限定下训练优化器 step 的全局 batch 为 `N×b×A` 条序列。A 增大会增加 step 总工作量，不意味着 A 个 microbatch 同时发包。上下文并行、流水交错、序列打包、混合 P/D 需要单独定义，首版核算不支持。

同一个 batch 数字在不同工具中可能表示请求数、token 数、每 rank 序列数或全局 batch，应转换后再比较。固定 local batch 扩到千卡增加全局负载，属于弱扩展；固定 global batch 会减少每 rank token，属于强扩展。EP 扫描时还要选择固定总 GPU、固定全局 token、固定模型及精度，避免把资源增加误认为算法收益。

### 2.2 All-to-All 不等于每对 rank 发等量数据

MoE Dispatch/Combine 通常是可变长度的 All-to-All-v：每个源 rank 向哪些目标发送多少，取决于实际 Top-K、放置、容量策略和通信实现；有些 rank 对可能是零。聚合后每层最多存在 `N×(P−1)` 个有向远程 rank 对，**不是每 token 发往所有 rank**，也不等于实际 QP 数（分块、优先级和连接复用会改变它）。

设每 token 向量为 `H×d` 字节，专家均匀分布，Top-K 从 E 个专家无放回抽样，无 drop/pad。整个集群单层单 microbatch 的远程 Dispatch 期望量：

```text
T = N × b × S
逐专家复制：          T × H × d × K × (1 − 1/P)
同目标rank去重：      T × H × d × (P−1) × [1 − C(E−E/P,K)/C(E,K)]
```

两式是不同通信模板的参考，不是同一系统必然的上下界。第二式只对同 token 同目标 rank 去重；若库先跨节点聚合再节点内转发，跨机量还会不同。Combine 是否能先局部归约也要查实际实现。shared expert、FP8 scales、索引、权重、padding 和转发另计。

核算假定 Dispatch 与 Combine 等字节，推理前向共两程；训练激活还包含反向的两程。**训练不是简单把推理总耗时乘二**：梯度 DP、通信/计算重叠、路由权重梯度、激活重算、流水与优化器均未纳入这四程的字节核算。累计包数量字段只对期望 payload 总量取整，不是实际逐流分包数或事件数。

示例 N1024、EP64、b1、S1、E256、K8、H7168、d2、58层：逐专家复制的所有前向 MoE 通信为 13,410,238,464 B，按目标 rank 去重参考约 12,866,705,058 B。均为**远程 rank 逻辑字节**，包含可能在服务器内部完成的部分，不能称为跨机网络测得流量。b 从1变4在这个固定模型下字节严格增4倍是定义推论，长尾和吞吐如何变化仍需网络执行。

### 2.3 何时选 EP，何时增加副本

先检查权重、激活、KV/优化器、通信缓冲能否容纳，再扫描并行配置；容量不合格的点不进入性能比较。

| 约束/目标 | 倾向与需要验证的问题 |
|---|---|
| 单副本专家权重无法容纳 | 增大 EP，或结合 TP/PP；同时检查通信是否跨服务器，不能只看专家参数均分 |
| 模型已容纳，推理请求吞吐不足 | 增加独立副本，控制 EP 跨机范围；推理副本一般没有逐 token 梯度同步 |
| 小 Decode batch、每专家 token 少 | 过大 EP 可能增加小消息、准备及尾部等待，优先验证较小 EP/本地性和低延迟通信 |
| 大 Prefill/训练 batch | 更易形成大通信块；检查 NIC、leaf 上行、目标 incast 与计算重叠，而非默认带宽足够 |
| 训练增加 expert DP 副本 | 需要专家梯度副本同步及 dense 梯度 DP，检查与激活 All-to-All 的同网竞争 |
| 热专家集中 | 先定位专家、rank、NIC或端口哪一级失衡；改变放置/副本/路由会引入额外代价，不能只均摊专家计数 |

GPU 型号影响计算、HBM 和本机互联；Scale-Out 还必须显式记录 NIC 代际、每卡带宽、PCIe/GPU-NIC 亲和性、rail 连接和交换机上行。一个 GPU 型号标签不能确定这些参数。

## 3. 网络结构与前端 trace 应怎样连接

单 rail 两层 Clos 是首个基线。每服务器八卡、每卡一 NIC 不等于服务器总共一个400G出口；示例为八个400G端口。leaf 每口400G、32个下行和32个上行，聚合两侧均12.8Tbit/s。若把上行改成200G，聚合变6.4Tbit/s、下/上比2；这是明确的网络超售，不是 GPU 性能变差。

多 rail 的下一阶段要显式给 GPU→NIC→rail→leaf→spine 连接和 GPU/NIC 亲和性，不将所有链路合成一个“总带宽”。同机路径、同leaf跨机路径、跨leaf路径、跨rail转发分别检查。跨机转发可能先走 NVLink、再由本节点某 NIC 发出；该策略应进入通信模板，不能由拓扑标签自动推导。当前容量命令只核算单fabric、一NIC/GPU，不声称已有多rail执行。

前端向后端传递的是**任务和依赖，而不是预先填好结束时刻的包流量**：

```text
请求/训练microbatch + 每token逐层专家选择 + 专家放置
    ↓ 通信模板（去重、聚合、分块、准备成本）
计算与通信DAG：rank、层/阶段、src/dst、字节、tag、前驱、资源
    ↓ ASTRA就绪任务，动态发起SEND；RECV登记等待
独立非UB适配器 → RDMA QP/优先级/分包 → NIC → Clos
    ↓ 本次仿真的数据就绪/完成事件
ASTRA推进后继、组完成 → 前端选择下一批/训练后继
```

路由 JSON 是 token→expert 的来源记录；计划/Chakra 图是任务 trace；ns-3 执行时才生成包、ACK和拥塞事件。这三层不能混称一个 trace。网络比较可以固定已保存的 DAG；batch、精度、E/K或通信模板改变一般需要重新生成图，不能只把某个包尺寸字段替换。

现有服务图和 UB 适配并非天然可直接用于 RDMA。新后端应独立可执行，只链接自己的 ns-3；复用稳定的图/控制/记录格式，新增 NIC/拓扑配置和能力声明。一个运行内全部竞争组共用网络与时钟；不将独立的 UB 与 RDMA 仿真结果相加称为联合仿真。

## 4. 专家热点：已有数据能支持什么

不能笼统说“现有仿真器都用 random”。本仓库已经有真实路由导入、校验、逐请求逐层选取；random 应是可复现基线，而非替代真实输入的唯一模式。

### 4.1 所给 Hugging Face 数据的实际定位

用户提供[MoE_expert_selection_trace](https://huggingface.co/datasets/core12345/MoE_expert_selection_trace)。本仓既有清单固定修订 `27febb7b2d24169560a9f6f83d38eb53f94916cf`，已用子集 `cognitivecomputations/DeepSeek-R1-AWQ/mmlu/`，证据见[来源清单](../../fixtures/m10_route_selection/README.md)。

- 已使用的是 **AWQ 推理请求的 Prefill/Decode 路由**，不能据此判断训练过程中专家随优化器 step 的变化。没有据此判定整个远程数据集的全部目录都只含推理。
- 原始 JSON 是 entry 列表：entry0 为 Prefill、后续 entry 为逐步 Decode；每个 entry 以原始 layer ID 为 key，MoE 层为 token×Top-K。R1 前3层dense/null，后58层256专家Top8。
- 历史基准从13,922份目录记录中固定顺序筛选前1,145份，取得1,024份可用请求，排除缺层和不足64步的文件。该基准保存的是来源清单、摘要和映射，**当前 clone 不含原始 JSON**。
- “至少64步且全部入口合格”的选择条件可能影响长度、任务和热点分布。热点研究要对任务/长度分层，并报告拒绝及抽样偏差，不能把便利子集当全数据总体。
- 历史准备的64步记录不意味着当前非UB系统已执行64步；来源固定也不等于 GPU/软件版本和时序已校准。采集硬件、权重修订等未知项仍保留未知。

用户暂未提供原始路径，本轮不生成真实热专家排名、热点比例或训练趋势。数据恢复后沿用 `route_evidence.validate_raw/iter_sources` 和 `route_records.RouteRecords` 等稳定读取逻辑，在实验分析层按文件流式累计，避免另造宽松解析器或一次加载全部数据。这里只是后续分析接入设计，未交付新的热点统计命令。

### 4.2 “热门专家”怎样变成网络问题

**专家频率高 ≠ 必然出现网络拥塞**。专家可能本地命中，多个热门专家可能分散在不同 NIC，也可能挤在一个 rank；相同总频率还可能是平滑到达或同步突发。要沿以下关系逐级检查：

```text
专家选择 → expert/rank放置 → src-dst字节矩阵
→ 同机转发/网卡归属 → 选路后的端口到达与服务
→ 队列/ECN/PFC/反馈 → 可用数据时刻 → 关键依赖上的业务长尾
```

必须同时记录准备/计算时间，否则专家计算慢导致到达错位，也可能被误判为网络排队。仅有路由频率而没有时序，只能回答潜在负载失衡，不能直接报告 P99 FCT 或训练加速比。

训练热点可能受数据域、层、路由分数、参数更新和负载均衡机制影响，随 step 变化；batch 聚合后可能平滑，也可能在同任务 microbatch 中集中。负载均衡损失、bias更新、capacity factor、token drop/溢出和复制专家都会改变 accepted traffic。容量限制下要分开统计“被选中”“被接纳”“被丢弃”，不能拿路由选择数直接算网络实际字节。

### 4.3 训练数据最小采集与分析计划

训练 trace 至少需要：模型和训练代码固定版本、E/K、精度、checkpoint/step范围、数据抽样方法；每条记录的 step、microbatch、layer、源rank/token、TP/PP/DP/EP组、选中专家及权重、accepted/drop/pad、专家放置。token身份可匿名，但必须保留跨阶段关联。另需准备/计算时间基线、前向/反向依赖、梯度bucket及同步方式；只有专家ID还不能重建训练网络。

| 分析层 | 指标 | 回答的网络问题 |
|---|---|---|
| 每层/微批专家 | 峰/均值、CV、归一化熵、top-m专家占比、零负载比例 | 总量相同是否存在明显偏斜 |
| 时间窗口 | 热点集合Jaccard、持续时间、自相关；多窗口敏感性 | 热点是否持续到足以让放置或调度受益 |
| token共选 | 专家共选矩阵、目标rank去重后的分布 | 热门专家是否共置、是否重复发向同一目标 |
| rank与NIC | src-dst字节、远程/跨机比例、收发峰值、同时活跃对 | 偏斜是否集中到实际网络资源 |
| 网络执行 | 端口到达/服务、队列分位数、ECN/PFC、反馈、丢包/重传 | 排队由目标incast、链路超售还是反馈机制触发 |
| 业务完成 | 层/微批/step完成、通信暴露时间、关键依赖 | 网络延迟是否传到研究对象，而非全部被计算覆盖 |

统计按层/任务/阶段分别报告，不把不同E/K混合。置信区间优先按请求/任务或训练step成组抽样，避免把高度相关的 token 当独立样本。缺少训练数据时只能交付推理结论和带来源标签的合成敏感性实验。

对照设计必须保留能区分解释的信息：

1. 原始有序路由；原始专家放置和可校准的时间依赖。
2. 保留每专家频率、打乱token时间：检验频率和突发性的区别。
3. 保留时序、打乱源rank映射：检验业务相关性与网络位置的区别；明确这会改变源局部性。
4. 固定真实路由、只改专家放置：检验从专家热点到NIC热点的映射，不改变模型选择结果。
5. 相同E/K/token量的uniform；另有Zipf/Markov合成扫描，均标注 synthetic，不能称真实训练分布。

只打乱expert ID相当于改变放置，不能声称消除了偏斜。不能任意增减真实trace的E/K保持“相同模型”；模型参数变化应采用对应来源或明确的合成机制。若动态复制专家，还要计入权重迁移、缓冲和训练梯度归并，不能无成本搬走热点。

## 5. 与现有平台的关系和可发表的问题

| 平台/组件 | 在本研究中的用途 | 不能直接替代的部分 |
|---|---|---|
| LLMServingSim | 推理请求到达、组批与计算/容量前端 | 不独立给出网络逐包拥塞或训练图 |
| ASTRA-sim 原生 ns-3 | 图依赖执行、网络接口、集合通信展开的基础 | 接入当前服务控制、版本和完成语义仍需验证 |
| SimAI / ns-3-alibabacloud | 训练并行/通信编排、RDMA及NVSwitch网络的源码和对照 | 本锁定版本存在已复现边界缺陷，不能直接照搬所有配置与时间构造 |
| DeepEP | 真实 EP 通信的转发/布局/准备/前反向语义参考 | 是实际通信库，不是完成了GPU时序和网络仿真的替代平台 |
| 本仓当前 UB 系统 | 已有真实路由、动态服务、依赖/反馈、观测与真值分离 | 没有可用非UB在线服务、千卡验证和真实训练热点结果 |

“加入ns-3”“支持更多GPU名字”“发现batch增大字节增加”本身不足以构成机制创新。近期合适的研究问题是：**在真实热点及多EP组共享网络下，哪些放置/聚合策略把专家偏斜放大为NIC与leaf排队，均匀路由假设何时会改变策略排序？** 先用对照证实这个差异及业务影响，再提出网络策略；若uniform与真实结果一致，正常报告适用范围，不人为制造热点。

近期产出应是可复现的非UB网络微基准、路由到端口负载的分析方法与经校准的短窗口结果；会议poster/工作坊或工具论文需按实际结果选择，不保证投稿日期。中期在千卡共享网络上验证一项可解释的放置/聚合或拥塞处理机制，与充分使用已有信息的强基线比较；有硬件/生产trace和可泛化结果后再考虑网络/系统主会。长期工具产出应包含稳定接口、固定依赖、来源清单、预算和误差说明，发布及真实数据再分发另按授权处理。

## 6. 每一步目标、交付与验收
