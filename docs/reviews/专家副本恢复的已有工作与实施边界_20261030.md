# 专家副本恢复：已有工作、可实现性与下一步

本轮结论：**不把“复制专家、换卡重做”作为创新点。保留一个更窄的待验证问题：局部网络失联时，能否在当前MoE调用内补齐缺失贡献，同时保留已经完成的工作，并控制额外网络和计算开销。** 这只是候选问题，尚无新算法、创新性证明或性能收益。先实现正确的任务身份、共享资源和退出语义，再做性能对照。

本轮完成公开资料和当前源码核查、已有正常/故障原件的离线重分析，未运行新网络、未编译、未运行GPU。机器证据见[审查摘要](../review_artifacts/replica_feasibility_20261030/evidence.json)，可读版见[网页](../review_artifacts/replica_feasibility_20261030/report.html)。

## 1. 服务目标与约束

服务对象是MoE推理的跨服务器通信，优先研究热点接收端或共享网络局部短时受损时，传输进展如何影响一次推理调用的完成。不是训练检查点恢复，也不以重传协议的已有机制作为新贡献。

- 后续网络选择128、256、512模拟GPU端点中的一档Clos；当前已有证据是128端点、两个EP64组，每组完整E256，每rank每层4专家。
- 当前15份独立R1-AWQ/MMLU专家选择记录，117个数据活跃rank；只模拟两层、两步Decode片段，计算为声明成本，不是完整671B模型或GPU测量，也不是满载生产请求流。
- 保持原专家选择和全部贡献，不以丢弃专家、换成不同专家或跳过必要完成依赖取得收益。当前没有数值张量，只能验证逻辑覆盖和成本；要声称数值等价还需要真实张量验证。
- 所有组、原尝试与备用尝试必须使用同一ns-3时钟、网络队列、NIC以及物理GPU计算资源。不得把另一次仿真的备用完成时间拼进主任务。
- 算法只读取当时可见的进展和超时，不能读取注入的故障结束时刻、内部丢包位置或未来到达记录。

## 3. 当前系统的五个实际障碍

### 3.1 另一个组有相同专家，不等于可以直接借用

当前偶数/奇数两个EP64组各有一套完整专家。按声明放置，GPU20和21都对应专家40–43；首层实际访问目标上的40、42。但这只是部署身份，未加载真实模型权重，更不证明两份权重版本和量化实现相同。

`scaleout_service.py`要求通信组恰好划分全部物理GPU。离线反例保留组大小和专家整除条件，只让两个组共享rank20，公开校验器明确拒绝。`backend/rdma/service.cc`又要求每rank只有一张活动图，消息两端属于本图的EP组。直接将目的20改成21，会违反现有执行定义。

**所需改进：** 将逻辑请求、专家副本和物理执行资源分开；跨组帮助必须是显式、可核验的调用，不能靠改图成员绕过归属检查。

### 3.2 当前故障例没有“已经完成的健康专家计算”可保留

当前图的每个`L0.experts`都依赖本组Dispatch完成门限。离线逐一核对原图和实际ASTRA日志：

| 条件 | 首Dispatch门限释放 | 组0核对rank数 | 门限前完成的首层专家计算节点 |
|---|---:|---:|---:|
| normal | 16.922 µs | 64 | 0 |
| local | 254.594 µs | 64 | 0 |

因此，本例首先能保留的是已到达激活和此前完成的工作。若声称保留“其他健康专家已经算好的结果”，需要另选真实支持通信计算流水的语义、生成更细任务，并验证目标通信库允许这样推进。不能直接删掉现有门限制造收益。

### 3.3 网络去重后的恢复单位不是一份任意专家结果

当前Dispatch按“token→目的rank”去重，Combine在rank内合并后返回。一份传输可能对应同一token在同一rank上的多个专家贡献。单纯按照收到多少字节，无法判断某个专家结果是否已经消费。

**首个可行单位：** 一个token在目标rank上的完整专家贡献集合，下文称“贡献包”。身份至少包含请求、Decode步、原始层、token位置、专家集合、模型/权重版本；网络发送另有attempt身份。备用rank必须拥有同一专家集合。一个贡献包只提交一次，迟到的原结果不能再加一次。若以后拆成逐专家恢复，需要新的Combine表示及覆盖核验，不能继续假定当前rank合并结果可任意拆开。

### 3.4 当前消息完成不能替代逻辑结果完成

`astra_adapter.cc`为每个原消息保存SEND/RECV回调；整个图退休要求全部消息回调完成。备用结果即使先回来，原SEND仍可能等待ACK或恢复耗尽。若不改变生命周期，所谓“更早完成”可能只存在于分析图上；若直接伪造ACK，又会错误释放原传输资源。

**所需改进：** 分别记录逻辑贡献已提交、备用/原尝试完成、源缓冲可复用、原连接排空。逻辑获胜不自动产生原连接ACK。定义取消或隔离时，也必须处理未到包、迟到写、缓冲隔离及仍在队列里的实际传输。

### 3.5 备用计算和检测不能免费

前端当前只在初始决策和整组图完成时交互，没有在途恢复决策接口。原生stream probe虽然有每GPU串行队列，但这是另一个入口，不能直接当作已与ASTRA共享的资源。`service/1`容量记录的`device_bytes`为空，`service/2`也仅核算声明权重和KV，不含完整工作区。

**所需改进：** 在同一时钟提供可见进展事件；普通计算与帮助计算进入同一物理GPU调度；原传输、备用输入、返回结果和控制流量共享真实NIC/交换队列。新增权重、缓存、控制及资源清理都有预算。不能使用真实丢包日志作为在线故障通知。

## 4. 收益有多少，空间如何判定

现有故障段363.964 µs，正常段132.159 µs，相差231.805 µs。这是**本条件下的故障代价**，不是新方法收益，也不是承诺能消除的空间。故障结束到下一次发送的141.392 µs间隔，同样不能直接当可回收收益。

对某个缺失贡献包，只有以下条件成立，备用执行才可能更早：

`可见信号后的检测/决策 + 备用排队 + 输入传输 + 专家计算 + 结果返回/提交 < 原尝试剩余完成时间`

这些时间必须来自同一次执行。后半项不能由算法读取；它只供事后评价。原实验中健康组反而更早，不支持把“故障恢复必然拖慢别组”作为立项前提。

还应同时计算正常路径新增开销。若请求受到故障影响的概率为`p`，受影响请求平均净节省为`d`，未受影响请求新增开销为`c`，平均净节省为`p*d-(1-p)*c`。其中`p`是请求受影响比例，不能用全网丢包率1.12%代替。尾延迟和SLO违约率必须按请求分布实测，不能从该均值公式推导。

当前没有生产故障频率、完整请求时延、真实权重或GPU成本，不能给收益百分比承诺。近期目标是得到“何时值得恢复、何时会因重复计算/网络竞争更差”的边界；若公平备用请求已消除收益，就关闭该候选。

## 5. 后续实现与验收顺序

以下均为待实现项，不是可用接口；实现前另登记平台范围和预算。

| 顺序 | 网络/系统修改 | 验收标准与停止条件 |
|---|---|---|
| 1. 逻辑贡献身份与尝试状态 | 显式贡献包、同版本副本、attempt、一次提交、原尝试退出状态；先独立CPU功能核验 | 原/备用任一先到、同刻到、重复到、过期版本、缺贡献、备用也失败均可判定；不能将逻辑提交伪装成网络ACK。当前数值正确性不在已验证范围。 |
| 2. 接入真实服务执行 | 在LLMServingSim/ASTRA服务内引入在途事件和可替代贡献；普通与帮助工作共用物理GPU计算/NIC；保留原图的合法依赖 | 关闭恢复时原图和执行保持一致；打开时帮助工作真实排队，所有旧包/缓冲有退出证据。若仍需等待原图/原ACK才能推进，就不能宣称业务恢复。 |
| 3. 冻结公平方法 | SR原地恢复、固定延迟的贡献包备用、整请求重试；候选只根据已观察进展选择贡献包和合法副本 | 相同输入、专家语义、观测、计算/NIC资源、副本与最大重复工作预算；提供正常无故障及无可用副本条件。不得将SR、超时或备用请求重新命名为创新。 |
| 4. 一档Clos研究 | 选128端点，继续真实独立路由；覆盖短时目标失联、共享上行拥塞、尾ACK丢失、误判和备用拥塞 | 分列请求/片段时延、尾部、重算量、实际重传/备用字节、健康组影响及排空时间。全包/图记录有界，失败保留，不靠提高故障强度获得正收益。 |
| 5. 去留判断 | 比较检测、恢复粒度和共享资源约束各自作用 | 只有比公平备用请求更好且正常开销可接受，才进一步查新、扩独立样本和做真实GPU小型实现；否则记录负面结果并结束候选。 |

论文贡献不能落在“搭了几个仿真器”。可能的贡献应是一个经过验证的网络—系统机制：**在保持专家语义和共享资源约束下，利用可见进展缩小恢复范围，同时证明何时不应启动恢复。** EEP等已有工作与此存在范围差异，是否有足够方法差异仍未证明。
