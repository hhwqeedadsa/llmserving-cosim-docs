# 丢包恢复机制、通信代价与优化空间

2026-10-23。本轮直接围绕三个目标开展实际网络实验：现有丢包怎样恢复、如何保持原有条件改进效率、目前能改善多少。13组条件已执行完成。结果表明，丢包位置决定反馈路径，而超时等待是否暴露在业务关键路径上，决定最后损失；单看重复字节不足以解释推理效率。

## 1. 原有条件保持什么

| 对象 | 本轮固定内容 |
|---|---|
| 服务任务 | 8GPU、两个交错EP4副本、每rank batch4、H1024/FFN4096、16专家/Top2、1层2步有限ready-KV Decode |
| 模型与计算 | 合成MoE片段和固定专家选择，声明计算成本；A100是描述标签，没有执行GPU或重新测量计算 |
| 网络 | 非UB的固定ASTRA原生RDMA ns-3，100G三层Clos，单rail/plane，各链路传播1μs |
| 源端资源 | 每源3消息/8192B FIFO软件额度；从准入占用到真实ACK且QP清理后归还，不提前释放 |
| 通信内容 | 每条件完整执行92条消息、389,120B必要payload，Top-K、模型、batch、图与路径保持一致 |
| 对照变量 | 故障位置与初始RTO；最大RTO保持160μs，最多3次无进展重试，其他协议参数不变 |
| 时钟 | 每个条件的所有组和两步共用一个持续网络实例，由实际完成反馈推动前端；条件之间独立，不合并耗时 |

输入不是生产热点记录；本轮用于解释机制并量化当前参考场景。没有用少发送、少完成或取消必要等待换取速度。

## 2. 现有丢包怎样恢复

实验从第一个正式无故障运行的实际任务图选出GPU0→4的Dispatch，业务量6,144B。payload为1,000B，尾包为144B。三种故障都只丢弃一次匹配包，实际命中分别核对。

| 丢失位置 | 当前恢复路径 | 本轮实际过程 |
|---|---|---|
| 中间数据，起始偏移3,000B | 后继数据到达后，接收端发现序号缺口并发送NACK；发送端回退到最早未确认字节 | 17,403ns收到NACK并开始重发3,000B以后的后缀，目标30,105ns完整确认；不需要超时 |
| 最后144B数据 | 没有后继数据提供缺口反馈，依赖源端ACK进展超时 | 40μs配置下，17,486ns最后取得ACK进展，57,486ns超时重发144B；69,660ns实际确认 |
| 最终ACK | 数据已齐，发送端仍只确认到6,000B；超时后重发尾部，接收端重新确认 | 同样在57,486ns重发144B，并在69,660ns补齐确认；原数据就绪仍为11,476ns |

RTO是重传超时时间。这里的超时恢复是项目显式实现的Go-Back-N参考扩展，保留原生NIC发送调度、排队、PFC和DCQCN。默认原生库尾包/最终ACK的限制不能解释成生产RDMA没有恢复。源码依据包括固定原生`ReceiverCheckSeq/ReceiveAck/RecoverQueue`和项目`RdmaRecovery`，没有变更依赖。

## 3. 丢包对效率影响多少

业务完成时间包含本有限任务的计算和网络推进。网络排空另计；重复payload为源发送总量减必要业务量，不含头部和ACK。线上模型字节在机器摘要中单独保存，不能当成生产RoCE精度。

| 40μs恢复条件 | 业务完成 | 比无故障增加 | 重复payload |
|---|---:|---:|---:|
| 无故障 | 122.068μs | 0 | 0B |
| 中间数据丢失一次 | 122.068μs | 0 | 3,144B |
| 尾数据丢失一次 | 134.108μs | 12.040μs（9.86%） | 144B |
| 最终ACK丢失一次 | 131.105μs | 9.037μs（7.40%） | 144B |

中间包故障使目标消息变慢并增加后缀重传，但在本例中被其他工作重叠掩盖；不能说丢包没有局部代价。尾包只多144B，相当于全任务必要payload的约0.037%，业务却明显推迟，说明反馈等待和依赖推进更值得检查。

尾数据丢失与最终ACK丢失的目标最终ACK时刻相同，业务仍相差3,003ns。前者还推迟接收消费者；后者数据已到，但发送资源仍被占用。前端记录中，受影响组首轮分别在86,102ns与82,774ns结束，相差3,328ns；第二轮持续时间差抵消325ns，最后净差3,003ns。这是实际阶段时间核算，不是删除某项等待就能得到相同收益的反事实证明。

## 4. 在原有条件下怎样改，实际改善多少

本轮只更改固定初始RTO，预先选择40、20、12μs，没有增加网络容量、源额度或专家冗余。最大RTO和重试数不变，仍要求完整ACK与QP清理后才能释放发送资源。

| 故障 | 40μs初值 | 20μs初值 | 实际缩短 | 相对40μs故障条件改善 |
|---|---:|---:|---:|---:|
| 尾数据丢失 | 134.108μs | 122.072μs | 12.036μs | 8.97% |
| 最终ACK丢失 | 131.105μs | 122.076μs | 9.029μs | 6.89% |

两种条件的重传量仍是144B。目标超时由57,486ns提前到37,486ns，完整ACK从69,660ns提前到49,594ns；目标确认早20,066ns，业务分别早12,036ns和9,029ns，不能直接将单消息改善当成服务改善。

20μs无故障结果与原生/40μs无故障的消息、端口、服务、队列记录和包捕获共有执行字段完全一致；中间包故障依然由NACK恢复，业务完成没有改善。

因此当前最简单的可执行改动，是在这一参考场景中减少过于保守的等待，而非先增加新的缓存或恢复控制器。本轮没有更改平台默认值：20μs是当前条件的候选配置，尚不能推广到不同传播、拥塞、路径或持久QP。

## 5. 为什么不能继续盲目缩短

12μs无故障配置产生60次超时决策，重复payload为237,568B，相对必要业务量多61.05%。业务从122.068μs变成122.438μs，网络排空则推迟到134.438μs。

目标首包于4,203ns发出，首个实际ACK到达是16,725ns，往返12,522ns；12μs计时器已在16,203ns超时，早于正常反馈。目标因此在健康情况下重复发送完整6,144B。它在故障时的局部反馈可能更快，但本例整体仍略慢于20μs，并产生大量额外流量。

缩短等待要有源端反馈证据和安全余量。已有Karn RTT估计、恢复历史等功能可作为后续强基线，但不能默认它们会改善短QP冷启动，也不能把经典超时参数调整当成新论文机制。

## 6. 提升空间和当前不能声称的结论

相对40μs无故障参考，尾包/ACK故障原有12,040ns/9,037ns差距；20μs后只剩4ns/8ns。当前实验已经实际收回了大部分这项差距，继续只围绕这个小场景缩短RTO，业务收益空间很有限。

这不是任何方法的理论最优或全平台提升上界。无故障执行的共享网络顺序会随策略改变，更多反馈延迟或持续丢失可能改变最佳取舍；13个确定性条件没有提供故障发生概率、生产p99或千卡泛化证据。

完整目标仍有三项后续工作：

1. 将当前结果推广到有边界的反馈时延和并发条件，确认简单RTO方案何时失效；保留同任务与同资源基线，同时报告无故障代价。
2. 当前持久stream/事务入口拒绝旧fault/recovery模式。若要研究现代通信，应先解决持久序号、恢复重放、完成信用和事务重复副作用，不能绕过校验把旧方案直接开启。
3. 在明确网络瓶颈后才比较新的机制，并计入稳态字节、缓冲、反馈与检测成本。论文创新还需证明相对已有恢复/拥塞控制的差异和跨条件价值。
