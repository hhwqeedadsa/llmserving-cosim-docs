# 事务容量扩展与完整应用研究门槛

本轮解决的是实际应用接入前的执行容量缺口。它使较长的程序能够沿真实请求、目标内存修改、回复和资源回收继续运行，不构成新的网络恢复机制，也没有证明论文创新成立。

## 为什么先做这一步

上一轮真实路由对照中，经典选择性重传将故障引起的最后源确认增量由19.028us降到0.515us。无直接丢包的stream8仍有61.213us额外接收等待，但没有决定全窗口完成时间。因此不能把单流等待直接当业务收益，也不应继续围绕已被强基线消除的大部分损失设计新算法。

下一步需要完整Dispatch—计算—Combine及实际集合屏障，判断共享队列是否影响应用关键路径。源码核对首先发现事务入口只容纳8条连接、32个远端操作；四卡EP全互通就有12条有向连接。目标请求上下文、序号和源读保护记录也各有旧上限，不能只改Python输入检查。

## 本轮改变和证据

v5可选显式生命周期额度，上限为64条连接、1024个远端操作和256个本地节点；缺省仍为8/32/16。Python、原生离线/在线准入、队列、请求/回复载体、目标上下文/序号及读保护元数据一致派生。窗口权限、地址范围、写入因果顺序、字节预算和16个同时本地输出写保护独立保留。64条连接不等于64个GPU，更不等于已执行千卡程序。

| 功能用例 | 实际结果 | 可支持的结论 |
|---|---|---|
| 四GPU标签全互通 | 同一网络12连接、96写、20本地copy完成；96源包/6144B | 已跨过旧连接/远端/本地累计上限，实际数据与完成事件一致 |
| 单连接长原子序列 | 64个请求，第33项对应字节1280实际丢一次；132源包/5280B，64个正确旧值，最终2080 | 恢复后恰好执行一次，实际回复推进完成，序号超过31 |
| 在线追加与拒绝 | 先40项，累计超额候选不改变会话；合法续跑96写/20copy完成；完成后本地超额仍拒绝 | 额度是全生命周期累计，整批准入失败不会泄漏候选前缀 |
| 修改前后默认回归 | 修改前HEAD消费者与新消费者使用同一载体/Fabric/八库，完整结果仅库路径不同 | 新字段缺省时保留本用例全部结果；不是全应用普遍等价证明 |

独立标准库审计按实际源字节、物理入站/ACK、回复、窗口和copy重建完成；六类篡改被拒绝。39项Python检查、23类原生准入拒绝、132066项请求额度CPU断言及7085项既有内存断言通过。CPU目标状态检查到64上下文×1024序号，不表示公开事务入口允许65536个操作，其全局上限仍是1024。

首次扩容运行揭示了遗漏的48个源读保护记录上限，0ns同步发出两帧后失败；没有删除失败或提高预算。修复与显式总节点额度的派生关系，再执行原定功能验证。取消单独健康长序列网络，实际网络总数仍为8，包含失败、直接native无效候选以及新目录默认参考。另保留恢复字段漏填、检查器字段假设、库版本判断和路径规范化错误；检查器修正只重分析已有结果。

同Linux主机新Python源码根/空cwd实际执行公开拓扑、扩容输入preflight及默认网络参考；三组离线审计逐字节相同。运行使用增量二进制及固定库，没有从零重建依赖，也没有执行GPU、安装、下载或push。完整输入、命令、监控和恢复证据见[功能验收](../../fixtures/transaction_limits/README.md)。

## 下一研究的必要条件

1. 接入现代应用事件：实际接收驱动计数、数据就绪、集合屏障和后续通信；现代DeepEP包含self-peer信号，不能省略或替换成零成本全局join。
2. 区分协议功能与物理成本：当前MRT1和显式local时长不能代表GIN、GPU可见性或实测计算。self-peer物理路径、源安全与真实provider观察仍需源码/测量支持；不匹配硬件不能用于校准结论。
3. 先核对应用关键路径，再设计优化：在同一资源和信息约束下保留选择性重传、合理恢复限速/公平队列及经典通信调度。只有可重复、强基线无法解释的应用损失，才进入新机制研究。
4. 扩大代表性而非只扩大数字：当前四个已见推理路由前缀不能代替独立请求、训练热点分布或千卡长程序；需明确模型、batch、EP/DP与网络层级，使用留出请求，并单独验证规模、成本和精度。

论文目标仍是网络与系统鲁棒性机制，以及可被他人复核的证据链。新的容量字段和功能数量只提供研究条件，不计作独立创新点，更不能据此宣称达到A类或最佳论文水平。
