# 网络鲁棒性进展：端口失效边界与缓冲一致性

本轮把“网络还有真实排队”和“仿真器计数没有释放”分开了。新增了可选终态诊断及可运行示例；没有交付物理链路故障恢复，也没有确立论文创新。

## 为什么检查这个问题

研究局部故障后能否继续服务，必须知道哪些包还在网络里、哪些缓冲仍受旧操作占用。如果把计数残留当作实际拥塞，后面的超时、恢复与安全复用结论都可能出错。

[原生状态转换探针](../../experiments/link_down_contract/README.md)表明：固定ns-3的端口关闭会把15个排队包清掉，但相应入口与出口各14,000B的MMU计数和5,808B共享计数没有释放。三者是同一批数据的不同视角，不能相加成内存。清队列走QbbDrop，当前适配器监听的接收错误走PhyRxDrop，不能混用同一种在途递减规则。

该探针直接种入队列/MMU状态，没有运行网络，也未构造完整私有转发计数。因此它说明接入物理故障前的实现边界，不是生产故障、安全漏洞或实际恢复性能结果。探针中按种子清单移除占用只是评价对照。普通dequeue含发送、ECN/PFC等副作用，不能当作丢弃清理函数使用。

## 平台现在新增什么

用户可在协议中用`mmu_snapshot`选交换机并声明端口总预算。最终Report读取这些交换机全部物理端口的原生队列/MMU及PFC状态；不增加模拟事件、不改包、不调整路径，也不清零计数。非法选择或预算不足在分配网络前被Python和C++分别拒绝。

`rdma-diagnose`只在收到快照时增加离线守恒检查：出口计数是否等于实际队列、全交换机入口与headroom是否对应出口、共享计数是否可由入口重建。优先级0控制包、序列化和在途字节不参与这些MMU检查。没有快照时保持旧结果和旧诊断。

实际8GPU/10交换机例中，32端口正常排空；开启功能前后的原有结果保持。另一个上层25Gb/s、4,000ns截止的小例有89,096B真实数据仍排队，计数一致。后者原命令按预期失败，不能因诊断生成成功就称网络完成。独立从真实入出队事件重建的队列与快照一致，也覆盖了事务请求/回复。

公开配置与命令见[缓冲小例](../../examples/scaleout_rdma_mmu/README.md)，字段见[输出格式](../record_storage.md)，完整验收及恢复边界见[功能证据](../../fixtures/mmu_snapshot/README.md)。46项不同单元、各10类Python/原生拒绝、13项固定依赖检查通过。六次实际网络包含旧/新对照、未排空条件、事务和为迁移验证的公开重放，不能算六个独立研究样本。

新源码根、空cwd使用包内八个原生库完成公开网络重放，原执行字段除库路径外相同；完整诊断和三份离线审计逐字节相同。恢复中的拓扑再生成因产物监控范围错误在启动前被拦截，未提高限额或重试，故只称使用包内已核验拓扑的重放。失败、修正、57份监控及约11.75MB本机持久检查点均保留，见验收入口。

## 离最终研究目标还差什么

| 要求 | 当前事实与下一门槛 |
|---|---|
| 准确的Scale-Out网络状态 | 共享原生网络和包记录已有；本轮补终态缓冲核对，仍不保证全过程及硬件准确 |
| 物理故障可表达 | 当前只支持接收错误丢包；端口关闭还需丢弃回收、PFC状态、路径/连接变化和在途退出的专门实现与验收 |
| 有限资源下持续恢复 | 复制缓冲已有容量和部分释放事件；失败源保留、目标缓存至会话退出等边界仍限制连续复用 |
| 超过强基线的新机制 | 简单保留owner策略已被同信息操作重放解释，不能继续当创新；经典重传与缓冲诊断也不是主贡献 |
| 代表性与规模 | 四份真实路由、有限层段及人工千卡短任务不等于完整大模型生产恢复验证 |
| 校准及论文成果 | 现代provider语义、匹配硬件测量、代表性留出和有价值的机制贡献仍缺，尚不能宣称A类或最佳论文水平 |

下一研究应围绕网络状态变化后的安全继续执行，而不是继续增加无关功能。先明确连接失败后哪些远端访问仍可能生效，给出有限窗口可复用的可检查条件；把等待退出、独立窗口、操作级重试作为同资源、同信息的强基线，纳入控制消息和重算成本。只有在真实专家依赖下仍有无法由这些基线解释的损失，才设计新方法。物理故障能力与研究算法分别提交，不能关闭现有顺序保护或用长传播时延伪造拥塞来制造论文现象。
