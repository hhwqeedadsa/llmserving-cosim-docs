# 先减少无效控制交互，再判断网络扩展性

四份真实路由的一次现代 Dispatch—专家—Combine 调用，之前在 36,845 ns 触及宿主接口 256 次交互上限。它没有完成，不能把这个限制解释为网络死锁、网络性能差或完整千卡应用不可行。本次只分析原记录，没有增加一次网络执行，也没有提高原上限。

## 可以保留的方案

前端通过当前未完成依赖，声明哪些**已经提交的工作**的实际回调能够推进下一个现代事件。其他回调仍保存，下一次唤醒一起交付；不从依赖满足推断传输完成。Dispatch 同 token 的全部 slot 分配和动态 Combine 通道顺序都必须纳入，静态计划不能覆盖它们。新增 `pending_dependencies()` 只读接口提供这些真实依赖。

| 保存的案例 | 原交互数 | 保持全部现代事件日志的离线唤醒数 | 证据范围 |
|---|---:|---:|---|
| 两 rank、两调用正常网络 | 213 | 165 | 完整原记录 |
| 相同输入、实际首包丢失 | 222 | 171 | 完整原记录 |
| 四请求、四 rank | 256 | 205 | 原失败前缀，完整调用仍未知 |

三组中，已提交任务的内容、批次、顺序、提交时刻以及完整现代事件日志均与原记录一致；未删 self、计数或屏障。独立检查还核对了 437/437/642 条实际回调的保留情况。这里的“完整”针对各自保存的记录，第三组不是完整应用。

## 暂不采用的方案

只在下一项原生任务能够提交时才唤醒，离线可降至 63/66/49 次，并保持已知任务提交内容、顺序、批次和时刻。但是它分别推迟了 185/187/334 项现代事件的前端记账，最大延迟 12,064/17,796/9,868 ns，事件日志也不再相同。因此不能把数字更小当作严格等价、网络提速或论文收益，暂不接入原生入口。

## 已验证与尚待验证

原控制器先逐项重现三份原执行快照，再做条件回放；独立检查器不导入控制器或条件生成器，拒绝虚假完成、改事件摘要、丢回调、改提交时刻、引用未提交工作及颠倒批次顺序六类篡改。8 项新单元检查覆盖只读隔离、Dispatch/Combine 动态顺序、目标可见与源完成的区别、未来未提交工作拒绝，以及六类不安全归档在写入前拒绝；与 25 项受影响回归共 33 项不同检查通过。

170 成员的初始包已逐成员核对哈希，再在新 Python 源码根和空工作目录重算三份记录，两份报告与原件逐字节一致；没有继承原阶段的 Python 模块或运行网络。最终包补入恢复收据和说明，不重新执行成功检查。原始记录和源码保存在 `runs/dependency_wakeup_checkpoint_20261024/`，版本化摘要及独立收据见[证据目录](../../fixtures/dependency_wakeup/README.md)。

目前原生接口未改，不能声称实际交互已减少、四卡验收已完成或支持更大应用。离线记录也不能单独证明更改 C++ 后同纳秒 ns-3 事件的调度顺序不变。下一步需要单独登记原生条件唤醒接口和预算，保持默认行为、全量历史、首次/排空/闹钟必唤醒及整批校验，然后用实际网络检查严格等价方案，再回到原四请求完整调用；若仍触及 256 次，保留新失败，不自动扩限。

这项工作解决的是仿真系统可信执行的前置限制，不是网络机制创新。论文仍需在完整应用上验证恢复竞争是否影响健康请求的关键路径，与强恢复、合理限速和公平调度比较，并补独立负载、硬件校准与完整规模证据。整体研究目标继续进行中。
