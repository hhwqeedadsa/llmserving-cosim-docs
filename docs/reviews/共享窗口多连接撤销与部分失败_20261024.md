# 共享窗口多连接撤销与部分失败

这轮确认了一项直接影响Scale-Out恢复建模的事实：**同一个应用窗口会按backend/connection分别注册，整个窗口的退出不能只看一个网卡、一个MR或最终返回码。** 固定源码还允许“前几个MR已经退出、后续句柄报错”，以及“所有相关MR都已退出、最后的元数据清理报错”的控制路径。模型应保留逐句柄进度，才能决定还能使用哪些资源、哪些范围尚不能复用。

这是对仿真依据的补强，不是新恢复算法、生产漏洞或性能提升。平台保持`a30296c`，本轮只执行CPU记录替身，没有运行NCCL、GPU、真实provider或ns-3。

## 实际库怎样注册和注销

固定NCCL `12df1a11afad322be5a204a2db890161cbf8131d`中，`ncclGinRegister`对每个backend的每个connection，把同一`address/size`传入`regMrSym`，分别保存host/device handle。GDAKI的下层注册为该collComm的保护域注册MR并交换rkey。上层连接选择使用`localGinDevs[commIdx % nLocalGinDevs]`：多个连接可能落在同一设备，不能简单地把连接数、NIC数和MR数画等号。本核查没有执行真实拓扑选择或证明某个合成布局实际可部署。

`ncclGinDeregister`按backend/connection顺序逐个调用下层，并在`NCCLCHECK`遇错时提前返回。GDAKI下层先`wrap_ibv_dereg_mr(mr)`，再清理设备句柄元数据、rkey元数据，最后释放包装对象。两次元数据清理本身都可返回错误；实际类的清理函数也检查`ncclCuMemFree`返回值。因此，最后非零状态无法单独说明哪些MR已经退出。

固定DeepEP主窗口共享workspace与GPU buffer；可选storage窗口另行注册。这里所说的“别名”是同一地址范围经不同连接注册产生的访问渠道，不表示所有服务只有一个MR，也不表示NIC的任意两个MR必然覆盖同一内存。

七份原文区间和hash见[证据](../../experiments/registration_fanout/results/20261024/evidence.json)，源码身份见[来源](../../experiments/registration_fanout/results/20261024/sources.json)。三份原文来自已有缓存，没有新增获取。

## 检查发现了什么

执行了3个精确原函数：上层注册、上层注销和GDAKI注销。其余API使用明确替身。独立整数核算逐条核对1,120个合成条件，覆盖1/2backend、每backend 1—4connection、声明1/2设备及逐位置失败。

| 情况 | 记录型检查结果 | 仿真不能怎样简化 |
|---|---|---|
| 正常全成功 | 按循环顺序注销全部已注册句柄 | 不能在第一条成功时宣布整个窗口安全复用 |
| 中途错误 | 420个条件出现非空、非全部的退出集合 | 不能把非零返回一律变为“此前什么都没完成” |
| MR成功、元数据报错 | 80个条件中，全部已创建MR都成功退出，但最终仍报错 | 不能把控制调用失败一律解释为所有DMA仍在进行 |
| 注册或能力检查失败 | 360个条件中，此前已有成功注册前缀 | 局部函数结果必须保留；未核完上层回滚前不能声称生产资源泄漏 |
| 同设备多个注册渠道 | 718个条件的已创建句柄数大于声明使用的设备数 | 不能只维护“每NIC一个已撤销标志” |

这些数字只是所枚举合成条件的计数，不是故障发生率、硬件支持规模、耗时或收益。替身中的`retired`仅表示模拟的provider调用返回成功；真实provider返回错误时，退出状态可能未知。这里没有真实DMA、实际并发或受支持应用调用时机的证明。

上层注销函数没有在释放成功后清空`ginHostWins`条目，整体失败也不自动回滚已经释放的前缀。因此恢复控制器不能未经生命周期核对就拿原数组重新调用相同全量注销。检查器每条件只执行一次该调用，随后由自身回收残留替身对象，没有执行重复释放或释放后使用。本轮没有核完更高层调用者的回滚、abort或重试策略，不能把这条局部边界称为NCCL漏洞。

## 下一轮平台应怎样改

当前MRT1功能模型的窗口只有owner/key/地址，注册时还拒绝同owner重叠窗口；它没有表达这种共享物理范围的多注册渠道。不能在该结构上简单添加一个`revoked=true`就声称支持multi-rail的安全恢复。应按以下关系扩展，并保持现有默认功能路径的含义：

1. **物理存储与访问权限分离。** 一份存储有owner、地址范围和存储生命周期；注册句柄另外保存backend、connection、设备、保护域、key、权限及其覆盖范围。同地址的多个注册渠道共享实际字节，而非复制成互不影响的独立buffer。
2. **逐句柄记录退出进度。** 区分撤销已请求、provider成功确认、provider结果未知、设备失效假设、元数据释放成功/失败。源停止、目标退出、重传资源回收和新key发布仍是不同事件。不能从元数据清理错误倒推正常MR退出失败。
3. **范围复用检查完整覆盖。** 先取与待复用范围重叠的全部注册实例；每个访问渠道必须取得适用的退出保证。集合为空、覆盖未知或设备失败都应显式解释。只有某个连接不再使用，不能自动把其余句柄视为已撤销。
4. **部分失败后不重做已完成副作用。** 保留逐句柄结果；重试、abort和资源隔离需要独立的合法接口依据，不通过再次释放已完成句柄“碰运气”。新注册生命周期不得与旧key/旧别名混淆。
5. **性能比较保留强基线和真实完成。** 正常全量注销按本源码已有顺序完成，不能人为规定为任意慢、全网广播或全GPU重启。正常任务实际受影响范围由共享地址、网络与应用依赖决定；多注册区、备用内存、额外句柄和key发布按相同资源预算计入比较。

这些是下一轮实现要求，本轮没有新增在线撤销接口。进入性能对照前仍需要合法并发调用约束、窗口回滚/abort覆盖、每设备退出保证及匹配硬件成本；未知时延不能由固定常数冒充校准。

## 复现和研究判断

独立核验按原文区间重取3个函数字节和7段摘录，NCCL来源继续核对commit→tree→blob；另用整数oracle核对全部1,120条记录，并拒绝“任意成功即全退出”“报错即零退出”“同设备只能有一个别名”三类错误结论，见[核验](../../experiments/registration_fanout/results/20261024/verification.json)。完整CPU记录在本地检查点，摘要见[结果](../../experiments/registration_fanout/results/20261024/summary.json)。

恢复与最终预算收据随本轮结果保存；操作见[实验说明](../../experiments/registration_fanout/README.md)。本轮的研究价值是排除错误恢复模型，后续仍须用同资源的强基线检验能否减少正常任务停顿。安全与性能证据、代表性负载、现代完整接入及千卡完整执行仍未齐备，论文创新尚未成立，整体目标保持进行中。
