# 分组路由约束与网络结论修正

本轮最重要的结果是修正研究解释：旧的无约束专家交换大多超出参考路由组数限制；补上限制以后，通信副本变化从明显增加变成略微下降。热点次数之外的结构仍然影响通信，但不能沿用旧增幅解释真实模型，更不能据此宣称优化收益。

本轮为四请求离线路由审计，没有新增网络、GPU、训练或模型推理执行。研究目标仍进行中；这些结果改善证据可信度，还没有形成A类论文主贡献。

## 一、先说明比较对象

一个token选择8个专家，不等于把token在网络上发送8次。固定现代DeepEP direct路径按目的rank去重：同一token的多个专家若在同一个远端rank，只发送一份token。此处“副本”是这种跨rank Dispatch数据副本，尚不是包数、线上总字节或完整推理延迟。

本轮区分两种组。逻辑路由组按原expert ID每32个形成一组，共8组；物理rank是后来分配专家的位置。逻辑组与物理rank不是同一个东西。随机物理放置不改变模型已经选出的专家，所以不能把随机放置说成非法路由。

本机旧Vidur适配目录的V3与R1-0528参考config均给出256个路由专家、Top8、8组、最多选择4组；这些是补充参考，未在本轮证明与官方模型配置逐字节一致。本轮以连续32专家为逻辑组，检查“最多4组”这一参考必要条件。数据集没有提供精确的历史AWQ collector模型revision；这两个本机config和当前可获取模型版本都不能补齐历史身份。原始选择符合条件，也不等于证明了采集版本或完整路由实现。

## 二、实际得到什么结果

固定四个原始请求，58个MoE层、每请求128个Decode位置。每条件29,696条token选择，按四请求声明对齐成7,424个窗口。每个source/层固定4,096次交换尝试，三个种子沿用旧协议，不按结果增加尝试或种子。

| 条件 | 超过4个逻辑组的token | Dispatch副本 | 相对原始变化 | 能说明什么 |
|---|---|---|---|---|
| 原始连续放置 | 0 / 29,696 | 69,409 | 基准 | 原始数据满足参考组数必要条件 |
| 旧无约束交换，种子01 | 23,594 | 79,599 | +14.681% | 数学扰动超出参考条件，不能推广为模型内变化 |
| 旧无约束交换，种子02 | 23,717 | 79,600 | +14.683% | 同上 |
| 旧无约束交换，种子03 | 23,450 | 79,432 | +14.441% | 同上 |
| 新cap4，种子01 | 0 | 68,733 | −0.974% | 保持边际热度且满足组数上限，副本仍可变化 |
| 新cap4，种子02 | 0 | 68,651 | −1.092% | 同上 |
| 新cap4，种子03 | 0 | 68,672 | −1.062% | 同上 |
| 新within32，三个种子 | 均为0 | 均为69,409 | 均为0 | 组内改变具体专家，完整通信矩阵保持不变 |

cap4表示双边交换后两个token都最多覆盖4个逻辑组；within32表示只交换同一逻辑组内的专家。两者都逐source/层保持每个专家被选中的总次数。全部旧交换与这六个新条件的逐专家远端贡献总数仍为176,567，不能用这个总数代替按目的rank去重的流量。

within32三个条件分别改变29,550、29,541、29,518条token的具体专家集合，但22,272个窗口的完整4×4矩阵、每token的目的rank计数都与原始相同。原因可以直接解释：连续64专家/rank使每个32专家组整体同址；同组内部换专家不会改变物理去向。这是有效负对照，不是算法未找到收益。

cap4三个条件分别改变7,261、7,256、7,282个窗口矩阵。原始有29,001条token正好覆盖4组；cap4后正好覆盖4组的数量分别为27,106、27,192、27,095。只限制上限并不保持每token逻辑组数量或具体组集合，下降不能简单归因于唯一因素，也不能称为“随机路由更省网络”。

两种交换使用相同的随机提议规则和种子，额外拒绝会改变后续状态与接受路径。有限次交换没有均匀采样或混合保证；必要组数条件没有约束完整分数排序、输出准确率和模型可执行性。这六个条件是结构对照，不是新模型生成的真实请求。

## 三、为何之前的LPT放置通信增加

在读取本轮诊断数值前，已将检查原逻辑组是否保持同址写入协议。对58层共464个逻辑组，固定放置结果如下。

| 已有放置 | 逻辑组横跨1个rank | 横跨3个rank | 横跨4个rank |
|---|---|---|---|
| 连续64专家/rank | 464 | 0 | 0 |
| 全Prefill计数LPT | 0 | 0 | 464 |
| 尾部Prefill计数LPT | 0 | 4 | 460 |

LPT按单专家计数平衡计算负载，几乎把所有原逻辑组拆散。这为此前计算最大输入下降、Dispatch副本上升提供了结构解释，但不是一次隔离所有因素的因果消融。放置本身不违反逻辑路由限制；限制物理共址也不应被伪装成模型必须遵守的条件。

已有精确覆盖下界表明，固定这些LPT分组后，仅换group→rank排列也无法消除其与连续放置的副本差距。因此不能把“换节点”当作足够的改进方法；是否重分组需要对照已有方法、计算与容量约束、迁移成本和真实执行结果。

## 四、最接近的已有工作已经做到哪里

本轮取得并读取MoETuner固定v1原文。它是Seokjin Go与Divya Mahajan的2025年预印本；以下按该版本内容说明，不把预印本状态写成会议录用，不推断后续版本。

| 工作 | 已核对的目标、输入与约束 | 与本研究的关系 |
|---|---|---|
| Patterns behind Chaos，固定v5 | 已明确专家共激活、DeepSeek组限制、Prefill信息、专家分离带来的计算/通信权衡以及拓扑与batch影响 | 热点、共选与该权衡不是本项目创新；其计数放置已作为强基线适配 |
| MoETuner，固定v1第4节 | 专家历史负载与跨相邻层路由关系；两阶段先平衡专家簇负载，再分配簇到GPU；第二阶段使用GPU对带宽，考虑专家总量平衡与簇/GPU一一映射 | “同时考虑计算和通信”“用带宽优化专家放置”均已有；不能只与连续放置比较后宣称新颖 |
| MoETuner，固定v1第5节 | Mixtral-8×7B，EP4；8卡用4EP×2TP，16卡用4EP×4TP；H100单节点/H200双节点；Megatron-LM改造、Gurobi 2.5%容差 | 它的16卡实验不等于EP16；与我们的R1 Top8/direct去重并非同一通信定义，需做语义一致的适配 |
| 当前联合仿真与研究 | 已有原生ns-3持久字节传输、路径/端口审计和真实路由输入；本轮检查任务是否保留参考路由结构 | 平台能力支持机制研究，但不等于现代DeepEP完整性能模型、硬件校准或千卡论文证据 |

MoETuner的路由关系主要描述相邻MoE层之间专家转换；本轮检查的是同一层一个token的专家集合及其去重目的集合。不能把跨层专家对矩阵直接替代为层内共选图，也不能称两者只换一个目标函数即可公平比较。

MoETuner正文公式按GPU对带宽建模；本轮没有在这些公式中核对到逐交换机端口队列项。这个有限事实不等于证明其完整实现没有网络优化。本文也未取得并执行其优化代码。公式中max作用范围、乘积线性化与部分约束的实现细节，不能靠自行补写后冠以“原版复现”。

## 五、网络主线下一步怎样推进

最终要回答的问题应是：在真实路由约束、内存和计算容量、通信库执行语义与固定网络资源下，如何可靠预测并降低Scale-Out推理通信尾部。拓扑、multi-rail、专家放置和batch是实验维度，不能各自变成堆功能的论文贡献。

近期首先完成近邻基线适配定义：区分跨层与层内统计，核实MoETuner、拓扑感知MoE方法的实现与适用场景。若强基线已经解决候选问题，正常收缩方向。不得将本轮约1%的离线副本变化当作优化收益。

第二步补独立请求与更大batch留出。四份MMLU请求不能复制成千卡生产样本，也不能支持训练热点结论。新请求采集尚未成功；代码已发现并修正mmlu下还有subject子目录的递归查询问题，但没有远端重试或取得新数据。旧失败记录和当时源码保留。

第三步在基线与负载就绪后预先限定网络判别矩阵：先在同一通信库语义下比较按GPU对带宽、按共享物理端口服务量、实际包级完成三种判断，检查方法排序是否在留出请求、ECMP种子与非对称上层带宽下稳定。已有小场景证明总副本相同可以有不同路径负担，但这本身是已知网络规律，尚不是新贡献。

若发现稳定且足够大的排序错误，再研究路由结构与共享链路约束下的方法，并与容量、迁移成本、简单规则和已有强基线比较；若差异消失，就保留负结果，不继续制造热点或削弱基线。现代库控制操作、provider反馈、self-peer语义与硬件校准不足仍须补齐，不能用自定义事务或ACK完成冒充现代GIN成本。

规模验证最后按独立平台任务推进。已有512卡参考执行不能外推为千卡完整推理；1024卡既有长工作量超时仍未解决。新的拓扑或连接规模先有明确资源预算和独立功能验收，再进入研究，不扩大本轮离线条件来充数。

## 六、证据与复现边界

独立检查回查四原件、旧hash与旧统计，枚举14条件共103,936个窗口、1,662,976个矩阵项、415,744条token选择；核对2,088个source/层边际单元与89,088条within32组计数。换工作目录重复准备的12份非执行日志产物逐字节一致。没有重写旧报告、原始结果或归档。

本轮成功取得MoETuner v1 HTML（218,757B），模型元数据请求20秒超时且0B，没有切源重试；历史collector身份仍未知。所有实验命令60秒、RSS1GiB、地址空间2GiB、单阶段32MiB、新产物64MiB、累计128MiB，磁盘预留8GiB；实际命令、峰值和失败记录见执行摘要。
