# 千端点持久网络容量与完整推理边界

本轮已经完成1024端点的原生包级共享网络执行：256个EP4组、3072条有向持久连接，在同一个Simulator完成两轮短合成程序。它证明这条入口可以实际承载千端点及跨轮连接状态；没有执行1024张实体GPU，没有完整MoE推理或现代GIN校准，也没有证明论文主创新。

## 原来的问题

历史完整Qwen3模型多组执行已经完成256/512卡，两种后端表示的1024卡都在600秒内未完成。因此不能将已有拓扑生成、通信量核算或这个新短程序，写成历史完整模型已经通过。

当前持久入口另有独立限制：Python/native/对象共同只允许128连接和8192工作；Python的验证描述符也间接限制128条，实际执行又被夹到1GiB宿主内存。千端点EP4分组需要3072条有向连接，两轮前后All-to-All加本地节点需要16384个节点；这些小例保护会在网络执行前挡住输入。它们不是GPU、NIC或协议的硬件上限。

新增v4只在显式声明时支持4096连接、65536节点和2000000次全网链路发送事件，并使用协议已验证的宿主RSS/地址预算。旧格式计数及夹限保留。实际物理NIC与plane在预检检查，普通消息probe仍保持默认128条，持久v4的非执行验证描述符才使用新声明。新Limits布局的三个入口及其消费者全部重新编译，不混用旧对象布局。

## 这次怎样执行

目标拓扑为8 Pod、32 ToR、16 Agg、2 Core、1104链路，各层100Gbps/1us，无机内bypass。每组四个rank跨四个Pod，组与组在上层交换机/链路共享物理资源；没有逐组独立跑完再相加。单ToR接入/上联比16:1，Pod接入/跨Pod出口比64:1，是明确的有超售参考输入，不能作为生产网络容量推荐。

每轮每组所有非self对先发送768B；rank等自己的全部实际入站及出站ACK后执行100ns声明local，然后做第二阶段All-to-All，完成本rank消费后才进入下一轮。没有固定后续通信时刻，3072条QP各创建一次，序号跨四次写连续，不重置拥塞状态。100ns和768B都只是合成功能参数，不是专家计算或现代token布局的实测值。

目标完成12288次写、4096个本地节点，实际12288个源包/9437184B有效负载；数据与ACK共147456次物理链路发送。模拟结束77,464ns，只描述本短程序。命令用时18.38秒、采样进程树峰值约2.20GiB；与历史完整48层/两轮推理的工作量不同，不能计算加速比或由两者拟合复杂度。

独立检查覆盖全部49152条端点捕获事件，按实际包头和端口识别流、重建接收/ACK前缀，再核对发布、队列信用、本地FIFO和QP寿命。中间交换机未全量逐包保存，路径只核对独立最短跳数对应的全网端口字节守恒；不能把它称为全部实际ECMP路径还原。细节与原始证据入口见[容量验收](../../fixtures/persistent_scale/README.md)。

## 研究上还缺什么

本轮把“可填写千端点”和“实际执行千端点短程序”分开，并补齐后者。它没有消除完整推理、长程序、大报文/多batch、单组大EP、真实热点/共选、现代self-peer与目标GPU可见性的缺项。四源路由不能复制成独立生产请求，A100标签也不能作为现代Hopper/GIN的校准。

后续研究仍须先接完整应用必要依赖，采用选择重传、合理恢复限速/公平队列及常见通信排程强基线，判断残余网络等待是否改变应用完成。资源评价必须保留必要状态与同等采集口径，不能用短消息、小EP或删控制请求换取“可扩展”。千卡完整模型的既有超时继续保留；需要先定位实际执行瓶颈并提出保持行为的改动，才考虑新的受控目标实验，不能简单加时重试。
