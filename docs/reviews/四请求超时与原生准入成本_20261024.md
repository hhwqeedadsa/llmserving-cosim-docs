# 四请求超时：整批校验不是目前最有力的解释

原四卡调用在宿主运行60秒后被预算终止，没有最终网络结果。本轮使用这次失败已保存的238对真实交互，在同一O0编译配置下调用原C++准入函数一次，没有重跑网络。这样先检查一个可以独立量化的解释：每次都校验全部已登记任务，是否单独就足以耗尽预算。

| 测量部分 | 238个候选累计宿主时间 | 累计线程CPU时间 |
|---|---:|---:|
| 复制并追加本次任务 | 0.187秒 | 0.181秒 |
| 完整候选校验 | 2.201秒 | 2.135秒 |
| 回调订阅校验 | 0.076秒 | 0.072秒 |
| 合计 | 2.464秒 | 2.387秒 |

全部候选通过原校验，最后145节点程序与238条实际COMMIT组成的程序完整相同；每条命令的节点数、新增数、已收到回调数和订阅数独立核对。八个实际加载的原生库hash不变。没有删必要操作、提高256次交互上限、调整模型或改编译优化。

该结果削弱“完整准入单独导致60秒超时”的解释。2.464秒约为原60.148秒观测的4.1%，这个比值只是两个测量的数量级比较，不能写成历史运行的精确CPU占比；原运行的负载、缓存和线程调度没有被同步剖析。本轮也没有测量每次进度通知的全量状态扫描、Python前端运行时推进、控制管道等待或实际网络事件处理，不能把剩下的57秒全部算给其中任意一项。

下一步应在实际联合执行中加有界、可选的分区宿主计时，并在超时前持续保存最近进度；默认数据包、回调和仿真时钟语义保持。先区分时间花在前端、原生状态处理还是实际事件处理，再修证据指向的最小瓶颈。之后仍需用原四份路由、原模型和全部Dispatch—计算—Combine依赖完成一次完整调用，不能以本次238条已发生的前缀通过替代。

本轮是仿真器系统诊断，不是新的网络优化机制，也不构成A类论文贡献。它的价值是排除一个过强归因，避免为了追求通过而删安全校验或扩大限额。网络恢复对健康请求关键路径的影响、同资源强基线、硬件校准、独立负载和完整千卡验证仍是后续研究门槛。证据入口见[诊断目录](../../fixtures/native_admission_cost/README.md)。
