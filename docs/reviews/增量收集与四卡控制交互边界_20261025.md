# 少做重复扫描之后，四卡仿真卡在了哪里

这轮改的是仿真器宿主程序的状态收集开销，服务于完整应用和后续网络鲁棒性研究；没有优化被模拟网络，也没有形成论文主创新。

## 实际改动及等价证据

原来每次网络通知都会把所有操作转成JSON，再寻找刚发生的回调。现在操作状态实际变化时登记id，只构造这些行；网络通知、本地条件、队列屏障、内存/资源和最后的全量报告继续保留。按原id、阶段和稳定时间顺序交付，不能因同纳秒就合并或重排。

提交、准备、发布、目标应用、请求确认、原子回复、自服务起止和前缀退休均登记变化。小型正常及真实丢包场景使用独立全量快照逐次核对，检查是否漏标、重复或改变当前值。生产程序不包含这项全量影子扫描。事务对象及两个直接消费者全部重新编译，原PersistentStreams、Fabric、八库及O0构建条件固定。

三组正常/计时正常/丢包的全部网络结果、现代快照和原始控制文本与原记录一致，只规范化已核hash的八库路径；健康/故障仿真结束仍为105,621/123,921ns。健康开启计时场景仍收集1,368次，该阶段exclusive墙钟约0.036秒，上一轮同一输入全量构造约1.37秒。两者都是含记录器开销的单次诊断，不能作为生产性能或整个仿真器的加速比。

## 下一项应解决的具体问题

先做离线因果核验：被抑制的回调批次必须保留原推进时刻、完整顺序及必要控制边界。前端逐批处理，检查每个被跳过的边界是否本应产生新的原生工作；任何任务提交时刻、同纳秒顺序、slot绑定或完整现代日志改变都应否决。只有这些事实一致，才考虑以有界批次传输减少同步交互，并回到原四卡验收。不能只将多个批次按最后时刻交给前端，也不通过提高交互上限掩盖结构问题。

另一方面，高频宿主观测需要有界聚合并说明覆盖；逐包分析也应选择完整的小窗口或记录明确的遗漏，避免把截断数据当完整证据。这两件事分别验证，不混成一组收益。

独立恢复已从已核验归档复制Python根，在空cwd使用包内程序/八库完成H512小例；152事件、46原生任务、45交互，结束61,918ns。三份完整对照和四卡失败摘要在新源码根重算逐字节一致。这只证明同主机ABI兼容迁移，不是干净原生构建或四卡替代。

## 与研究目标的关系

增量收集是系统实现改进，不是新网络机制。要回答“恢复流量是否拖慢健康MoE请求、怎样在同资源条件下减轻影响”，仍先要完成应用屏障，再比较选择重传、合理恢复限速/公平队列、通用通信调度及强退出等基线。独立代表性负载、GPU/provider校准和完整千卡执行均未就绪，不能据当前功能例宣称A类或最佳论文水平。证据入口见[本轮验收](../../fixtures/incremental_progress/README.md)。
