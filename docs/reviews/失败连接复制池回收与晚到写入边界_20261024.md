# 失败连接复制池回收与晚到写入边界

本轮修正了一个会夸大故障传播范围的平台问题：失败连接已经停止发包，却继续占满同GPU的共享复制池，导致健康连接也不能发送。新增显式配置，在实际源隔离后归还本地重传副本。健康连接随真实资源释放继续执行，失败连接没有获得虚构的ACK或完成。

这属于网络执行载体的资源生命周期修正，不能作为新恢复算法或论文主贡献。它的研究意义是去掉一个人为阻塞，避免把旧仿真器中的保留行为误判为网络恢复的必然成本。

## 为什么可以回收，又为什么不能复用远端地址

当前事务读取注册源窗口，复制到`Work.payload`；构造原生`Packet(buffer,size)`时，包再次拥有独立字节。重试耗尽并隔离源后，程序先移除调度中的QP、取消源计时器，再释放这一stream的副本。这里的QP是持久连接的发送队列对象。

仅仅清空副本不会改变已经构造的包，也不会撤销目标已经执行的写入。应用源窗口的lease（防止过早改写的引用保护）、目标去重缓存、队列完成信用分别有自己的释放条件，仍然保留。未发布的失败连接操作不能再捕获源数据或占用复制池。

最直接的反例来自本轮实际包执行：1μs计时器条件下，源在3,000ns判定失败并丢弃副本；先前发出的包仍在6,036ns写入目标。此时事务没有ACK或完成，源lease仍在。**本地停止和释放复制品不证明远端旧访问已经退出。** 如果随后把同一目标地址交给新请求，仍需要另外证明旧包不能覆盖新内容。

## 实际对照说明了什么

8GPU小Clos、GPU0的两条连接共享40B池，每条put是32B功能帧头加8B数据。失败连接持续丢数据或最终ACK，健康连接准备发送，池在失败前已被占满。旧默认保留副本，健康操作2无法发布，依赖它的操作3甚至没有提交。

开启可选策略后，两种丢失条件都在60μs真正隔离源并归还40B；健康操作2、3分别在72.060μs、84.120μs完成。失败操作及其后续操作保持未完成或未发布；整场仍在5ms截止退出1，结果为部分成功。这是证明局部资源隔离的功能用例，不能将两个时间当作生产MoE速度收益。

旧/新默认完整结果逐字节相同；健康开启条件只增加声明的元数据，原执行字段相同。在线会话先原子拒绝超目标缓存批次，再接受原有效批次。49项不同单元、两次公开回归及恢复后的公开健康网络通过。8份独立审计从真实包、池事件和窗口重放核验；篡改包、峰值、丢弃时刻或失败ACK会被拒绝。详见[验收与复核方法](../../fixtures/isolated_payload_release/README.md)。

## 对网络与系统研究的影响

1. 后续故障实验必须分别报告复制池、源窗口保护、目标缓存、在途包与应用完成，不能用一个“失败资源已释放”布尔值代替。当前`failed_resources_released=false`仍正确。
2. 下一步连续有限资源恢复需要证明远端旧访问退出，然后才能安全复用窗口或淘汰缓存。单纯释放本地副本只消除了其中一种阻塞。
3. 比较恢复方案时保持资源总量、可用信息和真实完成条件一致。旧版永久占池的实现不是足够强的研究基线，不能以它制造新方案收益。
4. 代表性MoE依赖、现代通信库及provider的完成/撤权语义、硬件校准和大规模泛化仍缺。当前MRT1是功能put载体，不能标成现代GIN、RoCE原子成本或千卡生产结果。

没有启动新的研究矩阵、安装下载、GPU执行或修改依赖；本轮只做平台增量和必要验收，保留两处测试/检查器修正记录。资源统计、源码身份和持久检查点见[收尾收据](../../fixtures/isolated_payload_release/closeout.json)。本机持久副本不是异机备份。整体论文目标继续进行中。
