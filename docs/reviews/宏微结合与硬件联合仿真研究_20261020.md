# MoE Scale-Out：宏观网络、微观硬件与系统级差异

2026-10-20，北京时间。面向MoE推理网络研究的方案评审材料。

**建议保留ns-3作为跨服务器网络后端，先补端点资源与完成语义，再按研究需要引入局部硬件仿真。** 当前系统已经有请求调度、任务依赖和逐包网络反馈；最需要核实的是GPU—NIC路径与计算/通信资源竞争是否改变瓶颈及优化方案排序。不能将“逐包”视为“完整硬件精确”，也不能把ns-3说成原则上无法表达这些行为。

本文完成源码核查、公开资料比对、只读硬件盘点和实验设计；**未实施新的端点模型、GPU微架构仿真、硬件性能测量或优化对照实验**。下文的候选机制不是已发现的实机瓶颈，论文创新性也尚未得到实验确认。

## 1. 对业内建议的具体回应

| 建议 | 应落实为什么 | 判定是否做成 |
|---|---|---|
| 宏观、微观必须结合 | 从请求/Decode轮次、EP放置和全网竞争，下探到关键GPU—NIC路径、DMA、缓冲及通信核；再把局部完成与资源释放返回上层 | 能解释某次轮次变慢的实际前驱和资源占用者；局部改动对整轮的作用有对照，而非仅展示队列图 |
| 可以考虑硬件仿真 | 区分测量校准的资源服务模型、GPU周期级模拟、整机协同仿真和RTL/FPGA仿真 | 明确目标设备、软件与形状，说明模拟了什么、由什么校准、遗漏什么及运行成本 |
| 关注纯ns-3的弱点 | 审查给定模型的边界：端点是否理想化、流量生成是否固定、完成是否等于可消费、资源是否共享 | 对每个缺项给出源码依据和可观测后果；不把框架可扩展性与现成模型能力混为一谈 |
| difference是否solid | 证明缺项会在实际相关条件下改变性能预测或决策，而且已有较强基线不能消除差异 | 经留出配置校准、消融和反例验证；仅有接线、更多参数或一组人为热点不算研究贡献 |

最终服务对象仍是**MoE推理的跨服务器网络部署与通信优化**：解释专家热点如何落到GPU/NIC/交换端口，判断网络容量、通信组织和端点节奏各自造成多少关键等待。硬件细化围绕这个问题展开，不扩张为通用GPU设计平台。

## 2. “纯ns-3仿不出来”应怎样准确理解

需要分三层讨论：

1. **ns-3框架**提供离散事件、对象和接口，可以新增资源模型或与其他模拟器耦合。这里没有证据支持“ns-3永远无法仿真某个系统问题”。
2. **锁定的RDMA模型**表达分包、QP、链路、交换队列、ACK/NACK、ECN/PFC和DCQCN等网络行为；不自动等价于真实GPU、NIC与交换ASIC的内部实现。
3. **本仓库Scale-Out入口**用有限Decode请求和声明计算成本生成依赖图，接入上述网络模型。它已经超出固定发包时刻的独立网络回放，但没有补齐完整端侧硬件路径。

因此，准确的问题是：**“给定目前的模型和输入，哪些系统因果链不能自然产生？”**不是“换一个模拟器名字，是否就更真实”。同样，阿里派生库、SimAI、ASTRA各有不同版本和配置，不能用未核查能力构造我们的独有优势。既有固定版本比较见[网络后端核查](scaleout_ns3_backends_20261015.md)，其中阶段状态是2026-10-15历史，当前能力以下面的源码核查为准。

### 2.1 当前缺项及其可能影响

| 对象 | 当前Scale-Out实现 | 可能漏掉的系统现象 | 定性结论 |
|---|---|---|---|
| GPU计算和打包 | COMP节点使用声明耗时；专家阶段按贡献数乘参考成本 | 负载形状、缓存、SM占用、HBM竞争改变计算与发包节奏 | 已证实是抽象，影响大小待测 |
| GPU—NIC搬运 | SEND就绪后创建QP；网络按剩余字节生成包 | PCIe拓扑、DMA读写、共享根端口、QP/WQE服务限制 | 没有显式联合资源服务模型，不代表NIC模型完全没有调度 |
| 接收数据就绪 | RDMA接收端连续接受字节达到消息大小即回调 | NIC接收、GPU内存写入、可见性与消费者使用之间的区别 | 不能把当前回调标成真实GPU数据可见 |
| 有限接收/转发缓冲 | 无与GPU消费进度相连的显式容量及信用释放 | 多轮/分块流水时的发送节流、端侧积压及可能的上游反压 | 当前严格阶段依赖可能使该缺项不触发，不能预设必有收益 |
| 机内网络 | 每GPU每方向共享服务的分块无阻塞织构抽象 | 实际NVLink/PCIe路由、共享桥、信用和中继开销 | 已有共享资源，不能称为完全无竞争；仍非真实协议级模型 |
| 通信库 | 按GPU对聚合的per-expert-copy直接传输 | 目的节点去重、NVLink—RDMA转发、通道/QP复用、分块流水与归约 | 不是DeepEP/NCCL完整复现，字节和时序都可能不同 |
| QP与拥塞控制状态 | 每条逻辑消息新建发送QP，确认完成后删除；初速为NIC速率 | 长期QP复用、拥塞控制状态跨消息延续、WQE提交与设备队列成本 | 持续Fabric不等于发送QP状态持续；可能影响短消息突发，收益待测 |
| 服务动态 | 有完成回传；当前有限请求在起点就绪、ready-KV Decode | 持续到达、补入请求、Prefill混合、KV迁移和抢占改变流量 | 不能宣称已经预测完整在线服务p99或TTFT |
| 交换机与NIC微架构 | 有队列/MMU/CC研究模型 | ASIC内部仲裁、流水线、真实共享缓冲划分及固件细节 | 现有源代码不能证明与某款商业设备逐周期一致 |
| 故障恢复 | 协议探针覆盖指定中间包与尾包丢失情况 | 尾包、ACK丢失、RTO和完整恢复 | 已知尾包不能自动恢复；研究范围仍限定无故障拥塞 |

网络流量变少与网络更快也不能混用：改变通信组织可能改变字节数量；改变QP数或消息端口可能改变ECMP路径。两类实验需要分别核算，不能只看一个完成时间。

### 2.2 本次查到的具体代码事实

源码基线为主仓`0b37b6a`、ASTRA `0210e24bf76f49b4111a73d1e419f6fee4f3f0b6`、原生ns-3 `3964b1d41cb5f7b51004c316b0eae1a3713c2498`。精确摘录、行号与文件哈希在[code_evidence.json](../review_artifacts/hardware_systems_20261020/code_evidence.json)。

- [消息接收](../../backend/rdma/fabric.cc)：`CheckReceived()`检查`ReceiverNextExpectedSeq >= bytes`。这证明顺序接收完成，不包含独立的HBM写服务或CUDA可见性模型。
- [任务图生成](../../python/moe_ub_cosim/scaleout_service.py)：pack、attention、experts、merge分别使用声明成本；一个GPU上的专家节点等待相应入站消息完成，没有表达真实通信库的逐tile专家计算流水。
- [原生RDMA](../../third_party/LLMServingSim/astra-sim/extern/network_backend/ns-3/src/point-to-point/model/rdma-hw.cc)：`GetNxtPacket()`直接按剩余字节创建Packet；这里没有先通过GPU内存读服务再取到payload的事件。
- 同一原生文件确有`PCIePause()`，但它按`TotalPauseTimes`计数，固定暂停10微秒，恢复后再过1000微秒重新允许暂停。它不是根据PCIe/HBM占用与服务率产生的硬件反压；[适配器](../../backend/rdma/fabric.cc)将`TotalPauseTimes`显式设为0。**有PCIe命名不等于建模了PCIe。**
- ASTRA的`HardwareResource`有计算/通信资源记账；`Workload::issue_replay()`会按给定runtime推进事件。因此不应说ASTRA“没有资源和依赖”。当前入口没有提供SM份额、HBM带宽和DMA共享服务，不能从已有记账推断这些竞争已被模拟。
- [联合服务](../../backend/rdma/service.cc)给每rank创建Sys，当前内存API列表为空；所有组共用同一Fabric和ns-3时钟。[适配器](../../backend/rdma/astra_adapter.cc)分别处理接收与发送完成，下一轮经前端回传推进。它已经有系统反馈，这部分不能重新包装为新颖性。

### 2.3 网络内部也有硬件抽象，不能只补GPU

- 原生`QbbChannel::TransmitStart()`在`txTime + link_delay`后交付完整Packet，交换机收到后才执行`SendToDev()`。这是当前整包转发的事件路径，没有在收到部分头部后提前转发的cut-through流水。不同包长、跳数和负载下，应核查这种抽象是否改变基线时延与策略比较；不能直接套用某款交换机标称延迟。
- 当前线上字节按模型Packet大小计算，报告明确不含未建模的Ethernet preamble、FCS和IFG；原生分包还使用PPP头部。它是RDMA数据中心研究模型，不是完整以太网逐比特帧实现。大量短包时，额外开销尤其需要统一口径。
- 原生NIC对可发送QP进行轮转调度，并优先处理相应控制队列。因此NIC并不是无限并行发送；需要进一步核对真实NIC的优先级、限速及QP调度，不能重复添加已有线路服务。
- 每消息QP由`AddQueuePair()`初始化`m_rate`和目标速率，`QpComplete()`取消该QP的DCQCN定时事件并删除发送状态。这与多消息复用同一QP的机制不同，但当前没有模拟真实控制面的每次QP握手成本。后续应先核查目标通信库的连接/传输类型，再决定是否需要持久QP；改变QP/端口布局时还要区分ECMP变化。

这些是明确可定位的模型差异，不等于已经证明存在显著性能误差。该路径及QP生命周期一并保存在源码证据中。

## 3. 宏观与微观应如何连接

```text
宏观：请求与batch → 专家选择/放置 → EP通信依赖 → 轮次/请求完成
                              ↓                     ↑
端点：打包/通信核 → 有限发送资源 → GPU内存读/DMA → NIC注入
                                                     ↓
网络：实际分包 → ToR/Agg/Core → 排队/ECN/PFC → 目的NIC
                                                     ↓
端点：DMA/内存写 → 数据可见/协议同步 → 解包/归约 → 专家消费
```

上图的端点硬件细节是**拟扩展内容**，不是当前全部可用的调用链。GPUDirect RDMA可能直接访问GPU内存，不应默认插入一次CPU内存拷贝；具体路径需要由目标硬件和软件配置确定。

统一关联至少保留`request/group/step/layer/phase/message/chunk`身份，以及GPU、NIC、端口和资源ID。算法可以读取哪些观测与研究者使用的内部真值继续分开；不能把真值暴露给优化器，或为了记录而改变消息、优先级与选路。

宏观指标用有限片段的轮次完成和生成间隔；微观指标包括发包前等待、端点缓冲占用、逐跳队列、PFC区间和速率反馈。**累计等待、关键路径上的暴露等待、能够被干预消除的业务损失是三个不同的量。**不得把各层或各资源的时间简单相加；通信与计算可能重叠，同一段等待也可能被多处记录。

此前独立Scale-Up实验已有一个提醒：[完整首轮对照](../../experiments/scaleup_observability/results-representative.md)中，目标出口队列积分增加57.60%，整轮仅增加0.1532%。这是UB参考场景中的仿真证据，不是当前RoCE实机结论；它说明我们已经遇到“局部变化大、业务变化小”的情况，宏微结合必须以实际依赖解释，而非仅看网络曲线。

## 4. 优先问题一：热点落到端点以后，瓶颈是否仍在交换网络

**问题表述：同样的专家选择和逻辑通信量，不同GPU—NIC路径、DMA/内存服务与有限缓冲，会不会改变网络拥塞的位置及有效优化手段？**

NVIDIA的[GPUDirect RDMA文档](https://docs.nvidia.com/cuda/gpudirect-rdma/index.html#supported-systems)讨论了PCIe连接条件；同文“Supported Systems”及“Synchronization and Memory Ordering”说明拓扑与可见性约束。原始文档包含平台与API上下文，不能将其理解为所有现代GPU网络都必须靠CPU同步。对目标NVSHMEM/IBGDA/NCCL实现，应核查其具体同步原语。

### 4.1 必须分开的事件与容量

| 项目 | 精确定义 | 当前情况/拟新增 |
|---|---|---|
| 连续网络接收 | 网络协议接受了完整且连续的消息字节 | 当前有 |
| GPU数据可见 | 目标内存服务与所选协议要求的可见性条件满足 | 拟建模；不是加一个任意常数 |
| 消费完成 | 专家计算、解包或归约不再使用该缓冲片段 | 由相应消费者的实际完成事件决定 |
| 发送完成 | 所选传输协议允许发送方释放或复用资源 | 当前远端消息按完整ACK，不应擅自改成等待消费者计算结束 |
| NIC/DMA暂存容量 | 接收数据到达而DMA未排空的有限资源 | 是否存在及如何反压，依目标硬件/协议验证 |
| GPU通信环形缓冲 | 软件/硬件约定的可复用通信空间 | 必须说明信用、覆盖保护与何时归还；不等同于KV容量 |

**GPU计算慢不必然导致PFC。**如果数据已经写入预分配且足够大的GPU目标缓冲，消费者暂时未读取不一定占住NIC接收队列。只有验证了相关缓冲的占用、释放与上游准入关系，才能声称发生了端侧反压；应用信用节流、NIC接收阻塞和交换机PFC也要分别记录。

当前每组一轮完成后才提交下一轮，层内也有较强阶段依赖。如果缓冲足够容纳一整个阶段，消费者释放速度可能根本不限制本场景。若要研究更深流水，应先明确扩展通信组织和依赖，而不是在原场景凭空制造缓冲溢出。

### 4.2 对照与否定条件

| 竞争解释 | 保持不变并做什么干预 | 应观察什么 | 什么会削弱该解释 |
|---|---|---|---|
| 上联总容量不足 | 固定端点服务与任务，改变上联容量 | 上联积压及关键等待随容量变化 | 上联有明显余量，扩大容量也不能缩短关键等待 |
| GPU—NIC/DMA服务不足 | 固定外部网络，比较已测量的亲和路径或服务曲线 | NIC空闲但发送前积压，或接收/DMA排空受限 | 端点测量无差异，工作量远低于服务上界 |
| 可复用缓冲成为瓶颈 | 固定服务率和总资源，比较合法流水深度与容量 | 缓冲满、信用耗尽、释放与继续发送可逐事件对应 | 同步阶段下容量从未用满；仅延迟回调而网络行为不变 |
| 路由碰撞而非端点热点 | 固定专家与字节，使用预先确定的多个ECMP种子 | 不同种子下拥塞位置/排序是否稳定 | 收益只存在于一个哈希布局 |

先在单机验证GPU内存与亲和路径，再在有条件的两台服务器上验证RDMA；使用同一来源的真实路由，增设均匀及打乱路由对照。只改变一个资源参数并不自动保证公平：应同时检查NIC总容量、内存容量、路径、请求量和字节拆分。

**该问题的预期产出**是端点与网络瓶颈的可辨识方法，以及在等资源条件下有依据的放置/转发或注入策略。当前证据只证明模型缺项和真实实现存在相关约束，尚不能断言它们在我们的工作负载中主导性能。

## 5. 优先问题二：通信在网络上更快，为什么整轮可能更慢

**问题表述：通信核、专家计算和打包/归约争用SM与HBM时，调整通信并发、分块及中继，是否会改变端到端方案排序？**

实际通信可能消耗SM、读写HBM，并受通信流与计算流的同步影响。提高通信核并发可能改善NIC利用率，也可能挤占专家计算；更小的块可提前启动网络，但也可能增加元数据、同步和调度成本。收益方向需要测量，不预设“细分一定更快”。

公开实现给出了具体依据：

- [DeepEP v1.2.1固定版本](https://github.com/deepseek-ai/DeepEP/tree/9af0e0d0e74f3577af1979c9b9e1ac2cad0104ee)支持通信SM数量控制；`Buffer`接口还暴露NVLink/RDMA缓冲、QP及异步完成参数。该版本文档也描述低延迟hook路径的特殊资源行为，不能概括为所有通信阶段持续占用SM。
- 本次读取的[DeepEP main](https://github.com/deepseek-ai/DeepEP)已是V2路线：统一接口、NCCL Gin后端，文档明确EP需要GPU SM并要求Hopper或更新GPU。**它与v1的NVSHMEM和零SM相关描述不能混用。**本次未安装或运行任一版本。
- 两个版本都不是“一个All-to-All字节数加固定延迟”就能等价表示的实现。README性能数字属于作者的硬件/软件条件，本文不将其带宽直接填入链路线速，也不转写为我们的测量结果。

### 5.1 应比较的模型层级

| 基线/候选 | 表达的内容 | 用途与限制 |
|---|---|---|
| 固定流量回放 | 预先指定消息与释放时刻，网络执行 | 隔离网络机制；难以预测改变调度后的新注入节奏 |
| 当前联合系统 | 计算声明耗时＋DAG依赖＋实际网络完成反馈 | 已能让网络影响后续任务；缺少真实通信核/计算争用 |
| 形状匹配的测量基线 | 用分阶段实测耗时替换声明值，依赖与资源不变 | 必须先作为较强基线，不能仅对比任意常数 |
| 拟增共享资源模型 | 通信/计算对SM、内存和DMA的占用及有界服务相互影响 | 只有能解释留出条件下的差异时才值得保留 |
| 局部周期级模型 | 对少量核心/形状细化指令、缓存和内存机制 | 用来诊断或生成校准数据，不直接跑千卡完整服务 |

### 5.2 最小验证方法

1. **分开测、合起来测。**对形状匹配的pack、专家GEMM、通信分别测量，再测确有合法独立工作的并发条件。独立耗时不能直接相加得到并发耗时；需要CUDA事件及可用性能计数交叉核查。
2. **固定硬件预算。**比较通信SM份额、分块大小和QP/通道配置，同时记录总SM、HBM工作量、协议元数据、缓冲及发包时间分布。QP改变了ECMP时，另做路径受控与原生选路两类评价，不能混为同一个因素。
3. **保留强基线。**对比“当前声明成本”“按形状校准但独立的成本”“共享资源模型”。训练或拟合用的形状不作为唯一验收集；保留batch、热点程度或并发深度的留出条件。
4. **评价整轮而非仅评价通信。**同时报告通信阶段、专家计算、NIC利用率、HBM/SM占用和关键等待；有限片段报告轮次/生成间隔，不冒充完整服务p99。
5. **接受反例。**如果计算和通信在目标场景几乎不争用、简单校准已足够、或网络远比端点慢，则保留简单模型，不为复杂模型寻找人为有利场景。

**该问题的预期产出**是能预测网络优化在什么负载/设备条件下有效或失效的模型与策略。仅增加通信核占用参数不是论文贡献；如果其不能改善误差、方案排序或部署决策，就没有足够理由持续细化。

## 6. 硬件仿真有哪些可行选择

表中“支持”表示本次读取的文档或源码说明，不表示本机完成构建、兼容所有算子或已达到作者报告精度。最新分支以2026-10-20抓取的内容哈希为准，来源与失败请求均保留在[sources.json](../review_artifacts/hardware_systems_20261020/sources.json)，关键摘录见[source_excerpts.json](../review_artifacts/hardware_systems_20261020/source_excerpts.json)。

| 路线/平台 | 适合解决的问题 | 必须具备的输入/条件 | 对本项目的选择 |
|---|---|---|---|
| 测量校准的离散事件资源模型 | GPU—NIC服务、有限缓冲、通信/计算共享与宏观反馈 | 匹配设备、路径、版本、形状和并发条件的测量；准确释放事件 | **近期首选**。保留单一ns-3时间，先证明比形状校准基线更有价值 |
| [Accel-Sim](https://github.com/accel-sim/accel-sim-framework) / [GPGPU-Sim](https://github.com/gpgpu-sim/gpgpu-sim_distribution) | SM、指令执行、缓存、内存系统及通信相关kernel的局部机制 | 对应架构模型、兼容二进制/指令trace及校准；真实执行trace往往需要对应GPU | 中期少量算子/窗口。当前Accel-Sim dev文档已声明2.0 Hopper支持，不能沿用“只支持旧GPU”的判断；作者精度数字未由我们复现 |
| [gem5 GPU FS](https://www.gem5.org/documentation/general_docs/gpu_models/gpufs) | AMD GPU ISA/驱动和系统软件交互 | 匹配ROCm、磁盘镜像及受支持设备 | AMD路线的条件候选。文档是gfx9、Vega/MI系列，不是现成A100/H100模拟器；其默认CPU也不能直接称为详细CPU时序模型 |
| [SimBricks](https://github.com/simbricks/simbricks) | 主机、NIC/PCIe、设备模型与ns-3等网络的协同 | 组件模型、接口适配、同步及对应软件栈 | 联仿方法参考。已有系统级组合先例，不能宣称“把硬件接ns-3”本身新颖；没有证据证明可直接启动完整NVIDIA MoE栈 |
| [FireSim](https://github.com/firesim/firesim) | 自有或开源RTL设计的周期精确系统评价、FPGA加速 | 可综合RTL、FPGA资源及硬件/软件环境 | 长期有明确NIC/加速器硬件设计时再考虑。其千节点主要指开放SoC等目标，不等于千张商业GPU |
| RTL＋Verilator等 | 定制FIFO、仲裁器、DMA/信用控制的精确机制 | 对应RTL与验证环境；模型边界及参数有依据 | 只在提出具体硬件机制时采用；简化RTL不能冒充NVIDIA GPU或商业NIC内部实现 |

周期精确描述的是**所建模型**的执行精度，不自动保证它与目标硅片准确。指令trace也不等于周期级模型本身；固定trace对依赖数据、线程/流交错及不同并发环境的适用性需要核验。单GPU模型不能自动推导真实分布式通信库行为。

### 6.1 接入时不可省略的约束

- 先用测量或局部微架构结果建立可复用服务模型；千卡层面执行这个模型与逐包网络。离线校准提供参数或服务曲线，不把两次独立仿真的总时长相加。
- 真正在线耦合其他模拟器时，必须定义时间单位、事件顺序、同步/前瞻条件和阻塞接口，禁止处理来自“未来”的完成事件。每个执行入口仍只能有一套ns-3，不能同时链接UB和RDMA两套库。
- 明确哪些资源共享：NIC线路、PCIe桥/根端口、DMA引擎、HBM、通信SM和缓冲。已经在网络中计过的序列化、ACK或传播不能在端点再次收费。
- 消息数据就绪、协议完成与缓冲释放分别处理；一条通信只发起一次。只延迟应用回调不能自动形成上游反压。
- 模型参数必须标为测量、文献参考或假设；IB资料不能直接当作RoCE交换机/PFC的校准，GPU型号标签也不能提供PCIe/NIC亲和关系。
- 逐级评估时间、内存和磁盘成本；先局部、再多机、最后扩规模。已有千卡两次超时仍是限制，不增加细节后直接宣称千卡可用。

## 8. 怎样判断difference确实成立

分四道验收，不能用后一道的愿景代替前一道证据：

| 验收 | 需要的证据 | 当前判断 |
|---|---|---|
| 缺项真实存在 | 我们的模型源码＋真实硬件/库的原始资料 | **已具备**：端点内存服务、可见性和共享资源未表达，真实实现存在相关约束 |
| 缺项在目标负载显著 | 两机/局部实测，或已校准且边界明确的硬件仿真；与强基线比较 | **尚未验证**：不能从缺项直接推出明显误差 |
| 缺项改变网络决策 | 固定输入与等资源下，瓶颈归因、方案排序、收益范围的配对对照；留出配置与反例 | **尚未验证**：不能预先声称排序反转或端到端加速 |
| 形成新的贡献 | 相对既有MoE通信、端点建模及协同仿真工作的明确增量；机制、方法和可复现验证 | **尚未确立**：连接平台、发现热点、提高模型细度本身不足以构成论文 |

度量应同时包括绝对/相对预测误差、方案优劣排序、资源开销和误差范围。误差容忍度需要根据目标决策的差异量和重复测量波动事先确定；不在看到结果后调整阈值使方法通过。真实路由目前只有4个用户选择的请求，不能给出生产总体代表性或可靠服务p99。

如果形状匹配的简单校准已经预测正确，或微观改动对业务没有有意义的影响，应保留负结果、缩减该模型需求，回到网络容量/放置等确有证据的问题。这是路线选择，不是实验失败。

## 9. 建议实施顺序与阶段产出

| 顺序 | 工作与限定范围 | 可审查产出 | 进入下一步的条件 |
|---|---|---|---|
| 1：当前已完成 | 源码边界、版本、硬件条件和原始资料核查 | 本报告、源码摘录、来源清单与盘点 | 研究问题及缺项可定位，不作实测收益承诺 |
| 2：校准强基线 | 选定A100与软件，匹配batch/形状；先独立再并发，先机内再两机 | 测量协议、原始时间线、形状/版本/资源记录、留出配置误差 | 有相关且可重复的端点差异；活动RDMA条件另行具备 |
| 3：最小端点扩展 | 只实现已测到会影响网络的DMA/缓冲/共享服务；区分数据可见与资源释放 | 小型功能验收、无额外竞争时退化到基线、记录启停不扰动、字节守恒 | 扩展与硬件事实一致，完整依赖和反压链可解释 |
| 4：系统问题验证 | 固定路由与等资源，比较端点/网络容量、分块与通信并发；多哈希种子和反例 | 两项问题的因果对照、效果边界、开销与否定结果 | 比强基线多解释了实际相关现象或改善了决策 |
| 5：必要时局部硬件仿真 | 对仍无法辨识的SM/缓存/DMA机制选Accel-Sim、SimBricks或具体RTL | 支持范围、校准误差、组件接口及成本报告 | 新增细节改变关键结论，值得承担成本 |
| 6：扩规模与论文/系统 | 先解决当前运行成本，再验证128/256等规模，最后审查1024卡 | 有界共享网络基准、可复现系统、论文方法与实验 | 不牺牲真实性换规模，不把超时或估算写成完成 |

顺序5是条件分支，不要求为了“硬件仿真”而强行接入。如果顺序2—4已经足以回答研究问题，应直接整理系统与论文证据；如果顺序2没有支持候选，则暂停该候选并说明原因。

近期系统产出定位为**具备来源、校准口径和端点/网络解释能力的MoE联合仿真原型**。论文候选定位为**端点资源约束下的MoE网络热点诊断及通信/放置优化**；在真实影响、较强基线和新颖性证据齐备前，不锁定“已实现创新”或顶会投稿结论。
