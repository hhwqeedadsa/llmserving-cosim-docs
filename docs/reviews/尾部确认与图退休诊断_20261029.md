# 尾部确认与图退休：一个需要先验证的系统约束

本项是平台模型诊断，使用已保存的人工四卡单层单步小例；不增加网络运行，不改公共业务完成定义，不把它当生产收益实验。依据平台`a76157e45d`，机器结果见[独立核对](evidence/astra_tail_lifecycle_20261029.json)，程序见[只读诊断器](evidence/astra_tail_lifecycle_20261029.py)。

## 实际观察到什么

两个条件的声明任务、路由、成本和依赖图完全相同，仅故障从连接最后ACK丢失改为最后数据包丢失。每个条件都真实发生一次超时和256B重传。

| 时刻，单位µs | 末尾ACK丢失 | 末尾数据丢失 |
|---|---:|---:|
| 最后一份消息被目标连续接受 | 13.913 | 106.006 |
| 所有rank最后merge计算回调已结束 | 13.943 | 106.036 |
| 最后一份消息在源端获确认 | 112.030 | 112.030 |
| 整图退出，前端收到完成 | 112.030 | 112.030 |
| 最后计算回调到整图退出的间隔 | **98.087** | **5.994** |

ACK丢失条件下，rank0/1/2/3的merge回调分别在13.482/13.628/13.920/13.943µs结束；数据丢失时前三者不变，rank3变成106.036µs。相同的最终112.030µs掩盖了两种不同的等待：一种数据已经被消费者接受，另一种消费者仍在等数据。

这里的merge是声明成本的COMP节点，**不是实机GPU结果可见时刻、完整推理输出或真实通信kernel结束**。数据、通知和GPU内存序尚未在此模板表达，不能从表中直接推出业务可以在13.943µs完成。

## 原因从哪里得到

逐节点日志核对全部COMP时长与依赖后，整图末尾事件确实是message14的源SEND回调。该回调与native消息ACK时刻一致，不是从配置或预期值推测。

- [Messages::Deliver](../../backend/rdma/astra_adapter.cc)只有`op.acked`才调用发送完成；接收完成独立触发。
- [Workload退出条件](../../third_party/LLMServingSim/astra-sim/astra-sim/workload/Workload.cc)要求待执行节点和在途计算/通信均为空。`can_load_graph()`还要求无active callbacks及pending events，不能在旧图资源仍活跃时替换图。
- [Service::Pump](../../backend/rdma/service.cc)只有整组rank完成、全部消息回调配对完且资源可装新图，才向前端报告完成并提供下一轮组批机会。

因此，当前服务的`application_finished_ns`准确表示**声明观察窗口的最后图退休**；它不是“只看最后消费者计算完成”。这是一项模型/调度范围约束，不能偷偷改读数来制造收益，也不能直接认定它是生产系统缺陷。

## 为什么这会改变后续实验

此前准备研究恢复流量如何拖慢健康任务。现在应先分清三种情况：数据/通知没到；恢复流量占住健康任务共享出口；源端确认/图退休门槛阻止后继任务进入。否则可能把仿真器的轮次边界误解释为网络拥塞，甚至设计出只对这个边界有效的方法。

98.087µs是该小例的**计算回调之后、图退休之前的间隔**，不是已实现收益、严格优化上界或生产发生率。删除等待会改变发送资源、工作队列及源buffer寿命；新任务进入还会改变网络竞争，不能用离线减法替代实际执行。

## 接下来应怎样验证

1. **先对准一种通信实现。** 从固定源码核对接收通知、异步事件、发送工作完成、epilogue和buffer epoch。过去的[DeepEP语义审计](DeepEP低延迟通信语义与建模修正_20261022.md)已指出整EP图结束不自动等价于真实服务边界；不同版本和direct/hybrid路径不能混用。确认真实调用是否必须等待这份ACK，哪些资源仍不能复用。
2. **在保留源确认与安全回收的条件下做平台对照。** 若目标语义允许后继先推进，需明确多个在研图/阶段的独立身份和共享硬件资源，保留旧SEND回调、源buffer保护与epoch。不能把`can_load_graph()`断言删掉、提前归还发送槽，或换成没有相同资源约束的图执行器。
3. **区分人工机制与真实负载。** 小例仅用来证明状态转换；之后用独立真实请求、有限Decode、多组共享物理出口，分别注入数据/ACK故障，核对实际路径和资源竞争。自然MMU丢弃原因仍须补齐；故障强度与出现频率单独说明。
4. **报告净效应。** 同时比较后继启动、健康/受损任务、图退休、网络排空、重复流量、保留buffer与正常开销。强基线使用同持久传输、合理RTO和普通公平/隔离；不能把经典重传或双buffer本身作为创新。

若源码表明真实库的必要完成事件就是等待这份源确认，或实际buffer资源不允许前推，当前“提前推进”候选应收敛/关闭。若有安全重叠空间，再研究如何利用当时可获得的任务/资源状态减少干扰；本项尚未证明其新颖性或收益。

## 复核方式与限制

只读诊断器从两份保存原件重建节点时间与最后SEND，核对声明图/配置一致，并输出输入和固定源码hash。运行示例：

```bash
PYTHONPATH=python python docs/reviews/evidence/astra_tail_lifecycle_20261029.py \
  --ack-run /path/to/saved/tail-ack --data-run /path/to/saved/tail-data \
  --output /path/to/new/diagnosis.json
```

图退休当前未修改；没有优化版运行、生产数据泛化或硬件计时校准。此诊断把下一步问题从笼统“恢复很慢”收敛到可逐项验证的依赖与资源门槛，整体论文目标继续。
