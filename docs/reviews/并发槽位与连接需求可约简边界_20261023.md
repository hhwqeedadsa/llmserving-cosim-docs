# 哪些网络需求可以不枚举token槽位顺序

结论：在本次固定现代DeepEP direct、BF16、expanded layout且本地多专家归约的范围内，**Combine每条声明连接的token操作数可以由计数精确计算，具体token的连接归属仍依赖实际槽位。** 这为后续实现区分了可静态核算的量和必须保留的动态身份；不是新的性能优化或A类论文主贡献证明。

证据入口：[中文HTML](../review_artifacts/slot_projection_20261023/report.html)、[独立核验](../review_artifacts/slot_projection_20261023/verification.json)、[执行前方法](../../experiments/paper_readiness/slot_projection_protocol.md)、[公开复核方法](../../experiments/paper_readiness/README.md#并发槽位与静态连接需求)。本轮没有网络/GPU执行，所有回调均为声明的无时间事件。

## 为什么能够精确计算

记原始rank `s`向专家owner `d`贡献的去重token数为`n[s,d]`，其中包含`s=d`的本地旁路。Dispatch按每source/destination的counter分配`0..n-1`槽位。固定copy epilogue按原始rank的计数前缀读取buffer，因此这些token在Combine输入中的序号占连续区间：

```text
P[s,d] = sum(n[r,d], r < s)
I[s,d] = [P[s,d], P[s,d] + n[s,d])
N[d]   = sum(n[r,d], all r)
h[d]   = ceil(N[d] / (SM数 × 每SM的Combine warp数))
J[g,d] = [g*h[d], min((g+1)*h[d], N[d]))
```

这里warp是GPU中执行同一组指令的一组线程。Combine每个warp遍历`J`中的连续序号；`g`到SM/warp/context的映射由固定源码决定。某个context收到的返回token数，就是所有映射到它的`J`与`I`的交集长度之和。

证明只需两步：任何slot双射都恰好覆盖`I`，不能改变其边界；每个warp恰好遍历自己的`J`，不能改变两区间的交集大小。多个warp共享context时求和即可。即使某些任意双射不满足真实执行依赖，所有合法双射仍在此集合中，计数不变性质继续成立。零接收owner没有token操作，不计算无意义的`index/0`。

固定H7168/Top8时，每份Combine数据操作数为14,400B，包含对齐后的元数据；不是只有hidden的14,336B，也不包含WQE、网络头、响应或控制signal。给定连接/context映射后，操作数乘以14,400可得对应的逻辑需求。对本地旁路行，仅记录名义执行通道，不表示创建物理QP或NIC流量。

源码依据是固定DeepEP `f6aa38fe06cd4a0489e7730365d4e0114970a2f3`的dispatch、copy epilogue、combine、get_qp_mode、TokenLayout及对齐常量，6文件均按Git tree/blob/SHA256复核。copy epilogue是必要证据，仅看到原子counter和Combine循环不足以证明原始rank连续布局。

## 实际核对了什么

| 输入或检查 | 结果 | 能支持什么 |
|---|---|---|
| 人工4-token，24个完整合法分配顺序 | 所有排列均完成496个声明事件；每条连接始终2次返回操作；4个token都存在跨连接身份变化 | 总需求可不变，身份仍会变化；不是只有一种分配顺序的无差异用例 |
| 四已见请求的entry0/层4，16/16/10/6 token | 48个原始token形成149个source→owner去重条目；32本地旁路、117跨rank返回put，跨rank操作数1,684,800B | 当前声明配置的静态网络需求，不是完整Prefill或生产规模 |
| 真实输入三种就绪策略 | 全部2,034事件完成，但实际只有1种slot分配，0个token跨连接变化 | 三策略没有形成不同slot顺序对照，保留负结果；不称3种独立验证 |
| 独立checker | 18,006个事件、543个Combine绑定；检查原件、slot双射、所有前驱、同warp顺序及发行记录 | 接口与声明执行的局部语义，不是provider/网络观测 |
| 两次只读分析 | 5个产物逐字节一致 | 分析可复核，不当作重复性能测量 |

真实策略失效的原因在驱动选择：slot一旦就绪就优先发起，而其他可用事件按字典序，往往先推进单个token的准备和分配，未让其他token的slot同时进入候选集合。没有在取得结果后追加策略或换参数。首次分析错误地对每一组都要求跨连接见证而失败；随后只修正这个额外断言，保留真实输入无区分力的事实，声明事件记录没有重跑或改写。

## 一个容易污染网络模型的简化

本地旁路token虽然不发跨机包，仍占Combine接收序号。若先将它们从`N/P`中删除，再分配远端token的通道，总跨机操作数仍为117，但此48-token输入的声明context/connection需求表有39个单元改变，计数差的L1距离为40，即至少有20份token操作数的需求质量被放到其他单元。

这是**人为构造的错误静态模型对照**，没有新增执行或性能条件；现有平台计划已经保留本地token，未发现当前平台存在这39处错误。它说明只检查跨机总字节无法验证通道映射正确，也不能把“本地不走网络”理解为“对后续网络没有作用”。不能从此计算网口利用率或时延收益。

## 不能约简成什么

连接总量相同不能证明完成时间相同。一个纯代数反例：4个等长写的前处理工作量为`9,9,1,1`，两个串行通道各分2个token。顺序`[0,1,2,3]`对应通道工作量`18/2`，`[0,2,1,3]`对应`10/10`；每通道始终2次写。这里是抽象工作单位，不是ns、真实GPU性能或本次内核的实测行为。它反驳从静态总量直接推出一般有异质处理成本下的时间等价。

因此，后续可用区间公式生成静态需求、核对动态执行，避免为核算总量枚举所有slot状态；仍须保留token身份、目标地址、源buffer寿命、归约成本、实际就绪、顺序与provider完成。变长token、非本次归约方式、hybrid、缓存路由、self-peer服务和跨NIC可见性均没有由此被解决。当前硬件校准、独立请求和现代完整联合执行仍缺；不以这项源码推论或有限枚举替代论文贡献。
