# 恢复边界实验与网络配置预检

本轮实际交付的是一项网络配置鲁棒性改进：改拓扑带宽、延迟后，用户可以在启动后端前知道交换机缓冲是否满足当前模型。恢复机制的创新性仍未成立，没有新的生产漏洞或性能收益结论。

## 实验哪里出了问题

原计划研究发送端失败后，旧写是否仍会覆盖恢复后的新值。但首个正常对照的新写缺少显式依赖，违反平台已有的同址跨连接写入规则。旧写在6036ns到达、12060ns完成；100us提交的新写被Python拒绝，未进入网络。随后原生记录的EOF来自控制器异常退出，不能归为源端超时。原五条件矩阵停止，余下四组未执行。

保留错误后，修订方案先尝试不同目标地址。此次250us接入传播延迟又触发了原生建网保护：按固定PFC模型，交换机8各端口合计需9,503,884B，而配置只有8,388,608B。没有回调、发包或result.json，第二个修订对照也停止。它只说明本实验输入不满足当前模型，不能推出真实交换机无法支持某类链路。

这两次错误都是实验设计遗漏了既存约束。没有提高缓冲、改延迟或放宽顺序保护来制造现象；没有获得源失败后旧包仍到达、覆盖或三种安全策略性能的证据。原始失败、独立核验、三类篡改拒绝和离线复算见[研究入口](../../experiments/late_write_isolation/README.md)。持久离线包51,606B，新源码根/空cwd核验逐字节一致。

## 修改了什么

新增公开命令：

```bash
PYTHONPATH=python python3 -B -m moe_ub_cosim scaleout rdma-preflight \
  --topology /path/to/topology --protocol examples/scaleout_rdma/rdma.json \
  --output /path/to/new-preflight.json
```

报告按每个物理交换机端口计算当前模型的headroom与保留量，列出哪个节点超限、端口贡献及剩余共享容量。容量不满足仍保存报告并返回退出码1；程序不会自动改配置。可选`--transactions <完整计划JSON>`同时检查已有的地址和依赖规则。在线未来追加的操作仍在提交时检查。

普通消息、持久流、事务、在线会话、推理服务五类Python入口共用这个检查，在启动backend及分配原生网络前拒绝非法容量和整数溢出。原生C++、固定库、依赖及有效配置保持；直接绕过Python调用原生程序，仍使用原来的建网保护。

预检复刻锁定源码的整数计算顺序，不是重新设计PFC，也不是硬件校准。通过只说明列出的静态初始约束满足，不说明动态无损、业务完成或时延准确。

## 结果如何核实

- 7项新增检查覆盖严格边界、混合速率取整、单端口/累计溢出、非法端口/类型、可选事务顺序及在线启动前拒绝；连同相关回归共126项不同检查通过。
- 新报告与已保存真实原生结果的32个交换机端口headroom及初始PFC阈值全部一致，没有重新运行网络。
- 10条公开命令在新目录完成验证；五类运行入口遇到超限输入均未启动标记backend，未创建运行结果目录。
- 13项固定依赖检查通过。6份监控均正常结束、无遗留PID，保守累计2.81秒、峰值约55.09MiB；原件与持久副本分配块499,712B，加64KiB收据预留仍在180秒/32MiB预算内。

独立参考来源、命令和收尾见[平台验收](../../fixtures/fabric_buffer_preflight/README.md)。完整本机记录在`runs/fabric_preflight_20261024/`；通过Git中的脚本、参考及公开小例可在新目录重做离线检查，不依赖旧运行目录。

## 对最终目标的影响

最终仍要解释代表性MoE任务的网络失效/长尾机制，并在有限资源、相同可见信息与强基线下给出有价值的新方法。当前的输入保护使实验更可靠，但不能替代这个贡献。

下一步应先确定能够表达真实故障恢复的合法实验：把网络排队与传播延迟区分，避免用过大的传播时间代替拥塞；明确失败源还有哪些访问可能到达，以及目标窗口何时能复用。需要对比等待退出、独立窗口和操作重放等已有办法，并把控制反馈与额外容量计入。静态顺序保护限制了当前接口可以研究的竞争范围，不能关闭它来声称发现新漏洞。只有连续有限容量下的未解决问题、现代provider语义依据和代表性负载都成立，才进入新机制设计；硬件校准与规模泛化仍是后续门槛。

本轮研究与平台改动分别本地提交，不push；整体A类论文目标继续进行中。
