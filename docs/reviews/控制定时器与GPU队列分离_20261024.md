# 控制定时唤醒与GPU本地排队分离

2026-10-24。平台现在可以在同一ns-3时钟上独立唤醒控制器，不再要求把业务期限写成一项GPU本地计算。它修正上一轮发现的计时输入问题，为后续有限缓冲恢复评价提供正确的控制入口；不是新的恢复算法或A类论文主贡献。

## 问题与实现

原本的本地节点按每GPU一个串行FIFO执行。用rank4的100μs本地节点表示重试timer，就会占住这条队列，使较早收到的数据也无法完成随后排入的复制。FIFO对计算节点的行为正确，问题在于控制期限不应被输入成GPU计算。

新增`NativeTransactionSession.commit(..., alarms=[{id,delay_ns}], cancel_alarms=[id])`：在实际提交时刻校验并安排/取消ns-3事件，真正到时才返回`alarm/fired/time_ns`。既不制造网络完成，也不引入第二套时钟、GPU槽或控制包。累计32个终身唯一ID，deadline严格早于全局截止；新工作、建立与取消请求整批校验，失败不执行有效前部。显式finish不得丢弃pending timer，允许本批取消后结束。

`drained`仍只反映已注册工作与物理网络，不证明控制timer已空。没有网络工作时，真实timer可唤醒前端再递交工作；它不能释放旧失败源租约或撤回在途包。无timer时不增加输出字段，既有语义保持。

## 实际结果

| 功能条件 | 实际观测 | 意义 |
|---|---|---|
| GPU本地节点充当100μs timer | 数据6.036μs收到，复制100μs完成 | 说明人为占用GPU队列的影响 |
| 独立控制timer，保留到100μs | 复制6.036μs完成，timer100μs触发 | 结果就绪与会话结束不能混为一谈 |
| 接收后复制并取消timer | 复制及取消6.036μs，正常结束12.060μs | 控制期限不会妨碍较早交付 |
| GPU有真实100μs本地工作 | 控制timer仍在20μs触发，本地工作100μs完成 | 控制唤醒不伪造GPU完成，复制仍遵守真实FIFO |
| 网络先空闲、20μs再唤醒 | 到时才递交并发包，同一QP继续，32.060μs正常结束 | 不重启或拼接独立网络 |
| 实际写入解除本地条件等待 | 20μs timer发起写，26.036μs收到后本地完成 | 未从未来结果提前解除条件 |
| 原源流失败 | 100μs timer启动健康流，106.036μs实际复制健康数据；旧8B源租约仍保留 | 正常工作继续，整体仍5ms partial，不掩盖失败 |

独立审计核对12份功能结果（11新条件和1旧对照）的控制记录、14次源TX、11次目标应用及窗口/复制内容。控制/旧GPU计时对照的源包和逐端口服务量相同；6.036μs与100μs的差别是本地排队输入语义，不能称网络提速。默认完整结果逐字节相同，新路径故意增加20ms宿主停顿也未改变仿真时刻。

22类非法原生命令、9项前端单元、旧在线3条和前缀32条命令及17项相关事务输入检查通过。触发时间、复制输出和重复回调三类篡改均被拒绝。首审计器对无数据timer条件遗漏“空payload字段可省略”处理，修正检查器并保留失败后通过，未重跑网络。编译仅更新session入口，旧对象/程序及固定8库、依赖保留；编译器产生的是既有第三方头文件警告，没有以依赖升级绕过。

## 研究边界与下一步

控制timer是声明的前端唤醒，没有CPU调度成本、跨端通知或真实故障检测校准；单次MRT1功能写与复制不是完整MoE/GPU推理。上一轮“只补缺失owner与操作级重试等价”的负面结果不因本轮修正而改变，也没有重跑原研究矩阵。

后续应在有限源/目标缓冲、多次故障和旧访问退出约束下，比较操作级重放加独立接收区与明确退出保证，检验是否仍有值得提出新机制的差距。本轮只解决控制和数据执行的计时分工，不宣称已解决缓冲回收、GPU可见性、现代provider接入或论文创新。
