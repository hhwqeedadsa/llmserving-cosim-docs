# MoE推理Scale-Out联合仿真：恢复、资源保护与实验交付

本阶段已把上轮发现的两个问题变成可配置、可审计的机制：后续短连接可以复用有期限的源端恢复历史；单一目的端可以受到占用上限约束。同时交付统一实验入口，修改模型、batch、网络与已实现的通信策略即可生成对照结果。24组独立实验和4组包级补采保留了正、负结果：减少重复流量并不保证业务更快，静态资源限制也可能阻塞健康消息。

审阅入口：[24组结果与包级解释](../review_artifacts/inference_resilience_20261022/report.html)、[详细证据](../review_artifacts/inference_resilience_20261022/summary.json)、[公开示例](../../examples/scaleout_rdma_resilience/README.md)、[条件证明](../communication_fragility.md)、[完成核对](../review_artifacts/inference_resilience_20261022/completion_audit.md)。平台提交为`52e1afb`；研究与收尾单独保存，本地修改和提交，不推送。

## 1. 最终目标、服务对象与限定条件

最终目标是建立可信的网络与推理联合实验平台：由真实业务依赖产生跨机通信，让网络排队、拥塞、确认和恢复反过来影响推理推进，再据此判断优化改变了什么、代价在哪里。研究核心是MoE专家并行的Dispatch/Combine交换及其长尾传播，不是单纯画通信量曲线。

平台服务于拓扑与带宽规划、专家放置和通信策略筛选、协议异常诊断与可复现实验。它当前是研究工具；绝对硬件性能、生产故障率、在线服务保障需要额外测量支持。

| 约束 | 本阶段具体含义 |
|---|---|
| 后端 | 只使用锁定ASTRA原生RDMA ns-3网络库；Scale-Out不使用UB。一个执行中全部组、层与轮次共用网络时间和状态。 |
| 前端任务 | 配置有限请求：每rank batch、上下文2048、2步Decode、KV已就绪。LLMServingSim请求/调度对象参与服务管理，联合服务生成SEND/RECV与计算图；下一步由真实完成反馈触发。未宣称完整原生LLMServingSim算子profile链路。 |
| 模型 | 合成MoE层段H1024/FFN4096、16专家/Top2、1层；batch/rank1或4。两组交错EP4，不是训练DP同步；没有语言文本语义或模型输出准确率验证。 |
| GPU | A100是逻辑端点标签，计算使用显式声明成本。仅改标签不能获得A100、RTX或其他GPU的真实速度差。 |
| 网络 | 本轮固定8GPU、100G三层Clos、单rail/plane。拓扑入口可配置多rail、层级和各层带宽，但本轮未测其收益。 |
| 资源 | 每源3条消息、16384B逻辑额度；份额开启时每目的端1条、8192B。是软件准入约束，不等同NIC物理缓存。 |
| 路由与故障 | 相同合成专家选择；目标从实际首图唯一选出。只定点丢某QP最终ACK，不模拟目的GPU整体宕机，不凭空制造热点。 |
| 预算 | 单例60秒/RSS1GiB/地址2GiB/仿真5ms；功能与研究各256MiB，研究补采包含在原额度内；预留8GiB。失败保留，不抬限盲重跑。 |

千卡拓扑生成与千卡包级联合执行是不同验收事项。本阶段没有千卡完整推理、训练、真实专家热点或硬件精度的新增证据；此前相应研究保留原范围，不把小场景推导成千卡结果。

## 2. 与现有仿真平台的关系及我们改进的维度

| 平台/层 | 擅长承担什么 | 本项目针对的工作问题 |
|---|---|---|
| LLMServingSim | 请求组织、组批与推理服务行为建模；计算profile需匹配硬件与形状 | 将有限Decode请求与专家通信依赖连接起来，避免把预定通信时刻作为业务反馈。 |
| ASTRA-sim | 工作负载图与集合通信执行、多种网络后端；已有ns-3适配路径 | 复用固定依赖的原生RDMA网络库；本项目当前联合入口自有服务/图驱动，不把链接该库说成完整复用ASTRA所有系统调度。 |
| ns-3及常见RDMA扩展 | 包、端口、排队、ECN/PFC、路由与传输行为；具体取决于分支和配置 | 增补明确的恢复、确认、QP清理和源额度语义，使包级异常可以反馈到推理依赖。 |
| SimAI等工作负载/集合通信仿真 | 已有训练通信与网络性能评估能力，需按具体版本核对 | 本阶段聚焦MoE推理，分别核对数据可消费、源确认、资源释放与业务完成，记录跨层传播链。 |
| 本联合仿真器 | 将请求、实际任务图和持续网络执行连接，并保存独立诊断与复现实验 | 可修改输入，观察网络原因怎样传到业务，并保留策略无收益与副作用。它不是替代所有上述平台。 |

以上是本次实际使用关系，没有把“本项目集成了某功能”写成“其他平台没有此功能”。差异需要按版本、配置和同一用例核对，不能用笼统钩叉制造独占性。

更改围绕五个维度展开：业务输入（模型、batch与依赖）、网络结构（层级、rail与各段带宽）、发送资源（总槽/字节与目的端份额）、传输反馈（超时、RTT与恢复历史）、证据与实验（包级观测、独立重算、有界执行与对照）。本轮主要实现后三项，并验证输入与网络参数可通过同一入口修改。

## 3. 每一步的目标、修改方法和交付结果

| 步骤 | 要解决的问题 | 本阶段完成内容 |
|---|---|---|
| 1. 明确完成语义 | 数据已到却无确认时，能否提前归还发送额度？ | 继续要求真实ACK与QP清理；数据就绪、业务依赖完成、确认、资源释放分开。故障不伪造成功。 |
| 2. 给后续短QP提供依据 | 过短初值导致首个反馈前重传，Karn规则下零有效样本 | 新增每源独立、有限容量、有证据年龄与LRU淘汰的恢复历史；可采用有效RTT基准或真实超时退避，后者不计RTT样本。 |
| 3. 限制单目的端占用 | 一个目的端可能持续占住源资源，健康候选无法获准 | 新增每目的GPU的槽/字节上限，跨plane合计；轮转可跳过受限目的端，同目的端FIFO不绕过；总资源不增加。 |
| 4. 分层核对 | 原生包执行复杂，不能只靠平台自己汇总的数字 | 纯C++状态模块、ns-3接入、被动记录和Python独立审计分开；从源包、ACK和超时事件重建历史与资源占用。 |
| 5. 统一可修改实验 | 改batch、模型或链路时需要多个临时脚本，难复现 | 新公开`scaleout sweep`支持最多32个显式条件；递归配置覆盖、全条件预检、图hash核对、预期失败和累计预算。 |
| 6. 用独立研究筛选方法 | 功能正确不等于有实际收益 | 独立24条件：batch1/4、正常/过短初值、历史/份额开关、单次/持续ACK丢失；4次被动补采解释负结果。 |
| 7. 可交付审阅与保存 | shm结果易失，临时会话不足以复现 | 公开JSON、版本化研究程序、Markdown/HTML、实际命令、来源校验与压缩归档；最终核对另见完成记录。 |

历史在QP首个实际发包时查找，初值为声明初值和历史值的较大者，受上限限制；不会改已经运行的QP。仅新证据刷新年龄，读取不延长证据有效期，到期即不能使用。它不能解决首批冷启动，也不预测同目的端未来ECMP路径。

目的端份额是占用上限，并非专用物理缓冲或请求级故障隔离；通信准入后一直占用到真实确认并清理。单条消息超过上限明确拒绝，不自动拆分。它既可能保护其他目的端，也可能压低健康并发。

## 4. 工作发现与实际机制证据

| 发现 | 实测结果 | 应怎样理解 |
|---|---|---|
| 历史减少短初值下的重复流量 | batch4无份额：payload1167360→686080B，少41.23%；超时184→72；RTT样本0→44 | 可以缓解后续QP的零样本重复负担，但不是修复首批，也不是默认加速保证。 |
| 减少流量仍可能稍晚完成 | 同组业务63838→64151ns，晚313ns | 实际反馈链40→下一步73确认→86准入/完成，局部ACK排队与资源释放比总字节更能解释完成顺序。 |
| 网络排空不是请求延迟 | batch1无份额：业务早407ns，网络反而晚1605ns；历史开启后业务完成与排空差8000ns | 最后事件是消息65的重复累计ACK回源，已有接收端重复响应记录，不能把8000ns全计入请求。 |
| 静态目的端上限会误伤健康QP | 单ACK丢失：业务98106→110962ns，慢12856ns，重传与payload不变 | 目标1到GPU4占用至67400ns，健康消息13也到GPU4，被限制到67400ns才准入；同目的端约束过于保守。 |
| 正常配置未必需要历史 | 正常初值下历史开关不改变业务完成 | 不凭命中率宣称优化；已有足够安全余量时，保守初值可能无影响。 |
| 份额效果随工作量变化 | 正常batch1慢875ns，batch4早501ns | 不选择一组有利数字推广；共享网络排序和业务依赖都要看。 |
| 持续故障仍整体失败 | 四组均280688ns停止，故障所有者不释放，失败界与诊断一致 | 是有界失败检测，不是成功率提升；少提交/少发送不是节省。 |

313ns的具体核算：消息40的数据到达不变，其ACK交换机驻留增加247ns；下一步晚247ns启动。消息73首发晚247ns，数据驻留减少162ns，但ACK尾部增加359ns（源端发ACK前38ns与交换机驻留321ns），故确认晚444ns。消息86等73释放后获准，其发出跨度再增加20ns、数据驻留减少151ns，最终444+20−151=313ns。包路径按实际节点和端口核对一致，UID只在同次运行关联。

这是已经发生的局部时间分解，不是“去掉某个排队就一定得到同样加速”的反事实保证。共享网络中策略改变会改变其他通信顺序，必须重新执行验证。

## 5. 证明、验收与可信范围

在[条件证明](../communication_fragility.md)中，保留完成安全性、旧反馈、采样、无进展失败界和固定依赖下的时延传播命题；新增源/目的端占用不变量、健康候选当前准入的充分条件、每源恢复历史容量/年龄/初值性质。健康候选准入还依赖可用总额度、消息大小、轮转资格和运行尚未终止，不保证整个推理成功。

纯SourceRecovery模块有界探索1602状态、28692转换；它不覆盖恢复缓存、准入、完整ns-3或完整推理，更不是无限状态证明。

平台检查通过72项Python、5个纯C++程序，固定恢复19个probe/5个服务、自适应10/3、新历史与份额11/4；固定模式与保存的真实旧二进制比较。普通用户五条件流程覆盖参考/组合策略、batch1、小模型形状与50G接入；预期失败后继续、意外失败中止、总预算停止终态均已检查。来源包括19个构建文件与13项固定依赖；最终再次核验结果见完成记录。

研究独立经公开入口执行，不导入tests、fixture或私有驱动。同batch共同已提交图逐字节一致；24组已发消息首包路径一致。4次包补采除新增记录外完整执行一致，不是额外独立样本。离线分析可确定性复算；HTML进行内容、生成一致性和本地链接核验，没有浏览器视觉验收。

保留的准备/检查失败包括：旧二进制复制最初丢失执行权限、预算检查误读字段；修正后新运行或对原输出重验，原失败未删除。更正前全局LRU版本作为历史产物保存，不能用它替代最终每源独立缓存的验收。

## 6. 代码结构与用户操作

| 路径 | 职责 |
|---|---|
| `backend/recovery_history.hh` | 每源实例的纯缓存规则：容量、证据年龄、LRU和保守初值。 |
| `backend/communication_admission.hh` | 纯源/目的端额度与轮转；不读研究结果。 |
| `backend/rdma/recovery.cc`及相关接入 | 原生QP、事件、真实发送/确认与生命周期。 |
| `python/moe_ub_cosim/scaleout_history_audit.py` | 离线独立重建；不反馈到在线策略。 |
| `python/moe_ub_cosim/scaleout_sweep.py` | 公开配置、执行、预算和统一结果。 |
| `examples/scaleout_rdma_resilience/` | 可复制修改的小型完整输入。 |
| `experiments/inference_resilience/` | 固定研究设计、公开CLI执行、补采与独立分析。 |
| `third_party/` | 外部固定依赖；本轮未修改。 |
| `runs/`与`docs/review_artifacts/` | 大产物本地归档与小型版本化审阅结果；不把临时输出混进源码。 |

从仓库根、已激活Python环境运行，设置后端与protoc绝对路径后：

```bash
PYTHONPATH=python python -m moe_ub_cosim scaleout sweep \
  --config examples/scaleout_rdma_resilience/sweep.json \
  --backend "$COSIM_NATIVE_SERVICE" --protoc "$COSIM_PROTOC" \
  --output /dev/shm/my-resilience-sweep
```

输出须为新目录。复制JSON，通过`patches.service.workload/model/parallel`修改batch、模型形状和EP组；`patches.topology`改rail、交换层级和各段带宽；`patches.protocol`改已实现的准入/恢复。GPU名称不自动换算成本；不接受尚未实现的任意通信算法名。对照组要求相同业务与拓扑，不同batch应另分组。详细默认值、限制、失败和复现命令见[示例](../../examples/scaleout_rdma_resilience/README.md)与[研究说明](../../experiments/inference_resilience/README.md)。

## 7. 后续工作怎样选择

本阶段交付的是可实验、可解释的联合仿真器增量和候选方法评价。下表是后续候选及进入条件，不声称已经实现，也不因本阶段结束自动启动。

| 优先级 | 下一目标 | 方法与停止条件 |
|---|---|---|
| 1 | 避免把单QP异常等同整个目的端故障 | 只用源端可观察反馈区分异常范围，对照静态份额与更细粒度限制；相同总资源、同样故障，健康QP与故障QP分别评价。没有稳健业务收益则保留负结果。 |
| 2 | 明确请求/副本级失败传播 | 定义失败RECV、依赖取消、QP清理及资源归属；验证故障副本失败时独立副本继续，不能返回伪成功。 |
| 3 | 真实热点与持续请求 | 对已获授权路由样本记录来源、覆盖及限制，映射专家到rank再生成Dispatch/Combine；冷/热变化和持续到达分别测吞吐、请求尾延迟、误重传与公平性。 |
| 4 | 扩大网络规模与拓扑对照 | 从小规模逐级扩展，估算事件/包量与宿主资源；区分千卡拓扑、千卡单轮和千卡持续推理。多rail、汇聚/Clos每层带宽按实际接入语义对照。 |
| 5 | 硬件校准与学术成果 | 用匹配GPU、软件、形状的计算及网络测量校准，形成可复用工具和基准；论文贡献需有跨负载稳健机制收益，不能把本轮单组数字当生产结论。 |

近期产出是平台代码、公开配置、可复现负结果基准和审阅报告；论文方向围绕“网络反馈如何经资源占用传播到MoE推理”以及可证明边界的干预机制。是否有足够新颖性和稳健收益投稿，应由真实负载与对照证据决定，不能由仿真器功能数量决定。
