## 1. 先说清楚：SimAI 和 LLMServingSim 的区别与项目选型

两者都有推理能力，也都能研究通信；不能用“SimAI 只做训练、LLMServingSim 才做推理”来区分。下面依据固定 SimAI `a57d765c` 完整归档中的 README、Vidur 分支说明，以及本地固定 LLMServingSim 源码，不代表对所有分支实跑后的性能排名。

| 维度 | SimAI | LLMServingSim |
|---|---|---|
| 整体范围 | 覆盖训练和推理，包含工作负载、集合通信、系统与详细网络工具 | 聚焦 LLM 推理服务、异构硬件、内存与分离式部署 |
| 推理调度来源 | 固定版本包含 `vidur-alibabacloud`，提供请求调度、组批和容量规划 | 自身 Python 服务前端，调度方式参考 vLLM，维护请求、组批与 KV |
| 工作量与计算依据 | AICB 等产生工作负载/成本，推理分支可选择多种执行时间后端 | 通过逐层硬件 profile 查询计算成本，生成任务/Chakra 图 |
| 网络路径 | 提供分析和 ns-3 详细仿真等模式，配有 Alibaba 的 ASTRA/ns-3 扩展及 SimCCL 工具 | README 默认使用 ASTRA 分析网络；其 ASTRA 依赖也有 ns-3，并非原则上不能接详细网络 |
| 百B/MoE支持 | 固定版本有 DeepSeek-671B、Qwen MoE 等配置/示例 | 有 MoE 和 TP/PP/EP/DP；具体模型能否可信执行仍取决于形状、内存和匹配 profile |
| 对本项目的用途 | 可作另一套推理调度来源和网络/通信建模参考 | 与最初确定的推理服务前端路线一致，可继续承担主线服务调度 |

规模、速度和精度不能仅按平台名称判断。两者都需要核对实际模型、GPU、输入、调度、通信模板、后端和校准；已有百B配置不等于执行了完整模型或测得真实硬件时延。

### 当前到底用了哪一套

工程里保留两条独立的 Scale-Out 服务前端：

- `scaleout_service.Frontend` 使用 LLMServingSim 的 `ConfiguredScheduler` 和 `Request`，是原定的 LLMServingSim 路线。
- `simai_service.Frontend` 使用固定 SimAI/Vidur 的真实 `Cluster/Orca/Batch/Request`。最近两组320卡研究走这条新增支路，初始KV已就绪、有限Decode、计算成本为声明参考。

新增支路复用本项目的真实路由适配、`make_wave/export_wave`、ASTRA适配和固定原生RDMA ns-3；**没有整体切换为 SimAI 的 ASTRA/ns-3-alibabacloud/SimCCL 全栈，也没有使用其计算时间预测器。** LLMServingSim 依赖仍在，但“仍依赖它所带的ASTRA”和“实际使用它的服务调度器”需要分开。

任务记录显示，新增支路是在后续SimAI前端/320卡真实路由任务中接入的；不是因为已经证明LLMServingSim不能支持R1、百B或详细网络。两条前端的就绪状态、请求映射和容量处理不同，目前没有完整的同输入等价/性能对照，不能宣称替换后更准确或更快。

### 按原定路线怎样继续

服务主线按原约定继续以 **LLMServingSim前端＋本项目工作量/通信适配＋独立原生RDMA ns-3** 为目标；SimAI支路保留为可选对照。这里明确的是路线，不声称最近的SimAI结果已被重新生成成LLMServingSim结果，也不自动更换入口。

恢复主线实验前，先把当前真实稀疏请求和独立来源读取能力在工作量层复用，再补到LLMServingSim适配器：现有旧入口按每rank固定batch创建请求，不能直接拿最新“15个请求分布在320个端点”的输入替换。没有本地请求的rank应允许只做远端专家工作，实际网络完成再推进对应批次。两条前端先核对固定输入下的请求/路由/字节/依赖与完成语义，再分别比较原生调度选择，不能为追求相等而删除各自实际调度行为。

来源：[SimAI固定归档](../../third_party/source_archives/SimAI-a57d765c.tar.gz)、[来源清单](../../python/moe_ub_cosim/simai_source.json)、[LLMServingSim前端](../../python/moe_ub_cosim/scaleout_service.py#L211)、[SimAI前端](../../python/moe_ub_cosim/simai_service.py#L99)、[近期实验范围](../tasks/simai_scaleout_spec.md)。

### 本项目对 LLMServingSim 的扩展侧重点

LLMServingSim 更偏向回答：**请求怎样组批、怎样部署模型、计算和通信怎样共同决定服务性能？** 本项目当前重点应是：**同一个 MoE 推理工作量放到不同跨机网络后，具体在哪里排队、为何等待，怎样在相同资源下减少等待？**

这不是两个完全不相交的范围。固定版本的 LLMServingSim 已有运行时反馈、MoE、TP/PP/EP/DP、多种硬件 profile 和服务调度。ASTRA 也已有 ns-3 后端。因此，“支持改 batch”“接上 ns-3”“发现专家不均匀”均不能单独作为我们的创新。

| 对象 | 固定 LLMServingSim 的侧重点/已有基础 | 本项目实际增加的侧重点 | 当前边界 |
|---|---|---|---|
| 请求与组批 | 请求生命周期、连续批处理、KV 容量和部署 | 网络实际完成回调推进服务；保存批次到网络的来源关系 | 最新 SimAI 入口只执行预先声明的有限 Decode 窗口 |
| GPU 计算 | 按硬件和算子形状查询 profile | 为网络实验提供可控计算依赖，也保留旧计算测量接口 | 当前 SimAI/Scale-Out 计算值为声明参考；没有完整 R1/H100 性能校准 |
| MoE 通信 | MoE 路由、通信节点及不同后端路径 | 原始逐 token 专家选择转为不均匀消息；独立现代路径还表达控制操作和缓冲依赖 | 主服务的贡献复制模板与现代 DeepEP 模板不同 |
| 网络 | 仓库默认说明使用 ASTRA 分析网络；ASTRA 依赖另有 ns-3 | 独立非 UB 原生 RDMA 后端，物理拓扑、队列、ECN/PFC/DCQCN、故障和恢复 | 不是完整商用 RoCE NIC/固件模型 |
| 输出 | 服务、请求及图执行结果 | 双端字节、逐包记录、累计有效到达、确认与源释放、失败原因 | 捕获截断或未覆盖的队列不能冒充完整观测 |
| 研究用途 | 通用服务配置与架构评估 | 定位跨机 MoE 长尾，比较网络/部署/通信选择及恢复干扰 | 机制可信和小例正确不等于已获得新方法收益 |

来源：[LLMServingSim README](../../third_party/LLMServingSim/README.md)、[其 Scheduler](../../third_party/LLMServingSim/serving/core/scheduler.py)、[trace 生成](../../third_party/LLMServingSim/serving/core/trace_generator.py)、[本项目 ASTRA 适配](../../backend/rdma/astra_adapter.cc)。比较针对本地固定版本及默认路径，不是对竞品所有最新分支作排他性断言。

## 2. 最终目标、服务场景与约束

最终交付应让研究者输入模型结构、请求/专家选择、并行组、专家放置、物理拓扑及故障条件，得到：哪些链路和端点限制任务；哪种部署/通信方式更合适；相对强基线能节省多少等待，以及这一判断的误差范围。

主场景限定为 **MoE 推理的 Scale-Out 跨服务器通信**。Prefill、Decode、训练不是可互换的标签；现有 MMLU 专家选择可研究推理热点，不足以证明训练热点或生产请求到达规律。

| 约束 | 对实验的实际要求 |
|---|---|
| 相同资源 | 比较策略时固定 NIC 总带宽、交换端口、上联容量、缓冲和计算成本；扩容对照另列资源变化 |
| 真实输入 | 保存原始专家选择、模型来源和 hash；不靠复制请求把少量数据包装成大规模真实负载 |
| 一次执行 | 所有通信组共用一套 ns-3 时钟、交换机和反馈状态；不能相加独立仿真时间 |
| 有限证据 | GPU 标签、容量参考、计算 profile 和网络配置分别说明；没有匹配校准时只作机制及敏感度判断 |
| 正确完成 | 接收数据就绪、发送确认、资源回收、任务完成和网络排空分别记录；失败时间不能充当成功时延 |
| 规模口径 | 同时报告物理卡数、活动卡数、源 rank 数、请求数、EP 大小和副本数；千端点不自动等于 EP1024 |
| 可实现控制 | 策略只能读取当时可获得的信息，不能读取未来完成时刻或评价真值；报告端侧开销及公平性 |

当前 E256 的静态分片要求专家数整除 EP。因此千卡部署可用多个 EP256/EP64 副本；不能直接把 EP 改为 1024 而仍声称每卡有一个完整、未切分的独立专家。扩大 EP 若引入专家复制或张量切分，必须同时重定义容量、路由和通信。

## 3. 当前工程结构：已有的优点与不能混用的入口

```text
请求 / 专家选择 / 模型形状 / 放置
  ├─ LLMServingSim 调度 → 旧 UB 联合服务
  ├─ LLMServingSim 调度 → Scale-Out 图 → ASTRA → 原生 RDMA Fabric
  └─ 固定 SimAI/Vidur Orca → 稀疏真实路由 → Scale-Out 图 → 同上

独立现代入口：DeepEP 操作/窗口控制 → 持久连接/事务 → 原生 RDMA Fabric
独立 RC 入口：有限 WRITE/原子语义 → RC 功能参考 → 原生 RDMA Fabric

实际回调 → 图 / 现代控制器推进 → 数据就绪、源释放及结果
```

这些入口可以复用基础模块，但当前不是任意拼装的一条统一全功能链。

| 层次 | 主要代码 | 已有的好处 | 需要保持的边界 |
|---|---|---|---|
| 服务 | `configured_scheduler.py`、`scaleout_service.py`、`simai_service.py` | 使用真实上游调度对象；网络完成后才推进 | SimAI 未使用上游计算时间预测器；也没有执行 Prefill |
| 工作量 | `route_evidence.py`、`scaleout_replay.py`、`modern_deepep_plan.py` | 原件校验、逐 token 来源和依赖可追踪 | 专家选择是工作量输入，不包含真实线上发包时刻 |
| 图/执行 | `export_wave`、`backend/rdma/astra_adapter.cc`、`service.cc` | SEND 只发送一次，RECV 只等待；单一仿真时钟 | 保存图转持久流的参考入口不保证 ASTRA 调度等价 |
| 网络 | `scaleout_topology.py`、`backend/rdma/fabric.cc` | Clos/Agg、共享上层、多 rail/plane；持续队列状态 | 拓扑能生成、路径可执行和主服务显式控制 NIC 是三件事 |
| 传输/事务 | `recovery.cc`、`persistent_streams.cc`、事务/RC 模块 | 已有经典恢复、有限缓冲、确认回收与失败保存 | 主服务恢复模式与独立持久路径支持范围不同 |
| 评价 | `scaleout_arrivals.py`、`simai_verify.py`、`run_summary.py` | 区分物理到达、唯一字节、协议接受和源确认；保留失败 | 主服务累计曲线按有序接收解释，不能原样用于选择重传 |

研究实验、功能测试和平台代码分开；固定依赖、运行预算及完整源码冷检出也已有基础。这些是继续研究的条件，不应推倒重建。目录调整应按实际修改逐步拆责任，不按“第几轮”复制平台。

## 4. 已确认的关键问题和修改方法

### 4.1 主服务还不能直接使用已有的选择重传强基线

`simai_service.py` 复用 `scaleout_service.make_wave`，ASTRA SEND 经 `Messages::Post` 调用 `Fabric::Send`。这条路径的 `recovery` 只接受 `native/go_back_n`。独立 `PersistentStreams` 则已有 `selective_repeat/1`、有限乱序缓冲、窗口、可选失败流隔离；现代功能入口也已接入相关配置。

**建议：先统一传输能力声明和适配边界。** 保留 ASTRA 的图调度、发送/接收回调以及资源释放定义，再让消息接口明确选择一次性 QP 或持久连接传输。不能只给 JSON 加上 `selective_repeat` 字段，或把保存图换成另一种执行器就称为等价完成。改造应先用纯 CPU 消息生命周期检查和最小实际小例验收，之后才重做受影响对照。

验收包括：正常/中间包/尾包/最终 ACK 丢失，有限乱序缓冲耗尽，数据先到而 RECV 晚登记，多组共享网络，重复回调拒绝。所有模式分列数据就绪、源确认和网络排空。已有[保存图到持久流入口](../../python/moe_ub_cosim/scaleout_causal_waves.py)明确声明不保证 ASTRA 等价，不能绕过此门槛。

### 4.2 人工丢包可核查，自然拥塞丢包仍有观测缺口

固定原生 `SwitchNode::SendToDev` 在 MMU 入口或出口准入失败时直接 `return`；该位置没有发出当前包捕获使用的专用丢弃通知。现有 `fault_drops/data_loss` 不能覆盖所有自然队列溢出。

**建议：补被动、带原因的交换机丢弃记录。** 区分入口容量、出口容量、链路不可用、人工故障和其他设备丢弃；保留时间、实际端口、优先级、字节和包标识。只记录已经发生的事件，不改变丢包决定或包身份。MMU 丢弃发生在物理到达之后，不能重复扣减在途包计数，也不能重复计入设备丢弃。

验收要求“接收、转发、缓存变化、实际丢弃”按各自事件边界守恒，并覆盖短反馈队列。补齐后才能判断等待究竟来自拥塞排队、自然丢包还是指定故障。来源：[switch-node.cc 的准入分支](../../third_party/LLMServingSim/astra-sim/extern/network_backend/ns-3/src/point-to-point/model/switch-node.cc#L147)、[现行限制](../rdma_congestion_loss.md)。这是平台可信度修正。

### 4.3 RTO 与实际反馈时延的关系应先校准，不能当新算法

320 卡最近对照中，25G 无人工丢包条件出现 126 次超时、2,008,392B 重复发送载荷；86 次超时发生时已有推进 ACK 在途。**这不证明 86 次都可避免，也不证明这些字节全处于最终关键路径。**

代码已经有 Karn RTT 估计和按源/目的保存的有界历史；近期严重丢包实验使用固定 RTO，没有启用这些选项。因此下一步应先比较固定 RTO、已有自适应估计及合理参数范围，再判断恢复外溢是否仍显著。`base_rtt_ns`、估计 RTT、RTO 和实际 ACK 往返不是同一字段。

需要增加或核对的事实包括：当时最早未确认字节、实际重发、ACK 覆盖范围、正反向传播/队列、PFC 暂停和拥塞控制限速。不能让发送端读取“远端 ACK 已经在路上”这一评价真值来免除超时。来源：[recovery.cc](../../backend/rdma/recovery.cc)、[配置](../../python/moe_ub_cosim/scaleout_recovery_config.py)、[既有逐包核验](../../experiments/simai_severe_loss/results/20261028/verification.json)。

### 4.4 通信模板必须显式区分“每专家贡献”与“每 token/目标 rank”

主服务对每个选中专家累加贡献数，再按 `count × hidden_size × activation_bytes` 生成 Dispatch/Combine。现代 DeepEP 计划的 Dispatch 则遍历同一 token 的**唯一目标 rank**，另有元数据、计数、原子操作和通知。

一个 token 选中同卡两个专家时，前者发两份激活，后者可向该卡发一份激活再本地分发。因此同一真实专家选择不能保证两条模板产生同样字节或等待。

本次独立读取最近 320 卡正常条件的四张保存图，并从 token 选择重新构建全部消息矩阵：

| 部分 | 远端专家贡献份数 | 唯一 token/目标 rank 份数 | 仅激活载荷差 |
|---|---:|---:|---:|
| EP256，两步各两层 | 380 | 380 | 0B |
| EP64，两步各两层 | 92 | 88 | 57,344B |
| 全部 Dispatch | 472 | 468 | 57,344B / 6,766,592B，约 0.85% |

EP64 子集份数差约 4.35%。这只是激活复制口径差，**不是现代 DeepEP 总流量减少量、时延收益或已发现的协议漏洞**；现代路径还有控制开销，Combine 也不能机械照搬去重。这个小样本不足以把去重列为高收益主线，但足以要求模板显式声明。

**建议：工作量层保留两份对象：专家计算贡献和实际数据投递。** 每个通信模板分别定义复制/去重、元数据、分块及完成条件。先按固定目标通信库核字节，再比较其网络性能；保留旧模板供历史复现，不能静默重算旧结果。

来源：[make_wave](../../python/moe_ub_cosim/scaleout_service.py#L143)、[现代 Dispatch](../../python/moe_ub_cosim/modern_deepep_plan.py#L188)、[本次核算证据](evidence/scaleout_project_review_20261029.json)。

### 4.5 拓扑已经参数化，但链路竞争和选路必须实际核对

原生 `RouteDistances` 按跳数安装最短路，交换机用 ECMP；它不会自动偏好带宽更大的路径。持久路径已经支持同 plane 物理 NIC 绑定及共享 Agg，不应再次把这一功能列成“尚未实现”。普通主服务按消息选 plane、再走原生选路，和持久路径显式指定 NIC 不是同一个接口。

**建议：输出每种路径的实际 NIC、rail/plane、ToR/Agg/Core、正反向候选和经过端口。** 使用真实路径和活跃区间确认共享资源，再研究竞争。两个 EP 组放在同一个 Fabric，并不保证它们会经过相同端口；不能据此直接声称跨组故障外溢。

对多 rail 先比较独立上层与共享 Agg，保持总接入/上联预算一致。对 Clos 与 HPN-inspired，明确后者只是参考结构；既有资源不等的结果不能解释为拓扑本身更优。后续若加带宽感知、flowlet 或适应性选路，分别说明控制信息、乱序、反馈返回和切换成本；现阶段默认仍是最短跳/ECMP。

来源：[路径实现](../../backend/rdma/fabric.cc#L332)、[物理 NIC 绑定验收](../../fixtures/physical_nic_binding/README.md)、[拓扑生成](../../python/moe_ub_cosim/scaleout_topology.py)。

### 4.6 主服务、模型容量与调度范围需要更明确

当前 SimAI 稀疏适配固定 R1 的 H7168/F2048/E256/Top8、连续专家归属；每源 rank 的全部声明请求必须一次选入批次。它使用真实 Orca 对象，却只支持当前有限、初始 KV 已就绪的 Decode 组织，没有持续外部到达和任意请求子集选批。不能把这个范围扩写成完整线上 R1 Serving。

**建议按三个独立接口改进：**

1. 模型结构/容量：抽出 shape、精度、权重/KV、专家/rank 和设备容量；专家放置允许逐层显式映射。先保持当前 R1 行为一致，再接其他模型。
2. 计算成本：将声明成本与匹配 profile 分开。profile 必须绑定 GPU、软件、算子形状及精度，未校准或超出范围时明确标记；不能只改 GPU 名称得到不同卡性能结论。
3. 请求流：显式加入到达、每请求观察长度和 EOS/窗口结束区别，再解除“全部请求必须一批选中”的限制。网络改变组批后，既比较固定工作量机制，也单独评价闭环服务效果。

另外，`simai.device` 与服务的描述性 `gpu_type` 目前分别校验，没有一致性/差异原因校验。若允许用其他设备作容量参考，应显式声明；否则应启动前拒绝混用。不能强制把容量参考误认为计时校准。

来源：[SparseRoutes 与 Frontend](../../python/moe_ub_cosim/simai_service.py)、[服务形状/成本限制](../../python/moe_ub_cosim/scaleout_service.py#L25)、[用户范围](../../examples/simai_service/README.md)。

### 4.7 失败隔离、安全资源回收已有局部基础，尚未贯通主服务

主服务的回退恢复重试耗尽会停止整个共享仿真；独立持久路径已有流级隔离、窗口撤销及旧写保护参考。平台功能不等于服务已经能恢复某个请求。

**建议：先定义失败影响范围，再接上服务。** 区分流、通信调用、EP 组和请求；保留健康工作。只有实际取消确认或合法的资源隔离条件满足后，才能复用旧缓冲。失败后重算/迁移需要计算、传输、重复副作用和晚到包的成本模型。

安全方向可研究“迟到重传跨越窗口复用边界”的风险及代价，但当前结果仅限声明功能模型，不是商用 RNIC 漏洞。已有检查和保护应作为基线，不能把重新实现 epoch、撤销或重传当新发现。来源：[已有流级隔离](源端故障隔离与健康工作保留_20261024.md)、[旧写覆盖边界](网络丢包与跨连接旧写覆盖_20261024.md)。

## 6. 收益到底有多少，哪些数字现在不能给

最近 320 卡研究中，物理端点 320、数据活跃 rank 218、真实来源请求 15；成功条件工作量相同。下表是**已完成的配置/故障对照**，不是新算法收益：

| 对照 | 仿真结束时刻 | 差值的含义 |
|---|---:|---|
| 400G 正常 → 上层 25G、无人工丢包 | 171.893 → 592.996µs | 相差 421.103µs；证明该负载对网络配置敏感。升级改变资源，不能说软件已可优化 71% |
| 25G 无人工丢包 → 50% 短窗人工丢包 | 592.996 → 663.998µs | 多 71.002µs；若假设能回到本次无故障时刻，相对故障条件差约 10.69% |
| 25G 无人工丢包 → 100% 短窗人工黑洞 | 592.996 → 702.706µs | 多 109.710µs；同一假设下相差约 15.61% |
| 持续 100% 数据丢失 | 603.090µs 明确失败 | 接受有效字节为 0；不是更快完成，不能参与成功时延排名 |

短窗比例只针对声明时间窗内实际到达数据包，包括重传；50% 窗口条件全观察期是 219/2517，约 8.70%，不能写成全程随机丢包 50%。

71.002/109.710µs 是当前模型的**条件差距参考**，既非严格理论上界，也非新方法承诺：故障持续、早期停顿、控制时延不可能任意消除，强传输基线也可能先缩小差距。单个负载、每条件一次执行，不支持生产故障率、请求 p99 或统计置信区间结论。

后续收益必须按同输入、同资源、同可靠性目标下的强基线计算：`净时延改善 = (T_strong - T_candidate) / T_strong`。另列无故障开销、成功率、健康任务拖累和额外缓冲。若作为工程筛选，可事先约定“故障条件改善至少 5%、无故障退化不超过 1%”等门槛；这些只是待选验收标准，没有测得或承诺。

整请求收益还受受影响阶段占比、故障发生率和普遍控制开销稀释。没有设备价格、生产故障/负载分布及匹配硬件验证，不能给商业收益率。原件：[严重丢包结果](../../experiments/simai_severe_loss/results/20261028/report.html)、[独立审核](../../experiments/simai_severe_loss/results/20261028/verification.json)。

### 9.2 新发现一：不同消息可以通过预检，却映射到同一传输端口

**严重程度：P1，正确性/规模可靠性。已复现Python预检放行，原生拒绝由源码确认，未执行故障网络。**

`Fabric::Send` 把线上端口设为 `10000 + id % 50000`，并用源地址、目标地址、端口建立 `port_to_flow_`。因此同一plane中两条0→4消息，逻辑编号0和50000都得到端口10000。当前 `validate_probe` 只保证逻辑编号不重复，会接受这组输入；原生 `emplace` 则拒绝碰撞。逻辑编号保持32位，没有截断成16位，并不足以证明线上连接身份不碰撞。

这一问题会影响自定义消息，以及某些更长层段/多轮组合的规模可用性。`port_to_flow_` 和历史flow记录跨轮保留，不能按“上一条消息完成了”就认为端口可随意复用。本轮不声称已有320卡结果发生碰撞。

**近期方法：**把线上连接身份计算集中为同一规则，在Python预检和原生入口都核对同一地址/端口组合；服务每次提交前检查本轮与已提交历史，启动前能预测的碰撞应提前报告具体消息。

**长期方法：**分开业务标识与传输连接标识；按端点连接分配有限端口，或复用已有持久QP与连续序号机制。不能简单在完成后删除映射：迟到ACK、重传、旧包和目标接收状态可能仍引用原连接，必须有安全回收条件或明确耗尽拒绝。

**验收：**同源同目标编号0/50000、不同目标/plane合法复用、跨轮碰撞、晚到反馈和端口预算耗尽。正常旧配置的地址/端口/ECMP路径不能因无关重构被静默改变。

来源：[Fabric::Send](../../backend/rdma/fabric.cc#L529)、[Python消息预检](../../python/moe_ub_cosim/scaleout_rdma.py#L222)。

### 9.3 新发现二：服务预检没有用实际消息检查发送字节额度

**严重程度：P1，配置一致性/失败定位。已用版本化人工小例复现，无需真实路由或网络。**

在SimAI小例设置每源活跃逻辑字节额度为1B，`validate_simai` 仍通过；随后 `make_wave` 生成0→8的14,336B消息。如果把这条实际消息交给已有 `validate_probe`，则正确拒绝“message exceeds max_active_bytes_per_source”。

原因是服务连通预检 `validate_groups` 使用1B代表消息检查拓扑/资源，不能替代实际消息大小检查。直接消息入口已经有正确规则，服务入口没有完整复用。原生准入仍有保护，因而这里是**过晚发现错误**，不是证明后端实际超额发送或造成死锁。

**方法：**把拓扑/协议检查与消息准入检查拆成两个可复用层。拓扑只校一次；每轮图激活前检查实际消息的端点、plane、字节数、全源/目的端份额、消息身份和累计预算。固定来源可先核算所有观察窗口；动态组批不能预知的部分在该轮真实选批后、任何发送前原子校验。

局部crossbar路径的豁免继续按现有定义处理，不把它误算成RDMA额度。不能通过自动放大额度或无说明拆消息绕过失败，因为拆分会改变调度、包数和拥塞反馈。

**验收：**`batch=1/4`导致消息变大、消息大小恰等于/超过额度、目的端份额不足、同机旁路、跨轮新消息。相同输入在直接消息入口和服务入口应得到一致的准入结论。

来源：[连通预检](../../python/moe_ub_cosim/scaleout_connectivity.py)、[已有字节规则](../../python/moe_ub_cosim/scaleout_rdma.py#L265)、[源端原生保护](../../backend/communication_admission.hh)。

### 9.4 新发现三：源确认时刻没有完全从逐包记录独立核对

**严重程度：P1，评价结果可信度。已复现人工记录反例；不是商用RDMA漏洞，也未证明历史原始结果错误。**

构造100B消息：数据在2ns接收完成，覆盖全部数据的确认在4ns到达源端。正常导出确认完成4ns。仅把消息摘要的 `ack_ns` 改为1ns，包事件不变，当前 `reconstruct` 仍接受并导出 `source_confirmed_ns=1`，早于数据收齐。

原因是程序会从源反馈重算确认字节，但最终时刻直接取消息摘要的 `ack_ns`；已有检查验证“确认总字节完整”，没有独立验证“确认完成时刻一致”。所以完整逐包记录和字节守恒也不能自动证明所有时间指标正确。

**方法：**从真实源端ACK/NACK接收序列重建累计确认进度，记录首次覆盖完整字节的时间，按当前协议回调语义与消息摘要、SEND回调逐项核对。另查时刻范围、数据就绪与确认的因果顺序，以及失败/未提交消息的缺失状态。摘要与事件矛盾时明确拒绝，不能择一保留漂亮曲线。

**验收：**最终ACK丢失、重复/迟到反馈、仅部分确认、同纳秒多事件、伪造早/晚确认时间和失败未完成。扩展选择重传时另声明其有序接受/乱序缓存语义，不能沿用GBN重建器。

来源：[确认字节重建](../../python/moe_ub_cosim/scaleout_arrivals.py#L123)、[终态检查与时刻导出](../../python/moe_ub_cosim/scaleout_arrivals.py#L138)。

**公共时间口径的新实证：**本轮调用当前`run_summary.describe()`读取两份旧结果，不重跑网络。固定40正常例公开`finish_ns=592996`，实际最终COMMIT/图完成为`569162ns`，相差`23834ns`；固定80正常例两者均为`563347ns`。公共outcome均无`application_finished_ns/network_drained_ns`字段。`scaleout_verify`与`simai_verify`也继续返回未分列的`finish_ns`。这是公共结果表达缺口，不是旧native时间戳错误；已有sweep分列了前端/网络时间，可复用其设计，但还需统一终态核验。见[本轮机器证据](evidence/current_project_review_20261029.json)。

**SR接入的规模约束：**`PersistentStreams`当前明确限制最多4096个stream。一个EP256域若全部rank对之间都有单向数据，连接对数为`256×255=65280`，已经大于此上限；这只是最坏需求核算，不代表当前稀疏负载实际建立了这么多连接。接入前应核算真实连接需求、复用规则和NIC/rail分裂，不能只调大上限；若采用池化/分批开连接，必须模拟等待，保证ACK、旧包与身份生命周期安全，并计入业务收益/代价。

### 10.5 创新方向怎样收敛，收益怎样计算

**优先候选：减少恢复对业务关键通信的干扰。** 典型问题是一个专家方向恢复时，重传和反馈是否占据健康任务需要的同一NIC、交换机队列或上联，从而推迟后继阶段。需要研究的是如何使用本地可获得的任务就绪/资源信息组织发送或准入，并验证它比普通公平发送、限速、隔离做得更好。

先做强基线：SR、合理RTT/RTO、相同可靠性、普通公平/隔离与源目的额度。之后用留出真实请求及不同热点/拓扑检查方案，而非在同15个请求上反复调参。候选只能读取当时可获得的信息；接收真值、未来ACK和最终关键路径只供评价，不能给发送策略。先查实际共享和竞争，否则不能把普通故障等待包装成任务干扰。

安全方向可作为后续独立候选：研究失败/取消后的晚到写入与缓冲复用边界，并量化安全回收的等待和容量成本。已有epoch、撤销、重复抑制等机制必须作基线；当前功能模型中的反例不等于发现商用网卡漏洞。仿真加速方向则以测得宿主瓶颈为前提，当前短窗口执行成本不足以支持先重构仿真内核。

近期已测业务时间如下，单位µs；来自已关闭的[恢复对照](../../experiments/service_recovery_baselines/results/20261029/verification.json)，本轮只读。

| 恢复配置 | 正常业务完成 | 短窗故障业务完成 | 相对本配置正常的额外等待 |
|---|---:|---:|---:|
| 固定40µs | 569.162 | 640.164 | 71.002 |
| 固定80µs | 563.347 | 705.271 | 141.924 |
| Karn80 | 563.347 | 699.488 | 136.141 |

固定40→80：正常业务改善约1.02%，故障反慢约10.17%；Karn80对固定80故障仅快约0.82%，且重复载荷增加434,776B。这些结果否定了“重传减少即可带来等比例推理收益”的简化判断，没有证明新策略收益。50%为`[0,100µs)`目标数据到达的周期丢弃规则，包括重传；不是全程独立随机50%，条件执行改变后也不保证丢同一批包。

量收益需分三层：

1. **机制可优化空间：**先从同资源强基线中，找到确实位于业务依赖上的额外等待；对候选控制点做有界干预。上表故障与正常差距只是条件差距，不能当作可全部消除的上界。
2. **方案净收益：**`(T_strong−T_candidate)/T_strong`，同时给正常代价、故障/健康任务完成、可靠性、额外字节/缓冲和公平性。不用网络排空、总队列时间或重传比例替代业务收益；有限层段时间不冒充整请求时延。
3. **部署价值：**实际故障概率为`p`时，平均节省为`(1−p)(T_normal,strong−T_normal,candidate)+p(T_fault,strong−T_fault,candidate)`；还需考虑尾延迟目标与可用性。没有真实负载/故障分布和匹配硬件验证，就不提供生产收益率。

研究优势在于已有真实选择→依赖图→共享网络→包级证据的链路，可以验证任务语义是否提供额外控制价值。能否形成论文贡献取决于强基线后的剩余空间、可实现的信息和留出验证，目前尚无已验证独有创新。若普通公平/隔离已经达到同样效果，应关闭该候选或转向有证据的新问题。

### 10.6 实施依赖与阶段交付

| 阶段 | 目标与交付 | 进入下一阶段的条件 |
|---|---|---|
| A：统一可信输出 | 公共终态读取器、能力清单、自然丢弃原因；文档和最小用例同步 | 实际收发、丢弃、确认和业务/排空时间可以独立核对 |
| B：贯通主服务 | LLMServingSim稀疏真实来源；保持ASTRA调度的SR适配；连接/消息区间映射与预算 | 小型实际前后端完整流程和错误路径通过，不靠另一个图执行器替代 |
| C：量化研究空间 | 另登记同资源、真共享端口、受损/健康任务明确的实验；对比SR与普通公平/隔离 | 强基线仍有可控制的关键等待，且候选信息确实可获取 |
| D：实现一个候选 | 单个任务干扰控制方案，给机制解释、消融、代价和失败条件 | 在留出请求/热点/拓扑上取得净业务价值，不能以弱基线维持收益 |
