# 有序载体与目标缓存：恢复强基线修正

本轮确认并消除了一个可能误导研究的问题：此前目标端永久保存每个请求的完整编码内容，容量随请求数累计增长；但现有持久字节载体已经过滤重传包，不会将同一完整帧再次交给目标应用。对于当前支持的单调put，这份缓存不是网络恢复必须付出的成本。

这直接改变后续研究基线：不能再用“目标缓存永久积累”证明网络恢复必然耗尽资源，也不能把取消这份缓存称为新的恢复机制。研究应继续面对真正没有解决的远端旧写退出、应用窗口复用和有效结果保留。

## 源码链条

`PersistentStreams::Receive`记录原生`ReceiverNextExpectedSeq`，调用原生接收逻辑后，只有连续前缀增加才把实际payload交给解码回调。完整旧包可以触发补ACK，但不再次交付。`MemoryFrameDecoder`累积新字节、消费完整帧并删除已消费前缀。`RemoteTransactions::Submit`按每连接已提交操作数分配MRT1序号，在线追加也不会重用旧序号。

因此，网络重传和应用重新提交旧事务是两个不同机制。此前`RemoteMemory::Apply`提供更宽的应用重放接口，缓存全部编码请求及原子旧值，且目标容量按整个候选累计预留。这是明确的软件模型选择；不能自动外推为真实NIC或现代provider的缓存需求。

## 实现与实包验证

显式`carrier_once_put/1`只用于v4注册源put：目标完整请求缓存额度为0，每context保留单调next序号。任何应用重放、跳号或原子都拒绝，避免在没有保存返回值的条件下假装支持更宽语义。旧模式完整保留，仍可检查应用重放和原子结果。

公开小Clos中的6个put使用同一目标地址和真实完成依赖。旧/新默认完整结果逐字节相同；新模式与足额默认缓存对照，去除声明和缓存字段后全部原执行结果相同。这里缓存内容是240B→0，不是总内存或GPU显存测量，也没有时延优化收益。

真正的数据包丢失和ACK丢失各触发1次重传。源发送7包；ACK丢失条件目标实际收到1个重复旧包，独立接收前缀重建仍只产生6次目标应用。新模式维持6个源ACK释放、最终窗口正确、无遗留源lease、目标next=6且请求缓存为空。在线入口在同一仿真时钟按回调追加也通过；原源隔离默认回归保持原部分失败结果。

相关39项Python单元、两个内存核心断言组、6类CLI/native拒绝、独立包/窗口/池审计及五类篡改拒绝通过。新源码根/空cwd的公开流程和六份离线复核另行验证；详见[验收及恢复方法](../../fixtures/carrier_once_put/README.md)。严格编译的旧测试初始化缺项保留更正，无生产保护放宽或已完成网络重跑。

## 研究决策与下一门槛

| 问题 | 本轮决定 |
|---|---|
| 网络重传是否需要逐请求长期复制完整put？ | 当前载体不需要；不能以旧模式累计缓存为唯一强基线 |
| 源失败后，旧包是否仍能写目标？ | 能。前轮3μs隔离后6.036μs旧写实证不受本次改变影响 |
| 目标窗口什么时候能复用？ | 仍需旧访问退出或真正撤权保证；目标不保存请求缓存不构成这种保证 |
| 是否具备持续无限恢复能力？ | 没有。固定操作数、元数据、源lease及窗口退出限制仍保留，不靠扩大额度绕过 |
| 是否有A类论文创新？ | 本轮没有证明。它排除了一个人为瓶颈，使之后的机制比较更可信 |

下一步先把目标端授权检查、已经获准的旧写及退出确认绑定到明确的实际provider语义，再选择可执行模型；不能把本地超时或请求副本释放当成远端退出。按同资源、同信息比较等待旧访问退出、独立目标窗口、操作级补做等强基线，并说明何时必须整体重试。现代硬件校准、代表性MoE依赖和规模泛化仍是论文门槛。

本轮仅本地平台增量，没有新研究矩阵、外部下载、GPU或依赖修改。整体论文目标继续进行中。
