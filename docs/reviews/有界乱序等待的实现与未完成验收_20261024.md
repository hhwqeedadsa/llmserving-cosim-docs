# 网络恢复强基线：第一阶段实现与验收缺口

本文保存第一阶段当时未完成验收的记录；后续独立补验已通过真实取消/RTO/流隔离/事务门槛，现行结论见[补验记录](../../fixtures/nack_grace_edges/README.md)。

整体目标仍是面向MoE Scale-Out网络与系统鲁棒性的可信研究平台，以及能经受强基线和真实语义检验的论文贡献。本轮补经典恢复基线，尚不能支持A类论文创新或最佳论文能力的判断。

## 解决的问题

之前固定真实路由实验发现，一部分被重复发送的字节，其初始副本最终也能到达。源码在每个新缺失前缀的第一次NACK立即恢复，没有给临时乱序留下等待时间。因此需要先检验经典等待能否解释或消除该现象，再决定是否值得设计新机制，不能把已知乱序问题当作创新。

新增显式`nack_grace/1`：实际源NACK启动固定等待，同缺口重复反馈不续期，ACK进度取消旧等待；到期调用原恢复，RTO独立保留。每连接只有一个等待事件，输入和日志有严格上限。算法不读目的端内部状态、未来拓扑或事后真值。默认省略时继续旧路径。

## 已发现并修正的问题

功能输入声明了两条连接，但只给一条发布数据。连接可以合法地保持空闲，其SourceRecovery要到首次发布时才创建。新关闭日志误认为每条连接都有SourceRecovery，导致SIGSEGV。修正为空闲连接记录发送高水位0、超时截止-1，不创建虚假恢复状态、不发送虚假包。失败及修复前程序/源码均保留，修复后空闲连接关闭已实际验证。

该边界说明系统鲁棒性不能只查“主流量完成”：已登记但未使用、尚未发布、失效后继续存在等生命周期也需要检查。

## 当前证据和缺项

独立CPU历史oracle通过9,565,943项状态检查，既有选择重传578,671项与持久恢复20项回归保留。33次Python检查含5次重复既有检查；三个native入口34种非法配置在网络分配前拒绝，13固定依赖保持。

六次网络尝试中5次成功、1次为上述崩溃。修复后单包丢失在29,898ns触发等待恢复，并实际发送缺口数据；首轮全丢时80,000ns独立RTO发生在任何反馈之前，最终完成。混合失效在新Python源码根、空cwd下执行，真实反馈重复不会延长等待。所有成功原件的字节、实际ACK/MSR1、物理收发、FIFO/队列与应用回调独立复核，六类篡改拒绝；新恢复源码根离线重算结果逐字节一致。

但混合例的真实缺口没有自行补齐，因而没有触发“ACK进度取消尚未到期的等待”。严格验收因此失败，未删断言；平台状态仍为in_progress。相同ns的RTO竞争、耗尽取消及启用该选项后的事务执行也未取得完整native覆盖。不能把CPU状态检查说成这些网络行为已经验证。

## 下一步与研究价值

先建立专门的临时乱序输入：在途旧路包经过绕行，后来短路包超越，但旧副本仍会到达。固定旧原件确实存在NACK前缀0与后续ACK前缀2000相隔2,004ns的事实，只能用来设计测试，不能把旧反馈塞进新执行。新阶段必须独立登记资源和具体次数，不能向已经关闭的六次追加运行。

平台验收完成后，再另立完整应用依赖下的研究对照。若经典等待消除异常，则淘汰相应创新候选；若仍有损失，继续沿真实关键前驱和队列服务追踪。减少重传字节与减少任务完成时间不能等同。现代DeepEP语义、独立负载、匹配硬件校准和完整千卡应用仍是整体目标的缺项。
