# 本地端口感知与故障恢复强基线

本轮解决的是一个会高估网络优化空间的基线缺口：交换机已经知道自己的端口断了，却仍按旧路由表往该端口转发。加入经典的本地失效端口剔除后，才能继续判断哪些等待需要新机制解决。它是研究可信度的改进，尚不构成论文主创新。

## 为什么需要这项修改

上一轮四请求、两层两步研究保留了完整应用依赖，确认故障的影响会传给后续健康通信。但关键首层Dispatch的44包全部初发丢失，源在81.193us先超时，84.902us才收到首个反馈。该事实不能仅靠选择重传解释：源没有反馈之前，也要检查交换机是否仍在向自己已知失效的出口转发。

对上一轮原始包复核，63个数据包和1个ACK的本地转发失败来自旧表选择坏端口，另有9次关闭清队列、3次物理到达丢失。这些是上一轮应用研究的计数，与本轮人工小例的包数不能混用。另发现原生本地drop回调绑定入口设备，因此包记录的port不是被选中的故障出口；必须结合实际入包、包头、候选和哈希判断。

## 实现与核验

新增可选协议字段`local_failover: {"mode":"live_ecmp/1"}`，必须配合显式故障日程。实际关闭发生后，只让故障边两端从原等价下一跳中删去自己的坏端口；顺序及原生哈希保持，无活候选仍丢包。全局更新重建也保留本地过滤，避免另一故障先收敛时把尚未全局收敛的坏端口装回。远端不提前获知另一故障，源仍按真实ACK和恢复事件推进。

六次实际功能网络覆盖旧/新默认、单故障、交错更新、零时刻及空候选。交错条件中，第二故障6us先更新，第一故障16us才更新；逐包核对期间8号交换机仍没有恢复自己的坏口，也没有把第一故障提前传播到其他表。第六次在新Python源码根、空cwd调用公开命令，实际出现31个空候选转发丢包，说明本地策略没有偷偷补全局绕行或取消丢包。

默认旧/新全字段结果相等，仅规范化已核同hash的八库路径拼写。独立检查按拓扑、故障时刻和固定原生哈希核对每次实际enqueue，再按真实接收、反馈、队列和回调核对工作完成。源/库/后端hash、篡改拒绝、归档安全和失败日志见[功能验收](../../fixtures/live_ecmp/README.md)。没有新增依赖或GPU执行，没有push。

## 研究结论与下一步

人工主例默认与本地剔除分别118.416us和40.768us，只说明这个输入确实触发了该机制；它们不是四真实请求的新结果，更不能当论文优化收益。本地调整额外时延为零，属于理想参考，未包含检测、ASIC编程或控制报文成本；不是生产FRR/LFA复现。

下一研究必须另立方法和预算，保持上一轮真实路由、应用依赖、拓扑、发送资源及恢复协议，先加入本地端口剔除，再区分永久容量减少、无反馈等待与全局收敛的影响。不要把端口变化导致的路径差、健康流等待或上层就绪延迟单独叫作可消除收益。如果经典本地处理已消除关键路径上的主要损失，应淘汰该创新候选。

只有残余损失经过完整应用依赖、公平队列/恢复限速/通用排程等强基线后仍有意义，才进入新机制设计。现代DeepEP必要屏障、self-peer和可见性接入，独立请求留出、匹配硬件校准以及完整千卡应用仍缺；平台已能做的短千端点网络不能替代这些要求。整体A类论文目标保持进行中，不承诺最佳论文。
