# 源端故障隔离与健康工作保留

已为持久RDMA字节流、事务和在线会话增加可选的源端流隔离。一条流重试耗尽后，其他流继续使用同一套ns-3网络状态；失败流的未确认工作和源缓冲区保护仍保留。默认全局停止模式保持原有结果。本轮仅在本地修改、验证和保存，不推送。

这一步解决研究工具的执行限制：此前一条流失败就停止整个仿真，无法继续观察其他专家通信、在途旧写和后续恢复动作。新能力让这些行为能够真实发生并被检查。**它是平台能力，尚不是论文机制贡献或MoE推理成功的证据。**

## 实际改变

工作配置的 `transport_recovery` 可增加 `on_exhausted: isolate_stream`。失败时移除本地NIC发送调度中的该QP，停止该源的重传与速率计时器；保持连接映射、真实发送/确认前缀和未确认资源。健康源仍能发送和执行自己的重传计时器。

原先初版会拒绝失败后才就绪的工作。最小网络例证实，这会从回调中抛错并停止其他流，未能实现隔离。已修为原预算内入队、保持未发布；同样覆盖失败回复源后来收到新请求、产生新回复的情况。原失败产物与修正后的结果均保存。

源端失败不撤回在途包。目标仍按实际收到的请求写入或执行原子操作，接收端仍可产生拥塞通知；源端迟到ACK/NACK/CNP只记入终态反馈，不能重新完成工作或释放信用。请求源与回复源单独处理，未通过全局状态向对端伪造错误通知。

## 核验结果

| 条件 | 实际结果 |
|---|---|
| 故障流与延后健康流 | stream0在70μs耗尽；健康流100μs就绪、112.054μs获ACK |
| 同一张NIC上的两条QP | 健康QP继续完成；故障QP的后续工作留在队列中，未发布 |
| 健康流也丢ACK | 故障源停止后，健康源仍执行自身重传，122.054μs获ACK |
| 在途请求晚于源失败到达 | 源2μs已失败，目标6.156μs仍实际应用请求；迟到ACK不完成事务 |
| 请求ACK持续丢失 | 失败请求的257B源读租约保持；独立健康请求完成并释放自己的租约 |
| 回复源失败 | 请求发起方仍等待真实返回；目标后续请求实际执行，新回复冻结，健康连接继续 |
| 在线前端 | 收到健康事务完成事件；失败事务不伪造完成，整个会话保持部分失败 |

独立标准库程序核对13个故障条件、132个实际源包、39个迟到反馈、13次目标副作用，并从实际MRT1字节重建目标内存。物理乱序接收不当成交付；共享NIC的ACK按线上端口区分。三类篡改结果被拒绝。原stream/事务/在线/前缀流程分别7/8/3/32条命令通过；46项相关单元检查及13项固定依赖核查通过。默认stream和事务完整结果与旧二进制逐字节一致。

## 对论文主线的作用与剩余问题

当前证据支持“局部源失败可以继续观察健康工作”，同时否定“本地宣告失败即可保证远端旧写消失”。隔离本身属于已有系统常见机制，不能作为本项目创新；同样，健康专家通信完成也不能代替所需专家贡献齐全。

下一步研究应检验：在旧写可能迟到、缓冲区有限且失败信息仅本地可见时，怎样安全保留已完成贡献、安排受影响部分重执行，并降低共享网络上的恢复代价。必须比较等待原工作结束、独立接收窗口等强基线，明确何种观测能证明窗口可复用；网络真值不能直接提供给恢复算法。代表性MoE依赖、独立请求、匹配硬件校准与显著收益仍待验证，A类论文的主贡献尚未成立。
