# 现代DeepEP真实路由与连接分流

本轮把固定现代通信语义落实到已有真实路由：四次MoE调用生成486个操作，独立枚举逐项匹配。在明确声明的双连接配置下，Dispatch数据只使用一条连接，而Combine数据分布在两条连接。这个结果说明，网络研究必须同时核对通信库的通道绑定，不能只给拓扑增加NIC或总带宽。

这是离线操作与依赖核查，不是通信库实测、包级网络或性能提升。证据见[摘要](../review_artifacts/modern_operations_20261022/summary.json)、[原件来源与逐条选择](../review_artifacts/modern_operations_20261022/provenance.json)、[公开命令](../review_artifacts/modern_operations_20261022/commands.json)、[独立依赖核查](../review_artifacts/modern_operations_20261022/verification.json)、[归档](../review_artifacts/modern_operations_20261022/archive.json)。

## 1. 输入、目标与约束

平台固定`fc5de83658053488a5c93f7628bd653577cdd108`。实验只调用公开`modern-deepep-plan/check`，读取公开保存结果；不导入测试、fixture或内部图生成器。四原件来自固定R1-AWQ/MMLU目录，revision为`27febb7b2d24169560a9f6f83d38eb53f94916cf`，全部hash复核；共8,193,641B，没有新下载。

选择Decode entry1/2、原层3/4，共16条rank/token选择，保持原顺序。声明EP4、每rank一个请求token、E256/Top8/H7168、连续等分64个专家、BF16、fresh direct、expanded本地归约、跨rank全部RDMA。不是完整R1四卡部署或测得的请求到达时间，也不能代表训练和生产总体。

为检查连接映射，明确声明每rank两条GIN连接、本地设备表[0,1]、2个SM、2个Dispatch数据warp、2个Combine warp、调用5个上下文、申请5个上下文而实际按连接数向上分配6个。这是条件配置，不是当前机器的实测硬件或现代库推荐参数。modern README的Hopper+等条件仍未匹配验证。

## 2. 真实选择生成了哪些操作

| 跨rank操作 | 数量 | 操作数字节含义 |
|---|---:|---|
| Dispatch token put | 38 | 共549,632B，每份14,464B，含metadata与对齐 |
| Dispatch rank计数 | 48 | 每个8B编码值 |
| Dispatch专家计数块 | 48 | 每块64个int64，即512B；其中10块全零计数仍需发布 |
| Dispatch入口/出口屏障signal | 96 | 64位原子增量的逻辑调用，不是8B普通包 |
| 本地归约后的Combine token put | 38 | 共547,200B，每份14,400B |
| Combine入口/出口屏障signal | 96 | 同样保留真实库要求的屏障 |

含本地项共486操作、2,334事件、51个Dispatch符号slot。逐源token/目的专家区间独立核对每个数据操作，另枚举全部rank计数、专家块与四次组屏障；不是只检查总数。rank计数按目的rank去重，专家块按专家贡献计数，两种计数不能混用。全部值采用`-count-1`编码，零值编码为-1。

数字只覆盖选定路径的操作数，不包括线上包头、响应、重传、真实WQE拆分、工作区或全部GPU内存流量。不能拿486和旧v1操作数相除作为加速比，也不能把signal调用直接当作包。

## 3. 双连接为什么没有让Dispatch均匀分流

每rank当前只有一个token，它只激活SM0的第一个Dispatch数据warp。选定`get_qp_mode`将它映射到GIN上下文1；两连接下，connection=1%2=1。因此38个跨rankDispatch token put全部选连接1。计数与屏障使用上下文0，走连接0。

Combine工作按接收来源的前缀顺序分配，通道选择与Dispatch不同。在本轮每源/目的最多一个token的条件下，slot只能为0，所有51个slot组都没有组内次序歧义。于是可以独立解析接收序号：38个跨rank返回中，23个选择连接0，15个选择连接1。

这不是“网卡0空闲”：它还承载计数、屏障和部分Combine。也不是两条连接的实际带宽份额，因为没有发起时序、包/响应及队列执行。它说明当前小batch的有效数据通道数与申请资源不同；增加NIC、QP或槽数可能同时改变多种机制，不能只修改一个总带宽数后解释性能。

更大batch时，同源/目的存在多个token，Dispatch原子slot顺序会改变Combine接收序号和通道。平台因此保留symbolic slot及运行时约束，而没有把本轮唯一slot结论外推。人工功能例已经检查两个合法slot可映射到不同连接，但未证明真实GPU采取哪种交错。

## 4. 完成事件怎样改变后继依赖

公开check对必要事件做暂扣，另用独立反向后继枚举核对所有32个应用阶段完成节点：

| 暂扣事件 | 被阻塞完成数 | 支持的解释 |
|---|---:|---|
| 不暂扣 | 0 | 当前保存表示的全部必要事件可达 |
| 首个远端Dispatch数据local_complete | 32 | 源flush不能完成，其退出屏障signal不能发起，影响全组后继 |
| 同一数据目标visible | 29 | 数据目标及其后继受阻；其他三个rank的本轮Dispatch可先完成 |
| 一个全零专家计数块visible | 32 | notify角色仍须等零块，不能因其没有有效token而删除 |
| 最后一次Combine退出signal的local_complete | 0 | 最后一轮应用不直接等该尾部反馈；不能据此证明网络排空或无资源反压 |

这是逻辑依赖判别，不是丢包、ACK延迟或时延实验。`local_complete`、目标visible、消费者完成和网络排空分别处理。计划未从远端真值决定源端发起；源flush等待本地完成，目标signal的可见条件由未来provider兑现，跨NIC可见性仍需匹配验证。

三份重复生成产物逐字节一致，7条公开CLI均正常退出，子进程最大RSS32,436KiB。输出和原件均保留，未执行新网络。源码布局与固定依据见[布局报告](现代通信布局与并发槽位_20261022.md)，用户接口见[现代计划示例](../../examples/modern_deepep_partial_order/README.md)。

## 5. 对下一步研究的具体影响

首先，需要把动态slot分配和通道内顺序接到实际就绪事件，再与持久队列资源核心连接；之后补provider多槽、原子事务、可见性、CQ与源buffer寿命。未有这些能力时，不能用普通字节流替代控制操作声称完成现代基线。

其次，后续Clos、汇聚和multi-rail比较必须固定有效通信算法、合法连接/NIC绑定、专家放置及各层端口/超售；验证有多少通道真的发数据。硬件校准需匹配所选GPU、网卡、软件版本和provider，不能靠修改GPU标签替代。

最后，正常无故障、多EP组共享网络中是否存在显著且能被优化的关键等待仍待在线验证。当前工具、源码核算和模型修正提高了研究可信度，但尚未成立A类论文主贡献；留出请求、真实测量与千卡长工作量仍缺。该目标保持进行中。
