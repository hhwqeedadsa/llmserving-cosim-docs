# 现代GIN自发请求与网络基线更正

本轮发现并修正一个会影响网络研究基线的错误：**发给自己不等于绕过通信库**。固定DeepEP direct中的屏障通知和专家计数块仍进入GIN；固定GDAKI为它们创建self-peer QP。此前操作计划把这些请求归为普通本地操作。它们需要provider资源，但物理回环路径、服务成本及是否涉及外部线速尚未验证，不能直接添加交换机流量。

平台修复为`c08cbb98acdb9a8b3bbc97fa959e0ca28ea817e8`。本轮用相同四份真实原件、相同16条选择和相同声明参数重新生成计划；旧结果保留，未重写为新结果。实验通过公开CLI完成，不调用测试或fixture生成负载。结果与独立比较见[摘要](../review_artifacts/modern_self_gin_20261022/summary.json)、[核查](../review_artifacts/modern_self_gin_20261022/verification.json)、[来源](../review_artifacts/modern_self_gin_20261022/provenance.json)及[归档](../review_artifacts/modern_self_gin_20261022/archive.json)。

## 1. 更正了哪些行为

| 操作 | 发给自己的真实源码路径 | 仿真要求 |
|---|---|---|
| Dispatch/Combine token | 显式本地指针/TMA旁路 | 保留本地依赖，不创建GIN请求 |
| rank count | put_value中的本地store旁路 | 不占GIN提交队列 |
| expert count block | 非NVLink分支直接GIN bulk put | 保留发送区、目标区和provider完成；零计数也要发布 |
| 入口/出口屏障signal | GIN signal，无self旁路 | 使用self-peer上下文，保留原子请求与完成义务 |

依据为固定DeepEP `f6aa38f` 的dispatch/combine、NCCLGin句柄和屏障，以及固定NCCL `12df1a1` 的GIN API、GDAKI peer QP选择和self-loop QP建连。平台的[逐层源码依据](../../fixtures/modern_self_gin/source_basis.json)附完整hash与Git blob核对。本研究不将该fixture用作实验输入或分析依据；原始选择、公开生成结果和历史归档分别核查。

## 2. 同样的真实选择，provider请求核算发生了什么变化

配置仍是条件EP4、每rank一个原请求token、E256/Top8/H7168、BF16、fresh direct和本地专家归约；四调用选自entry1/2、原层3/4。两连接、本地设备表[0,1]、2SM及各2个数据warp为声明参数，不是实测部署。四文件不代表训练热点或生产总体，也不构成完整R1四卡部署。

| 操作类别 | 数量 | 解释 |
|---|---:|---|
| 跨rank GIN | 364 | 其中Dispatch/Combine token各38份；其余是计数与屏障 |
| self-peer GIN | 80 | 64次屏障原子通知、16个专家计数块；其中3块全零计数 |
| 本地旁路 | 42 | 16次rank count store、26次本地token处理 |
| 全部操作 | 486 | 操作总数、2,334事件及51个符号slot都未改变 |

由此，本次输入包含444个GIN API请求。80/444约为18.0%；这是需要保留的provider请求份额，**不是漏掉18%的网络字节、WQE、带宽或耗时**。self-peer操作的逻辑操作数共8,704B，其中信号宽度不能作为线上报文大小。旧计划已经列出这些操作，错误在于将它们分类为不经GIN的local。

原报告跨rank数据结论保持：Dispatch为549,632B，Combine为547,200B；Dispatch的38份数据选声明连接1，Combine在slot唯一的本次输入中为连接0/1各23/15份。独立比较旧归档确认，路由、布局、完整事件DAG及动态slot公式未改，只修正路径/verb并补专家计数发送区；不能将正确的旧跨rank结论一并否定。

加入所有GIN操作后，声明连接0/1分别对应391/53个请求，80个self-peer请求都绑定上下文0及连接0。这里统计的是条件请求分布，不能写成网卡利用率；尚无请求发布时间、NIC服务、原子响应、CQ反馈及链路排队。不同类型请求的单位成本也不同。

## 3. 对千卡研究的具体约束

集群GPU数与EP组大小必须分开。对本分支一次Dispatch+Combine，若EP组有R个rank，四次屏障分别产生R²个signal，专家计数产生R²个bulk put，rank计数有R(R−1)个GIN请求；合计6R²−R个GIN控制请求，其中5R个为self-peer。它们与token数据请求分开核算。

| 条件集群 | EP组数 | 每组GIN控制请求 | 每组self-peer请求 | 全集群self-peer请求 |
|---|---:|---:|---:|---:|
| 1024 GPU、EP4 | 256 | 92 | 20 | 5120 |
| 1024 GPU、EP8 | 128 | 376 | 40 | 5120 |
| 1024 GPU、EP16 | 64 | 1520 | 80 | 5120 |
| 1024 GPU、EP32 | 32 | 6112 | 160 | 5120 |

表格是固定源码分支、各组各执行一次调用的代数核算，没有复制四份路由构造千卡生产负载，也没有运行千卡。它说明小EP加多组共享网络与一个大EP不能仅按总GPU数互换。推理吞吐、显存约束、专家分布、调用并发及计算成本仍须分别定义。

## 4. 什么没有被证明，下一步怎样做

本次self零专家块可见或self屏障源完成被暂扣时，均阻塞后续32个应用完成节点。这是必要依赖的反例核查，不能解释为真实硬件一定有严重长尾。静态分类修复不是论文机制创新，18%的计数比例也不是性能收益。

当前后端的src=dst限制使它不能直接承载该现代分支。下一步必须单独定义self-peer GIN在NIC、WQE/CQ及内存中的行为，并与跨rank流在同一provider资源上推进；不能默默跳过、强加交换机路径或用零成本本地事件代替。然后接入窗口及现代事件核心，明确哪种GPU/NIC/provider可测、校准哪些成本。没有这些证据前，不使用MRT1给现代DeepEP排性能名次。

有A类论文竞争力的研究仍需证明正常真实负载中的关键网络等待存在、解释能排除模型伪影、方法优于现代强基线，并有留出数据、规模与匹配硬件校准。本轮让基线更准确，尚未满足这些论文要求。
