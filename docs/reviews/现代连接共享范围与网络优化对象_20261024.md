# 现代连接共享范围与下一步网络优化对象

本轮得到一个会改变研究方向的结果：**旧完整应用里观察到的两条跨阶段限速来源，在现代通信基线中一条仍有共享连接的条件，另一条已被不同context分开。不能直接把旧结果当作现代推理的优化空间。** 本轮没有提出加速比，也没有执行新的网络；它把后续实验应保留和应淘汰的解释分开了。

## 一、具体检查了什么

上一轮已沿真实数据包和拥塞通知追溯到work90→108、work80→132。旧完整应用只为每个方向建立一个持久QP，四卡之间共12条，因而同方向的不同阶段都继承这条QP的状态。QP是持有传输和拥塞状态的队列对；它不等于应用消息、专家或网卡。

现在对照固定DeepEP `f6aa38fe06cd4a0489e7730365d4e0114970a2f3`和NCCL `12df1a11afad322be5a204a2db890161cbf8131d`的GIN/GDAKI路径。应用的context index先选GIN连接，再选连接内context，provider再按peer选择QP。每个操作都保留这些层次，而不是只按源/目的卡合并。

输入仍是用户提供的4份R1-AWQ/MMLU路由，Decode entry1/2、原layer3/4，16条token-layer选择。配置明确声明EP4、2个SM、Dispatch/Combine各2个warp、申请5/调用5个context、2条连接、设备标识[0,1]，四次调用复用同一Context。这是此前选定的功能配置，**不是现代默认值、真实设备参数、完整R1四卡部署或GPU执行结果**。连接绑定的物理可达性也未由这个离线计划证明。

从固定源码精确提取`get_qp_mode`和`ncclGinInitCommon`，用CPU标量类型及限定词替身执行486次查询；独立Python整数/区间枚举核对全部操作。这里没有编译/运行完整DeepEP、NCCL、CUDA或真实provider。对于本地旁路，也检查其通道赋值，但不把它计入GIN操作或QP活跃量。

## 二、看到了哪些共享关系

| 对象 | 本轮固定配置的结果 | 对网络研究的含义 |
|---|---:|---|
| 全部逻辑操作 | 486 | 含token数据、计数、屏障及本地旁路，不等于包数 |
| 需要provider的操作 | 444 | 364个跨rank请求、80个self-peer请求 |
| 显式本地旁路 | 42 | token和本地rank count；不占GIN QP |
| 活跃远端QP身份 | 33 | 旧模型按方向合并成12条，12个方向都隐藏了多个context |
| 活跃self主QP身份 | 4 | 保留GIN需求，不据此指定外部交换机路径或零成本 |
| 同时承载数据和控制的QP | 4 | 都是context0，Combine数据会与计数/屏障共享 |
| 同时涉及Dispatch/Combine的QP | 22 | 包括控制角色，不能把22条全部称数据相互干扰 |
| 跨多次调用复用的活跃QP | 33 | 只在本轮同一Context寿命假设下成立 |
| 分配的QP对象总数 | 120 | 4卡合计96个主QP＋24个self responder，与37个活跃主QP不同 |

申请5个context会按2条连接上取整为每卡6个；选定FULL、rankStride=1且counter默认0的初始化不需要companion QP。主QP按context和peer分配，self另有独立responder；responder不是第二次应用事务。120不表示120条同时发包流，更不是已测显存或CQ开销。

Dispatch的38个跨rank数据操作全部使用context1；Combine的38个跨rank数据操作分到context0—3。计数和屏障使用context0。因此既不能说“现代库已经完全隔离数据和控制”，也不能说“所有通信都像旧模型一样按方向共用一条连接”。本地token虽然不发跨机数据，仍占Dispatch接收序号，影响Combine的warp/context分配；本轮每源/目的最多一个token，slot唯一，不猜测并发顺序。

如果每次调用另建独立devComm，四次调用的活跃身份并集由37变成119，静态分配对象由120变成480。这个数字只是资源作用域对照，不是已经运行的重建方案，更不是免费重置拥塞状态的性能基线。实际应用复用哪个Context仍需运行配置或测量证明。

## 三、原来两条关键来源还能否沿用

全部76个旧SEND已经逐图节点、work、消息和rank投影匹配到现代数据操作；两套表示使用相同的16条原始路由选择。旧图的物理rank为0/2/4/6，现代逻辑rank为0/1/2/3，不能直接用节点名称中的数字当作物理卡号。

| 上一轮真实来源 | 对应现代数据操作 | 条件身份判别 |
|---|---|---|
| work90→108：第二步L0 Combine 0→2，随后L1 Dispatch 0→2 | `m2.combine.data.s0.d2.t0` → `m3.dispatch.data.s0.t0.d2` | 都用context1，连接1/连接内context0/peer2；同一devComm下仍共享QP |
| work80→132：第二步L0 Dispatch 2→0，随后L1 Combine 2→0 | `m2.dispatch.data.s2.t0.d0` → `m3.combine.data.s2.d0.t0` | 前者context1、后者context0，已经分开QP；本声明设备表下还选不同本地设备 |

第一行只保留“可能有状态延续”的语义条件，没有证明现代基线仍有相同CNP或降速。第二行否定的是将旧80→132解释直接搬到现代同QP控制器上；共享交换机和其他干扰仍可能存在，不能据此宣布关键路径问题消失。

现代基线还改变了目的rank去重、完整布局字节、计数、屏障、原子事务和完成条件。没有把旧报文、CNP、速率或完成时间赋给现代操作，也没有用这两行计算可消除时延。旧实验的包级事实继续有效，适用范围保持为旧贡献复制参考模型。

## 四、QoS和空闲状态的边界

固定DeepEP在Context初始化时从环境/可选参数取得traffic class，写入`reqs.ginTrafficClass`；NCCL据此或通信器配置构造GIN config；GDAKI从config取得值并设置AH的SL/traffic class。这个链的作用域是所建的Context/provider配置，没有看到本路径按热点专家或逐token自动设置类别。源码中变量名有SL，不能直接把它当作本仿真器的priority group编号，更不能略去真实交换机的DSCP/SL→队列/PFC映射。

因此，若考虑恢复流量或关键通信的QoS隔离，需先表达真实的类别映射和同等共享缓冲/带宽，检查健康流、公平性、控制包及PFC代价；仅增优先级、增连接或增带宽不能当创新。这里的初始化核查不覆盖所有provider或运行中修改路径。

QP持久存在只说明资源和身份可复用。host建连源码和标量索引函数没有证明网卡在空闲后怎样保留、衰减或重置拥塞控制状态。此前`figure7_reference/1`与原论文相符，也不等于当前网卡固件。没有用“未看到reset语句”证明生产设备永不重置；ACK、flush和屏障同样不能被当成控制状态清零收据。

## 五、下一步应怎样实践

1. **先把现代连接身份接到实际网络。** 用devComm、context、peer和物理NIC作持久键，保留不同角色的必要控制操作。沿用真实包/ACK/目标事务事件，不把同方向字节压成单QP。未有self-peer、原子返回和跨NIC可见性依据的组合明确拒绝；先功能验证，再做性能研究。
2. **把强基线做成同资源对照。** 保留现代去重/计数/屏障、已有通用调度和恢复等待；固定连接、总队列容量、内存、可见信息和链路资源。比较应回答关键数据与控制共享何时损害完整应用、是否已有调度即可解决，不能通过免费新增连接证明收益。
3. **核对匹配设备的控制器。** 对同一连接的连续发送、空闲后追加、拥塞后追加和多context共享做匹配GPU/NIC/provider测量，区分数据ACK、源buffer可用、目标可见和控制状态。现在不具备的参数保持未知，不给A100/Hopper贴标签代替校准。
4. **通过后再扩大负载和规模。** 引入独立请求和更大batch，保留动态slot引起的通道差异；千卡区分EP规模与多组共享集群。37个活跃QP的离线核查不证明千卡完整推理可运行，也不替代系统开销和应用完成时间验证。

这轮没有新优化算法或论文主贡献，确实淘汰了一条未经现代基线支持的解释，并限定了仍值得验证的共享关系。A类论文需要在这些边界之后建立新的机制/方法贡献及独立证据，整体目标继续进行。

代码、声明配置、原始来源、归档和离线恢复入口见[实验说明](../../experiments/provider_binding/README.md)。新目录只用包内研究源码和公开产物复算分析、来源比较及核验，不能把此类复算写成现代provider执行或从零构建。预算和原始监控另见实验收尾，交互式源码查看不计入受监控执行总量。
