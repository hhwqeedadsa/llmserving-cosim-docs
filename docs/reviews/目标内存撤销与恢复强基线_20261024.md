# 目标内存撤销与恢复强基线

本轮最重要的结果是修正恢复研究的比较对象：固定Linux v6.12的mlx5驱动已经提供注册内存区（Memory Region，MR）范围的DMA退出保证。不能把“只换key、旧写仍在途”的弱方案作为它的替身，再把等待旧写退出包装成创新。当前值得继续判别的是安全撤销的作用范围、资源成本，以及对仍正常运行的任务的影响；这些代价尚未校准。

总体目标仍是面向MoE推理Scale-Out的网络与系统鲁棒性。平台功能通过不等于A类论文贡献成立。本轮固定平台`a30296c`，仅做来源和CPU控制逻辑核查，没有修改仿真行为、执行新网络或运行GPU。

## 一、哪些事情已查明

| 对象 | 本轮证据 | 能得出的结论与限制 |
|---|---|---|
| mlx5正常MR撤销 | `mlx5_umr.c:383`起注释明确承诺退出DMA；`mlx5r_umr_revoke_mr`构造禁用WQE并调用等待函数 | 所选正常路径有强退出边界，不能建模成零成本改key。保证来自驱动原文，没有实测DMA |
| mlx5完成与错误 | 等待函数阻塞到UMR完成，存在恢复/flush重试；注销先撤销，再释放umem，撤销失败可提前返回 | 恢复耗时、失败和设备内部错误必须区分。内部错误分支直接返回0，不能把“返回0”单独当作硬件正常栅栏已执行 |
| RXE快速失效 | `rxe_invalidate_mr`只接受MEM_REG类型，拒绝普通USER MR及有绑定MW的情况 | 快速失效不是普通用户MR注销；MW是内存窗口，不能与MR混用 |
| RXE已持有引用的写 | 查找核对完整key、保护域、权限、VALID状态并持有引用；复制函数不再次检查状态 | 在记录型调用顺序中，先取引用、再快速失效、再复制可以继续写。不是实际并发应用合法性证明、生产漏洞或真实DMA |
| RXE普通注销 | 正常清理先移除索引可见性、释放owner引用、等待已有引用退出 | 正常排空与快速失效不同，必须保留较强基线 |
| RXE异常超时 | v6.12的清理超时仍走cleanup；注销包装函数记录错误并返回0 | CPU替身记录了分支，没有释放后使用。超时常数200的单位是jiffies，不能直接当200ns或200ms；不能推广到其他版本/provider |
| 有限key复用 | RXE低8位生成只排除上一个值；快速注册允许同索引历史低位值再次使用 | 65,280个不同前后值对及A→B→A核查说明“永不复用”没有此源码依据，不说明生产碰撞概率或现代用户MR复用频率 |
| 现代共享窗口 | 固定NCCL的GDAKI注册MR并交换rkey；固定DeepEP主窗口覆盖workspace和GPU buffer，另有可选storage窗口 | 所选路径没有免费按专家撤权依据。不能据此声称每进程、每NIC或所有服务恰好只有一个MR |

## 二、对仿真器具体意味着什么

1. **撤权与退出必须分开。** 不再接受新查找，只说明新访问被挡住；已经授权的访问是否仍能写，必须由provider的退出保证决定。当前MRT1是本地功能模型，不能仅加一个key字段就声称重现RoCE或mlx5。
2. **复用必须等待有依据的事件。** 后续应区分停止发起、目标拒绝新访问、旧访问退出、源重传资源释放、重新注册与新key发布。业务完成、源ACK和目标安全复用不应共用一个未经解释的时间点。
3. **记录实际覆盖范围。** 覆盖对象至少包括设备/保护域、MR实例、key、地址区间、注册生命周期。若同一范围还存在另一NIC或别名注册的访问权限，单个MR的撤销不能代表所有访问渠道已经退出。本轮没有核完NCCL上层全部注册扇出，不能假定multi-rail已被一个事件覆盖。
4. **按实际共享范围计算影响。** 专家共享主窗口时，撤销其注册权限可能影响其他专家或控制数据。具体哪些任务停顿、是否可用其他注册区继续，必须由地址布局、依赖和真实注册关系决定，不能预先规定“整个集群全部重启”制造收益。
5. **错误和未知成本保持显式。** 超时、撤销失败、设备失效时不自动释放或换key继续成功；正常UMR等待和重新发布成本在有实测前保持未知，不以随手填的固定延迟报告性能收益。缓存、注册额度和备用窗口按相同总资源计入比较。

以上是下一轮平台修改要求，本轮没有把这些要求写成已实现能力。现有有界缓冲、实际ACK回收、源隔离和有序载体仍保留各自已验证范围，不能据本报告升级为真实provider恢复模型。

## 三、下一步如何判断创新是否存在

先比较四类有明确语义的方案：应用协同停止并排空；正常provider整MR撤销；预先划分多个注册区；备用窗口切换后等待旧区安全回收。后两类都是已有机制组成的基线候选，不能先命名成新算法。各方案必须承担相同的MR额度、备用内存、通知成本和可见信息，并只在其合法支持的调用时机运行。

竞争解释如下：如果正常整区撤销已足够快、正常任务本来就被同一屏障阻塞，局部恢复可能没有业务价值；如果差异全部来自额外备用内存或更细预分区，应归给资源/布局；只有在这些强基线之后仍存在稳定、可消除的额外等待，才值得设计新机制。安全性和性能应分别评价，不能用减少等待换取尚未退出的旧写覆盖。

后续需要匹配硬件或可信provider回调测量：撤销开始/完成、已授权访问退出、重注册和rkey发布、正常任务暂停区间、源端积压、控制消息与重传。完成时间应沿共享网络和应用依赖实际推进，不能把可重叠的几个阶段耗时直接相加。留出请求、不同热点/故障位置、不同EP组及multi-rail另设对照；四份路由不能代表千卡生产故障分布。

安全研究目前限定为恢复过程中的旧访问隔离，不声称发现远程攻击、合法可触发漏洞或厂商安全缺陷。真实并发调用约束、MW细粒度方案、QP退出保证、别名注册和现代GPU可见性仍需独立核实。

## 四、检查与复现

12份源码完成SHA256/Git blob核对；12个精确原函数在记录型替身上编译执行。独立核验按原文行区间复取全部16项主张，并拒绝四类结论篡改，见[verification](../../experiments/target_retirement_contract/results/20261024/verification.json)。替身包含单线程引用、索引表、确定等待结果、数组复制和固件等待记录；不提供硬件性能结论。

初次raw获取被60秒上限停止；`urlopen(timeout=8)`没有限制整个请求wall，部分请求约16秒，保留为违反原单请求目标的失败。随后在同一固定提交改用contents API，8份文件取得并核blob；没有原样重跑raw批次。初版分析器误选前置声明，已修正定位且确认已编译12个函数字节完全未变，见[correction](../../experiments/target_retirement_contract/results/20261024/correction.json)。补齐主窗口摘录的hash后才完成独立核验，没有删断言保住结论。
