# 真实路由共选与网络偏斜：八组受控分析

本轮得到的结果是：在已声明的四卡专家并行场景中，即使每个专家被选中的次数完全相同，改变同一个 token 选择哪些专家，跨卡 Dispatch 副本数仍增加了 14.44%—14.68%。因此，仿真负载若只复现“哪些专家热门”，仍可能改变通信工作量。另一方面，累计通信完全相同，也不能确定每个短窗口的入量分布。

这是一项使用真实输入的离线机制判别。本轮没有运行 GPU 或网络，没有得到时延、拥塞或算法收益；上述非线性关系可由去重公式解释，不能单独作为论文创新。它为后续网络实验筛出了必须保留的输入结构，尚未证明已有平台普遍存在多大误差。

## 一、服务什么问题，固定哪些约束

最终目标是让 scale-out 联合仿真能够可信地比较 MoE 推理网络方案：改变专家放置、网络结构或通信方式后，判断哪里排队、为何拖慢、方案排序是否可信。当前具体检验的问题是：用随机专家选择、热点直方图或累计通信矩阵代替原始路由，会丢失哪些网络相关信息？

| 项目 | 本轮采用的值及边界 |
|---|---|
| 原始输入 | 用户提供的 1472、1808、2675、6447 四份 JSON，均来自数据集的 cognitivecomputations/DeepSeek-R1-AWQ/mmlu 目录；固定数据集 revision，四份 hash 均核对 |
| 模型观察 | DeepSeek-R1-AWQ 路由，256 专家、每 token 选 8 专家，层 3—60；不假定量化观察等同所有精度和生产配置 |
| 推理阶段 | 仅 entry 1—128 的 Decode；entry 0 的 Prefill 不纳入 |
| 并行/请求 | 专家并行 EP=4，每 rank 一个请求、每窗口一个 token，共 4 个 token；每 rank 64 专家。它是条件映射，不代表完整 R1 能装进四卡，也不表达完整 TP/DP 部署 |
| 窗口定义 | 同层、相同 Decode 位置组成一个窗口，共 58×128=7,424 个；没有真实时间戳，不认为四请求实测同步 |
| 通信语义 | 固定现代 DeepEP direct Dispatch，源 token 对每个目的 rank 只计一份数据，本 rank 的数据另计；本轮不核算 Combine 或完整控制操作 |
| 网络/GPU | 不选择 GPU 计算 profile，不执行拓扑、NIC、路由、包或队列；EP4 是逻辑通信组，不是千卡实测 |
| 数据范围 | 四请求不是训练热点分布或生产总体；所有结构扰动都不是重新运行模型所得的合法路由，不能据此讨论模型准确率 |

固定配置及预算见[协议](../../experiments/paper_readiness/route_controls_protocol.md)和[配置](../../experiments/paper_readiness/route_controls.json)。现代去重的源码依据见[源码/路由核查](../review_artifacts/nccl_gin_20261022/report.html)，完整数据布局见[布局核查](现代通信布局与并发槽位_20261022.md)。

## 二、八组输入怎样比较

第一组是原始路由和连续等量专家放置。第二组把四请求分别循环移动 0、17、43、79 个位置：每请求的 token 选择、循环顺序、专家热度、累计专家矩阵和累计去重矩阵都不变，只改变请求之间的对齐。这是相位敏感性对照，没有真实到达时间的含义。

第三至五组在每个请求、每层的 token—专家二部图上做合法的双边交换，三个种子事先固定，各固定 4,096 次尝试。每个专家出现次数和每 token 恰好 8 个不重复专家保持不变，但 token 内共选关系及时间结构改变。因此，累计跨 rank 专家贡献矩阵不变，而去重后的 token 副本数未必相同。复核确认 696 个请求/层/种子单元的度数守恒，三组各有 29,696 个 token 选择集合改变。有限交换没有证明均匀采样或充分混合。

第六至八组保留原始选择，每层生成一次随机、等容量专家放置，并让所有请求共用。它同时改变本地旁路、去重、副本目的地及计算输入分布，不能将全部差异归因于某个单独网络因素，也不能叫作优化算法；没有迁移成本评估。

准备、分析和评价分别执行。准备程序读取原件，分析程序只读取 observed 下的路由和放置；独立评价程序回查原件、各不变量和每窗口的 16 个矩阵项，不导入分析程序或平台内部实现。

## 三、结果一：专家热度相同，去重通信量仍不同

| 条件 | 跨 rank token 副本 | 相对原始 | 跨 rank 专家贡献 | 入量最大/均值 p50 | p95 | 最大值 |
|---|---:|---:|---:|---:|---:|---:|
| 原始 | 69,409 | 基准 | 176,567 | 1.3333 | 1.5000 | 2.4000 |
| 请求相位移动 | 69,409 | 0.00% | 176,567 | 1.3333 | 1.5000 | 2.0000 |
| 共选交换，种子 2026102201 | 79,599 | +14.68% | 176,567 | 1.0909 | 1.3333 | 1.7143 |
| 共选交换，种子 2026102202 | 79,600 | +14.68% | 176,567 | 1.0909 | 1.3333 | 1.7143 |
| 共选交换，种子 2026102203 | 79,432 | +14.44% | 176,567 | 1.0909 | 1.3333 | 1.7143 |
| 等容量随机放置，种子 2026102211 | 80,627 | +16.16% | 178,968 | 1.0909 | 1.3333 | 1.7143 |
| 等容量随机放置，种子 2026102212 | 80,376 | +15.80% | 178,108 | 1.0909 | 1.3333 | 1.7143 |
| 等容量随机放置，种子 2026102213 | 80,544 | +16.04% | 178,136 | 1.0909 | 1.3333 | 1.7143 |

表中是数据操作数，不是 RDMA 包数。固定每份 token put 布局时，副本数变化可按比例换算这部分数据字节；不能直接换算完整线上字节、完整两阶段通信量、网络时长或吞吐。

原因可以用一个小例子说明：源卡有两个 token，每个选两个专家；a、b 在目的卡 1，c、d 在目的卡 2。若两个 token 分别选 {a,b} 和 {c,d}，共发两份；若改为 {a,c} 和 {b,d}，则共发四份。每个专家都出现一次，区别只在于哪些专家被同一个 token 选中。

一般地，源 token t 选中的专家集合为 S，专家所属 rank 为 owner(e)，则目的 rank d 的数据份数是指示量 1{存在 e∈S 且 owner(e)=d}，跨 rank 份数再排除源 rank。专家计数使用加和，这里使用“是否至少出现一次”，所以不能从边际频次唯一恢复去重流量。本轮给出的是这一已可解释关系在四份具体输入中的量级，而不是发现一个新去重原理。

对工作负载生成器的直接要求是：至少保留每 token 的专家组合与专家到 rank 的映射；只拟合专家热度，无法保证现代 direct 的通信量正确。对于是否实际忽略这些信息的特定平台，仍需按版本和接口查证，不能给所有竞品统一打叉。

## 四、结果二：累计矩阵相同，窗口分布仍变化

相位对照累计副本同为 69,409，完整累计专家矩阵和去重矩阵逐项相同。但 7,424 个窗口中，7,239 个窗口的去重矩阵改变，占 97.51%；5,353 个窗口的目的入量最大/均值改变，占 72.10%。

两组 p50、p95 相同，最大比值由 2.4 变为 2.0。这个结果说明累计量不能唯一确定窗口序列，也提醒不能仅看一个极值宣布整体长尾改善。由于窗口未绑定实测发起时间，这还不能说明真实突发持续时间、交换机队列长度或重叠程度，更不能说相位控制在生产中可执行。

后续网络输入应保留每请求的 token 次序、必要的执行依赖及来源不确定性。若没有实测调度，应声明到达/计算假设并做有界敏感性分析，不能把对齐窗口直接当成真实同时发包。

## 五、结果三：“更均衡”的比值可能来自发送更多数据

以下是看到主结果后，从已有矩阵追加的代数诊断，不是事前协议的主要指标；没有因此重跑或挑选对照。

| 条件 | 最忙目的 rank 收到 2 份的窗口 | 收到 3 份的窗口 | 绝对最大入量 p50 / p95 |
|---|---:|---:|---:|
| 原始 | 286 | 7,138 | 3 / 3 |
| 请求相位移动 | 282 | 7,142 | 3 / 3 |
| 共选交换 2026102201 | 20 | 7,404 | 3 / 3 |
| 共选交换 2026102202 | 21 | 7,403 | 3 / 3 |
| 共选交换 2026102203 | 28 | 7,396 | 3 / 3 |
| 随机放置 2026102211 | 13 | 7,411 | 3 / 3 |
| 随机放置 2026102212 | 15 | 7,409 | 3 / 3 |
| 随机放置 2026102213 | 11 | 7,413 | 3 / 3 |

比值定义为 4×最大入量/总副本数。增加其他卡的入量，就可能在最忙卡负担没有下降时降低比值。在第一组共选交换中，相比原始比值下降的 5,188 个窗口里，5,082 个的绝对最大入量没变，91 个反而增加，只有 15 个下降；其中 5,173 个窗口的总副本数增加。独立检查保存了其他条件的逐窗口配对数。

EP4、每源一个 token 的去重模型中，每个目的 rank 最多收到其他三个源各一份，因此绝对入量上限为 3；各条件的分位数接近这一结构上限，区分力有限。这个局限也不能靠称它为“千卡热点指标”来掩盖。

后续比较需要同时给出总数据量、绝对瓶颈服务量、相对偏斜及网络完成时间。这里的绝对入量只是一个 rank 的 token 份数，也不等价于 NIC/rail 或交换机链路负担；多 NIC 分流、控制流、响应和共享上行仍需执行模型解析。

## 六、怎样推进论文，而不是堆功能

| 当前能支持的判断 | 当前不能支持的判断 | 下一项有判别力的验证 |
|---|---|---|
| 本条件下，边际热度不足以决定 modern direct Dispatch 数据份数 | 某个现有仿真器一定产生了 15% 时延误差 | 固定具体平台版本和负载生成方式，确认其保留哪些字段，再比较实际输出 |
| 累计矩阵不足以恢复构造窗口的分布 | 已发现真实系统的同步突发拥塞 | 接入有依据的执行依赖或实测时间；比较完整路由、热度替代、累计矩阵替代 |
| 比值下降可以伴随总工作量增加 | 随机放置是有效的网络优化 | 同时比较绝对服务量、实际队列、端到端完成、计算负载和迁移成本 |
| 四份输入可用于有限、可重复的机制判别 | 已覆盖训练、生产热点、不同模型或千卡部署 | 取得独立留出请求；分别设计更大 batch、EP/DP/TP 组合及千卡拓扑，保留超时和无差异结果 |

下一阶段主问题应收敛为：忽略 token 共选或请求对齐，是否会改变网络方案的排序；若会，哪些最小输入结构足以恢复排序？先做可信的正常无故障对照，并事先规定业务指标及反证：若更强基线或执行语义消除差异，应如实缩小或放弃该论文主张。

平台侧已有原生持久连接、真实事务负载、接收窗口等待和源队列前缀屏障，但尚未组成完整现代 DeepEP/GIN 性能模型。尤其 self-peer GIN 的物理路径、provider/CQ 服务与 GPU 可见性不能补成零或凭空拟合；当前 MRT1 功能协议不等价 RoCE/GIN。应先补足会影响比较的语义和成本依据，再向同一原生网络注入两阶段与控制流，全部组共用网络状态，不相加独立仿真耗时。

目前可见 A100 和禁用的 RDMA 条件不满足固定现代分支的匹配校准，见[校准条件](../review_artifacts/calibration_readiness_20261022/report.html)。不得以这轮离线结果代替实机校准，也不得把四请求复制成千卡生产样本。历史 1024 卡长工作量仍未完成；目标保持进行中。
