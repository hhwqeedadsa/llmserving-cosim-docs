## 一、先回答老师的五个问题

| 老师关注的问题 | 本项研究的回答 |

**研究主线可以集中表述为：真实MoE流量在共享Scale-Out网络中，如何由专家偏好和物理放置形成通信长尾，以及在资源约束不变的情况下怎样改善。**

参照刘江川CoolStreaming/DONet案例，值得借鉴的是从代表性系统问题出发，提出机制、通过系统与实验验证，再沉淀论文和可复用平台的路径。本项目目前已形成较完整的实验能力，但“接通多个仿真器”“支持千卡配置”“发现热门专家”本身还不足以构成新的机制论文。[S15]

## 二、服务场景与研究边界

### 2.1 当前服务的具体业务

一次MoE Decode可以理解为：若干请求各生成一个新token；每个token选择少数专家；输入送到持有这些专家的GPU；专家计算后返回结果；依赖满足后继续下一层，最终推进下一轮Decode。

若专家位于其他服务器，Dispatch和Combine会经过NIC及交换网络。多个推理副本即使不相互交换业务数据，也可能共用同一个ToR、Agg或Core出口。一组业务的发送因此可能推迟另一组的数据就绪，进一步推迟消费者计算和下一轮服务。

本平台近期服务三类使用者：

- **网络研究者**：定位NIC、上联、路径和流控引起的关键等待，验证网络感知通信方法。
- **推理部署研究者**：比较EP大小、模型副本、专家放置和组批的代价，理解为何计算均衡不等于网络均衡。
- **组内及合作研究者**：复现实验，修改输入，检查结论是否随负载和网络变化。生产选型需要额外校准。

## 五、现在前端究竟输出什么，怎样注入后端

### 5.1 当前链路

```text
请求/上下文/模型结构/专家选择/专家放置/计算成本
                  ↓
LLMServingSim调度：选出本轮请求和每卡batch
                  ↓
本项目生成执行计划及每rank的Chakra任务图
  COMP：计算节点及声明持续时间
  SEND/RECV：源、目的、有效字节、标签、前驱依赖
  来源：请求、原始层号、Decode入口及专家选择
                  ↓
ASTRA：前驱完成后发起任务；SEND只发送一次，RECV只等待
                  ↓
同一ns-3中的机内织构或跨机RDMA
                  ↓
接收连续数据齐备→消费者继续；完整ACK→发送资源回收
                  ↓
组内本轮完成→返回前端→推进请求并决定下一轮
```

**输入给后端的是“需要做什么、依赖什么”的任务图，数据包与完成时刻由本次网络执行产生。** 没有把解析模型算好的结束时间塞给网络，也没有将每条流独立仿真后相加。

网络结果保存消息、实际路径、接收/ACK时刻、端口和队列摘要；前端保存请求推进；图与节点日志用于核对计算释放。`queue_capture=summary`只保存摘要，不提供完整队列时间序列，不能从没有详细事件推断没有排队。

### 5.2 旧链路与现在的区别

旧链路从LLMServingSim提取选定Block，投影出Ring/Tree peer任务，网络完成只推进该Block回放内部阶段；完整请求指标仍由analytical路径给出。新链路将网络完成回报给实际服务控制，能推进下一轮Decode。

但**反馈范围扩大，不等于所有模型与阶段已迁入**。当前真实R1输入只执行有限MoE层段；不能把其结果称为完整R1每token时延或TTFT。[S1][S4][S7][S11]

| 完整形状百卡/规模基准 | Qwen3-30B-A3B，48层，H2048/F768/E128/K8，GQA，BF16；参数量30,532,122,624，约30.53B | 每卡batch1，context2048，2步Decode | H100标签，声明成本，设备容量声明80 GiB | 16/128单EP；256/512/1024多EP4副本，机内＋RDMA |

H为隐藏维，F为路由专家中间维，E为路由专家数，K为每token选中专家数。参数量是模型容量口径；每token激活参数、单卡权重占用和网络消息大小是不同的量。R1来源不意味着当前入口执行了其全部参数和Attention结构。

当前服务输入校验的数值边界为：H为64—8192、F为64—32768、E为2—256、K为1—8且不超过E，激活每元素1—4字节。有限片段支持1—4层，完整结构入口支持1—128层并要求额外GQA/容量字段；合成输入为2—4步Decode，来源回放为1—128步并受原件窗口约束。GPU描述标签接受A100、H100、A800、H800、NONE。**通过这些数值校验只说明输入可表达，不代表任意模型架构都支持，更不代表已经执行或校准。**

### 6.2 batch和上下文怎样影响网络

当前`batch_per_rank`表示**每卡每轮请求数**。一组EP4中，B1对应4个请求，B4对应16个请求；1024卡、256个EP4副本在每卡等量时分别有1024/4096个请求。当前输入校验允许每卡batch 1—16，不保证全部组合已执行通过。

Decode时每个选中请求每轮新生成一个token。`context_tokens=2048`表示已有KV长度，不表示每轮向专家发送2048个token。增加context主要改变KV容量和Attention成本；增加batch会改变本轮token量、专家贡献、计算和通信。

真实回放中，增加batch需要更多独立请求文件，不能把同一文件相邻Decode入口当作多个并发请求。本次只有四个原件，不能无说明地复制成千卡真实独立请求。

修改模型、batch、专家放置或通信模板后，要重新构图、执行和核验。旧结果或Trace乘一个倍数不能代替新的实验。

### 6.3 EP与“DP”什么时候选

- **选择EP**：单卡难以容纳专家，或希望分散专家计算时，将一个模型的专家分配给多卡。收益是容量与并行计算，代价是专家交换与同步；组越大不一定越快。
- **选择多个推理副本**：一组EP已能容纳模型后，复制多组以承接更多请求；组间不交换本轮专家输入，但可能争用相同网络。这里可称复制部署，不能与训练DP梯度同步混淆。
- **选择时应比较同一服务目标**：固定总GPU、模型、请求量和容量约束，比较EP4×多副本、EP8×较少副本等方案；同时列出权重复制量、每副本batch及跨机字节。

当前E128要求EP整除128，不能直接设EP1024；千卡基准实际为256个EP4。旧EP320设想涉及冗余专家、shared expert和芯片/die映射，需要另外表达，不能只改一个EP数字。[S1][S8]

## 七、Scale-Out网络怎样连接，哪些带宽可以改

### 7.1 已形成的拓扑表达

可参数化两层leaf-spine、三层ToR—Agg—Core、Agg汇聚结构、multi-rail和参考HPN的双平面。Pod、Segment、每服务器GPU数、各层交换机数量、上联扇出及链路层速率可以在已开放范围内配置。

- **ToR、Agg、Core**分别表示接入、汇聚和跨Pod核心交换层。
- **rail**按GPU/NIC位置划分接线组，是否可跨rail通信取决于上层连接和中继能力。
- **plane**是不同网络平面。双平面需要声明NIC端口与总带宽；多一份网络不天然公平或更快。
- 用户图中的**OCS已按普通分组交换Core处理**，没有光路重构、时隙或光交换调度。

当前生成器不是任意图编辑器：各Pod等规模、速率按链路层设置等限制仍存在。HPN参考结构不是阿里生产网络完整复刻；静态生成四种千卡候选也不等于四种均已完成性能比较。[S6]

### 7.2 历史千卡实际输入

| 对象 | 实际配置 |
|---|---|
| GPU、服务器、Pod | 1024GPU；128服务器，每台8GPU；8Pod，每Pod16服务器 |
| 交换层 | 32 ToR、16 Agg、2 Core；单rail、单plane |
| 外部边 | 1024接入＋64 ToR–Agg＋16 Agg–Core＝1104条 |
| 逐边外部容量/传播 | 每方向400 Gb/s；1 μs |
| 机内抽象 | 每GPU每方向450 GB/s；16 KiB分块；进、出织构各100 ns |
| 专家部署 | 256个EP4副本；每卡32个专家；例如组[0,1,512,513]跨两个Pod |
| 跨Pod路径 | GPU→ToR→Agg→Core→Agg→ToR→GPU |
| 容量限制 | ToR下/上容量16:1；Pod接入/跨Pod出口64:1；是超售参考基准 |

400 Gb/s约为50 GB/s，不能与450 GB/s混用单位。每个Agg只连分组中的一个Core，不能按示意图误认为全互连。上述容量比不等于实际时延或吞吐下降倍数，也不是生产网络推荐。

### 7.3 应分别检查什么共享资源

| 位置 | 可改变的因素 | 需要回答的问题 |
|---|---|---|
| 机内GPU入口/出口 | 机内速率、分块和并发 | 机内转发会不会先限制跨机发送？ |
| GPU—NIC | NIC数、亲和、端口速率和共享关系 | 热点集中在GPU计算，还是少数NIC？当前通用共享NIC/PCIe模型尚不完整 |
| NIC—ToR | 接入速率、端口数、rail映射 | 同服务器不同GPU是否真正分流？ |
| ToR—Agg | 上联数、带宽和组内放置 | 多源是否汇入同一个机架出口？ |
| Agg—Core | Pod出口容量、Core分组 | 跨Pod流量是否比同Pod更易产生关键等待？ |
| 多路径与平面 | ECMP、消息到plane的映射 | 流量是否偏向少数路径，分流代价是否超过收益？ |

公平比较要同时记录GPU总数、NIC总带宽、交换端口和链路资源；不能一边多加链路，一边将收益全记给算法。

### 8.2 新的非UB Scale-Out小规模结果

8GPU、2层、4次Decode的主矩阵已执行10条件×3个路由seed，共30次；另有独立rail用例。主矩阵及rail共31次、42,712个ASTRA节点经独立检查，基线重跑的`result.json`和36个语义/Chakra文件一致。它们是实际有限片段执行，并非静态核算。[S7]

评价首先看消息完成、Dispatch/Combine阶段、消费者开始和Decode片段完成，再用端口服务、队列及协议事件解释。有限层段不是完整模型TPOT；ready-KV Decode不测Prefill TTFT。三种seed和两至四步窗口也不支持生产p99或稳定吞吐结论。后续应在足够请求和轮次下报告尾部分布、吞吐、置信范围和SLO达标情况，SLO指预先声明的服务延迟要求。

| 发现 | 具体结果 | 研究含义 |
|---|---|---|
| 上联瓶颈会传到消费者和后续服务 | 同一seed下Agg→Core由100G降至50G/25G，片段由193.252 μs增至217.751/265.896 μs；首层专家开始随接收依赖后移 | 已验证网络完成的因果反馈；不只是给总时延增加常数 |
| 双plane不自动加速 | 单plane100G为206.393 μs，双plane各50G为220.101 μs；两plane均实际承载流量 | 需检查分配、序列化与路径；不能只凭“多平面”判断收益，也不能称严格等成本 |
| 热专家不等于更高队列 | 50% token选专家0时，片段193.252→209.152 μs，而最大queue 11,272→9,672 B | 计算分布、消息和释放节奏共同变化；队列峰值不能独立解释业务长尾 |
| EP组变化会混入本地化收益 | 两个同Pod EP4较跨Pod EP8的远程payload由1,794,048降至1,507,328 B | 不是“只改EP”的对照；需要分离放置、副本数与负载 |
| 协议开关存在不等于业务中已触发 | 64流汇聚探针触发CE、PFC和DCQCN反馈；主业务未必触发同样机制 | 要看有效参数和真实事件，不能按配置名字归因 |
| 原生RDMA恢复有边界 | 中间包丢失可由后续包触发NACK恢复；尾包丢失无后续包时预期失败 | 当前服务研究限定无故障，故障恢复要另立任务 |

同时修正了ECN输入字节与原生decimal KB接口的单位适配、headroom配置顺序，以及零时长COMP的ASTRA退出状态问题。阿里固定版本探针还验证了`Time(integer)`单位风险及按包长猜发送完成导致的重复/缺失回调；这些结果限定被核查源码和局部探针，不等于整个SimAI端到端误差。[S5][S7]

## 九、接下来应围绕哪些维度更改和优化

平台正确性、仿真效率和被仿真系统性能分开验收，避免“代码加了功能”与“业务得到优化”混为一谈。

| 维度 | 已有基础 | 下一步针对的具体缺项 | 应验收的结果 |
|---|---|---|---|
| **真实负载与batch** | 可改每卡batch、context、轮次；四原件已接入 | 扩展有来源的任务/长度子集；明确到达和并发假设；更长窗口 | 不复制请求凑规模，逐token贡献、KV及网络字节可核对 |
| **专家偏好及时间关系** | 分层分阶段热点统计、顺序保留 | 比较真实顺序、保直方图打乱、均匀控制；检查热点持续性 | 说明是频率、共选还是短时聚集影响网络；预测只用过去 |
| **EP、推理副本与放置** | EP组和逐层等容量静态放置 | 固定总资源与请求量，区分改变EP和改变物理本地性 | 同时报告专家负载、机内/跨机/跨Pod字节、Decode尾部 |
| **通信组织** | 逐专家复制、GPU对聚合的A2A-v | 研究按目的GPU/节点去重、机内汇聚—跨机—机内分发；按真实库核查 | 不漏转发、合并、额外准备、缓冲与元数据成本 |
| **拓扑与逐层容量** | Clos/Agg、rails/planes、各层速率 | 建立合理容量配比及等资源网络对照；核查可达性 | 能区分总容量不足与特定出口热点；多加资源单列成本 |
| **NIC和路径分配** | 每GPU端点及显式部署；稳定plane映射/网络选路 | 按需要补共享NIC资源与跨rail中继，研究消息到plane/rail的分配 | 流真正进入同一物理队列；不把GPU当路由中继绕过不可达 |
| **RDMA队列、流控与CC** | DCQCN、小型incast探针和有效参数审计 | 选定端口有界时序，区分NIC、队列、PFC及ACK反馈 | 给出阻塞依赖与竞争解释；未触发机制不归功于该机制 |
| **计算释放与GPU校准** | 声明成本、旧RTX表、局部A100表 | 测匹配设备/模型/精度/shape的计算与通信，旧Prefill另补真实序列边界 | 在独立验证shape给误差；网络对照固定计算，变化另做敏感性 |
| **服务反馈与诊断** | 已有有限Decode反馈、图与来源记录 | 完善关键等待链，报告影响后续层/轮次的可消除等待 | 区分累计等待、相关性与业务损失，不重复相加 |
| **规模与执行成本** | 128/256/512完成、千卡超时证据 | 拆分构图、ASTRA、逐包与写出成本；先优化表示和记录 | 小例语义/字节/完成一致，明确预算内再验收千卡 |
| **复现与代码组织** | 公开CLI、版本锁、输入快照及独立检查 | 形成紧凑基准、配置矩阵、失败摘要与浏览入口 | 新环境可获取依赖和合法输入，结果能追到版本/配置/来源 |

近期主线建议优先选**网络感知的等容量专家放置或分层Dispatch/Combine**之一。batch、plane和CC先作为控制因素及竞争解释；不在一轮同时开发所有策略。

## 十、需要回答的研究问题，以及怎样验证

### Q1：热点专家什么时候会成为网络热点？

固定同一批真实选择，只改变专家放置，比较本卡、同机、同Pod和跨Pod的目标分布。先核算GPU对矩阵，再看实际端口和Decode完成。热门专家本地化可能减少跨机流量，分散专家也可能降低计算峰值却增加网络复制，因此不能只按专家频率排名给结论。

### Q2：总字节相同，短时到达和释放节奏是否仍影响长尾？

使用保持逐层专家直方图的顺序打乱，记录具体保留条件；与原始顺序及均匀控制比较。不能把token窗口当纳秒窗口，必须由计算/通信依赖生成实际释放时序。若网络本来有足够容量，差别可能很小，应保留这一结果。

### Q3：多rail、多plane和更大EP是否一定值得？

保持总NIC容量和声明工作量，分别控制交换机资源、放置与流分配。检查是否真的多路径承载、是否需要额外机内中继，以及关键消息是否被低速分片拖延。EP比较还要固定服务目标和模型复制成本。

### Q4：千卡逐包仿真怎样做得可用？

先测量每层宿主开销，再决定稀疏图表示、路由/来源复用、有界记录等优化。不能删去争用流或将持续网络拆为独立小仿真来获得“千卡加速”。解析/流级筛选、逐包验证代表性条件是一条长期方法路线，但不同精度结果需要误差验证；当前尚未完成可互换的多精度联合实现。

### Q5：训练热点问题怎样延伸？

现有数据是推理路由。训练还需要microbatch、step、前反向、梯度同步、EP/DP/TP/PP分组、accepted/drop/pad以及实际动态split。已审阅的Megatron分支说明，负载均衡可以在不同统计范围起作用，强制随机路由只是特定选项，不能概括为真实训练默认random。现有SimCCL/ASTRA部分等分A2A路径的限制是丢失非均匀矩阵，也不等于整个仿真器只能随机。

因此，训练先作为独立扩展规划；取得训练来源与依赖后再研究“全局均衡是否仍存在microbatch或NIC窗口热点”，不拿当前四份MMLU推理记录证明训练结论。[S12]

## 十一、每一步的目标、交付物和最终完成标准

以下是后续路线，按前置条件推进，不表示本次已执行，也不是会议截止日期承诺。

| 步骤 | 目标 | 交付物 | 进入下一步的依据 |
|---|---|---|---|
| 1．统一现状与研究口径 | 让老师和协作者明确目标、边界、证据和差异 | 本报告；历史与当前能力对照 | 能明确说出服务对象、网络问题和不支持范围 |
| 2．建立真实路由研究基准 | 在现有四请求可复核链路上，设计规模适当的分层样本 | 来源清单、分层热点统计、请求映射、字节核验与负载说明 | 原始选择保持完整；样本量支持相应结论；无未来信息泄漏 |
| 3．先判断现象是否值得研究 | 证明热点、放置或通信组织对关键网络等待确有影响 | 等容量放置、真实/打乱/均匀、足容量/受限容量对照 | 排除工作量、资源总量和计算差异；业务影响具有实际意义，否则正常收尾 |
| 4．选定一种网络感知方法 | 改善一个明确机制，控制实现复杂度 | 放置或分层传输算法、开销模型、强基线与反例 | 等资源下减少关键等待；计算、迁移、转发和缓冲代价完整计入 |
| 5．补齐目标硬件校准 | 将模型内观察对应到可测系统 | 匹配GPU/NIC/软件的单流、incast及小型多机对照；留出验证集 | 不只拟合均值，还检查阶段完成、尾部误差和方案排名 |
| 6．扩展代表性规模 | 明确方案在128—1024卡的适用范围与仿真成本 | 分规模结果、资源报告、失败记录；千卡预算内完整验收 | 小规模语义保持；无自动扩限；超时不补造业务结果 |
| 7．形成论文和可复用产物 | 让他人验证机制与适用边界 | 论文、配置/输入方法、代码版本、轻量基准、复核网页 | 独立复现、强基线、消融与失效区间完整 |
| 8．验证实际部署价值 | 支持运营方/推理团队减少试错 | 脱敏生产案例、部署建议、容量/资源成本报告 | 预测与真实决策一致，合作方确认价值；此前不声称商业收益已验证 |

实际执行应以小型机制对照为先，硬件校准与效率分析按需要交错推进；不能等所有参数和所有模型均支持才开始研究，也不能在证据不足时先写优化结论。

## 十二、近期与长期论文、工具和产品规划

### 12.1 近期：可靠实验报告与可复用基准

优先完成真实输入下的网络机制问题筛选、来源和字节核验、等资源基线，以及小规模硬件校准条件确认。产出应为技术报告、可审查网页、复现配置和轻量基准；有系统性测量结果后，再考虑相关workshop、poster/demo或测量工具短稿。

近期不以修复一个Profile问题、生成几种拓扑或四请求热点直方图作为独立创新论文。旧Prefill shape问题可作为平台修复与校准工作保留，当前论文主线仍集中在Scale-Out网络。

### 12.2 中期：形成一篇主要论文

建议问题表述为：**真实专家偏好与部署位置怎样共同造成跨Pod MoE通信长尾，网络感知的放置或分层传输在哪些条件下有效？**

需要形成四部分证据：真实输入的代表性问题；可复核的网络机制；一种有成本约束的方法；实机/仿真、强基线、消融及反例。原数据配套论文已研究热门专家、共选、Prefill预测及放置/复制，不能重复“发现热点并调整专家”就声称新贡献；差异应落实到跨服务器共享网络、等容量/等资源约束和Decode等待，而非仅专家计算均衡。[S10]

方向按实际贡献选择：网络测量与机制可考虑IMC、CoNEXT；建模和仿真方法可考虑ISPASS、SIGSIM-PADS；网络算法/系统结合可考虑INFOCOM、ICDCS；Serving系统决策可考虑MLSys。届次、track与截止时间需在确定投稿时查官方CFP。

### 12.3 长期：机制部署与研究平台

若形成新的通信组织、路径分配或拥塞控制方法，并在真实多机系统验证服务收益，再评估SIGCOMM、NSDI等目标；若主要贡献是仿真方法，则围绕精度、速度与决策正确性形成方法论文，而非以支持参数数量论贡献。

工具可沿“复现实验包→网络诊断与方案比较工具→经校准的部署规划工具”演进。产品应让使用者输入模型、请求、专家放置和网络约束，看到瓶颈及有依据的方案差异。商业价值是减少大集群部署试错和错误扩容，仍需云厂商/AIDC或推理团队的实际问题、脱敏数据和决策对照证明。

## 十三、仓库与迭代如何组织

后续代码继续在`/home/lry/moe-ub-cosim`本地维护，保留原仓为历史证据；按已确认要求不push。已有第三方锁定层次继续使用，不再随每轮实验复制平台。

| 位置 | 负责内容 |
|---|---|
| `python/moe_ub_cosim/` | 通用配置、来源校验、服务调度、图生成和公开CLI |
| `backend/rdma/`、既有UB后端文件 | 各自网络实现、ASTRA适配和完成事件；UB与非UB分别构建 |
| `third_party/` | 固定版本的正式依赖；ASTRA及ns-3沿父级依赖管理；对比源码不自动变正式依赖 |
| `examples/`、`tests/`、`fixtures/` | 可运行小例、平台正确性和验收证据；研究不依赖测试fixture驱动 |
| `experiments/<研究问题>/` | 假设、配置、独立分析、结果摘要和反例；按问题组织，不按轮次复制源码 |
| `data/`、`runs/`、`build/` | 原始输入、运行大产物、各后端隔离构建；不提交原始受限数据或二进制 |
| `docs/reviews/`、`docs/tasks/current.md` | 综合报告与当前状态；阶段结果链接到所属实验 |

已有布局建议中的子包拆分是逐步演进目标，不能当作已经完成的大规模重构。平台不导入`experiments/`；实验使用公开命令与读取接口。算法可读观测和评价真值分开，内部来源身份不能改变包的路径、优先级和时延。[S13]

## 十四、可直接用于向老师汇报的集中表述

本项工作的最终目标，是面向MoE推理的跨服务器网络，解释专家路由、部署位置和通信组织如何形成关键等待，并验证在资源约束不变的情况下改善Decode长尾的方法。当前限定在KV已就绪的Decode、EP专家交换和多推理副本共享网络，重点研究NIC、交换机各层出口、路径和拥塞反馈，计算成本与硬件精度单独说明。

前期已完成A100通信测量、仿真平台与Trace研究、代表性Block逐包分析，以及模型、batch和通信参数的统一实验。后续在师兄仓库的因果执行基础上，新增独立非UB Scale-Out链路、可配置Clos/Agg与多rail/plane拓扑，完成小规模机制实验和百卡至512卡验收，并接入四份真实专家路由。现有发现表明，热点专家不必然对应最大网络队列，多平面也不必然加速，专家放置和实际共享出口需要联合研究。

下一步先用真实路由和等容量基线识别值得优化的网络问题，再选择专家放置或分层通信的一条方法，补齐硬件校准、代表性规模和反例验证，形成“问题—机制—方法—论文—可复用平台”的研究成果。千卡完整执行、完整R1硬件性能及生产商业收益目前尚未验收，保留为后续目标。
