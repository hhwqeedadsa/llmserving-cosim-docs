# 窗口注销、底层注册复用与恢复边界

这轮把恢复判断从“某个窗口注销成功”推进到“哪些底层访问渠道真正退出”。**一个用户窗口消失，不代表它覆盖的底层MR已经撤销；多个用户窗口还可能共享同一份底层注册。** 因此，不能在现有静态NIC权限上直接增加一个`revoked`字段，就把它作为MoE故障恢复的安全边界。

这是恢复建模依据的修正，不是论文新机制、生产漏洞或性能收益。平台固定`08bf585`，本轮没有修改平台、执行GPU/provider或运行新网络。

## 实际发现

| 对象 | 固定源码及本轮证据 | 对仿真研究的影响 |
|---|---|---|
| DeepEP正常destroy | 先调用带CPU同步的全体屏障，再finalize窗口；host屏障前后各`cudaDeviceSynchronize`，设备屏障flush各GIN context并等待对端信号 | 正常销毁不是已经验证的故障恢复接口。缺席rank、未退出kernel或失败flush不能被仿真器直接补成成功 |
| NCCL注册 | 由用户地址取得底层分配范围，再做跨rank信息交换及注册结束屏障 | 注册一个替代窗口不能随手建模为单端、零控制流量、任意时刻完成 |
| NCCL公开注销 | 本地创建非阻塞CUDA stream、调用销毁并同步该stream；本函数没有注册路径中的bootstrap集合屏障 | 注册与注销必须分开描述，不能把所有注销都说成集合通信；同步新stream也不能自动等同全部应用生产者已停止 |
| 底层注册复用 | 相同底层地址、大小、段handle和flags可成为复用候选，所有rank的registry候选一致才复用；窗口保存相对底层的offset，并复制底层GIN句柄 | 两个逻辑窗口、两段用户地址不一定是两个可独立撤销的MR。按专家划分窗口不能自动得到按专家撤权 |
| 最后引用释放 | `symMemoryDropRef`只有在引用减至0时逐段调用`ncclGinDeregister` | 一个窗口注销成功而其他引用仍存在，是预期的共享生命周期，不是库错误，也不意味着旧rkey无效 |
| 下层错误传播 | `symMemoryDropRef`为void，未检查`ncclGinDeregister`返回；外层继续清理窗口元数据 | 公开API返回值不能独自充当逐MR退出收据；错误路径需独立核验，不能据此直接声称真实DMA尚存或厂商漏洞 |
| 销毁后段错误 | MR处理之后，窗口表、shadow或本地注册清理仍可报错；公开注销也没有检查最后的stream同步返回 | “返回非零就没有任何MR退出”同样不成立。控制状态、目标权限和元数据必须分别记录 |
| 失败回滚与abort清理 | 分段注册失败只对已完整注册的段调用清理；finalize有剩余窗口遍历销毁 | 上层并非完全没有清理。失败段内部前缀和下层错误仍需保持，完整abort/设备失败保证尚未取得，不能直接推断泄漏或安全性 |

固定NCCL为`12df1a11afad322be5a204a2db890161cbf8131d`，DeepEP为`f6aa38fe06cd4a0489e7730365d4e0114970a2f3`。12份完整来源及14段精确原文见[来源](../../experiments/window_lifecycle/results/20261024/sources.json)与[摘录](../../experiments/window_lifecycle/results/20261024/evidence.json)。新增取得6份小源码/文档、原文191,375B；没有更换版本，也未运行上游安装/构建脚本、下载二进制或完整库；仅执行下述精确提取的CPU控制函数。

## 用原函数实际检查了什么

精确提取并编译`ncclGinDeregister`、`symMemoryDropRef`、`symWindowDestroy`、`ncclCommWindowDeregister`四个原函数。CUDA、provider、shadow、注册表初态和free均为明确记录替身；原函数分支、循环及返回关系保持。没有执行真实GPU调用或释放后访问。

在引用数1—3、段数1—3、每段连接数1—3的432个合成条件中，独立调用顺序oracle核对全部记录：

| 条件结果 | 合成条件数 | 能说明什么 |
|---|---:|---|
| 注销返回成功，但其他引用保留，没有任何MR调用 | 18 | 用户窗口生命周期与共享底层注册生命周期不同 |
| 注销返回成功，但出现下层错误返回 | 72 | 公开结果没有完整传播所选下层错误 |
| 上述条件中仍有访问渠道未取得替身成功退出 | 54 | 不能从公开成功推断全体退出；真实失败provider的状态应记未知，不能直接记“仍有效” |
| 上述条件中全部MR替身已成功退出，后续元数据返回错 | 18 | 不能从下层报错反推MR退出全失败 |
| MR替身全部成功退出，但外层窗口处理返回错 | 36 | 元数据失败和访问退出分别处理 |
| 同步替身报错，公开返回仍成功 | 27 | 最后同步的返回值没有传入ret；不证明真实同步失败可合法触发 |

各行可能重叠，数字不是生产故障率、网络样本或硬件规模。新数据只细化源码控制关系。provider替身返回错误不证明该MR在真实设备上仍有效，也不证明应用在此时调用注销符合支持约束；内存模拟没有真实并发、DMA或GPU内存序。

独立核验不导入提取器或harness，逐条计算期望调用前缀、跨段继续行为、引用及元数据结果，拒绝四类结论篡改。第一次摘要将provider与元数据两类下层错误共用含provider字样的计数名，已改为`lower_error`以免混淆；保留初稿，只重新分析已有记录，没有重跑CPU原函数。补充底层句柄共享的两段摘录，也只重核已有结果。方法及离线复现见[实验说明](../../experiments/window_lifecycle/README.md)。

## 下一次实现应按什么顺序推进

首先增加**应用窗口—底层分配/注册域—分段—逐连接注册实例**的身份与引用关系。上一轮已实现物理字节与静态NIC/rkey权限分离，但还没有表达多个应用窗口共用一份底层注册，不能把用户窗口数量当作独立撤权单元数。相同分配范围不意味着一定复用：flags、段handle和跨rank一致性条件都必须保留。

再把结果拆为窗口已失效、底层引用仍存、MR退出已确认/未知、元数据清理成功/失败。成功退出仍沿用已核实的mlx5正常强保证，不改成弱key开关；所有覆盖渠道和应用生产者停止条件都满足后，才能讨论物理范围复用。当前公开API没有暴露这些逐项收据；若未来方法需要它们，必须说明新增provider接口与实现代价，不能让在线算法读仿真真值。

随后比较同资源强基线：协同停止并排空；正常整底层MR退出；预先使用独立底层分配而非仅切逻辑窗口；备用独立分配切换后等待旧区退出。后两类必须承担相同的额外内存、MR和控制通知成本。正常任务停顿要由实际共享域、应用屏障和网络进度决定，不能把整群重启预设为唯一对照。

最后才进入收益实验。需要先确认受支持的故障类型与调用时机、失败设备的退出保证、下层错误的真实处理、重注册/rkey发布成本及可用校准硬件。如果强基线已消除差异，或方法必须等待同样的全局屏障，应收尾候选；不能用更多生命周期状态数量替代创新。当前四份请求、现代完整网络接入、硬件条件与千卡完整执行的既有缺口仍在，A类论文及整体目标没有完成。
