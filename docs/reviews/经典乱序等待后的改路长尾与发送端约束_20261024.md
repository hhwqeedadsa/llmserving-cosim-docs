# 经典乱序等待后的改路长尾与发送端约束

2026-10-24，平台固定`fa6f001`。本轮完成三次新的包级网络执行，另外三份立即恢复结果只读取上一实验的固定归档。没有新增第四次网络，没有搜索等待参数，没有修改平台或依赖。

## 核心结论

经典16us乱序等待显著削弱了旧解释：旧stream12在立即改路时重复发送的218,688B降为0，两种故障条件都更快。但立即改路仍比延迟改路晚8.986us，而且发送的总字节反而更少。说明旧异常不能完全归因于那条流的重复发送，也不能靠“字节更少”推出“应用一定更快”。

这不是一种新算法的收益证明。当前价值是排除了弱基线下的部分解释，并暴露了下一步必须核查的源端限速与调度等待。论文创新、真实硬件泛化及可消除收益仍未成立。

## 原有解释哪些还成立

旧立即改路时，stream12的218,688B重发对应的初始副本最终全部送达。本轮相同条件下该流完全没有重发，因此不能继续把整个剩余长尾称作这条重复流造成的拥堵。

延迟改路条件下，这条流仍重发39,344B：初始副本真正丢失14,000B、重发前已经到达22,000B、重发时仍在途3,344B。有限固定等待没有消除全部乱序重复发送。这个分类使用了事后结果，只用于评价；源端当时并不知道最终结果，不能把22,000B直接称为可避免流量或可回收收益。

旧突出展示的work24现在反而快9.142us。继续使用它说明“立即改路更慢的瓶颈”，会混淆不同基线下的机制。

## 剩余8.986us如何传到应用

分析保留全部216原始节点、76次写和全部并列最晚前驱，没有重排或删除依赖。以下为相同工作在立即条件相对延迟条件的精确时间差，不是可独立相加的全局因果贡献。

1. 首步work10接收晚16.036us，源就绪和见证包相对就绪发送没有差别，差距都发生在实际输出队列中。15→17端口等待从0.119增到14.227us，其间实际服务包含stream12的**初次发送**7.172us，而不是旧解释中的重发。其他流及控制帧也共享端口。
2. 第二步work99属于保留的最终并列前驱。其接收晚12.670us，精确等于就绪晚3.819us、见证包相对就绪上网晚18.106us、包在途队列等待少9.255us，固定路径传输差为0。
3. 最后的work123就绪晚12.670us，就绪后到ACK反而快3.684us，最终应用仅晚8.986us。两条件该接收见证包的输出队列等待都为0。这条最后消息继承了上游就绪延迟，不能仅看其自身队列就断言“网络没有影响”。

逐包服务量和真实前驱可以证明上述核算，却没有证明把某一流删掉会得到同等收益，也没有给出唯一的跨流因果链。

## 为什么继续核查发送端

work99在两条件都是29包/57,344B连续数据，没有本段重发。首包在任务就绪当时就上网，因此18.106us差距不是整段任务最初等待发布或准入造成的，而是在发送这29包的过程中累积。

| work99发送序列 | 延迟改路 | 立即改路 |
|---|---:|---:|
| 首包TX/ns | 319,820 | 323,639 |
| 末包TX/ns | 342,379 | 364,304 |
| 首包至末包跨度/us | 22.559 | 40.665 |
| 按下一次可发时刻累计的间隔/us | 14.552 | 28.973 |
| 已可发到实际TX的累计时间/us | 8.007 | 11.692 |
| 其中实际源NIC物理发送服务/us | 0.511 | 0.556 |
| 其中源NIC空闲/us | 7.496 | 11.136 |

每一相邻包的间隔按“前包TX→调整后的可发时刻→本包TX”划分，因此表中后两种时间没有重叠。可发时刻随参考控制器的实际速率更新调整；它不是不受其他条件影响的反事实限速代价。

发送开始时，立即条件的持久QP参考速率约11.108Gbit/s，延迟条件约23.987Gbit/s。各自恢复定时器到期后分别约16.577和35.704Gbit/s。在这段发送过程中没有新的CNP降低该QP速率，只有既有恢复定时器；差异继承自先前真实拥塞反馈和持久连接状态，而不是每条消息重建空白连接。

独立核对56个相邻包间隔，下一次可发时刻符合固定原生`PktSent`与`ChangeRate`的整数传输时间；真实源NIC物理发送不重叠。该端口PFC暂停/恢复计数均为0，发送窗口大于整连接总字节，不能用PFC或窗口约束解释这里的全部等待。

但可发以后仍存在端口空闲，当前记录没有完整的调度队列成员、每次选队及唤醒事件，无法唯一解释这部分。源码中原生`QbbNetDevice::DequeueAndTransmit`在无可发包时遍历QP求最小`m_nextAvail`；是否被没有待发字节但尚未确认结束的QP影响，需要用独立最小用例核验。**这只是源码支持的待验证候选，不是已经证明的仿真器漏洞。**

下一步应先验证源调度唤醒的正确性和控制器依据，再研究恢复限速或公平排程。不能把可能的模型/调度偏差包装成MoE机制创新；若发现平台缺陷，先做独立平台修复，再另立协议重新生成受影响研究结果。

## 输入代表性和限定约束

四个请求来自用户确认的`cognitivecomputations/DeepSeek-R1-AWQ/mmlu`目录，文件1472、1808、2675、6447，数据集revision为`27febb7b2d24169560a9f6f83d38eb53f94916cf`。专家选择来自真实记录，但本实验只投影两层两步，使用旧贡献复制和声明计算。216原始节点、76次写、2,609,152B及跨步/资源前驱保持；rank0/2/4/6活动，其余四GPU空闲。

拓扑为单plane Clos，100G接入/25G上层，每跳1000ns；两故障条件都在4us失效，本地剔除实际坏口，全局更新分别为16us和4us。payload2000B、chunk8000B、接收524288B、窗口522289B，每连接全部≤444416B；RTO80us、上限640us、最多3次。唯一新字段是16us有界NACK等待，不改变图、映射、路由规则或队列参数。

因此这是小型、单工作负载的强基线判别。不是现代DeepEP/GIN完整语义、A100实测校准、生产负载统计、千卡完整应用或独立留出验证。DCQCN为显式功能参考，也不是硬件吞吐测量。
