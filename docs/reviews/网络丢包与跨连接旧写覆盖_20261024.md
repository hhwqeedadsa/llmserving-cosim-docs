# 网络丢包下的旧写覆盖：实际反例与接纳修复

本轮发现并修复了仿真器自身的一个顺序校验缺陷：源端“已经准备请求”，不能证明请求已经写入远端。原校验把所有依赖祖先都当作重叠写的顺序证据，导致旧请求丢包延迟后，新连接可以覆盖同一地址，随后旧请求重传再次覆盖新结果。网络和内存执行本身按输入运行；错误在于把不满足既有安全约束的输入当作合法程序接纳。

## 实际发生了什么

使用8 GPU小型100G Clos，两个GPU0→GPU4连接，共享一个原生ns-3时钟和网络。旧请求写8字节`11`；源端收到本地prepared后启动20μs声明期限，随后另一连接写8字节`22`，再在独立计数位置加2。目标端有100μs声明本地工作，完成后只检查本地计数等于2，再真实复制数据到输出。

旧请求第一个数据包在GPU4物理接收端真实丢失一次，80μs源重传。没有把故障时刻/接收真值交给源端，也没有靠固定通信时间跳过前驱。20μs和100μs是本测试声明的期限与本地槽占用，不是GPU实测，不表示完整推理调度。

| 事件 | 改前不安全输入的实际时间 |
|---|---:|
| 旧请求准备、发布、首次源TX | 0ns |
| 旧请求首包物理丢弃 | 6,036ns |
| 新连接写入`22` | 26,036ns |
| 新通知计数变为2 | 38,096ns |
| 旧请求重传后写入`11` | 86,036ns |
| 目标检查到计数2并实际复制 | 100,000ns，复制到`11` |

原程序最终`passed=true`，但这不等于应用拿到本轮数据。独立检查从实际源包解码MRT1，对照端点TX/RX/drop，重放目标写入及复制，确认复制结果来自迟到的旧写，而不是绘图、标签或终态统计误差。

## 做了什么修改

现在分别维护完整控制依赖和已证明的远端副作用顺序。prepared只保留前驱已成立的完成事实，不证明它自己的写入已经到达；本地等待完成也不能升级这个事实。跨连接重叠非原子写需要真正的applied、请求ACK或事务完成链。同一连接已准备前驱和其因果后继仍沿有序字节流执行，后继的真实完成可以覆盖这些前驱。单纯输入数组位置不能证明独立请求的实际提交顺序。

Python校验、原生离线事务v1—v5和原生在线追加都执行相同约束。在线已接纳一个合法旧请求后，再提交不安全后继批次，会在注册这个批次之前拒绝，不让批次前部先产生副作用。先前合法请求的部分状态保留，不回滚已经发生的网络。

## 强对照与验收

- 新请求改用不与旧请求重叠的地址：100,000ns复制到`22`。
- 在源端等待旧请求真实ACK，再安排后继：130,156ns复制到`22`。
- 同连接有序后继与经同连接后继完成再跨连接，两种合法程序都复制到`22`。
- 前两组安全程序改前改后的完整result逐字节相同；修复只改变接纳判断，没有改变合法运行的包、排队和完成时间。

这些时间只说明该人工交错的功能结果，不能用两数相除宣称MoE恢复加速。新窗口和等待旧执行完成本来就是强安全替代，本轮没有提出超越它们的新机制。

7个主要条件独立核对38个源数据包及对应端点TX见证；有两个合法同连接条件包含乱序包，按接收端连续前缀接纳重放。篡改复制内容、应用时间和通知观察值三种记录均拒绝。首次检查器漏掉RC乱序丢弃，失败原件保留，修复检查器后只复算已保存网络结果。相关25项Python单元、事务/在线/前缀工作流及13项固定依赖检查通过，详见[验收入口](../../fixtures/transaction_effect_order/README.md)。

## 对总目标的意义和边界

此前CPU模型中的“旧写可能破坏新轮数据”，现在有了实际包丢失、源重传、目标应用和数据消费的联合执行证据；也找到了本仿真器错误接受这类程序的具体原因并修复。这使后续恢复实验更可信，但它是平台正确性进展，还不能支撑A类论文主贡献。

下一步局部恢复研究必须把“健康结果仍有效”和“旧请求不能覆盖恢复结果”同时纳入，并与等待旧执行退出、足量独立窗口、可证明的provider撤权/连接重建等强基线比较。不能用目前默认的全局停止机制当作弱基线制造收益。仍需真实现代通信调用语义、代表性MoE负载、恢复资源代价、有限窗口回收及硬件校准；本轮没有实现千卡故障恢复、GPU内存可见性或现代GIN/provider语义，也没有证明外部生产系统存在漏洞。
