# 网络链路失效与鲁棒性研究进展

目前补齐的是“网络真的断开之后，仿真是否仍然自洽”的能力。它使我们能够研究恢复期间的网络代价，但还没有形成新的恢复算法或论文主贡献。整体目标仍是有代表性负载、可信网络执行、强基线和可复现证据支撑的网络/系统研究。

## 本轮改动解决什么问题

此前入口只能按规则丢弃收到的包，无法表达交换机间物理连接断开。原生端口关闭又存在排队已经清空、交换机缓冲计数没有相应释放的问题；到达关闭端口的在途包与本地清队列丢包共用回调，会使上层在途计数失真。这些缺项会直接影响故障后的排队、PFC流控、网络排空及业务结束判断，必须先修正。

现在可以在JSON中选择最多8条实际交换机间边，分别声明关闭时刻和路由更新时间。关闭两个真实端口后，已经发出的包仍沿原链路到达并丢弃，队列中的数据按实际入队来源回收入口、出口和共享缓冲。健康入口满足条件时发送真实PFC恢复报文。路由更新只使用当时已经获知的故障，不能把另一条尚未被检测到的故障提前排除。更新不重新创建连接、不清零序号或拥塞状态，源端继续依靠真实反馈和超时。

这项更新采用集中最短路与ECMP表重建。控制延迟是用户声明值，没有控制报文、分布式协议或实测检测时延，不能拿它直接预测生产恢复时间。范围、命令和限制见[公开例子](../../examples/scaleout_link_failure/README.md)。

## 实验确认了什么

主例是8个GPU标签、10个交换机、下层100Gb/s及上层25Gb/s的人工Clos网络。三条流各64,000B，故障时真正丢弃了27个排队包、27,972B；入口和出口MMU同步减少。完整记录中2,367次物理发送对应2,363接收和4个物理丢弃，另外28次旧路由本地丢弃不重复扣在途。受影响流在同一个QP上重发59个源包后完成，实际出口从失败方向切换到另一上联。

第二个故障使用更长的获知延迟，检查路由不能提前获得故障真值。另一个合法1MiB缓冲的小例实际触发PFC与headroom，记录7次暂停和7次恢复，关闭时回收110包、113,960B，最终所有占用归零。持久字节例检查同一连接空闲后继续追加；17B请求早在12.144微秒ACK，仿真仍等待512微秒的未来网络事件。永久分区例则保留失联流失败，另一条健康流完成，不生成虚假ACK。

事务例中，一次请求确实丢失并超时重传；独立解释实际源MRT1负载及物理到达，核对6次目标应用、4个原子回复和最终计数10。这是功能协议，不能代替生产RoCE原子操作、GPU内存可见性或恢复安全证明。

60项相关Python单元和18类Python/原生输入拒绝通过。独立检查器重建实际包、队列、缓冲、反馈及事务内存，拒绝13类足以改变结论的篡改。无故障时，新旧完整原生结果只在库路径上不同。检查点在新源码目录、空cwd完成公开拓扑生成和真实包执行，完整结果及独立审计一致。详细数字、失败、检查范围、包及资源记录见[功能验收](../../fixtures/switch_link_failure/README.md)。这些都是小型功能证据，没有千卡或硬件性能结论。

## 对论文主问题有什么帮助

研究重点应放在恢复过程中正常任务为何继续受拖累，以及哪些等待在同等资源下可以被消除。现在可以区分物理丢失、错误路由期间的转发丢失、排队/流控和源端重试四种实际事件，避免把缓冲泄漏、提前知道故障或虚假完成当成算法收益。

接下来的候选假设是：某条流已完成路由收敛，但其重传、源端资源持有或共享PFC仍可能延长健康MoE工作的关键等待。它也可能被已有机制充分处理，或只在不合理的软件额度下出现。需先用最小真实包条件追踪到允许健康工作前进的具体事件；如果没有稳定且有意义的额外等待，就结束这一候选，不能靠调参保留现象。

评价至少保留原生NACK、固定和Karn自适应超时、常规改路及更强已有恢复基线；集中获知所有故障可以作为明确标注的理想上界，不能与受限观测算法直接宣称公平比较。正常/故障条件必须保持业务量、源/目标资源、链路容量和可用信息相同，分别报告全部任务完成、健康任务损失、重传字节、队列与资源占用。四份现有专家路由只能作为有限来源，不能复制成千卡生产分布或当训练trace。

## 后续阶段与未满足条件

1. 用已有真实故障执行语义，定位恢复期间健康工作等待的具体包、队列或资源拥有者；先判别机制和价值，再决定是否提出新策略。
2. 在机制成立后引入有来源的MoE阶段/专家路由，保留请求、token、Dispatch/Combine及应用依赖，避免用固定通信时刻拼接独立仿真；现代GIN仍需完成窗口、provider和真实网络反馈接入。
3. 对照强基线，使用独立请求、路径哈希、上联带宽及多rail/plane留出条件验证；收益被强基线消除时正常收尾。
4. 建立可取得的匹配硬件测量，或明确受限模型的验证边界。现有A100及不可用RDMA环境不能冒充现代Hopper/GIN校准。
5. 能力和资源允许后才扩大规模。千卡拓扑输入已能生成，不代表完整千卡负载执行已通过；必须报告宿主时间、内存、观测开销与近似误差，不能以小例乘法外推性能。

当前没有NIC失效、rail重绑定、故障恢复上线、应用状态恢复、GPU生产者停止或动态注册退出。相关源码边界核查仍有效，本轮不会把网络恢复与内存安全恢复合并成一个“完成”状态。只有主问题、机制创新、充分强基线、代表性评价、校准及规模证据全部成立，才能讨论A类投稿；最佳论文不是可预先保证的工程验收项。
