# 选择重传强基线与下一步研究

本轮补齐了一个关键对照：丢一个包后，接收端可以暂存后面收到的包，并把已收到的区间通过真实网络告诉发送端；发送端收到反馈后只补缺口。此前若只与回退重传比较，容易把经典选择重传已有的效果误认成新算法收益。

平台已实现显式发送窗口、有限乱序缓冲、真实扩展ACK/NACK及源端区间跟踪，累计确认才释放工作额度。头部丢包小例实际缓存3,000B，缺口由快速重传恢复；尾包或最后确认丢失仍由超时恢复。它不删除交换机里的旧包，也不给发送端提供远端真值。反馈会排队和丢失，模型ACK从48B增为50B。完整配置和逐项证据见[选择重传验收](../../fixtures/selective_repeat/README.md)。

12次实际网络覆盖正常、数据与反馈丢失、链路关闭、拥塞通知、旧模式回归和新目录公开流程。9种选择重传条件经过独立的实际包/队列/回调核算，另有26项不同Python检查、578,671项CPU状态检查及非法配置/篡改拒绝。这些证据证明限定功能，不证明生产收益或论文创新；本轮没有把人工小例与前轮真实路由直接做性能对比。

研究仍聚焦一个可证伪的问题：链路故障的恢复流量是否通过共享队列拖慢没有直接丢包的通信，并进一步延长完整应用完成时间；在强传输、限速/公平队列和通信调度基线下是否仍有值得解决的损失。前轮已经逐包证明一条健康通信受排队影响，但它不是全窗口最后完成者，等待不能直接等同优化空间。

下一实验先固定同一真实路由、映射和工作依赖，比较回退与选择重传，明确两者窗口、缓冲及反馈成本差异，再沿Dispatch集合完成、计算和Combine追踪应用关键路径。现代库源码有真实集合屏障，不能为了制造收益而按单token提前释放计算。若经典方案已消除业务影响，结束该候选；若差异仍在，再区分源端恢复控制、共享队列与应用依赖各自贡献，之后提出新机制。

A类论文目标仍未完成。独立请求留出、匹配硬件校准、现代provider成本、完整现代应用和千卡长工作量仍缺。此轮的价值是把后续研究建立在更强、可核查的传输对照上。
