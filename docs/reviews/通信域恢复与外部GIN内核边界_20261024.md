# 通信域恢复与外部GIN内核的适用边界

本轮进一步收紧了恢复研究的比较对象：**NCCL已有Revoke和故障后Shrink；不能把“整群重启”当成唯一基线，也不能把通信域静止、用户CUDA内核退出和MR退出合成一个事件。** 官方窗口注销还有明确的无访问前提，因此不能直接把正常注销放到任意未排空的数据流中，再将结果解释成合法故障恢复。

本轮平台固定`917e42d`，没有新增恢复API或改变网络行为。新证据来自固定NCCL `12df1a11afad322be5a204a2db890161cbf8131d`和DeepEP `f6aa38fe06cd4a0489e7730365d4e0114970a2f3`原文，以及明确替身上的CPU控制函数执行。没有运行整库、GPU、provider或新ns-3网络，也没有性能、生产故障或漏洞证据。

## 一、发现与对仿真器的要求

| 已核对对象 | 原文事实 | 必须保留的区别 |
|---|---|---|
| 窗口注销 | `api/comms.rst:293–294`明确要求调用者保证窗口中的对应buffer不被任何NCCL操作访问 | 应用视图关闭不是满足该前提的自动证明；不能以正常注销模拟任意在途故障的合法恢复 |
| CommRevoke | 文档说明不销毁资源；非阻塞时可返回InProgress，需要查询AsyncError直到Success；之后可destroy/split/shrink，不能继续发起新collective或调用Finalize | API返回、异步静止、底层MR退出和新服务可用各自有完成条件 |
| Revoke worker | 所读原函数依次同步库的host/device strong stream，处理回调和proxy，最后重置abort flags并设置async结果 | 这不是整个库的执行，也没有证明其覆盖用户自建CUDA stream或所有外部GIN生产者；不能把worker成功解释为所有用户内核被终止 |
| Shrink默认模式 | 新通信器由剩余rank共同创建，排除rank不参与；默认要求没有未完成NCCL操作，允许配置资源共享 | 不能当成单rank修改集群大小；rank编号、通信初始化和后续注册/专家恢复仍需处理 |
| SHRINK_ABORT | 官方支持父通信器出错时使用，并明确禁止父子资源共享；原函数置abort、同步device strong stream、清flag后初始化child | 已有故障恢复机制必须进入强基线；不是零成本原地续跑，也不能沿用“总可共享QP/MR”的假设 |
| 外部devComm | 创建先清零结构；只有`isInternal`才赋`abortFlag`；公开创建job调用内部实现时传false；DeepEP使用该公开API | 当前读到的路径没有自动给用户devComm接入该内部abort指针；不据此推断所有外部内核都不可终止或NCCL故障恢复API失效 |
| GDAKI wait | 无deadline且abort指针为空时直接调用阻塞等待；有deadline或有效指针时进入轮询；abort分支可返回Success | wait的返回不应脱离上下文当作数据完成证明；设置host abort flag也不能自动变成所有等待者已观察到它 |
| DeepEP等待 | 一处flush使用无deadline接口；signal wait传timeout，错误时诊断并trap；另有timeout_while等待后trap | 不能给所有GPU等待套一个“到期即安全恢复”的通用定时器；trap不是新通信器、MR退出或可继续服务的收据 |
| 上层清理 | Abort走资源回收路径，设备finalize遍历剩余窗口，GIN有host/shared资源finalize | 不能声称没有清理；完整并发、失败设备、DMA及终止保证仍未证明 |

## 二、CPU检查证明到哪里

精确提取5个原函数：`setCommAbortFlags`、`commRevokeAsync`、`ncclCommShrink`、GDAKI `waitImplCore`和utility的CPU版`testAbort`，另执行原文的abort指针选择与资源共享表达式。CUDA、stream/proxy、child初始化、CQ、clock和fence均由明确记录替身提供；不是编译和运行完整上游库。

共208条合成条件由独立整数/调用顺序oracle逐条核对：84条异步Revoke worker、20条Shrink、32条共享条件及72条GIN wait。12条注入proxy-stop错误的worker继续到成功返回，说明该原函数记录错误后不传播该下层返回；未证明生产中此错误分支可触发，不能据此宣布漏洞。共享表达式确认revoked或abort-shrink不走共享分支。

同样的合成“CQ未提供完成、host/device abort值为1”下，内部指针路径可在10000次检查后走abort退出；外部空指针、无deadline路径进入记录型阻塞替身。有deadline时可能由合成clock触发timeout。CPU与GPU版testAbort原文都使用10000次间隔，但CPU检查没有执行GPU atomic load，也没有真实轮询速度；不能换算成微秒或恢复耗时。

阻塞替身在未提供立即完成时抛出记录停止，轮询替身在20001次停止，共4条阻塞记录、1条轮询上限记录。它们不是原函数返回、真实死锁或合法rank故障实验。检查器分别拒绝4种错误结论及一次轮询次数篡改。详见[摘要](../../experiments/communicator_recovery/results/20261024/summary.json)与[独立核验](../../experiments/communicator_recovery/results/20261024/verification.json)。

## 三、实现顺序与研究问题调整

上一轮`local_views/1`继续作为应用引用功能模型：它没有调用真实窗口注销，最后视图关闭后实包仍能写入的反例也不能被改称“正常NCCL注销不安全”。当前应先把恢复的前提和完成证据分开，再接逐MR退出。

1. **生产者停止。** 明确库内部工作、用户CUDA内核、已提交GIN工作分别由谁停止，哪个真实事件证明停止；timeout或host abort位只表示请求或观测，不能代替完成。没有依据时维持未知或停止该场景，不能补成恢复成功。
2. **通信域管理。** 保留Revoke异步完成、默认Shrink无未完成操作的前提、Abort-Shrink的剩余rank集合参与与新资源初始化；不能瞬间改拓扑和rank号后继续旧句柄。
3. **目标访问与存储。** 应用引用排空之后，仍需逐段、逐连接MR退出和旧访问清退的适用保证。通信域静止、公开注销返回、metadata清理、源副本回收不能共用一个BOOL；未知退出不得授权安全重用。
4. **业务恢复。** 新通信域、注册/key交换、rank映射、专家状态/数据就绪及应用恢复需独立完成，正常任务的停顿由实际共享域和依赖决定。控制流量与额外资源不能凭空省略。

强基线至少包括：协同排空后正常管理；现有Revoke→Split/Shrink或SHRINK_ABORT；正常provider整MR退出；预先独立分配/注册及备用窗口。它们必须使用同等内存、MR、控制信息和合法调用范围。研究问题继续是：在这些基线之后，能否用更合理的恢复隔离范围减少正常任务停顿，而非“是否能新增一个撤销状态”。若收益只来自多给内存、更细预分区或忽略用户内核退出，应归给资源或模型偏差，不能包装成新机制。

目前尚缺外部生产者终止、失败设备/并发DMA、重建/发布成本、代表性故障与负载、现代完整接入和千卡完整验证。本轮不启动性能矩阵，不预定算法名或投稿贡献；论文总目标保持进行中。

## 四、来源、失败与复现

16份全文共668,242B；4次固定小原文请求共230,030原文字节，各约1.07—1.67秒，无网络重试。NCCL保存commit→tree→blob，DeepEP保存固定ref与指定commit树端点响应hash，再逐文件核Git blob；不将后者冒称新增取得了commit对象。原文、响应、编译和CPU记录均打包保存。
