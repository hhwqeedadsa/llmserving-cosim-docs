# 链路失效后，健康通信为什么也会变慢

本轮从平台功能验证推进到真实路由通信的机制研究。结论是：在这个小型MoE Dispatch窗口中，链路故障确实能通过共享出口队列拖慢没有直接丢包、路径也没有改变的通信；部分已经获得源端确认的重传副本仍在交换机中占据排队位置。这个问题值得继续验证，但目前没有证明新的恢复方法或整次推理收益。

## 我们实际做了什么

平台保持`c8627e8`，没有新增后端功能或更换依赖。实验输入来自用户下载的四份DeepSeek-R1-AWQ/MMLU推理专家选择记录，固定原版本和原文件hash；不是训练数据。每份只取entry0、第4层前8个token，不足8个取全部，共30token。连续64个专家放到一个rank，EP4得到74个远端token副本，按声明BF16 Dispatch布局发送1,070,336B。

12条连接放在8个GPU标签、10个交换机组成的单rail Clos中，接入100Gb/s、上层25Gb/s，每跳1us。GPU只是端点标签，没有运行显卡。所有工作同时就绪、深度1024且全部0ns发布，排除了软件额度不足造成的发送前等待；还没有计算、Combine及完整服务请求。

执行前固定四组：正常/故障网络 × 固定80us/Karn自适应超时。故障在4us关闭交换机边8—10，在16us集中更新最短路和ECMP；故障时刻、控制延迟和网络参数都是声明条件，没有硬件校准。全部连接和背景流共用一次网络时钟，来自真实包的完成事件，没有把独立模拟时延相加。

| 条件 | 全窗口最后确认 | 源数据payload（含重传） | 超时重传 |
|---|---:|---:|---:|
| 正常、固定80us | 144.955us | 1,070,336B | 0 |
| 正常、Karn80us | 144.955us | 1,070,336B | 0 |
| 故障、固定80us | 163.983us | 1,636,432B | 0 |
| 故障、Karn80us | 164.225us | 1,743,144B | 3 |

故障固定超时相对正常，全窗口确认晚19.028us，源payload增加566,096B；增加主要来自原生NACK相关重传，而非超时。Karn故障条件又增加106,712B和3次超时，最后确认还晚242ns。因此“自适应一定更快”“所有重传都是超时触发”均不成立。正常两组包记录完全相同，均无重复负载。

## 最具体的一条事件链

12条流中5条直接丢包。其余7条既无直接丢包，观测到的数据、ACK/NACK与独立拥塞通知路径边集合也未改变，其中4条变慢、3条变快。故障会重新分配拥塞，不是所有流统一变差。本轮没有PFC暂停，不能把现象解释成流控扩散。

stream8从GPU4发往GPU0，确认时间从77.026us变为145.007us，晚67.981us。它没有重传，源负载仍为101,248B。最后触发连续前缀接收完成的是序号100784、payload464B的包，两组实际路径均为4→12→15→17→11→8→0。

| 该包的实际事件 | 正常 | 故障 |
|---|---:|---:|
| 源实际发送 | 24.304us | 24.272us |
| 全路径队列等待 | 39.934us | 107.296us |
| 序列化和传播 | 6.720us | 6.720us |
| 目标接收并推进前缀 | 70.958us | 138.288us |
| 源收到覆盖确认 | 77.026us | 145.007us |

接收时延差可由真实事件逐项核对：队列多67.362us，源早发0.032us，合计晚67.330us；剩余0.651us的确认差来自返回反馈阶段，不能重复计入数据队列。这里没有从累计队列面积直接推断业务损失。

主要积压在11→8的25G出口：该包等待从0.172us变成55.884us。它80.204us入队时，前面已有stream8自身38,296B、stream12的57,408B、stream4的70,876B模型帧，其中stream12/4有103,456B属于重复发送。更进一步，stream4的56,908B在此时已经被源累计ACK覆盖，仍在出口队列中。

例如stream4的序号5000重传包：39.681us源发出，41.082us源收到覆盖ACK，53.274us旧副本进入11→8出口。80.204us健康包入队时，该副本仍排在前面。这表明源侧得到确认，并不等于网络中的所有旧副本已经退出；它不表示源在知道确认之后故意发送这个包。56,908B包含模型头，不能与上表payload直接相加。

## 这对研究路线意味着什么

首先，研究对象可以从“失败流多久重传”推进为“故障恢复流量怎样干扰其他专家通信，以及哪些旧副本已失去业务价值”。需要观测真实队列拥有者、累计确认和包所在阶段，单看流量总量、热点专家直方图或平均完成时间无法判别。

其次，这还不是独立创新。选择性重传、一般流量整形、公平队列以及通用通信组调度都必须成为下一轮强基线；不能只战胜旧式go-back-N或某个超时参数。若这些基线在相同资源和信息条件下足以解决现象，就应结束当前候选。只基于网络恢复事件宣称发现生产漏洞或安全攻击也没有依据。

最后，stream8并不是这个窗口的最后完成者，stream4才决定163.983us的末尾。因此，即便单独消除stream8本身的等待，也不能推导出整个窗口变快。下一轮必须接入完整专家任务依赖，先判断正常任务的进度是否改变应用关键路径，再决定是否需要任务重要性感知的恢复机制。它还必须超过通用调度基线，而不是只添加MoE名称。

## 核验和仍缺的证据

独立checker重建74项工作与原路由的对应关系，从实际端点包核对连续接收前缀和累计ACK时刻；逐物理跳匹配发送/接收/丢弃，并核对序列化与传播时间；重建全部交换机队列积分、峰值、FIFO次序、MMU末态和排在健康包前面的发送者。四组分别有12,188/12,188/15,930/17,170次物理发送，故障两组各5次真实物理接收丢弃、201次本地丢弃；本地丢弃没有重复计为在途包丢弃。ACK时刻、到达时刻和重传队列拥有者三类篡改被拒绝。

这支持所述小窗口事件，不支持硬件精度、训练热点、独立样本泛化、现代GIN、整次推理收益或千卡验证。当前仍缺代表性独立请求、真实GPU/网卡校准、完整应用依赖、较大规模和超过强基线的机制贡献。A类论文目标保持进行中。

设计、代码、固定摘要与离线重放见[实验目录](../../experiments/fault_externality/README.md)。本轮仅本地保存，不push；离线分析可重放不等于原生后端从零构建或跨机器复现已经完成。
