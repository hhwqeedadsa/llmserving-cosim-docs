# CM384 / DeepSeek-R1 Decode 参考场景

本场景以 CM384 的公开网络结构、D128 部署规模和完整 DeepSeek-R1 模型为依据，模拟一个 **KV 已就绪的 Decode 实例**。它用于研究专家通信、计算依赖和交换端口观测之间的关系。公开资料没有给出同一部署的全部参数，因此场景同时包含可追溯来源和明确选定的参考值；当前结果不能称为 CM384 实机性能复现。

已经完成的验收范围是 128 rank、1024 请求来源、61 个 Transformer 块的完整首轮，以及该首轮的观测重采样和后端重放。最初准备的 64 步路由仍保留，但完整 64 步服务不属于目前的收尾验收。执行规模、等价比较和宿主资源的完整证据集中在[首轮验收记录](../../fixtures/m10_research_slice/README.md)。

## 部署与研究范围

| 项目 | 当前选择 |
|---|---|
| 阶段与初态 | 一个 Decode 实例；权重、prompt KV 与首个生成 Token 已就绪 |
| 计时范围 | 从 Decode 就绪开始；不含原始请求等待、Prefill 或 KV 搬运，不提供原始 TTFT |
| 并行配置 | attention 数据并行 128、专家并行 EP=128；TP=1、PP=1 |
| rank 映射 | 每个逻辑 rank 对应一个 die；128 个活动 rank 使用 8 台服务器、64 个芯片 |
| 物理网络 | 保留 48 台服务器、384 个芯片、768 个 die；640 个非活动端点仍存在 |
| 请求 | 每 rank 8 个，合计 1024 个独立来源；Decode 就绪时间均为 0 |
| 专家放置 | 每个 MoE 层 256 个 routed experts，rank r 放置专家 `2r`、`2r+1`；各层相同 |
| shared expert | 每个 MoE 层每 rank 一份，在 Token 所属 rank 执行；计入计算与内存，不增加跨 rank 业务流量 |
| 其他选择 | 不做 PD 分离或 P/D 共执行；不做 attention/expert 分离、MTP、动态专家迁移、冗余专家或额外背景流量 |

rank r 的服务器编号为 `floor(r/16)`，服务器内芯片编号为 `floor((r%16)/2)`，芯片内 die 编号为 `r%2`。这是确定性的实验编号，不代表论文中的物理设备编号。非专家权重在每 rank 复制。

本场景只研究跨芯片 Scale-Up 网络。同 rank 和同芯片跨 die 的专家贡献、计算和依赖仍保留；同芯片跨 die 通过本地事件和参考处理耗时表示，不建立芯片内链路，也不生成芯片内数据包或端口计数。

## 网络与后端参数

### 拓扑和路由

每个 die 是一个 DEVICE，每平面有一个端口。每台服务器、每平面有一个 L1；该平面的全部 L1 与该平面的 16 个 L2 相连。完整网络有 336 个 L1、112 个 L2，保持各平面独立。输入和生成规则见 [fabric.py](../../python/moe_ub_cosim/fabric.py)，小网络路径检查见[网络测试输入](../../fixtures/m10_fabric/README.md)。

生成器从零编号。令 D 为每服务器 die 数，N 为全部 die 数，P 为平面数，J 为每平面 L2 数：

| 对象 | 编号和端口 |
|---|---|
| DEVICE | `node=server×D+local_die`；全局 `chip=node//dies_per_chip` |
| L1 | `node=N+server×P+plane`；下行口为 `local_die`，上行口为 `D+spine` |
| L2 | `node=N+servers×P+plane×J+spine`；端口为 `server` |
| 平面 | DEVICE 的端口号等于平面号；交换机和链路只属于一个平面 |
| 层输入的物理身份 | `die-{node}`、`chip-{chip}`、`server-{server}` |

本场景取 D=16、N=768、P=7、J=16，生成 1216 个节点、10752 条双向物理链路、21504 个端口、47152 行压缩路由和 56448 行双向预建通道。路由使用原生连续目的 node 区间表示，覆盖全部设备；业务通道仅为活动组内跨芯片端点对创建，每对每平面一行，不为同芯片或组间创建业务通道。每个端点的本地 TPN 唯一。

同服务器跨芯片流量经过一个 L1，跨服务器流量经过源 L1、一个 L2 和目标 L1。跨服务器路径在源 L1 保留该平面全部 16 个 L2 候选，不提前删除到未用端点的网络结构。

当前选路有两个步骤：一次提交给 UB 的工作请求（WQE）先在最短传输通道（TP）候选中选择一个，因此使用一个平面；交换机再按 HASH 在该平面内选择最短出口。`EnableMultiPath=false` 不代表拓扑只有一个平面，也不表示每次 WQE 同时使用多个 TP。未启用逐包喷洒，不依据内部操作身份选路。选择使用显式 `seed=1`、`run=1`。

生成前检查节点、链路、路由行与通道数量预算；当前生成器另限总节点不超过 4096、各 shape 参数不超过 128、L1 端口数 D+J 不超过 128。数量检查不能代替宿主内存测量。场景 `resolve` 只生成并核验输入；运行时 C++ 还会独立检查实际拓扑、最短路候选、TP 和 rank 物理映射。

TA 分段把一次事务拆为若干段，TP 再将数据放入传输包；两者都不同于集合通信模型的向量分块。Jetty 是后端发送端资源对象，其在途上限与每 rank 的发送槽也分别计数。

关闭拥塞控制（CC）时，配置中的 CAQM 算法名不代表该算法正在运行。native LD/ST 与 XCCL 未启用；设计 YAML 中列出的候选参数不表示已经集成或参与本次流量。URMA WRITE 与原生 MTE/LDST 的完成语义不能互换，见[通信模型](../model_validation.md#依赖完成与并发)。

网络输入解析后会保存请求配置与实际后端参数；显式节点/链路覆盖值优先于属性缺省值。修改实验参数时核对这些实际值和源码支持范围，不能仅修改文档表格或未启用字段。完整参数分类、可变项和拒绝规则见[后端说明](../../backend/README.md)。

## 通信与计算成本

通信模板是 `cann_a3_v850_fullmesh_v1`，固定 CANN A3 v8.5.0 的 `fullmesh_v1` 路径；Dispatch 动态 INT8，Combine BF16，按 Token×专家贡献复制，不按目的 rank 去重。固定源码、完整字节公式与并发近似集中在[模型依据](../model_validation.md#通信行为模型)。

对 H=7168，每个 Dispatch 向量实际应用载荷为 7212 B，其中 7168 B 业务、16 B 元数据、28 B 填充；Combine 为 14336 B 业务。两者窗口地址步长分别为 7680 B 和 14336 B。Dispatch 计数与 Combine 完成标志各为 32 B 应用元数据，零贡献状态也保留。每 Token 的网络量还取决于 Top-K 贡献及本地/跨芯片分类，不能只用单个向量大小乘请求数。

当前完整目标成本由[小模型成本输入](../../fixtures/m10_full_model/service.json)中的显式参考数值按完整 R1 结构声明，构造方式见 [full_round_probe.py](../../python/moe_ub_cosim/full_round_probe.py)。下表是本例的输入值，**没有根据 Ascend 算子测量标定**。

| 成本组 | 数值及单位 |
|---|---|
| 首尾阶段 | embedding 11、final_norm 13、lm_head 17、sampling 19 ns/Token |
| 各块公共阶段 | attention_norm 2、mla_prologue 3、mla_output 7、attention_residual 11、ffn_norm 13、ffn_residual 17 ns/Token |
| MLA attention | 5 ns/上下文 Token，按本地各请求实际上下文求和 |
| dense FFN | 23 ns/Token |
| MoE 阶段 | router 19、dispatch_quant_pack 20、combine_unpack_merge 100、shared_expert 500、shared_routed_add 29 ns/Token |
| routed expert | 100 ns/Token×专家贡献 |
| CANN 局部处理 | Dispatch 重排 30 ns/贡献，状态检查 10 ns/次，结果打包 20 ns/贡献，归约 40 ns/贡献 |
| 同芯片准备 | Dispatch 30、Combine 40 ns/向量；不生成芯片内网络流量 |

这些成本用于功能与依赖实验，没有体现真实大矩阵随维度、batch 或精度变化的性能曲线。A100 的 H=F=256 FP16 GQA/FFN 测量表不能替代本场景的 H=7168 MLA/INT8 成本。研究对计算/通信重叠敏感的问题时，应明确成本假设并做小规模敏感性对照，不能将这些值导出的绝对时延当作 NPU 预测。

## 容量参数

权重存储选择为：MLA 五个投影、dense/routed/shared gated FFN 矩阵采用对称 INT8，每输出通道一个 FP32 scale，零点和额外矩阵填充为零；embedding、lm_head、norm 使用 BF16，router 及路由修正向量使用 FP32。INT8 激活临时空间归入工作区。这是可复算的存储方案，没有加载原始 FP8 或采集用 AWQ4 权重，也没有执行已验证的 W8A8 内核。

五个 MLA 投影按“输出×输入”计数为 Q×H、N(Dn+Dr)×Q、(C+Dr)×H、N(Dn+Dv)×C、H×NDv。每层另有两个 H 维 block norm 与 Q/C 维 LoRA norm。gated FFN 包含两个 F×H 和一个 H×F 矩阵；router 为 256×H，另有 256 维修正向量。非专家权重及每层 shared expert 在各 rank 复制，routed experts 每 rank 两个，排除 MTP。

| 项目 | 每 rank 数值，另有说明除外 |
|---|---:|
| 完整模型唯一参数数目，含路由修正、不含 MTP | 671,026,419,200 |
| 按本例放置的驻留参数数目 | 22,226,310,656 |
| 权重张量 / INT8 scale | 24,400,011,264 B / 24,624,384 B |
| 权重与 scale 合计 | 24,424,635,648 B |
| 条件设备容量 | 64,000,000,000 B |
| 工作区与运行时预留 | 4,294,967,296 B（4 GiB） |
| 每层 CANN 数据窗口下界 | 62,652,416 B |
| 每层声明的数据 / 状态 / staging | 67,108,864 B / 1,048,576 B / 28,928 B |
| 生效通信预留下界 | 每层 176,160,768 B；58 层合计 10,217,324,544 B |
| 剩余 KV 空间 | 25,063,072,512 B，可容纳 22,291 个完整块 |

通信预留采用[模型容量公式](../model_validation.md#通信缓冲区与输入限制)的较大下界：本例 `8×128×8×7168×(1+2)=176,160,768 B/层`。58 层保守求和已经显式应用[预算修订](../../fixtures/m10_resource_efficiency/communication-reserve.json)；这没有把 CANN 的数据窗口改为 176 MB，也没有改变消息或等待规则。旧容量审计中 3,954,809,344 B 的通信预算属于历史输入，不能继续作为完整目标服务的生效预留。

MLA 缓存采用 BF16 latent+共享 RoPE key，不按 128 个头复制，且未增加额外 KV 填充：

```text
KV/token = 61 × (512 + 64) × 2 = 70,272 B
KV/block = 16 × 70,272 = 1,124,352 B
64 步片段每请求预留 = ceil((实际 prompt P + 64) / 16) × 1,124,352 B
```

EP 不切分本 rank 请求的 KV。逐请求取整后相加，当前 1024 请求映射的每 rank 预留为 46,098,432–89,948,160 B。容量检查计入驻留但本轮未选中的请求，使用每 rank 唯一 KV 池。

64 GB 为选定的条件预算，工作区与通信预留也不是实测 HBM。实际内核的权重副本、量化布局、RoPE 表和临时矩阵若要求更多空间，应显式增加后重算。宿主 RSS、仿真中的设备容量和硬件 HBM 带宽是不同量，不能相互替代。

## 请求与专家路由

来源是 [core12345/MoE_expert_selection_trace](https://huggingface.co/datasets/core12345/MoE_expert_selection_trace)，固定修订 `27febb7b2d24169560a9f6f83d38eb53f94916cf`，子目录为 `cognitivecomputations/DeepSeek-R1-AWQ/mmlu/`。来源模型为完整 R1 的 AWQ4 版本，与本场景的 INT8 存储和通信选择不同；采集权重及 runtime 的精确修订仍未知，数据集修订不能替代这两项信息。

固定目录共 13922 个 JSON 元数据项。候选文件按 `(sha256(UTF8(str(seed)+"\n"+仓库相对路径)), 路径)` 升序，seed=0；算法名 `sha256_seed_newline_path_v1`。在该顺序前 1145 个文件中核验并选择 1024 个独立来源，排除 30 个末尾缺层文件和 91 个不足 64 个 Decode 入口的文件。只核验了这个前缀，没有下载或验证完整数据集。

文件先检查大小和 Git blob/LFS 身份，再检查完整 JSON：61 层、前三层 null、后 58 层各为 Top-8、专家 ID 在 0–255 且不重复、各层 Prefill 长度一致、每 Decode 入口一行 Token。检查包括未选入片段的后续入口；末尾缺层不能通过截取合法前缀补数。缺少早序候选、摘要不符、重复路径/内容或预算不足会失败。选择规则及拒绝原因见[路由选择证据](../../fixtures/m10_route_selection/README.md)。

选择顺序中的第 i 个文件（i 从 0 开始）对应 `request_id=i+1`、`file_id=request-{i:04d}`、`rank_id=i%128`。全部 `arrival_ns=0`，`first_decode_entry=1`，原片段 `decode_steps=64`，`target_total_tokens=null`。实际 prompt 为 1–521 Token，选中源文件可用 Decode 入口为 65–128。

## 如何用于后续实验

现有目标产物位于原开发机器的 `runs/v03-research-slice/`。它们不是克隆仓库后自动存在的文件，跨机器复用时应先取得完整数据包和相应配置，再用 `moe-ub slice inspect --slice 数据包目录 --verify` 核对。

| 目录 | 使用场景 |
|---|---|
| `target-slice/` | 保存完整首轮图、输入、原始事件和清单，是复用入口 |
| `target-config/` | 保存本次实际采样、重放配置和有限资源策略 |
| `target-sample-baseline/observed/`、`target-sample-10us/observed/` | 已生成的 1 µs、10 µs 算法可读观测 |
| `target-replay/` | 后端重新执行产生的原始记录、观测、评价用对应关系和日志 |

只改变采样周期、观察范围、所选端口或已有时钟模型时，使用 `sample` 从原始事件重新生成观测。实际首轮结束后，原声明的一秒观测区间还有无流量尾部；应依据执行记录选择研究区间，并明确零窗口口径。关联算法读取 `observed/`，真实对应关系保留在 `truth/` 供评价。

`replay` 读取已保存的完整依赖图，通过本次 ns-3-UB 事件重新推进计算和通信，省去路由导入与构图。当前结构化 fabric 数据包只支持原网络配置的重放；用户入口的链路延迟覆盖仅适用于旧 CSV 网络，不能直接在本例里覆盖。改变拓扑、通信分块、贡献规则、计算成本、批次或路由等条件，需要相应的新配置和图，不属于离线重采样。

当前数据适合首轮操作与端口流量的关联、观测粒度和时钟变化等参考实验。研究持续到达、请求退出后补入、长期热点或稳态吞吐时，需要另行设计多轮负载并验证相应范围。新增功能先用小场景验证，完整目标只在必要条件齐备后做最终检查；现有首轮证据无需因文档或普通小功能修改重复执行。
