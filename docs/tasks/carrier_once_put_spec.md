# 有序字节载体下的 put 目标状态

平台基线`cb67c6f`。目标是消除当前功能载体中的冗余完整请求缓存，为后续有限容量恢复提供更强且语义明确的基线，不引入新的恢复算法。

## 依据与范围

`PersistentStreams::Receive`仅在原生`ReceiverNextExpectedSeq`前进时把实际连续payload交给`MemoryFrameDecoder`；完整旧包只补ACK，不再交付。解码器只消费新输入前缀，提交操作的MRT1 sequence按连接单调增加。因此正常请求、数据重传和ACK丢失不会把同一帧再次交给`RemoteMemory::Apply`。既有`RemoteMemory`仍缓存全部编码请求/结果，适用于更宽的显式应用重放接口；不能将其累计字节限制当成这条有序put路径必须支付的成本。

新增显式`buffer_model.target_delivery="carrier_once_put/1"`，仅限现有transactions/4 bounded source-window put；`target_cache_bytes_per_owner`必须为0。缺省继续原有完整重放缓存，原结果逐字节保持。新模式在每context仅保留单调next sequence，不保存请求或返回值。序号回退、重放、缺口、原子和Reply都拒绝，不能悄悄接受丢失的exactly-once保证。网络内数据重传仍由原有序号处理，正常包/路径/ACK/完成不变。

注册窗口、源副本池、源lease、本地copy、目标写入及失败资源规则保持。新的零额度仅指长期完整请求缓存；解码临时内容、序号元数据、包和观察副本另计，不能称总目标内存为0。当前32远端操作/8连接等支持预算保持，不宣称无限连续服务。

## 验收

1. 纯内存检查：两context单调put、实际缓存为空、重放/跳号/原子拒绝且不修改窗口或进度；旧原子/重放/稀疏检查保持。
2. Python/native严格接纳：新模式要求0缓存且无未知字段，旧模式仍按累计请求量拒绝；两可选策略可组合，源池/注册/本地额度仍检查。
3. 公开8GPU小Clos：6次同地址、依赖真实完成的put。默认足额缓存与新模式除声明和缓存状态外执行完全一致；新模式的单次数据/最终ACK丢失均实际恢复，目标恰写6次。在线追加保持相同语义。
4. 由真实包RX连续前缀独立重建所有目标应用、线上ACK和最终窗口，核对实际重传不是第二次应用；篡改重放/缓存/窗口被拒绝。检查受影响公开事务/源隔离流程。
5. 新源码根/空cwd从持久包执行一个公开小例及离线审计，核对实际加载八库和执行字段。失败保留，不重复已经执行的网络或提高预算。

## 资源与研究边界

阶段`/dev/shm/moe-carrier-once-put-20261024/`；每命令60秒/RSS1GiB/地址2GiB/产物64MiB，网络≤5ms/result16MiB，全轮监控600秒/新产物256MiB（含失败、检查点、恢复和持久副本），tmpfs8GiB/根盘64MiB预留。只增量构建受头布局影响的三个事务消费者、两个入口和两个内存单元程序，复用前轮Fabric/持久流对象与固定八库。无安装下载/GPU/依赖变化或旧失败研究矩阵重跑。

先平台独立验收、本地提交不push。该模式依赖当前实际载体合同，不能外推成现代RoCE/provider重放策略、远端撤权保证或论文贡献；后续仍须远端旧访问退出、有限窗口复用、代表性负载、强基线和匹配校准。
