# 发送发布边界的下一项实现要求

本规范明确后续网络接入边界。既有GinWorkQueue与现代事务staged_prefix已实现基本准备/发布；新增旧低延迟同步策略的独立CPU核心见[可运行示例](../../examples/low_latency_posting/README.md)。它尚未接入网络，不表示下面的网络验收已经完成。前置证据见[通信库发送核查](../../experiments/library_posting_audit/README.md)。

## 服务对象与目标

为MoE跨机网络研究分别表达“数据可发送”和“网卡已获知工作”，避免把GPU准备、WQE提交、物理TX与ACK视为同一时刻。目标是检查发送发布是否改变突发流量、交换机排队与集合尾部；不是通过调整ACK规则制造恢复收益。

保留现有rank-reduced direct基线。DeepEP v1.2.1低延迟的每四次逻辑put发布与末尾原子通知，只能用于该命名模式的显式假设，不能成为现代GIN/direct默认。现代DeepEP调用GIN；QP配置、provider发布和硬件ACK须各自核对，固定源码版本不代表库组合已经可编译或性能已校准。

## 必须分开的事件

| 事件 | 依据与约束 |
|---|---|
| 数据就绪 | 前端及应用依赖满足；不代表实际TX |
| WQE保留/写就绪 | 按注册key拆分；显式布局或未知，不能从真实专家选择推断地址 |
| provider发布 | 只发布连续写就绪的QP前缀；按声明库策略、门铃或实际异步代理事件推进 |
| 实际TX/RX | 沿同一原生ns-3网络执行，进入原NIC/交换机队列；未发布的数据不得提前注入 |
| 接收应用可见 | 由相应库通知与接收接口决定，不能从本地CQ标记伪造 |
| 源完成/资源复用 | 独立确认条件；迟到ACK和失败清理仍须保留，不因应用先完成就释放输家 |

每个QP保留reserved、ready和published三个单调位置；多个producer先后保留时，后一个写完不能跨过未就绪的空洞。逻辑put、拆分WQE、数据包和ACK各有身份，CQ update请求单列；CQ标志不能作为ACK请求位的替代。异步postsend未知时报告不支持，不能静默当成同步或零延迟代理。

## 实施顺序及检查

1. 复用已有工作前缀状态机，另交付旧低延迟同步策略，操作显式给出QP、WQE跨度、就绪与发布触发。用0/1/3/4/5/8/9条put、末尾通知、注册边界1/2/3个WQE、保留空洞和跨轮次检验；计数单位不得混用。该CPU核心已提供独立示例与检查，逻辑检查不称网络执行。
2. 确定目标库及当前前端能提供的字段，再通过独立公开入口接入持久QP。当前旧低延迟EP32/E256完整计划超出既有操作限额，不能遇到失败后自动提限，也不能删零token通知、缩到小网络或偷换为现代模式以通过；应先设计可控表示与资源预算。
3. 功能验收采用用户限定的一种128/256/512端点Clos，检查未发布零TX、连续前缀实际出包、尾通知推动不足四条的数据、同QP顺序、跨QP共享网络，以及ACK/重试/释放不变。仅在同资源与同语义条件下比较任务、其他组、排空和线上字节。

下一项是否进入网络实现取决于上述字段和预算是否完整。新创新候选仍是利用任务进度安排有限共享网络服务；成熟发布批处理本身不作为论文贡献。若模型修正不改变瓶颈或同信息基线已解决主要等待，应正常记录并收敛方向。
