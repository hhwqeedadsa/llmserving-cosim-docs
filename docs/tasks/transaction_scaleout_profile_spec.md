# 显式Scale-Out事务容量模式

目的：为128端点Clos上的真实EP32连续调用打通底层容量，保持全部控制、self、源保护与事务完成义务。本轮独立平台增量先扩展通用事务/会话能力；现代包装输入、完整EP32执行及研究对照仍是后续验收，不用人工事务测试替代。

transactions/5的`execution_limits`可显式增加`profile="scaleout_ep32/1"`。没有profile的旧三字段输入、所有旧schema及默认上限保持。扩展模式仍必须逐项填写max_connections/max_remote_operations/max_local_operations，分别封顶2048/16384/1024；固定软件上限为128窗口、256 NIC注册、32本地等待项、128直接依赖、物理endpoint id≤511、128并发本地输出lease，合法端点还必须在实际拓扑中存在。配置不是硬件规格。

Python与C++在同一解析入口验证profile/数值/未知字段；内存核心仅显式初始化新模式后允许扩展值，不能修改所有旧调用的边界。传输声明使用已有stream/4的有界形式（派生serial local model），双向流≤4096/work≤32768、记录链路发送≤200万；不改变线格式、选路、拥塞或重传。新模式会话最多1024同步交互，回调缓存/单行界保持；旧模式仍256。宿主预算新模式最多180秒/RSS3GiB/地址6GiB/产物512MiB，协议未要求增加时仍取较小值。静态分析、原生准入与实际内存访问检查均保持，不通过删除写入顺序断言迁就扩大后的输入。

验证先做Python/C++纯准入边界与内存独立检查，再在一种128Clos运行最多3个新网络：一个扩展模式正常人工事务例、同一例的一次受控丢包恢复、一个无profile旧例兼容检查。扩展示例保留96窗口、64 NIC注册、至少65连接以及32项本地条件/超过32前驱，含物理id>31、自服务、源窗口put、fetch_add32和实际回调后追加工作。正常与恢复最终内存须相同；故障是否落在关键依赖按实际包判断，不预填收益。人工事务不是真实MoE路由、满载128卡或现代GIN。Python拒绝及原生Fabric前拒绝分别留证。

构建只重编受影响的平台单元，固定已有Fabric/ns-3库复制并逐hash核验，不重编/升级依赖、不安装下载或用GPU。预算根runs/transaction_scaleout_profile_20261031：累计2400受监控秒/3GiB新增产物/卷留8GiB；编译阶段至多900秒/RSS3GiB/地址6GiB，其余每阶段180秒/RSS3GiB/地址6GiB，单结果512MiB。失败保留，不自动扩限或重跑成功网络。平台、现代接入和真实研究分别提交验收，仅发布user既有分支，整体目标active。
