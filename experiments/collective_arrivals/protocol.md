# 真实路由collective切片的逐包到达曲线

用户要求任务发送/接收两端的规模统计、逐包打点、百B模型与每rank专家数说明，以及复杂场景的累计有效到达曲线。本实验研究可观察性和因果核对，不评价新恢复算法。

固定原四份DeepSeek-R1-AWQ/MMLU路由，文件逐hash核对；各rank独立请求、batch/rank=1，源层3—4、Decode入口1—2。E256/Top8、H7168、声明BF16激活、声明计算，4rank EP4、每rank每层64个专家；按每专家贡献复制，不是DeepEP目的rank去重。8个Dispatch/Combine阶段共用一个原生网络时钟。连续专家等容量放置，两个Pod，每台服务器1GPU，100Gb/s接入、25Gb/s上层、1µs/边；没有机内旁路。

仅两个条件：正常；同输入下两类故障。目标在执行前由首个Dispatch需求确定：选择跨Pod消息中有效字节最多的消息（并列按ID小者），在其目的端丢序号2000两次；选择第二条跨Pod消息，在其源端丢最终累计ACK一次。最多2条精确规则；不是随机丢包率，也不人工改变真实专家选择。源端有界Go-Back-N RTO初值40µs/上限160µs/4次重试。

预期数据缺口可能产生乱序丢弃和恢复平台，ACK丢失可能拖延源端确认而不拖延数据到达；累计物理去重到达不能替代协议接受曲线。保留零变化及不符合预期的实际结果，不为放大现象调参。所有rank、交换机、控制包全程采集，最多100000事件；有效接收曲线须逐消息核对最终连续接收字节和实际data-ready回调，统计源发包须与C++源计数一致。曲线对象预定为g0.w0、图内层0（原层3）、整个Dispatch；另导出同层Combine。

使用已有service二进制，不构建、不联网、不运行GPU。新阶段最多两次网络；各60s/1GiB RSS/2GiB地址/5ms仿真，累计600s/256MiB产物。任一失败保留输入、日志、原因，停止后续网络，不扩限或自动重试。原始文件位于忽略的data/，产物位于新的runs目录；Git仅保存配置方法、小型摘要和静态报告。该有限片段不声称完整R1执行、硬件校准、千卡或算法创新。

执行补充：首次系统Python在schema导入时缺protobuf，原生网络未启动，两条件均未执行。保存失败后，依赖检查前置，明确使用既有`.venv/frontend/bin/python`。以新目录执行原定条件；此为启动环境修正，不复用/覆盖失败目录，也不重复成功网络，预算累计不变。
