## 背景：MoE 推理通信的丢包恢复方法谱系

| 层次 | 代表方案 | 丢包处理机制 | 与本实验的关系 |
|---|---|---|---|
| 链路/网络层：无损化 | InfiniBand credit 链路流控；RoCE 常配 PFC，并结合 ECN/DCQCN 控制拥塞 | 尽量减少拥塞丢包；PFC不是重传机制，也不是所有RoCE部署的必选条件，RC仍须处理错误 | 本实验直接注入丢包，正是检验无损假设失效后的协议行为；PFC 自身有队头阻塞/死锁/风暴问题，是"无损化"路线的已知代价 |
| 传输层重传：Go-Back-N | RC可靠服务的经典有序接收/整体回退实现；不代表所有RNIC都采用同一算法 | 累计 ACK + NAK 指出缺口序号，发送端从缺口起整体重发；超时兜底 | 本实验两种模式均整体回退；同首包缺口、同两轮丢失和相同RTO下代价相同，不能推广到任意丢包位置 |
| 传输层重传：选择性重传 | IRN（SIGCOMM'18）等选择性恢复方案；设备是否支持须核对型号/固件/驱动 | 接收端记录到达位图，只重传真正丢失的包，不要求底层无损 | 本项目另一事务路径已有选择性重传；本轮未测，不能从GBN结果直接推算其重发量或时延 |
| 传输层：多路径与乱序容忍 | MP-RDMA（NSDI'18）；AWS SRD/EFA（NSDI'20，可靠数据报 + 多路径喷洒 + 乱序交付） | 单包级多路径分散，乱序到达直接放置，丢失只重传单包 | 这些是已有方法；本轮没有逐包多路径对照，不能声称MoE收益最大 |
| 超时估计 | 固定 RTO；Karn/Partridge 采样 + RFC6298 平滑；Swift（SIGCOMM'20）精确时延测量 | RTO 决定"等多久才认定丢失"；过短放大重复流量，过长拖延恢复 | 扩展可选 rtt_estimator=karn，但本轮未启用；固定初值40µs。RFC6298是TCP参考，不是RoCE协议规范 |
| 拥塞控制与丢包信号 | DCQCN（SIGCOMM'15）；Timely、HPCC、PowerTCP 等 | ECN/时延/带内遥测降速，尽量避免丢包发生；丢包仍被视为严重信号 | 本实验固定原生 DCQCN 不变，隔离丢包恢复单一变量 |
| 集合通信库 | NCCL/DeepEP及其具体网络provider；行为须按所用分支核对 | 库层一般不自带恢复算法：依赖传输层可靠性，失败沿 QP 错误上抛，由框架决定重连或放弃 | 本仓库 hybrid/GIN 系列筛选已核过 DeepEP 完成机制；本实验对应"库下层协议"的行为 |
| 服务系统层 | PD 分离 KV 传输（Mooncake、NVIDIA Dynamo/NIXL、vLLM 连接器）；请求级重试/重路由；副本冗余；引擎重启 | 单请求失败由调度层换实例重算，不要求单条连接必然恢复；用隔离域限制爆炸半径 | 组1在共享仿真停止前完成两轮；它不是失败后仍继续服务的证据 |

本仿真器原生模式 = 无损假设 + NACK 触发 go-back-N（无有界超时）；可选恢复扩展 = go-back-N + 有界重试显式失败（Karn可选，本轮未启用）。三个观察分别对应三个工程取舍：整体回退放大是选择性重传（IRN 等）存在的理由；静默停滞说明有界超时是必要件；ACK 掩盖说明累计确认自带确认路径容错。库层与服务层（请求级重试、隔离域）是传输层失败之后的两道防线。

## 本周期工作与丢包处理现状

- 环境能力（本周期范围）：Scale-Out 推理全链路 `rdma-run`（固定LLMServingSim调度/完成逻辑（初始化适配）→ 项目Chakra图 → ASTRA → 原生RDMA逐包执行，含 DCQCN/PFC/ECN）；`rdma-build` 锁定原生 `e929264` 现场构建（本周期修复其构建登记的 str/Path 哈希 bug）；`rdma-diagnose` 诊断与全节点逐包捕获。未触及 UB 侧。
- 丢包注入：`FaultModel` 精确规则（≤32 条、每条 ≤10,000 次）+ `drop_once` + 永久断链；已知缺口：不支持全网随机丢包率，需比率型规则与原生重编译。
- 丢包恢复（实测）：原生 = NACK go-back-N 无超时兜底（两轮丢包后静默停滞至 5ms）；可选 `go_back_n` = 固定初值RTO + 有界重试显式失败（目标确认+39.5µs，或444.2µs终止）；另一EP组在全局停止前完成；事务路径已有流隔离，本rdma-run尚未接入。

## 新增能力方向（由本实验证据驱动）

| 新增方向 | 解决什么 | 依赖与工作量 | 证据锚点 |
|---|---|---|---|
| 全网比率型随机丢包 | 回答"DCQCN+PFC 在真实丢包率（0.1%→50%）下的表现"，支持丢包率扫描找拐点 | FaultModel 增加 rate 规则 + 一次原生重编译；规则预算从 32 条精确匹配改为比率模型 | 本实验 README/protocol 已声明该缺口；当前 57% 是单消息确定性规则 |
| 将已有选择性重传接入本推理服务路径 | 与有界 Go-Back-N 做同输入、同故障和明确缓冲成本的对照，不预报节省包数或时延 | PersistentStreams/事务路径已有 selective_repeat/1；rdma-run 的 recovery 目前只支持 go_back_n，不能直接改一个字段 | 本实验未执行选择性重传；两轮各丢6包不能当成只需补6包，也不能把已有算法当创新 |
| 推理服务中的单 QP 错误传播与隔离 | 恢复耗尽只终止该 QP 并让服务层重路由，而非整体停止共享仿真 | 事务/持久流路径已有 on_exhausted=isolate_stream；rdma-run 仍整体停止，尚缺请求依赖清理与重新调度 | 组1在全局停止前已完成；这不证明错误后的其他业务仍能持续服务 |
| Karn 自适应 RTO 的重度丢包对照 | 固定 40µs 初值 vs 自适应采样在 50%+ 丢包下的恢复代价与重复流量差异 | Karn估计器是扩展的可选项；在本实验条件族中，先以当前固定初值配置作对照 | communication_fragility.md 命题 3 已证明采样无歧义；缺重度丢包场景实测 |
| 多路径/乱序交付（MP-RDMA/SRD 语义） | MoE all-to-all 短消息高扇出，最能从单包级多路径与不保序放置受益 | 拓扑生成已支持 multi-rail/多平面；需 QP 乱序放置与逐包路径选择 | 谱系表第 4 行；本平台当前为单路径保序 QP |
| PD 分离 KV handoff 大流量 + 丢包 | 检验长 KV 消息中的回退放大、流控与服务等待是否改变，不能由消息变长直接断言损失更大 | M4 已有 kv_handoff 提交类型与容量账本；复用本实验的故障注入即可 | 本实验仅测6KB消息；长流的窗口、反馈及丢包位置需要另立对照 |

边界：单消息确定性逐序号丢包，非全网随机丢包率；声明计算、合成路由；失败仅指 5ms 窗口内未完成。详见 [protocol.md](../../protocol.md) 与 [README.md](../../README.md)。
