# 从四卡direct转向较大EP，下一步该补什么

本阶段确认了一个有实质工作量差异的建模缺项：分层通信路径。已核对的真实请求下，相比逐目标GPU跨机发送，按目标服务器域发送的隐藏向量需求在EP64约少46.7%～46.9%，EP128约少27.5%～27.6%，EP256约少14.9%～15.0%。Hybrid还增加/使用域内转发，Combine的三种归约分支有不同返回份数。不能把现direct模型放大后当作现代分层EP。

这些差额属于DeepEP已经实现的算法，尚未证明时延改善，更不是本项目创新。逐目标GPU计量也不是其他仿真器必然使用的模型；ASTRA、SimAI或通用任务图可以承载用户提供的正确分层算法。我们的下一项价值应落在可检查的表示和可靠执行，而非再次集成ns-3或重复宣称层次化通信。

两个方向收紧如下，但均未成立：

1. **从真实路由生成可复用的分层因果通信表示。** 输入应声明服务器域与rail映射、库分支、通道、进度、归约和缓冲生命周期，输出应能驱动真实完成反馈，而不是从某次已有运行的truth绑定反编译。与正确分层流模型、完整DAG及逐包模型比较，证明具体误差/决策或表示成本优势；若只得到相同执行的更漂亮文件，属于平台工程。
2. **围绕进度和消费门槛按需展开网络细节。** 零数据通道也要结束通知，不能只处理热点数据；实际共享域内转发、rail/NIC/交换队列、ACK/CNP/重传及源保护都可能跨越边界。应先证明哪些重复处理占完整成本，再给出细化/回退条件和净加速；不从这轮计数推导仿真速度，也不把删除控制消息当优化。

本轮真实prefill中的六个见证仅支持单通道必要偏序：首批6份已发布即可放行转发，不需先看到最终finish。它们没有完整GPU资源、所有通道或硬件时间，尚不能证明更改串行阶段会改变方案选择。

下一项有依据的实际工作是独立的平台规范：输入驱动、版本明确、受域/rail约束的Hybrid逻辑表示及逐token数据/通知/转发来源检查，先在可支持的小规模做独立参考，不扩大现有原生四卡和事务上限。完整包级Hybrid、GPU/GIN/NVLink成本与千卡共享网络仍缺；在具备这些依据之前，不承诺两个论文贡献、商业ROI或生产收益。
