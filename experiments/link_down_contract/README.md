# 原生端口关闭：队列清空不等于缓冲释放

固定平台 `104cafa`、原生 ns-3 `3964b1d`，一次公开原生 API 状态转换探针证实：`QbbNetDevice::TakeDown()` 清空出口队列，却未解除相应的交换机缓冲管理器（MMU）占用。本项明确了物理故障接入前必须解决的正确性边界；该固定版本公开接口只支持接收错误丢包。后续平台`aa32b96`及原生补丁`6088174`已实现[真实链路关闭与声明延迟改路](../../examples/scaleout_link_failure/README.md)，新的实际排队核验见[验收](../../fixtures/switch_link_failure/README.md)。本文保留旧版本证据；这里的手工种子未填私有转发计数，不应在新补丁上当作有效转发状态重跑，构建程序会检查旧提交。

## 实际结果及范围

人工构造入口 1、出口 2 的一致队列/MMU 状态：优先级 3 有 8×1000B，优先级 2 有 6×1000B，控制优先级 0 有 96B。使用真实接纳、更新和队列 API，但没有调用 `Simulator::Run`，没有端到端流量，也没有填充私有完整转发状态。

| 状态 | 实际队列字节 | MMU 入口字节 | MMU 出口字节 | 共享占用字节 |
|---|---:|---:|---:|---:|
| 关闭前 | 14,096 | 14,000 | 14,000 | 5,808 |
| 原生关闭后 | 0 | 14,000 | 14,000 | 5,808 |
| 向关闭端口调用 Receive 后 | 0 | 14,000 | 14,000 | 5,808 |
| 按种子清单显式移除 MMU 占用后 | 0 | 0 | 0 | 0 |

入口、出口和共享计数是同一批数据的重叠视角，不能相加成物理内存。最后一行使用评价端保存的种子清单，只是守恒对照，不是部署修复。

15 个清队列丢弃全部经过 `QbbDrop`；关闭端口的后续 Receive 再产生一个 `QbbDrop`。`PhyRxDrop` 与 `PhyTxBegin` 都为 0。该固定版本 Fabric 和持久连接恢复监听的是 `PhyRxDrop`，因此接入链路关闭时必须分别处理排队丢弃与在途接收丢弃，不能直接沿用同一物理在途计数递减逻辑。这不证明原先已支持的接收错误路径存在该问题。

源码依据：`qbb-net-device.cc::TakeDown/Receive`、`switch-node.cc::SwitchNotifyDequeue`、`switch-mmu.cc`；平台入口为 `backend/rdma/fabric.cc` 和 `persistent_streams.cc`。普通 dequeue 会减少私有 `m_bytes`、做 ECN/PFC 处理并更新发送相关状态，不能当作 drop 清理函数直接调用。

## 复核与证据

独立审计从种子与实际 drop 重建字节，拒绝占用篡改、遗漏 drop、伪造接收错误三类输入。标准库审计可以在任意空工作目录运行：

```bash
python3 -B /path/to/moe-ub-cosim/experiments/link_down_contract/audit.py \
  --result /path/to/native-result.json --output /path/to/new-audit.json
```

版本化原始结果、独立审计、空 cwd 复算及资源收尾见 [results/20261024](results/20261024/)。完整本机持久包在 `runs/link_down_contract_20261024/`，包含源码快照、原始编译失败、修正记录与监控；`manifest.json` 逐文件记录 SHA-256。八个原生库仅保留身份，不打包，因此该包直接支持离线审计，不宣称可独立执行原生程序。

首次编译因回调 `Drop` 与 ns-3 枚举重名失败；保留原件后改为 `QueueDrop`，只在尚无二进制/结果的条件下继续编译。唯一状态转换成功，没有网络重跑、扩限、依赖修改、安装或下载。资源数据见 `closeout.json`，嵌套监控之和不当作完整日历耗时。

下一平台工作为可选、有界、只读的终态队列/MMU快照及离线守恒诊断，先让状态不一致可见。真正物理故障恢复还需专门的丢弃回收、PFC、路径重建及在途处理设计。该发现是仿真正确性证据，不是生产漏洞、恢复收益或论文主贡献。
