# 端网映射的分析价值实验

本实验检验：MoE Decode 执行变慢时，已知端侧调用与网络端口记录的对应关系，能否帮助缩小排查范围，并区分直接受限位置与随后受到依赖影响的操作。这里先提供完全正确的关系，检验这种信息的用途，不开发映射恢复算法，也不设计优化控制策略。

平台能力与实验分别验收。[v0.4 平台方案](../../docs/archive/moe_ub_cosim_dev_v0.4.md)负责协议、选路、执行参数、记录和接口；本页负责场景、允许输入、对照、评价与复现。实验依赖通过功能验收的平台提交，不能把补后端能力算作实验结果。执行状态只维护在[当前任务](../../docs/tasks/current.md)。

本文是待实现实验的操作约束，不表示程序、配置或结果已经存在。实现后在本页补充实际可用命令和必要入口；详细结果单独保存，不把过程日志追加到本页。

## 研究问题与完成条件

| 问题 | 要比较的判断 |
|---|---|
| 端侧准备变慢与交换出口服务变慢能否区分 | 优先检查哪个端点或物理出口，哪些候选可以排除 |
| 局部通信变化是否影响整轮完成 | 区分局部持续时间增加、依赖传播造成的晚完成和整轮损失 |
| 仅关联业务字节是否遗漏同步信息 | 增加应用状态消息关联后，是否能够解释原先无法解释的等待 |

完成条件是输入可追溯、对照公平、分析不读取隐藏答案、评价可重复，并报告适用范围。映射没有改善、只有增强观测有效或仍然无法确定，都可以是有效结果；不预设映射必须提高某个百分比。

独立研究文件 `traffic_mapping_v0.1.md` 的全文目前不在仓库。本实验沿用仓库已有的“业务字节大于零即有关联”口径，不改写该文件的目标或定义。下面的调用引用方式只是实验输入的表示约定；如需更改研究定义，须取得原件另行核对。

## 平台与输入依据

实现依据为 [749c8c5](https://github.com/baoy21/moe-ub-cosim/tree/749c8c55fce4e5199888b63b3ae56cf55d7d92ef) 之后通过验收的 v0.4 平台版本。现有模型近似、记录含义和参考部署分别见[模型依据](../../docs/model_validation.md)、[输出数据](../../docs/record_storage.md)和 [CM384/R1 场景](../../docs/scenarios/cm384_r1.md)。

主要实验采用已验证的原生 LOAD/STORE 通信路径与逐包喷洒，保留现有 URMA WRITE 作为参考。采用哪一种消息模式由通信模板决定，不为填满组合表把每份数据强制同时改写为 LOAD 和 STORE。原生路径通过不等于目标硬件或完整通信内核已经校准。

每次实验固定并记录以下资料，复用平台运行清单，不另造一套替代清单：

| 资料 | 需要固定的内容 |
|---|---|
| 平台与依赖 | 主仓提交、子模块提交、依赖锁文件和实际后端二进制摘要 |
| 工作负载 | 请求选择、路由来源版本与摘要、Token 范围、模型、专家放置和计算成本 |
| 通信与网络 | 模板版本、LOAD/STORE 或 WRITE 模式、选路、拓扑、链路与发送资源参数 |
| 运行条件 | 初态、随机配置、实际输入、干预声明及实际生效记录 |
| 观测条件 | 端口范围、窗口、时钟条件、字段与字节口径、记录保留范围 |
| 资源与产物 | 时间、内存、磁盘预算，实际命令、退出状态、日志、结果摘要和文件摘要 |

真实路由按场景文档记录的来源、版本和选择规则取得；本地来源数据放在 `data/`，不能假定执行者已有某台机器的目录。已有首轮结果摘要不代替原始数据包。复用时取得对应数据包并核对清单与摘要；无法取得则按固定来源和配置重建，并记录新的运行身份。

小场景使用模型、专家数、容量相互一致的缩小配置。完整参考配置保留 CM384/R1 的 128 rank、61 个块、KV 已就绪的首轮 Decode；不将缩减 rank 的配置称为原部署，不把首轮结果解释为稳态服务结果。

## 五种信息条件

同一个物理运行产生以下信息条件。E1 至 E3 先行；E4、E5 只在所选聚合队列统计通过平台验收并核算采集成本后加入。

| 条件 | 分析程序获得的信息 |
|---|---|
| E1 | 端侧操作记录与所有组共同允许的静态资料 |
| E2 | E1 加端口窗口内的包数、整包字节数 |
| E3 | E2 加完全正确的业务字节二元关联 |
| E4 | E2 加少量指定出口的聚合队列均值、峰值 |
| E5 | E4 加与 E3 相同口径的二元关联 |

E3 对 E2、E5 对 E4 比较映射增益；E4 对 E2、E5 对 E3 比较观测增益。E1 用于判断网络信息整体增加了什么。分析规则应尽量共用；有意使用不同规则时要说明差异，不能将算法更换的收益全部计为新增信息的收益。

增强信息仅选少量已有明确定义的聚合队列量。具体队列位置、单位、均值的时间权重、窗口边界和峰值定义遵循平台输出格式，同时记录覆盖端口、存储量及运行开销。不将一个物理出口的队列统计解释为全部网络等待。

同次执行保存的资料足够时，改变信息条件、观测窗口或本地时钟只重新导出，不重跑网络。若仅保留指定窗口的聚合量，就只能使用这些窗口或已经证明可正确合并的窗口；没有原始资料时，不宣称可以任意细化或平移窗口。物理服务、协议或选路发生变化则重新运行。

原执行没有采集所需队列资料时，不能凭空补出 E4、E5。确需新运行时，从该次执行重新生成全部待比较条件，不把新运行的 E4、E5 与旧运行的 E2、E3 拼接成一次信息对照。

第一批比较给各组相同的准确时间关系，排除时间对齐差异。后续需要考察偏移或漂移时，各组使用相同误差和校准信息，单独报告结果，不能将时间对齐收益计入映射收益。

## 允许输入与理想关系的生成

准备程序可以读取内部执行记录，分析程序只接收准备好的输入目录。评价程序另行读取对照运行和内部记录。分析入口不得接收整个运行目录，不能依赖相邻的 `truth/`、`raw/`、图文件或运行清单寻找答案。

| 输入范围 | 可以包含的内容 |
|---|---|
| 各组共用静态资料 | 已声明的拓扑、名义网络参数、端点位置、EP 组成员和调用引用规则 |
| 端侧观测 | 当前公开字段；新增字段须单列条件并说明来源 |
| 基本网络观测 | 公开端口窗口、包数和整包字节数 |
| 增强网络观测 | E4、E5 明确选择的聚合队列字段 |
| 理想关系 | E3、E5 使用的调用引用与端口窗口之间的二元关系 |
| 仅准备与评价可读 | 干预目标、时段、强度、全局身份、逐包来源、内部时钟及影响标签 |

公开资料不包含干预后的服务变化安排。场景名、文件名、额外元数据和目录名也不得编码异常位置或标签。静态资料与可用正常参考必须在五组中一致；数据规模、完整依赖、请求身份等当前未公开的信息，不能因程序实现方便而默认开放。

### 用公开锚点引用逻辑调用

当前 `operation_id` 表示多个 rank 本地调用组成的一次逻辑调用，公开端侧记录却只有各 rank 的本地编号。实验采用以下确定规则，避免泄露内部编号或把全局流量错说成某个 rank 自己的流量：

1. 首批实验固定一个公开 EP 组，组成员不随信息条件变化；以成员编号最小的 rank 为锚点。锚点只是引用位置，不表示该 rank 发出了全部数据。
2. 锚点的每条 Dispatch 或 Combine 端侧记录，以 `(rank_id, local_record_id)` 引用一次逻辑调用。各组都能从同样的公开记录得到这份调用列表。
3. 准备程序用内部注册表找到该引用所对应的逻辑调用。必须恰好找到一条锚点记录；缺失或不唯一时准备失败，不根据隐藏信息另选锚点。
4. 对该逻辑调用，读取业务字节归属表，只保留字节量大于零的端口窗口，去重后输出关系；不输出字节量、内部 `operation_id` 或其他 rank 的本地调用配对。
5. 关系字段仅为锚点的两个引用字段，以及 `switch_id`、`port_id`、`direction`、`local_window_start_ns`、`local_window_end_ns`。其含义是“所引用的整个逻辑调用与这个端口窗口有关”。

锚点记录的起止时间仍只描述该 rank 的本地调用，不是整个逻辑调用的全局起止。生成理想关系时不得用锚点本地时间裁剪或排除其他 rank 的贡献；其覆盖范围由声明的完整观测区间决定。

不能把同一全局调用的全部端口关系复制给所有 rank，再解释为每个本地调用各自的流量。该输入也不提供完整的跨 rank 调用匹配答案；如果未来研究需要这种额外能力，应另列信息条件。

准备清单声明所覆盖的调用、端口和时间范围。在此范围内关系完整，未出现的组合表示没有业务字节关联；范围外表示没有提供关系。计数中的协议开销不会自动获得业务归属。

### 无映射基线与输入检查

无映射组允许认真使用公开时间、拓扑、调用次序和已开放字段进行关联，包括简单的时间重叠或流量分段；不能刻意禁止合理方法。分析输出可以是候选端点、候选物理出口或未确定，并保留每次排除候选的依据。

默认分析对象为声明组的完整首轮。若需要给定某个慢调用，调用引用须由公开端侧记录和预先固定的选择规则产生，并对各组相同；不能通过内部影响真值偷偷挑选有利样本。

实现独立的输入白名单检查，验证字段、目录和关系引用。分析只接受检查后的资料；准备与评价保留的内部文件不复制进去。用小型人工数据检查关系去重、缺失范围、锚点唯一性和禁止字段，不能只查看程序最终结果似乎合理。

## 三类实验

### A. 端侧准备与交换出口服务

固定请求、专家选择、放置、计算成本和正常网络，准备正常运行、端侧准备变化、物理出口服务变化三种情况。干预使用平台公共参数：端侧变化落在声明的准备或计算阶段；网络变化作用于指定物理出口与时间段，由真实排队和完成事件推进后续任务。

干预不得按隐藏调用身份选择性延迟消息，也不能修改导出后的流量或操作时长。时段可由正常参考运行帮助选定，但须在干预运行前固定；实际是否碰到目标业务由运行后评价确认。

保留正常、空闲出口、未命中业务、命中但没有明显整轮影响的情况，再加入少量端侧变化与无关网络变化时间重叠的情况。低并发时简单时间关联已经足够，也是需要保留的结果。

这组主要比较位置判断、候选范围和错误归责，检查是否把晚准备当成网络服务不足、把同时发生的无关事件归给慢调用，或把依赖传播当成多个独立异常。

### B. 局部变化与整轮影响

保留同一工作负载与依赖，只改变物理干预的位置、时段和声明强度。选择既可能被并行计算吸收、也可能延长整轮的情况，实际分类由成对运行决定，不从“经过干预端口”直接生成影响标签。

分别比较操作持续时间、操作完成时刻和整轮完成时间。前驱晚完成导致多个后继一起后移时，不把这些后移量相加成多份损失。第一阶段判断是否有实质整轮影响，不要求预测精确的纳秒损失。

分析候选必须来自固定的公开端点与物理出口集合。不同粒度分别报告，不通过把多个出口合并成一个大范围标签来制造候选数量下降。

### C. 业务数据与应用同步状态

研究问题是：业务数据已到达而应用同步条件尚未满足时，仅业务字节关联能否解释停顿。现有 WRITE 参考模板中的计数发布和完成标志可作为起点；原生模式必须按已经验证的模板重新说明数据发布、状态消息与后继可执行条件。

不得凭空加入原模板没有的轮询或用旧 WRITE 消息直接证明原生行为。模板实际使用 LOAD 时，按其已验证的请求、响应和完成语义分类；是否存在应用状态读取由模板依据决定。协议确认等控制消息不因附带任务信息就自动获得应用调用归属。

先用小场景保持应用语义和数据量一致，在物理出口施加固定时段的服务变化，分别观察业务传输与状态发布阶段。干预仍作用于资源和时间，不按“状态消息”身份特殊延迟。

在 E3 的业务关系之外，单列“增加应用状态消息关联”的条件；具备 E5 时可以同样比较。新增关系沿用锚点引用，但必须声明消息范围和判定依据，不能混入原业务关系并悄悄扩大定义。

这项比较依赖平台实际保留相应应用消息类别的操作到端口窗口来源。准备程序只按模板语义筛选和投影，不能从元数据总量、时间接近或旧运行中不存在的资料补出关系；来源缺失时先按已验证的记录配置重新运行。

结果可支持保持业务字节口径、增加应用状态关联，或说明已有信息仍不足。若已验证模板没有预期的同步现象，报告这一事实，不通过改平台行为保证出现正例。

## 成对运行与评价

每项干预配对一个移除该干预的正常条件，保持请求、路由、放置、成本及其余物理参数一致。端侧成本有意变化时，保存相应生成输入与差异，不强求不同输入产生同一图摘要。随机配置固定，但不强制不同执行产生相同逐包路径；执行时序造成的选路变化也属于实际结果。

评价程序使用内部身份对齐两次运行，计算干预运行减去对照运行的差值；这些配对身份和差值标签不交给分析程序。直接受限位置还需结合实际准备、排队和完成记录核对，平台只记录事实，不生成“最应排查谁”的研究答案。

局部操作持续时间按各 rank 对应调用的实际起止计算，完成时刻使用同一仿真时间基准，整轮时间取该组真实完成事件。不同 rank 的重叠区间不累加为整轮耗时，锚点的本地结束也不代替逻辑调用或整轮完成。

多项干预同时存在时，移除一项得到的是其他干预仍存在条件下的增量影响，不能默认相加为总损失。首批以单项干预为主，组合情况保持少量且可解释。

评价前固定“实质影响”的阈值或判定规则，说明与时间分辨率、正常变动范围的关系；不能为提高结果而反复更换。保留实际数值，避免只留下二分类标签。

| 指标 | 报告要求 |
|---|---|
| 位置判断 | 分端点与物理出口报告命中、错误位置和未确定 |
| 候选范围 | 报告减少数量，同时报告实际受影响位置是否被错误排除 |
| 判断覆盖 | 报告全部可评价样本中给出判断的比例，不丢弃未确定样本 |
| 错误归责 | 单列正常、未命中、局部变化但无整轮影响的情况 |
| 性能影响 | 分别报告局部持续时间、完成时刻和整轮时间差值 |

理想关系已完全正确，不以其映射准确率作为研究指标。单个分析程序没有改善，只能说明该方法在这些条件下没有利用出增益；结合候选排除依据说明新增信息是否减少歧义，不据此宣称映射普遍无用。

首轮中的多个请求共同参与一次执行，不是等量独立时延样本。需要重复时更换预先声明的请求选择或随机输入，并报告独立运行数；不由首轮推导稳态尾时延结论。

## 目录与实现分工

实验保留在本仓库，单向调用平台公共命令和读取器。平台不能导入实验模块，实验不能导入功能测试内部工具。现有 `fixtures/` 的平台用例不改成正式实验输入；可复用能力应先成为平台公开接口。

以下是实现时的职责约定，按实际需要创建文件，不提前提交空模块：

| 位置 | 职责 |
|---|---|
| 本目录 `configs/` | 版本化实验选择和平台输入，复用已有格式，不另造仿真参数语言 |
| 本目录运行程序 | 调用公开流程、成对运行并核对预算，不能直接改后端事件 |
| 本目录准备程序 | 检查来源，生成五种允许输入和受限的理想关系 |
| 本目录分析程序 | 只读允许输入，输出候选与依据 |
| 本目录评价程序 | 读取内部记录与对照运行，计算指标、表格和必要图形 |
| 本目录 `tests/` | 小型人工数据检查输入隔离、关系和指标计算，不承担平台协议验收 |
| `runs/mapping_value/<run_id>/` | 平台原始产物、分析输出、评价、日志和资源记录；沿用清单分工 |
| `data/` | 按来源与摘要登记的输入数据；获取方式进入版本控制，原始大文件不提交 |

实验结果作为运行产物的附加目录保存，不能修改平台已封存文件来写分析结论。Git 保留配置、程序、必要摘要和数据获取规则；大文件按清单备份，不让 `runs/` 中的临时脚本成为复现实验的前提。

完成后可新增本目录 `results.md`，只写问题、配置版本、结果、限制和产物入口。命令与日志留在运行目录；进展仍只更新当前任务，不建立第二份状态表。

## 执行次序与最终交付

1. 选择通过相关验收的平台提交，固定输入来源、候选集合、阈值、正常参考和资源预算；检查选用的 native 与喷洒组合确实可用。
2. 用小场景实现并检查准备、分析、评价，先完成 E1 至 E3；确认正常、无影响及未确定情况没有被丢弃。
3. 完成三类机制比较；增强聚合统计通过验收且成本可接受时，再从符合保留条件的执行资料生成 E4、E5。
4. 固定分析规则后，仅把少量代表性情况放到完整 CM384/R1 首轮。完整场景安排在最后，不要求 64 轮，也不自动进行大规模参数扫描。
5. 保存可复现配置、结果摘要与限制，区分真实输入来源、行为正确性和目标硬件校准；交付后停止于当前任务范围。

各承诺支持的协议与选路组合由平台小功能例检查。正式研究不要求所有组合乘以全部场景形成完整矩阵；若要宣称某差异由 native 或喷洒单独造成，才补相应单因素对照。所有仿真使用明确预算，失败保留原因与产物，不自动提高预算或重跑。

最终复核应能从新检出的仓库找到输入获取规则和真实命令，生成一个小型完整实验，追溯全部信息条件，并独立重算一组指标。实验完成不以平台建设工作量或预设的正收益代替这些证据。
