# 现代EP32运行扩展：修改顺序和边界

这是尚未实现的后续方案，不是当前可用接口说明。目标保持一个128端点Clos，先完成真实单EP32的两次连续调用，再扩展多个组共用同一Fabric/Simulator；不能减EP、删零通知、复制请求或把未来token合进当前batch来绕过问题。

## 1. 先压缩依赖覆盖状态，保持全部因果关系

`ModernNativeController._schedule`当前为每个节点复制祖先覆盖字典，区分applied和completed两个等级。规模增加会累计保存大量重复祖先；还需对所有历史节点重复计数。下一增量应把两等级覆盖分别保存为紧凑位集合，并保留精确的成员查询、合并及前驱压缩规则。完整转移记录与原实现逐项一致后再替换，不能用截断祖先或省略依赖节省内存。使用运行期远端/本地计数器避免每次提交扫描全历史，但计数仍核对实际插入，不提前制造完成。

这属于仿真宿主效率优化，不改变网络、GPU模型或协议算法。要分别测量存储占用、宿主CPU与控制输出；内存下降不能换算成模拟推理加速。

## 2. 成套引入显式扩展容量

当前两组最大需求分别为1,162条连接、12,436远端/self节点、646本地节点、96内存窗口和至少64条NIC注册。现有16MiB明文保存检查仍在运行布局中生效；压缩计划功能没有修改它。

建议采用新的显式输入/事务扩展模式，保留既有v1/v2现代输入和transactions/5的默认规则。拟定封顶可取连接2,048、远端节点16,384、本地节点1,024、窗口128、注册256、单条件列表32项；这些是待验收的软件预算，不能描述成NIC规格。旧事务的stream/2描述最多128条流，而已有stream/4允许4,096条流；扩展事务应明确派生适配的传输格式和各项计数，并检查实际请求/回复双向流数量，不直接让旧格式接受新数值。

对应修改同时覆盖：

- 现代布局的rank/物理节点范围、完整计划展开容量、连接集合和存储格式。
- Python及C++事务容量、窗口/注册、owner和local rank范围，以及实际物理NIC绑定。
- 屏障32项本地等待和可能超过32的动态前驱。依赖宽度需实际核算，必要时显式提高有界范围并同步所有验证器，不能偷偷截断或去掉写入顺序检查。
- 原生会话256次交互、16,384逻辑批次、每批/总缓存、单行预算、结果读取和宿主期限。先核算必要工作与已有记录，再制定显式预算；不得失败后反复自动扩限。
- 现代完整快照及逐包记录的存储需求。计划的21.8MB限制与最终运行日志大小分开，报告格式支持压缩不代表运行内存已受控。

每个扩展字段都需要Python/C++边界一致、逐项越界拒绝、旧输入行为保持及实际原生最小流程验收。沿用固定原生ns-3，不混入UB、不升级依赖。不默认已支持现代多组共享；须先沿实际代码核对，单独会话的运行时不能拼接。

## 3. 实际网络验收后再选择研究算法

执行前冻结一个EP32真实两调用的来源、部署、成本与记录预算。继续使用合成可追踪激活标记、BF16完整布局及明确的功能可见性；未知GPU成本不能由网络结果反推。先验证动态slot、跨调用复用、源保护、实际请求/回复、最终内存与物理排空，再加入已授权的局部短时故障与成熟选择性重传/绕路基线。

只有在强基线下仍观察到足够大的任务损失、并能追到共享端口/队列和实际前驱，才考虑恢复流量组织或进度相关策略。目前尚无新的已验证论文算法贡献，不能把容量检查、压缩、位集合或已有重传当作该贡献。
