# DCQCN参考模式的实施门槛

本文规定后续平台工作的设计门槛。持久字节入口现已实现有明确边界的`figure7_reference/1`，机制范围和功能证据见[平台验收](../../fixtures/dcqcn_reference/README.md)；硬件匹配与研究对照仍未完成。依据见[反馈抽象审计](../../docs/review_artifacts/dcqcn_validity_20261022/report.html)。目标是区分当前ACK反馈抽象与明确的一手参考机制，避免未经校准的拥塞状态成为MoE网络结论的前提；不是照抄2015年的参数来代表现代网卡。

## 模型分层

| 层次 | 需要明确的状态与行为 | 不能混同的对象 |
|---|---|---|
| 交换机拥塞点 CP | 实际出口队列、ECN阈值/概率、字节口径、PFC独立配置 | 目的端唯一CE包与逐跳重复观测 |
| 接收端通知点 NP | 每流最近通知、待通知标志、抑制定时器、首次标记和边界规则 | 传输ACK与独立CNP |
| 反馈网络 | CNP实际包格式/长度、优先级、反向路由、排队和到达 | “生成通知”与“发送端收到通知” |
| 发送端反应点 RP | current/target rate、alpha、首次通知、降速、timer与发送字节计数恢复、阶段切换 | 收到通知次数与实际降速次数 |
| 持久连接 | QP初始化、空闲、后续发布、关闭及未到达反馈 | 应用工作结束与QP寿命结束 |
| 配置与来源 | 全部有效值、单位、覆盖顺序、参考模式、源码和参数依据 | 功能验收与硬件校准 |

需要先确定图6/图7的边界语义，再实现：NP在抑制期收到多次标记时保留pending；空闲期、恰好到期、同纳秒标记/到期按公开规则处理。接收端通知不能在源端提前生效。RP的恢复以真实发送字节/计时器事件推进，不能按应用声明总量提前推进。多个恢复触发同时发生时需要定义合并/重置行为。

当前锁定`ReceiveCnp`没有调用mode1的`cnp_received_mlx`，不能只打开独立CNP发包而继续依赖该入口自动完成DCQCN更新。新路径必须连接正确RP处理，且明确停用旧ACK-CNP控制分支，防止同一反馈被两套控制器重复处理。

ACK仍负责传输确认与当前功能队列信用；独立CNP只更新拥塞状态，不释放工作槽或伪造完成。QP关闭时未发出的NP通知、在途CNP及定时器是丢弃、排空还是阻止关闭，需要明确并验证，不能依靠悬空对象或静默消失。保留历史模式与旧结果，新增模式另行命名和记录。

## 实现前后验收

1. 人工因果用例：首个标记立即通知、周期内多次标记、周期边界、空闲后新标记、周期末pending通知及QP关闭。
2. 独立CNP实际走反向网络；反向拥塞推迟RP反馈。检查数据/ACK/CNP包数及字节分别计数，ACK信用不受CNP替代。
3. RP小型状态oracle：首次降速、alpha更新、无反馈衰减、timer/byte两条恢复路径、同纳秒事件和最大/最小速率。
4. 同一持久QP跨工作保存协议状态；只根据实际包/反馈推进。观察开关不能改变包、路径或完成事件。
5. 公开配置严格拒绝无效组合，输出实际值及来源。旧模式逐字段回归，新模式单独验收；平台与研究分别提交。

功能参考可以选原论文明确的部署作为命名模式，但N=50us、恢复55us和字节阈值10MB只能标记为该文献配置；不是A100/H100、某代NIC或当前生产部署的通用参数。不能仅换恢复timer就声称已校准。

## 后续研究的可证伪问题

机制验收通过后才另行预注册闭环对照：固定请求、专家选择、数据布局、流标识、源端资源和拓扑，检查反馈机制是否改变并发深度/放置选择的排序及实际暴露通信。必须控制CNP引入的真实网络服务量，区别“反馈时序变化”和“反向流量变化”。不能过滤旧CE序列后直接预测新完成时间，因为新反馈会改变后续发包、队列和CE。

若现象在可信参考模式下消失，收缩或放弃候选，不调参将它重新制造出来。若保留，再用物理出口服务量、已有网络感知放置和明确的协议状态基线解释；既有窗口实验17/18排序已被简单出口服务量区分，不能削弱该基线。只有超出这些解释且影响明确、在独立请求与匹配硬件下成立，才值得发展新机制。

HOTI 2022已覆盖ASTRA+Alibaba、incast、分块All-To-All和拥塞控制调参，所以联合仿真接通或“拥塞控制影响集合通信”本身不构成新贡献。当前仍缺独立负载、现代完整通信库在线语义及匹配硬件校准。
