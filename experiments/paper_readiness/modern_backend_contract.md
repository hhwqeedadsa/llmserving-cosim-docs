# 现代DeepEP direct与GIN/GDAKI后端实施规范

状态：待实现设计，不是可调用接口。服务于正常无故障、多专家并行组共享Scale-Out网络的机制研究。依据固定DeepEP `f6aa38fe06cd4a0489e7730365d4e0114970a2f3`和NCCL `12df1a11afad322be5a204a2db890161cbf8131d`；来源与限制见[审计报告](../../docs/reviews/NCCL_GIN资源语义与真实路由网络偏斜_20261022.md)。旧rank聚合在线入口与v1离线计划保持各自版本，不把本规范写成已实现能力。

## 1. 最小范围与拒绝条件

首个实现只选择fresh-routing direct、关闭跨rank NVLink、显式FULL互通、固定团队和已声明的单个provider行为。仅实现有来源的put、内联put_value、原子signal、flush及相应wait；不自动支持get、缓存路由、hybrid、NVLS/FP8或任意NCCL插件。模型参数、top-k及buffer布局必须与所选分支一致。精度和元数据先按布局核算，不沿用v1包长。

物理端点不可达、原子事务/可见性未定义或记录预算不足时明确失败。硬件未知时可交付有范围的功能模型，但不宣称时延校准。普通字节流路径不能代替原子路径，也不能混接UB和原生ns-3。

必须按具体API分支区分本地旁路和self-peer GIN：本范围内token与rank count存在显式本地指针路径；专家计数bulk put及四次屏障signal即使src=dst仍调用GIN。固定GDAKI会创建并连接self-peer QP，故这类请求必须保留provider资源需求。源码只证明接口及资源关系，未证明物理回环路径、是否经过外部链路或固定服务代价。当前plan/2以`gin_self`单独分类；原生字节及MRT1事务入口拒绝src=dst是尚未支持的能力，不能以此跳过请求、改为零成本事件或任意交换机路由。证据见[self-peer更正](../../docs/reviews/现代GIN自发请求与网络基线更正_20261022.md)。

## 2. 分层状态及标识

| 对象 | 持久键或字段 | 生命周期与用途 |
|---|---|---|
| 专家并行组/团队 | communicator、WORLD/RAIL/LSA映射、rank到物理GPU | 组间可共享物理链路；不共享不属于同一运行时的信号窗口 |
| GIN连接 | communicator、connectionId、本地NIC、远端设备、可达rail | 在建连时绑定；不能每消息重新用ECMP选一张NIC |
| GIN上下文 | connectionId、local contextId | 映射自应用索引i的模/整除；记录请求量、实际分配量和实际活跃量 |
| 面向peer的QP | provider实例、contextId、peer、传输状态 | 包括self-peer；空队列时持续存在，保留序号、拥塞与重试状态；关闭需满足排空条件 |
| 工作条目 | operationId、QP、ticket、verb、远端窗口/偏移、epoch、操作数或源buffer | 就绪后才能reserve；操作、WQE和包分别编号 |
| buffer区域 | owner、window、offset、length、epoch | 数据就绪和复用权限分开；重叠写需显式依赖或拒绝 |
| flush/wait | 调用时各相关QP的覆盖位置、目标值、内存序 | 只等待已定义前缀或信号条件，不将未来操作纳入完成条件 |

内部研究关联保留在truth，观察接口仅暴露可获得事实。operationId不能写入报文改变路径、优先级或包长。多工作共用QP后，原来按端口一对一关联消息的方法需要改为序号区间/事务关联，且不能拿内部真值驱动算法。

## 3. 工作队列状态与不变量

为每个工作保留以下事实，允许源码支持的并发准备，不能用一个全局消息完成标志代替：

1. 应用依赖满足，源buffer就绪；尚未满足的操作不得提交。
2. reserve取得单调ticket；这不表示槽已经可写，也不表示NIC已经看到工作。
3. 槽使用许可由相关完成进度决定；在深度D的环中，ticket复用对应位置前需满足先前工作完成的条件。
4. prepare写完描述符及必要数据依赖；不能覆写仍在使用的槽。
5. doorbell发布可处理前缀；仅聚合准备的工作不得自动产生包。前缀中尚未准备完成的条目不能被当成有效数据。
6. NIC消费工作，按provider的传输/原子协议生成包并推进同一网络时钟。
7. 接收、目标可见、本地完成和完成槽可回收分别更新；完成压缩按选定CQ模式表达。

建议记录reserved、prepared、published、completed的前缀及必要的稀疏就绪集合。reservation可以领先于物理可写槽，不能简单要求所有reserved ticket都小于深度；同时不允许将所有超深度条目提前prepare。上述字段是实现建议，最终需覆盖固定provider的实际并发与内存序。

必须保持：每个应用操作发起一次；重传不得重复执行原子增量；每个条目完成一次；等待者只被已发生且满足谓词的事件唤醒；CQ压缩不丢失被覆盖工作的完成事实；QP空闲不自动清除传输状态。不存在任意固定通信时刻或提前喂入未来token。

## 4. API语义和后端事件

| 操作 | 输入与依赖 | 完成含义 |
|---|---|---|
| put | 源buffer就绪、目标窗口/偏移、长度、上下文和peer | 源可复用与目标可见分别报告，不默认同一事件 |
| put_value | 不大于8B的值、目标位置、上下文、聚合标志 | 内联值无外部源buffer；仍占所需提交/传输资源 |
| signal | 目标信号槽、增量、strong/weak、上下文和peer | 原子应用一次；strong只在声明范围内建立前序put可见关系 |
| flush | 作用上下文与各peer的已保留前缀快照 | 保证所选put源安全复用；不能自动标记所有远端消费就绪 |
| wait | 信号槽/epoch、比较条件、内存序 | 实际目标状态满足才结束；不能只按预定时长返回 |
| barrier | 团队、阶段、所需flush、通知和wait | 所有必要前驱完成才推进；保留入口buffer安全与出口数据依赖 |

GDAKI的MLX5特定可见性作为provider规则单独实现，不能冒充通用GIN保证。跨连接屏障先完成源码顺序，再通过来源明确的provider机制形成目标可见；没有资料时标为不支持或校准缺项，不发明一个零代价全局fence。

应用返回、设备完成、网络排空和资源释放分开记录。不能因上层完成就取消尚未完成的响应或清理仍会参与拥塞的网络状态。

## 5. 接入当前平台的顺序

| 增量 | 位置与工作 | 独立验收 |
|---|---|---|
| 现代操作输入 | Python公开计划模块和CLI，独立schema，计数/数据/屏障来自相同路由 | 人工同rank多专家去重、零计数块、两轮buffer epoch、非法模式拒绝 |
| 连接/队列功能核心 | backend独立资源状态，不依赖experiments；显式NIC/context/peer绑定 | 延迟就绪不提前提交、D+1工作反压、交错prepare、未ring不发送、CQ覆盖、空闲后追加 |
| provider事务 | 原生ns-3独立适配，必要依赖修改须保存固定基线分支及gitlink | 小型真实执行put/signal、正确目标偏移、原子去重、ACK延迟阻塞槽复用、重试不重应用 |
| 在线应用推进 | 现代计划和网络回调共享一个时钟 | 两轮数据/屏障/计算由实际事件推进；不把每轮独立仿真耗时相加 |
| 观测与归因 | 提交等待、端口队列、包/响应、目标wait和排空记录 | 有界且不扰动执行；同一时间区间不重复归因，保留并列依赖 |

这是实施顺序，不表示已实现任何新CLI或已获准改变锁定依赖。当前阶段不通过修改端口号模拟连接复用，也不将研究脚本接入平台。

## 6. 有区分力的验收场景

只改变一个操作数或字段可能同时改变机制，验收前分别列明保持和变化的因素。

| 问题 | 最小对照 | 能排除什么 |
|---|---|---|
| 是否偷发未来工作 | 第二条put由第一轮消费后才就绪 | 第二条在依赖完成前有reserve/包即失败 |
| 是否真实保留连接状态 | 同一QP先发送、空闲、再追加 | 不能把QP创建次数等同操作数；序号/拥塞状态按定义延续 |
| CQ与数据可见是否混淆 | 延迟完成反馈，但允许目标先满足可见条件 | 消费可按已满足条件推进，源槽不能提前复用；记录两者反压 |
| Aggregate是否被误作发送 | 先准备聚合条目，稍后非聚合提交 | 前者不得提前发包，后者仅推进已准备工作；全聚合尾项按API约束处理 |
| signal是否普通流 | 一次原子增量、重复传输及目标wait | 重传不能重复增量；不是按收到若干字节就释放wait |
| self-peer是否被漏掉 | 同rank token旁路，对照同rank专家计数put与屏障signal | 后两类保留GIN提交、源完成及目标可见；无依据的物理回环成本明确不支持，不能自动给外部流量或零成本 |
| NIC选择是否被ECMP替代 | 固定context到connection到NIC，交换机保持原选路 | 发端端口必须匹配绑定；链路无可达路时拒绝 |
| 多组是否真正共享网络 | 两组发向共同物理瓶颈，与分离链路对照 | 队列状态在一次执行中相互影响，不用独立结果相加 |

功能正确仍不等于真实代价。匹配GPU/NIC/provider的小型测量应区分单put、聚合提交、队列满反压、signal和跨NIC屏障；留出报文大小/并发/连接数量验证后，才能用时延模型评价策略。

## 7. 研究决策

先用现代去重与批量计数、合法端点绑定及简单排程作为强基线，回答正常网络的关键等待是否存在、何时出现、是否可消除。论文候选是可证伪的问题，不是本规范中的模块数量。

目前四份Decode请求只能支持条件路由核算。不得复制成千卡真实生产负载；更大合成规模用于资源开销与功能边界，真实分布和泛化必须另有留出数据。千卡完整推理尚无通过证据。只读检查已确认本进程可见6张A100，未发现所需Hopper候选，当前verbs不可枚举且所见端口Down；这是当前环境范围，不是全实验室资源结论。匹配校准仍缺失，功能实现继续保留未知代价和不支持边界，见[实机条件与方法](../../docs/reviews/现代通信校准条件与论文验证路线_20261022.md)。

## 8. 调用间隔与默认连接配置的新增实施门槛

[固定源码调用审计](../../docs/review_artifacts/invocation_semantics_20261023/report.html)补充了Python默认与launcher依据：API默认hybrid；本研究显式direct分支自动申请17 contexts，调用推荐min(SM,9,allocated)，fresh Dispatch通常把context0留给notify。多个context不等于多个NIC，实际有数据的集合还取决于token数、设备可用共享内存及SM/warp映射。此前12条人工数据QP的两轮探针验证了参考状态延续，但没有验证现代默认配置的排序。

进入现代性能比较前，除了前述语义，还须满足：

- 读回并保存设备实际SM/共享内存、API有效模式及申请/调用context数量；按来源映射到NCCL连接和物理NIC。离线假设共享内存条件不能作为可部署GPU配置。
- 明确每次调用复用哪个buffer/Context、哪些QP；未来数据只有在实际输入事件和资源条件满足后发布，保留空闲恢复及在途反馈。真实通信/计算流事件不能用全组ACK统一替代。
- 将Dispatch消费、可选epilogue、专家计算、Combine和后续输入就绪接到同一时钟。需要计算时延时使用匹配系统测量，缺值明确不支持，不用固定通信时刻补齐。四份路由JSON没有实际调用时间字段。
- 分别记录已预留SQ前缀的flush、源buffer复用、目标可见与应用消费。flush/屏障没有要求所有CNP排空或QP恢复线速，不能把它们当控制状态重置点。
- 多context/rail基线说明同时改变的任务分工、门铃资源、NIC和ECMP；用相同路由/布局/必要字节及实际就绪语义评价，不把所有收益归给拥塞粒度。self-peer、signal成本和GPU可见性未验证时仍不宣称现代端到端复现。

本节是实施与验收要求；没有新增平台命令、配置字段或已校准成本模型。当前最小下一步是以真实设备配置生成持久连接映射并验证发布/完成，再决定是否进入网络优化，而不是继续对人工单QP的经典反馈现象调参。

## 9. Combine静态需求与动态身份的约简边界

[槽位投影研究](../../docs/reviews/并发槽位与连接需求可约简边界_20261023.md)核对了Dispatch counter、copy epilogue的原始rank连续布局及Combine连续warp区间。在固定fresh direct/BF16/expanded本地归约范围内，原始rank到owner的去重token计数足以精确计算每声明context/connection的Combine数据put操作数与操作数字节，无需猜测实际slot排列。计算接收序号的总量和prefix时必须包含本地旁路token；它们不发跨机包，但占用接收序号。

这个结论只约简静态需求核算。token身份、目标地址、局部归约、真实就绪和按通道发起的依赖仍须保留；不能用连接总字节直接替代事件执行、WQE或包，也不能由总量相同推断排队/完成时间相同。固定参数、完整数据布局、控制/self-peer、provider和校准门槛均不变。

人工4-token的24个合法全排列提供了同一token跨连接而总量不变的见证；真实48-token输入的3种已注册就绪策略实际只有1种slot排列，缺少不同顺序的实证对照，该负结果保留。静态区间公式有源码及独立整数枚举依据，不将这3次执行写成3种不同并发分配或生产性能证据。该有限性质本身不是论文主贡献。

## 10. 通知覆盖范围与强基线的新增门槛

[多context屏障审计](../../docs/reviews/多连接屏障与远端可见性_20261023.md)取得固定NCCL的`impl/gin_barrier__funcs.h`和`impl/barrier__funcs.h`：`ncclGinAllContexts`分支按**每个已分配context**发signal并逐context等待，不只是每连接或每NIC一次；同一NIC上的不同QP也不能仅凭名称合并其顺序。单context构造仍保留自身范围，不把全部NCCL屏障统称为全context。NCCL另有利用`FlushesAllPutsOnAnySignal`能力的分层优化，故不能从全context分支反推所有真实系统都必须使用同样控制请求数。

现代DeepEP自定义路径先flush所用contexts，再通过context0通知。GDAKI宣告MLX5到达signal刷新已收到put，但其跨context/连接/NIC的物理可见性覆盖范围仍未在本环境验证；上述源码差异不证明DeepEP缺陷。实施时须逐项保存数据context/QP、连接、设备和目标可见性域映射，及signal覆盖依据。未有保证时，不能把原生字节ACK直接转成全部`visible`事件，或在收到context0通知后遍历解锁其他域的token。

强基线须分别定义固定DeepEP自定义协议及明确选用的NCCL all-context协议：包括allocated/active contexts、self-peer请求、flush与signal数、源完成和目标消费，不能偷偷换屏障再将差异归因于网络算法。两者即使跨机数据字节相同，必要控制量也可能不同；API调用数不等于包或成本。缺少目标域能力与匹配校准时，完整现代性能比较仍不通过；允许无时间源码/依赖核验，不能补零成本全局可见性。

## 11. Self-peer资源及集群/EP规模

[固定源码执行核查](../../docs/reviews/self_peer_provider_20261023.md)在记录型API替身上执行原文，确认FULL路径的每个self主QP连接独立responder QP，且反向连接回主QP。两个对象均保留建连属性；不能合为同一个QP或因此复制一次应用事务。self循环不传远端分支的LAG端口亲和，默认0；responder列表创建前显式改用VALID_DBR（静态证据）。这些事实不确定物理回环路线或时延，不能支持跳过self操作、自动零成本或自动经过外部交换机。

固定DeepEP Context初始化沿用`ginCounterCount=0`，该路径不覆盖此字段，故本配置无companion QP。FULL且rankStride=1、EP组R、请求Q个context、C个GIN connection时，allocated A=ceil(Q/C)×C，每GPU主QP为A×R，另有A个self responder，总A×(R+1)。这是持久对象配置核算，不是执行、HBM/CQ容量或活跃流量证据；不套用RAIL/CUSTOM_STRIDE。C也不自动等同C个独立物理NIC。

规模输入必须分开集群GPU数、每组EP规模、组数与物理映射，并另列DP/TP/PP和其通信。增加同规模EP组与扩大单EP组不是同一实验。当前现代前端的支持上限及千卡执行缺项不因本资源投影而改变；后续先测实际对象内存/调度开销，再选择保留必要状态的稀疏实例化方案，不能用本表直接承诺千卡可运行。
