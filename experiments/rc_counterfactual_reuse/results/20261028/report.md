# 从正确性参考走向执行缩减：一次有边界的尝试

这次实现并验证了“只重算故障影响的尾部”的原型，但**普通解析基线已经得到同样答案，尚未形成新的论文贡献或测得完整宿主加速**。结果帮助排除简单案例，不能继续把已有RTO、缓存或少跑几次仿真写成创新。

## 输入到底是什么

用户提供的1472路由原件，entry0、层3、第0个token，8个专家为49、61、77、84、167、178、204、52。模型E256/Top8/H7168，声明BF16；按连续64专家/rank放到EP4，源rank0，远端目的去重后为1、2、3。分别发送一个14,336B向量，再做一次64位加1通知，共43,008B有效数据、三个QP。

这是一个token的跨机Dispatch数据/通知片段，未执行完整DeepEP、Combine、专家计算、LLMServingSim服务组批或GPU。张量内容是确定性的功能字节，不是真实激活。GPU类型NONE只代表通信端点；没有A100/RTX性能校准。来源确认与接收hash不冒充新HF远端版本核验。

4台单卡服务器经两组ToR/Agg和共享Core连接，单rail、所有链路100Gb/s、1000ns。目的1与源同ToR，往返经过4条链路；目的2/3分别往返12条链路。MTU256B、RTO100μs，逐跳发送和接收来自同一原生ns-3时钟。

## 三个网络结果

| 条件 | 网络排空/μs | 逐跳TX/RX/丢弃 |
|---|---:|---:|
| 正常 | 28.245 | 826/826/0 |
| 最终原子回复丢失 | 112.041 | 830/829/1 |
| 写入中间包丢失 | 113.363 | 942/941/1 |

三个新网络各只执行一次，没有重建ns-3或重开旧条件。两故障均只影响QP0的重试；目标计数仍各加1一次，返回旧值0，未重复写入或重复加法。

## 原型如何少重算

先运行正常网络；预测程序只能读取正常缓存、输入、拓扑和故障声明，在故障网络执行前保存预测及hash。最终Atomic ACK在源GPU的接收位置丢失，目标原子已执行；此QP已经没有后继操作，其他QP不依赖其源完成。重试在108.019μs开始，晚于正常全网排空。此时可复用先前过程，只为隔离的原子重试与缓存回复计算尾部。

原型预测112.041μs，与包级执行的完成、旧值、最终内存、目标效应、收发数及全部尾部时刻一致。原正常过程有826次逐跳发送，新增尾部仅4次；这只是可复用的执行结构，不等于跳过同数量ns-3事件或获得相同比例CPU加速。读取、哈希、检查和复制缓存也有成本。

普通“原RTT加RTO”和“RTO加空闲路径往返”两种基线的时延误差均为0。后者本来就是已有网络解析方法，因此不能把准确预测归为新增MoE语义优势。

对数据包丢失，程序事先输出“需要详细重算”，未套用复用公式。完整执行为113.363μs；拒绝不是已正确预测这个数字。数据丢失会涉及缺失段、NAK、后续数据与重放，比最后一次回复丢失的范围更广。

## 新发现与不能宣称的收益

单条连接在故障中增加100μs等待，但整个片段从28.245μs变为112.041μs，增量为83.796μs。正常情况下另一条连接更慢，所以不能把单连接RTO直接当整任务额外等待。

源请求从171包增至172包，逐跳TX从826增至830。模拟时间大幅增加，并不意味着模拟器CPU按同样比例增加；离散事件模拟本来就会跳过没有事件的空闲时间。不能以“故障等待很长”推断存在同样大的仿真提速空间。

核验独立解析实际包字段、逐跳传播与取整、每段目标效应、反馈完成和原始专家选择，六类篡改拒绝。首次核验后额外审查了缓存输入身份及概率ECN前提：没有观测到CE不足以证明未来无CE，现要求孤立尾部严格低于全部kmin，并限制已审阅MMU配置；旧源码/初始核验保留。加固后离线预测与故障前封存版本逐字节相同，没有重新运行网络。

## 两个研究方向现在怎样落地

1. **为网络决策选择必要精度。** 对同一工作负载，在正确分层算法、完整依赖图和逐链路/连接哈希等强基线之上，找出真正会改变网络方案排序的反馈条件。已有健康小场景没有证明额外决策价值，不能用总字节弱基线维持主张。
2. **带适用性检查的增量重仿真。** 改一项网络条件后，复用不受影响的执行，只重算反馈及依赖传播范围；无法判断时退回详细执行。本轮是最简单终端反馈分支的原型，普通解析已足够，尚不构成独有方法。

这两个方向分别回答“需要算哪些细节”和“变化后需要重新算多少”。真正的投稿门槛仍是：同信息、同资源、同目标协议下，击败通用DAG/符号buffer/常规增量执行，保留错误决策及回退率，实测包含准备与缓存验证的完整宿主成本，并用独立负载和硬件匹配证据验证。当前没有两个已成立的创新点。

## 与其他平台的实际区别

以下沿用已核本地固定来源，不是对各项目最新分支的重新评测，也没有竞品同机速度排名。

| 平台 | 对本问题的长处 | 使用时需要补什么 |
|---|---|---|
| LLMServingSim 2.0 / Vidur | 请求、组批、profile与部署/容量研究已有基础；不是只能使用RTX | 目标现代EP通信库、逐包恢复及对应GPU/网络校准须逐版本确认 |
| ASTRA-sim | 依赖图、集合通信和多种网络后端，已经能接ns-3 | 正确输入分层算法、资源和完成语义；连接后端本身不算创新 |
| SimAI | 工作负载、通信库、系统与网络体系，已含训练/推理相关路径 | 目标版本对热点、现代MoE路径及恢复的具体支持要核，不写成只有random |
| SimAI-CLEM | 已有真实旧CCL、host verbs、持续QP与ACK/CQ反馈，并有规模优化 | 公开版本对现代GPU发起操作和通用远端原子的适配范围需匹配；不能将其规模倍数当宿主加速倍数 |
| 原生ns-3 / 阿里RDMA派生库 | 包、队列、拥塞反馈和网络故障细节 | 需要正确应用任务与端点模型；逐包不等于GPU或服务真实 |
| 本项目 | 已有真实路由选择、明确网络层级、独立RC及结果核验，可以做有边界的端网因果试验 | 完整现代Hybrid/RC/拥塞反馈、硬件匹配及两项强基线之外的收益尚未完成 |

场景特殊性不是“模型是MoE”这个名字：一个token会按专家和服务器域去重后跨多个目的发送；小通知和完成反馈可能决定下一个阶段何时产生流量；多rail、共享NIC、交换缓冲及并行组又会把原本无关的任务耦合起来。总字节不足以覆盖这些关系，但正确通用依赖图和真实CCL也能表达，必须在它们之上证明精度/成本改进。

本轮条件关闭。下一项若继续，必须另行限定故障与其他流量重叠、有后继依赖或拥塞反馈的目标；本轮固定速率RC不能替代完整RoCE/Hybrid。不能为了保留结果追加有利配置。
