# 在途 MoE 恢复：状态存活与保留价值判别

本轮先检验候选是否值得实现，不开发恢复调度器。候选是：局部故障后，复用健康端已经完成且语义仍有效的结果，安全补齐必要贡献。若已有操作级重放可获得同样效果，或现有错误路径使可保留状态失效，不把保留机制本身当作新贡献。

## 预登记假设、对照与淘汰条件

1. 网络暂时不可达、执行端进程故障、源端/KV故障、等待内核异常分别处理。只有专家选择的 trace 无法确定上述状态的存活，也没有任何已完成结果或故障时刻记录。
2. 读取固定 DeepEP 的 timeout/trap 与 Combine 局部归约路径；只读 NVIDIA PTX 与 CUDA 官方文档，区分指令描述、运行时错误枚举、对具体内核的实测。不能从一个 `trap` 静态映射到某个 CUDA 错误码。
3. 仅以四份已核哈希 Decode 路由构造 EP4、每源一 token、连续64专家/卡的假设部署。四请求按相同 Decode 序号人为对齐；不是生产并发/故障样本，不扩为千卡/训练结果。BF16隐藏向量只是参考，不从 AWQ 权重推断激活类型。
4. 对每个窗口、每个失效 owner，分别核算请求源独立存活、源与专家卡合并部署（失效源 token 不算可恢复）。乐观地假设所有健康 owner 的所需结果都已完成、仍有效且可定位，失败 owner 的结果不可用；实际可保留量在0与此上界之间。无替代权重时不能完成，不能用路由计数证明可用性。
5. 强基线保留同样有效的输入、KV和历史 token。比较本轮有效 token 的整层重做、仅受故障影响 token 的当前 MoE 层重做、只重做缺失 owner 贡献。不得让基线重算全部请求前缀制造收益。若最后一种已足够，则逐专家完成日志没有本轮证据支持。
6. 按每(token, owner)一份局部归约向量与逐专家向量比较有效结果表示量；仅核算隐藏向量和理论完成位数，不把它们叫新增显存/RSS，不含已有缓冲是否可零拷贝复用、代际、权重、日志、备份和保留时间。局部归约数学等价不等于浮点逐位等价。
7. 不做时延预测。微秒层传输与已有论文秒级权重恢复不能直接相除推收益；只有共同故障/部署/状态模型下实测或执行的端到端对照才能支持服务价值。

## 实施与验收

- 新目录 `experiments/recovery_value/`，原件 `/dev/shm/moe-recovery-value-20261023/`。保存官方资料正文哈希/最终URL/摘录，固定源码重新核 SHA256、Git blob 和树身份。
- CPU独立读取原始JSON，导出逐窗口/失败owner记录与汇总；不导入平台、tests、fixture或旧研究程序。
- 第二个程序独立按专家区间扫描原件，核对每行和汇总；针对删除一行、篡改可保留量、把失效源当存活三类篡改均应拒绝。离线在新cwd复算并比较确定性产物，不重做网络或GPU实验。
- 输出候选去留、强基线、实现前置条件和下一步最小判别；同时交付Markdown、HTML和机器摘要。平台待收尾工作保持原样，研究单独本地提交，不push。

预算：每命令60秒、RSS1GiB/地址2GiB、单阶段64MiB；全轮180秒/128MiB，tmpfs保留8GiB。只读官方文档最多两份、每份8MiB/合计12MiB，超限或超时保留失败且不自动重试。无安装、依赖升级、GPU执行或旧失败Prefill/1024仿真。仅源码和小型摘要进入根卷。
