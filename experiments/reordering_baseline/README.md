# 经典乱序等待后的完整应用对照

本实验检验：旧“立即全局改路比延迟改路慢”的结果，是否只是第一次NACK立即恢复、缺少经典乱序容忍造成的。平台固定`fa6f001`，三次新网络已经关闭；旧立即恢复的三份结果从固定归档读取，不重跑。

结果是：16us固定等待消除了旧stream12的218,688B重复发送，使两种故障条件分别快30.326us和36.997us；但立即改路仍晚8.986us。不能再将剩余差距全部解释为该流的重传，也不能用减少字节直接代表应用收益。这是一次强基线筛选，不是新恢复算法。

## 固定范围

四个真实MMLU路由JSON、两层两步、216原始节点、76次远端写、2,609,152B有效负载及全部原图依赖保持。只在恢复配置中加入显式16us源NACK等待。拓扑为单plane Clos、100G接入/25G上层，rank0/2/4/6活动、其余四GPU空闲。它是旧贡献复制和声明计算参考，未证明现代DeepEP语义、GPU计算成本、千卡完整推理或生产泛化。事前假设、参数和预算见[protocol.md](protocol.md)。

应用组完成397.733/446.808/455.794us分别对应无故障/延迟改路/立即改路；健康物理排空为401.871us，不能混用应用完成和网络排空。全部健康结果只移除新增等待日志及新增配置字段后完全相同，库路径字符串也相同。

## 离线复核

持久包位置为本机`runs/reordering_baseline_checkpoint_20261024/evidence.tar.gz`，未包含原生程序或八个动态库。离线复算只需要Python标准库与包内研究源码，不依赖这些外部运行文件；重新执行网络则需要固定平台、依赖、原生构建和完整预算。

从仓库根目录恢复到一个**尚不存在**的目录：

```bash
PYTHONPATH=python:. PYTHONDONTWRITEBYTECODE=1 python3 -B \
  -m experiments.reordering_baseline.checkpoint restore \
  --archive runs/reordering_baseline_checkpoint_20261024/evidence.tar.gz \
  --output /tmp/moe-reordering-review
```

恢复前检查成员路径、类型、数量、大小和全部内容hash，再写文件。随后在新研究源码根、空工作目录下重算完整分析、原件/传输核验、源发送序列分析及核验、简明摘要五份JSON，与包内预期逐字节比较。不启动网络。离线操作也应按协议施加60秒/1GiB RSS/2GiB地址空间及磁盘限额；上述恢复命令本身不替代宿主监控器。

新网络执行入口是`prepare.py`和`run.py`，前者要求协议固定的旧证据包，后者仅通过公开CLI执行三种条件；它们不会下载输入、编译或自动重跑。准备、执行和宿主命令都保存在证据包中，本轮不再追加参数扫描。

## 实现与证据边界

- `analyze.py`只读observed保存图、计划和公开网络结果。它复用`experiments/local_fault_baselines/`的研究分析器，不导入fixture、tests或平台解码器。
- `verify.py`独立核原始四路由、全图依赖、字节/ACK/MSR1、物理跳/FIFO/队列积分、全部实际enqueue的BFS+hash、76接收见证及等待状态；七类语义篡改必须被拒绝。
- `train.py`与`verify_train.py`对保留的并列最终前驱中的work99作事后深入核查。两条件首包均在就绪时发送，29包/57,344B连续且没有本段重发。发送序列跨度22.559→40.665us；按真实下一次可发送时刻分段核对，其中仍有7.496/11.136us端口空闲。只有时间核算成立，调度成员和唤醒原因尚未完整记录，不能强行归因。
- `checkpoint.py`封存必要研究源码和六条件原件，拒绝八类异常归档；`summary.py`生成小型可审阅摘要。

`verification.json`及`source-history/verify-v1.py`保留初验；最终核验为`verification-final.json`。修订只移除了离线核验对本机动态库文件的读取，健康两份结果的路径原本已经相同，未改变任何网络结果。外部程序/八库/构建源码身份在执行和收尾阶段另行核hash。
