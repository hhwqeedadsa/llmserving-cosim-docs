# 连续Decode窗口、真实热点与网络需求

上一轮15个单token、双EP32完整通信没有显示明显旁观拖累。本轮先判别这种切片是否遗漏持续热点，以及扩大观察窗口时系统真正缺少什么。不运行新网络，不从热点统计推断故障收益。

## 事前固定范围

来源沿用15份不同R1-AWQ/MMLU本地原件的可迁移清单。公共`python -m moe_ub_cosim.route_evidence`先校验全部原件/层/入口并生成只读归一化Decode记录；本轮分析只读取这份归一化产物与其hash，不调用旧研究驱动或测试fixture。

仍使用一个128端点Clos，实际access连接推导两组部署，与上一轮相同：第一组0、4、…、124；第二组排除这些端点及ToR128，按pod各取最小16个。两组各EP32/E256，每rank8专家；来源清单前8份、后7份分别放在本组rank0开始。不同文件不证明严格独立采集；不改变来源或复制请求。

固定分析原层3、31、60，逐请求取入口1..64。窗口为非重叠的1、4、16、64个Decode步骤，各组每一步仍是8或7个请求。任一原件不足64步则整体拒绝，不跳过、不补齐。其他Decode记录只计入覆盖，原始Prefill不进入本轮热点统计。没有真实时间戳或请求到达过程，窗口和相同步号对齐是分析假设，不称实际同时发生。

## 两个要区分的问题

1. **专家偏斜能否转成网络偏斜**：记录每层专家频率、按连续等容量放置的rank负载、逐步远端流量和端点入/出方向需求。比较逐专家贡献与按目的rank去重两种表示，激活本体均按H7168/BF16=14,336B核算；另列已有布局中的元数据/对齐开销，不能比较缺少控制流的“总网络字节”。不执行专家重排优化。
2. **热点是否持续**：非重叠窗口的Top8集合Jaccard及上一窗口Top8在下一窗口的选择覆盖率；排名只含正计数专家，同频按ID，同时记录截断点并列数量。对每份文件独立打乱其前64步，seed固定11/29/47，保留全部逐token Top8及单专家边际频率，作为丢失时序后的参考。真实与打乱的差不能泛化为预测论文贡献。

端点服务量界只用相同一步中的激活本体、源/目标access端口400Gb/s求`ceil(max_port_bytes*8*1e9/rate)`，分别对Dispatch/Combine报告；不含包头、ACK、控制、路由、排队和计算，不能相加称完整推理时延，更不是完整现代DeepEP收益。

## 系统容量核查

连续Decode步骤必须是后续调用，不能把同一请求的未来token放进当前batch。按实际选择推导旧库每调用全部操作、事件和请求/回复工作，计算1/2/4/64步的需求；这些只是计数，现代direct和旧低延迟路径分别说明。

另外用公开`deepep-plan --format indexed-jsonl`为原层3的前两步生成真实双EP32计划，然后调用`deepep-shared-run --validate-only`。预计可能触及当前完整计划寿命预算，接受或拒绝都记录，不删通知、不降低E256或将两次独立ns-3结果相加。预检不会运行原生准入或网络；命令失败不证明模拟行为，只定位公开Python接口的实际容量。

## 竞争解释与停止条件

- 专家很热但分散到多个rank，或同一token多个专家在同rank：网络端点偏斜可能远小于专家偏斜。
- 统计热点来自每请求稳定偏好而非时序：保留边际的打乱后可能同样明显。
- 大窗口降低离散抽样误差，但不会自动增加单步并发或可用网络带宽压力。
- 无法继续扩大可能是表示/寿命或记录容量，而非网络硬件上限；用公开计数及拒绝位置区分。

不按结果改层、窗口、seed或请求划分，不执行新故障或参数扫描。本轮不设计新恢复算法，不增加硬件校准。结果应指导下一项实际系统增量；若只是现成方法或负面结果，如实交付。
