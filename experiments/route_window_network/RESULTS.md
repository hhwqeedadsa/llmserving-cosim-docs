# 连续Decode、网络热点和系统容量：本轮结果

本轮把分析范围从每请求一个token扩展到连续64个Decode步骤，确认热点专家不等于相同比例的rank/链路热点；同时查清旧库连续调用的寿命限制，并交付现代操作计划的可选压缩保存。**本轮零新网络运行，没有新的故障优化或时延收益结论。**

入口：[网页](results/20261031/report.html)、[指标](results/20261031/analysis.json)、[来源核验](results/20261031/verification.json)、[现代完整计划核验](results/20261031/modern-verification.json)、[资源](results/20261031/receipt.json)、[原方法](README.md)。

## 真实任务与网络对象

来源为原15份不同R1-AWQ/MMLU文件，前8、后7份组成两个EP32组。每请求取前64步、原层3/31/60，共960个Decode token、2,880条token-layer记录、23,040次Top8选择。公共归一化同时校验了所有105,038条Decode层记录，其他记录不混入本轮样本。最短原件72步，未补齐、复制或推断EOS。

固定一个128端点Clos，部署与上一轮相同，64端点属于两个组；源数据每步仅15个rank持有选定token。每组E256/H7168、每rank8专家；BF16是声明的激活载体，不由AWQ精度推导。记录没有真实batch、纳秒时间或到达过程，相同步号对齐是分析假设。没有执行LLMServingSim调度或完整R1计算。

**一个请求的64个未来token必须属于后续Decode调用，不能合并为同一并发batch。**窗口变长不自动增加单步并发或网络压力。

## 专家、rank与网络需求的区别

| 组 / 原层 | 64步专家峰均比 | 专家归属rank峰均比（含本地贡献） | 按目的rank去重后远端激活本体减少 |
|---|---:|---:|---:|
| 0 / 3 | 4.12 | 1.62 | 14.65% |
| 0 / 31 | 5.19 | 1.87 | 14.40% |
| 0 / 60 | 5.62 | 1.63 | 16.27% |
| 1 / 3 | 3.50 | 1.54 | 13.36% |
| 1 / 31 | 9.36 | 1.68 | 14.94% |
| 1 / 60 | 5.29 | 1.53 | 14.60% |

峰均比按全256专家或32个归属rank计算，包含零项。专家峰值显著不均，汇总到rank后偏斜被稀释；rank选择次数仍不等于远端流量，更不等于交换机排队。逐步远端矩阵另按真实选择、源rank与连续等容量专家放置计算。

去重比较保持同一选择与14,336B激活本体，仅改变每个token到同一目的rank是否重复发送；减少13.36%～16.27%属于现代通信已有表示，不能称新算法收益或同幅时延收益。另保留旧布局14,352/14,336B、现代direct布局14,464/14,400B的元数据/对齐量；没有把控制、ACK、包头或恢复开销算进这些投影。

按目的rank去重后，各样本64步中最大的源/目标access方向激活服务量下界均约2.294µs（400Gb/s）。它反映单步端点需求，不包含传播、交换机共享上行、控制、计算、排队或关键依赖，不能作为完整时延，也不能与两个阶段的界相加当成业务结果。

## 热点持续性有多少

按非重叠4步窗口，用前窗Top8覆盖下一窗口的专家选择，覆盖份额约6.5%～12.3%。独立打乱每请求64步、保留全部单token Top8组合与边际频率后，三个固定seed经常得到相近覆盖。个别层的真实顺序高于打乱，浅层也有打乱高于真实的情况。

因此，存在每请求的专家偏好，并不自动证明一个新时序预测器有稳定优势。窗口Top8有截断并列影响，报告保留同频数量；三个seed只作描述参考，不给显著性、跨任务泛化或生产时间尺度结论。热点预测本身也已是相关数据集论文的研究内容，不能直接冒充本项目创新。

## 发现的系统限制及实际修复

原层3前两步的完整旧库计划分别为33,024和32,992操作。两组均超过旧native每组32,768操作寿命上限，公开`deepep-shared-run --validate-only`在Python层拒绝。完整通知没有删除，原生准入与网络都未运行。该限制属于这个旧库入口，不是Clos硬件限制，也不是整个仿真器只支持一步。

相同真实选择生成现代direct计划，每组操作/事件分别为12,508/51,308与12,478/51,154，逻辑数合法，但旧明文保存预算16MiB拒绝了约21.8MB规范JSON。**现代native直接从配置构造运行时，明文保存失败不证明native本身不能运行。**

平台独立交付`modern-deepep-plan --format compressed-json`及自动检查，标准zlib保留规范JSON的全部字节，实际保存总预算仍16MiB、逻辑上限不变，新格式展开上限64MiB。两组现在分别保存为988,190B、984,016B，较21,842,925B、21,785,503B减少约95.48%。这是实验产物空间改善，未测得同幅运行期内存或时间收益。

默认flat三个产物与改动前逐字节一致；7项新增格式方法、24项旧计划/事件/窗口方法通过。独立读取器核对每组全部32×32四类屏障、rank计数、expert计数块和token数据，保留每组320个self-peer控制操作、全部零值、符号slot与完整无时间拓扑闭包。两个真实压缩计划分别通过公开plan/check；另从空cwd、仅用发布配置复现第一组，manifest完全相同，不依赖原始大文件或历史runs。

## 失败、验证和下一项

初次旧库预检继承9000B载荷却配8192B接收缓冲，被公开校验拒绝；原件保留。只改为上一轮1024B载荷/4096B分块，frozen-v2保留原冻结hash与代码修订关系。两次现代flat输出预算拒绝也原样保留，不覆盖为成功。后续压缩检查使用新目录，无网络重跑。

来源独立核验重新读取15原件，重算768个逐步贡献/去重矩阵及2,040个真实/打乱窗口，并核对两个完整旧库两调用计划。研究12个受监控阶段约33.59秒，峰值RSS214,302,720B、累计产物峰值95,948,800B；资源小计在发布时单独注明，出版和交付检查不混为网络耗时。平台功能预算与研究预算分别保留。HTML只完成静态链接核验，没有浏览器渲染验收。

下一项先审计并推进**现代direct真实连续两调用的运行期**：同一128Clos、因果依赖、动态slot、真实回调和跨调用缓冲复用保持，检查既有交互次数、逻辑步、原生节点及记录容量。单组正确后再扩多组共享，避免把独立网络耗时相加。未发现实际平台缺口前不重写已支持的功能，不仅靠提高故障强度制造收益。只有在成熟通信/恢复充分启用后仍有足够业务损失，才决定进度感知恢复或流量组织的算法设计；当前尚无新的已验证论文算法贡献，整体目标active。
