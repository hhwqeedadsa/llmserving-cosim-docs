# 固定Decode任务下的软件准入与丢包对照

问题是：较少的在途消息是否只是把网络积压转成发送前等待，能否因此缩短实际Decode？本实验使用已验收的[软件准入接口](../../examples/scaleout_rdma_admission/README.md)，只调用公共CLI、读取已保存产物，不导入tests或私有运行器。

固定8 GPU、两组交错EP4、32请求、batch/rank=4、1层2步ready-KV Decode，H1024/F4096/E16/K2，A100标签及声明计算成本，三层Clos 100G。模型数值计算、完整Prefill、持续到达、训练、硬件QP上限均不在本实验范围；它也不证明生产p99或千卡性能。合成路由种子不变，不为取得收益另造热点。

## 预先定义的对照与竞争解释

| 对照 | 唯一干预及目的 | 什么结果会削弱解释 |
|---|---|---|
| 透传 / FIFO1 / FIFO2 | 软件并发额度；检验少发是否减少积压却拖慢业务。物理带宽、硬件模型、消息顺序规则不变。 | 队列下降而整轮变慢，否定“队列更少就是优化成功”。 |
| FIFO1 / 目的端轮转1 | 相同软件额度下仅改当前就绪任务顺序。 | 改进很小、为零或退化，不能主张复杂调度方法已经必要。 |
| FIFO1 / FIFO1决策10ns | 仅增加每次准入的串行显式成本。 | 零成本微小收益被成本吞没，不能宣称免费策略的实用收益。 |
| FIFO1 / 中间数据包丢失 / 最终ACK丢失 | 固定同一目标逻辑消息，分别在接收端丢一次数据偏移1000、源端丢一次完整ACK。 | 没命中不算干预；数据齐备后若提前归还额度，说明完成模型错误。 |

所有请求、专家选择/放置、每消息字节、计算成本、拓扑和协议保持不变。透传与不同限额的对照有意改变软件允许的活跃数，不声称这一因素不变；FIFO与轮转比较才保持相同额度。每个条件重新执行同一个网络实例，全部组/波次共享状态；不拼接独立仿真耗时。失败后未提交的未来波次不补造，核对每个共同实际提交的图逐字节一致。

## 执行与评价

```bash
python experiments/scaleout_admission/run.py --backend-json <原生构建>/backend.json \
  --protoc <既有protoc> --output <不存在的目录>
python experiments/scaleout_admission/analyze.py --run <上一步目录> --output <新目录>
```

每次运行沿用公开60秒、RSS1 GiB、地址2 GiB、5ms仿真和512 MiB预算；实验累计产物不超过128 MiB、卷留8 GiB，失败不扩容。最终ACK场景预期原运行非零退出，诊断命令另行执行。硬件恢复校准缺口保持明确。

分析读取完整生命周期、包事件、图和前端结果，分别输出实际波次完成、请求末态、软件待发、在途占用、数据齐备后ACK尾段、重传字节与BEgressQueue积分。队列积分使用有类型的入/出队事件：入队读数为加字节后，出队读数为减字节前，减去该包大小才得到出队后状态；不把旧无类型queue_events积分。队列不含NIC数据QP和单独高优先ACK队列，积分不是业务损失。

累计等待、全部额度占用者与一次干预造成的业务变化分别报告，不相加或互作替代。所有全局身份、图关系和接收状态均用于离线评价，不进入在线策略。收益不是实验成功的条件；若简单基线已解释现象或没有有意义的剩余问题，就记录结论，不凭空增加复杂策略。
