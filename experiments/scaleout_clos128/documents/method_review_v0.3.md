# MoE Scale-Out 联合仿真实验方法

审阅稿 v0.3 · 2026-10-16 · 百卡三层 Clos 与千卡扩展路线

## 1. 核心目标：解释网络怎样拖慢推理

研究 MoE（混合专家模型）推理中，专家分发 Dispatch 与结果回收 Combine 的多对多通信，如何在 GPU 出入口、机内互连、ToR、汇聚层和跨 Pod 链路形成竞争，并通过依赖关系推迟本轮 token 完成和下一轮调度。

最终交付是一套可以修改模型、batch、专家分组、放置和分层带宽的联合仿真方法；近期先完成百卡三层 Clos 的可信执行与网络机制对照，再逐级扩展千卡。千卡配置生成、逐包执行和硬件精度校准分别验收。

## 2. 本轮研究范围

| 对象 | 本轮约定 |
|---|---|
| 服务 | KV 已就绪的 Decode；每条活跃序列每步生成 1 个 token；暂不测首 token 延迟 |
| 模型 | Qwen3-30B-A3B-Instruct-2507 的完整 48 层结构；BF16 尺寸；合成专家路由与声明计算成本 |
| 近期网络 | 每服务器 8 GPU；机内共享带宽抽象；机外 ToR—Agg—Core 三层 Clos；Core 为普通电交换机 |
| 执行 | LLMServingSim → Chakra → ASTRA → 单一非 UB ns-3 → 完成事件 → 下一轮 |
| 扩展顺序 | 16 → 32 → 128 卡通过后，分级评估 256 / 512 / 1024 卡；高级结构另行验收 |

## 3. 本次审阅希望确定的研究口径

优先判断：能否解释某条共享链路的排队怎样影响业务，而非只比较总耗时；是否同时报告网络服务量与额外等待；不同条件是否保持请求量、路由、计算成本和总网络资源可比。

> 本文是实验方法审阅稿。128 卡校验尚未通过；multi-rail、HPN 参考结构、真实路由与实机校准不作为本轮已经完成的结论。本文生成不触发新的仿真或参数扫描。

# 01 / 联合执行与 trace 的含义

::: flow

## 1. 前端生成依赖图，不固定发包时刻

Scheduler 根据活跃请求、KV 状态和 EP 组决定本轮 token；构图器生成逐层计算节点、逻辑消息及前驱；Chakra 图交给 ASTRA 执行。消息只有在实际前驱完成后才进入网络。Python 构图的宿主耗时不计入仿真时间。

| 输入或记录 | 内容与用途 |
|---|---|
| 请求与路由 | request、token、layer、context、源 rank、专家选择、seed 和来源标签 |
| 计算图 | node_id、rank、duration_ns、前驱；包含 embedding、attention、pack、expert、merge、残差及输出阶段 |
| 逻辑消息 | group / wave / layer / phase / id、src、dst、payload bytes、前驱和聚合身份 |
| 放置与网络 | 专家→rank→GPU→server、NIC 连接、每条链路速率/传播、交换机和协议参数 |

## 2. 机内和跨机共享同一仿真时钟

同 GPU 的专家贡献不产生网络消息；同服务器不同 GPU 走分块机内互连；跨服务器走原生 RDMA。机内事件与 RDMA 事件均登记到同一个 ns-3 Simulator，所有组、层和轮次保持网络状态，不独立运行后相加。

## 3. 完成事件必须区分

同一逻辑消息只发送一次，RECV 仅等待。跨机接收端得到完整连续字节后放行消费者；发送端完整 ACK 后回收相应发送事务资源。机内消息按实际分块交付触发数据就绪，没有 RDMA ACK。字段复用不能改变事件解释。

> 原始包、路径、队列和回调用于验证；它们不是前端预设的结果。固定时刻的流量重放仅作网络微基准，不替代在线服务实验。

# 02 / 模型、batch 与 All-to-All-v

## 1. 固定模型及设备声明

基线取锁定 LLMServingSim 中已有的 Qwen3 配置：48 层，隐藏维 H=2048，专家 FFN 中间维 768，128 专家，Top-K=8；Q heads=32、KV heads=4、head_dim=128。按声明结构核算总参数为 30,532,122,624，约 305.3 亿。

设备标签 H100、容量 80 GiB；每 GPU 外部 NIC 400 Gb/s。标签不会生成实机性能表。attention、expert、pack 等采用配置中的声明成本；模型全层依赖已建模，但不执行张量数值前向。权重和 GQA KV 单独核算，工作区、激活和分配器开销尚未校准，不能据此给生产容量保证。

## 2. 明确 batch 和输入大小

B = 每 rank 每轮的活跃序列数；N = 使用的 GPU/rank 数；全局每步 token 数 T=N×B。context=2048 表示已有 KV 的上下文长度，不是每轮发送 2048 个新 token。近期运行 2 轮 Decode 作因果验收，不能由此估计稳定态 p99。

## 3. 专家选择决定非均匀字节矩阵

C[i,j] 为源 rank i 的 token 选中、且专家归属于 rank j 的贡献数。每个贡献大小 H×2=4096 B。Dispatch[i,j]=C[i,j]×4096 B；Combine 反向返回同尺寸结果。相同目的 rank 的贡献聚合为消息，当前按专家复制，不作跨专家去重。

因此采用按实际字节矩阵生成的直接成对 All-to-All-v 参考实现；零元素不发包。它不是 NCCL/DeepEP 算法复现，也不是所有 GPU 对之间都发送相同字节。

| 层级 | 每层每轮、每个方向的统计口径 |
|---|---|
| 总逻辑贡献 | T×8×4096 B；128 卡、B=1 时为 4 MiB，含同 GPU 项 |
| 机内 payload | i≠j 且 server(i)=server(j) 的矩阵元素之和 |
| 跨机 payload | server(i)≠server(j) 的矩阵元素之和；进一步拆同 Pod / 跨 Pod |
| 线上字节 | 数据、报头、ACK、重传分别统计；不能用 payload 代替链路占用 |

> EP=专家并行，一个组内分片专家；多个 EP 组表示多个推理副本。TP=PP=1。本轮不含训练 DP 梯度 AllReduce，也不将副本吞吐变化写成纯网络收益。

# 03 / 百卡三层 Clos 与机内拓扑

## 1. 默认 128 卡物理连接

2 Pod × 每 Pod 8 台服务器 × 每服务器 8 GPU。每 GPU 配 1 条 400G 外部接入链路；每 Pod 4 ToR、4 Agg；全网 4 Core。每 ToR 连本 Pod 全部 4 Agg，每 Agg 连分组对应的 1 Core。Core 全为普通电交换机，不使用 OCS 光电路交换。

跨 Pod 路径为 GPU→ToR→Agg→Core→Agg→ToR→GPU；实际采用哪条等价路径由网络实现选择并记录，不用拓扑示意图代替运行路径。

| 分层对象 | 数量、速率与时延 |
|---|---|
| 外部接入 | 128 条；每方向 400 Gb/s；每条传播 1 μs |
| ToR—Agg | 32 条；每方向 400 Gb/s；每条传播 1 μs |
| Agg—Core | 8 条；每方向 400 Gb/s；每条传播 1 μs |
| 机内互连 | 每 GPU 入/出方向各 450 GB/s；传播参数 100 ns；分块 16 KiB |
| 总量 | 128 GPU、16 server、8 ToR、8 Agg、4 Core；外部链路共 168 条 |

## 2. 这是显式超售的基线

每 ToR 下接 16 GPU，接入总量 6.4 Tb/s，上联 1.6 Tb/s，局部下/上行比 4:1。每 Agg 的 ToR 侧 1.6 Tb/s、Core 侧 0.4 Tb/s，局部比也是 4:1。每 Pod 的 GPU 接入为 25.6 Tb/s，跨 Pod 出口总量 1.6 Tb/s，比为 16:1。双向容量分开计算，不把收发相加冲淡瓶颈。

## 3. 机内模型的能力边界

机内采用非阻塞交换织构：每块先竞争源 GPU 入链路，再竞争目的 GPU 出链路，有串行化、传播和 FIFO 等待。两源发往同一 GPU 时共享目的出口；不同 GPU 对可并行。

这是一种可校准的带宽与端口竞争抽象，不是完整 NVLink/NVSwitch 协议，不包含信用、交换机内部拥塞、PCIe/HBM 或 NIC DMA 的全部细节。450 GB/s 和 100 ns 均为声明参考值。

> 可配置每层数量、扇出、逐层带宽、时延和端口限额；必须同时审计物理可达性、端口数与超售比。多 rail、双 plane 和 HPN 参考结构待基线验收后另做容量匹配对照。

# 04 / 对照设计：每次回答一个问题

## 1. 先固定输入，再研究网络

模型结构、精度、上下文、专家归属和 seed 写入配置。网络对照重用完全相同的专家路由与逐对字节矩阵；不能因网络完成顺序而重新抽样。batch、EP 或放置改变时，另报实际 token、专家贡献、机内及跨机字节的变化。

| 组别 | 对照方法与目的 |
|---|---|
| A：规模验收 | 16 / 32 / 128 卡，B=1、全体组成一个 EP 组；只检验执行与资源扩展，不能叫强扩展加速比 |
| B：跨 Pod 出口 | 固定 128 卡与流量，仅改 Agg—Core 速率，建议 100 / 200 / 400G；ECN 阈值需显式匹配各速率 |
| C：接入与汇聚 | 分别改变接入或 ToR—Agg 带宽；与 B 比较，区分源 NIC、汇聚与跨 Pod 出口瓶颈 |
| D：batch | 固定 128 卡，B=1 / 4 / 8；统计负载增量、包数、队列和阶段完成，先通过有界规模预检 |
| E：热点和放置 | 相同 token/Top-K 下对照均衡与合成热点；固定同一热点路由再改变专家放置，分离计算热点与网络热点 |
| F：机内争用 | 单源→单目的，与双源→同目的对照；再固定服务流量改变机内带宽，检验机内是否遮蔽跨机优化 |

## 2. 把负载扩展与网络扩展分开

固定 B=1 从 16 到 128 卡，总 token 增加 8 倍，EP、专家复制开销、网络规模和路径结构也变化；结果用于说明各条件，不能直接宣称网络扩展效率。

拟增加两类更严格对照：①固定全局 T=128，16 / 32 / 128 卡对应 B=8 / 4 / 1，明确 EP 变化带来的放置影响；②固定 EP=16，改变副本数 1 / 2 / 8，同时区分固定每副本负载与固定全局负载。二者仍需分别解释，不能合成一个“规模效应”。

## 3. 不无条件扫描全部组合

先用一个条件查机制，再补能区分竞争解释的条件。跨 Pod 降带宽若没有显著业务影响，检查实际跨 Pod 字节和关键依赖，不人为增加热点来维持预期。

> B—F 为拟开展的机制实验，不表示本轮新矩阵已经执行。带宽改变若还要改协议参数，必须记录该联动；结构对比同时给等容量、等端口或等交换机预算口径。

# 05 / 热点、EP 分组与千卡部署

## 1. 热点不等于随机不均匀

当前均衡路由为确定性构造的专家选择多重集，seed 用于排列；并不是从真实分布独立随机采样。合成热点条件规定一半 token 包含专家 0，Top-K 内不重复。二者用于控制变量，不证明真实 MoE 训练或推理存在同样的热点。

真实输入拟使用 core12345/MoE_expert_selection_trace，但原始数据尚未取得和核验。接入前必须确认模型、层、专家编号、Top-K、训练/推理阶段、token 顺序和 batch 含义；缺少源 rank/设备放置时，只能分析专家热度，并显式声明补充的放置假设。

| 分析对象 | 需要验证的现象 |
|---|---|
| 专家热度 | 每层选择次数、最大值/均值、变异系数、零负载专家比例；不能只看平均值 |
| 热点持续性 | 热点是否跨 batch / step 持续；分别看层内与跨层，不将打乱后结果当原始时间序列 |
| 网络热点 | 将同一专家选择映射为字节矩阵、目的 GPU/NIC 汇聚、跨 Pod 割集负载 |
| 基线 | 原始路由与保留边际热度的重排、均衡构造对照；区分频率偏斜与同步相关性 |

## 2. EP 与副本的选择依据

先核算每组权重、KV 和设备容量，再比较该 EP 下跨机字节、热点汇聚与每步完成。EP 扩大可能降低单卡专家权重，却增加跨服务器流量；增加推理副本提高并发容量，但不等于缩短单请求通信。

本模型 E=128，当前每 rank 持有完整专家子集，要求 E 可被 EP 整除。因此不能直接设置 EP=1024。千卡可采用 8 个 EP128 推理副本，或更多较小 EP 组；多个组共享同一物理网络并独立推进。专家内部再切分属于未来新增能力。

## 3. 千卡的第一种候选拓扑

可保持单 rail 三层结构：8 Pod × 每 Pod 16 server × 8 GPU=1024 GPU；每 Pod 8 ToR、8 Agg，全网 8 Core，每 ToR 连 8 Agg、每 Agg 连分组的 1 Core。共 64 ToR、64 Agg、8 Core，外部链路 1600 条。它仍是有超售的设计候选，须经过生成、端口/路径审计及后端资源评估。

> 先比较 EP 组放在单 Pod 内与跨 Pod 分布：前者可能不产生跨 Pod 专家流量。千卡终点数量本身不保证触发核心层瓶颈；必须以实际流量与路径为准。

# 06 / 正确性验收与现有进度

## 1. 先通过小场景，再讨论百卡结果

| 关卡 | 通过条件 |
|---|---|
| G0 输入 | 模型尺寸、EP 合法性、容量、节点/链路、端口预算和可达性校验；拒绝不支持的配置 |
| G1 网络微基准 | 单流串行化下界、同机 incast、跨机路径、MTU 边界；每条消息交付/事务回调恰好一次 |
| G2 因果 | 逐消息核对路由→字节→包；消费者开始不早于数据就绪；发送回收不冒充消费完成 |
| G3 服务 | 完整 48 层、两轮 Decode；请求进度与下一轮启动来自实际回调；机内/跨机字节守恒 |
| G4 目标规模 | 128 卡真实执行、全部验收通过并保存资源和来源；随后才进入机制对照和千卡扩展 |

## 2. 截至本稿的实际状态

16 卡：48 层两轮通过，18,876 条逻辑消息；32 卡：同范围通过，43,912 条逻辑消息。这是声明成本/合成路由下的功能证据，不能替代 H100 校准。

机内探针：单源 1 MiB 于 2605 ns 完成；双源同目的分别于 4936 / 4973 ns 完成，支持“目的出口共享带宽”的模型内行为。相同线端口号、不同端点的两条 RDMA 消息也完成一次性回调核验。

128 卡：原生执行子进程返回 0，随后服务校验报告缺少 ('g0.w0',0,1,'issue') 事件，尚无通过结论。该问题须区分执行遗漏与日志/解析遗漏，定位并复验后才可报告完整百卡流程。不能以正常退出代替因果验收。

## 3. 校验不能只依赖汇总器

逐 token 重算矩阵和每方向字节；检查完整首尾及逐层依赖；抽查跨 Pod 的真实跳数/节点；按 GPU/方向核算机内链路 payload；核对原始 ASTRA issue/callback 与请求完成记录。每次失败保留原始证据，不删除断言、不拼接独立耗时。

> 当前全量场景的队列采集采用 summary，仅记录钩子观测次数和最大值等摘要。它支持峰值检查，不足以绘制完整队列时序、计算队列分位数或独立证明某次等待的原因。归因需有界补采 events 或缩小场景。

# 07 / 指标、机制归因与结果解释

## 1. 网络是主要评价对象

| 层次 | 输出指标与解释 |
|---|---|
| 服务 | 每轮 token 完成、相邻完成间隔、组吞吐、请求完成；短窗口不称稳定态 TPOT/p99 |
| 消息 | ready / issue / receive_ready / ACK，payload、包数、FCT；机内与跨机分开 |
| 链路 | 按接入 / ToR—Agg / Agg—Core 汇总线上字节、忙碌时间与利用率；区分方向 |
| 拥塞 | 出口队列峰值、PFC/ECN/速率反馈（仅在实际有记录时报告）；机内端口等待另计 |
| 业务影响 | 等待对应的真实资源、占用者、放行事件及后继启动；不能将全体流 FCT 相加充当业务延迟 |
| 扩展成本 | 宿主用时、RSS、产物大小、消息/事件/节点数；与仿真 ns 时间分开 |

## 2. 提前列出竞争解释

解释 A：跨 Pod 上联不足。预期同一字节矩阵下，该层队列与业务关键等待同时变化；若实际没有跨 Pod 流量或等待不在关键依赖上，解释被削弱。

解释 B：目的 GPU/NIC 汇聚或专家计算。预期改变 Core 带宽作用弱，改变专家放置、机内出口或目的端容量更有效；要固定路由后再比较，避免把字节减少当成排队优化。

解释 C：发送并发/资源与反馈。预期未注入前等待也可能与此前事务、ACK、PFC 或发送调度相关；仅看当前消息路径不足以排除网络影响。应追到允许发送的实际事件。

## 3. 把服务量和额外等待分开

先以割集跨越字节/容量、单消息串行化和传播给出必要下界，再解释超过下界的等待。某端口累计忙碌、队列峰值和业务慢请求具有相关性，仍不足以证明可消除的服务损失。

拟采用相同流量下的有限反事实：只扩指定层容量，检查哪条依赖提前、是否传到最终完成。存在并列瓶颈时，局部等待减少可能不缩短业务；这种无收益结果也应保留。

> p95/p99 需要明确样本单位、足够样本及预热/测量窗口。机制实验先从可解释的小场景入手；使用固定路由的网络配对对照，再用预声明 seed 集合检查稳健性，不将少数确定性运行包装成统计结论。

# 08 / 复现、扩展边界与最终产出

## 1. 每次实验交付哪些文件

配置与有效参数、平台/依赖提交、未提交补丁或源码哈希、路由来源/seed、完整命令、拓扑审计、wave/Chakra 对应关系、原始网络结果与日志、校验报告、资源记录、CSV/JSON 摘要和绘图源。图表只读已完成产物；方法、结果和失败说明分开存放。

现有入口为 scaleout topology / rdma-probe / rdma-run / rdma-check；百卡实验脚本为 experiments/scaleout_clos128/run.py，配置位于 examples/scaleout_clos128。统一脚本逐级执行，任一关卡失败即停止；不把当前校验失败的配置写成已验证教程。

## 2. 资源预算与逐级扩展

本轮单例预算：宿主 300 秒、进程树 RSS 6 GiB、单进程地址空间 12 GiB、仿真最多 100 ms；本轮专用目录累计 3 GiB，并保留卷空间 8 GiB。失败保留，不自动扩限或重跑。

128 卡校验通过后，先分析图节点、活跃消息/QP、固定交换机数组、KV 元数据与日志体积，再为 256 / 512 / 1024 卡分别制定预算。可采用稀疏消息生成、摘要观测、有界详细窗口等工程改进，但不得改变消息字节、依赖或完成语义。当前配置允许的数值上限不代表实际规模已验证。

## 3. 后续网络结构与校准顺序

先完成三层 Clos 基线及分层容量归因，再对比参数化 multi-rail、单/双 plane 和 HPN 参考电交换结构；同时固定 GPU 数、流量和总 NIC 容量，并列出额外端口/交换机预算。阿里 ns-3 作为独立机制参考与对照候选，不与当前 ASTRA 原生 ns-3 混链。

硬件校准先匹配实际 GPU、NIC、交换机、通信库和消息尺寸，再覆盖单流、incast、多对多及分层路径；报告误差与适用边界。只改 GPU 名称、带宽数字或拓扑名称，均不能视为完成校准或完整复现商用网络。

## 4. 最终研究产出

近期：可审计的百卡基线、统一配置/执行/校验入口、网络瓶颈证据和负面结果。中期：千卡多 EP 组共享网络的有界执行与真实路由对照。长期：以实机校准和强基线验证一种针对 MoE 通信长尾的优化，形成可复用工具、基准与论文；扩规模与提高带宽本身不作为机制创新。

> 审阅焦点：①Decode 与网络主线是否合适；②模型和超售拓扑是否代表目标集群；③先解决哪类网络瓶颈；④真实路由和实机校准的可获得来源。源配置、源码依据及当前证据索引附于可编辑原文末尾。
