# MoE Scale-Out 网络联合仿真实验方法

审阅稿 v0.4 · 2026-10-16 · 参数化拓扑、专家通信与规模成本

## 1. 研究要回答什么

MoE（混合专家模型）的专家分发与结果回收，会让不同 GPU 同时向多个目的地传输数据。本研究关注：这些通信在接入、汇聚、跨 Pod 出口或目的端哪里发生竞争；竞争怎样沿计算依赖拖慢 token 完成；改变网络结构、带宽或专家放置后，业务是否真正受益。

最终目标是形成一套可复现的网络实验平台：固定模型和路由后修改网络，固定网络后修改 batch、专家并行或放置，以逐消息、逐链路和业务完成事件解释结果，为 MoE 集群网络设计与优化提供证据。

## 2. 本稿的研究范围

| 对象 | 方法约定 |
|---|---|
| 服务 | 先研究 KV 已就绪的 Decode；每条活跃序列每步生成一个 token |
| 通信 | 专家并行的 Dispatch / Combine，使用非均匀 All-to-All-v 字节矩阵 |
| 网络 | 普通电交换 Core；支持接入、Agg 汇聚、类 Clos，以及 multi-rail / 双平面结构的研究输入 |
| 执行 | LLMServingSim → Chakra → ASTRA-sim → 非 UB ns-3；网络完成反馈推进下一轮 |
| 扩规模 | 分开评价物理图生成、实际业务执行、正确性和宿主等待成本 |

## 3. 审阅重点

请重点审阅：目标拓扑是否代表实际集群；网络对照是否公平；热点与跨 Pod 流量是否真实；各阶段产出能否回答明确问题。本文给出实验方法，不将尚未执行的对照写成研究结论。

> 相比 v0.3，本稿突出可配置拓扑与网络对照，补充宿主运行成本的测量方法。旧稿保留其生成时的历史状态；本稿不重复旧稿中已经过时的验收进度。

# 01 / 前端生成什么，后端执行什么

::: flow

## 1. 输入是业务与依赖，不是预先写死的发包时刻

前端根据请求、KV 状态、batch 和专家选择生成每轮任务：包括计算节点、逻辑消息、消息大小及前驱依赖。Chakra 保存任务图，ASTRA-sim 推进就绪节点；通信只有在实际前驱完成后才注入 ns-3 网络。

| 记录 | 关键内容 |
|---|---|
| 请求与路由 | 请求、token、层、上下文、源 rank、专家选择、来源与 seed |
| 计算依赖图 | 节点身份、rank、声明计算时间、前驱；包括 attention、专家和首尾阶段 |
| 逻辑通信 | EP 组、轮次、层、阶段、源/目的 rank、payload 字节、逻辑消息身份 |
| 物理映射 | 专家→rank→GPU→服务器→NIC；交换机连接、链路速率与传播时延 |

## 2. 后端决定通信何时完成

同 GPU 的贡献不产生网络消息；同服务器不同 GPU 走机内分块带宽模型；跨服务器消息走原生 RDMA。两者使用同一个 ns-3 Simulator，多个 EP 组共享持续存在的网络状态，不能分别运行后把耗时相加。

接收端获得完整数据后放行消费者；发送端得到完整 ACK 后释放相应发送事务资源。数据就绪与发送回收分别记录，同一逻辑传输只发送一次。

> 固定发包时间的重放可用于单独测网络，但不能代替在线依赖实验。构图消耗的宿主时间计入运行成本，不计入被模拟的业务时间。

# 02 / 模型、输入大小与 GPU 声明

## 1. 近期固定模型作为可解释基线

采用 Qwen3-30B-A3B-Instruct-2507 的声明结构：48 层、隐藏维 H=2048、专家中间维 768、128 专家、Top-K=8；Q/KV heads=32/4，head_dim=128。按声明结构核算总参数约 305.3 亿，通信元素采用 BF16，即每元素 2 B。

设备声明为 H100、80 GiB，每 GPU 外部接入为 400 Gb/s。计算时间使用声明参考成本，不执行张量数值前向。更换 A100/H100 名称不会自动产生对应性能；比较 GPU 时应同时提供有来源的计算成本、容量和机内/NIC 参数。

## 2. batch 与上下文分别控制什么

令 B 为每 rank 每轮的活跃序列数，N 为总 GPU/rank 数。当前每条序列在每步产生一个新 token，因此全局每步 token 数 T=N×B；单个 EP 组的 token 数为 EP×B。

context=2048 表示已有 KV 的上下文长度，并非每轮输入 2048 个新 token。GQA 的 BF16 KV 为每 token 全层 98,304 B；context 改变 KV 占用和 attention 成本，不自动改变每个专家贡献的 H×2 B。

| 可修改对象 | 必须一起核对的内容 |
|---|---|
| 模型尺寸 | 层数、H、专家维度、专家数、Top-K、注意力结构与权重/KV 容量 |
| batch | 实际活跃序列、token 数、专家贡献、聚合消息大小、KV 与计算成本 |
| GPU 类型 | 容量、计算成本来源、机内互连、NIC 与共享资源约束 |
| 输入阶段 | Decode 与 Prefill 分开；多序列 Prefill 须有匹配的 attention 采样形状 |

> 近期先用完整 48 层、两轮 Decode 检查因果执行。Prefill、训练和稳定态尾延迟另设输入与验收，不能由本轮短窗口直接推导。

# 03 / All-to-All、EP 与副本怎么定义

## 1. 从专家选择得到通信量

令 C[i,j] 为源 rank i 的 token 选中的、归属于 rank j 的专家贡献数。每个贡献为 H×2=4096 B，因此 Dispatch[i,j]=C[i,j]×4096 B；Combine 沿反方向返回同尺寸结果。

当前将相同目的 rank 的贡献聚合为消息，按专家复制，不跨专家去重；零元素不发消息。这是直接成对的 All-to-All-v 参考实现，尚不能代表 NCCL 或 DeepEP 的具体算法与分层优化。

每层、每轮、每个方向的总逻辑贡献为 T×8×4096 B，包含同 GPU 项。物理网络字节必须扣除同 GPU 项，再分别统计同服务器、同 Pod 跨服务器及跨 Pod 部分。线上占用还包含报头、ACK 和重传。

## 2. 选择 EP 前先做容量与位置核算

EP 是专家并行，一个组内的设备分担专家。当前要求专家数可被 EP 整除，每个 rank 持有完整专家子集；128 专家的模型不能直接设为 EP1024。先核算权重、KV 和声明容量，再比较跨机字节与目的端汇聚。

| 配置方向 | 网络上要回答的问题 |
|---|---|
| 扩大 EP | 单卡专家权重下降时，通信范围和跨服务器比例增加多少 |
| 增加推理副本 | 多组共享网络后，吞吐、互相干扰与完成时间如何变化 |
| 同 Pod / 跨 Pod 放置 | 相同组与路由下，哪些消息真正经过 Agg—Core |
| 训练 DP | 额外存在梯度同步；必须加入明确依赖图后才能研究与 EP 的竞争 |

## 3. 千卡不是千卡全互发

可使用多个较小 EP 组共享千卡物理网络。例如 EP4 对应 256 个推理副本；EP128 对应 8 个副本。EP4 的组内交换与 EP128 的组内交换是不同工作量，应分别解释，不能合并成同一条扩展效率曲线。

> 本轮 TP=PP=1，不含训练 DP 梯度 AllReduce。推理副本与训练 DP 的通信含义不同；千卡终点数量也不保证核心层有负载。

# 04 / 可配置网络结构与图片对应关系

## 1. Agg 和 Clos 不是互斥选项

Agg 是汇聚层交换机的角色；Clos 是交换机之间的连接结构。实验既要能生成 ToR—Agg 汇聚网络，也要能生成带跨 Pod Core 的三层类 Clos，并用端口、扇出和容量约束判断其实际性质。

| 结构 | 连接方式与用途 |
|---|---|
| 两层 Leaf–Spine | GPU→ToR→Core；Agg=0，用于较小网络或层数对照 |
| Pod 内汇聚 | GPU→ToR→Agg；Core=0，多 Pod 时不能默认互通 |
| 三层类 Clos | GPU→ToR→Agg→Core；Pod 内汇聚，Core 连接不同 Pod |
| Multi-rail | 按 GPU 槽位/NIC 分接入组；上层可按 rail 隔离或共享 |
| HPN 参考结构 | Segment、槽位 rail、双 plane、Pod 内 Agg 与跨 Pod 电交换 Core |

用户第二幅图的 OCS 替换为普通电交换 Core，不建模光路重构、重构时间或时隙调度。该结构与 HPN 在分层组织上有参考关系，但不能据此声称完整复现阿里生产网络。

## 2. Rail 和 plane 分别是什么

Rail 是接线分组；plane 是独立交换网络副本。每 GPU 只有单 rail NIC 且上层也隔离时，跨 rail 的 All-to-All 可能不可达。不能把 GPU 当交换机，凭空补出跨 rail 路径。

双 plane 需要明确 NIC 的端口预算和选 plane 规则。例如同一 NIC 总预算 400G，可配置两个 200G 端口；若改成两个 400G，就同时增加了硬件容量，不能将全部收益归因于双平面结构。

> 当前已有这些结构的参数化生成与审计；业务验证主要沿单 rail 三层基线推进。双平面自动分流、跨 rail 中继和故障切换须单独实现与验收。

# 05 / 每层几个、怎么连、带宽在哪

## 1. 配置项与计数关系

| 参数类别 | 公开字段及作用 |
|---|---|
| 部署规模 | pods、segments_per_pod、servers_per_segment、gpus_per_server |
| 接入分组 | rails、planes、rails_by_gpu_slot；明确每个 GPU/NIC 接到哪里 |
| 交换机数量 | tors_per_segment_per_rail、aggs_per_pod_per_group、cores_per_group |
| 连接规则 | tor_uplinks、agg_uplinks；Core 可全互连、分组或循环连接 |
| 分层带宽 | access、tor_agg、agg_core、tor_core；分别设置 rate_bps、delay_ns |
| 物理约束 | NIC 总速率、各类节点端口上限，以及节点、交换机和边数量预算 |

令 P/S/H/G 分别为 Pod、每 Pod 的 Segment、每 Segment 的服务器、每服务器 GPU 数，R/L 为 rail/plane 数，T/A/C 为相应层的配置数量；Q 在共享上层时为 1，在按 rail 分组时为 R。

GPU=P×S×H×G；ToR=P×S×R×T×L；Agg=P×Q×A×L；Core=Q×C×L。Core 数不再乘 Pod 数。计数采用同构分层配置，当前不承诺逐 Pod 异构数量或任意逐链路覆写。

## 2. 修改数量时同时审计什么

检查实际端口数、各层可达性、等价路径、闲置交换机和下/上行容量比。分组 Clos 必须满足分组关系，任意增加交换机数量不保证无阻塞；不合法配置拒绝，分裂网络如实报告。

带宽按每个方向分别计算。比如某 Pod 下接 64 个 400G 端点、仅有 4 条 400G Core 上联，其接入/出口比为 16:1。这是声明容量比，不等于实测吞吐，也不能用收发相加来稀释超售。

> 链路 b/s 与机内 GB/s 的单位必须区分。当前机内参考为每 GPU 每方向 450 GB/s、两段各 100 ns、16 KiB 分块；这是共享端口抽象，尚无完整 NVLink 协议与硬件校准。

# 06 / 对照实验：一次区分一个原因

## 1. 先固定业务，再改变网络

每组网络对照重用相同模型、token、专家选择、专家放置和逻辑字节矩阵。固定路由来源与 seed，避免网络完成顺序变化后重新抽样。先小范围核验，再扩到能暴露目标瓶颈的规模。

| 对照组 | 改变什么，以及回答什么 |
|---|---|
| 分层容量 | 固定流量，分别修改接入、ToR—Agg、Agg—Core 速率；定位限制层 |
| 汇聚与类 Clos | 固定 GPU 与流量，列出端口、链路和割集容量差异；判断结构收益来源 |
| 单 / 多 rail | 固定可达性与总 NIC 容量后比较；未实现跨 rail 传输的条件不进入性能排名 |
| 单 / 双 plane | 固定总接入预算，明确选 plane 策略；分离多路径与容量增加的作用 |
| batch | B=1/4/8，报告 token、字节、包数与计算变化；不将负载增长称为排队优化 |
| EP 与放置 | 固定路由，改变组大小或同/跨 Pod 放置；报告复制、通信范围和容量变化 |

## 2. 避免混淆结构与资源数量

等成本、等端口和等割集容量是不同口径。每次明确选择一种主要约束，并同时列出其他资源差异。现有四套千卡结构的交换机、端口和带宽并不相同，直接比较总耗时不能证明哪一种结构更好。

带宽对照还需控制传输与拥塞参数。可先做协议参数保持不变的敏感性实验，再做阈值随容量匹配的实验；两者回答的问题不同，不能悄悄联动后称为仅改带宽。

## 3. 优先证伪，保留无收益结果

若增加 Core 带宽没有缩短业务完成，先检查跨 Pod 字节是否足够、等待是否位于关键依赖上，以及目的端或专家计算是否遮蔽了收益。保留无收益结果，不人为制造热点来维持预期。

> 本页是拟开展的机制对照，不表示整张矩阵已经执行。通信算法的层次化、去重和调度优化属于后续独立变量，必须先核对字节与依赖语义。

# 07 / 热点：从专家分布到网络汇聚

## 1. 为什么不能只用均匀随机路由

MoE 的专家选择可能偏斜，但专家热度不自动等于网络热点：同一热门专家若在本 GPU、同机或跨 Pod，会产生不同流量；多个 token 同时到达还可能形成目的端瞬时汇聚。

当前合成均衡与热点条件只用于控制变量。真实输入候选为 core12345/MoE_expert_selection_trace；原始数据尚待取得与核验，不能把合成结果当成该数据集的发现，也不能从推理路由推断训练分布。

| 分析步骤 | 输入、动作与预期产物 |
|---|---|
| 来源核验 | 确认模型、训练/推理阶段、层、专家编号、Top-K、batch 与时间顺序 |
| 热度分析 | 每层计数、最大/均值、变异系数、空闲专家比例及热点持续性 |
| 通信重建 | 加入明确的 token 源 rank 与专家放置，生成逐对字节矩阵 |
| 物理投影 | 统计目的 GPU/NIC、机内、同 Pod 与跨 Pod 负载；核对实际路径 |
| 配对比较 | 原始顺序、保留边际热度的重排与均衡基线，分离热度和同时性 |

## 2. 数据缺项怎么处理

缺源设备信息时只能直接分析专家热度；若要研究网络，须补充有标记的 rank/放置假设。缺时间顺序时不能研究热点持续性。不同模型层数或专家数不直接套入当前 Qwen3 结构，需先建立有效映射或更换模型配置。

## 3. 把计算热点与网络热点分开

第一组保持同一路由和专家计算成本，仅改变放置，观察网络流量与完成；第二组保持物理输入，改变有依据的专家计算成本，观察计算等待。专家变热时若计算量和网络同时变化，应明确两者贡献。

> 接收队列峰值或热门专家计数只能提示竞争位置。要解释业务拖慢，仍须追踪实际占用者、放行事件及后继依赖。

# 08 / 千卡扩展与实际等待时间

## 1. 两种规模变化分别报告

一类为单副本 EP 随 GPU 数增大，例如 16/32/128 卡、B=1；此时全局 token、EP 与拓扑同时变化。另一类保持 EP 不变、增加副本，例如 EP4 下 256/512/1024 卡；此时多个组共享网络，负载随副本数增大。

两类不能画成同一条强扩展曲线。固定全局 token 的实验又是另一口径；需明确不同规模对应的 batch、放置及网络总容量。

## 2. 必须分开的时间口径

| 指标 | 测量与解释 |
|---|---|
| 仿真内部时间 | 网络与业务事件的 finish_ns，回答被模拟业务用了多久 |
| Worker 墙钟时间 | 从初始化、构图到后端执行和结果写出，回答本机实际等多久 |
| 完整命令时间 | 公共运行命令的开始/结束；还可能包含准备与自动校验 |
| 独立校验时间 | 单独调用检查命令时测量；不能把所有时间差都称作校验成本 |
| 内存与产物 | 进程树采样峰值 RSS、产物体积、消息/图节点数；标明采样口径 |

## 3. 有界执行与增长趋势

沿小规模→百卡→256→512→1024 分级观察；每例预先声明墙钟、内存、磁盘和模拟时间上限。达到预算即停止，保留日志，不自动加限额重跑。千卡是否完成与增长趋势是否可测是两个验收问题。

超时点写为“超过预算仍未完成”，作为右删失数据，不能画成在预算时刻完成。图中按实现版本、EP 和负载口径分组；只对同版本可比完成点计算增长比。外推单独标为预测，不替代实测。

> 趋势报告同时列宿主机器、构建、源码/依赖版本、并发背景、预算与状态。一次运行只支持一次实测；若估算整张矩阵成本，注明顺序执行与每例耗时假设。

# 09 / 正确性、归因与最终交付

## 1. 先验证执行，再解释机制

| 阶段目标 | 验收依据与产出 |
|---|---|
| 输入正确 | 模型/EP 合法、容量声明、拓扑端口与可达性；保存配置和审计 |
| 网络正确 | 单流、同机汇聚、跨 Pod 路径；逐消息数据就绪/事务回调恰好一次 |
| 联合执行正确 | 全层与多轮实际推进、消费者不早于数据就绪、机内/跨机字节守恒 |
| 规模成本清楚 | 保存完成/超时及资源记录，形成可比较的等待时间曲线 |
| 机制证据成立 | 相同流量下改一个资源，定位等待与后继变化，报告有效或无收益结果 |

## 2. 网络指标怎样连接业务

记录消息就绪、发起、完整接收与 ACK，逐层汇总线上字节、忙碌时间和队列。先用跨割集字节/容量给必要服务量下界，再追踪超过下界的等待。不能把所有流完成时间相加充当业务延迟。

当前 summary 观测可支持队列峰值检查，不能提供完整队列时序或独立证明长尾因果。需要归因时在预算内补采详细窗口或缩小场景。短至两轮的功能实验不报告稳定态 p99。

## 3. 复现与阶段产出

每例保存有效配置、路由来源/seed、源码与依赖提交或补丁哈希、完整命令、预算、拓扑审计、任务图、结果、校验、资源记录及绘图源。平台与实验分开维护；本地修改与提交，不推送仓库。

近期产出为可审计基线、等待成本报告和分层瓶颈对照；中期引入真实专家路由，比较放置与结构；长期在实机校准及强基线支持下提出一项 MoE 网络优化，沉淀工具、基准和论文。规模扩大本身不作为机制创新。

> 建议优先审阅：①目标集群的每层数量和容量预算；②先做哪项分层网络对照；③真实路由与硬件校准的来源。方法审定后再据预算展开矩阵。
