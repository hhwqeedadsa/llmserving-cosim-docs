# 小规模 Scale-Out 基础实验结果

本轮打通实际 LLMServingSim Scheduler → Chakra → ASTRA → 单一非 UB RDMA ns-3 → 完成事件 → 下一轮组批。主实验为8个逻辑GPU、4台双卡服务器、2个Pod；H1024/F4096/E16/Top-K2、激活2B、2层4次Decode、每rank batch 1/4/16，TP=PP=1。GPU标签为A100，计算使用声明成本，路由为合成数据，KV初态已就绪。

## 1. 实际完成了什么

- 10个主配置×路由seed 11/23/37，共30次真实服务运行；另1次独立rail的合法EP4，非法EP8注入前拒绝。
- 另行完成跨Pod交错EP4：两个组在0 ns启动、共享4个Agg物理出口，8波次、358条消息、972个ASTRA节点全部核验，192.154 μs完成。该功能检查不估计独立的组间竞争损失。
- 5类协议探针：1000/9000B payload分包边界、64流incast、中间包丢失恢复、尾包丢失预期失败。
- 主矩阵及rail共31次结果独立复核，42712个ASTRA节点的前驱与回调符合声明；基线独立重跑的原生result.json及36个语义/Chakra文件逐字节一致。
- H512/F2048/E8变形输入真实运行通过，证明模型维度可修改；不是仅改配置文件或静态估算。
- 28项Scale-Out单元检查、原有完整模型导出兼容检查（4个小型case）、13项固定依赖检查通过。篡改ECN实际阈值、混链第二套ns-3、修改声明计算时长的3个负对照均被拒绝。

## 3. 网络发现及解释

**降上联带宽会把等待传到计算和下一轮调度。** seed11下，Agg→Core从100G降到50G/25G，片段由193.252 μs延至217.751/265.896 μs。业务图、计算成本、远程字节和实际消息路径相同。rank0首层expert由12.162 μs延至13.888/17.487 μs，实际最后依赖分别在该时刻完成接收；不是预写的计算延迟。更多逐节点例子见可视化目录的mechanisms.json。这是网络服务速率与依赖传播的证据，不是排队时延的可加分解。

**固定总带宽的双plane没有自动加速。** 单plane各链路100G，对照双plane每份50G，NIC合计仍100G；seed11由206.393 μs变为220.101 μs。两plane分别实际承载870400/923648 B，没有只走一plane。小消息序列化、flow分配和路径改变共同影响结果，当前证据不支持认定某一项是唯一原因。交换机与队列数量不同，也不称严格等成本部署。

**专家热点不等于更高的网络队列。** 热点使专家0贡献从32增到128，seed11片段由193.252增至209.152 μs，最大queue反而从11272降至9672 B。热点同时改变计算分布、消息数量与释放时序，不能把差值全归给网络拥塞。专家成本统一设0的独立诊断中，均衡/热点分别186.847/193.856 μs，差7.009 μs，说明在该参考条件下网络分布和依赖本身也有影响；不能将其从主差值直接相减。

**batch不是只改通信字节。** B1/B4/B16同时改变请求数、计算量、分包、并发和本地比例。payload为450560/1794048/7245824 B；基于逐token选择重算，不能假定每个seed都精确按batch比例增长。context2048描述KV上下文，并不是本次Dispatch的token数。

**EP4结果混合了放置与副本变化。** 主EP4分组为[0,1,2,3]/[4,5,6,7]，各在单个Pod，本地化减少远程字节到1507328 B；该优势不能当作只改EP的收益。交错[0,2,4,6]/[1,3,5,7]另测共享fabric，证明两组会使用同一Agg出口。两者均是推理副本，不是训练DP AllReduce。

## 4. 协议核查和平台修复

64流汇聚探针全部完成，出现11489次跨端口CE观测、17次PFC pause，64条流均有DCQCN反馈；CE观测不是唯一标记包数。主业务不必触发ECN/PFC，不能因为配置开启就称其主导了性能。

发现原生ConfigEcn参数单位为decimal KB，而公共输入为bytes；适配层现直接设置准确字节字段并导出生效值。headroom需逐端口配置后才汇总ConfigNPort，已纠正顺序。修正前matrix-02归档保留，不用于最终表格。

零专家成本诊断暴露锁定ASTRA跳过零时长COMP后未清除active_nodes的问题；使用其已有零时长事件路径处理，保留依赖、日志与完成断言。主矩阵没有零时长COMP；修复后基线独立重跑一致。

中间包丢失后NACK恢复：逻辑4000 B，源payload因重传变为7000 B，完整接收/ACK分别19352/25376 ns，回调一次。尾包最后1 B丢失后无后续包触发NACK，receive/ACK均为空、完成回调0次，按预期失败。服务主实验限定无故障，不能声称通用可靠恢复。

## 5. 适用范围与交付

模型是有限MoE片段，attention/pack/expert/merge采用显式参考耗时，未自动加载A100/H100实机表。网络为直接成对All-to-All-v，不模拟NCCL/DeepEP全部算法。没有Prefill、训练反向、KV迁移、机内NVLink/PCIe详细模型或千卡逐包运行；HPN只取结构、Core为普通电交换机。
