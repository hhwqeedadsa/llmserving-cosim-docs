# 小规模 Scale-Out 联合仿真实验方法

审阅稿 v0.2 · 2026-10-15 · 网络机制实验方法

## 1. 本次要证明什么

建立从 LLMServingSim 请求与组批，到 ASTRA 依赖图，再到非 UB ns-3 分组网络的全流程。用小规模实验回答：batch、跨 Pod 汇聚和 rail / plane 结构怎样改变 MoE 通信的排队与阶段完成时间，以及这些等待怎样传回服务调度。

首轮采用 8 个 GPU 逻辑端点、4 台双卡服务器。先证明通信与计算之间的事件因果关系，再解释网络现象；千卡、完整训练、真实模型精度与生产容量不作为本轮结论。

## 2. 建议审阅的默认范围

| 项目 | 拟采用方法 |
|---|---|
| 业务 | ready-KV 的 MoE Decode；每序列每步产生 1 个 query token |
| 模型 | 合成 MoE 层：H=1024、F=4096、16 专家、Top-K=2、激活 2 B；2 层、4 次 Decode；计算成本显式声明 |
| 规模 | 8 端点 / 4 服务器 / 2 Pod；EP=8，TP=PP=1 |
| 网络 | 主线复用锁定 ASTRA 的原生 RDMA ns-3；阿里库只作独立语义核查 |
| 重点 | batch、分层带宽、跨 Pod 路径、单/双平面和专家热点 |
| 不纳入首轮 | Prefill、KV 迁移、训练梯度同步、完整 HPN 协议、自动故障切换 |

## 3. 方法、实现与结论分开审阅

已有拓扑生成器与小规模非 UB RDMA 入口。实际实验链路采用 LLMServingSim Scheduler → Chakra 图 → ASTRA → 原生 ns-3 → 完成事件 → 下一轮组批。本文集中描述方法，不列性能结果。

范围分开：1024 GPU 拓扑可静态生成与审计；当前逐包服务入口限制为最多 32 GPU、16 交换机。本稿的主实验仅用 8 个 GPU 逻辑端点，不据此宣称完成千卡网络仿真。

> 审阅重点：网络瓶颈是否有真实路径、端口队列和后继启动证据；对照是否同时改变容量、放置或远程字节。计算成本和专家路由属于声明输入，结果的适用范围由这些假设限定。

# 从前端到网络后端的完整流程

## 1. 业务图与网络执行分工

::: flow

LLMServingSim 的 Scheduler、请求与 KV 状态决定本轮参与序列和 token；中间表示记录计算节点、逻辑通信及依赖；ASTRA 按数据依赖推进节点；唯一一套非 UB ns-3 执行共享的 NIC、链路、队列及协议状态。波次完成后返回前端，更新请求进度并形成下一轮 batch。

固定图重放用于早期排错；最终验收必须跑到下一轮调度，不能用一次离线流量回放代替全流程。Python 构图的宿主耗时不进入仿真时钟。

## 2. 前端究竟生成什么 trace

| 记录 | 必需内容与用途 |
|---|---|
| 请求与路由 | request / token / layer、context 长度、源 rank、所选专家、来源与 seed |
| 计算 DAG | node_id、rank、声明的 duration_ns、前驱；保留 pack、expert、merge 等阶段 |
| 逻辑消息 | run/group/wave/layer/message_id、src/dst、payload_bytes、前驱节点、分块和聚合身份 |
| 映射与配置 | 专家→rank→GPU→server、可用 NIC/rail/plane、分层网络参数、版本与 hash |

这些是依赖和消息描述，不是固定发送时刻表。消息只在前驱实际完成后注入；ns-3 再分成数据包。trace 不预置 FCT、队列长度或“网络结束时间”。Chakra 文件送入 ASTRA；配套 wave.json 保留请求、路由、消息与图节点的对应关系。

## 3. 必须守住的事件语义

同一逻辑消息只发送一次；RECV 负责等待，不再发送一份。区分提交发送、末字节到达、ACK 确认与发送资源回收。消费者只能在声明的数据可用事件之后启动；释放发送资源不能冒充接收就绪。

接收端累计连续字节达到完整消息长度后，放行 RECV 及消费者；发送端等完整 ACK 后结束 SEND。原生按包发送通知不作为业务完成依据。两类事件分别记录并核验，消息及回调均检查恰好一次。

> 全部 EP 组共享同一网络执行与时钟；禁止独立跑各组、各层或 scale-up / scale-out，再将时延相加。

# 输入参数与 MoE 通信量定义

## 1. 负载、GPU 与计算成本

主实验层使用 16 个 routed experts、无 shared expert；H=1024，FFN 中间维 F=4096，Top-K=2，激活采用 FP16/BF16 的 2 B 逻辑尺寸。按三矩阵 gated FFN 粗算，仅专家权重约 0.201B 参数 / 384 MiB，不代表完整语言模型的大小。

GPU 标签为 A100；切换标签不会自动改变性能。计算成本为：attention 1000 ns/token、pack 与 merge 各 30 ns/token、expert 100 ns/贡献。它们用于控制网络对照，尚未经完整 A100/H100 算子校准，不能输出相应实机性能预测。

每序列初始 context=2048，KV 预先就绪；运行 4 次 Decode，逐轮记录启动与完成；有限窗口只作机制观察。单层结果叫“层/阶段完成时间”；只有具备完整 token 依赖与服务回传，才报告相应服务时间。输入 context 不等于本次传输 token 数。

## 2. batch 与通信矩阵

B 明确定义为每 rank 每波次的活跃序列数，取 1 / 4 / 16。EP=8 时全组每步分别产生 8 / 32 / 128 个 token，不使用含糊的“batch=4”代替两者。

首版固定 per-expert-copy 语义：同一 token 选择的专家不能重复，但落在同一目的 rank 的不同专家仍分别计一次贡献；可聚合成消息，不跨专家去重。初版不用 CANN 动态量化、UB 状态消息或 DeepEP rank 去重行为冒充通用 RDMA。

| 对象 | 定义 |
|---|---|
| C[i,j] | 源 rank i 的 token 中，目标专家位于 rank j 的选择次数 |
| Dispatch[i,j] | i≠j 时，C[i,j] × H × 2 B；i=j 走本地路径 |
| Combine[j,i] | 对应专家结果返回源 rank，初版每贡献也按 H × 2 B |
| 网络总量 | 分别统计远程 payload、跨服务器/Pod payload、包头、ACK 与重传 |

B=4 时全部专家贡献的 Dispatch 逻辑量为 8×4×2×1024×2=131072 B；其中含本地项，实际网络 payload 必须减去本地项，不能直接当作注入量。Combine 的逻辑贡献量同口径。

## 3. 路由来源与 EP 分组

均衡病例用可复现的专家选择多重集；热点病例规定 50% token 包含专家 0，并保证 Top-K 不重复。它们均标记 synthetic，不能作为真实训练热点结论。用户所给 HF 原始数据待可用后再做独立扩展；所选子集须区分训练与推理来源。

EP=4 为两个独立推理副本，主对照分组 [0,1,2,3] 与 [4,5,6,7]，各在一个 Pod。全局序列数与每副本 16 专家不变，但副本、放置和跨 Pod 流量共同改变，不能归因纯 EP 效果。本轮没有训练 DP 梯度 AllReduce。

# 小规模拓扑与带宽配置

## 1. 用同样的 8 端点覆盖结构

全部采用 2 Pod × 每 Pod 1 Segment × 2 服务器 × 每服务器 2 GPU。T0/T1 的每 Segment/rail 有 2 ToR；T2/T3/T4 则每 GPU 槽对应 1 rail、每 Segment/rail 有 1 ToR。Core 全为普通电交换机。

| 编号 | 结构 | ToR/Agg/Core | rail/plane | 连接规则 |
|---|---|---|---|---|
| T0 | 两层 leaf-spine | 4 / 0 / 2 | 1 / 1 | 每 ToR 连全部 2 Core |
| T1 | 三层 Clos | 4 / 4 / 2 | 1 / 1 | 每 ToR 连 2 Agg；每 Agg 连分组的 1 Core |
| T2 | HPN参考单平面 | 4 / 2 / 1 | 2 / 1 | Pod 内共享 Agg，跨 Pod 共享 Core |
| T3 | HPN参考双平面 | 8 / 4 / 2 | 2 / 2 | 复制 T2 交换网络，每 NIC 同时接两 plane |
| T4 | 独立 multi-rail | 4 / 4 / 2 | 2 / 1 | Agg/Core 按 rail 隔离；禁止跨 rail 中继 |

数量由参数化生成器推导，并在装载时核对真实节点、端口与链路。T4 的 EP8 跨 rail 不可达，注入前拒绝；合法 EP4 组为 [0,2,4,6] 与 [1,3,5,7]，它与主 EP4 对照的部署不同。

## 2. 主线与公平对照

T0/T1/T2 的接入与上层链路均先设 100 Gb/s、每跳传播延迟 1000 ns；NIC 总预算 100 Gb/s。T1 带宽敏感性只改变 Agg→Core 为 100 / 50 / 25 Gb/s，其他字段固定。

T2 对 T3 时，单 plane 各层 100G；双 plane 各层每份 50G，单 NIC 合计仍为 100G，同时核对每层对应逻辑连接的合计容量。双 plane 的设备与队列数量不同，不视为严格等成本部署。按消息身份确定性选 plane，并记录策略；禁止依赖默认“第一张 NIC”来声称双平面生效。

若启用双平面流量分配，两平面都必须出现实际业务字节，消息不重复、不遗漏、不跨 plane 桥接。首版使用 flow-level 固定哈希，不增加 packet spray 或故障切换作为隐含变量。

## 3. 灵活配置与结构比较边界

数量可配置：Pod、Segment、服务器/GPU、每 rail 的 ToR、每组 Agg/Core，以及上联数、分组和 NIC 映射。T0 不设 Agg，T1 显式设 Agg；T2/T3 仅参考 HPN 结构，Core 采用普通电交换机。结构比较须报告端口与容量，不能据耗时直接排名。

服务器内 NVLink/PCIe 不在首轮物理网络中：同 GPU 的专家贡献走本地计算路径，不同 GPU 的通信按当前分组网络接线执行。结果只适用于这一部署假设，不当作真实八卡机器内通信性能。

# 对照矩阵与可证伪假设

## 1. 主矩阵：10 个有效配置 × 3 个路由 seed

默认 B=4、EP=8、均衡合成路由、同一参考计算表。各条件使用配对的 routing seeds 11 / 23 / 37，并固定记录网络 seed/run；复用相同基线，不重复计数。本页定义对照方法，性能数据另行报告。

| 实验 | 改变因素 | 主要观测与判断 | 新增配置 |
|---|---|---|---|
| E1 结构 | T0 / T1 / T2 | 路径、实际瓶颈与阶段完成；不宣称等成本胜负 | 3 |
| E2 batch | T1：B=1/4/16 | payload、消息并发、队列与计算成本分别如何增长 | 2 |
| E3 上联 | T1：Core 上联100/50/25G | 确认参数生效；区分出口服务不足与前端释放不足 | 2 |
| E4 平面 | T2单100G / T3双50G | 固定总容量；验证双平面分流与哈希碰撞 | 1 |
| E5 热点 | T1：均衡 / 50% token选专家0 | 专家热度是否映射到 rank、链路及时间窗口热点 | 1 |
| E6 EP分组 | T1：EP8 / 两组EP4 | 保持总序列数；分开解释副本、远程比例与共享竞争 | 1 |

T4 的 EP8 拒绝和同 rail EP4 可达性作为功能验收，另列，不并入这 10 个性能条件。底层微实验也单独计数。先单条件通过再展开其余 seed；若预算耗尽保留已跑条件与失败原因，不把缺项写成通过。

## 2. 需要检验的解释

H1：上联受限会延后跨 Pod 消息及依赖它的 expert/merge。支持证据需同时出现该出口实际服务/排队、消费者后移；若流量不足或发送端额度先受限，单纯降低带宽可能没有明显影响，应据此修正解释。

H2：固定总带宽的双 plane 可能因路径与队列分散改变长尾，也可能因 flow 哈希不均或负载太小而无收益。先排除总带宽翻倍和只使用一 plane，才解释改善或退化。

H3：热点专家不必然导致最热网络链路。专家放置、源分布、跨 Pod 比例和时间聚集共同决定瓶颈。E5 的远程字节可能变化，必须分开报告；不能把其全部耗时差异归给排队。

H4：batch 增大时逻辑贡献量可按定义线性增加，但 payload 的本地比例、分块、计算和并发也会变；既不预设延迟同比增长，也不把定义推出的字节倍数当作创新发现。

> 阴性结果也是结果：没有排队、双 plane 无收益或热点未映射到 Core，都应说明限定条件，而不是继续调参保证预期现象出现。

# 观测指标与可视化交付

## 1. 业务、消息、端口三个层次

| 层次 | 必报指标 | 使用边界 |
|---|---|---|
| 服务/阶段 | Dispatch、expert、Combine与波次完成；具备条件后报告逐token间隔 | 单层时间不冒充完整模型 TPOT；无 Prefill 不报告 TTFT |
| 逻辑消息 | payload、ready/start/receive/ACK时刻、FCT、完成次数 | FCT 明确起止；排队等待与发送服务、传播、ACK分开 |
| 端口/队列 | 每方向数据与控制字节、利用率、队列曲线、最大值、ECN/PFC与重传 | 没有原生钩子的指标记“未采集”，不补造0 |
| 放置/热点 | 专家计数、rank入流、GPU/NIC及跨Pod矩阵、窗口峰均比 | 专家不均衡与链路不均衡是两类指标 |

# 实施顺序、门槛与通过标准

## G0：协议与物理输入先可信

先装载不超过 16 交换机的小图，核对节点、真实设备端口、rate/delay 与跨 Pod 路径。单消息覆盖 payload 1000 B 下的 999/1000/1001/3000 B，payload 9000 B 下的 8999/9000/9001/27000 B；另验双消息并发和可控重传。每逻辑消息恰好完成一次，无重传时 payload 守恒，有重传时逻辑与线上字节分开。

拥塞控制先选源码有实现的 DCQCN 模式 1，不继承未核实的 CC_MODE=12。PFC、ECN阈值、缓冲、headroom、MTU、ACK与窗口全部进入有效配置；50/100G均需有合法阈值映射。单流跑通后，再用汇聚微实验确认 ECN、速率变化或PFC实际生效，不能仅以配置名称作证。

## G1：从 LLMServingSim 产生的图进入真实网络

保留请求身份、token与专家选择，生成中立的 Dispatch/Combine 消息与依赖，不把UB特有状态复制进RDMA。比较手算矩阵、图内贡献量、实际网络注入量及接收完成数，逐项核对本地与远程分量。

先完成固定图的小型真实执行，再引入在线控制。此门槛只证明业务图可执行，不单独宣布全流程完成。

## G2：两层、四波次的在线闭环

使用 2 个连续 MoE 层、4 次 Decode 波次，网络完成推进层内后继，并返回 LLMServingSim 更新请求状态/下一轮组批。两组EP并发时共用同一网络状态；结束时逻辑消息和业务波次全部完成；接收 QP 状态可保留至网络实例销毁，不冒充待完成消息。

做同一业务输入的上联降速对照：固定计算节点耗时不变，发生变化的网络事件与消费者启动必须可追踪；不得预写下一波固定发送时刻。分别核对完整接收与 ACK 回调，禁止只以程序退出作为因果正确的证据。

## G3：开展 E1—E6，并解释机制

通过前述门槛后才展开矩阵。每个结论同时提供有效配置、通信矩阵、实际路径/端口负载、队列与阶段依赖证据。无法观测的等待保持未解释，不用结构超售比代替实际拥塞。

| 层次 | 本轮验收产物 |
|---|---|
| 平台 | 独立非UB构建目标、完成事件适配、公开运行/导出接口及小例 |
| 实验 | 有版本的条件配置、结果表、失败记录、因果分析与可复现图表 |
| 全流程证明 | 前端请求 → 图 → 单一ns-3 → 回调 → 下一轮服务的实际记录 |

> 任一门槛失败，停在该门槛修复平台并重跑受影响检查；不切换成理想网络、随机流量或多次独立仿真来满足“正常结束”。

# 复现、扩展边界与审阅事项

## 1. 修改配置后如何复现

模型与 batch 在 examples/scaleout_rdma/service.json；拓扑在 small-clos-100g.json；协议在 rdma.json。分别保存修改后的副本，拓扑修改后先运行 scaleout topology，再用 rdma-run 执行、rdma-check 复核。每次使用新输出目录，不覆盖旧结果。

主矩阵入口为 experiments/scaleout_e2e/run_matrix.py，传入 --backend-json、--protoc、--output。脚本只调用公共 CLI，按组保存输入、命令、stdout/stderr、退出状态与结果；分析独立进行，不能改写执行记录。

当前模型 H、FFN、专家数、Top-K、层数可变；batch 每 rank 1—16，Decode 2—4 轮。GPU 标签不提供性能表，通信为直接成对 All-to-All-v，不提供 NCCL/DeepEP 算法一键切换。切换真实 GPU 或通信库需新增校准或实现，不能只换名称。

## 2. 千卡扩展与当前资源上限

1024 GPU 先做拓扑/端口/可达性及工作量估算；逐包执行必须另过资源门槛。按实际交换机固定数组、QP数、消息数和包数估算，再按 16→64→256→1024 分级验证；当前小图入口不能直接解除限制当作千卡能力。

本轮网络单例限 5 ms 模拟时间、宿主60秒、RSS1 GiB/地址空间2 GiB。构建限300秒、并发2、RSS2 GiB/地址空间4 GiB。专用工作卷累计产物512 MiB并保留8 GiB空闲；失败保留日志，不自动扩限。临时内存盘的结果需要持久备份。

## 3. 必须随结果公开的限制

主实验是无故障网络：中间包丢失可由 NACK 恢复，但尾包丢失无后续包触发 NACK，已有失败病例；不能声称通用可靠恢复。ACK interval=1；ECN阈值须核对实际生效字节，不能仅验证输入字段。

训练需要额外引入前向/反向 Dispatch、Combine、专家负载均衡与梯度 DP 通信；推理热点 trace 不能代替训练热点。真实 HF 路由和实机 GPU 校准尚需独立完成，合成路由与声明成本均不能提升为生产结论。

## 4. 建议优先审阅

1. 是否以网络路径、队列、反馈和业务因果为近期重点，以有限 Decode 片段为首轮范围？

2. 是否采用电交换 Core 的 Clos/Agg 与 HPN 参考结构，并固定双平面合计带宽作对照？

3. 是否接受上述10条件矩阵，同时明确 EP4 本地化、热点计算成本和结构资源差异的混杂？

4. 后续优先真实路由/硬件校准，还是千卡资源优化？二者作为独立阶段制定验收，避免同时扩展。
