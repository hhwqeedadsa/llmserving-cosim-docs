# 数据丢失、确认丢失与MoE组推进

研究问题：一次包丢失影响的是接收数据、发送事务，还是整个推理组？另一独立EP组是否也无法继续？这不是故障恢复新算法或准入方法的收益实验。

固定8个逻辑GPU、三层Clos、100G链路、32个起点就绪请求、两组交错EP4、1层2步Decode、batch/rank=4、路由seed=11。模型H1024/F4096/E16/K2，成本是声明值。两组独立推理，共享同一Fabric/Simulator，不涉及训练DP同步。

竞争解释与判别：

| 解释 | 预期证据 | 对照 |
|---|---|---|
| 缺失数据拖住专家计算 | 连续接收停在缺口，RECV未回调 | 中间数据包丢失，记录NACK、重传与真实RECV回调 |
| 数据完整，发送确认拖住组退出 | RECV已回调，SEND没有；其他节点可完成 | 只丢最终ACK，核对全部节点与前端组进度 |
| 前端/网络全局停住 | 两组都不能继续 | 检查同一运行中的另一EP组是否完成两轮 |
| 观测改变了执行 | 开关或截断记录改变回调、端口或队列 | 平台功能门分别检查；不以研究结果替代被动性验收 |

先做基线，从实际第一轮计划选择GPU 0→4的Dispatch消息，之后固定同一消息，分别丢中间数据包、最终ACK或入口交换机处的首个数据包。每条规则必须命中一次；所有共同提交的任务图逐字节相同。故障组无法提交的未来图不会被补造，因此完整执行的流量不保证相同；共同输入与已提交图分别说明。

```bash
python experiments/scaleout_faults/run.py \
  --backend-json <原生构建目录>/backend.json --protoc <既有protoc> \
  --output /dev/shm/moe-fault-study-new
python experiments/scaleout_faults/render.py \
  --run /dev/shm/moe-fault-study-new --output <新的报告目录>
```

运行脚本只调用公共CLI和读取保存产物，不导入测试或平台私有执行器。每个运行使用协议默认的60秒宿主、RSS1GiB/地址2GiB、5ms仿真限额；研究目录累计结果上限128MiB，卷预留8GiB。四次服务运行建议外层再用`python -m moe_ub_cosim.host_probe`限定300秒、RSS1GiB/地址2GiB、256MiB累计产物，并登记研究目录。失败后不扩容或覆盖重跑；最终ACK丢失是预先定义的非零退出负例，保留其失败与frontend/result。

报告只陈述有限仿真窗口内的行为。真实系统的重传定时器、应用超时与容错库尚未校准；不将后端停滞说成生产RDMA缺陷，也不据此直接提前WAVE_DONE。恢复后的延迟可讨论，未完成运行不计算“完成时延”。结果与局限见[本轮结果](results.md)。
