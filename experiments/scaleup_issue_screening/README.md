# Scale-Up 正常业务问题筛选

本实验从正常 MoE 执行中观察参与端拖后、通信持续偏慢与网络竞争，核验具体原因，再判断已有端网观测是否足够。长尾与拥塞只是候选入口，不要求它们同时出现，也不预设需要新增测量机制。

整体问题与原始安排见[实验方案 v0.1](plan_v0.1.md)，原平台要求保留在[平台 v0.5 规范](../../docs/archive/moe_ub_cosim_dev_v0.5.md)。当前状态、实际基线和执行顺序只维护在[当前任务](../../docs/tasks/current.md)；本轮完整执行要求见[候选筛选与核验](candidates.md)，不将原方案中的历史清单重新执行。

查看已有发现先读[研究结论](conclusions.md)，核对具体过程再看 [E1 正常业务](results/e1/README.md)和 [E2 成因对照](results/e2/README.md)。[资源汇总](results/resources.md)说明实际耗时、内存、保存空间及计量边界；复现或恢复结果见[操作说明](usage.md)。

## 本轮工作

2026-10-13 用户确认冻结 C1 发送队列分支，回到已有正常运行中的网络竞争筛选。先重分析交换机记录，核对具体通信是否真的等待，再检查是否推迟必要交付、归约或后继计算。有合格候选时，继续完成有限服务对照和初步信息缺口判断；没有候选、没有业务作用或已有信息足够，都允许形成完整结论。

这是一轮连续交付，不在每项内部检查完成后重复等待确认。最多深入两个候选，新增目标后端运行共享候选文档规定的次数和资源上限；不要求用满，不靠故障注入或参数扫描保留现象。路由、拓扑、计算成本、端侧资源及核内同步保持既定范围，正式 E3/E4、测量算法和硬件实现不自动启动。

C1 已完成请求阻塞核验、32→64 额度对照、完整消费者依赖检查及固定额度的 FIFO/轮转对照。其结果、工具和约束继续保留，完整方案见[收尾版本](https://github.com/baoy21/moe-ub-cosim/blob/f60de083d014423a6d05b086502d877636bbb662/experiments/scaleup_issue_screening/candidates.md)。不因已有这些工具就继续深挖 worker、状态优先级或未知硬件同步。

## 实现与资料职责

`configs/` 保存独立输入和控制条件，`workflow.py` 组织公共平台命令，`analyze.py` 等程序做研究者分析，`archive.py` 保存与恢复结果。已有 `consumer_review.py` 和 `organization_review.py` 可复用完整依赖核验，但新对象来自本轮实际记录，不固定为 C1 的层、端点或传输。新增程序与紧凑结果按实际需要进入本目录，不预建脚本、配置或结果占位。

平台通用代码不导入实验。必要的被动记录、读取或公共接口修复先以小型输入验收，再由正式实验调用；不使用测试 helper 驱动研究，也不靠某台机器上的默认运行路径复现。显式读取历史归档时核对其来源和摘要。

研究者核验可以读取内部任务、资源与实际交付记录；初步观测判断只读取明确开放的资料。完整依赖、逐包来源、干预声明与真值不自动开放。负面结果、未确定和没有信息增量均应正常记录。

要求、方法、结果、进度和用户操作分别维护。研究结果不写回方案，过程日志不堆入技术正文；下一次汇总应提供候选去留及理由，不只给出下一步清单。产物仍使用 `runs/scaleup_issue_screening/` 下的独立路径并遵循预算，大图、真实数据和日志不提交 Git。每批检查、本地提交及发布权限沿用仓库约定。
