# 候选 C1 与成因核验

C1 继续研究 Combine 等待及其对后层执行的影响。2026-10-12 按用户确认增量修订本页，重点转到专家计算结束后的发送推进，不新建候选或实验任务。整体目标仍按[实验方案](plan_v0.1.md)，进度只维护在[当前任务](../../docs/tasks/current.md)。原候选选择及三项对照的运行前安排保留在[固定历史版本](https://github.com/baoy21/moe-ub-cosim/blob/6ebe4984280465316f90886ccdbf4f66f4fe9d49/experiments/scaleup_issue_screening/candidates.md)。

## 1. 保留什么，继续查什么

[E1](results/e1/README.md)保留三档正常输入和较长前序检查；[E2](results/e2/README.md)已经完成专家参考成本 100→50、100→200 ns/输入，以及复制栅栏 `data_ready`→`local_read_complete` 三项对照，并补采候选路径。它们说明当前模型内准备节奏有作用，不证明发送资源已对应真实硬件，也不自动构成新增测量的动机。

本次固定原始真实专家路由、物理网络、请求和专家放置，以及线性计算成本。已有负载和计算趋势可作为基线，不重复开展代表性调查、成本函数替换、硬件算子校准或专家复制研究。输入复用时检查身份和摘要即可；只有发现直接影响当前判断的新错误才重开相关项。

当前只回答三件事：约 12 μs 内实际执行或等待了什么；决定等待的请求组织与软件同步是否有依据；在必要修正或有判别力的对照后，该现象是否仍值得作为测量问题继续。状态消息和 LD/ST worker 是核验对象，不预定为优化课题。

## 2. 现有证据起点

### 两条时间链

使用已有 `g0-b2-short`，保持 128 rank、256 请求、原始第 6～8 层及完整部署容量。第 7 层消费者 rank 27 的关键供数端是 rank 70；第 8 层消费者 rank 58 的关键供数端是 rank 65。专家计算结束至关键数据提交分别为 12,020 ns 和 12,583 ns。

按[基线前驱记录](results/e2/baseline-witnesses.json)，第 7 层 rank 70 的 `aiv:8` 从 54,198 ns 到 66,218 ns 可分为以下相接区间。本表是交接时对已有记录的重算，不是新增运行，也不是可节省时间或完整根因比例。

| 链上的动作或等待 | 时长 |
|---|---:|
| 五次结果打包，每次 20 ns | 100 ns |
| 四次前序数据提交后至数据栅栏满足 | 5,732 ns |
| 四次前序状态提交后至原生请求形成 | 6,188 ns |
| 合计 | 12,020 ns |

四条状态传输 ID 为 `4295045018`、`4295045021`、`4295045024`、`4295045027`，提交至请求形成分别等待 1,902、1,776、1,421、1,089 ns；形成后各经 88 ns 到达。它们之后的结果准备依赖该请求形成事件。`4295045029` 是 66,218 ns 提交的关键数据分块；不要把一个分块误当作整份专家结果。

执行者先根据原始记录复核上述数值、区间边界及字节身份，再独立分解第 8 层；不得假定其组成相同。已有前驱程序保留的并列依赖也要核对，不能将任意选中的一个前驱当作唯一原因。数据栅栏时长已包含可能重叠的请求形成与传输过程，后续细分不得重复累加。

### 配置来源与调用含义

以下均对应交接前主仓 `6ebe498`、锁定 ns-3-UB `c0f1fe5`。需要用实际生效对象和保存配置核对，不能只读示例或默认值。

| 对象 | 已查到的事实 | 要继续核验的内容 |
|---|---|---|
| `UbLdstInstance::ThreadNum` | 锁定后端与原上游基线的默认值均为 48 | 默认值的模型含义不能直接解释为硬件规格 |
| M21 与 E 实验配置 | M21 `input-basis.json` 显式取 1，规模验收程序应用该值，实验 `workflow.py` 再次明确取 1 | 查提交和本地记录能否说明选择理由；没有依据就如实记录，不补写动机 |
| 原生请求资源 | 每 worker 的 `StoreOutstanding=32`，端点共享 `RequestIdCount=256`，STORE 请求粒度 4096 B | 等待发生时究竟哪个限制生效、由哪些请求占用 |
| worker 使用方式 | `UbApp` 将每份任务交给全部 worker，`HandleLdstTask` 按字节均分 | 这与把不同核的完整任务分配给不同队列不是同一行为 |
| A3 通信核 | 前端保留核身份、局部处理及同步 | 核内搬运流水与后端请求队列怎样对应，状态发布后需要等待什么 |

源文件入口为 [M21 输入](../../fixtures/m21_platform/input-basis.json)、[规模验收调用](../../tests/integration/check_a3_scale.py)、[实验准备](workflow.py)，以及固定后端的 [LD/ST instance](https://github.com/baoy21/ns-3-ub/blob/c0f1fe54245203a3b14468e44e893a38792cfcc8/src/unified-bus/model/ub-ldst-instance.cc)、[应用提交](https://github.com/baoy21/ns-3-ub/blob/c0f1fe54245203a3b14468e44e893a38792cfcc8/src/unified-bus/model/ub-app.cc)、[worker 推进](https://github.com/baoy21/ns-3-ub/blob/c0f1fe54245203a3b14468e44e893a38792cfcc8/src/unified-bus/model/ub-ldst-thread.cc)和[请求形成与回收](https://github.com/baoy21/ns-3-ub/blob/c0f1fe54245203a3b14468e44e893a38792cfcc8/src/unified-bus/model/protocol/ub-ldst-api.cc)。

在当前调用方式下，直接从 1 改为 48 会同时改变分段、请求数量、包长分布、在途总额度和提交顺序。按代码推算，8192 B 任务可由两个请求变为 48 个请求，32 B 状态可拆成 32 个 1 B 子任务。先用最小输入检查实际输出，不能据此报告单纯增加并发的收益。worker 是仿真中的请求推进对象，不是宿主线程，也不自动等同于 AIV 或 MTE。

## 3. 核查顺序

### 先核对软件依赖和现实对应

在现有固定 CANN 源码及公开架构资料中，集中检查 Combine 数据复制、状态发布、局部缓冲复用和下一份结果准备的顺序。沿[来源清单](../../fixtures/m10_cann/source-evidence.json)核对文件摘要与选定分支，追查前端 `a3.py` 的对应依赖及后端实际事件。不要换用 A5 的标志布局解释 A3。

重点判断两处关系：多个通信核的搬运是否应按当前统一队列方式推进；状态请求全部形成后才能开始下一份准备，究竟来自源码的真实缓冲/流水依赖，还是平台额外施加的完成映射。区分源码可以确认的局部关系、协议共享资源假设和仍缺少的硬件信息，不要求逐指令复现。

应主动检查固定缓存、可获得的官方文档和提交历史。每条结论留下版本与对应片段，不能以参考配置已声明代替机制核验。公开资料无法确认精确共享容量时，继续完成模型内的阻塞事实和限定对照，不无限等待校准；说明尚缺的是容量数值还是作用关系。不得把默认 48、通信核数或条目合法范围当作目标设备规格。

### 再补齐实际阻塞过程

先复用归档、`facts` 和已保存传输记录；不足处只为上述两个供数端及必要时间范围补有界内部事件。需要能够核验任务进入哪个队列、队首是谁、请求何时形成、worker 在途占用与端点请求池占用、具体阻塞原因，以及哪个响应或前序事件使它继续。

请求占用者保留任务、字节范围及可取得的通信核身份；身份通过实际执行对象传递，不从接收端或时间邻近猜测。记录等待开始时已存在的队列与在途状态，必要时覆盖更早任务及其他操作。只记录当前四条状态而遗漏其阻塞者，不能算完整核验。

在途额度不足、共享标识池耗尽、队首前序字节未发完和核内同步分别判断。应从实际分支与状态给出原因，不能仅凭长时间没有 RequestCreated 就标记某类阻塞。继续追踪释放资源的响应；当前包到首次交换机前的等待可能包含此前传输和流控反馈，不能直接归为与网络无关。

新增记录只监听，不改变事件调度、队列顺序或随机数。先做小型启停等价检查，再在基线上检查任务、传输、数据与状态字节及完成结果一致。初态、覆盖上限、溢出和缺失显式保存；不为这项核验默认开启全网逐包采集。详细记录只供研究者解释，不作为硬件已有测量接口或 E3 输入。

## 4. 按解释选择对照

执行方式遵循[性能现象核查要求](../../docs/development.md#性能现象核查)。每个对照运行前写明候选原因、支持和削弱该解释的预期、实际改动及不变量。先完成最小机制测试，再对已有 256 请求三层场景进行必要验证；不预先扫描所有 worker、请求大小与容量的组合。

| 待区分解释 | 应出现的直接证据 | 条件成立后采用的对照及限制 |
|---|---|---|
| worker 请求额度限制 | 目标任务等待期间额度满，响应释放后继续；标识池是否同时满单独记录 | 保持 1 worker 和拆分不变，只改请求额度；例如 32→64，且共享池保持 256。档位属于诊断条件，不宣称硬件优化 |
| 统一队列产生跨核排队 | 找到挡住目标任务的其他核任务及其剩余字节；等待无法仅由总在途容量解释 | 需要独立控制任务分配和字节拆分时才补最小公共能力；比较须保持每份任务的请求范围和总资源预算，不用 ThreadNum 直接代替 |
| 状态发布或缓冲同步放大等待 | 下一份准备确实被某个状态或缓冲事件阻塞，并能核对源码条件 | 仅修正缺乏依据的依赖或采用有依据的替代映射；保留数据/状态顺序、缓冲生命周期和消费者到齐条件，不删除所有同步 |
| 较早传输、出口服务或流控使请求迟迟不释放 | 占用者及其响应路径、服务或等待能够与资源释放对应 | 有证据后才做相关网络服务的定向比较，区分串行化与排队效应；不以最后几个包没有排队排除网络反馈 |

这些解释可以同时成立。容量未满时不继续靠加大容量寻找收益；改变组织方式必须先检查请求与总额度是否一起改变。若现有配置不能独立改变待研究因素，先指出混杂并以小型测试校正接口，不能以单个参数名认定单因素。

任务分配和分段控制的实现只限本次机制验证需要，不建设完整调度系统，不自动加入状态优先级、专用 VC 或新通信协议。已确认的实现错误可以在当前授权范围内修复并补测试，无法核实的硬件策略只作为独立参考对照，不直接替换主基线。

每项对照同时比较同一贡献的等待、原消费者的完成和本次实际最晚消费者、后续计算与所选层段结束。关键任务改变时按业务身份重新匹配，不只沿用旧 transfer ID。保持请求与业务输入，保存实际包数、字节及路径变化，单独解释不可保持的因素。局部区间缩短不自动等于业务收益，也不能把重叠等待相加。

## 5. 平台改动、复用和资源

平台通用变更进入现有公共模块；输入校验、实际对象、有效配置、事实导出、保存和重放一起核对。只增诊断记录时先检验执行等价；行为或依赖修正后重新构图并固定新的源码、依赖、二进制及有效输入。不能静默删除 `workflow.py` 的原平台校验，或将新代码结果标成旧基线。旧归档按原版本解释，历史测试与性能结果不改写。

先小型回归，再使用上述 256 请求、128 rank 三层输入。仅在解释已明确且确需复核时，选择一个已有的其他负载条件确认；不默认重跑 E1 全批或完整 61 块。保留原计算成本、网络服务和业务输入，除已声明的定向因素外不变。

预算沿用原[方法](method.md)与当前任务：后端 RSS 48 GiB、地址空间 56 GiB、7200 秒；其他阶段 RSS 8 GiB、地址空间 12 GiB、1800 秒；累计产物 48 GiB，最低空闲磁盘 20 GiB。原归档已接近累计上限，先核对实际空间并流式读取。原两层事实导出的节点 500000、传输 100000、计划 2 GiB 和压缩明细 128 MiB 上限不自动提高；新记录须有更小或明确受原总预算约束的局部范围。

只恢复必要资料，使用本实验新的运行路径，保留原始输入、失败与旧归档。空间不足时停止受影响运行，不自行清理历史产物或扩大预算。复用步骤见[操作说明](usage.md)，不得把本机临时脚本作为必要入口。平台与实验分别建立本地提交，远端发布仍须明确授权。

## 6. 自主推进与结束条件

已允许的源码溯源、局部重分析、小型测试、必要补采和定向验证由 Codex 连续完成，不把每个未知都交回讨论，也不将文档写完或校验通过当作根因已经成立。前一步否定原解释时，依据竞争解释调整下一项小检查；不能无证据地扩展为新的业务或硬件研究。

本次结束时，应给出两条时间链的可复核分解、决定主要等待的资源/依赖及现实依据、具有判别力的对照结果，以及候选去留判断。结论可以是模型设定造成主要等待、真实机制有意义、影响有限，或经已有手段核查后仍有明确缺项。最后一种情况须说明已排除什么、缺少的最小资料或能力及其影响，不能只写原因未知。

若主要来自未经证实的模型设定，先修正或限制结论，不据此设计测量；若等待有依据且影响业务，再指出已有工作量、操作时序和网络统计具体分不清什么；若简单基线足够或影响很小，可以关闭 C1。现象消失也是有效结果，不为保留候选继续调参数。

机制核验结果写回既有 E2 结果及结论，必要的新证据文件在取得结果后加入原目录。可提出后续信息比较建议，但本次不实施 E3/E4，不将供数端定位、32 B 状态或 worker 数预定为研究主线。
