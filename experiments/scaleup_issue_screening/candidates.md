# 正常业务网络竞争筛选与核验

本页按 2026-10-13 用户确认的方向，承接同一项 Scale-Up 正常业务问题筛选实验。C1 发送队列分支收尾，改从已有正常运行中的交换网络竞争出发，连续完成候选筛选、实际等待核验、业务影响检验和初步信息缺口判断。不开新任务、平台版本或实验目录。整体问题仍见[实验方案 v0.1](plan_v0.1.md)，本轮范围、进入与停止条件以本页和[当前任务](../../docs/tasks/current.md)为准；原方案中的首批运行、成本敏感性和完整场景安排不自动重跑。

本次交付单位是一轮有结论的问题筛选，不是一个采集脚本或一次仿真。Codex 应在已确认范围内主动选择对象、检验竞争解释、处理小型缺陷并按证据继续，直至完成本页规定的收尾。中间阶段不重复请求确认，也不以必须找到拥塞、长尾或映射收益为目标。

## 1. C1 收尾与本轮固定条件

C1 的请求额度核验与固定总额度组织对照已经完成。[组织效应](results/e2/c1-organization-effect.json)显示，前序状态等待明显减少，数据等待增加，三层最后计算仅提前 945 ns；[进一步分解](results/e2/c1-organization-waits.json)确认数据等待的增加主要位于请求形成之前。局部等待不能直接换算成可消除的业务损失。

保留 C1 作为模型内解释案例及回归资料，冻结其 worker、额度、状态优先级和核内同步研究。完整要求、来源核查与去留依据见[收尾时的 C1 文档](https://github.com/baoy21/moe-ub-cosim/blob/f60de083d014423a6d05b086502d877636bbb662/experiments/scaleup_issue_screening/candidates.md)和[E2 结果](results/e2/README.md)。本轮不再追索缺少的 A3 硬件容量或编译同步资料，不以这些缺项阻止其他网络侧事实分析，也不因换了观察入口就宣称原假设已被验证。

固定现有真实专家路由、物理拓扑、请求与专家放置、A3 STORE/STORE、线性计算成本、请求拆分、全部核内同步和协议资源配置。输入复用核对身份及摘要，不重新开展负载代表性、计算成本拟合、专家复制、A5 移植或完整芯片模拟。发现直接影响正确性的新错误时，只处理有证据的具体问题，并限定受影响结论。

研究对象是正常执行中实际发生的网络等待及其业务作用。数据、状态及协议反馈都可以进入证据，但不重新把小状态消息优化当作默认主题。网络等待不只接受最终层段耗时作为影响指标，也可体现为有意义的通信操作或后继计算推迟；必须明确完成对象，不能以包很慢代替业务影响。

## 2. 自主执行顺序与结果分支

| 环节 | 要完成的判断 | 满足条件后继续什么 |
|---|---|---|
| 资料与网络侧筛选 | 已有正常执行在哪里出现积压，记录覆盖到什么程度 | 无需等待确认，选择最多两个有依据的候选深入 |
| 实际等待核验 | 哪些具体通信已进入交换资源并等待，等的是服务、仲裁还是下游反馈 | 排除时间巧合、正常固定处理和端侧未注入等解释 |
| 业务影响核验 | 这些等待是否推迟必要数据、状态、归约或后继计算 | 有影响线索才执行对应的网络服务对照 |
| 定向对照与反证 | 改变所怀疑的资源后，局部等待及业务完成是否按预期变化 | 解释成立后自主检查已有观测的判断能力 |
| 初步信息缺口判断 | 既有信息能判断什么，哪一种额外信息能消除具体歧义 | 输出候选去留及可继续研究的问题，不直接开发完整测量方法 |

没有可信积压、没有足够业务作用、已有信息足够、现象依赖未核实模型，或记录不足以判断，均可形成有效结论。一个候选被否定后继续完成其他已选候选，不为保留它反复改参数。最多深入两个不同机制的候选；筛选表可保留其他线索，不轮番扩充深查对象。

不能把每个未确定项都留给用户。源码及字段核对、既有归档重分析、小型功能检查、限定补采、一次有判别力的对照及初步观测比较均属于已授权的连续工作。仅在权限、不可恢复的数据、预算或实质性范围扩张阻止必要工作时停止受影响部分，完成其余可执行项后汇总最小阻碍。新候选用同一文档内的记录标识管理，不复用 C1 的含义、不另开工程任务。

## 3. 复用输入与证据，不先重建场景

以[原方法](method.md)固定的四次正常运行作为主要发现来源。

| 已有执行 | 本轮用途 |
|---|---|
| 256、512、1024 请求，原始第 6～8 层 | 分别筛选网络事件，重点比较第 7、8 层；保留各档实际工作量 |
| 1024 请求，原始第 3～8 层 | 比较相同第 7、8 层，检查候选是否主要由短段入口造成 |
| 已有 FIFO/32、FIFO/64、轮转/32 的 256 请求记录 | 辅助判断网络现象是否仅依赖某种注入条件；不把参考条件混作独立正常样本 |

主发现不能靠选取最容易产生拥塞的参考档位。已有成本对照只在确有帮助时读取，不重跑成本实验。不同执行按层、操作、端点和业务身份比较，不用相同绝对时间窗口、包 UID 或请求编号强行匹配；三档嵌套请求、同层相关 rank 和重放不是独立重复。

先查看清单和小型摘要，再流式读取所需文件。每项分析绑定原平台、输入、清单及程序摘要；仓库更新不改变历史执行所属版本。旧输入和运行归档不改写。复用[无损压缩与重放能力](usage.md)，不为方便分析展开所有归档，也不要求全部旧运行先用新二进制重跑。

检查记录实际含义与覆盖，特别是队列等待量是否排除正在服务的包、是否包含 VOQ、FIFO 或信用等待，时间戳位于入队、获准发送还是链路开始。1000 ns 窗口面积和峰值只能支持相应界限，不能反推出精确连续积压；没有详细事件时，不能靠减小重采样周期补出事实。已观测零值、未捕获、区间首尾截断分别处理。

## 4. 从网络记录筛选候选

对全部已声明覆盖的交换机出口，分别整理短时峰值、连续或重复积压、等待面积与实际业务量。已有数据不能分辨连续与间歇时，保留不确定性，不给区间强贴标签。不只按总面积选最大端口，也不只查 C1 的 rank 70、65、Combine 或最后几份数据；Dispatch 和其他参与端同样纳入。

先用发送字节、服务速率、固定处理与传播时间作量级检查，区别正常串行化、单次固定仲裁和需要解释的额外等待。高利用率不自动等于异常，队列非空也不自动构成研究问题。必要时检查不同源是否在该资源重叠到达，但不能从专家输入不均直接宣布存在网络 incast。

查看业务影响前固定候选选择规则和范围。将同一资源的相邻窗口合并为有依据的事件组，避免把同一次积压或上下游传播重复计算成多个发现。保留筛选覆盖、选中和排除理由及完整排序的紧凑摘要，防止只留下最有利的两个样本。

最多深入两个候选，可以是一个有业务影响线索的事件与一个同类排队明显但影响较小的参照。参照优先来自已有正常执行，不制造慢卡、限速、额外背景流量或人为热点。若仅有一个候选就处理一个，不补齐数量；不同运行中的辅助出现不算新的研究方向。

## 5. 核验具体网络等待

对每个候选先复用已有实际路径、队列、消息归属及完成记录，确认目标数据确实进入了该交换资源。仅在同一窗口有流量或理论路径经过，不足以确认目标等待。逐包喷洒下按实际逐包路径检查，不能给整份通信指定一条推测路径。

具体区分以下情况，并保留无法区分的部分。

| 情况 | 需要的证据与边界 |
|---|---|
| 物理出口正在服务其他包 | 目标入队、前序占用、链路忙碌截止及实际发送事件；扣清固定服务口径，不把整包串行化称为额外排队 |
| VOQ 等待仲裁或下游信用 | 对应缓冲与调度或信用状态，说明哪个条件使其继续；只有非空字节曲线时不指定根因 |
| 目标尚未进入该交换资源 | 属于发送准备、请求准入或更早路径，不能归为该出口造成的等待 |
| 候选是上游受阻的表现 | 沿实际路径及反馈核对最小必要范围；不把首先被采到或队列最大的端口直接认定为起因 |

已有 `egress-queue-audit.jsonl` 主要覆盖物理出口 FIFO；`queue-state-events.jsonl` 可以保留 VOQ/FIFO 等待量，`truth/classified_packet_ranges.jsonl` 等资料可供内部关联。具体能力以[记录说明](../../docs/record_storage.md)及回调源码为准，不能把一个接口没有覆盖的过程写成已经测得。

资料不足时，只对选中的端口、相关路径及必要时间范围补采，包含区间初态和此前已在队列中的阻塞者。多项候选属于同一执行时合并补采，窗口不足先说明缺失，不无限向全网扩展。首先验证观测开关不改变调度、请求划分、随机数、路径及完成事件；目标补采与其来源运行核对执行和原观测等价，结果身份清楚后再分析。

允许为当前问题补最小被动记录、稳定读取或导出能力，并完成小型守恒、边界、缺失和不扰动检查。不新增端点内存服务、修改转发粒度、改变流控或核内同步来制造竞争。确有此类未建模过程阻碍结论时，限定候选并继续其他分析，不将其变成新的平台开发计划。

## 6. 把等待关联到业务完成

按操作、贡献、方向和字节范围将候选网络等待对应到数据、状态或协议反馈，再检查实际接收、数据栅栏、Token 归约、算子完成和后继计算。消息中多个分块及数据/状态条件分别核对；一个分块到齐不等于整份结果就绪。

复用 [consumer_review.py](consumer_review.py) 和 [organization_review.py](organization_review.py) 的完整依赖核验方法，需要泛化时移除硬编码层或 rank，不能从旧 C1 标签猜测对象。对受影响端的全部相关归约、本核发送条件、并列前驱及资源调度间隔给出足够覆盖；同时查本次实际最晚参与端，不仅追踪原来选中的消费者。

区分三层证据：包在交换资源中等待；该等待延迟某份必要交付；后继操作或层段结束因此受影响。静态依赖和时间顺序可以说明潜在作用，不能单独给出可消除损失。允许形成操作级影响明确、整段影响较小的结论，不能把任意局部等待都称为业务瓶颈。

请求反馈可能改变后续注入。若候选涉及响应或信用，核对它释放了什么资源及后继动作；但不重新深入 C1 的未知硬件队列。候选的现实解释若完全依赖已冻结的请求组织或同步假设，就记录这种依赖，不用网络侧入口替它消除疑点。

对没有进入必要完成条件的排队，保留低影响参照。等待总和、队列面积、最长消息和实际可节省业务时间分别报告，不相互替代。先完成本节，避免为没有业务作用线索的局部队列追加昂贵对照。

## 7. 有条件地完成网络服务对照

有正常等待和业务作用线索时，Codex 自主为每个合格候选选择一次定向对照。运行前记录少量竞争解释、支持与削弱它们的结果、作用出口、时间范围、有限服务档位、不变量和比较对象。主要使用已有 `port_service` 能力，提高已被证据指向的有向出口服务能力；不以降速制造正例，不扫描档位直到有收益。

改变一个局部出口为默认选择。只有证据明确指向同一必要出口集合时才采用小范围联合变化，并说明不能据此归到单个端口；不把整个网络变为无限带宽。档位是诊断假设，不宣称实际设备能够升级到该速率。若候选等的是下游信用而提高本地速率不能检验解释，先检查实际阻塞位置；无法在当前能力内干净对照就保留限制，不做一个预知无判别力的实验。

保持原业务图和依赖、路由轨迹、放置、计算、端侧资源与队列策略、请求拆分、物理拓扑、流控和随机配置。只改声明的服务项，通过有效对象回读核对。由本次网络完成事件继续推进业务，不固定历史发包时刻、不修改导出时间戳、不把独立运行流量拼接。实际选路和竞争会随执行变化，报告它们，不以相同种子要求逐包路径相等。

分别比较同一贡献的等待和到齐时刻、原受影响操作、本次全部并列最晚完成条件、后继计算及层段最后模型计算，网络排空另列。检查对照是否覆盖当次相关阶段；不能以时间窗错位的无效干预否定原解释，也不能事后反复扩大范围寻求收益。

提高速率同时减少串行化并改变排队。结合已记录服务过程或已有低竞争样本分清这两项；必要时在本轮总运行上限内增加一次预先说明用途的补充对照。不能分清时只报告局部服务变化的总效应。正向结果仍需说明网络反馈及注入假设，不把它当作硬件优化收益。

若局部等待下降但业务几乎不变，主动追踪新的必要完成条件，检查是否有其他数据、状态、计算或资源等待抵消。优先重分析同次记录，不因指标变化方向不符就追加仿真。分析 bug 的修正只重做分析；执行缺陷必须以最小用例确认并独立修复，受影响运行才重新执行。

## 8. 初步信息缺口判断

对机制解释可信且影响值得关注的候选，本轮允许继续完成小型离线信息比较，不必再次同步才开始。目标是给出下一步是否值得设计测量方法的依据，不是完成原 E3 的全面算法评估。候选不成立时跳过本节，不能为了比较算法而制造标签。

先选择一个具体判断，如找出受到某次排队影响的通信操作、识别值得优先排查的出口，或区分网络服务等待与数据尚未注入。给合理基线开放端侧本来可得的工作量和算子起止、端点位置、拓扑与操作次序，再比较加入端口统计和可用队列信息的能力。不将仿真内部阶段时间、实际路径、完整依赖和请求持有者默认称为真实 profiler 已有字段。

先运行并保存基线判断，再用内部事实评价。准备程序可以读取真值生成受限输入；判断程序不能读取真值目录、原运行位置、干预声明或带有答案的样本名称；评价程序独立使用真值。各条件使用相同对象范围、时间精度、静态信息和分析规则，允许输出未确定。

基线存在明确歧义时，最多增加一种与该歧义直接对应的信息，例如操作与端口窗口的真实对应关系，或一项额外时间事实。可以用理想正确的关系测试信息价值，但不能同时泄露完整依赖、精确故障位置或影响标签，也不能称为已经实现了映射恢复。缺的是时间粒度时，不改其他信息和覆盖来混淆收益。

在未参与规则选择的已有操作或同类区间中作有限复核，并说明这些样本仍可能相关。找不到可用复核样本时给出案例级结论，不报告泛化准确率。评价保留判断依据、误判、遗漏、候选范围和未确定项及分母；两个精选案例不足以支持普遍性能结论。新增信息没有帮助或现有信息足够，均正常结束。

输出明确到缺少什么信息、它消除哪项歧义、可能从哪里采集及大致记录规模。不要先设计采样压缩、协议标记、状态优先级、P4 或学习模型。本轮准确时间关系对各条件相同，不另做时钟误差矩阵。正式 E3、E4 和硬件实现仍需后续决定。

## 9. 工作量、实现与资源边界

先完成已有四次正常执行的资料覆盖与筛选，不以大规模重跑代替读取。本轮最多深入两个候选。目标规模新增后端运行总计至多六次，通常由最多两次合并补采或必要等价基线、每候选一次定向服务对照，以及至多两次有明确排除目的的补充执行构成。它们共享六次上限，不因更换程序名重计；不要求用满。预算预检或证据不允许时减少执行并按实际覆盖收尾。

失败执行也计入实际资源和运行清单。只在明确输入或代码错误、完成最小修复验证且原预算允许时重试一次受影响项；性能无收益和分析脚本失败不是重跑依据。新增前端输入、合成故障、层或规模扫描、完整 61 块和 64 步均不在本轮。

沿用后端 RSS 48 GiB、单进程地址空间 56 GiB、7200 秒；其他受监控阶段 RSS 8 GiB、地址空间 12 GiB、1800 秒；累计产物 48 GiB、最低空闲磁盘 20 GiB。上轮收尾取样约 47.253 GiB 仅供预警，启动前重新核对实际清单。先流式读取和无损压缩，按需恢复，串行执行并及时核验归档、释放本轮可再生副本；不得删除旧归档或以改根目录逃避累计计量。没有空间完成新运行时，先完成已有证据分析再说明最小缺口，不自动提高限额。

平台只增加当前确需的被动记录、受控导出或接口修复；先小型测试，再验证采集开关和旧行为等价，平台与实验分别提交。复用公开命令，不让平台导入实验代码或让正式实验调用测试 helper。新增程序在本实验目录按实际职责保存，不预建新目录体系、空结果页或版本规范。读取和回放接受显式来源路径并绑定清单，不能靠某台机器的默认绝对路径复现。

## 10. 完整收尾

下一次同步应能直接判断是否有值得继续的测量问题。交付至少包含一份覆盖与候选筛选摘要，以及每个已深查候选的过程、反证、业务作用和信息判断；已有 `conclusions.md` 用于综合判断，具体新结果按既有结果目录组织，原 E1/E2 证据不改写。没有候选时同样交付范围和否定依据，不以空白结果结束。

| 结果 | 应给出的决定 |
|---|---|
| 机制可信、影响有意义、已有信息不足且少量新增信息确有帮助 | 推荐一个具体测量问题，说明最小观测需求和剩余验证，不直接启动算法建设 |
| 网络等待成立，但不推迟所关心的完成对象 | 作为低影响参照保留，不把排队规模当研究收益 |
| 业务影响成立，已有信息能够可靠判断 | 保留现象与基线，停止为它增加测量机制 |
| 解释依赖未核实模型，或补采仍不能区分 | 限定或暂停候选，说明已排除解释和具体缺项，不转入无限建模 |
| 当前正常输入范围内没有值得深查的网络竞争 | 明确本轮未找到，保留覆盖和统计边界，不代表所有 Scale-Up 场景无问题 |

每个结论分清直接记录、机制解释、定向对照的总效应及信息比较；没有执行的部分明确标记。完成一个合格环节后按本页分支继续，直到所有已选候选处理完并给出总判断，而不是只提交下一步建议。记录与恢复流程同步到已有 `usage.md`，但只写经过验证的命令。进度只更新当前任务页，详细命令、预算和失败日志留在运行目录。

任务验收与研究正收益分开。一次完整否定结果可以完成本轮；权限或预算导致核心目标未完成时如实标记受阻，并交付其他已完成工作。本轮完成后停止，不自动重开 C1、进入正式 E3/E4 或推送新实现。
