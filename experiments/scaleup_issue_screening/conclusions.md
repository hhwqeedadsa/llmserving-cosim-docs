# 正常业务问题筛选结论

本轮只深入一个候选 C1：准备较晚的供数端拖后其他消费者，并影响后层进入。原四次正常业务运行、三次成本/完成条件对照和实际路径补证继续保留；新增请求队列补采及一项额度对照表明，当前模型的共享请求推进设定显著影响业务时间。**C1 限定为模型内现象，暂不据此进入新增测量研究**：A3 的实际队列组织和核内同步到协议事件的对应尚未确认，不能将这份结果直接解释为硬件瓶颈。原交付依据见[交付复核](results/delivery-review.md)，增量证据见 [E2](results/e2/README.md)。

本次用户确认在同一 C1/E2 内继续补查最晚消费者的完整依赖，并开展固定总额度的队列组织对照，具体要求见[候选 C1](candidates.md)。这项安排尚未形成新结果，不改变下述已完成运行事实，也不表示继续推进测量算法。

## 发现及证据

正常输入保留完整 128 rank、256 专家、Top-8、CM384 物理网络和 61 块部署容量。256、512、1024 请求各运行原始第 6～8 层，分析第 7、8 层；另用 1024 请求运行第 3～8 层，比较同样的分析层。三档是同一来源组的嵌套子集。

1. **供数端的工作量与消费者的等待需要分开看。** 256 请求下，第 7、8 层工作最多的端分别处理 203、219 个专家输入，平均每端仅 16 个。基线最后完成 Combine 的 rank 27、58 自身都只有 3 个专家输入，但关键前驱指向热点供数端 rank 70、65。进入晚、操作持续久、最终完成晚并不是同一指标。
2. **准备节奏的影响经实际执行得到验证。** 专家参考成本减半和加倍后，第 8 层最后计算结束从 110.792 微秒分别变为 83.025、166.613 微秒，即 −25.06%、+50.38%。请求和路由相同，重新构图并由当次完成事件推进后继；这些是模型内总效应，不是真实硬件优化收益。
3. **队列总量不能直接代表业务损失。** 成本减半时交换机总队列等待面积增加 10.17%，业务却变快；加倍时面积减少 4.52%，业务变慢。面积包含重叠和逐跳累计，不能扣除为可节省时长，也不能证明网络没有影响。
4. **主要形态保留，具体最晚端和事件会变。** 较长前序下两层 Combine 中位持续时间与短段接近，但 Dispatch 的细微完成排序改变。替代复制完成条件只缩短业务结束 1.22%，关键供数端仍是 70、65，最晚消费者和关键到达事件却改变。因此不将短段单个最晚 rank 或默认栅栏的状态等待推广为一般硬件根因。
5. **实际路径会随执行反馈改变。** 四份补采均保持各自原执行的节点、传输、聚合和包内容/发送时刻摘要。在共同的 20 个候选包中，成本减半、加倍、替代完成条件分别有 14、10、20 个改变路径。基线两份关键数据在所见后两交换机上各驻留 1 ns、端口先进先出队列（FIFO）等待为零，较长间隔位于首次交换机发送前；其他对照也存在几十纳秒的所见交换机驻留，不能推广为全网无排队。

详细数值及依赖时刻分别在 [E1 结果](results/e1/README.md)和 [E2 对照](results/e2/README.md)。原运行前的候选选择与三个对照安排保留在[固定历史记录](https://github.com/baoy21/moe-ub-cosim/blob/6ebe4984280465316f90886ccdbf4f66f4fe9d49/experiments/scaleup_issue_screening/candidates.md)，[候选 C1](candidates.md)继续维护经确认的增量核验要求。

## E2 判断与后续边界

E2 没有额外注入热点或降速，也没有重新选择路由、拓扑与线性计算成本。原准备成本对照的作用继续成立。增量核验将第 7、8 层的 12020、12583 ns 分别拆为打包、前序数据栅栏、前序状态请求形成三段，并以被动记录确认具体队首、字节范围占用者及释放响应。八段状态等待期间均有 worker 额度满的直接分支，共享请求池未耗尽；绝大部分时间目标状态排在其他核任务之后。这些解释同时成立，不能分别加总成可消除的损失。

已完成的额度对照保持单 worker 和请求拆分，只将 STORE 额度从 32 改为 64。三层结束时间缩短 12846 ns（11.59%），所选端点的实际请求范围及全局逐跳累计业务字节保持，执行时序和端口分布改变。它确认资源设定的模型内总效应，未测出真实硬件增加额度的收益，也没有分离此前数据传输与确认反馈的全部网络作用。

该额度对照中的新最晚消费者是 rank 33、56，完成时间及业务结束有执行记录支撑。不过，[效应分析程序](native_review.py)的 `latest_incoming_data_for_actual_last_consumers` 只筛选最后到达的数据，未在此项输出中完整检查状态、本核发送结束和归约条件。因此该字段目前只支持最后到达数据的来源，不能独立认定最终阻塞者。本轮将用已有记录补查完整依赖；这项分析限制不否定已测得的 11.59% 总耗时变化。

[源码核查](results/e2/c1-source-review.json)进一步把“事实存在”与“现实对应”分开：固定 CANN 分支有数据/状态顺序和局部缓冲约束；模型中下一份打包等待上一状态请求全部形成的映射，以及所有 AIV 的任务统一进入一个 worker 的设定，均没有取得充分对应依据。最小缺项是选定 A3 实现的同步关系和请求队列组织，不是泛泛要求重新做负载或成本校准。已完成的核验保留原同步，未用删除依赖或改成 48 worker 制造理想基线。

据此暂不把 C1 的发送等待提升为新增测量课题。当前授权的下一项是保持每端总额度 32、共享编号池 256、请求划分及核内同步不变，对照统一 FIFO 与按核轮转的请求组织。它检验现象是否依赖统一队列假设，不验证轮转就是 A3 硬件行为；现象在对照中保留也不能自动消除同步依据的缺项。结果形成后先判断 C1 的去留，不追加参数扫描。

方案 §6.1 允许供数端定位，但该方向仍需解释相对工作量和操作时序基线增加了什么；供数热点定位本身不解决上述现实机制缺项。限定或负面结果均符合[方案第 5.2、8 节](plan_v0.1.md)，不要求得到一个网络瓶颈。E3、E4 及完整 64 轮均未执行，本次没有新增候选或实验阶段。

这不是“已有观测已经足够”或“端网映射没有价值”的验证结果。本轮没有比较受限观测算法，没有映射收益、准确率或泛化结论。内部依赖只用于研究者核验，没有当作真实 profiler 默认可见的输入。后续去留以机制证据和具体信息缺口为准，不以完成阶段清单或保留某个现象为目标。

## 覆盖与复核

已有来源只支持一个不重复的 1024 请求组，本轮没有下载或循环补造来源；相关 rank、嵌套批量、同一执行的回放均不算独立重复。计算成本、分核和完成事件保留参考假设，没有完成目标 NPU 校准。三层和六层片段从明确初态执行，不能证明稳态、在线服务尾延迟或稳态每 Token 时延。三次对照只在 256 请求档执行，不能替代 1024 请求下的对照验证。

原运行的平台固定为 `e3db37a` 及当时锁定依赖。增量被动记录使用 `8fe4884`，额度重放接口使用 `4e23dda`，二者后端依赖均为 `fd1c6f0`，后端二进制相同；平台与实验分别提交。基线补采先通过原执行等价核对，额度对照另按实际变化比较，不把新结果标为旧平台运行。原分析在 `runs/scaleup_issue_screening/analysis/`，原完整输入和运行在 `archives/`，内部事实在 `facts/`；请求队列增量位于 `runs/scaleup_issue_screening/c1-mechanism-20261012/`，摘要入口见 E2。查看摘要无需解压，后端复用可恢复短段切片。新队列组织的实现与运行另行绑定实际版本，不改写这些历史范围。

命令、输入输出及恢复方式见[操作说明](usage.md)，资源和保存范围见[资源汇总](results/resources.md)。方法、方案、结果和任务状态分别维护，不以本页代替运行清单。
