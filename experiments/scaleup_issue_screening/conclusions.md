# 正常业务问题筛选结论

原已完成阶段深入候选 C1：准备较晚的供数端拖后其他消费者，并影响后层进入。原四次正常业务运行、三次成本/完成条件对照和实际路径补证继续保留；新增请求队列补采及一项额度对照表明，当前模型的共享请求推进设定显著影响业务时间。**C1 限定为模型内现象，暂不据此进入新增测量研究**：A3 的实际队列组织和核内同步到协议事件的对应尚未确认，不能将这份结果直接解释为硬件瓶颈。原交付依据见[交付复核](results/delivery-review.md)，增量证据见 [E2](results/e2/README.md)。

固定总额度的队列组织对照进一步显示：两条原链的前序状态请求形成等待分别由 6188、4306 ns 降至 1161、1302 ns，但数据请求形成变慢，第 8 层最后计算只提前 945 ns（0.85%）。热点供数端仍为 rank 70、65，最晚消费者改为 rank 10、34。**保留模型内现象，冻结 C1 发送队列分支，不继续围绕局部请求排队展开测量或调度设计。** 对照口径见[C1 收尾版本](https://github.com/baoy21/moe-ub-cosim/blob/f60de083d014423a6d05b086502d877636bbb662/experiments/scaleup_issue_screening/candidates.md)，数据和完整完成条件见[组织效应](results/e2/c1-organization-effect.json)及[E2 解释](results/e2/README.md#固定总额度的队列组织)。

正常网络侧筛选选出 N1（出口 802:6 的虚拟出口队列 VOQ）和 N2（810:2 的物理先进先出队列 FIFO）。原 256 请求辅助档的局部服务变化只让三层最后计算提前 8 ns，保留为低影响参照。放宽磁盘预算后，已补齐原 1024 请求发现档的被动等价、实际等待、完整依赖及一次 N1 服务对照：N1 最长到达至 FIFO 间隔由 5556 降至 417 ns，第 7 层最晚 Dispatch 提前 811 ns，三层最后模型计算提前 842 ns（0.213%），后续状态接替成为完成条件。**N1 的模型内业务作用成立，N2 缺少值得追加独立服务对照的业务线索。** 全 rank 的改善、退化和新最晚端均保留，不能把局部等待下降等量换成整段收益。

**信息增量经加强基线和跨记录复核后仍存在，但当前判断器只需要操作在出口的最后发送窗口，无须完整窗口映射。** 原 1024 请求全部 193576 次网络传输、原 256 请求全部 120980 次网络传输及冻结图依赖均支持：当前 `data_ready` 模板的源端操作结束是自身应用数据/状态交付的上界。逐源使用这个已有字段后，相关已知等待窗口仍分别只能唯一归属 105/132、36/49；理想信息增加到 116/132、40/49。两个原选峰值始终已能定位，不增加新信息。旧结果完整保留，新增对照见[离线核验](results/e2/README.md#离线信息核验)。

完整关系与只含最后发送窗口及覆盖声明的简化输入，在旧、加强两种基线下逐窗完全等价。只用公开非零发送计数与逐源时间范围的保守恢复没有过早宣布结束或遗漏已知等待，但没有取得这 11、4 个唯一归属增量。例如 N1 上第 6 层 Combine 的理想最后发送窗口结束于 80 μs，公开计数上界仍为 91 μs，不能排除与其他流量相容的旧操作。此结果只是否定这一简单恢复规则足够，不是普遍不可识别证明；两份嵌套记录也不是独立泛化证据。

**有限保留“特定应用操作在设备侧出口的发送结束边界”这个研究问题，暂不推荐投入完整映射恢复系统。** 已证实的用途是把已经离开该出口的旧阶段排除，为交叠阶段提供更紧的端网对照范围。若后续单独批准继续，具体观测需求是在出口发送开始记录中关联端侧操作身份，汇总最后非零应用窗口并证明覆盖完整；真实采集的身份关联、及时结束判定与成本尚未验证。本次使用后续封存记录，不能称在线判断；未证明新增归属覆盖主要业务损失。实际混合、13/4 个正队列未知窗口及部分上游缺项保留。N1 的模型内服务作用案例、N2 的低影响参照和 C1 冻结边界不变，不重开服务实验，不自动进入正式 E3/E4。

## 发现及证据

正常输入保留完整 128 rank、256 专家、Top-8、CM384 物理网络和 61 块部署容量。256、512、1024 请求各运行原始第 6～8 层，分析第 7、8 层；另用 1024 请求运行第 3～8 层，比较同样的分析层。三档是同一来源组的嵌套子集。

1. **供数端的工作量与消费者的等待需要分开看。** 256 请求下，第 7、8 层工作最多的端分别处理 203、219 个专家输入，平均每端仅 16 个。基线最后完成 Combine 的 rank 27、58 自身都只有 3 个专家输入，但关键前驱指向热点供数端 rank 70、65。进入晚、操作持续久、最终完成晚并不是同一指标。
2. **准备节奏的影响经实际执行得到验证。** 专家参考成本减半和加倍后，第 8 层最后计算结束从 110.792 微秒分别变为 83.025、166.613 微秒，即 −25.06%、+50.38%。请求和路由相同，重新构图并由当次完成事件推进后继；这些是模型内总效应，不是真实硬件优化收益。
3. **队列总量不能直接代表业务损失。** 成本减半时交换机总队列等待面积增加 10.17%，业务却变快；加倍时面积减少 4.52%，业务变慢。面积包含重叠和逐跳累计，不能扣除为可节省时长，也不能证明网络没有影响。
4. **主要形态保留，具体最晚端和事件会变。** 较长前序下两层 Combine 中位持续时间与短段接近，但 Dispatch 的细微完成排序改变。替代复制完成条件只缩短业务结束 1.22%，关键供数端仍为 70、65，最晚消费者和关键到达事件却改变。因此不将短段单个最晚 rank 或默认栅栏的状态等待推广为一般硬件根因。
5. **实际路径会随执行反馈改变。** 四份补采均保持各自原执行的节点、传输、聚合和包内容/发送时刻摘要。在共同的 20 个候选包中，成本减半、加倍、替代完成条件分别有 14、10、20 个改变路径。基线两份关键数据在所见后两交换机上各驻留 1 ns、端口先进先出队列（FIFO）等待为零，较长间隔位于首次交换机发送前；其他对照也存在几十纳秒的所见交换机驻留，不能推广为全网无排队。

详细数值及依赖时刻分别在 [E1 结果](results/e1/README.md)和 [E2 对照](results/e2/README.md)。原运行前的候选选择与三个对照安排保留在[固定历史记录](https://github.com/baoy21/moe-ub-cosim/blob/6ebe4984280465316f90886ccdbf4f66f4fe9d49/experiments/scaleup_issue_screening/candidates.md)，当前[候选文档](candidates.md)维护离线信息核验要求，不追溯改写 C1 或 N1/N2 的实验设计。

## C1 的 E2 判断与收尾边界

E2 没有额外注入热点或降速，也没有重新选择路由、拓扑与线性计算成本。原准备成本对照的作用继续成立。增量核验将第 7、8 层的 12020、12583 ns 分别拆为打包、前序数据栅栏、前序状态请求形成三段，并以被动记录确认具体队首、字节范围占用者及释放响应。八段状态等待期间均有 worker 额度满的直接分支，共享请求池未耗尽；绝大部分时间目标状态排在其他核任务之后。这些解释同时成立，不能分别加总成可消除的损失。

已完成的额度对照保持单 worker 和请求拆分，只将 STORE 额度从 32 改为 64。三层结束时间缩短 12846 ns（11.59%），所选端点的实际请求范围及全局逐跳累计业务字节保持，执行时序和端口分布改变。它确认资源设定的模型内总效应，未测出真实硬件增加额度的收益，也没有分离此前数据传输与确认反馈的全部网络作用。

该额度对照中的新最晚消费者是 rank 33、56。已有记录的[完整依赖复核](results/e2/c1-fifo64-consumers.json)确认最终分别等待 rank 70、65 的状态，在 60514、97354 ns 到达后立即归约 500 ns，再执行 92 ns 后续计算；本核发送和资源调度没有成为这些端的最后条件。[旧程序](native_review.py)的 `latest_incoming_data_for_actual_last_consumers` 仍只表示最后到达的数据，不再用它单独认定最终阻塞者。此次更正没有重跑仿真，也不改变已测得的 11.59% 总耗时变化。

[源码核查](results/e2/c1-source-review.json)进一步把“事实存在”与“现实对应”分开：固定 CANN 分支有数据/状态顺序和局部缓冲约束；模型中下一份打包等待上一状态请求全部形成的映射，以及所有 AIV 的任务统一进入一个 worker 的设定，均没有取得充分对应依据。最小缺项是选定 A3 实现的同步关系和请求队列组织，不是泛泛要求重新做负载或成本校准。已完成的核验保留原同步，未用删除依赖或改成 48 worker 制造理想基线。

统一 FIFO 与按核轮转的对照保持每端总额度 32、共享编号池 256、请求划分和核内同步不变；全图 139139 个实际请求范围与 128 个发起端的固定对象参数均一致。数据栅栏增量主要位于全部请求形成之前，相应任务在队列中等待且 worker 额度占满，形成后的尾段反而缩短。状态更早推进被数据推进的变化部分抵消，不能把局部状态等待下降相加为业务收益。这一结果保留了热点供数端拖后消费者的模型内形态，却显示局部等待组成依赖组织假设；既没有测出纯 FIFO 损失，也没有验证轮转是 A3 硬件基线。C1 到此收尾，实际请求组织和同步依据作为限制保留，不再通过更多参数或同步对照继续挖掘同一局部等待。

方案 §6.1 允许供数端定位，但该方向仍需解释相对工作量和操作时序基线增加了什么；供数热点定位本身不解决上述现实机制缺项。限定或负面结果均符合[方案第 5.2、8 节](plan_v0.1.md)，不要求得到一个网络瓶颈。C1 收尾时 E3、E4 及完整 64 轮均未执行；后续网络侧筛选另按已确认范围开展。

C1 没有得出已有观测足够或端网映射无价值的结论，也未比较受限观测算法，没有映射收益、准确率或泛化结论。内部依赖只用于研究者核验，没有当作真实 profiler 默认可见的输入。后续去留以机制证据和具体信息缺口为准，不以完成阶段清单或保留某个现象为目标。

## 覆盖与复核

已有来源只支持一个不重复的 1024 请求组，本轮没有下载或循环补造来源；相关 rank、嵌套批量、同一执行的回放均不算独立重复。计算成本、分核和完成事件保留参考假设，没有完成目标 NPU 校准。三层和六层片段从明确初态执行，不能证明稳态、在线服务尾延迟或稳态每 Token 时延。原三次成本/完成条件对照只在 256 请求档执行；网络侧 N1 另在原 1024 请求短段完成一次局部服务诊断，不能据此外推其他因素或长段收益。

原运行的平台固定为 `e3db37a` 及当时锁定依赖。增量被动记录使用 `8fe4884`，额度重放接口使用 `4e23dda`，二者后端依赖均为 `fd1c6f0`，后端二进制相同；平台与实验分别提交。基线补采先通过原执行等价核对，额度对照另按实际变化比较，不把新结果标为旧平台运行。原分析在 `runs/scaleup_issue_screening/analysis/`，原完整输入和运行在 `archives/`，内部事实在 `facts/`；请求队列增量位于 `runs/scaleup_issue_screening/c1-mechanism-20261012/`，摘要入口见 E2。查看摘要无需解压，后端复用可恢复短段切片。

组织对照绑定主仓 `4e5fd4d`、ns-3-UB `13cf3da`。新 FIFO 的全部原记录与 2688 个端口指纹先通过等价核验，随后仅进行一次轮转运行。记录位于 `runs/scaleup_issue_screening/c1-organization-20261013/`，原图保存在可直接重放的 `compact-slice/`，两个新增 case 已分别核验归档；22 项实验工具小测、平台独立验收和具体预算见[资源证据](results/e2/c1-organization-resources.json)。这些版本不改写历史运行范围。
