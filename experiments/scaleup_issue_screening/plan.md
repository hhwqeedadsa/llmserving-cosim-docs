# Scale-Up 性能问题与被动诊断能力实验方案

本方案落实 2026-10-14 确认的下一阶段安排，继续现有正常业务问题筛选。目标是检查不同网络运行状态为何造成等待、已有观测能否区分原因，以及在有限采集和上报成本下需要保留什么证据。它替代此前以少数候选递进的当前执行安排，不追溯改变历史实验定义。

本文件是本轮唯一的执行方案。进度、实际提交、预算使用和停止位置只维护在[当前任务](../../docs/tasks/current.md)；实际方法见[方法](method.md)，已验证命令见[操作](usage.md)，研究判断见[结论](conclusions.md)。目录规则见[实验总索引](../README.md)，历史资料见[归档入口](archive/README.md)。遵循 [AGENTS.md](../../AGENTS.md)与[开发维护](../../docs/development.md)。

## 1. 研究目标与判断范围

本轮连续回答三个问题。

第一，等待发生在哪里。数据尚未进入交换网络，还是已在某个交换资源等待；看到的上游积压，是本地竞争还是下游受限传播的结果。

第二，哪些通信受到影响。能否把实际受限资源与端点、通信阶段及必要完成条件联系起来，避免把最大队列或最后消费者直接当作原因。

第三，哪些证据值得持续保留。充分利用已有字段后还缺什么；细粒度资料能够判断的情况，在降低采集频率、状态量和上报量后还能判断多少。

测量价值可以来自增加有效信息，也可以来自相同诊断效果下减少代价。不要求先发现全新瓶颈，不预定必须增加映射或协议字段，也不把一个出口提速后的业务收益作为所有测量问题的统一准入门槛。性能影响、诊断作用和采集成本分别评价。

最终最多保留一至两个后续研究方向。没有足够强的候选可以完成本轮，但必须说明检查过的机制、合理基线、否定依据及未覆盖部分，不能因一个局部案例无收益就判断整个问题域无价值。

## 2. 固定场景与不开展的工作

沿用现有 CM384/R1 参考场景的真实专家路由、物理拓扑、专家放置、128 rank、256 专家、Top-8、隐藏维度 7168、完整模型部署容量，以及已验收 A3 STORE/STORE 模板、原生请求划分、有限资源、核内依赖和线性计算成本。原输入及来源见[历史方法](https://github.com/baoy21/moe-ub-cosim/blob/b345694fbc2faed8feebb425d43c60f765f7eee9/experiments/scaleup_issue_screening/method.md)。本轮固定这些条件，不重复开展路由代表性、计算成本校准或芯片容量审计。

主要使用已有 256、512、1024 请求短层段及较长前序。新增运行保留目标 rank 和物理网络，只运行已明确初态的有限层段，不将小型功能测试冒充目标部署，不将短层段解释为稳态在线请求 p99。

所有计算和通信仍由同一次执行的实际完成事件推进，共享持续存在的网络状态。改变网络服务时不固定历史发包时刻，不改导出的时间戳，不把独立网络运行拼接成一次竞争。

C1 发送队列分支冻结，不再扫描 worker、请求额度、轮转策略或核内同步。N1/N2 及操作结束边界保留为历史参照，不再主导本轮选点；只复用其数据和已核验能力，不以完成旧方案为由重开旧对照。

本轮不研究完整 HBM、缓存、芯片内网络、逐指令执行、A5 移植、P/D 分离、多模型混部、新拥塞控制或调度算法、自动故障处置、完整 61 块首轮或完整 64 步服务。接收消费导致反压尚未表达的部分属于未覆盖，不通过延迟应用回调代替。本轮时钟条件先保持准确对齐，不单独开展时间同步或事件锚点课题。

## 3. 三类问题及共同参照

| 问题类别 | 需要区分的情况 | 具体诊断输出 |
|---|---|---|
| 本地竞争与服务不足 `local_service` | 多源短时集中、出口有效服务减少、工作量增加但不存在额外受阻 | 直接受限资源、实际等待时段和相关通信，区分负载事实与服务原因 |
| 下游阻塞与排队传播 `backpressure` | 出口持续忙碌、有待发数据但不能推进、上游队列属于下游受限的传播结果 | 当前不能发送的条件、下游约束位置、受到牵连的上游范围 |
| 多平面推进差异 `multipath` | 各平面承担工作不同、工作相近而服务不同、少量残余传输决定完成 | 实际工作与服务差异、受限位置及其是否进入必要完成条件 |

三类问题可以在同一执行中同时出现，不能强行构造互斥标签。端侧晚准备是三类问题共同的排除性参照，优先复用已有记录，不重开计算模型研究。短时事件是否被采集覆盖、是否容易被平均值掩盖，贯穿三类问题。

无损网络中，队列上涨先后不能单独证明传播方向。必须核查实际待发对象、所用流控层或虚通道、报文长度对应的信用条件、服务状态及允许恢复的事件。信用非零不等于当前报文能发送，信用低也不等于此时确实阻塞。多个约束同时存在时保存集合或未知，不将重叠时段重复计为可消除损失。

多平面比较使用实际承载字节、服务时间和完成事实。不能用总字节均衡推导服务均衡，也不能以总工作量除以平面数代替实际路径与单出口预算。总利用率低时，先区分无数据可发、下游限制和流量分配差异。

## 4. 先完成项目整理和机制覆盖核对

### 4.1 独立完成目录迁移

先按第 10 节整理现有实验模块、检查、配置和历史结果，单独验收并提交，再开始新实验实现。交接已建立总索引、当前文档入口和历史导航；这不表示代码、配置及结果已经迁移。

迁移前保存当前可执行分析的小型检查及一份可取得的已有摘要作为比较起点。迁移只改变组织、导入和路径解析，不改字段、统计、预测或仿真行为；确需修正缺陷时另立修复提交和证据，不能混在纯整理提交中。无须为目录整理构建或运行目标规模后端。

### 4.2 建立机制和观测覆盖表

对第 3 节每一类逐项记录执行对象、产生/占用/释放关系、现有事实记录、公开可见字段与最小缺项。结果放在实际方法的覆盖部分，不另建一套平行进度表。

| 状态 | 后续动作 |
|---|---|
| 机制与足够记录均存在 | 直接分析已有执行 |
| 机制存在、记录不足 | 补有界且不扰动执行的事实记录，先小型验证，再按预算补采 |
| 接口可解析但作用过程未经验证 | 先用可手工核算的小例检查实际行为，不能以配置接受证明功能完整 |
| 关键作用过程没有建模 | 明确未覆盖和最小缺项，继续其他可执行类别，不伪造替代机制 |
| 已具备条件、声明范围内未出现 | 作为正常探索的有限否定结果，可进入有依据的受控能力验证 |

这项核对围绕三类问题，不重做完整芯片源码审计。不能等待模型无法产生的现象出现后才承认缺项，也不能为填满表格自动扩展端点内存模型。

### 4.3 明确已有观测的能力依据

在研究开始时一次性核对与所选场景直接相关的公开设备文档和最接近的原始论文，记录字段、采集位置、时间分辨率、接口语义和持续采集限制。保留版本或访问日期及直接来源，不把项目会议推测写成产品规格。来源找不到就标为参考能力假设，不因此暂停全部仿真研究。

至少区分现实可用基线、较充分但需接口支持的工程参照、研究者完整事实。不能把微秒级队列、精确应用身份或完整阻塞状态免费加入现实基线；也不能忽略已有链路计数、端侧工作量和明确硬件告警来人为削弱它。已有告警与隐藏的实验注入清单是不同输入：前者按实际可得性公平开放，后者只供准备和评价。

本轮原理和现象的公共依据只查与三类问题直接相关的材料，不开展宽泛行业综述。可借鉴拥塞传播与高精度测量工作，但要说明其协议、观测位置和资源假设，不把原有机制重新命名为 Scale-Up 独有发现。

## 5. 正常执行中的跨机制筛选

先复用已有正常运行，覆盖声明范围中的设备侧出口、共享交换链路及相关平面，不仅限于历史两个热点。记录未覆盖的端口和时间，缺失不补零。探索阶段研究者可以读取内部事实，但诊断程序不能据此获得精确待查端口或异常区间。

筛选同时考虑是否有待发数据、资源是否持续服务、何种条件阻止继续、相关通信是否尚未完成。队列均值、峰值、面积和 rank 持续时间只作为其中的观察，不再作为唯一排序。

各类最多深入两个代表，总计最多六个。这是深度核验的上限，不是全局只分析六个事件。每类保留全范围筛选的覆盖与分布，再选择不同状态的代表，包括明显积压且持续忙、积压但服务间断、多平面推进差异、等待被其他工作覆盖等。选择规则先保存，不按对照收益或新增字段收益挑样本；同一事件的相邻窗口不计为多个独立发现。

连续事件只有在状态记录支持时才能定义；相邻正面积窗口可能包含多个不连续时段，不能直接当作一次持续拥塞。输入量与服务量、同一传输和同一操作的比较分别说明，不将跨层、跨批量的耗时混为尾延迟分布。

每个深入候选需要回答观察到了什么、有哪些竞争解释、现有事实支持或排除了什么、下一项检查为何能够区分剩余解释。若简单工作量和必要依赖已解释主要现象，保留为参照，不因它数值大就继续包装新瓶颈。

一类没有自然候选时，先记录已检查范围，再按第 6 节决定是否值得受控验证。其他类别仍继续执行，不因某类无正例而缩小整轮研究范围。

## 6. 用有依据的受控变化核验机制与诊断能力

### 6.1 对照的用途和选点

正常运行说明自然出现的竞争。受控变化用于区分机制和检验诊断，不用来证明生产发生频率或制造研究必要性。优先复用已有正常图和平台出口服务接口，保持原业务、计算、请求组织与核内依赖。

从有正常业务经过的位置中，选直接面向设备的出口、多目的共享链路、不同平面中作用可比的链路作为代表。不因历史 N1 的收益有限就只重跑它，也不专挑最容易造成整体停顿的位置。

每类使用一个预先说明的主要服务档位，必要时一个具有不同判别作用的替代档位。依据名义服务、基线到达量、链路方向和问题所需时间尺度确定，不以期望的总时延损失反复调节。短时与较持续区间按需要取代表，不扫描位置、时长和强度的全部组合。

启动前保存对照的作用对象、时间、幅度、预期区分的解释、负例和评价定义。结果不支持解释时按反证收尾或转向已经列出的替代解释，不能不断换因子保住原候选。

### 6.2 实际作用与必要检查

变化必须作用于真实服务过程。下游反压通过实际服务下降、缓冲占用和流控反馈产生，不直接写零信用、添加无依据阻塞事件或延后应用回调。只影响指定方向还是双向，需要由接口和配置明确；ACK 与信用的反向作用不可忽略。

对每个对照核对有效配置、实际承载和被改变的服务；干预目标不自动作为唯一原因标签。没有待发数据、没有相关通信或未影响必要完成条件的情况应保留为负例。至少包含未干预正常执行和一类有变化但缺乏业务作用的参照，不能只交付成功受损案例。

使用同次执行核验具体报文/任务等待、竞争者、所受下游约束和恢复事件，区分直接受限资源、上游传播结果和仅时间相关的活动。不能以队列上升最早或最大的端口取代这些事实。

服务率变化同时改变串行化和排队，报告总效应并在记录支持时分解；不能把全部改善称为拥塞消除。工作完成反馈会改变发包时刻和路径，同种子不保证逐包同路径。保留全局守恒、实际路径分布与未保持的条件，不用固定历史路径制造纯因素效果。

复核当次全部必要完成条件，包括数据、状态、本核发送、归约及资源调度，保留并列条件和新的最晚消费者。原链局部提前不等于等量业务收益，零总收益也不自动证明对应等待不存在或诊断无用。

### 6.3 平台补充边界

本轮允许补必要的被动记录、公共读取能力及已有服务接口中与计划直接相关的小缺口。先核对记录点真实状态及超限处理，再通过不扰动调度、随机数、包内容、路径和完成结果的小型检查。平台代码不能导入实验模块；平台修正和实验分别提交、验收。

若发现必须改变原协议完成语义、核心调度策略或端点消费模型才能出现目标情况，该部分标记受阻或未覆盖，交付已完成工作，不把它自动扩为新平台里程碑。

## 7. 诊断信息与采集成本比较

### 7.1 三类可用信息与独立真值

| 条件 | 作用 | 评价边界 |
|---|---|---|
| 已有能力基线 | 端侧操作/工作量、拓扑、可得到的端口计数与告警，采用有依据的采集粒度 | 不隐藏已有字段，不把实验内部事实说成实际 profiler 接口 |
| 较充分的工程参照 | 在声明接口假设下，增加较细队列、服务或流控受阻等局部信息 | 检验哪些事实有用，明确新增硬件状态和记录代价 |
| 受预算约束的被动测量 | 以有限状态、更新和上报保留必要信息，使用局部可执行规则 | 不利用真实标签、精确事后选点或未来事件决定采集 |

完整路径、私有操作归属、精确传输时间、内部依赖及干预安排只供准备与评价，不作为第四种可部署方法。公开输入使用中性身份和显式白名单，运行名、路径、文件名及附加元数据不能泄露原因。

诊断应面对预先声明的完整范围，由可见信息检测和选择对象。研究者精选的深度核验区间可以作为单独的条件性分析，但不能据此宣称全网检测成功；采集成本应计算实际监测全部端口和背景状态，不能只算事后命中的两个出口。

先检查端口计数、队列、实际服务与相关流控状态分别消除什么歧义，再在必要时单独加入端网关联。加强已有字段规则、增加字段、提高时间分辨率和改变记录策略分别比较，不同时变化后把收益归为完整映射。

规则输出至少包含候选位置或位置集合、局部原因和支持事实、可能受影响的端点/通信范围，以及未确定部分。应用和协议控制分别解释，多个原因可以共同存在。较充分资料仍不足时明确缺项，不用更复杂分类器代替不存在的证据。

### 7.2 时间粒度与采集方式

在资料支持范围内先比较 1、10、50 μs，作为研究设置而非目标设备规格。已有 1 μs 聚合只能合法合并；亚微秒变化、窗口平移和新相位需要对应原始事件，不能插值补出。均值、峰值和面积与定时瞬时采样不同，准确标明每项统计需要的硬件更新方式。

比较固定周期、受限随机采样、局部事件触发的有界记录三种简单策略。先固定同样字段、观察范围和预算，再比较策略；需要变化字段时另设消融。随机样本采用明确的抽样对象、随机源和纳入概率，不从未来标签挑选。事件触发可保留有限事前/事后上下文，但事前缓存也计入持续开销，静默、短空队列或一次不发送都不能证明通信最终结束。

可以在已有完整记录上离线重放因果采集策略，但按时间顺序只访问截至当前的局部状态，不能回看后来的瓶颈再选保留范围。限制环形缓存、触发频率和最坏上报突发；记录溢出显式计为信息损失或失败，不能无声截断。若策略需要跨设备请求或反馈，其传输/处理延迟及代价必须说明，不假定全局零时延触发。

不要求三策略做所有参数组合。先以共同预算确定可比起点，再选择少量预算档位形成效果与代价关系；周期/概率/阈值在开发记录上确定，随后固定，不对每个评价事件重调。事件策略没有优势同样正常收尾。

### 7.3 评价、复核与硬件边界

以事件和实际排查判断为主要单位，记录漏检、误报及观察时长分母、候选资源范围、将传播队列误判为直接受限位置的情况、影响范围和未确定比例。对多个正确位置、真实混合及不完整真值分开处理；窗口数不当作独立样本数，未观测位置不补零。

实际通信完成和后续计算变化作为业务作用证据，但不设统一加速百分比作为所有测量价值的门槛。解释排查结论改变了什么，避免只提高无实际用途的标签唯一率。

代价至少包括字段位宽、每端口/队列状态项数、需要持续读取或更新的次数、缓存容量、平均及峰值记录率、上报字节和分析量。报得少不等于采得便宜；JSON/gzip 大小和宿主 RSS 不是交换芯片资源。相同上报量仍可能有不同硬件读取开销，应分别报告并给出可比预算。

P4 能实现摘要逻辑，不代表 P4 已能读取目标 UB 芯片的内部信用或仲裁状态。只说明实际采集位置、所需接口和轻量处理逻辑，不把离线策略验证写成硬件实现或零业务开销。仿真记录开关不扰动的检查也不能代替真实测量开销测量。本轮不自动开展硬件原型。

至少在既有不同请求规模或不同端口/阶段的一部分记录上冻结后复核。开发与评价的划分在打开相应标签前保存；曾被分析或嵌套来源明确标为相关复核，不宣称独立泛化。评价失败不回头按样本身份调规则。缺少足够复核资料时限定结论，不靠扩大错误分母掩盖。

## 8. 自主执行、预算和停止条件

Codex 负责研究核查而不只负责运行。授权范围内连续完成资料核对、目录迁移、分析、小型测试、必要的被动记录、定向服务对照、简单诊断与采集比较及反证检查，不在每个内部步骤后重复要求确认。

拟定首批 8～12 次新增目标规模短层段后端执行，另留最多 4 次补证，总计不超过 16 次，不要求用满。准备前登记每次用途及可复用结果；补采、等价基线、干预及启动后失败的目标运行均计入总数，不能通过换编号重置。纯读取、dry-run 和小型功能检查不计为目标运行，但仍受分项资源限制，不得借小例名义反复运行目标规模。

| 阶段 | 原有分项上限 |
|---|---|
| 后端运行 | 进程组采样 RSS 48 GiB，单进程地址空间 56 GiB，7200 秒 |
| 准备、导出、分析和校验 | 进程组采样 RSS 8 GiB，单进程地址空间 12 GiB，1800 秒 |
| 累计磁盘与空闲 | 64 GiB 累计产物，至少 20 GiB 空闲；保留原 16 个计量根，新增目录一并计量 |

开始前按当前实际占用评估图、执行、导出和归档的共存峰值。历史约 49.017 GiB 仅作预警，不当作当前实测。优先复用图、全局聚合与局部细节、流式统计和已核验无损归档，不删除旧归档，不通过换目录规避预算，不自动提高限额。只释放明确登记的本轮可再生副本，保存失败原因和产物清单。

首批名额应覆盖三类问题、参照与评价所需资料，不让同一候选用尽全部预算。未使用名额不自动转为新方向授权。无资料、权限、预算或需实质性扩围时，停止受影响部分，记录最小缺项，继续能完成的工作；不能只把原因未知留给使用者而跳过仍可执行的局部检查。

无完整硬件参数不应阻止所有研究，但某项参考限制成为主解释时必须有针对性核对。已有充分记录能解释的部分停止补采；关键解释被否定后停止保留该候选，不增加强度或换更弱基线维持收益。

## 9. 一次性研究交付

交付由三部分组成，不另建每轮一份的过程报告。

覆盖与发现写入各问题的结果说明，明确正常观察、受控验证、负面结果、缺记录和未建模。记录实际覆盖的链路角色、时间和业务条件，不能只报运行数。

诊断能力与成本写入比较结果，包含较强基线、逐项信息作用、采集粒度和策略、成本、误判与未知，以及一至两个可由具体记录复核的完整例子。不要求每个类别都有正收益。

综合判断写入 conclusions.md，最多保留一至两个候选，分别回答具体诊断任务、已有方法的不足、必要证据、作用位置、轻量实现的条件、相对开销和下一步验证。已有信息足够则保留为基线；只能在充分记录中看到则区分采集不足与信息缺失；依赖模型假设则限定适用范围。不要将少量标注改善写成重要业务问题已经解决。

完整探索要求三类问题都有明确处理，并让合格候选走完机制核验、诊断及代价比较。不能在只完成覆盖表或首批运行后标 completed，也不能因否定结果而强行进入新的测量机制。结束本轮后停止，不自动转向时钟对齐、协议标记、硬件穿刺或重开 C1。

## 10. 目录、文档和迁移要求

继续现有三个顶层实验目录，只把本目录作为当前工作入口；前两个保留历史身份，不新增第四个近义目录。迁移后的目标结构如下，实际有内容才建立子目录，不预建空脚本、空测试和空结果页。

```text
scaleup_issue_screening/
  README.md                  入口与阅读导航
  plan.md                    已确认的当前方案
  method.md                  实际方法、字段与评价定义
  usage.md                   已验证的操作
  conclusions.md             当前研究判断
  configs/
    baseline/                固定业务和网络输入
    scenarios/               受控条件与运行组合
    observation/             字段、采集及预算
  analysis/                  运行辅助、准备、诊断、核验、评价与代价分析
  tests/                     实验分析和输入隔离的小型检查
  results/
    local_service/
    backpressure/
    multipath/
    measurement_budget/
  archive/                   历史方案、结论及已结束分支索引
```

analysis 内按实际职责命名，区分研究者核验、受限诊断和独立评价。通用读取能力只有在多个当前模块确实复用时提取，不另建空泛的大工具框架。平台模块不导入 experiments，实验不导入 tests 或旧实验驱动作为正式执行依赖。

先在 archive/README.md 的对应表登记旧路径、用途和拟保留位置，再分批整理。已有 results/e1、results/e2 按初始探索、发送队列、网络案例、操作边界分组归档，不再追加新一轮结果到 e2。统计摘要的内容与历史源摘要保持，不通过迁移重写旧代码版本、输入身份或清单。历史原始数据保留在既有 runs 根，不整体复制进 Git 或新任务目录。

旧 plan_v0.1.md 和 candidates.md 在交接时仅留历史链接，以免既有引用失效，不再共同维护当前要求。首批迁移核对全仓相对链接后删除这些过渡入口；原方案由固定提交完整保存，需要本地归档时修正其链接或明确版本。历史结果原文件内容不因目录整理而润色或改算。

代码搬迁需要核对相对导入、Path(__file__) 根目录推导、模块 CLI、配置路径、归档内成员、被记录的程序摘要及外部调用。历史执行绑定旧代码，不能把新程序哈希写回旧运行冒充一致；新重分析单独绑定来源和版本。旧命令通过对应 Git 提交复现，不添加大量兼容包装永久维持每个旧模块入口。

迁移验收至少包含导入与 CLI 帮助、文档和本地链接、分析单元检查、资料白名单、一个小型完整准备/诊断/评价流程，以及可取得的已有逐项结果等价。缺历史大归档不妨碍小型检查，但不能据此宣称历史重算已完成。新接口验证后再写 usage；method 只写实际实现，设计仍在本方案。

results 每类使用简明结果说明及机器可读证据；完整命令和日志留在 runs。结论应能依次追溯到比较表、运行清单与配置、原始证据。新运行标识稳定、中性，研究者清单保存真实条件，算法输入不从文件名获得答案。进度只维护当前任务，其他文档不复制阶段状态表。
