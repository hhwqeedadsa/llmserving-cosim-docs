# 下游阻塞与排队传播

正常来源复用[四档筛查](../local_service/normal.json)，真实判断见[精确正常复核](normal-exact.json)。1024 请求短段在全部 3584 个被补采端口、`[0,394911 ns)` 中没有实际失败的 CBFC 队首信用检查。CBFC 指按信用额度限制发送的流控；这里检查的是当前报文所需额度，不把非零信用或低发送量当作能否发送的证据。

预先选出的低发送量 `768:0` 和 `768:17`，在 1～3 μs 分别只有 6、4 个相关报文；从实际网络到达至出口发送均为 1 ns，FIFO 无额外等待。其相邻正面积窗口不能证明持续阻塞或下游排队传播，两个自然候选均不成立。

这是声明范围内未出现信用阻塞的有限否定结果。接收应用消费速度导致的反压没有建模，属于未覆盖；不能由本结果否定该机制，也不能把没有正例时的诊断召回率写成 100%。

## 服务受限后的核验

[八项完整结果](study.json)记录正常补采、直接/共享/两平面服务对照及较小规模复核。持续对照将 `768:6` 在 0～400 μs 的速率设为 4 Gbit/s，实际忙碌 397992 ns，发生约 400 μs 的真实出口等待和显著业务拖延；仍没有实际失败的队首信用检查。短时、共享和平面对照也没有失败检查。

信用始终采用每虚拟通道 6553 cell、每 cell 160 B、归还门槛 1024 cell。当前闭环阶段、分散路径与既定额度并不保证一个出口减速就耗尽上游信用。本轮没有减小额度、增加请求或延迟接收回调来制造正例。

必须区分两种传播：网络的逐跳信用限制，以及数据完成较晚后引起的业务依赖传播。后者已由实际数据就绪、源端回调、状态发送和后续完成条件证实；它不要求出现前者。[本地服务结果](../local_service/README.md)给出可复核实例。

## 诊断范围与取舍

完整队列与服务字段足以判断这些对照存在本地服务不足；新增信用字段没有带来本轮正例上的诊断增量。全程实际失败检查为零，因此失败检查检出率、根因定位正确率及将传播队列误判为根因的比例均未定义。算法只在实际失败时报告信用见证且根因未定，没有声称从队列先后推断下游根因。

保持两个不同结论：已建模信用机制在所查有限执行中没有支持候选；接收应用消费反压及未捕获物理链路尚未覆盖。该类别不保留后续算法候选，也不被整体否定。增加更强受控输入只为获得正结果，不是本轮收尾的必要条件。
