# C1 的依赖事实与成因对照

本页保存[候选 C1](../../candidates.md)的实际核验，完整正常输入发现见 [E1](../e1/README.md)。这些是研究者对内部事实的检查，不是测量算法的结果。

## 基线中的具体等待

公共事实导出覆盖第 7、8 层全部 128 个 rank，共 379068 个节点、81263 次交付。沿每层最后完成 Combine 的消费者，以及专家输入最多的端，分别取一条最晚前驱链；并列前驱全部列明，未选中的前层节点保留边界。链上不能看到的资源持有者保持未知。

下表单位为微秒。数据行只指链上决定相应完成标志的那份关键传输，不是该端全部结果的累计量。

| 实际事件 | 第 7 层：rank 70 → rank 27 | 第 8 层：rank 65 → rank 58 |
|---|---:|---:|
| 消费者进入 Combine | 33.072 | 72.634 |
| 供数端专家计算结束、进入 Combine | 54.198 | 95.268 |
| 关键数据提交 | 66.218 | 107.851 |
| 该传输全部原生请求形成 | 67.636 | 109.530 |
| 该份数据到齐，完成标志提交 | 68.132 | 110.112 |
| 标志到达，消费者开始归约 | 68.220 | 110.200 |
| 该 Token 归约及消费者 Combine 完成 | 68.720 | 110.700 |

两处消费者的关键前驱都是供数端的状态到达；满足条件后立即执行 500 ns 归约，没有额外的归约调度间隔。归约开始早于对应状态事务的 ACK 回收，不能把协议回收时间重复加入消费等待。供数端的专家输入数分别为 203、219，而消费者自身都只有 3 个专家输入，不能将消费者完成晚解释为其自身专家工作多。

默认 `data_ready` 栅栏确实让状态提交等待相应数据交付。发送路径也有从提交到全部原生请求形成的间隔：上述两份数据分别为 1.418、1.679 微秒。它们涉及原生推进和有限资源，但本次记录没有给出具体资源持有者，也未观察端设备出口队列；不能把这段全部归为交换机排队，或反过来断言它与网络反馈无关。

当前事实支持执行预定的专家准备成本与复制完成条件对照。它尚未给出每一处原生等待的根因，也不允许把若干前驱链的重叠等待相加成可节省时间。
