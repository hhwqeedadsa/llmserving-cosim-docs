# 本地竞争与服务不足

[四档正常来源](normal.json)保存各 2688 个声明交换出口的首次筛查；[精确正常复核](normal-exact.json)补充 1024 请求短段的真实服务和逐包等待。补采覆盖这些出口及其链路对端共 3584 个端口，范围为 `[0,394911 ns)`，19,123,879 条事实完整无丢弃；原 2688 出口报文/时刻及 8,082 份原记录[等价通过](capture-equivalence.json)。

正常运行有 140 个持续至少 1 μs、峰值至少 8192 B 的声明范围排队事件；没有低于名义速率的服务事件或实际信用检查失败。预选 `768:6` 在 2～12 μs 的 178 个相关报文，实际到达至发送等待累计 448102 ns，其中出口忙碌覆盖 447519 ns（99.87%）；报文最大等待 7400 ns。这支持短时来流竞争，不能把累计等待等同于业务可缩短时间。

另一预选共享出口 `768:18` 的 1～4 μs 共 27 个报文，最大实际等待 77 ns；相邻有面积的窗口并非持续拥塞。两种状态均保留，不以队列面积大小替代机制。

[方法](../../method.md)说明字段、真实事件和采集成本口径；[六个预选对象](../../configs/scenarios/mechanism-cases.json)在服务对照结果之前固定。

## 短时直接出口与共享链路对照

[服务对照证据](service-controls.json)保存实际服务、完整业务条件、私有回调核验及固定规则解释结果。

| 对照 | 实际生效 | 最终通信完成变化 | 信用失败 |
|---|---|---|---|
| `768:6`，2～12 μs，100 Gbit/s | 区间内 39 个开始发送的报文均使用该速率 | +7062 ns | 0 |
| `768:18`，1～101 μs，100 Gbit/s | 255 个报文使用该速率，已归属业务涉及 75 个目的设备 | +729 ns | 0 |

发送开始字节包括跨越区间末尾完成的整包，不当作区间内实际序列化字节。图、计算时长、原生请求与资源配置相同；采用原选路算法及种子，但后续完成反馈和实际路径不被强制固定。

短时直接出口中，rank 102 发往设备 6 的必要数据包，在基线与对照都于 7209 ns 到达出口；等待从 4635 ns 增至 12239 ns，数据就绪从 11946 ns 推迟到 19550 ns。该数据完成条件继而约束源端状态发送、状态数据就绪与整理，Dispatch 最晚完成从 15208 ns 变为 21654 ns。该条连接在单独核查最终消费者最后一跳时并不显现；不能由“最后一跳不经过该口”排除其作用。

局部数据晚 7604 ns、Dispatch 晚 6446 ns、最终通信晚 7062 ns 是不同量。中途最晚消费者会切换，原本未限制完成的条件也会接替。共享链路的总作用更小，保留为幅度有限的对照；不能把降低速率自动等同于持续阻塞，更不能把全部变化称为可消除的队列等待。
