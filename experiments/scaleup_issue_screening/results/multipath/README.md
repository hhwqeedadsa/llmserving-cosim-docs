# 多平面推进差异

[四档来源](../local_service/normal.json)以相同物理对端、整段实际工作相差不超过 10% 选出两组；[精确正常复核](normal-exact.json)进一步分开业务到达和实际发送。

| 出口对 | 业务字节 | 到达的 90% 时刻 | 发送的 90% 时刻 |
|---|---|---|---|
| `799:14` / `801:14`，对端 78 | 436224 / 408576 B | 324775 / 269004 ns | 324776 / 269005 ns |
| `805:10` / `809:10`，对端 90 | 437248 / 401408 B | 316059 / 263394 ns | 316060 / 263395 ns |

两组约 55.8、52.7 μs 差异在业务报文到达出口时就已存在，对应发送分位点仅晚 1 ns。四个出口的逐业务包等待中位数均为 1 ns，最大分别 55、165、58、72 ns。分操作工作量与到达进展一并保存在摘要，不能由整段字节相近推导每阶段工作相同。

因此，这两组正常推进差异不支持“平面服务不足”的自然候选。原含控制报文的窗口统计约 55、53 μs 差异仍有效，但不是业务完成时延；必要的残余完成条件另由实际依赖核验，不以 90% 进展代替最后消费者。

## 相同对端的两侧服务对照

在预先固定的 200～400 μs 区间，分别将 `799:14`、`801:14` 限为 50 Gbit/s，其他条件保持。前者有 149 个开始发送报文实际采用低速，区间忙碌 23741 ns；后者同为 149 个，忙碌 24106 ns。最终通信完成分别增加 150、292 ns。两个结果都保留，没有增加强度来寻找更大的收益。来源、各操作实际工作、到达与发送进展见 [study.json](study.json)。

| 执行 | `799:14` 业务字节 / 到达 t90 | `801:14` 业务字节 / 到达 t90 | 最终通信完成 |
|---|---|---|---|
| 正常 | 436224 B / 324775 ns | 408576 B / 269004 ns | 394543 ns |
| 只降低 `799:14` 服务 | 434176 B / 310091 ns | 449536 B / 321688 ns | 394693 ns |
| 只降低 `801:14` 服务 | 434176 B / 306427 ns | 429056 B / 274198 ns | 394835 ns |

t90 表示实际业务字节累计达到 90% 的时刻。三种执行的这些发送 t90 都只比对应到达 t90 晚 1 ns，但逐包核验确有受控增加的等待。尤其第一项降速后，该出口 t90 反而提前 14.684 μs：相同选路算法和种子并不固定之后的实际来流构成及路径选择。整段分位点可以掩盖局部低服务，也可以在没有低服务时出现很大差异。

## 完成条件与诊断取舍

研究者检查每次执行各操作的最晚消费者、并列条件、固定接收方和原基线最晚者，并沿源端实际回调继续展开。两侧对照的最晚通信完成节点可以改变；仅“必要传输曾经过该出口”不是它决定最终完成的证据。`801:14` 对照有设备 78 的状态包与其本地数据就绪条件精确匹配，但这些接收并非该操作全体最晚消费者；影响幅度仍以完整反事实执行结果为准。

公开端口计数的推进差能提出待查资源，公共阶段/工作量能够限制比较对象；实际到达与服务资料则排除了预选正常案例的服务不足解释。本轮不能由这种研究者侧核查，直接推出必须向在线算法暴露完整包路径或业务身份。它也没有证明整段均衡足以排查所有残余完成问题。

该类别不保留新测量候选：有限范围的自然候选被竞争解释消除，服务对照虽真实生效，已有服务统计能定位这些受限资源，尚无额外完整映射不可替代的诊断任务。条件、反例和未证明的部分同时保留，而不是把小幅业务影响当作统一否定门槛。
