# 发送槽等待的基础观测对照

本轮接续[发送槽结果](results-slots.md)，检查端口记录能把发送资源等待的检查范围缩小到什么程度。研究者知道内部依赖和槽占用，不表示端口测量能够直接知道这些状态。本方法在新的 seed=3 执行前固定，实际结果另见结果说明；本页不记录运行发现。

## 输入与固定规则

开发参照为 seed=0/1/2、每 rank 8 请求的三个单槽/双槽对，共六次既有正常执行。新的 seed=3 仍按 `sha256-top2-v1` 规则生成请求和路由，两次执行仅改变发送槽 1/2。旧用户入口验收的重复运行不增加研究样本。都是合成输入、参考计算成本，未作硬件校准。

每次开放 **[0,100000 ns)**、8 个 rank、32 个交换机出口。这个完整区间根据既有小场景范围预先选定，包含计算、通信、尾部空闲；测量程序不知道实际结束时刻。新运行超出区间则报范围不适用，保留记录，不延长区间或截断目标来继续本轮评价。

原始计数与队列基础窗口为 100 ns。使用五种网格：`(周期, 起点)=(100,0)、(1000,0)、(1000,500)、(10000,0)、(10000,5000)`，单位 ns。规则网格与声明区间相交，保留两端短窗；所有边界与基础窗口对齐。计数及字节时间积分求和，峰值取最大。零值由各自完整的声明覆盖范围补齐，不能从无计数推断队列为空。

| 信息条件 | 开放字段 | 固定候选规则 |
|---|---|---|
| C0 `counts` | 每个出口的包数、包字节数，静态拓扑、端口/rank 列表、时间窗 | 任一出口有计数字节就选择该窗 |
| C1 `counts-queues` | C0 加 VOQ/FIFO 等待字节时间积分和峰值 | 任一出口有正等待字节时间积分就选择该窗 |

VOQ 是面向输出端口的虚拟队列；FIFO 是物理出口的先进先出队列。积分只计算等待，正在发送的数据不在其中。峰值可能包含同一时刻的瞬时变化，因此不以正峰值代替正时长等待。

每个选中时间窗都需要检查全部 8 个 rank。本轮规则不借助内部关联定位端点，也不把任一网络证据直接标为“发送槽满”。所有窗口的原因状态均输出 `undetermined`（未确定），安静窗口也不标为“无可发工作”。两档均提供节点、链路、端口与 rank 映射的静态拓扑；本轮简单规则只检查全体出口是否出现对应证据，未利用拓扑进行端点定位。C1 是使用新增队列字段的简单筛选基线；它未必优于 C0，结果不能代表所有可能的测量算法。

## 准备、测量、评价的边界

准备程序验证输入及执行摘要、同平台/后端版本、公开记录存储和零偏移/零漂移时钟，分别写出 `observed/counts/`、`observed/counts-queues/` 和 `truth/`。公开包使用不含实验条件的编号，不含路径、seed、槽配置、真实结束时刻、节点/传输身份、真值摘要或精确异常范围。开发/复核角色和源路径只在评价侧保存。

测量程序只读传入的独立公开目录。严格字段检查和 Python 文件访问审计阻止意外读取旁边的 `truth/` 或源记录；这是防止实现误用的检查，不是抵御恶意代码的操作系统安全沙箱。计数条件的目录不包含队列数据。实际准备与评价由其他模块执行，测量模块不导入这些模块。

评价目标是**显式依赖满足后、SEND 尚未开始、且全部发送槽被其他 SEND 占用的 rank 时间**。准备程序用现有依赖节点和提交/资源释放记录交叉核验，再对同 rank 的待开始 SEND 区间取并集，与满槽占用区间求交。多个同时等待节点只计算一份 rank 时间。它是内部重建标签，不是调度器直接保存的 ready 原因，也不是完整关键路径损失。

每个 rank/窗保存满槽等待、其他待开始等待和无待开始 SEND 时长。“无待开始 SEND”允许有在途通信或尚未满足依赖的后续工作，不能解释成 GPU 空闲。按半开区间计算，不推断同一纳秒内的先后顺序。

## 评价指标与成本

分别报告每个输入、网格及信息条件，再按开发/复核组求和。核心指标为：

- 检查范围：选中 rank·ns / 全部声明 rank·ns；另报只计实际执行期间的范围，结束时刻仅评价可读。
- 等待覆盖率：被选窗口覆盖的满槽等待 rank·ns / 总满槽等待 rank·ns。
- 检查时间中的目标占比：被覆盖等待 / 选中 rank·ns，不称为原因识别准确率。
- 误选：选中但没有目标等待的 rank/窗；漏选：未选中的有目标 rank/窗和等待时长。窗口粗化会改变格数，因此不能只比较格数。
- 未确定比例：原因均未确定。候选覆盖不等于已经区分“无可发工作”和“资源占满”。

保存实际输入/输出字节数、处理窗口和端口记录数、宿主时间与受控内存。这里没有设备采集开销的实测。窗口聚合重复使用同一执行，不能当作独立随机重复或额外实验样本。

## 最小端侧事实记录候选（尚未实现）

端口计数表明发生了发送，队列积分表明出口前发生了等待；两者均未直接给出某 rank 是否有依赖已经满足的 SEND，也未给出发送槽占用。现有操作阶段的 `prepare_end` 是计算准备阶段终点，不等于所有 SEND 的依赖就绪时间。缺失项应具体记录为：

1. 每 rank 的依赖已满足、尚未发起 SEND 数 `ready_send_count`。
2. 实际在途 SEND 数 `active_send_count` 与配置容量 `send_slot_capacity`。
3. 同一端点本地时间下的状态更新，以及记录覆盖范围/丢失标记。

候选采集位置为 ASTRA `workload/Workload.cc::issue_dep_free_nodes()` 完成当前就绪队列扫描后，以及完成回调释放资源、解锁后继并重新派发后；槽数应读取 `HardwareResource` 的实际占用集合（已有 `active_p2p_sends()`）。要区分扫描时临时取出的节点和最终留在可派发队列中的节点，不能记录队列扫描中间状态冒充稳定状态。

`ready_send_count>0` 且 `active_send_count==send_slot_capacity` 才提供直接的端侧资源限制证据；只有占用数不足以区分“没有新的可发任务”和“仍有可发任务”。上述只是本仿真器可实现的被动事实记录方案，不声称真实设备已有对应硬件接口。后续若实施，需独立平台任务验证记录开关不改变事件/包/完成时刻、有界存储和时间语义，再与本轮端口基线比较。
