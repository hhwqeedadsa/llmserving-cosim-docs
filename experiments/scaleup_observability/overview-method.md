# 首批执行概览的计算口径

`normal-overview-v1` 供研究者检查完整执行，可以读取内部任务图和事件。它不是被动测量算法，不给出根因标签，也不把这些内部资料自动开放给后续测量方法。只接受本阶段一次完整 Decode、全 32 出口详细记录和统一无误差时钟的小场景。

## 网络资源

`ports.csv` 每行一个物理出口，包含源/目标节点类别、名义速率、实际包数/字节、链路占用时间，以及 VOQ（按出口组织的虚拟输出队列）和 FIFO（出口先进先出队列）的面积、均值与峰值。

- 包计数来自成功开始发送事件，每个出口独立计数。全网累加有逐跳重复，不能当作唯一业务交付量。
- 链路占用取实际 `tx_start.time_ns` 至 `busy_until_ns` 的区间并集；先核对该审计与所有逐包发送记录一一对应。占用率分母是本次实际仿真时长，不使用 1 ms 观测尾部的零值稀释。
- 队列面积按详细初始状态和变化积分，单位 byte·ns；均值为面积除以实际仿真时长。峰值保留同一时刻持续零时间的中间状态。原始队列字节包含协议开销及控制包，不等于业务字节。
- 独立核对详细发送总量与公开窗口总量，以及详细队列积分、峰值与公开统计一致。无发送的非零队列窗口仍参与核算。

`queued-without-transmission.csv` 保存“VOQ 或 FIFO 非空，且该出口没有实际发送”的连续区间。精确地用队列非空区间减去物理发送区间，不把两个发包时刻之间的整个间隔都算成停发。该指标可能包含仲裁等正常开销，不单凭它判定信用耗尽、反压传播或异常。跨端口相加的单位为 port·ns，不能解释为整轮损失。

## 传输完成

`transfers.csv` 一行一份实际跨芯片 UB 搬运任务，由计划与执行记录的传输身份配对。保存逻辑调用所属层、Dispatch/Combine、消息角色、STORE/LOAD、字节数和物理角色。LOAD 的数据拥有者和消费者与请求发起方向分开。

| 字段 | 来源与含义 |
|---|---|
| `submit_ns` | `send_start_ns`，适配器登记并提交任务的起点，不代表首包已发出 |
| `data_ready_ns` | 实际有效数据完成通知，不用末包发送代替 |
| `protocol_complete_ns` | `transaction_done_ns`，原生任务完成并清理发起资源的回调 |
| `initiator_release_ns` | `send_done_ns`，发起方 SEND 回调及发送槽释放 |
| `other_callback_ns` | `receive_done_ns`；STORE 对应消费者接收回调，LOAD 对应供数方缓冲等待回调 |
| `data_latency_ns` | 数据就绪减提交时刻 |
| `task_latency_ns` | 协议完成减提交时刻 |
| `data_to_protocol_complete_ns` | 数据已经就绪后，原生任务尚未完成的尾段 |
| `committed_segments` | 适配器实际累计的有效数据分段数；不表示保存了每个原生请求的完整时间线 |

`local-deliveries.csv` 单独保存同芯片交付，不能把它算成网络任务。每个计划交付必须恰好对应一项网络任务或本地交付，核对字节、一次提交和双侧一次完成。原生 starts/completions 表记录的是内存任务起止，也不等于任务内部原生请求起止。

`transfer-groups.csv` 按通信种类、消息角色、原生操作、任务字节数和同服务器跨芯片/跨服务器分组。报告均值、最小、最大及最近秩分位数（升序第 `ceil(p*N)` 个值）。全体任务混合分位数只用于概览；比较拖尾优先看相同分组，避免大小、角色差异造成误读。两类路径是拓扑类别，不是固定逐包路径。

## 执行影响与完成进度

`nodes.csv` 核对图节点与执行起止，并保存层、阶段和依赖关系推导的最早就绪时刻：图激活与全部显式前驱完成时刻的最大值。它只说明显式依赖已经满足，不是调度器直接记录的资源就绪事件。实际开始减去该值记作 `after_dependencies_before_start_ns`，不直接标记为发送槽、计算槽或信用等待。

每个 COMP 计算节点的实际持续时间必须等于本次计划成本，核对一个 rank 的计算区间不重叠。`ranks.csv` 保存逐 rank 计算工作量、计算占用率、显式依赖满足后尚未开始的累计时长，以及完成时刻；这些累计等待可能互相重叠，不能加成整轮损失。`layers.csv` 保存逐 rank、逐块的实际起止和计算工作量。

`summary.json.input_expert_counts` 沿用平台计划字段，数组按 rank 汇总该 rank 上两个专家收到的贡献数；不是 16 个专家各自的计数。逐专家输入量在执行前冻结的 `batch.json.cases[].expert_inputs` 中，二者可按每两个相邻专家求和核对。

`progress.csv` 使用 100 ns 半开窗口，保存逐跳发送字节、数据就绪任务数、唯一跨芯片业务交付字节、协议完成任务数、已完成计算节点的声明工作量及累计量。计算工作量在节点完成时记账，不能将单窗值视为该窗口实际计算占用。最后一窗覆盖结束时刻的事件，因此其右端可能略晚于仿真结束；没有声称仿真执行到该端点。

服务结果必须证明所有声明请求在一次完整 Decode 中各推进一个 Token，逐层路由消费完整、KV 资源释放、网络排空。整轮完成取实际服务完成事件。`decode_tokens_per_second` 是本次单轮完成 Token 数除以时长，不代表连续服务的稳态吞吐，也不把请求当独立时延样本。

## 缺失资料与解释边界

首批保留直接调度就绪/受阻原因、信用与原生在途资源占用历史、逐原生请求时序、接收消费/HBM 服务模型等缺口。现有数据可以描述很多等待与完成差异，但不能对这些缺失状态填零或用邻近事件代替。成本为未校准参考值；是否补记录或模型，要由后续选定现象决定。
