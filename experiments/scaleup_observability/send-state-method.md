# 新增端侧状态的观测对照

本轮继续同一实验的观测需求判断，接续[基础观测结果](results-observations.md)。实际发送状态记录已通过平台功能检查；这里要检验它在受限采样下带来的判断能力和代价。规则在本轮执行前固定，结果另页保存，不修改原实验方案。

## 输入与比较条件

固定四次运行：seed=3、seed=4 各一组每 rank 单槽/双槽输入。seed=3 是已知输入的复现参照，不能再称未见样本；seed=4 是规则固定后新生成的复核输入。沿用 `sha256-top2-v1` 规则、8 rank、每 rank 8 请求、原生 STORE Dispatch / LOAD Combine、小模型完整一轮。输入对只改变发送槽数；不额外改变计算、网络、路由生成规则或负载规模。

四次全部使用相同的已验收后端，开启实际发送状态记录。三档信息从同一份执行准备，不将旧版本运行与新版本运行混在同一对照中。全局声明区间仍为 `[0,100000 ns)`，开放所有 8 个 rank 和 32 个交换出口；若实际执行超出范围，报错并保留原因，不自动延长范围。公开输入不含真实结束时刻。

| 条件 | 开放信息 | 固定规则 |
|---|---|---|
| C0 `counts` | 原端口包数、包字节数及静态拓扑 | 任一出口有字节则检查该窗全部 rank；端侧状态未确定 |
| C1 `counts-queues` | C0 加原 VOQ/FIFO 等待积分和峰值 | 任一出口等待积分为正则检查该窗全部 rank；端侧状态未确定 |
| C2 `counts-queues-send-state` | C1 加每 rank 采样时的实际待发数、占用数、槽容量 | 按端侧计数判断采样时状态；仅在有待发任务且槽满时选择对应 rank 的该窗 |

C0/C1 完全沿用既有规则，使用已有测量程序。C2 开放的容量本身就是候选事实，不能再宣称分析不知道槽数。C2 不要求同时有网络发包或正队列积分；否则可能人为漏掉网络安静时仍未释放的资源。这里评价的是三条明确的简单规则，不代表每档信息能够达到的最佳算法。

## 时间采样与状态解释

沿用五个 `(周期, 起点)` 网格：`(100,0)`、`(1000,0)`、`(1000,500)`、`(10000,0)`、`(10000,5000)`，单位 ns。网格与完整声明区间相交，保留首尾短窗。端口计数/积分合并，峰值取最大。

C2 在每个窗口左边界取一次三个计数：读取该 rank 不晚于边界的最后一条真实状态更新，同刻更新按序号取最后状态。不使用窗口未来的状态、窗口内最大值或事后标签；完整逐变化记录只用于准备这些点采样。输入时钟仍为零偏移、零漂移，本轮不同时引入时钟对齐算法。

- `full_pending`：待发数大于零，实际占用等于正容量。
- `other_pending`：待发数大于零，仍有空槽。
- `no_pending`：容量已配置且待发数为零；可以存在在途通信、计算或未满足依赖的任务。
- `undetermined`：容量尚未配置。未知不填成没有等待。

这些描述只适用于采样时刻。为与原候选窗比较，选择一个点为 `full_pending` 的 rank/窗后，将整窗计入检查范围；这可能包含等待结束后的时间，也可能漏掉两次采样之间的短等待。评价同时报告点判断和整窗覆盖，不能用点判断准确来声称整段连续状态都准确。

## 输入隔离与独立评价

准备程序从平台公开 `observed/endpoint_send_state.jsonl` 读取真实采集的三个计数，经覆盖、序号、字段及校验和核验后采样。不允许用图依赖反推出计数再写入 C2。三个公开目录各自封闭，均含完整区间、匿名样本编号、相同静态拓扑；C0/C1 不含新增状态。

研究者评价侧沿用图依赖满足、实际 SEND 提交/释放重建的区间，并核对真实传输和本地完成回调。每 rank 的等待按区间并集计算，不把多个同时待发 SEND 重复累计。按独立区间计算各窗满槽等待、其他等待、无待发时长，以及左边界状态；真值不从新增计数生成。

测量程序只读传入的公开目录，不导入准备或评价程序，不读取真值、执行图、源路径、实验输入角色或配对结果。继续使用字段白名单和文件访问审计防止意外越界。评价程序单独连接预测与真值，核对内容摘要。

核心指标沿用检查范围、等待覆盖率、检查时间中目标占比、误选 rank/窗、漏选 rank/窗和等待时长；分别报告每个输入、槽数、网格，再按参照/复核合并。新增点状态混淆计数、已判断点的正确率、未知比例；另按“将点状态保持整窗”的假设报告时间一致比例，明确该假设的误差。保存输入字节数、窗口/端点采样量、方法时间及宿主资源。

直接读取就绪和占用计数，本来就应帮助识别对应局部状态；即使点判断完全吻合，也不表示推断出了信用反压、接收端慢或协议拖尾，更不证明具备硬件采集接口。真正需要量化的是相较端口基线的范围收缩、采样漏检以及信息成本。

## 资源与执行边界

只运行上述四次小场景，串行执行；分析阶段复用同一执行，不增加随机样本数。沿用 8 GiB RSS、12 GiB 地址空间、每阶段 1800 秒、共享累计 48 GiB 和 20 GiB 空闲。累计目录见 `common.py`，包括之前发送状态支撑任务的构建与产物。新增四次运行按现有每次 768 MiB 保守预留，共 3 GiB；执行和导出仍受实际共享总上限约束。失败不自动提限、清理旧产物或重跑。完成后记录研究发现及未解决问题，本轮不自动扩展完整场景或新增平台模型。
