# 发送槽 1 与 2 的配对方法

本轮基于[首批结果](results.md)中发送节点的开始前间隔，检查增加端侧发送并发是否改变等待、网络竞争和整轮完成。条件在执行前固定：输入组 0、1、2 全部使用，每 rank 8 请求，共 64 请求；每组单槽、双槽配对。首批单槽结果通过输入、程序和完成摘要核验后可复用，不按结果筛选输入。

唯一变化是 `send_slots_per_rank` 从 1 改为 2，同时写入场景执行配置和层模板。所有请求身份、专家选择、计算成本、消息大小、拓扑、链路、随机种子、原生资源和观测配置不变。worker 数、STORE/LOAD 在途上限、请求标识池分别保持 1、32/32、256。双槽不是增加传输通道，也不改变 LOAD/STORE 的发起及完成语义。

运行前重新解析配置和容量。比较前核对生成的计算及通信依赖图、传输描述和实际工作量相同，并核对平台源码、后端与概览统计实现一致。逐包路径允许随实际时序变化，不强行沿用单槽的包轨迹。仍只运行四块小模型的一次完整 Decode，采用参考计算成本。

## 指标与等待关系

三层概览继续采用[既有口径](overview-method.md)，主要比较整轮时间及其相对变化、同大小同角色任务时延、队列面积及峰值、实际链路占用，以及节点显式依赖满足后的开始前间隔。正向与负向变化均保留；队列面积增长不自动等于整轮退化，平均占用率变化要结合其时长分母。

发送槽占用由各 rank 的 SEND 节点实际 `[start_ns,end_ns)` 区间还原，并与对应传输的提交、发送完成回调核对。零时长同芯片交付不形成正时长占用。同刻事件只给纳秒级区间，不能恢复同一纳秒内部的回调顺序。

对每个 SEND 的 `[dependency_ready_ns,start_ns)` 间隔，计算其中全部发送槽已占用的时长，以及其余时长。前者证明当时没有空槽可用；后者仍只称“有空槽但尚未开始”，不虚构直接调度就绪或受阻原因。每个节点的等待区间可能重叠，累计 node·ns 不作为整轮损失。

每组保存按等待时长排序的前五个节点，并列出占用重叠、最后释放事件及显式前驱，用于核验等待关系。选择规则对六次执行相同，不在看过双槽结果后挑例。跨运行按 rank 与 node_id 配对，保存开始、完成、依赖就绪及等待变化；不能仅凭某个长等待缩短就认定它决定整轮改善。

预先保留三种解释：并发增加使整轮更快且槽满等待减少，支持该资源限制实际推进；局部等待减少但整轮未改善，需继续看依赖链；任务时延或网络积压增加，则记录并发带来的竞争。任何一种情况下，结论均限于这些输入与参考模型，不能直接推断真实硬件。信用、原生在途资源及接收内存服务没有完整状态历史时，不把它们标为已证明的根因。

本轮只交付三对比较、等待证据及下一步取舍。现有资料不足时指出缺项，后续平台记录、其他干预和被动观测比较另行确定范围。
