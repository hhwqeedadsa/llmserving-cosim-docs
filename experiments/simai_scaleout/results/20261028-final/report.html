任务是怎么进入网络的？

真实R1专家选择JSON → SimAI实际Cluster/Orca调度 → 按专家部署生成Dispatch/Combine消息与计算依赖 → ASTRA驱动同一个ns-3网络 → 实际完成事件返回SimAI。

前12个请求在EP256组，每rank每层1个路由专家；后3个请求在EP64组，每rank每层4个专家。共256个路由专家、Top8、hidden 7168，BF16激活，每份专家贡献14,336B。仅观察原层3—4、Decode entry1—2，初始KV状态是声明前提。

前端管理请求、batch和KV资源；后端计算包的路径、链路争用、丢包和恢复时间。没有源token的卡不增加虚假的Attention/pack/merge，收到专家任务时仍执行专家计算。计算采用声明参考值，H100/DeepSeek671B是上游容量配置，未调用计算性能预测器或硬件profile。

本适配按专家贡献复制载荷；同token同目的rank的多专家不做现代通信库的去重，不包含完整DeepEP控制操作。不能将此抽象称为生产通信库复现。

怎样读累计有效到达图？

曲线向上走，表示有更多数据到达。橙线长时间停住，表示部分必要数据仍在恢复；其他消息到齐也不能让整个collective完成。最终有效值是这次g0.w0、原层3、一个Dispatch或Combine的1,376,256B。

发送字节包含重传；物理接收可能包含重复或乱序数据；去重到达表示曾经抵达的不同字节；有效接受按当前Go-Back-N协议只累计连续正确序号；源确认还要等反馈回到发送方。它们可能在不同时间达到目标，有效接受也不等于GPU内存可见。

恢复配置相同：GBN、初始RTO40µs、最大160µs、最多4次重试。事前从输入选跨Pod消息，数据offset9000丢两次，另一消息最终ACK丢一次；这是特定故障功能对照，不能称为50%随机丢包实验。

网络如何影响下一轮任务

每一条是原生网络中的实际图执行区间。g0.w1起点等于g0.w0终点，g1同理；两组共享一个持续存在的网络，但一组故障不会凭空改写另一组依赖。这里没有将两个独立仿真耗时相加。

可以得出什么，还缺什么？

  • 已证明真实选择、前端调度、320端点共享网络和逐包统计能连起来；942条消息和全部有效字节均完成。
  • 本次少量指定丢包即可拖住必要的通信阶段，并将等待反馈到后续批次；这是恢复影响的观测，不是新恢复算法或优化收益。
  • 正常Clos为87.346µs，HPN启发为91.815µs。资源、路径和接入带宽均不同，本实验不支持把差异全部归于拓扑，也没有证明HPN有净收益。
  • 后续网络研究需要更多独立请求/更大真实batch、统一资源预算的拓扑对照，以及对计算、网络参数和通信库语义的校准。当前15文件是用户方便样本，没有生产代表性保证。

PYTHONPATH=python python experiments/simai_scaleout/run.py audit --root runs/my-simai-320
