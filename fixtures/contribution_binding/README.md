# 原专家贡献的实际服务绑定验收

本轮在原有实时事件上，把每个原请求、原始MoE层、Decode入口及目标rank完整专家集合接入ContributionAttempts。输入、聚合专家计算、完整贡献返回、消息源确认和原图退出分别记录。没有插入备用任务、改门限或生成ACK；没有恢复算法收益。

执行源码为`ca9cf6ea8d`；不改依赖或C++，复用已验原生服务。输入是[公开自包含示例](../../examples/scaleout_contribution_tracking/README.md)：128端点Clos、16服务器×8、8ToR/8Agg/4Core、168链路、单rail/plane、各层400G、每链路1us。两个EP64组、E256/Top8、H256、两层两步、每rank每层4专家；四份不同人工请求、31个数据活跃rank，不是满载集群、真实R1或GPU测量。SR是已有字节级功能参考，参考DCQCN不代表商用RoCE校准。

## 方法

新增身份规格`moe-contribution-attempts/2`显式使用`simulation_lineage/1`和原路由入口，不能用路由JSON的hash冒充激活张量hash；没有门控系数/专家权重数值。旧/1规格与独立CLI逐字节兼容。

11项新增CPU检查及45项相关回归，共56项不同检查通过；独立旧CLI五次调用通过。人工回调检查状态机，不预测性能。跟踪预算在后端启动前按实际专家选择核算，每图注册时再检查，输出逐记录限字节；短缺预算的公开`rdma-run`在创建输出目录前拒绝。

正常与局部故障两个新的128端点Clos功能条件各执行一次。后者仅GPU6在[0,20us)丢弃目的DATA，控制保留；没有改变重传或拥塞控制。两次均通过公开`rdma-run/rdma-check`。正常条件只离线比较上一轮保存原件，完整原生网络结果、任务图和事件JSONL一致，没有重跑旧成功网络。

原件目录名`normal`表示正常对照，`local`表示局部短时故障对照；`local`不是本机运行或服务器内部通信。两者使用相同跨服务器Clos、输入和协议，只改变上述局部丢包条件。

`tests/integration/check_contribution_binding.py`从原JSON独立核对请求/层/入口、专家放置和Top-K覆盖，再逐包核对实际发送，逐节点/消息核对输入、计算、结果、源确认和退休时刻；不调用绑定构造器来生成预期。复制运行的公开检查通过，篡改请求身份、漏专家、提前结果、提前资源关闭、漏调用或改退休摘要，六种情况均被拒绝。该程序只读已保存原件，不执行网络。

## 结果

| 指标 | 正常 | GPU6前20us局部接收故障 |
|---|---:|---:|
| token/层调用 | 16，全部覆盖和退休 | 相同 |
| 目标rank贡献包 / 专家贡献 | 32 / 128 | 相同 |
| 绑定生命周期事件 | 380 | 380 |
| ASTRA节点 / 消息 / 布局载荷 | 3708 / 62 / 37696B | 相同 |
| 原生执行事件 | 7669 | 7669 |
| 完整包事件 / 注入丢弃包 | 2120 / 0 | 2126 / 1 |
| 任务完成 / 网络排空 | 103.852 / 103.852us | 175.778 / 175.778us |

例如`g0.w0.l0.r0.s0`：目标rank6的专家输入正常3.058us到达，故障83.058us到达；rank8的输入两次都在5.100us到达。两者的专家节点正常13.134us开始、故障85.060us才开始，体现原图组级Dispatch门限的等待，不能声称故障前已经完成健康专家计算。

同一调用全部贡献正常17.882us到齐，故障89.808us到齐；原图分别51.908us、123.834us退出。rank6的Combine在15.858us/87.784us接收，但源端到17.860us/89.786us才得到确认，相应消息义务只在真实确认时关闭。图引用还须等待原图退出，不把逻辑引用冒充独占物理显存。

关键Dispatch消息2（stream0、0→6）实际源发送为1.030us，故障下下一次为81.030us，每次640B数据；故障在20us结束不代表立即再次发送。本例额外任务时间71.926us是故障代价，尚未测得其中多少可在相同资源和合法通信语义下消除。
