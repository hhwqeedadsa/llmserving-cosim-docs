# 增量操作状态收集

规范见[本轮边界](../../docs/tasks/incremental_progress_spec.md)。`RemoteTransactions`在实际状态改变处登记操作id，session只构造变化行；最终全量报告、网络通知、所有就绪检查、回调顺序/时刻和256次交互上限保持。

默认健康与丢包条件使用同时编译的`MOE_VERIFY_PROGRESS_UPDATES`事务/消费者，每次收集都由全量快照值变化独立核对；正常生产程序没有该影子扫描。默认、开启计时/订阅健康和订阅故障三组完整网络结果/现代快照/原始控制文本与此前对应记录一致，只规范化经hash核对的八库路径。健康/故障完成105,621/123,921ns；新观测健康的1,368次操作行收集exclusive墙钟约0.036秒。后者包含计时开销，不能当生产性能或整机加速比。

原四卡保持全部输入、拓扑和协议，约17.45秒推进至52,700ns/526个现代事件/157项原生登记，实际256次交互后失败；需要566事件，未完成。旧238次控制前缀逐字节保持。新部分result保留`session decision budget exceeded`，不能写成网络死锁、整体成功或用小例替代。物理捕获仍20,000条，另有102,521条遗漏；不能从这份前缀宣称全网逐跳还原。

变更覆盖提交、准备、发布、请求ACK、目标应用、原子回复、自服务起止及前缀退休；多次修改按原id/阶段顺序合并成当前完整行。`Report/OperationProgress`不消费变化集合。`build.py`保存O0原配方并重编事务对象与两个直接消费者，也分别构建影子消费者，避免对象布局混用。固定PersistentStreams/Fabric和八库；编译对象在保存hash后按`prune.py`释放，保留全部可执行程序、源码和精确配方，不清理原始成功或失败。

公开用户流程不变，见[现代入口](../../examples/modern_deepep_native/README.md)。`verify.py`不导入控制器，比较完整结果并调用独立字节/内存/控制审计；`final_checks.py`记录原四卡限制，零提交交互不直接视为冗余。证据见[核验](verification.json)、[失败限制](limitation.json)、[独立恢复](recovery.json)与[资源收尾](closeout.json)。持久原件包存于`runs/incremental_progress_checkpoint_20261025/`；恢复仅限本机Linux ABI兼容环境，不是干净原生构建。

高频观测聚合与长程序控制接口另行改进，不提高本阶段的记录或交互限额。本平台改进不构成A类论文主创新；原完整四卡、现代GPU/provider校准、恢复/公平调度强基线和千卡完整应用仍未完成。
