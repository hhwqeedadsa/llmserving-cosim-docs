# 旧DeepEP完整通信：功能验收

128端点Clos中，EP32/E256完整正常与一次精确通知丢包条件均已完成，并通过独立逐包、DAG、内存和排空核验。另以EP32/E128连续两调用验证跨调用清理与复用。这是旧库功能模型的验收，不是完整推理、现代GIN、GPU性能或新算法收益。

三个条件均为128端点、20交换机、168链路和EP32；网络规模与EP未缩减。原256专家条件每rank8专家、仅4个源rank各1个人工Top8 token；补充128专家条件每rank4专家、每调用4个token。全部零token通知保留；没有把功能流数当成GPU数或把4个人工token当成满载真实请求。

## 已验证的行为

- 完整Dispatch/Combine计划驱动同一持久原生网络。请求目标应用、实际源ACK、原子旧值回复和源退休分别核查。
- 实际源TX、目的RX、包UID/序号/内容、载体解码、全部操作与事件、32位通知及最终内存逐项核验。单条件正常32,464源包，故障32,465源包；两者都交付32,464个唯一包，最终内存hash一致。
- 本地copy/store绕开发送队列，不生成WQE、发布、网络ACK或回复；源返回值仅由远端实际回复填写。
- 同步四条发布与尾通知推动、队列前缀、源捕获寿命、零token计数/标志和物理排空通过。两调用用相同选择复用地址，功能字节随call变化，检查清理后读写。

包核验子摘要的`complete_application_proven=false`仅表示该子检查单独不证明业务完成。顶层验收还要求完整操作、依赖图、内存、源退休和网络排空，不能只引用其中一个字段。

## 故障结果怎样理解

精确故障在2.002µs丢弃stream0/sequence0的一份36B零token通知载体。17µs超时重传，19.002µs交付，21.004µs源确认；目标没有重复应用，最终结果与正常条件一致。载体字节含32B MRT1帧头，不等于36B模型激活或全部线上字节。

该通知在相关接收屏障的最晚前驱之前恢复，因此17µs局部恢复未产生同等的任务延迟。故障与正常总时间相差−41ns，微小差值尚未逐跳归因，不作为故障有益、恢复优化或算法创新的证据。当前是选择性重传已有机制的正确性检查。

## 容量、失败与来源

第一次完整网络在4,237ns触及10,000条参考日志上限。用户明确允许适度提高限额后，将其调整为100,000，其他1800受监控秒/1GiB产物/卷留8GiB及阶段120秒/RSS2GiB/地址4GiB预算保持。正常新条件实际记录48,336条参考事件，其中32,464条源发送。原配置与25MiB失败结果保留，新条件在独立目录执行。

首次失败后还修复了本地队列/反馈字段等问题，新旧二进制不同；不能将旧失败和新成功解释为只有日志上限不同的性能对照。来源、当前源码/后端/加载库hash和原失败身份见核验摘要。失败前报告以展示副本归档，链接已调整；原运行快照未修改。

当前不验证256专家连续两调用，该组合超过32,768操作上限，入口仍整体拒绝。现代DeepEP/GIN、RoCE线协议、GPU可见性/数值专家、真实服务请求与硬件时延校准均不在本次验收范围。真实专家选择研究属于单独实验，不能把其来源套用到本例。

## 不重跑网络的复核

保留本机原件时，可将结果输出到新目录：

```bash
python3 -B tests/integration/summarize_legacy_acceptance.py \
  --root runs/legacy_native_20261030 \
  --output /path/to/new-summary --publish-dir fixtures/legacy_native
```

该脚本绑定三份原生结果、已有独立审计、公开执行清单、授权和源码/输入/二进制/库hash，不启动网络。`audit_legacy_native.py`的独立审计用法见公开示例。大原件仅保存在`runs/legacy_native_20261030/authorized-capacity-100k/`，仓库保存代码、输入及必要摘要；未备份原件的检出仍须按公开操作重新生成运行结果。

以上历史汇总冻结了c35721160c的源码hash，完整重算该旧汇总应检出该提交。后续公开审计迁移改变了源码身份；当前版本可通过`scaleout deepep-audit`直接只读复核保留的原件，迁移等价证据见[公开审计验收](../legacy_public_audit/README.md)，不能为通过旧hash检查改写旧报告。

网页仅完成静态资源检查，不声称浏览器渲染已验收。该平台增量已取得功能证据，整体研究及新算法贡献尚未完成。
