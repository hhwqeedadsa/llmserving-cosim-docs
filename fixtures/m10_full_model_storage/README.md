# M10 全模型合并的存储优化

本步仅调整 `full_model.py` 的对象持有与复制方式。内部构图保留自己创建的子层图；重构校验只读已有子层图，继续逐层验证、重建全部合并节点与传输并逐字段比较。对外直接调用合并器仍复制子层记录。没有删除校验或改变执行计划 schema。

合并头部不再复制马上被替换的首层节点/传输；复制子节点时不先复制即将替换的旧依赖列表。偏移后的节点编号每个只创建一个整数对象，供依赖边引用；依赖列表、节点、传输和来源等可变记录保持独立。身份唯一性检查通过后释放临时集合。合并输入单独复制，避免保留子图后使合并输入与校验依据相互联动。

`RunIdentities`、CANN 生成器、完整重构校验的检查步骤、JSON/Chakra 导出器、C++ 加载器及后端均保持原样。计算和通信的仿真时间不变；这次测量的是 Python 构图占用的现实时间和主机内存。

## 等价性检查

[golden.json](golden.json) 保存修改生产代码前，由 `a828c0a` 生成的四组完整图摘要；对象字段和列表顺序都纳入 SHA-256。包括单 MoE、dense 穿插、无 shared expert、八块模型/32 请求/小分块、不同上下文、零 Token 成员、合成来源以及非默认传输/任务/通信标签。生产校验始终开启，独立语义断言继续运行。

同时检查调用方的配置、模型、费用和来源不被修改，返回图不受后续输入修改影响；对外合并的子图记录有复制隔离；校验成功或拒绝均不修改被检图。层内与合并后的来源、字节范围、收发节点、依赖和阶段费用被篡改时仍拒绝。

新增合成大批次案例最初沿用了小场景的 1 MiB CANN 窗口，被未改的旧校验按 tiling 下界拒绝；仅将该测试输入的显式窗口设为 8 MiB 后保存基线，生产要求未变。原失败日志保留。

实际命令、输入、工作目录、退出状态、阶段与资源采样保存在 `runs/v03-full-model-storage`；原数据没有重新下载或复制。历史预检结果保留。

## 回归与保护结果

24 项单元测试通过。完整模型服务的 8 个对照、空服务和 6 项后端篡改拒绝通过真实 UB 检查；基准仍为 5 轮、305 次写、131279 ns。覆盖多组多轮、共享专家与 sampling 费用、KV 等待、观察窗口、慢网络反馈、来源开关与场景入口。

61 块小 EP 图仍为 3102 节点、754 次 UB 写、986 次交付、315509 ns；穿插 dense 且无 shared 的图为 114 节点、26 次写、34 次交付、10829 ns。小图 C++ 加载和损坏 JSON/Chakra 拒绝通过。四块、61 块、穿插 dense 三组 plan.json、generation.json 和 Chakra 文件共 15 个，与旧产物逐字节一致。

13 个依赖和 1304 个受保护文件摘要未变，C++/构建/启动锁/原来源/首轮 bundle 保留。复用三个二进制的链接仍分别只含各自构建目录的一套 ns-3-UB，无 C++ 重编译。
