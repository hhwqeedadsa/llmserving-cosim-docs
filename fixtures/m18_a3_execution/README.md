## 完成事件的参考映射与限制

源码能确认分核、队列使用、同步位置和状态布局，不能给出目标设备搬运引擎与 UB 网络接口的完整实现。因此下面的连接是显式平台参考关系，不宣称是实测硬件语义：

- 局部数据已被读取：复用现有 `RequestCreated` 事件，按实际有效字节累计到整份复制所需长度。该事件发生在原生请求池成功分配、数据包建立后；池满时不会凭提交调用立即释放缓冲。它不表示数据已经上链路或到达目标。
- 远端数据栅栏：默认等待相应业务数据在目标交付，以保存数据先于状态可消费的关系；与源协议 ACK 返回及资源回收分开。这是对源码搬运同步的保守参考映射，应允许明确声明的替代完成关系用于后续敏感性检查。
- 原生 STORE 事务回收：继续使用原生响应及请求清理后的完成回调；SEND 仍只发起一次，局部事件等待不生成额外网络请求。
- Combine 的某个 Token 可归约，不表示下一层可启动。普通算子继续等待本 rank 必需局部处理及所选算子完成条件。

核数是设备平台输入。目标参考选择须写明依据或参考假设；CANN 的 `GetCoreNumAiv()` 不能单独证明 CM384 某个 die 的实际核数。原生 `ThreadNum`、`StoreOutstanding`、`RequestIdCount`、请求粒度和整包转发也保留为有效网络配置，不把软件复制长度等同于协议请求或线上整包长度。

准备、打包、重排和归约仍采用声明的成本。拆分时逐项记录原工作量、分配到的局部工作和总成本；旧的混合准备成本缺少独立量化测量时，其分配方式属于参考假设，不能说已经获得逐指令或逐核硬件耗时。

## 实现与验收边界

在现有平台模块中新增明确身份的通信模板，不静默改变历史 `fullmesh_v1` 或 `native_v1`。前端构图、C++ 独立重建、Chakra 装载、真实资源占用、事件等待、输出和重放必须一致；不依赖测试脚本执行正常业务。

先完成并行/缓冲、部分到达、共享出口与数据晚准备四类小测试，以及数据/状态数量、字节、成本、回调及资源退出核验。再通过公开命令验证记录不扰动执行和有限连续层段。目标规模保留完整部署、原始层编号及容量核算；本阶段不运行 E 部分的正常业务筛选或完整 61 块研究实验。

关键未校准项为局部复制与协议事件映射、设备核数/资源容量、参考成本、协议粒度及转发方式。已有源码足以推进上述有限参考模型；它不支持声称硬件绝对时延准确，也不支持新增接收内存服务反压或跨算子流水。
