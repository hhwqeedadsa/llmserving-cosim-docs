# 连续解码两步功能输入

two_steps.json 明确给出同一组 A、B、C、D 的两步输入。两步均沿用 M2.1 的专家选择、四 rank 映射、8192 字节单块、一发送槽和固定计算 profile。Token 索引从 9 增到 10；没有读取真实路由或服务调度器。

| 字段 | 第一步 | 第二步 |
|---|---|---|
| graph_id | g.m24.0 | g.m24.1 |
| wave_id | D.w24.0 | D.w24.1 |
| UB task_id / comm_tag | 100～113 | 114～127 |
| transfer_id | 2^32+100～2^32+113 | 2^32+114～2^32+127 |
| UB 写数 / 业务字节 | 14 / 114688 | 14 / 114688 |
| 专家输入份数 | 2、2、3、1 | 2、2、3、1 |

每步两个逻辑操作，共四个 operation_id。四张图的局部 node_id 在第二步复用；实际通信 tag、传输和操作编号不同。Chakra 文件与配套元数据 始终配套生成，不能把两次独立生成且身份重复的计划直接拼成连续运行。

输入中的 ready_ns=0 是固定步骤尚未提交时的值。联合驱动在第一步全部 rank 完成后，于同一 ns-3 时刻装载、登记和激活第二步；运行目录中的第二份计划保存实际 ready_ns。两步共享原 Sys、UbApp、控制器、拓扑、连接状态和仿真时间，不重新初始化网络。

正常结果中，第一步各 rank 完成为 21168、21506、21552、17675 ns；第二步在 21552 ns 提交，各 rank 完成为 42761、43099、43145、39268 ns。两轮耗时不按独立运行的固定值累加。该功能入口仍在 1000000 ns 测试边界退出，并保留较晚事件能执行的检查；此时刻不是图完成时间，也不是 M3 服务退出协议。

交换机 4 的端口 2 连续观测到 36 个包、51678 整包字节，其中业务 49152、数据协议开销 936、控制 1590 字节。每条经过该端口的传输均覆盖完整有效范围，按窗口核对分项守恒。内部操作登记区分两步；observed 端侧局部记录号递增至 4，没有添加 graph_id、transfer_id、请求或 Token 身份。

检查分别运行来源开启、关闭、不挂观测、重复运行及独立故障测试目标。故障目标在第二步运行时注入第一步的一个 COMP、两个 SEND、两个 RECV 旧回调，还覆盖忙时替换、未激活执行、重复激活、已用图身份与末 rank 损坏。十二种坏输入和旧输出覆盖另在启动前拒绝。故障测试使用 ns-3-UB 仿真，并未替换网络完成时刻。

使用方式见 [联合程序说明](https://github.com/baoy21/moe-ub-cosim/blob/e20d42a2bcf0b2ac2529b8641a9492638ffc786f/backend/README.md#m24-连续两张固定图)。本用例只检查固定两步。动态请求与共享瓶颈分别见[服务到达](../m3_dynamic_arrivals/README.md)和[共享网络对照](../m3_shared_bottleneck/README.md)；该用例没有真实路由或硬件校准结论。
