# M3.2 动态到达与独立 EP 组

两个输入均沿用 [M3.1](../m3_service/README.md) 的短请求、显式 Top-2 路由及已就绪 KV 初始条件。单层通信与计算取自 `../m2_single_layer/layer.json`，每个请求执行三步；每个 rank 的真实 Scheduler 保持单请求、单 Token 调度预算。

| 输入 | 到达时刻 | 请求与组 | 验证对象 |
|---|---:|---|---|
| `busy.json` | 0 ns | 101～104，ep0，rank 0～3 | 首批请求执行 |
| `busy.json` | 5200 ns | 201～204，ep0，rank 0～3 | UB 写仍在途时只进入等待队列 |
| `two_groups.json` | 0、5200 ns | 同上 | 忙碌组保留在途图 |
| `two_groups.json` | 5500 ns | 301～304，ep1，rank 4～7 | ep0 仍有在途写时，空闲 ep1 当场提交 |

`busy.json` 使用原 M2 网络。`two_groups.json` 使用本目录 `network/`：八个 NPU，两个四端口交换机 8、9，每组各接一个交换机。带宽 400 Gbps，传播时延 20 ns；其属性文件与 M2 单层输入逐字相同，路由和 TP 表按两个明确的四节点域列出。全部对象仍属于一个 C++ 进程和一次 ns-3 仿真。本输入没有跨组共享端口，不用它推断共享瓶颈效应；该对比属于 M3.3。

服务配置可增加 `groups`，每组明确给出 `group_id`、排序且互异的 `rank_ids`、`rank_to_ub_node` 和八项 `expert_placement`。本步限定一或两个四成员组，成员互不重叠，所有 rank 合计覆盖 0～N-1，rank 与 UB node 使用恒等映射，每个成员放置两个专家。没有 `groups` 时沿用层输入的单组定义。生成的 `deployment.json` 在 C++ 初始化前用于核对组和 NPU 映射，图内的组、放置和通信端点必须与它一致。

M3.2 验收输入要求每组同一到达时刻恰好有四个请求，各成员一个，且剩余步数一致（2～32 步）；当前入口按 [M3.4](../m3_service_boundaries/README.md) 允许稀疏参与、不同到达与 1～32 步。一个运行最多 64 个请求。到达只写入前端的已就绪 KV 待接纳队列 `pending`；当前入口在组空闲且本 rank 旧请求完成并释放容量后，经原 `Scheduler.add_decode()` 接纳下一个，再调用 `schedule()`。`pending` 与上游 `Scheduler.waiting` 分别记录，不能把上游 waiting 为空理解为没有排队。给定 KV 在待接纳阶段不占用目标 Scheduler 的块池；本输入不模拟外部缓存、Prefill、KV 搬运或容量争用。首个 ITL 从本次到达算起（包含排队），后续 ITL 从前一轮完成算起；首次完成前 `latest_completion_ns` 为 null。

基线结果：ep0 首轮 21552 ns 完成，排队批次在 64738 ns 开始，六轮于 129517 ns 完成。ep1 在 5500 ns 开始，三轮分别于 27052、48645、70238 ns 完成。双组共有九轮、126 次真实 UB 写、1032192 业务字节；十二个请求全部结束。

[集成检查](../../tests/integration/check_dynamic_service.py) 还生成全空闲后 9000 ns 到达、100000 ns 未来到达跨越多次图完成、到达与完成同刻、两组同时到达，以及来源开/关/不挂观测/重复执行用例。检查实际收发回调、局部依赖、原始执行日志、端口跟踪和资源回收；忙碌组替换、非法唤醒、部分组提交、重复身份及第二组末 rank 坏图必须失败。

运行入口见 [M3.2 使用说明](../../backend/README.md#m32-动态到达与独立组)。这些结果只验证合成单层功能；零 Token 成员、不均匀请求结束和故障检查见 M3.4，真实数据和校准仍未完成。
