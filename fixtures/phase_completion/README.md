# EP阶段完成依赖：实现与128卡真实路由验收

本轮补上了研究故障长尾前必须明确的阶段依赖。旧逐贡献图允许本rank收到所需数据后就启动专家计算，即使本rank还有Dispatch未确认；它可描述一种接收就绪模型，但不能直接代表固定DeepEP direct调用。该库在Dispatch/Combine结束先flush相关连接，再跨rank发/等屏障信号；异步API也保留计算流事件依赖。

新增显式`ep_transport_flush/1`：同一EP组完成本阶段实际SEND确认、RECV和生产计算后，才能进入专家计算或归并。所有rank仍在同一ASTRA/ns-3时钟执行，没有请求的专家卡也参加门限。缺省继续使用旧模型，旧结果不被改写。

**该模式只是零协调成本的必要依赖下界。** 未模拟GIN控制信号、真实CQ/GPU可见性、token按目的rank去重或现代多context映射。它补齐约束，不是新的通信优化算法，也不是完整现代DeepEP强基线。依赖旧重叠的“Combine已发布但被未完成Dispatch拖住”现象，不能直接作为真实库的可消除收益。

## 128卡的真实输入与结果

输入为用户提供的DeepSeek-R1-AWQ/MMLU专家选择，使用原始层3、4及Decode入口1、2；15个独立请求映射到明确的源rank，不填满128卡。E256、Top8、H7168，EP128，每层每rank两个专家，无专家副本。只回放选择，激活每元素2字节和计算耗时为声明值；H100是描述标签，未运行GPU。初始KV已就绪，不执行Prefill、完整671B模型或完整生成。

网络为单rail/plane的三层Clos：16台服务器×8卡、两个Pod，8个ToR、8个Agg、4个Core，168条链路；各层400Gb/s、每跳1µs，ToR与Agg各4:1下行/上行带宽比。同机流量也经RDMA。804条固定持久连接、参考选择重传和DCQCN；未人工注入故障，未改变恢复预算或控制参数。

实际完成926条消息、13,676,544有效字节，源发送/目标接受与独立原件矩阵一致；66,874条完整包事件、4,924个ASTRA节点通过核验。8个门限、1024次成员到达全部满足“最后成员到达才释放”，各阶段最早消费者均不早于最后源确认。

首层首步Dispatch的尾数据到达10.964µs，尾源确认及门限释放16.970µs，最早专家计算同为16.970µs。这直接验证该模式没有把接收数据就绪误当成传输完成；6.006µs间隔不能自动当作优化空间，也不证明源ACK等同真实CQ。

声明的有限任务窗口在137.377µs完成，网络在151.445µs排空，后续排空14.068µs。**这些不是完整R1推理时延或新算法收益**；仅说明这个固定输入和参考网络能按新增依赖运行。256/512本轮只有离线图检查，没有新增网络结果。

## 使用与复核

公开配置和命令见[稀疏Clos示例](../../examples/scaleout_sparse_clos/README.md#可选的ep阶段传输完成依赖)，完成规则见[平台规范](../../docs/tasks/phase_completion_spec.md)。本轮执行提交为`05f63e9f16`；完整原件、输入、编译和运行命令保存在`runs/phase_completion_20261030/`。

```bash
PYTHONPATH=python python fixtures/phase_completion/prepare.py \
  --inputs /path/to/source-checked-real-inputs \
  --topologies /path/to/prepared-clos-topologies \
  --output /path/to/new/phase-inputs

PYTHONPATH=python python fixtures/phase_completion/verify.py \
  --root runs/phase_completion_20261030 --output /path/to/new/verification.json
```

准备程序针对上一轮已验证的输入目录约定：`inputs`包含三档`service{卡数}.json/rdma{卡数}.json`，`topologies`包含`clos{卡数}/topology/topology.json`。它重验原件及固定来源、保存输入与计划，不运行网络。独立核验程序从实际运行内快照重读原始JSON，重算全部贡献矩阵，并直接比较消息接收/源确认、ASTRA gate issue/callback与后续计算时刻；不导入构图函数，也不重跑仿真。

结果摘要见[verification.json](verification.json)，实际命令、资源、旧构建不变及源码绑定见[receipt.json](receipt.json)。受限原始路由、包和二进制不进入Git。

增量编译只重编服务对象并链接现有固定对象/库，新二进制放在独立任务目录。原7个程序与8个库的SHA全部保持；不代表冷环境完整构建验收。首次准备构建命令时PATH没有ninja，尚未启动编译就失败；保留失败后读取既有CMakeCache的ninja路径，完成唯一一次实际增量编译。没有下载、安装、依赖修改、网络重跑或自动扩限。

## 后续研究怎样继续

后续仍限定128/256/512卡Clos。先固定真实专家选择、部署、上述完成语义及其近似，设计两个确实共享上行的EP组，再比较正常和局部短时受损条件，逐包追踪健康组的关键消息、排队和源端等待。进一步检验去重、控制信号及多连接强基线对现象的影响；只有较强基线下仍有明显业务损失且能定位原因，才进入新方法和收益评估。
