# 恢复请求未实际发送的终态诊断

2026-10-30完成。目的：解释固定合成incast中多次恢复请求却无源数据TX的现象，避免把计时器决策当作实际重传。输入沿用[交换机丢弃观察小例](../../examples/scaleout_switch_drops/README.md)，只增加 `recovery.terminal_snapshot=true`，没有改变RTO、重试数、请求、路由、消息字节或网络。

## 已经定位到什么

失败消息4的发送节奏门限晚于重试耗尽。终态实际QP速率为100Mb/s，最后模型包9036B，其序列化节奏间隔为：

`9036 × 8 / 100000000 = 722.880µs`

| 事件 | 仿真时刻µs | 含义 |
|---|---:|---|
| 最后一次源数据TX | 187.792 | 完整源端包记录中的实际发送 |
| 最后一次ACK进展 | 261.088 | 累计确认推进到126000B |
| 后续恢复请求 | 301.088、381.088、541.088、701.088 | 源游标回退并触发原生发送调度；没有实际源数据TX |
| 重试耗尽 | 861.088 | 整个共享仿真失败停止，未完成业务 |
| 下次允许发送的节奏门限 | 910.672 | 终态QP读取值；仿真未执行到该时刻，不表示届时一定发包 |

`187.792 + 722.880 = 910.672µs`，比失败停止晚49.584µs。失败时 `snd_nxt=snd_una=126000B`，当前游标后剩136144B，窗口配置0、`window_blocked=false`。源端PFC暂停/恢复各6次，最后PFC RX为66.349µs；但终态快照不保存完整PFC/NIC状态，不据此单独宣称所有暂停因果已排除。

这说明在当前显式参考配置下，恢复尚未通过限速门限，超时预算已耗尽。源码中 `RdmaRecovery::Fire`只请求恢复并保留原生调度；`RdmaEgressQueue::GetNextQindex`检查 `m_nextAvail`，`RdmaHw::UpdateNextAvail`按实际速率计算该门限。发送窗口和游标回退不能绕过限速。

**49.584µs不是优化收益。** 即使允许继续运行，仍需传输、确认并完成其余工作。本轮没有增加重试预算或延长超时来制造成功，也没有证明这是硬件或真实RDMA协议的缺陷。实际100Mb/s是锁定模型在本条件中的QP速率；PFC、ECN和DCQCN的参数均未经生产网卡校准。

## 实现与验证

新增可选 `recovery.terminal_snapshot`，默认关闭；C++只在最终Report读源QP，不新增仿真事件、不改变包或恢复状态。QP已经清理时只保存 `qp_present=false`。公开 `rdma-diagnose`核对时间、QP身份、速率、游标与窗口后导出同一观察。配置、命令和字段见[恢复示例](../../examples/scaleout_rdma_recovery/README.md)。该字段适用于逐消息GBN；持久SR的源速率采集是独立接口。

| 验证 | 结果 |
|---|---|
| 一次针对缺失终态的实际采集 | 保留原失败，7消息仅2完成，861088ns停止 |
| 与旧完整结果对照 | 删除明确新增的观察字段后，所有旧仿真字段相同；加载库按路径及次数核对 |
| 交换机与逐包事实 | 28次入口拒绝、6830条包记录，与原件一致 |
| 公开失败诊断 | 命令成功，原任务仍标失败；导出7个源状态快照 |
| 相关CPU检查 | 192项通过；包含非法输入、终态篡改、默认关闭兼容和服务分析回归 |
| 构建 | 一次增量编译并重链接6个native程序，8个ns-3库hash不变，无依赖升级 |

首个完整CPU回归因OpenBLAS初始化内存分配失败中断；保持相同512MiB RSS/1GiB地址限额，仅对检查进程设置 `OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1`后完成。原失败保留，不影响实际网络或随机状态。没有重跑旧成功服务或新的320卡实验。

原件在本机 `runs/recovery_terminal_snapshot_20261030`。[verification.json](verification.json)保存机器摘要，[evidence.json](evidence.json)绑定源码、构建、程序、库、配置及监控记录。[离线检查程序](../../tests/integration/check_recovery_terminal_snapshot.py)只读两份结果，不执行网络。

## 对后续研究的影响

旧逐消息GBN在这个配置中发生失败，不足以证明MoE方法能比成熟通信系统更快。后续对照应使用已接入的持久GBN/SR、相同连接与拥塞控制，检查恢复决策能否实际获得发送机会，并分别统计恢复请求、实际重传、有效接受和任务完成；有限重试下的失败单独报告。只有在成熟恢复配置和正常场景代价都明确后，才能评价减少恢复干扰的方法是否有额外收益。
