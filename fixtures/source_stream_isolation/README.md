# 源端单向流失败隔离

平台基线 `7d5d468`，规范见 [source_stream_isolation_spec.md](../../docs/tasks/source_stream_isolation_spec.md)。公开输入与字段见 [持久恢复](../../examples/scaleout_rdma_streams/README.md#可选的持久连接丢包恢复)。默认不变；显式 `isolate_stream` 只冻结本地失败源，保留在途写、队列信用和未完成租约。

验收原件位于 `/dev/shm/moe-source-isolation-20261024/`。`build.py` 复用已固定的本机构建收据，分别构建五个类布局消费者与三个入口，未改依赖；用户正常构建使用公开 `scaleout rdma-build`。`run.py` 检查默认完整结果字节一致、延后健康工作、自身恢复、双失败、迟到ACK、请求/响应源失败及CLI/native非法输入；`edges.py` 检查终态独立CNP、v5源租约与在线正常恢复；`online_failure.py` 验证真实在线回调下健康工作完成；`shared_source.py` 检查同一NIC的健康QP，以及失败回复源后来收到的新请求仍实际应用、生成的回复冻结。

初版实现曾在故障源的新工作就绪时抛异常，连带停止其他流。`late-submit-before/`保留原件及初版stream二进制，`late-submit-after/`验证修正为有界入队、未发布、未ACK，而健康工作完成。失败源队列不丢弃已有未确认项，迟到反馈不释放其资源。

独立 `audit.py` 只用标准库，重建实际源TX/端点RX/丢包、源端失败后无新TX、实际迟到ACK/NACK/CNP、MRT1帧、目标内存和源租约。物理乱序RX不当成接收交付；同一NIC的ACK按真实端口区分，不按GPU整体判失败。13个故障条件核对132个源包、39个迟到反馈、13次目标副作用，并拒绝删除反馈、篡改确认前缀和篡改目标内容三类产物。

原stream/事务/在线/前缀流程分别7/8/3/32条公开命令，以及准备顺序反例与安全对照通过；13个固定依赖核查通过。此轮没有执行完整模型、GPU、生产热点或千卡压力任务。

这些是传输和资源语义的功能证据。局部流继续不代表一次MoE请求已经完成，也不表示失败通知可撤回旧写。尚无重连、错误回调、失败源资源回收、GPU可见性或匹配硬件校准。局部隔离本身不是论文新算法；后续研究须在完整专家依赖下证明安全保留工作优于已有恢复基线。
