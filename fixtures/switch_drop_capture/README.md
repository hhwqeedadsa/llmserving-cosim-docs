# 原生交换机丢弃观察验收

2026-10-30的平台增量用于解释丢弃原因，不是新拥塞控制或恢复算法。[公开输入生成器](../../examples/scaleout_switch_drops/prepare.py)不依赖私有数据；[测试驱动](../../tests/integration/check_switch_drop_capture.py)仅调用公开CLI。完整原件和旧程序保存在本机 `runs/switch_drop_capture_20261030`，本目录保留必要摘要。

| 检查 | 实际结果 |
|---|---|
| 固定incast观察关闭/开启，各一次 | 8端点、7消息、计划1835008B；两次原有native字段完全相同，包括失败、包、队列和资源状态 |
| 模型内自然准入丢弃 | 28次入口拒绝；交换机10/14/16分别9/17/2次；没有配置人工故障 |
| 独立逐包核算 | 840次交换机数据RX = 812次入队 + 28次丢弃；6830条包事件和28条原因记录均完整 |
| 失败状态 | 只完成2/7消息；861088ns因消息4无进展重试耗尽停止，不是成功完成时间 |
| LLMServingSim→ASTRA→持久SR服务 | 4端点、50消息成功，native终态67668ns；全部仿真字段与旧正常结果相同，没有交换机丢弃 |
| 新旧服务加载库 | 路径及出现次数相同，重链接改变枚举顺序；原始列表保留，库内容由构建收据绑定 |
| 实际SwitchNode分支 | 入口拒绝、无路由、链路关闭通过；拒绝不增加MMU/队列占用，旧QbbDrop通知保持 |

分支检查显式预置满缓冲；实际incast没有预置MMU状态，两者分开。incast的1MiB缓冲、头部空间、链路与RTO为功能参考，模型内自然丢弃不证明生产发生率。丢弃在72131—259229ns，共252000B载荷，包含发送尝试，不能作为唯一业务损失或端到端丢包率。

失败消息4最后确认进展为261088ns；此后301088/381088/541088/701088ns触发4次恢复请求，却没有实际源数据TX，最后一次源数据TX为187792ns。`recovery.timeout_retransmissions`是源计时器恢复请求计数，不能直接当作实际重传包数量。发送节奏/PFC的具体阻塞原因仍需单独核查，不能仅从超时和丢弃次数推断。相关时序来自已保存的完整包记录，未新增网络条件。

首个公开probe失败后原件保留，只续验未执行的开启观察与服务条件。服务旧记录比较首次因动态库排列顺序未通过；逐项检查确认全部仿真字段相同、加载路径多重集相同后，仅重做离线分析，没有重跑网络。显式 `--resume`核对已登记命令及终态，不重试它们。

新增被动回调不调用队列操作、PacketEvent、在途修改或排空调度，开关对照核验其实际行为。原生类布局变化，因此service/probe与既有stream/RC/transaction/session目标全部重编译；旧完整output保留，新收据绑定7个程序、8个ns-3库与源码。只增加固定依赖的项目补丁，没有升级上游、下载或安装。

最终190项相关CPU检查通过，覆盖Scale-Out配置与分析、SimAI服务、持久服务核验和终态时间；原生分支检查独立通过。它们不证明硬件准确性或研究收益。

本轮没有新320卡真实R1实验，也没有GBN/SR性能收益对照。SR小例是功能证据，incast失败是恢复边界证据；后续须固定真实路由、连接、拥塞控制和网络资源，区分丢失、ACK迟到与低速发送造成的无进展，再评价MoE优化。
