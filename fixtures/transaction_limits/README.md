# 事务执行额度的功能验收

目标是在同一原生时钟、持久连接和真实MRT1请求/回复上容纳超过旧8/32/16限制的程序。只扩展平台执行容量，不提出新恢复算法或现代GIN时延结论。基线`fd3b714`，输入与独立限制见[规范](../../docs/tasks/transaction_limits_spec.md)；普通使用见[公开示例](../../examples/scaleout_rdma_transactions/README.md#配置较多连接与较长程序)。

`prepare.py`产生四GPU标签0/1/4/5的12向连接、96个源窗口写和20个本地copy，以及单连接64个fetch-add。后者在字节序号1280（第33项请求）实际丢弃一次，仍须逐项返回正确旧值、最终累加2080，不能用补记完成代替网络回复。所有声明10ns本地时长只为功能验证。

`build.py`只增量编译三个事务消费者，复用固定八库、Fabric静态库和已验证的SR载体对象；后者ABI与更早载体不同，不能任意替换。`build_reference.py`从基线Git提交读取原始消费者，以同一载体/库构建默认行为参考。两者都不是从零依赖构建。

`online.py`先接受40项，随后构造累计超额候选，核对拒绝不改变配置、待决事件、序号或控制记录，再以合法批次完成96远端/20本地；完成后第21项本地工作仍被拒绝，合法finish可继续。直接绕过Python的native候选也须在全部状态改变前拒绝。

`audit.py`仅使用标准库，独立构造线格式、解码实际源payload，核对物理源/目标NIC、累计接收/ACK与实际回复，再重放最终窗口、本地copy及队列回收。`checks.py`运行三组审计、六类篡改敏感性、Python输入回归及23类native准入拒绝。目标事件只供评价，不提供给调度算法。

首轮遗漏原来48个源读保护记录上限，0ns准入48项后失败，同步发送回调已发两帧；修复其与显式总节点额度的派生关系，保留原始失败及第一版二进制/对象。另保留漏填显式恢复的CLI输入拒绝、错误的零包断言和检查器对可选NIC字段/回复默认地址的错误，不为修检查器重跑成功网络。

预算为600累计受监控秒/256MiB新增存储（含恢复与持久副本），每命令60秒/RSS1GiB/地址2GiB/新产物64MiB，网络5ms/result16MiB，最多8次实际执行，含首轮失败和新目录公开流程。取消独立健康长序列网络以保留此额度。历史旧二进制加载更早库，虽业务结果一致，不能作为同库严格对照；预算内最后一次执行使用新目录中的基线参考二进制，核验修改前后默认完整结果，仅规范化已验证相同的八库路径。

运行目录`/dev/shm/moe-transaction-limits-20261024/`保存命令、cwd、退出状态、输入、部分失败和原始监控；持久检查点位于`runs/transaction_limits_checkpoint_20261024/`。`checkpoint.py`对所有成员先验证路径、类型、范围、成员关系和hash再写入新目录。`replay.py --execute-reference-once`会消耗预先登记的最后一次实际网络；默认只核查已有输出，不自动追加网络。具体结果和资源终态见本目录`verification.json`、`recovery.json`、`closeout.json`。

现代DeepEP的self-peer、真实GPU可见性和provider事件仍未接通；GPU标签不表示执行对应显卡，没有千卡、完整MoE推理或校准证据。容量扩展用于下一步正确接入完整应用，不能作为论文主贡献。
