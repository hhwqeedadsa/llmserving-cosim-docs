# 完整片段副本与结果提交验收

本轮补齐“一个完整尝试已完成，逻辑结果可以提交，但另一尝试仍须收尾”的平台能力。立即执行两个完整副本是成熟的冗余基线，不是新恢复算法。实现与网络执行固定于`d926723d29`，复用原生服务二进制，没有重新编译或修改依赖。

先看[结果网页](report.html)，接口与限制见[完整片段副本](../../docs/whole_call.md)，可复制的准备及运行命令见[公开示例](../../examples/scaleout_whole_call/README.md)。

## 实际输入与条件

- 128个模拟GPU端点的Clos，16台服务器；8个接入、8个汇聚、4个核心交换机。单平面、单rail，各层400Gbps，每条链路1µs；本轮不是GPU测量。
- 两个互斥EP64组，各组预先持有256专家的完整副本，每rank每层4专家。源rank为0/2/4/6，对应副本rank为1/3/5/7；专家计算仍可发生在其他rank。
- 用户提供的真实R1-AWQ/MMLU路由1472、1808、2675、6447，按既有固定manifest核对原路径与SHA；只取原层3/4和一个Decode入口。4个逻辑请求、8次显式执行、1个批次片段调用，不称8份独立数据。实际数据活跃rank为70，不称128卡满载。
- 两条件使用相同路由、任务图、物理部署、选择性重传（SR）及参考DCQCN拥塞控制。`normal`不额外注入故障；`local`只在`[0,20µs)`丢弃发往GPU28的DATA，不丢控制包，不模拟整机宕机。
- 两份完整权重和等价ready-KV是显式初态声明，未验证数值等价或模拟建立成本；仅执行有限MoE片段，不模拟完整671B请求、客户端张量交付或后续请求调度。

## 结果

| 条件 | 完整赢家 | 逻辑结果就绪 | 原尝试完成 | 副本完成 | 服务/网络排空 |
|---|---|---:|---:|---:|---:|
| normal | 原尝试 | 67.594µs | 67.594µs | 68.863µs | 117.091µs |
| local | 副本 | 64.659µs | 136.829µs | 64.659µs | 136.829µs |

每条件244条实际消息、2280个ASTRA节点、8个阶段门限和512次成员到达。正常/故障分别16780/16434条完整包事件，无截断；两份尝试各1,760,704B有效负载。计划流量及声明计算均执行两份；累计计算工作量不能当作任务耗时。

故障窗口内6/6个目标DATA丢弃；目标端整个观察期共14个DATA到达，不是全网100%丢包。源数据包488→494，实际发送负载3,521,408→3,564,800B，额外43,392B。故障中较晚尝试仍在结果就绪后运行72.170µs，所有接收、ACK、计算、门限及KV释放继续按实际执行退出，没有伪造原任务完成。

正常组在两份尝试均结束后仍有CNP拥塞通知，最后CNP于117.091µs到达；这解释了排空晚于尝试完成，不能将尾部全部计为推理网络等待。故障最后ACK为136.799µs，图退休及服务退出为136.829µs。

## 研究判断

这一轮证明的是完整结果消费者和后台退出语义可以工作。它尚未证明相对无副本SR或成熟延迟备用的净收益。

健康副本首层Dispatch门限在两条件都为18.022µs，之后才分化；ECN标记接收20→7，CNP接收20→7，最终68.863→64.659µs。它与受损组暂缓推进、共享竞争改变相符，但没有独立因果对照，不能据此说丢包有利。两组最快结果差2.935µs，不能解释为创新收益。

下一项研究应在相同128端点、相同原始请求、SR参数与资源约束下，比较无冗余、立即副本、成熟延迟备用，分别核算正常开销、故障尾时延、重复字节、计算/KV占用与其他任务的影响。不能以同一次运行内72.170µs的首尾间隔作为收益空间。没有强基线之外的可重复收益时，应保留负面结论，不削弱基线制造创新。

## 检查与证据

45项不同CPU检查通过，包含10项新增完整副本检查。首次测试误写原专家选择期望，按原JSON修正测试；失败命令与日志仍保留，不改原件或恢复参数。

正常/局部故障各执行一次，没有成功网络重跑。独立检查从四个原JSON重算逐层token-rank矩阵、BF16传输字节与完整图；核对全部节点前驱和时长、全部门限64成员、消息接收及ACK、原始OBSERVE帧、完整赢家和生命周期。另将逐源发送记录与原生设备TX逐包匹配，按连接字节区间核对唯一有效负载及接收前缀，重复重传单列。
